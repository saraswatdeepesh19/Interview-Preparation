# Idempotency for safe retries

---

## 🟢 Junior Level

An operation is **idempotent** if doing it once or many times has the **same effect**. Retries are only safe for idempotent operations: when a request times out, you don't know whether the server processed it — retrying a non-idempotent "charge the card" can charge twice.

| HTTP method | Idempotent by spec? | Why |
| --- | --- | --- |
| GET, HEAD, OPTIONS | Yes | Read-only |
| PUT | Yes | Full replacement: same body → same final state |
| DELETE | Yes | Deleting twice leaves it deleted (second call may return 404) |
| POST | **No** | Creates something new each time |
| PATCH | Not necessarily | `{"op":"increment"}` isn't, `{"status":"PAID"}` is |

### The idempotency key
For non-idempotent operations, the client generates a unique key per **logical operation** and sends it with every attempt. The server remembers keys it has processed and returns the stored result instead of executing again.

```http
POST /v1/payments HTTP/1.1
Idempotency-Key: 8f14e45f-ceea-4b1e-9b9e-5d1e7d3e9c21
Content-Type: application/json

{"orderId": "o-42", "amount": "49.90", "currency": "EUR"}
```

## 🟡 Middle Level

### Server-side implementation

```sql
create table idempotency_keys (
    key           text primary key,
    request_hash  text not null,            -- detect key reuse with a different body
    status        text not null,            -- IN_PROGRESS | COMPLETED
    response_code int,
    response_body jsonb,
    created_at    timestamptz not null default now()
);
```

```java
@Transactional
public PaymentResponse pay(String key, PaymentRequest req) {
    String hash = sha256(canonicalJson(req));
    int inserted = jdbc.update("""
            insert into idempotency_keys(key, request_hash, status) values (?, ?, 'IN_PROGRESS')
            on conflict (key) do nothing
            """, key, hash);

    if (inserted == 0) {                                     // seen before
        IdemRecord rec = loadForUpdate(key);                 // select ... for update
        if (!rec.requestHash().equals(hash)) throw new IdempotencyKeyReuseException(key);   // 422
        if (rec.status().equals("IN_PROGRESS")) throw new RequestInProgressException(key);  // 409, retry later
        return rec.storedResponse();                         // replay the original result
    }

    PaymentResponse res = gateway.charge(req, key);          // pass the key downstream too
    jdbc.update("update idempotency_keys set status='COMPLETED', response_code=201, response_body=?::jsonb where key=?",
                toJson(res), key);
    return res;
}
```

Key details:
* **Atomic claim** of the key (`insert ... on conflict do nothing` or a unique constraint) — two concurrent retries must not both execute.
* **Request fingerprint** — reusing a key with a different payload is a client bug; reject it.
* **Replay the stored response**, including the status code, so the client can't tell a retry from the first call.
* **Expiry** — keep keys for a defined window (e.g. 24 h–7 days), then delete.

### Natural idempotency
Often you don't need a separate table:
* Upserts with a natural key: `insert ... on conflict (order_id) do nothing`.
* Conditional updates: `update orders set status='PAID' where id=? and status='PENDING'` — a retry updates 0 rows.
* Optimistic locking (`@Version`) or `If-Match` ETags for PUT/PATCH.

## 🔴 Senior Level

### Idempotency across a distributed flow
A payment flow touches your DB, a payment provider, and a message broker. Each hop needs its own guarantee:
1. **Client → API**: idempotency key (as above).
2. **API → payment provider**: forward a derived key (`Idempotency-Key: pay-<orderId>`); providers like Stripe and Adyen deduplicate on it.
3. **API → broker**: transactional outbox so the event is published once per committed state change.
4. **Broker → consumers**: at-least-once delivery means duplicates *will* arrive; consumers deduplicate with an inbox table (`processed_messages(message_id primary key)`) in the same transaction as their side effect.

### The tricky window: crash after side effect, before recording
If the process crashes after `gateway.charge` succeeded but before marking the key `COMPLETED`, the key stays `IN_PROGRESS`. Options:
* Make the downstream call itself idempotent with the same key — on retry, the provider returns the original charge and you complete the record.
* A recovery job that re-checks `IN_PROGRESS` keys older than N minutes against the downstream (query by key/reference) and resolves them.
* Never hold a DB transaction open across the remote call in high-throughput systems; split into: claim key (commit) → call → record result (commit).

### Retries must be designed together with idempotency
* Retry only on transient failures; a `422` with a validation error must not be retried.
* Use the **same key** for all attempts of a logical operation — generating a new key per retry defeats the purpose (a common bug in retry interceptors).
* Respect `409 Request in progress` with backoff.
* Document key semantics in the API (scope per account? TTL? which endpoints?).

### Scale considerations
* Key storage can live in Redis (`SET key value NX PX 86400000`) for speed, but then the claim and the business write aren't in one transaction — accept that or keep keys in the same database as the business data.
* Partition/cleanup: index on `created_at`, delete in batches, or use time-partitioned tables.
* Return a header like `Idempotent-Replayed: true` on replays to aid debugging.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Retries are only safe if operations are idempotent. GET/PUT/DELETE are idempotent by definition; for POST I require an idempotency key, atomically claim it, store the request fingerprint and the response, and replay the response on retries. Across a distributed flow, I forward keys downstream, use an outbox for publishing and an inbox for consuming, and handle the crash-in-the-middle window.

**Must know:**
* Idempotent HTTP methods; POST and some PATCHes aren't.
* Idempotency-Key: atomic claim, fingerprint, stored response, TTL.
* Natural idempotency: upserts, conditional updates, versions.
* Same key across all retry attempts.
* Inbox pattern for at-least-once consumers.

**Common follow-ups:**
* What if two retries arrive concurrently?
* What if the server crashes mid-operation?
* Redis or database for key storage?

**Red flags:** retrying POSTs without keys; a new key per attempt; "exactly-once delivery solves it".
