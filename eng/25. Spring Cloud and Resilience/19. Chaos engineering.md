# Chaos engineering

---

## 🟢 Junior Level

**Chaos engineering** is the practice of **deliberately injecting failures** into a system — in a controlled way — to discover weaknesses before they cause real outages. Netflix popularized it with **Chaos Monkey**, which randomly terminated production instances to make sure services survived it.

It is *not* random destruction. It is a scientific experiment:

1. Define the **steady state** — measurable normal behavior (e.g. checkout success rate ≥ 99.5%, p99 latency < 800 ms).
2. Form a **hypothesis** — "if one payment pod dies, checkout success stays ≥ 99.5%".
3. **Inject** a realistic failure — kill a pod, add 500 ms latency, drop 10% of packets.
4. **Observe** whether the steady state holds.
5. **Fix** what broke and repeat.

### Typical failures to inject
* Instance/pod termination, node drain, zone outage.
* Latency and packet loss between services.
* Dependency errors (HTTP 500, database failover, broker restart).
* Resource exhaustion (CPU, memory, disk full, file descriptors).
* Clock skew, DNS failure, expired certificates.

## 🟡 Middle Level

### Tools

| Level | Tools |
| --- | --- |
| Application (in-process) | Chaos Monkey for Spring Boot (latency/exceptions in `@Service`/`@Repository` calls), WireMock/Toxiproxy faults in tests |
| Network | Toxiproxy, `tc netem`, Istio fault injection (`fault.delay`, `fault.abort`) |
| Kubernetes | Chaos Mesh, LitmusChaos, kube-monkey |
| Cloud | AWS Fault Injection Service (FIS), Azure Chaos Studio, Gremlin |

### Istio fault injection

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: inventory }
spec:
  hosts: [ inventory ]
  http:
    - match: [ { headers: { x-chaos: { exact: "true" } } } ]   # only for tagged test traffic
      fault:
        delay: { percentage: { value: 50 }, fixedDelay: 2s }
        abort: { percentage: { value: 10 }, httpStatus: 503 }
      route: [ { destination: { host: inventory } } ]
    - route: [ { destination: { host: inventory } } ]
```

### Chaos Monkey for Spring Boot

```yaml
spring:
  profiles:
    active: chaos-monkey
chaos:
  monkey:
    enabled: true
    watcher:
      service: true
      repository: true
    assaults:
      level: 5                 # attack every 5th request
      latency-active: true
      latency-range-start: 1000
      latency-range-end: 3000
      exceptions-active: true
```

Good for verifying timeouts, circuit breakers and fallbacks in a staging environment.

## 🔴 Senior Level

### Running experiments safely
* **Start small and in non-production**: staging game days with realistic load (replay or synthetic traffic), then production with a minimal **blast radius** (one pod, 1% of traffic, one AZ, tagged test users).
* **Abort conditions**: automatic stop if SLO burn rate or error rate crosses a threshold (AWS FIS stop conditions on CloudWatch alarms; Chaos Mesh with workflows and status checks).
* **Communication**: announce windows, have on-call aware, and a rollback plan.
* **Observability first**: if you can't see the impact on SLIs, you're not ready for chaos.

### Experiments that find real bugs
* **Kill the leader** of something (scheduler with ShedLock, Kafka consumer group member) — does work resume once, not twice?
* **Database failover** (RDS Multi-AZ, Patroni switchover) — do connection pools recover? HikariCP keeps dead connections until validation; `maxLifetime` and TCP keepalive settings decide recovery time. DNS caching in the JVM (`networkaddress.cache.ttl`) can keep pointing to the old primary.
* **Slow dependency**, not dead dependency — the most dangerous mode: threads pile up, pools exhaust, retries amplify. Verify timeouts and bulkheads, not just circuit breakers.
* **Zone loss** — is capacity in the remaining zones enough (N+1 planning)? Do pods reschedule within the PodDisruptionBudget and topology spread constraints?
* **Certificate/secret expiry** simulated in staging.
* **Broker outage** — do producers buffer, block, or drop? Does the outbox recover without duplicates?

### From experiments to culture
* **Game days**: scheduled, cross-team exercises simulating incidents, including the human response (paging, runbooks, communication).
* **Continuous chaos**: low-intensity automated experiments in CI/CD or production (pod kills during business hours) so resilience regressions surface quickly.
* Feed findings into backlog with owners; track "experiments run" and "issues found/fixed" as resilience indicators.
* Pair with **resilience requirements** in design reviews ("what happens when X is slow?") — chaos validates designs, it doesn't replace them.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Chaos engineering runs controlled experiments that inject realistic failures — pod kills, latency, errors, zone loss — to verify a hypothesis about steady-state behavior measured by SLIs. I start in staging with small blast radius and automatic abort conditions, use tools like Chaos Mesh, Istio fault injection, Toxiproxy or AWS FIS, and focus on slow dependencies, failovers and leader loss, which reveal the real bugs.

**Must know:**
* Steady state → hypothesis → inject → observe → fix.
* Blast radius, abort conditions, observability prerequisite.
* Tools at app, network, Kubernetes and cloud levels.
* Slow is worse than dead; failover and DNS/pool recovery.
* Game days and continuous chaos.

**Common follow-ups:**
* Would you run chaos in production? How?
* What experiment would you run first on our system?
* How do you measure the result?

**Red flags:** chaos without monitoring; random destruction without hypotheses; only testing instance kills.
