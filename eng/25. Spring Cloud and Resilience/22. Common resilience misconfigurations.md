# Common resilience misconfigurations

---

## 🟢 Junior Level

Resilience patterns only help when configured correctly. Misconfigured, they **cause** outages. The most common mistakes:

1. **No timeouts** (or default infinite / 30 s timeouts).
2. **Retrying non-idempotent operations** (double charges, duplicate orders).
3. **Retries at every layer** (retry storms).
4. **Fallbacks that hide failures** (returning empty lists that look like "no data").
5. **Annotations that silently do nothing** (`@CircuitBreaker` on a private method or a self-call).

### The silent annotation problem

```java
@Service
class PriceService {
    public Price price(String sku) {
        return fetch(sku);                    // self-invocation: bypasses the Spring proxy
    }

    @CircuitBreaker(name = "pricing", fallbackMethod = "cached")   // never applied!
    Price fetch(String sku) { return client.get(sku); }

    Price cached(String sku, Throwable t) { return cache.get(sku); }
}
```

Resilience4j annotations work through Spring AOP proxies — just like `@Transactional`. Self-calls, `private`/`final` methods, and objects not managed by Spring are not intercepted. Put the annotated method on a separate bean, or use the programmatic API.

## 🟡 Middle Level

### More real-world misconfigurations

**Fallback signature mismatch** — the fallback must have the same parameters plus a `Throwable` (or specific exception type) and the same return type; otherwise startup or runtime fails with `NoSuchMethodException`, or a narrower exception type means the fallback isn't used for others.

**Retrying on everything**

```yaml
resilience4j.retry.instances.orders:
  max-attempts: 5
  # no retry-exceptions / ignore-exceptions => retries 400 Bad Request and validation errors too
```

Define `retry-exceptions` (or a `retry-exception-predicate`) for transient errors only, and `ignore-exceptions` for business exceptions.

**Timeout on the wrong layer** — a `TimeLimiter` around a synchronous call doesn't stop the underlying HTTP request; it just stops *waiting* while the thread keeps blocking (and the pool fills). Configure connect/read timeouts on the HTTP client itself; `TimeLimiter` is for async `CompletionStage`s.

**Circuit breaker that never trips** — count-based window of 100 with `minimum-number-of-calls: 100` on an endpoint that gets 10 calls per minute, or slow calls not counted. Conversely, a breaker that trips at startup because `minimum-number-of-calls` is 1.

**Bulkhead with a queue** — `ThreadPoolBulkhead` with a large `queue-capacity` turns overload into latency instead of fast rejection.

**One shared instance for all dependencies** — `@CircuitBreaker(name = "default")` on every client: one failing dependency opens the breaker for all.

## 🔴 Senior Level

### Misconfigurations that create cascading failures
* **Inverted timeouts** — the caller's timeout is shorter than the callee's processing timeout: the caller retries while the callee is still working; work is duplicated and load doubles.
* **Retry multiplication** — gateway, service mesh, Feign/RestClient retryer and Resilience4j all retrying: 3 × 3 × 3 = 27 calls. Audit every layer (Spring Cloud OpenFeign's `Retryer`, Spring Retry `@Retryable`, mesh `retries`, client SDK retries like the AWS SDK's default 3 attempts).
* **Retries without jitter** — synchronized retry waves after a dependency hiccup.
* **Health checks including dependencies** — mass restarts when a dependency blips.
* **Fallback calling the same failing dependency** (or another overloaded one), multiplying load.
* **Caching errors**: a cached fallback or `Mono.cache()` storing an exception and serving it for hours.

### Configuration hygiene checklist for reviews
| Check | Expected |
| --- | --- |
| Every outbound client has connect + read timeouts | Yes, from measured latency |
| Retries | Only idempotent + transient; one layer; jitter; budget |
| Circuit breaker | Per dependency; rate-based; slow calls counted; `CallNotPermittedException` not retried |
| Bulkhead | Per dependency; fast rejection |
| Fallback | Explicit degraded marker; no hidden data loss; doesn't hit the same dependency |
| Metrics | Exported and alerted |
| Tests | Fault-injection tests prove the behavior (WireMock delays/faults, Toxiproxy) |

### Verify instead of trusting configuration
Write integration tests that assert behavior, not settings:

```java
@Test
void slowPricingTripsBreakerAndUsesFallback() {
    pricing.stubFor(get(urlPathMatching("/prices/.*")).willReturn(ok().withFixedDelay(2_000)));

    long start = System.nanoTime();
    for (int i = 0; i < 30; i++) service.price("SKU-" + i);
    Duration elapsed = Duration.ofNanos(System.nanoTime() - start);

    assertThat(registry.circuitBreaker("pricing").getState()).isEqualTo(CircuitBreaker.State.OPEN);
    assertThat(elapsed).isLessThan(Duration.ofSeconds(15));   // timeouts + open breaker kept latency bounded
}
```

And re-run such tests after upgrading Spring Cloud/Resilience4j — default behaviors (aspect ordering, property names) change between versions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The usual resilience misconfigurations are missing or inconsistent timeouts, retries on non-idempotent or non-transient errors, retries at multiple layers, annotations bypassed by self-invocation, fallbacks that hide failures or hit the same dependency, breakers that never or always trip, and shared instances across dependencies. I review against a checklist and prove behavior with fault-injection tests.

**Must know:**
* AOP proxy limits: self-calls, private methods.
* `TimeLimiter` doesn't cancel blocking I/O; set client timeouts.
* Retry layers multiply (gateway, mesh, SDK, Feign, Resilience4j).
* `retry-exceptions` / `ignore-exceptions`.
* Per-dependency instances; slow-call thresholds.

**Common follow-ups:**
* Why does my fallback never run?
* How would you find all retry layers in a system?
* What's wrong with a bulkhead queue?

**Red flags:** `name = "default"` everywhere; fallbacks returning empty data silently; no tests for resilience behavior.
