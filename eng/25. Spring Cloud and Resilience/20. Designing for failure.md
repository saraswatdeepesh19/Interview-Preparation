# Designing for failure

---

## 🟢 Junior Level

In distributed systems, failure is not an exception — it is the normal state somewhere. Networks drop packets, disks fill up, deployments go wrong, dependencies get slow. **Designing for failure** means assuming every component *will* fail and making sure the system as a whole keeps working, or fails in a controlled, recoverable way.

### The fallacies of distributed computing
Classic wrong assumptions (Peter Deutsch and others):
1. The network is reliable.
2. Latency is zero.
3. Bandwidth is infinite.
4. The network is secure.
5. Topology doesn't change.
6. There is one administrator.
7. Transport cost is zero.
8. The network is homogeneous.

Every remote call in your code should answer: *what happens if this is slow, fails, or succeeds but the response is lost?*

### Basic toolkit
* **Timeouts** on every remote call.
* **Retries** with backoff — only for idempotent operations.
* **Circuit breakers** to stop hammering a broken dependency.
* **Bulkheads** to isolate resources.
* **Fallbacks** and graceful degradation.
* **Redundancy** — multiple instances across availability zones.

## 🟡 Middle Level

### Failure modes to design for

| Failure mode | Example | Design response |
| --- | --- | --- |
| Crash | Pod killed, OOM | Redundant instances, stateless services, health checks |
| Omission | Request or response lost | Timeouts, idempotent retries |
| Timing | Dependency 10× slower | Timeouts, bulkheads, load shedding |
| Response | Wrong/corrupt data, bad deploy | Validation, canaries, automated rollback |
| Byzantine | Inconsistent behavior | Rare in business apps; checksums, consensus protocols |

### Make operations safe to repeat
Because "did it happen?" is often unknowable after a timeout, operations should be **idempotent** (idempotency keys, upserts, conditional updates) and messaging consumers must tolerate **duplicates** and **reordering**.

### Prefer asynchronous coupling for non-critical paths

```java
// Synchronous chain: checkout fails if email or analytics is down
orders.save(order);
email.sendConfirmation(order);     // remote call
analytics.track(order);            // remote call

// Asynchronous: checkout depends only on its own database; side effects via outbox events
@Transactional
public void checkout(Order order) {
    orders.save(order);
    outbox.add(new OrderPlaced(order.id()));   // same transaction; relayed to the broker later
}
```

The more synchronous dependencies on the request path, the lower the availability: five dependencies at 99.9% each give at most ~99.5% combined.

### Static stability
A system is **statically stable** if it keeps working when its control plane or dependencies are unavailable — using what it already has. Examples: services cache configuration and discovery results; pods run with pre-provisioned capacity instead of relying on autoscaling during an incident; feature flags default to safe values if the flag service is down.

## 🔴 Senior Level

### Availability math and dependency budgets
* Serial dependencies multiply: `A_total = A1 × A2 × ... × An`.
* Redundant replicas improve availability: two independent replicas at 99% give `1 − 0.01² = 99.99%` — *if failures are independent*. Correlated failures (same AZ, same bad deploy, same config) break that assumption, which is why canaries, zone spreading and cell-based architectures matter.
* Set an **error budget** from the SLO (99.9% monthly = 43 minutes) and allocate it: deploy risk, dependency risk, infra risk.

### Blast radius reduction
* **Cells / shards**: split customers into independent stacks (cell-based architecture). A bad deployment or poison request affects one cell, not everyone. AWS uses this widely; shuffle sharding further reduces the chance that two customers share all cells.
* **Bulkhead by tenant or feature**: separate thread pools, connection pools, or even deployments for premium vs free tenants, or for batch vs interactive workloads.
* **Progressive delivery**: canary → small percentage → full rollout, with automatic rollback on SLO regression.

### Backpressure and load shedding
Systems fail under overload in non-linear ways: queues grow, latency explodes, timeouts trigger retries, and goodput collapses. Defenses:
* Bounded queues and pools everywhere (unbounded queues hide overload until memory runs out).
* **Adaptive concurrency limits** (Netflix `concurrency-limits` library, Envoy adaptive concurrency) that lower limits when latency rises.
* Prioritized load shedding: drop health-check-irrelevant, low-priority or retried requests first.
* Clients honor `Retry-After` and use jittered backoff and retry budgets.

### Dependency classification and timeouts budget
For each dependency document: criticality, timeout, retry policy, fallback, bulkhead size, and owner. The request's end-to-end deadline should be split across calls, and propagated so downstream services stop working on requests the caller has already abandoned (gRPC deadlines, custom deadline headers).

### Operational design
* Runbooks and alerts tied to SLOs, not to every CPU spike.
* Automated recovery (restart, failover, rollback) before human recovery.
* Regular **game days** and chaos experiments to verify that the designed behavior actually happens.
* **Blameless postmortems** that produce design changes, not just "be more careful".

## 🎯 Interview Cheat Sheet

**30-second pitch:** Designing for failure means assuming every dependency will be slow, fail or lose responses, and building in timeouts, idempotent retries, circuit breakers, bulkheads, fallbacks and redundancy. I keep synchronous dependencies on critical paths minimal, move side effects to async events, aim for static stability, limit blast radius with cells and progressive delivery, and protect against overload with bounded queues and load shedding.

**Must know:**
* Fallacies of distributed computing.
* Failure modes: crash, omission, timing, response.
* Serial availability multiplies; redundancy helps only with independent failures.
* Static stability, cells, shuffle sharding.
* Load shedding, adaptive concurrency, retry budgets, deadlines.

**Common follow-ups:**
* How many nines can a service with five synchronous dependencies achieve?
* What is static stability?
* How do you prevent overload collapse?

**Red flags:** "the cloud handles failures"; unbounded queues; synchronous calls for non-critical side effects.
