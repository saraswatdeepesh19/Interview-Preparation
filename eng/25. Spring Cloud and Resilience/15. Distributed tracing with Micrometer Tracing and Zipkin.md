# Distributed tracing with Micrometer Tracing and Zipkin

---

## 🟢 Junior Level

When one user request passes through a gateway and five services, logs in each service only show a fragment. **Distributed tracing** stitches the fragments together:

* A **trace** represents the whole request journey and has a **trace ID**.
* A **span** represents one unit of work (an HTTP call, a DB query, a Kafka publish) with a start time, duration, and a parent span.
* The trace ID is **propagated** between services in headers (W3C `traceparent` by default).

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             version-trace id (16 bytes)-------- parent span id - flags (sampled)
```

In Spring Boot 3, **Micrometer Tracing** (successor of Spring Cloud Sleuth) creates spans automatically; **Zipkin** (or Jaeger, Grafana Tempo, an OpenTelemetry collector) stores and visualizes them.

```xml
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-actuator</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-tracing-bridge-brave</artifactId></dependency>
<dependency><groupId>io.zipkin.reporter2</groupId><artifactId>zipkin-reporter-brave</artifactId></dependency>
```

```yaml
management:
  tracing:
    sampling:
      probability: 0.1          # sample 10% of traces (default 0.1)
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
logging:
  pattern:
    level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"
```

## 🟡 Middle Level

### What gets instrumented automatically
* Incoming HTTP (Spring MVC/WebFlux) and outgoing `RestClient`, `RestTemplate`, `WebClient` — **only when built from Spring's auto-configured builders**.
* JDBC via `datasource-micrometer`, Kafka/RabbitMQ templates and listeners (with `observation-enabled: true`), `@Scheduled` tasks, Spring Data repositories (Mongo, Redis), Spring Security filters.

### Custom spans with the Observation API

```java
@Service
class PricingService {
    private final ObservationRegistry registry;

    Price price(Cart cart) {
        return Observation.createNotStarted("pricing.calculate", registry)
                .lowCardinalityKeyValue("currency", cart.currency().getCode())   // also becomes a metric tag
                .highCardinalityKeyValue("cart.id", cart.id())                   // span-only attribute
                .observe(() -> rules.apply(cart));
    }
}

// or declaratively (needs ObservedAspect bean + AOP)
@Observed(name = "pricing.calculate", contextualName = "calculate-price")
Price price(Cart cart) { ... }
```

One Observation produces **both** a timer metric and a span — low-cardinality key-values become metric tags; high-cardinality ones only go to the span (never put user IDs in metric tags).

### Logs ↔ traces correlation
With `traceId`/`spanId` in the MDC and log pattern (Spring Boot 3.2+ adds them to the default console pattern when tracing is on), you can jump from a log line to the full trace and back — the main day-to-day value of tracing.

### Baggage
Business context propagated alongside the trace (e.g. `tenant-id`) to all downstream services:

```yaml
management:
  tracing:
    baggage:
      remote-fields: tenant-id
      correlation:
        fields: tenant-id      # also put into MDC
```

Baggage travels in every outgoing request header — keep it small and never put secrets in it.

## 🔴 Senior Level

### Sampling strategies
* **Head-based** (default): decide at the trace start (`probability: 0.1`); downstream services honor the `sampled` flag. Cheap, but you may miss the rare slow or failed request.
* **Tail-based**: collect all spans in an OpenTelemetry Collector and decide after the trace completes (keep 100% of errors and traces > 1 s, 1% of the rest). Requires buffering in the collector, but gives far better signal per stored byte.
* Always sample 100% in dev/staging; in production, combine low head sampling with exemplars (metric → trace links) and tail sampling for errors.

### Brave vs OpenTelemetry bridge
Micrometer Tracing is a facade with two bridges:
* `micrometer-tracing-bridge-brave` + Zipkin reporter — mature, simple.
* `micrometer-tracing-bridge-otel` + OTLP exporter (`management.otlp.tracing.endpoint`) — sends to any OpenTelemetry-compatible backend (Tempo, Jaeger, Honeycomb, Datadog, vendor APMs). The industry is converging on OTLP; choose it for new systems.

An alternative is the **OpenTelemetry Java agent** (bytecode instrumentation, zero code changes, broad library coverage). Don't run the agent *and* Micrometer instrumentation for the same libraries without configuring which owns spans — you'll get duplicates.

### Propagation across async boundaries
* `@Async`, `CompletableFuture`, custom executors: wrap executors with `ContextExecutorService.wrap(...)` (context-propagation library) or use Spring's `TaskDecorator` with `ContextPropagatingTaskDecorator` (Boot 3.2: `spring.task.execution.*` beans get it automatically).
* Reactor: enable `Hooks.enableAutomaticContextPropagation()` (or `spring.reactor.context-propagation=auto`).
* Kafka: enable observation on templates and listener containers so `traceparent` is written to/read from record headers.

### Cost and pitfalls
* Span volume: a request with 30 DB queries creates 30+ spans; at 5,000 req/s and 10% sampling that's still 15,000 spans/s. Budget storage and collector CPU.
* Cardinality: span names must be low-cardinality (`GET /api/orders/{id}`, not `/api/orders/42`).
* Missing context in logs usually means an async boundary without propagation or a client built with `RestClient.create()` instead of the injected builder.
* Clock skew between hosts distorts span timelines; keep NTP in sync.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Distributed tracing assigns a trace ID to each request, records spans for each unit of work, and propagates context via W3C `traceparent` headers. In Spring Boot 3, Micrometer Tracing with a Brave or OpenTelemetry bridge instruments HTTP, messaging and JDBC; the Observation API creates spans and metrics together; Zipkin or an OTLP backend stores traces. Sampling, async propagation and cardinality are the operational concerns.

**Must know:**
* Trace, span, parent; `traceparent` format.
* Use Spring's builders for instrumented clients.
* Observation API: low vs high cardinality key-values.
* traceId/spanId in MDC; baggage for business context.
* Head vs tail sampling; Brave vs OTel bridge.

**Common follow-ups:**
* Why is my traceId missing in `@Async` methods?
* Sleuth vs Micrometer Tracing?
* How do you trace Kafka flows?

**Red flags:** 100% sampling in high-traffic production without a plan; user IDs as span names or metric tags.
