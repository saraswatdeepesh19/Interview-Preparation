# Health checks and graceful degradation

---

## 🟢 Junior Level

* A **health check** is an endpoint that tells the platform (Kubernetes, a load balancer) whether an instance should receive traffic or be restarted.
* **Graceful degradation** means that when a dependency fails, the system keeps serving the most important functionality with reduced features instead of failing completely.

### Spring Boot Actuator health

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true            # /actuator/health/liveness and /readiness (auto-enabled on Kubernetes)
      show-details: when-authorized
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
```

```yaml
# Kubernetes deployment
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8081 }
  periodSeconds: 5
  failureThreshold: 2
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8081 }
  periodSeconds: 5
  failureThreshold: 30          # up to 150 s to start before liveness kicks in
```

### Degradation example
An online shop: if the recommendations service is down, the product page still shows the product and price — just without "customers also bought".

## 🟡 Middle Level

### Liveness vs readiness
* **Liveness** — "is this process broken beyond recovery?" Failing it makes Kubernetes **restart** the container. It should check only the app itself (event loop alive, no deadlock), **never external dependencies**.
* **Readiness** — "can this instance serve traffic right now?" Failing it removes the pod from Service endpoints **without restarting** it. Use it during startup warm-up, shutdown, and when an essential local resource is unavailable.

```yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include: readinessState, db      # include the DB only if the service is useless without it
        liveness:
          include: livenessState
```

### Why dependencies in liveness are dangerous
If liveness includes the database and the database has a 30-second hiccup, **every** pod fails liveness and Kubernetes restarts the whole fleet at once — turning a minor blip into a full outage with a thundering herd of reconnects on recovery.

### Custom health indicator

```java
@Component
class PricingFeedHealth implements HealthIndicator {
    private final PricingFeed feed;
    @Override
    public Health health() {
        Duration lag = feed.lag();
        return lag.compareTo(Duration.ofMinutes(5)) < 0
                ? Health.up().withDetail("lag", lag.toString()).build()
                : Health.status("DEGRADED").withDetail("lag", lag.toString()).build();   // custom status
    }
}
```

Map custom statuses to HTTP codes (`management.endpoint.health.status.http-mapping.DEGRADED=200`) so "degraded" doesn't remove the instance from rotation.

## 🔴 Senior Level

### Graceful shutdown
Restarts and deployments must not drop in-flight requests:

```yaml
server:
  shutdown: graceful                       # stop accepting, finish in-flight requests
spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s
```

Sequence on `SIGTERM`: readiness switches to `REFUSING_TRAFFIC`, but endpoint removal propagates asynchronously through kube-proxy/ingress/load balancers. Add a `preStop` sleep (e.g. 5–10 s) so the pod stops receiving new requests *before* the server stops listening, and keep `terminationGracePeriodSeconds` > preStop + shutdown timeout. Stop Kafka consumers and schedulers in an orderly way too (commit offsets, finish batches).

### Designing degradation deliberately
Classify features by criticality before incidents happen:

| Tier | Example | Behavior when dependency fails |
| --- | --- | --- |
| Critical | Checkout, payment | Fail clearly; protect with retries/idempotency |
| Important | Prices, stock | Serve cached/stale data with a marker; disable "buy" if stale beyond X |
| Nice-to-have | Recommendations, reviews | Hide the widget |

Mechanisms:
* **Fallbacks** (Resilience4j) returning cached or default data.
* **Feature flags / kill switches** to turn off expensive features under load (e.g. disable search suggestions).
* **Load shedding**: reject low-priority traffic early (429/503 with `Retry-After`) when concurrency or latency exceeds thresholds — better to serve 80% of users well than 100% badly.
* **Static fallback** at the edge (CDN serving a cached homepage when origin is down).

### Health checks at the edge and between services
* Load balancers' health checks should hit **readiness**, not a deep health endpoint that checks every dependency (dependency failures would mark all instances unhealthy simultaneously).
* For dependency health, prefer **circuit breakers** and **metrics-based alerts** over health endpoints: the circuit breaker reacts per call path, the health endpoint flips the whole instance.
* Deep health ("synthetic" checks of end-to-end flows) belongs in monitoring/alerting, not in Kubernetes probes.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Liveness tells Kubernetes to restart a broken process and must not depend on external systems; readiness controls whether an instance receives traffic; startup probes protect slow starts. Graceful shutdown with readiness flip, preStop delay and `server.shutdown=graceful` avoids dropped requests. Graceful degradation means planning per-feature fallbacks — stale data, hidden widgets, kill switches and load shedding — so a failing dependency reduces functionality instead of taking everything down.

**Must know:**
* `/actuator/health/liveness` vs `/readiness`; health groups.
* Never put DB checks in liveness.
* Startup probes for slow JVM/Spring starts.
* Graceful shutdown + preStop + termination grace period.
* Criticality tiers, fallbacks, kill switches, load shedding.

**Common follow-ups:**
* Why did all pods restart when the database blipped?
* How do you deploy without dropping requests?
* Health endpoint vs circuit breaker for dependency failures?

**Red flags:** one deep health endpoint used for liveness; no preStop delay; degradation decided during the incident.
