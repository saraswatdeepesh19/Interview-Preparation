# Tuning resilience in production

---

## 🟢 Junior Level

Default timeouts, retry counts and circuit-breaker thresholds are guesses. **Tuning** means choosing values from **measured behavior** of each dependency and adjusting them as traffic and dependencies change.

### Start from data
For each dependency, collect from metrics:
* Latency percentiles: **p50, p99, p99.9** of successful calls.
* Error rate and error types (timeouts vs 5xx vs 4xx).
* Throughput (requests/second) and peak concurrency.

### Rules of thumb
* **Timeout** ≈ the dependency's p99.9 latency plus a margin — not "30 seconds because that's the default".
* **Retries**: 1–2 for idempotent calls with exponential backoff and jitter; zero for non-idempotent ones.
* **Circuit breaker**: trip on a failure (or slow-call) **rate** over a window with a minimum number of calls — not on a single error.
* **Bulkhead**: concurrency ≈ throughput × latency (Little's law) plus headroom.

## 🟡 Middle Level

### Worked example
Pricing service measurements at peak: 400 req/s, p50 40 ms, p99 180 ms, p99.9 420 ms; errors mostly connection resets during its deployments.

```yaml
resilience4j:
  timelimiter:
    instances:
      pricing:
        timeout-duration: 500ms                 # above p99.9 (420 ms)
  retry:
    instances:
      pricing:
        max-attempts: 2                         # one retry; connection resets are transient
        wait-duration: 50ms
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2
        enable-randomized-wait: true            # jitter
        retry-exceptions: [java.io.IOException, java.util.concurrent.TimeoutException]
  circuitbreaker:
    instances:
      pricing:
        sliding-window-type: TIME_BASED
        sliding-window-size: 30                 # seconds
        minimum-number-of-calls: 100            # ~0.25 s of traffic at peak; avoids tripping at night on 3 errors
        failure-rate-threshold: 50
        slow-call-duration-threshold: 450ms
        slow-call-rate-threshold: 60
        wait-duration-in-open-state: 15s
        permitted-number-of-calls-in-half-open-state: 10
  bulkhead:
    instances:
      pricing:
        max-concurrent-calls: 120               # 400 × 0.18 s ≈ 72 at p99, plus headroom
```

Worst-case latency budget for the caller: 500 ms + 50–100 ms backoff + 500 ms ≈ 1.1 s. If the caller's own SLA is 800 ms, reduce attempts to 1 or the timeout to ~300 ms with a fallback.

### Dashboards to watch
* `resilience4j_circuitbreaker_state` (and transitions), `_failure_rate`, `_slow_call_rate`, `_not_permitted_calls_total`.
* `resilience4j_retry_calls_total{kind=...}` — `successful_with_retry` rising means a degrading dependency.
* `resilience4j_bulkhead_available_concurrent_calls` near zero means saturation.
* Downstream latency from client metrics (`http_client_requests_seconds`).

## 🔴 Senior Level

### Timeouts must be consistent across layers
Timeouts form a hierarchy; each outer layer must exceed the sum of inner work:

```
client/browser (10s) > ingress/gateway (5s) > service A request deadline (3s)
      > A→B call: (timeout 800ms × 2 attempts + backoff) ≈ 1.8s
            > B's DB statement timeout (500ms) & Hikari connectionTimeout (250ms)
```

When an inner timeout is *longer* than an outer one, the outer layer gives up while inner work continues — wasting resources and producing retries of work still in progress. Configure DB statement timeouts (`spring.jpa.properties.jakarta.persistence.query.timeout`, PostgreSQL `statement_timeout`), pool acquisition timeouts, HTTP connect/read timeouts, and gateway route timeouts together.

### Adaptive and per-endpoint tuning
* Different endpoints of the same dependency have different latency profiles (`GET /price` vs `POST /bulk-quote`). Use separate Resilience4j instances per operation class.
* Tune for **peak and off-peak**: count-based windows trip too easily at low traffic; time-based windows with `minimumNumberOfCalls` handle both.
* **Adaptive concurrency limits** (gradient algorithms, Netflix concurrency-limits, Envoy adaptive concurrency) adjust limits automatically to latency changes and often outperform static bulkheads.

### Change management for resilience config
* Treat config as code: versioned, reviewed, rolled out progressively.
* Allow **runtime changes** without redeploys in emergencies (Spring Cloud Config refresh, feature flags for "disable retries", or Resilience4j registry updates via actuator/admin endpoints) — with audit trail.
* Validate with load tests and chaos experiments: inject latency equal to the dependency's p99.9 × 2 and confirm the breaker opens, the bulkhead caps concurrency and the caller stays within SLO.

### Common tuning mistakes found in postmortems
* Retry + circuit breaker counting the same failure multiple times, tripping too early — or retries continuing against an open circuit.
* `waitDurationInOpenState` too short → breaker flaps; too long → slow recovery after the dependency is healthy.
* Slow-call thresholds ignored, so the breaker never opens when the dependency is slow but not failing (the common case).
* Same configuration copy-pasted for all dependencies.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I tune resilience from measured per-dependency latency and error data: timeouts just above p99.9, one or two jittered retries only for idempotent transient errors, circuit breakers on failure and slow-call rates with a minimum call count, and bulkheads sized by Little's law. Timeouts must nest consistently from gateway to database, configuration is versioned and changeable at runtime, and every change is validated with load tests and fault injection.

**Must know:**
* Timeouts from percentiles; latency budget math with retries.
* `minimumNumberOfCalls`, time-based windows, slow-call thresholds.
* Nested timeout hierarchy including DB statement and pool timeouts.
* Key Resilience4j metrics and what they signal.
* Separate instances per dependency/operation.

**Common follow-ups:**
* How would you set the timeout for a new dependency with no data?
* Why does my circuit breaker never open?
* How do you change retry settings during an incident?

**Red flags:** 30 s default timeouts; identical config for all clients; tuning without dashboards.
