# How to manage technical debt

---

## 🟢 Junior Level

**Technical debt** (Ward Cunningham's metaphor) is the future cost of choosing a faster or easier solution now instead of a better one. Like financial debt, it can be useful — shipping earlier to learn — but it accrues **interest**: every change in that area takes longer and breaks more often.

### Martin Fowler's technical debt quadrant

| | Reckless | Prudent |
| --- | --- | --- |
| **Deliberate** | "We don't have time for design" | "We must ship now and deal with consequences" (with a plan) |
| **Inadvertent** | "What's layering?" | "Now we know how we should have done it" |

### Common forms
* **Code debt** — duplication, huge classes, missing tests, unclear names.
* **Design/architecture debt** — wrong boundaries, tight coupling, shared databases, distributed monolith.
* **Dependency debt** — outdated frameworks (Spring Boot 2, Java 8), unpatched libraries.
* **Test and pipeline debt** — slow, flaky or missing tests; manual deployments.
* **Operational debt** — missing monitoring, runbooks, alerts; snowflake servers.
* **Documentation/knowledge debt** — only one person understands a critical module.

## 🟡 Middle Level

### Make debt visible
Debt that isn't tracked can't be prioritized. Keep a **debt register** (tickets with a `tech-debt` label or a lightweight list) with:
* **Description and location** (module, service).
* **Interest** — concrete cost today: "every pricing change takes 3 days instead of half a day", "2 incidents last quarter", "blocks upgrading to Java 21".
* **Principal** — estimated effort to fix.
* **Risk** — security, compliance, availability consequences.
* **Owner** and links to ADRs if it was a deliberate decision.

### Measure where it hurts
Combine code metrics with change data — debt matters most where code **changes often**:
* **Hotspots**: files with high churn (git history) *and* high complexity — tools like CodeScene, or `git log --format=format: --name-only | sort | uniq -c | sort -rn` combined with complexity reports.
* Defect density per module, lead time per area, incidents per service.
* Static analysis trends (Sonar "technical debt ratio" is a rough indicator, not a goal).

### Paying it down
* **Boy Scout rule** — leave code a bit better each time you touch it (small refactors within feature work).
* **Dedicated capacity** — e.g. 15–20% of each sprint for debt and platform work, protected and agreed with product.
* **Targeted initiatives** — for large items (framework upgrades, splitting a module), plan as projects with milestones.
* **Prevent new debt** — fitness functions, code review standards, Definition of Done including tests and observability.

## 🔴 Senior Level

### Talking to the business about debt
Don't ask for "refactoring time"; present **economics and risk**:
* "Checkout changes take 2× longer than other areas because of the pricing module; fixing it costs ~3 weeks and saves ~2 days per change — about 20 changes a year."
* "Spring Boot 2.7 is out of OSS support; staying exposes us to unpatched CVEs and blocks Java 21 virtual threads, which we need for the scaling target."
* Tie debt work to roadmap items: refactor the area you're about to build in (*preparatory refactoring*: "make the change easy, then make the easy change" — Kent Beck).

### Prioritization model
Score items by **interest × likelihood of touching the area** vs **principal**, plus risk:
1. Security and compliance risks (non-negotiable, time-bound).
2. Hotspots blocking upcoming roadmap work.
3. Debt causing incidents or on-call load.
4. Cheap fixes with broad benefit (build speed, flaky tests).
5. Everything else — maybe never; some debt is fine to keep forever in stable, rarely changed code.

### Large-scale remediation patterns
* **Strangler fig** — replace a legacy component gradually behind an interface or routing layer.
* **Branch by abstraction** — introduce an abstraction, build the new implementation behind it, switch, remove the old one — all on trunk.
* **Parallel run / shadow traffic** — compare old vs new outputs in production before switching.
* **Automated refactoring** — OpenRewrite recipes for framework migrations (Spring Boot 2→3, JUnit 4→5, `javax`→`jakarta`), applied across many repositories.

### Organizational debt
Technical debt often mirrors organizational issues: unclear ownership, teams split against the architecture (Conway's law), pressure without slack. Fixing code without fixing ownership and delivery practices brings the debt back.

### Finding hotspots and recording debt

```bash
# Files changed most often in the last year (churn); combine with complexity reports
git log --since="12 months ago" --format=format: --name-only -- 'src/main/java' \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

```yaml
# Debt register entry (kept in the repo or as a ticket template)
id: TD-042
title: PriceCalculator mixes pricing rules with persistence and HTTP calls
location: pricing-service/src/main/java/com/shop/pricing/PriceCalculator.java
interest: "Each pricing change ~3 days (vs ~0.5 elsewhere); 2 incidents in Q2"
principal: "~8 days: extract PricingRules, add approval tests, inject clients"
risk: medium
owner: team-pricing
trigger: "Do before the Q4 promotions epic"
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** Technical debt is the future cost of expedient choices, and its interest is paid on every change in that area. I make it visible in a register with interest, principal, risk and owner, prioritize by hotspots — high churn and high complexity — and roadmap impact, pay it down continuously with the boy scout rule, protected capacity and preparatory refactoring, use strangler fig, branch by abstraction or OpenRewrite for large items, and explain it to the business in time, risk and money.

**Must know:**
* Fowler's quadrant; types of debt.
* Interest vs principal; debt register.
* Hotspot analysis; metrics as indicators, not goals.
* Paydown strategies; preparatory refactoring.
* Strangler fig, branch by abstraction, OpenRewrite.

**Common follow-ups:**
* How do you convince product to prioritize debt?
* Which debt would you leave alone?
* How do you prevent debt from growing?

**Red flags:** "rewrite everything"; refactoring without tests; unmeasured "clean code" crusades in stable code nobody touches.
