# How to manage dependencies and choose between a library and a framework

---

## 🟢 Junior Level

* A **library** is code **you call** (Jackson, Guava, Apache Commons, Caffeine). You stay in control of the flow.
* A **framework** is code that **calls you** (Spring, Quarkus, Hibernate, JUnit). It defines the structure and lifecycle; you fill in the extension points — *inversion of control*.

| | Library | Framework |
| --- | --- | --- |
| Control flow | Your code | The framework |
| Replaceability | Usually easy (wrap it) | Hard (shapes your whole app) |
| Learning curve | Small, focused | Larger: conventions, lifecycle, configuration |
| Productivity | Solves one problem | Solves many cross-cutting concerns at once |
| Lock-in | Low | High |

### Every dependency is a liability as well as an asset
Each JAR brings transitive dependencies, CVEs, upgrade work, license obligations, and bugs you can't fix yourself. Before adding one, ask:
1. Do we really need it? (Is it 20 lines of code we could write and test?)
2. Is it **maintained**? Recent releases, responsive maintainers, healthy community, bus factor > 1.
3. What does it **pull in** transitively? (`mvn dependency:tree`)
4. Is the **license** acceptable (Apache-2.0/MIT vs GPL/AGPL/"source-available")?
5. How hard would it be to **replace**?

## 🟡 Middle Level

### Containing dependencies
* **Wrap volatile or replaceable libraries** behind your own interface at the boundary (payment SDKs, PDF generators, feature-flag clients) — the rest of the code depends on your abstraction.
* Don't wrap stable, ubiquitous libraries everywhere (Jackson, SLF4J, JDK APIs) — the indirection costs more than it saves.
* Keep framework annotations out of the **domain core** where practical (hexagonal architecture), so business logic survives framework upgrades and is testable without the container.

### Versions and conflicts in Maven/Gradle
* Use a **BOM** (Spring Boot dependencies, `platform()` in Gradle) so versions are consistent and tested together.
* Maven picks the **nearest** version in the tree for conflicts (Gradle picks the highest by default) — surprises lead to `NoSuchMethodError` at runtime. Detect with `maven-enforcer-plugin` `dependencyConvergence`/`requireUpperBoundDeps`, and Gradle's dependency insight.
* Avoid version ranges; use lockfiles (Gradle) and Renovate/Dependabot for regular, small upgrades.

```xml
<plugin>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions><execution><goals><goal>enforce</goal></goals>
    <configuration>
      <rules>
        <dependencyConvergence/>
        <bannedDependencies>
          <excludes>
            <exclude>commons-logging:commons-logging</exclude>   <!-- use jcl-over-slf4j / spring-jcl -->
            <exclude>log4j:log4j</exclude>                       <!-- Log4j 1.x, end of life -->
          </excludes>
        </bannedDependencies>
      </rules>
    </configuration>
  </execution></executions>
</plugin>
```

## 🔴 Senior Level

### Choosing a framework (or not)
Frameworks pay off when they solve problems you'd otherwise solve badly yourself: DI, transactions, security, configuration, observability, HTTP and data access integration. Spring Boot's value is largely its ecosystem and production features. Evaluate:
* **Fit**: does its model match your app (request/response, reactive, batch, serverless, native image)?
* **Operational characteristics**: startup time, memory, native image support (Quarkus/Micronaut/Spring AOT), observability.
* **Ecosystem and hiring**: availability of integrations and engineers.
* **Longevity and support**: release cadence, LTS/commercial support, migration history (how painful were past major upgrades?).
* **Escape hatches**: can you drop to plain JDBC/HTTP when the abstraction doesn't fit?

### Governance at organization scale
* **Approved/curated dependencies** (an internal BOM or platform) with security scanning and license policy, without blocking teams from proposing new ones.
* **SBOMs** per build and continuous CVE monitoring of deployed artifacts.
* **Upgrade cadence** as routine work (monthly patch updates, framework majors planned) — falling multiple majors behind turns upgrades into projects.
* **Automated migrations** with OpenRewrite for framework upgrades across many repositories.
* **Internal shared libraries**: keep them small and stable; prefer platform capabilities (sidecars, templates) over a "common" library everyone must upgrade in lockstep. A shared library with business logic is a coupling point — treat it as a product with semantic versioning and owners.

### Build vs depend
For core differentiating logic, own the code. For commodity concerns (JSON, HTTP, crypto, caching), depend on well-maintained libraries — never hand-roll crypto or security protocols. For mid-size concerns (feature flags, workflow engines, rules engines), compare total cost of ownership including operations and lock-in (see build vs buy).

## 🎯 Interview Cheat Sheet

**30-second pitch:** A library is code I call; a framework calls my code and shapes the application, giving productivity at the cost of lock-in. Every dependency is a liability — CVEs, upgrades, transitive conflicts, licenses — so I evaluate need, maintenance, transitive footprint and replaceability, wrap volatile libraries at boundaries, keep frameworks out of the domain core, manage versions with BOMs, enforcer rules and automated updates, and run regular upgrades with SBOM-based CVE monitoring.

**Must know:**
* Library vs framework (inversion of control).
* Dependency evaluation checklist.
* BOMs; Maven nearest-wins vs Gradle highest-wins; enforcer rules.
* Wrapping at boundaries; domain free of framework annotations.
* Upgrade cadence, OpenRewrite, internal library pitfalls.

**Common follow-ups:**
* Would you add Lombok to a new project?
* How do you resolve a `NoSuchMethodError` at runtime?
* Should you wrap Spring?

**Red flags:** adding a library for a one-liner; years-old framework versions; shared "commons" libraries with business logic.
