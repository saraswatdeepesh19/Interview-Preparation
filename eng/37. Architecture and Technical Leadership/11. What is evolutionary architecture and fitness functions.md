# What is evolutionary architecture and fitness functions

---

## 🟢 Junior Level

**Evolutionary architecture** (Neal Ford, Rebecca Parsons, Patrick Kua) is architecture designed to **change incrementally and safely** over time, instead of being fixed upfront and slowly eroding. Requirements, technologies and scale will change; the goal is to keep the system's important qualities intact while it evolves.

A **fitness function** is an automated (or at least objective) check that a system still has a desired architectural characteristic — like a unit test, but for architecture:

| Characteristic | Example fitness function |
| --- | --- |
| Layering / modularity | "Controllers must not access repositories directly" (ArchUnit test) |
| Performance | "p99 of checkout < 500 ms in the nightly load test" |
| Security | "No dependency with a critical CVE" (SCA gate) |
| Resilience | "Service survives loss of one AZ" (chaos experiment) |
| Coupling | "No cycles between modules" |
| Operability | "Every service exposes health and metrics endpoints" |

### An architecture test with ArchUnit

```java
@AnalyzeClasses(packages = "com.shop")
class ArchitectureTest {

    @ArchTest
    static final ArchRule layers = layeredArchitecture().consideringAllDependencies()
            .layer("Web").definedBy("..web..")
            .layer("Application").definedBy("..application..")
            .layer("Domain").definedBy("..domain..")
            .layer("Infrastructure").definedBy("..infrastructure..")
            .whereLayer("Web").mayNotBeAccessedByAnyLayer()
            .whereLayer("Application").mayOnlyBeAccessedByLayers("Web")
            .whereLayer("Domain").mayOnlyBeAccessedByLayers("Application", "Infrastructure");

    @ArchTest
    static final ArchRule domainIsFrameworkFree = noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAnyPackage("org.springframework..", "jakarta.persistence..");
}
```

These run in every build: architecture drift fails CI instead of being discovered in a review months later.

## 🟡 Middle Level

### Kinds of fitness functions
* **Atomic** (one characteristic, one context) vs **holistic** (several together, e.g. performance + security under load).
* **Triggered** (run on change/in CI) vs **continual** (monitoring in production, e.g. SLO checks, synthetic tests).
* **Static** (code analysis, dependency rules) vs **dynamic** (load tests, chaos experiments).
* **Automated** vs **manual** (some, like legal reviews, stay manual but should be explicit and scheduled).

### Enabling incremental change
* **Modularity with enforced boundaries** — modules or services with explicit APIs (Spring Modulith, Java modules, ArchUnit rules).
* **Deployment pipelines** that make small changes cheap and safe (continuous delivery, feature flags, canaries).
* **Last responsible moment** — defer irreversible decisions until you know enough; keep options open with abstractions only where volatility is real.
* **Reversibility** — favor choices you can undo (feature flags, strangler fig, parallel runs).

### Example: preventing a distributed monolith
Fitness functions for a microservice landscape:
* No service reads another service's database (check DB grants or connection configs in IaC).
* Synchronous call depth per request ≤ 3 (derived from tracing data).
* Each service deployable independently: contract tests + `can-i-deploy` gate.
* No shared mutable libraries beyond a small platform BOM (dependency analysis).

## 🔴 Senior Level

### Choosing what to protect
Fitness functions are only valuable for characteristics the business cares about. Start from **architecture characteristics** (the "-ilities") identified with stakeholders — e.g. for a payment platform: auditability, availability, latency, security, deployability — and define a measurable function for the top few. Ten good fitness functions beat a hundred brittle rules nobody understands.

### Implementing at scale
* **Code-level**: ArchUnit/jMolecules for Java (layers, ports/adapters, naming, annotations, cycles); Spring Modulith's `ApplicationModules.of(App.class).verify()`; Error Prone custom checks.
* **Dependency-level**: Maven Enforcer (banned dependencies, dependency convergence), license checks, CVE gates.
* **Runtime-level**: SLO dashboards and burn-rate alerts; synthetic monitoring; chaos experiments on a schedule; cost-per-transaction thresholds.
* **Infrastructure-level**: policy as code (OPA/Kyverno, Checkov) — "no public S3 buckets", "all databases encrypted", "every service has PodDisruptionBudgets".

```java
// Spring Modulith: verify module boundaries and generate documentation
@Test
void verifiesModularStructure() {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
    modules.verify();                                   // fails on cycles and access to internal packages
    new Documenter(modules).writeModulesAsPlantUml();   // C4-style component diagrams from code
}
```

### Governance without bureaucracy
* Fitness functions encode architectural decisions (ADRs) as executable checks — link each rule to its ADR.
* Allow **explicit, time-boxed exceptions** (freeze lists of existing violations — ArchUnit's `FreezingArchRule` — so new code complies while legacy is fixed gradually).
* Review the functions themselves: remove those that no longer reflect business priorities.

### Common anti-patterns
* "Big up-front architecture" documents that nobody checks.
* Architecture rules only in people's heads, enforced by review heroics.
* Hundreds of noisy rules causing teams to disable the checks.
* Treating evolvability as "microservices everywhere" — a well-modularized monolith with fitness functions evolves more easily than a tangled set of services.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Evolutionary architecture supports guided, incremental change, and fitness functions are objective — ideally automated — checks that the architecture keeps its important characteristics: ArchUnit or Spring Modulith rules for boundaries, dependency and CVE gates, performance tests against SLOs, chaos experiments and policy as code. I pick a few characteristics that matter to the business, encode decisions as executable checks linked to ADRs, freeze legacy violations, and favor reversible decisions.

**Must know:**
* Definition of evolutionary architecture and fitness functions.
* Atomic/holistic, triggered/continual, static/dynamic.
* ArchUnit layered rules; Spring Modulith `verify()`.
* Runtime and infrastructure fitness functions.
* `FreezingArchRule`; link to ADRs; avoid rule overload.

**Common follow-ups:**
* How would you stop teams from bypassing the service layer?
* How do you measure "deployability"?
* What's the difference between a fitness function and a test?

**Red flags:** architecture enforced only in code review; rules without business rationale; no way to handle legacy violations.
