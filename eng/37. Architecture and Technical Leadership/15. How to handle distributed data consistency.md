# How to handle distributed data consistency

---

## 🟢 Junior Level

When data lives in **one database**, an ACID transaction keeps it consistent: debit and credit commit together or not at all. When data is spread across **services with their own databases** (or across a database, a cache, a search index and a broker), no single transaction covers everything. You must choose a strategy per operation:

| Strategy | Guarantee | Cost |
| --- | --- | --- |
| Keep related data in **one service/database** | Strong (ACID) | Bigger service boundaries |
| **Distributed transaction (2PC/XA)** | Atomic across resources | Blocking, coordinator failure, poor support in cloud/brokers, low throughput |
| **Saga** (local transactions + compensations) | Eventually consistent, business-level atomicity | Compensation logic, no isolation |
| **Outbox + events** (propagate changes) | Eventually consistent replicas/read models | Lag, idempotent consumers |
| **Consensus-based databases** (Spanner, CockroachDB) | Strong across nodes/regions | Latency, cost, vendor choice |

### First rule
Draw service boundaries so that **data that must change atomically lives together**. Many "distributed consistency" problems are boundary mistakes.

---

## 🟡 Middle Level

### Patterns in practice
* **Transactional outbox** — write the state change and an event row in the same local transaction; publish asynchronously. Consumers update their own data → eventual consistency without dual writes.
* **Saga** — for business transactions across services (order → payment → inventory), each step commits locally; failures trigger compensations (refund, release stock). Orchestrated sagas (a coordinator/workflow engine) are easier to reason about than long choreography chains.
* **Idempotent consumers** — at-least-once delivery requires deduplication (inbox table) so replays and retries don't double-apply.
* **Reservation / TCC (Try-Confirm-Cancel)** — reserve resources first (hold stock, authorize payment), confirm when all reservations succeed, cancel otherwise; reservations expire automatically.
* **Read models** — denormalized copies built from events (CQRS) for queries across services, accepting staleness.

### Choosing consistency per use case
* **Must be strongly consistent**: balances, inventory reservation at checkout, uniqueness constraints, permissions changes. Keep the authority in one place and validate there at decision time.
* **Can be eventually consistent**: search indexes, recommendations, analytics, notifications, caches, cross-service views (customer name shown on an order).
* Make the window **observable** (lag metrics) and **bounded** (SLOs like "search reflects changes within 5 s").

## 🔴 Senior Level

### Isolation anomalies in sagas and countermeasures
Sagas are ACD without I: intermediate states are visible.
* **Semantic locks**: mark entities as `PENDING_*` so other operations respect in-flight sagas.
* **Commutative updates**: debits/credits as deltas rather than absolute writes; order-independent operations.
* **Version checks / reread before acting**: optimistic concurrency on the aggregate when a compensating or final step runs.
* **Pivot transaction**: order steps so that irreversible actions (shipping, external payouts) happen last, after all fallible, compensatable steps.

### Reconciliation as a safety net
No matter how good the design, distributed systems drift: lost messages from misconfigurations, bugs in consumers, manual fixes. Build **reconciliation jobs** that compare sources of truth with derived data and external systems (payments vs provider settlements, orders vs warehouse shipments) and repair or alert. Financial systems treat reconciliation as a core feature, not a hack.

```sql
-- Example: orders marked PAID without a captured payment in the payments service's replica
select o.id from orders o
left join payment_replica p on p.order_id = o.id and p.status = 'CAPTURED'
where o.status = 'PAID' and o.paid_at < now() - interval '10 minutes' and p.order_id is null;
```

### Consistency between DB and other stores inside one service
* Cache: delete-after-commit, TTLs, CDC-driven invalidation.
* Search index: CDC (Debezium) or outbox → indexer; rebuildable from the DB.
* Broker: outbox, never "save then publish".
* Object storage + DB (file metadata): write the object first with a unique key, then commit metadata; clean orphans with a lifecycle job.

### Talking about CAP/PACELC pragmatically
Under network partitions you choose between availability and consistency per operation; even without partitions, stronger consistency costs latency (PACELC). State the choice for each operation: "checkout reads stock from the inventory service synchronously (consistency); product pages show cached stock (availability, staleness up to 30 s)."

## 🎯 Interview Cheat Sheet

**30-second pitch:** Without a single ACID transaction, I first try to keep data that must change atomically inside one service. Across services I use the outbox to propagate changes, sagas — preferably orchestrated — with compensations and semantic locks for business transactions, reservations with expiry, idempotent consumers, and read models for cross-service queries. I choose strong or eventual consistency per operation, bound and monitor staleness, and add reconciliation jobs as a safety net; 2PC is rarely worth it in microservices.

**Must know:**
* Boundaries first; strategy table.
* Outbox, sagas, inbox/idempotency, TCC reservations, read models.
* Saga isolation anomalies and countermeasures; pivot transaction.
* Reconciliation jobs.
* Per-operation consistency decisions; PACELC.

**Common follow-ups:**
* How do you avoid overselling stock across services?
* Why not use XA transactions?
* How do you detect that two systems drifted apart?

**Red flags:** dual writes; assuming "exactly-once" brokers solve consistency; no compensation design.
