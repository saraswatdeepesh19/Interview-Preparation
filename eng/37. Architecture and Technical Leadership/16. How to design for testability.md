# How to design for testability

---

## 🟢 Junior Level

**Testable code** is code whose behavior can be verified quickly and reliably in isolation. Hard-to-test code is usually a design smell: hidden dependencies, global state, mixing logic with I/O.

### Principles
1. **Inject dependencies** — pass collaborators (repositories, clients, clocks) in through the constructor instead of creating them inside.
2. **Separate logic from I/O** — keep decisions in pure functions/objects; push databases, HTTP and files to the edges.
3. **Control non-determinism** — time, randomness, UUIDs, threads: make them injectable.
4. **Small, focused units** with clear inputs and outputs.
5. **Avoid static and global mutable state** (singletons, static caches).

```java
// Hard to test: hidden time, hidden DB, hidden email
public class SubscriptionRenewer {
    public void renewDue() {
        List<Subscription> due = new SubscriptionDao().findDue(LocalDate.now());
        for (Subscription s : due) {
            s.renew();
            new SmtpMailer().send(s.email(), "Renewed");
        }
    }
}

// Testable: dependencies explicit, time injected, logic separable
public class SubscriptionRenewer {
    private final Subscriptions subscriptions;   // port (interface)
    private final Notifier notifier;             // port
    private final Clock clock;

    public SubscriptionRenewer(Subscriptions subscriptions, Notifier notifier, Clock clock) {
        this.subscriptions = subscriptions; this.notifier = notifier; this.clock = clock;
    }

    public int renewDue() {
        LocalDate today = LocalDate.now(clock);
        List<Subscription> due = subscriptions.dueOn(today);
        due.forEach(s -> { s.renew(today); notifier.renewed(s); });
        return due.size();
    }
}
```

## 🟡 Middle Level

### Functional core, imperative shell
Put business rules in a **pure core** (no I/O, deterministic), and a thin **shell** that loads data, calls the core, and persists/sends results:

```java
// Core: pure, trivially unit-testable with hundreds of cases
public final class PricingRules {
    public static Money price(Cart cart, CustomerTier tier, List<Promotion> promotions, LocalDate date) { ... }
}

// Shell: orchestration + I/O, tested with a few integration tests
@Transactional
public Quote quote(CartId id) {
    Cart cart = carts.get(id);
    Customer c = customers.get(cart.customerId());
    List<Promotion> promos = promotions.activeOn(LocalDate.now(clock));
    return new Quote(PricingRules.price(cart, c.tier(), promos, LocalDate.now(clock)));
}
```

### Ports and adapters
Define interfaces (ports) for what the domain needs (`Orders`, `PaymentGateway`, `Notifier`); implement adapters for JPA, HTTP, Kafka. Tests use **fakes** (in-memory implementations) for fast, realistic behavior, not only mocks:

```java
class InMemoryOrders implements Orders {
    private final Map<OrderId, Order> store = new HashMap<>();
    public void save(Order o) { store.put(o.id(), o); }
    public Optional<Order> byId(OrderId id) { return Optional.ofNullable(store.get(id)); }
}
```

Fakes make tests readable and survive refactoring better than deep mock setups that verify call sequences.

### Testability signals in code review
* A test needs 10 mocks → the class has too many responsibilities.
* `@SpringBootTest` needed to test a calculation → logic is entangled with the framework.
* Tests use `Thread.sleep` → time/async not injectable.
* `PowerMock`/`mockStatic` required → static dependencies to refactor.

## 🔴 Senior Level

### Testability at the architecture level
* **Modular boundaries** (modules/services with explicit APIs) let you test each module with its dependencies faked at the boundary; Spring Modulith's `@ApplicationModuleTest` boots only one module.
* **Contracts** between services (OpenAPI, consumer-driven contracts, schema registry) make integration testable without end-to-end environments.
* **Deterministic infrastructure** in tests — Testcontainers for real databases/brokers, WireMock/Toxiproxy for dependencies and failure injection.
* **Observability as testability**: structured events and metrics let you assert behavior in integration/E2E tests and production (e.g. "exactly one `PaymentCaptured` event per order").
* **Seams for time and concurrency** — schedulers, executors and clocks injected so async and time-based behavior can be driven deterministically (virtual time, direct executors).

### Designing APIs and data for testing
* Idempotent operations and explicit IDs (client-provided or returned) make retries and assertions straightforward.
* Feature flags and configuration injectable per test.
* Test data builders/object mothers to construct valid aggregates concisely; avoid shared fixtures that couple tests.

### Trade-offs
Testability isn't free: every interface and injection point adds indirection. Introduce seams where behavior varies or I/O happens — not around every class. Prefer testing **behavior through public APIs** of a module over testing private details; mutation testing (PIT) shows whether tests actually catch regressions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I design for testability by making dependencies explicit through constructor injection, separating a pure functional core from an imperative I/O shell, injecting clocks, randomness and executors, and defining ports with adapters so tests can use realistic fakes rather than deep mocks. At the architecture level I add modular boundaries, contracts, Testcontainers and fault injection, and I treat hard-to-test code — many mocks, static calls, sleeps — as a design smell.

**Must know:**
* DI, pure core/imperative shell, injectable `Clock`.
* Ports and adapters; fakes vs mocks.
* Testability smells in review.
* Module tests (`@ApplicationModuleTest`), contracts, Testcontainers.
* Balance: seams where behavior varies.

**Common follow-ups:**
* Mocks or fakes — when each?
* How do you test code that depends on `LocalDateTime.now()`?
* Why is a 10-mock test a design problem?

**Red flags:** `new` of infrastructure inside business logic; static singletons; tests that only verify mock call sequences.
