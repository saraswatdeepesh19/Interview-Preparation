# What are the trade-offs of event-driven architecture

---

## 🟢 Junior Level

In an **event-driven architecture (EDA)**, components communicate by publishing **events** ("OrderPlaced", "PaymentFailed") to a broker; other components react asynchronously. The producer doesn't know who consumes its events.

### Benefits
* **Loose coupling** — new consumers can be added without changing the producer.
* **Temporal decoupling** — consumers can be down; events wait in the broker.
* **Scalability** — consumers scale independently and absorb load spikes via buffering.
* **Responsiveness** — the user request finishes quickly; side effects (emails, analytics, search indexing) happen later.
* **Audit/history** — event logs (especially with Kafka retention) record what happened.

### Costs
* **Eventual consistency** — other parts of the system see changes later; UIs and APIs must handle "pending" states.
* **Harder to understand and debug** — the flow is spread across services and time; no single stack trace.
* **Operational complexity** — brokers, schemas, DLQs, replay tooling, monitoring lag.
* **Delivery semantics** — at-least-once delivery means duplicates and ordering issues; consumers must be idempotent.

---

## 🟡 Middle Level

### Synchronous vs event-driven: compare per interaction

| Concern | Synchronous request/response | Event-driven |
| --- | --- | --- |
| Caller needs an immediate answer | Natural | Requires request-reply or polling |
| Availability coupling | Caller fails when callee is down | Producer works while consumers are down |
| Consistency | Easier to reason about (one call) | Eventual; needs compensations for failures |
| Change impact | Callee API changes affect callers | Schema changes affect all consumers |
| Observability | Tracing straightforward | Need trace propagation through messages, lag metrics |
| Testing | Contract/integration tests | Plus message contract tests, async assertions |

Most systems mix both: **synchronous for queries and commands needing immediate results**, events for **notifications, propagation of state changes, and long-running workflows**.

### The usual failure stories
* **Events as hidden RPC** — `SendEmailRequested` events where the producer actually waits for a result: complexity of async with coupling of sync.
* **Event spaghetti** — choreography chains across 10 services with no one able to explain the end-to-end flow; changing it requires touching many teams.
* **Lost or duplicated effects** — no outbox (events lost on crash), no idempotency (duplicates double-charge).
* **Schema chaos** — events changed without compatibility rules, breaking consumers silently.

## 🔴 Senior Level

### Mitigating the costs deliberately
* **Reliable publication**: transactional outbox or CDC; **reliable consumption**: idempotent consumers with inbox/dedup, retries with backoff and DLQs.
* **Clear event design**: facts in past tense, versioned schemas in a registry with compatibility checks, event-carried state transfer for consumers' needs, stable integration events separate from internal domain events.
* **Flow visibility**: distributed tracing through messages (W3C `traceparent` in headers), an event catalog (AsyncAPI, schema registry, Backstage), and **orchestration** (Temporal, Camunda, Step Functions) for business-critical multi-step workflows where choreography gets opaque.
* **Consistency UX**: return `202 Accepted` with a status resource, show "processing" states, read-your-writes via the write model, and design compensations (refunds, cancellations) as first-class features.
* **Operational readiness**: lag-based alerting on time, replay procedures (consumer offset resets, EventBridge archives), poison message handling, capacity planning for partitions.

### When EDA is the wrong default
* CRUD-heavy systems with one team and simple flows.
* Strong consistency requirements across operations (financial ledgers where a single ACID transaction is simplest — keep them in one service/database).
* Low-latency request paths where every hop adds tens of milliseconds and failure modes.

### Evaluating with numbers
"Order placement must stay available even if email, loyalty and analytics are down (each 99.5%). With synchronous calls, checkout availability ≤ 0.995³ ≈ 98.5% — unacceptable. Publishing `OrderPlaced` via outbox makes checkout depend only on its own database (99.95%), with downstream effects eventually consistent within seconds, monitored by consumer lag SLOs."

### Documenting events as contracts (AsyncAPI)

```yaml
asyncapi: 3.0.0
info: { title: Order events, version: 1.4.0 }
channels:
  orderPlaced:
    address: orders.order-placed.v1
    messages:
      OrderPlaced:
        headers:
          type: object
          properties: { traceparent: { type: string }, eventId: { type: string, format: uuid } }
        payload:
          type: object
          required: [orderId, customerId, total, occurredAt]
          properties:
            orderId:    { type: string }
            customerId: { type: string }
            total:      { type: string, description: "decimal amount in EUR" }
            occurredAt: { type: string, format: date-time }
operations:
  publishOrderPlaced:
    action: send
    channel: { $ref: '#/channels/orderPlaced' }
```

An event catalog like this answers the two hardest EDA questions — "who publishes what?" and "what exactly is in it?" — and feeds schema compatibility checks.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Event-driven architecture decouples services in time, scale and knowledge, improves availability of the producing path and enables new consumers without producer changes. The price is eventual consistency, harder debugging, operational complexity and at-least-once semantics. I use events for state-change propagation and side effects, keep synchronous calls for immediate answers, and mitigate the costs with outbox and idempotent consumers, schema governance, tracing through messages, orchestration for complex flows, and UX for pending states.

**Must know:**
* Benefits vs costs list.
* Sync vs async comparison per interaction.
* Failure stories: hidden RPC, event spaghetti, lost/duplicate effects, schema chaos.
* Mitigations: outbox/inbox, schema registry, tracing, orchestration, lag SLOs.
* Availability math argument.

**Common follow-ups:**
* When would you not use events?
* How do you debug a flow across 6 services?
* Choreography or orchestration?

**Red flags:** "events everywhere" as a principle; no idempotency; events with no owner or schema rules.
