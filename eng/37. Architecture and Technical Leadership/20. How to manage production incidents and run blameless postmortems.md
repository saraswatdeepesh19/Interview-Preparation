# How to manage production incidents and run blameless postmortems

---

## 🟢 Junior Level

An **incident** is an unplanned event that degrades or interrupts service for users (or threatens to). Incident management is about **restoring service quickly, communicating clearly, and learning** so it doesn't happen again.

### Core roles (scaled to incident size)
* **Incident Commander (IC)** — coordinates, decides, keeps the big picture; doesn't debug.
* **Operations/technical lead** — investigates and mitigates with responders.
* **Communications lead** — updates stakeholders and status page at a regular cadence.
* **Scribe** — records the timeline (decisions, actions, observations with timestamps).

### Severity levels (example)

| Sev | Definition | Response |
| --- | --- | --- |
| SEV1 | Critical user-facing outage or data loss/security breach | Page immediately, all hands, exec comms, status page |
| SEV2 | Major degradation (key feature down, many users affected) | Page on-call, IC assigned |
| SEV3 | Minor/partial impact, workaround exists | Handle in working hours |

### The incident lifecycle
**Detect → Triage (severity) → Mitigate → Resolve → Postmortem → Follow-up actions.**

Mitigation first: roll back, toggle a feature flag, fail over, scale up, shed load. Root cause analysis can wait until users are safe.

## 🟡 Middle Level

### Running the incident
* Open a dedicated channel (`#inc-2026-10-16-checkout`) and a video bridge; post the IC and current status at the top.
* **Declare early**: it's cheaper to downgrade a false alarm than to discover a silent SEV1 an hour late.
* Keep a **timeline** as you go (UTC timestamps): alerts, hypotheses, actions, results.
* **Communicate on a schedule** (e.g. every 30 minutes) even if there's no news: impact, what's being done, next update time.
* Avoid too many cooks: the IC assigns tasks explicitly ("Alice: check DB locks; Bob: prepare rollback").
* **Hand over** in long incidents (fatigue causes mistakes) with a written status summary.

### Blameless postmortem template
* **Summary** — what happened, impact (duration, users affected, revenue/SLO budget consumed).
* **Timeline** — detection, escalation, mitigation, resolution.
* **Root cause(s) and contributing factors** — technical *and* process (missing alert, unclear runbook, risky deploy practice).
* **What went well / what went poorly / where we got lucky.**
* **Action items** — specific, owned, prioritized, with due dates (prevent, detect faster, mitigate faster).

"Blameless" means focusing on **how the system allowed the failure**, not on who typed the command. People acted on the information they had; if one mistake can cause an outage, the system lacks safeguards.

## 🔴 Senior Level

### Getting real learning out of postmortems
* Go beyond a single "root cause": complex systems fail from **combinations** of factors (a config change + missing validation + an alert routed to the wrong team + a runbook that was out of date). Techniques: "5 whys" (carefully — it tends to find one linear cause), causal analysis diagrams, or contributing-factor lists.
* Ask **"how did it make sense at the time?"** to understand decisions under uncertainty.
* Write action items that change the **system**: automated rollback on canary failure, config validation in CI, alert on symptom with runbook link, guardrails for dangerous operations (lock timeouts for DDL, `--dry-run` defaults). Avoid "be more careful" or "add more reviews".
* **Track action items** to completion; review open items in a weekly ops review. Recurring incident themes signal investment areas (e.g. deploy safety, dependency resilience).
* **Share widely**: postmortems readable by other teams spread lessons (internal newsletter, incident review meeting).

### Measuring incident response
* **MTTD/MTTA/MTTR** (detect, acknowledge, restore) and incident counts by severity; DORA's change failure rate and recovery time.
* **Error budget consumption** per incident to prioritize reliability work against SLOs.
* Pager load per on-call shift (sustainability; burnout causes more incidents).

### Preparing before incidents
* **Runbooks** linked from alerts (what this alert means, dashboards, first checks, mitigation steps).
* **Game days / chaos drills** practicing incident roles and failovers.
* **Feature flags and fast rollback** paths tested regularly.
* **On-call readiness**: access to logs, dashboards and production tools; escalation policies; shadowing for new engineers.

### Postmortem skeleton

```markdown
# Postmortem: Checkout write failures (SEV2) — 2026-10-16

Impact: 14 min of failed order placement for ~18% of requests; ~420 orders retried by users; 31% of monthly error budget.

## Timeline (UTC)
- 10:02 Deploy 2026.10.16-3 starts (migration V87)
- 10:05 Alert: checkout 5xx burn rate 14x
- 10:07 Incident declared, IC: Maria
- 10:09 Author reports migration holding lock on orders
- 10:16 Index build cancelled, app rolled back; errors recover

## Contributing factors
- CREATE INDEX without CONCURRENTLY on an 80M-row table
- Staging data 1000x smaller than production
- No lock_timeout for the migration role

## Action items
| Action | Owner | Due |
| Squawk migration linting in CI | Ali | 10-23 |
| lock_timeout=5s for migration role | DBA team | 10-20 |
| Production-scale anonymized staging refresh | Platform | 11-15 |
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** In an incident I declare early, assign roles — incident commander, technical lead, communications, scribe — mitigate first via rollback, flags, failover or load shedding, communicate on a fixed cadence and keep a timeline. Afterwards I run a blameless postmortem focused on how the system allowed the failure — contributing factors, what went well and poorly — and produce owned action items that add safeguards, tracked to completion and measured with MTTR, change failure rate and error budgets.

**Must know:**
* Roles, severity levels, lifecycle.
* Mitigate before root cause; communication cadence; timeline.
* Postmortem template; blameless principles.
* Contributing factors over single root cause; system-changing actions.
* Metrics and preparation: runbooks, game days, on-call health.

**Common follow-ups:**
* Tell me about an incident you handled.
* What makes a postmortem action item good?
* How do you keep postmortems blameless when someone clearly made a mistake?

**Red flags:** blaming individuals; debugging for an hour before rolling back; postmortems with no follow-up.
