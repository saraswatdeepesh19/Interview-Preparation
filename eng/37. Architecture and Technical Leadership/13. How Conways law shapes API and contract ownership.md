# How Conways law shapes API and contract ownership

---

## 🟢 Junior Level

**Conway's law** (Melvin Conway, 1968): *"Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure."*

In practice:
* Three teams building a compiler produce a three-pass compiler.
* A frontend team, a backend team and a DBA team produce a layered system where every feature needs all three teams to coordinate.
* Teams that don't talk to each other produce integrations full of mismatches.

### The inverse Conway maneuver
If architecture follows organization, you can **design the organization to get the architecture you want**: structure teams around business capabilities (checkout, catalog, payments), and the system will tend toward services/modules with those boundaries.

### Ownership
Every API, event schema and service needs **one owning team** responsible for its design, evolution, documentation, availability and support. Shared ownership ("everyone owns the common library") usually means nobody does.

## 🟡 Middle Level

### Team Topologies vocabulary
Matthew Skelton and Manuel Pais describe four team types and three interaction modes:

| Team type | Purpose |
| --- | --- |
| **Stream-aligned** | Delivers value for a business stream end to end (owns its services, APIs, data) |
| **Platform** | Provides self-service internal products (CI/CD, observability, runtime) to reduce cognitive load |
| **Enabling** | Helps other teams adopt skills/technologies, temporarily |
| **Complicated-subsystem** | Owns parts needing deep specialist knowledge (pricing engine, ML models) |

| Interaction mode | Meaning |
| --- | --- |
| Collaboration | Working closely for a period (discovery, new domains) |
| X-as-a-Service | Consuming another team's well-defined API/platform with minimal coordination |
| Facilitating | Enabling team helps another team learn |

Good API boundaries make **X-as-a-Service** possible: consumers integrate via documented contracts without meetings for every change.

### Contract ownership practices
* **Provider owns the API**, consumers influence it via feedback, RFCs or consumer-driven contracts.
* **API as a product**: documentation, versioning policy, deprecation timelines, SLOs, changelog, support channel.
* **Events are public APIs too**: the producing team owns event schemas in a registry; internal domain events stay private.
* **No shared databases**: a database shared by multiple teams is an implicit, unversioned contract that couples their release cycles.

## 🔴 Senior Level

### Diagnosing Conway problems
* **Every feature requires changes in several teams' services** → boundaries are wrong (technical layering instead of business capabilities), or a "distributed monolith".
* **One team is a bottleneck for many others** (shared "core" service, central DBA/integration team) → split responsibilities, offer self-service, or move capabilities into stream-aligned teams.
* **APIs reflect org charts rather than domains** (`/team-a-api/...`, chatty APIs mirroring screen designs of one consumer) → realign with domain concepts (DDD bounded contexts).
* **High cognitive load** — a team owns too many services/technologies to operate well → reduce scope or invest in platform.

### Designing boundaries with DDD and Conway together
* Map **bounded contexts** (consistent models and language) and give each context to one team; context maps (customer/supplier, conformist, anti-corruption layer, published language) describe how teams' models interact.
* A **customer/supplier** relationship needs explicit negotiation of the supplier's API roadmap; a **conformist** downstream team simply adopts the upstream model; an **anti-corruption layer** protects a team's model from a messy upstream (legacy systems, third parties).
* Align **deployment units and repositories** with teams: one team can deploy its services without coordinating with others.

### Governance at the API level
* Lightweight standards (style guide, error format, pagination, auth) enforced by linting (Spectral) and platform tooling, so teams don't negotiate basics each time.
* API review for **public/cross-team** contracts only; internal APIs within a team change freely.
* Ownership metadata in a service catalog (Backstage): owner, on-call, SLOs, API specs, dependencies — so consumers know who to talk to.
* Track coupling metrics: number of teams that must coordinate for a release, cross-team PRs, shared-library change frequency.

### Interview-style example
"Our checkout needed changes in five services owned by three teams for every promotion feature. We regrouped into a 'Promotions' stream-aligned team owning pricing rules end to end, merged two services that always changed together, and turned the remaining dependencies into versioned APIs with contract tests. Lead time for promotion features dropped from 3 weeks to 4 days."

### Making ownership explicit in a service catalog (Backstage)

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: order-service
  annotations:
    pagerduty.com/service-id: P1234AB
spec:
  type: service
  lifecycle: production
  owner: team-checkout                     # exactly one owning team
  system: commerce
  providesApis: [orders-api, order-events]
  consumesApis: [payments-api, catalog-api]
---
apiVersion: backstage.io/v1alpha1
kind: API
metadata: { name: order-events }
spec:
  type: asyncapi
  lifecycle: production
  owner: team-checkout                     # event schemas are owned like any public API
  definition: { $text: ./asyncapi/order-events.yaml }
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** Conway's law says system structure mirrors communication structure, so I align teams with business capabilities — the inverse Conway maneuver — and give every API, event schema and service exactly one owning team that treats it as a product with docs, versioning, SLOs and deprecation policy. Team Topologies — stream-aligned, platform, enabling and complicated-subsystem teams — plus DDD bounded contexts guide boundaries; shared databases and cross-team bottlenecks are the warning signs.

**Must know:**
* Conway's law and the inverse maneuver.
* Team Topologies team types and interaction modes.
* API-as-a-product ownership; events as public contracts.
* Bounded contexts and context map relationships.
* Symptoms: cross-team features, bottleneck teams, shared DBs, cognitive load.

**Common follow-ups:**
* How would you split a 40-developer monolith team?
* Who owns a shared library?
* How do you handle an upstream team that won't change their API?

**Red flags:** component teams split by technical layer for product work; shared databases as integration; APIs with no owner.
