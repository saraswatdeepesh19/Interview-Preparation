# What are code review best practices and how to mentor juniors

---

## 🟢 Junior Level

**Code review** exists to improve the codebase and share knowledge — not to gatekeep or prove who's smarter. A good review catches defects, keeps design consistent, spreads understanding of the system, and teaches.

### For authors
* **Small PRs** — ideally < 400 lines of meaningful change; one purpose per PR. Large PRs get rubber-stamped.
* **Describe the why**: context, approach, trade-offs, how it was tested, screenshots for UI, links to tickets/ADRs.
* **Self-review first**: read your diff before requesting review; remove debug code, add tests.
* Let **automation** handle formatting, linting, tests and coverage — humans shouldn't comment on whitespace.

### For reviewers
* Review **promptly** (within hours, not days) — waiting PRs are the biggest delivery bottleneck.
* Focus on what matters, in order: **correctness → security → design/architecture → tests → readability → naming/style**.
* Comment on the **code, not the person**; ask questions instead of issuing orders ("What happens if `items` is empty?").
* Label comments by importance: `blocking:`, `suggestion:`, `nit:`, `question:`, `praise:` (Conventional Comments).

## 🟡 Middle Level

### A practical review checklist for Java services
* **Correctness**: edge cases (null, empty, large inputs), error handling, concurrency (shared mutable state, thread safety), transaction boundaries, idempotency of retried operations.
* **Security**: input validation, authorization checks on every new endpoint, no secrets in code/logs, safe SQL (parameters), dependency changes.
* **Data**: migrations backward-compatible, indexes for new queries, N+1 risks, large result sets paginated.
* **Resilience**: timeouts on new remote calls, retries only where idempotent, fallbacks deliberate.
* **Tests**: meaningful assertions, failure cases covered, no sleeps, test names describing behavior.
* **Observability**: logs at the right level with context, metrics/traces for new flows, no PII in logs.
* **Design**: fits existing patterns and module boundaries; no premature abstraction; public API changes are compatible.

### Giving feedback that lands

```text
blocking: This loop calls pricingClient.price() per item — for a 200-line cart that's 200 HTTP
calls. Could we use the batch endpoint POST /prices:batch? Happy to pair on it.

suggestion (non-blocking): Extracting the discount calculation into PricingRules would make it
unit-testable without Spring.

nit: `tmpList` -> `eligibleItems`?

praise: Nice use of Testcontainers here — this test would have caught last month's migration bug.
```

### Review culture
* Two-way: seniors' code gets reviewed too (by juniors as well — great learning).
* Disagreements about taste → follow the style guide or let the author decide; about correctness → discuss with evidence (tests, benchmarks), escalate to a quick call if a thread exceeds ~3 rounds.
* Track review latency and PR size as team health metrics (not individual performance metrics).

## 🔴 Senior Level

### Mentoring juniors effectively
* **Calibrate autonomy**: start with well-scoped tasks with clear acceptance criteria, increase ambiguity as confidence grows (task → feature → project → problem area).
* **Teach the reasoning, not just the answer**: in reviews and pairing, explain *why* ("we retry only idempotent calls because…"), point to principles and docs, let them find the bug with hints.
* **Pair and mob programming** for complex areas; let the junior drive while you navigate.
* **Psychological safety**: normalize questions and mistakes; share your own past mistakes; thank people for raising issues.
* **Regular 1:1s** with goals (technical skills, system knowledge, communication), feedback in both directions, and visible progress (they present a design, own an on-call shadow rotation, lead a small RFC).
* **Opportunities to lead**: give juniors ownership of a small component, a migration step, or a team demo; praise publicly, correct privately.

### Scaling review and mentoring as a lead
* Write **guidelines** (review checklist, architecture principles, ADRs) so feedback is consistent and not dependent on one senior.
* Use **CODEOWNERS** to route reviews to people with context, but rotate reviewers to spread knowledge.
* Encourage **design review before code** for significant changes (short RFC/design doc) — catching a wrong approach in review after 2 weeks of work is expensive and demotivating.
* Watch for **review bottlenecks** on seniors: share reviewing load, coach mid-levels to review for design, use pairing to reduce review cycles.

### Example answer
"When I joined, PRs waited two days and averaged 1,200 lines. We agreed on a 'review within 4 working hours' norm, split work into vertical slices under 300 lines, moved formatting to Spotless in CI, and introduced Conventional Comments. Review latency dropped to under half a day. I paired weekly with two juniors; within six months both were reviewing each other's PRs for design issues and one led the Java 21 migration."

## 🎯 Interview Cheat Sheet

**30-second pitch:** Code review is for correctness, shared understanding and teaching. Authors keep PRs small and explain the why; reviewers respond quickly, prioritize correctness, security and design over style, ask questions, label comments by severity, and leave formatting to automation. As a mentor I calibrate autonomy, teach reasoning through reviews and pairing, create psychological safety and growth opportunities, and scale through guidelines, design reviews before code and shared reviewing load.

**Must know:**
* Small PRs; good descriptions; self-review.
* Review priority order; Java-specific checklist.
* Conventional Comments; constructive phrasing.
* Mentoring techniques: autonomy ladder, pairing, 1:1s, ownership.
* Team-level metrics: review latency, PR size.

**Common follow-ups:**
* How do you handle a disagreement in review?
* What do you look at first in a PR?
* How have you helped a junior grow?

**Red flags:** nitpick-only reviews; reviews as gatekeeping; ignoring PRs for days.
