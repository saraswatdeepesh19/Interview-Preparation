# Specification pattern

---

## 🟢 Junior Level

The **Specification** pattern turns a business rule — "is this customer eligible for a discount?" — into an object with one method, `isSatisfiedBy(candidate)`. Specifications can be **combined** with `and`, `or`, `not` to build complex rules from small, named pieces.

### Real-world analogy
A recruiter's checklist: "has 5+ years of Java" AND "lives in the EU" AND NOT "currently on notice period". Each line is a reusable criterion; the recruiter composes them differently for each job.

### Basic implementation

```java
@FunctionalInterface
public interface Specification<T> {
    boolean isSatisfiedBy(T candidate);

    default Specification<T> and(Specification<T> other) { return c -> isSatisfiedBy(c) && other.isSatisfiedBy(c); }
    default Specification<T> or(Specification<T> other)  { return c -> isSatisfiedBy(c) || other.isSatisfiedBy(c); }
    default Specification<T> not()                       { return c -> !isSatisfiedBy(c); }
}

public final class CustomerSpecs {
    public static Specification<Customer> isPremium()         { return c -> c.tier() == Tier.PREMIUM; }
    public static Specification<Customer> hasOrdersOver(int n) { return c -> c.orderCount() > n; }
    public static Specification<Customer> isBlocked()         { return Customer::blocked; }
}

Specification<Customer> eligibleForDiscount =
        isPremium().or(hasOrdersOver(10)).and(isBlocked().not());

boolean ok = eligibleForDiscount.isSatisfiedBy(customer);
```

This is essentially `java.util.function.Predicate<T>` with a domain name — and that is fine.

## 🟡 Middle Level

### Three uses of a specification (Evans & Fowler)
1. **Validation** — does this object satisfy the rule? (`isSatisfiedBy`)
2. **Selection** — find all objects that satisfy the rule (filtering collections *or* querying a database).
3. **Construction to order** — describe what an object must satisfy before creating it.

### Selection in the database: Spring Data JPA Specifications
Filtering in memory does not scale; the same rule must become SQL. Spring Data JPA provides `org.springframework.data.jpa.domain.Specification<T>` built on the JPA Criteria API:

```java
public interface CustomerRepository extends JpaRepository<Customer, Long>, JpaSpecificationExecutor<Customer> { }

public final class CustomerQuerySpecs {
    public static Specification<Customer> tier(Tier tier) {
        return (root, query, cb) -> cb.equal(root.get("tier"), tier);
    }
    public static Specification<Customer> createdAfter(Instant since) {
        return (root, query, cb) -> cb.greaterThan(root.get("createdAt"), since);
    }
    public static Specification<Customer> inCountry(String iso) {
        return (root, query, cb) -> cb.equal(root.join("address").get("country"), iso);
    }
}

// Dynamic search endpoint: only add predicates for provided filters
Specification<Customer> spec = Specification.where(null);
if (filter.tier() != null)    spec = spec.and(tier(filter.tier()));
if (filter.since() != null)   spec = spec.and(createdAfter(filter.since()));
if (filter.country() != null) spec = spec.and(inCountry(filter.country()));

Page<Customer> page = repository.findAll(spec, PageRequest.of(0, 50, Sort.by("createdAt").descending()));
```

Generated SQL contains only the predicates that were added — no `WHERE (? IS NULL OR tier = ?)` tricks that ruin index usage.

### When it is worth it
* Search screens with many optional filters.
* Rules reused in several places (validation *and* querying).
* Rules that business people name ("dormant account", "high-risk order").

For two fixed filters, a derived query method (`findByTierAndCountry`) is simpler.

## 🔴 Senior Level

### One rule, two evaluators
The hard problem is keeping the in-memory and SQL versions consistent. One approach is a small specification AST that can be both evaluated and translated:

```java
public sealed interface Spec<T> permits Eq, Gt, And, Or, Not {
    boolean test(T t);
}
public record Eq<T, V>(String field, Function<T, V> getter, V value) implements Spec<T> {
    public boolean test(T t) { return Objects.equals(getter.apply(t), value); }
}
public record And<T>(Spec<T> left, Spec<T> right) implements Spec<T> {
    public boolean test(T t) { return left.test(t) && right.test(t); }
}
// ... Gt, Or, Not

// Translator to JPA Criteria (or jOOQ Condition, or Elasticsearch query)
static <T> Predicate toPredicate(Spec<T> spec, Root<T> root, CriteriaBuilder cb) {
    return switch (spec) {
        case Eq<T, ?> eq   -> cb.equal(root.get(eq.field()), eq.value());
        case And<T> and    -> cb.and(toPredicate(and.left(), root, cb), toPredicate(and.right(), root, cb));
        case Or<T> or      -> cb.or(toPredicate(or.left(), root, cb), toPredicate(or.right(), root, cb));
        case Not<T> not    -> cb.not(toPredicate(not.inner(), root, cb));
        case Gt<T, ?> gt   -> cb.greaterThan(root.get(gt.field()), (Comparable) gt.value());
    };
}
```

Sealed interfaces plus pattern matching for `switch` (Java 21) make the translator exhaustive: adding a new node type without handling it is a compile error. A property-based test can then assert `inMemory(spec).equals(fromDatabase(spec))` for random data.

### Pitfalls
* **Joins multiply rows.** A spec joining a `@OneToMany` returns duplicates; add `query.distinct(true)` and remember that `distinct` plus pagination over joins can force in-memory pagination in Hibernate (`HHH90003004` warning).
* **Index-hostile predicates.** `cb.lower(root.get("email"))` needs a functional index (`CREATE INDEX ON customer (lower(email))`); `like '%x%'` needs trigram (`pg_trgm`) or a search engine.
* **Count queries.** `findAll(spec, pageable)` runs a second `count(*)` with the same predicates; on large tables consider keyset pagination or `Slice` to skip it.
* **Security.** Never build specs from raw field names in request parameters without an allow-list — it becomes a query-injection and data-exposure vector.

### Alternatives
QueryDSL predicates (`QCustomer.customer.tier.eq(PREMIUM)`) and jOOQ `Condition`s offer type-safe composition with less boilerplate than the Criteria API; the pattern is the same — composable, named predicates.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A Specification encapsulates one business rule as an object with `isSatisfiedBy`, and specs compose with and/or/not. It is used for validation, for selecting data, and in Spring Data JPA as composable Criteria API predicates for dynamic queries.

**Must know:**
* It is a named, composable `Predicate` for domain rules.
* Spring Data `JpaSpecificationExecutor.findAll(spec, pageable)` builds SQL dynamically.
* Only add predicates for provided filters — keeps SQL index-friendly.
* Keep in-memory and query versions consistent (shared AST or tests).

**Common follow-ups:**
* How do you avoid duplicates when a spec joins a collection?
* Spec vs QueryDSL vs derived query methods?
* How does this relate to the Interpreter pattern?

**Red flags:** loading all rows and filtering in Java; building predicates from arbitrary client-supplied field names; `(:param IS NULL OR col = :param)` everywhere.
