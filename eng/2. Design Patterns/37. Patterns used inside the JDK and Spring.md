# Patterns used inside the JDK and Spring

---

## 🟢 Junior Level

Interviewers often ask "where have you seen pattern X?". The best answers point to code you use every day. The JDK and Spring are full of classic GoF patterns:

| Pattern | JDK example | Spring example |
| --- | --- | --- |
| Singleton | `Runtime.getRuntime()` | Default bean scope |
| Factory Method | `List.of()`, `Calendar.getInstance()` | `FactoryBean<T>` |
| Builder | `StringBuilder`, `HttpRequest.newBuilder()` | `UriComponentsBuilder`, `RestClient.builder()` |
| Prototype | `Object.clone()` | `@Scope("prototype")` |
| Adapter | `Arrays.asList()`, `InputStreamReader` | `HandlerAdapter` |
| Decorator | `BufferedInputStream`, `Collections.unmodifiableList()` | `TransactionAwareDataSourceProxy` |
| Proxy | `java.lang.reflect.Proxy` | AOP proxies for `@Transactional`, `@Cacheable` |
| Iterator | `Iterator`, `Spliterator` | — |
| Template Method | `AbstractList`, `HttpServlet.service()` | `JdbcTemplate`, `AbstractController` |
| Strategy | `Comparator`, `ThreadPoolExecutor` rejection policies | `PlatformTransactionManager`, `Resource` |
| Observer | `java.util.concurrent.Flow` | `ApplicationEventPublisher` + `@EventListener` |
| Chain of Responsibility | `javax.servlet.FilterChain` | Spring Security `SecurityFilterChain` |
| Command | `Runnable`, `Callable` | `TaskExecutor` jobs |

### Decorator you use without noticing

```java
try (BufferedReader reader = new BufferedReader(           // adds buffering + readLine()
        new InputStreamReader(                             // Adapter: bytes -> chars
            new GZIPInputStream(                           // adds decompression
                new FileInputStream("logs.gz")),           // the real source
            StandardCharsets.UTF_8))) {
    reader.lines().filter(l -> l.contains("ERROR")).forEach(System.out::println);
}
```

Each wrapper implements the same abstraction (`InputStream`/`Reader`) and adds one responsibility.

## 🟡 Middle Level

### Template Method + callback: `JdbcTemplate`

```java
List<Customer> customers = jdbcTemplate.query(
        "select id, name from customer where tier = ?",
        (rs, rowNum) -> new Customer(rs.getLong("id"), rs.getString("name")),  // your step
        "PREMIUM");
```

`JdbcTemplate` owns the invariant algorithm — get connection, prepare statement, execute, iterate, translate `SQLException` into `DataAccessException`, release resources — and calls your `RowMapper` for the variable step. Modern Spring prefers callbacks (Strategy-style lambdas) over subclassing, which is why it is often called "template with callbacks".

### Strategy: pluggable infrastructure

```java
// The service depends on the abstraction; the implementation is chosen by configuration
@Transactional   // uses whatever PlatformTransactionManager bean exists:
                 // JpaTransactionManager, DataSourceTransactionManager, JtaTransactionManager...
public void transfer(...) { }
```

`Resource` is another Strategy: `ClassPathResource`, `FileSystemResource`, `UrlResource` behind one interface, selected by prefix (`classpath:`, `file:`, `https:`) in `ResourceLoader`.

### Observer: application events

```java
public record UserRegistered(long userId, String email) {}

@Service
class Registration {
    private final ApplicationEventPublisher events;
    @Transactional
    public void register(SignUp cmd) {
        long id = users.save(cmd.toUser()).getId();
        events.publishEvent(new UserRegistered(id, cmd.email()));
    }
}

@Component
class WelcomeMail {
    @TransactionalEventListener   // AFTER_COMMIT by default
    @Async
    void on(UserRegistered e) { mailer.sendWelcome(e.email()); }
}
```

### Factory and Builder in modern JDK APIs
* `List.of`, `Map.of`, `Path.of`, `HttpClient.newHttpClient()` — static factory methods that can return hidden, optimized implementations (`ImmutableCollections.List12` for one or two elements).
* `HttpRequest.newBuilder()`, `ProcessBuilder`, `Stream.builder()`, `Locale.Builder` — builders for objects with many optional parts.

## 🔴 Senior Level

### Proxy: how `@Transactional` really works
Spring creates a proxy around beans that need advice. `AbstractAutoProxyCreator` (a `BeanPostProcessor`) decides in `postProcessAfterInitialization`:
* the bean implements interfaces and `proxyTargetClass=false` → **JDK dynamic proxy** (`java.lang.reflect.Proxy`, `InvocationHandler`);
* otherwise → **CGLIB subclass** generated at runtime (Spring Boot defaults to `proxyTargetClass=true`).

The proxy runs an interceptor chain (`TransactionInterceptor`, `CacheInterceptor`, `MethodSecurityInterceptor`...) — itself a Chain of Responsibility via `ReflectiveMethodInvocation.proceed()`:

```java
// Conceptually what TransactionInterceptor does
Object invoke(MethodInvocation mi) throws Throwable {
    TransactionStatus tx = tm.getTransaction(attributesFor(mi.getMethod()));
    try {
        Object result = mi.proceed();          // next interceptor or the target method
        tm.commit(tx);
        return result;
    } catch (RuntimeException | Error ex) {
        tm.rollback(tx);                       // checked exceptions commit by default!
        throw ex;
    }
}
```

Consequences you must be able to explain: self-invocation bypasses the proxy; `final` and `private` methods cannot be advised with CGLIB; checked exceptions do not trigger rollback unless `rollbackFor` is set.

### Lesser-known but interview-worthy
* **Flyweight**: `Integer.valueOf(int)` caches −128..127 (`-XX:AutoBoxCacheMax` widens it); `String` interning and the string deduplication in G1 (`-XX:+UseStringDeduplication`).
* **Abstract Factory**: `DocumentBuilderFactory.newInstance()` and `ServiceLoader` discover provider families via `META-INF/services`; JDBC's `DriverManager` uses the same mechanism.
* **Composite**: `java.awt.Container`; Spring's `CompositeCacheManager`, `CompositePropertySource`.
* **Interpreter**: `java.util.regex.Pattern` compiles to a node tree; Spring Expression Language (`SpelExpressionParser`) builds an AST evaluated against a context.
* **Visitor**: `javax.lang.model.element.ElementVisitor` in annotation processing; `java.nio.file.FileVisitor` for `Files.walkFileTree`.
* **Memento**: `java.io.Serializable` state snapshots; Spring Statemachine persisting state contexts.
* **Mediator**: `java.util.concurrent.Executor` decouples task submitters from workers; Spring Integration channels.

### Why this knowledge matters in production
Recognizing the pattern tells you the failure modes. Knowing `@Async` and `@Transactional` are proxies explains why they silently do nothing on self-calls. Knowing `Arrays.asList` is an *adapter* over the array explains why `add()` throws `UnsupportedOperationException` and why changes write through to the original array. Knowing `Collections.unmodifiableList` is a *decorator* (a view) and `List.copyOf` is a *copy* explains why the first still reflects changes to the underlying list.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The JDK and Spring are built from classic patterns: I/O streams are decorators, `JdbcTemplate` is template-method-with-callbacks, transaction managers are strategies, application events are observers, security filters are a chain of responsibility, and `@Transactional`/`@Cacheable` are proxies with interceptor chains.

**Must know:**
* JDK proxy vs CGLIB proxy, and the self-invocation pitfall.
* Decorator vs Proxy: same structure, different intent (add behavior vs control access).
* `Arrays.asList` (adapter, fixed-size) vs `List.of` (immutable factory) vs `unmodifiableList` (view).
* `ServiceLoader` = provider discovery (Abstract Factory family).

**Common follow-ups:**
* Why does `@Transactional` not roll back on a checked exception?
* Where is Chain of Responsibility in Spring Security?
* Which pattern is `Comparator`?

**Red flags:** naming patterns without concrete JDK/Spring examples; claiming Spring beans are GoF singletons (they are singleton *per container*).
