# Service Layer and Transaction Script vs Domain Model

---

## 🟢 Junior Level

These are three patterns from Martin Fowler's *Patterns of Enterprise Application Architecture* that describe **where business logic lives**:

* **Transaction Script** — each use case is one procedure that does everything: load data, check rules, change data, save. Entities are plain data holders.
* **Domain Model** — business rules live *inside* objects that have both data and behavior (`order.cancel()`, `account.withdraw(amount)`).
* **Service Layer** — a thin layer of application services that defines the use cases, opens transactions, and coordinates domain objects and repositories. It works with either style.

### Real-world analogy
A *transaction script* is a checklist the cashier follows for every refund. A *domain model* is a trained cashier who knows the refund rules by heart — you just say "refund this" and they decide. The *service layer* is the shop manager who receives the request, makes sure the till is open, and hands it to the right person.

### The same use case two ways

```java
// Transaction Script: logic lives in the service, Order is a data bag
@Transactional
public void cancelOrder(long orderId) {
    OrderEntity order = orders.findById(orderId).orElseThrow();
    if (order.getStatus().equals("SHIPPED")) {
        throw new IllegalStateException("Cannot cancel a shipped order");
    }
    order.setStatus("CANCELLED");
    order.setCancelledAt(Instant.now());
    payments.refund(order.getPaymentId(), order.getTotal());
}
```

```java
// Domain Model: the rule is part of the Order itself
public class Order {
    private OrderStatus status;
    private Instant cancelledAt;

    public void cancel(Clock clock) {
        if (status == OrderStatus.SHIPPED) {
            throw new OrderAlreadyShippedException(id);
        }
        status = OrderStatus.CANCELLED;
        cancelledAt = clock.instant();
    }
}
```

## 🟡 Middle Level

### Service Layer responsibilities

```java
@Service
public class OrderApplicationService {
    private final Orders orders;
    private final PaymentGateway payments;
    private final Clock clock;

    // ... constructor

    @Transactional
    public void cancel(CancelOrderCommand cmd) {
        Order order = orders.get(cmd.orderId());   // load aggregate
        order.cancel(clock);                       // domain rule
        payments.refund(order.paymentId(), order.total()); // side effect
        // no explicit save: JPA dirty checking flushes at commit
    }
}
```

The service layer should own:
* **Transaction boundaries** (`@Transactional` belongs here, not on controllers or repositories).
* **Security checks** (`@PreAuthorize`), input validation, mapping DTOs to commands.
* **Orchestration** across aggregates and external systems.

It should *not* contain business rules that belong to one entity — those leak into "god services" and get duplicated.

### Choosing between them

| Factor | Transaction Script | Domain Model |
| --- | --- | --- |
| Business rules | Few, simple | Many, interacting invariants |
| Team skill / time | Fast to write | Needs modeling effort |
| Change over time | Duplication grows with each new script | Rules stay in one place |
| Testing | Integration-heavy | Rules unit-testable without Spring |
| Persistence | Any (JDBC, jOOQ, JPA) | Works best with an ORM or careful mapping |

Fowler's curve: transaction scripts are cheaper at first, but the cost of each new feature grows faster as complexity rises. A CRUD admin panel is fine as scripts; a pricing or claims engine is not.

### The anemic domain model smell
An *anemic* model has entities with getters/setters and services full of `if (order.getStatus() == ...)`. It looks like a Domain Model but is really Transaction Script with extra ceremony. Signs:
* Entities have no methods other than accessors.
* The same rule (e.g. "cannot cancel shipped orders") appears in several services.
* Invariants can be broken by any caller via setters.

## 🔴 Senior Level

### Protecting invariants in a JPA domain model

```java
@Entity
@Table(name = "orders")
public class Order {
    @Id private UUID id;
    @Enumerated(EnumType.STRING) private OrderStatus status;
    @Version private long version;                         // optimistic locking for concurrent cancels

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private final List<OrderLine> lines = new ArrayList<>();

    protected Order() { }                                  // for JPA only

    public void addLine(Sku sku, int qty, Money price) {
        requireStatus(OrderStatus.DRAFT);
        if (qty <= 0) throw new IllegalArgumentException("qty must be positive");
        lines.add(new OrderLine(this, sku, qty, price));
    }

    public Money total() {
        return lines.stream().map(OrderLine::subtotal).reduce(Money.ZERO, Money::add);
    }

    public List<OrderLine> lines() { return Collections.unmodifiableList(lines); }

    private void requireStatus(OrderStatus expected) {
        if (status != expected) throw new IllegalOrderStateException(id, status, expected);
    }
}
```

Techniques: no public setters, a protected no-arg constructor for the ORM, unmodifiable collection views, value objects (`Money`, `Sku`) for validation, and `@Version` so two concurrent cancels cannot both succeed.

### Domain events instead of service sprawl
When cancelling must also release stock and notify the customer, do not keep adding calls to the service. Record events in the aggregate and publish them after commit:

```java
public class Order extends AbstractAggregateRoot<Order> {   // Spring Data helper
    public void cancel(Clock clock) {
        // ... rule checks and state change
        registerEvent(new OrderCancelled(id, clock.instant()));
    }
}

@Component
class StockListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(OrderCancelled e) { stock.release(e.orderId()); }
}
```

Spring Data publishes `registerEvent`s when `save()` is called on the repository. `AFTER_COMMIT` guarantees listeners never see rolled-back state; for cross-service delivery, use a transactional outbox instead of in-memory events.

### Performance and pragmatism
* A rich model loaded through JPA can trigger N+1 queries (`order.total()` touching lazy lines). Load aggregates with fetch joins or entity graphs per use case.
* Read-heavy screens don't need the domain model at all — query DTO projections directly (a light form of CQRS).
* Mixing styles is normal: domain model for the core subdomain, transaction scripts for supporting CRUD subdomains.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Transaction Script puts each use case's logic in one procedure; Domain Model puts business rules inside the entities that own the data; the Service Layer defines use cases, transactions and orchestration on top of either. Pick scripts for simple CRUD and a domain model when rules are complex and change often.

**Must know:**
* `@Transactional` belongs on the service layer.
* Anemic domain model = scripts disguised as objects.
* Rich models need encapsulation: no setters, value objects, invariants in methods.
* `@Version` protects aggregate invariants under concurrency.
* Domain events decouple side effects; `AFTER_COMMIT` avoids acting on rolled-back state.

**Common follow-ups:**
* Is an anemic domain model always bad?
* Where do you put validation that needs a database lookup?
* How do domain events relate to the outbox pattern?

**Red flags:** business rules in controllers; entities with public setters for every field "because JPA needs them"; one `OrderService` with 3,000 lines.
