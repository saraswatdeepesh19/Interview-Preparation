# Object Pool and connection pools

---

## 🟢 Junior Level

The **Object Pool** pattern keeps a set of ready-to-use, expensive objects. Instead of creating and destroying one each time, a client **borrows** an object from the pool, uses it, and **returns** it. The best-known example in Java backends is the **database connection pool** (HikariCP, the Spring Boot default).

### Real-world analogy
A bike-sharing station. Building a bike for every trip would be absurd; instead there is a fixed number of bikes. You take one, ride, and dock it. If all bikes are out, you wait — or give up after a while.

### Why connections are pooled
Opening a PostgreSQL connection means a TCP handshake, TLS negotiation, authentication (SCRAM), and the server forking a backend process — typically **5–50 ms**. A query on an indexed table can take **under 1 ms**. Without a pool, connection setup would dominate every request.

```java
// Borrow and return — try-with-resources returns the connection to the pool
try (Connection conn = dataSource.getConnection();               // borrow
     PreparedStatement ps = conn.prepareStatement("select name from customer where id = ?")) {
    ps.setLong(1, id);
    try (ResultSet rs = ps.executeQuery()) {
        return rs.next() ? rs.getString(1) : null;
    }
}                                                               // close() = return to pool, not a real close
```

`dataSource` is a `HikariDataSource`; `conn` is a proxy whose `close()` hands the physical connection back.

## 🟡 Middle Level

### What a pool must handle
* **Bounded size** — `maximumPoolSize` caps concurrent connections so the database is protected.
* **Waiting with a timeout** — if all are busy, `getConnection()` blocks up to `connectionTimeout` (default 30 s in Hikari) and then throws `SQLTransientConnectionException`.
* **Validation** — connections can die (DB restart, firewall idle timeout). Hikari uses JDBC4 `Connection.isValid()` when a connection has been idle.
* **Lifetime** — `maxLifetime` (default 30 min) retires connections before infrastructure (load balancers, PgBouncer, cloud proxies) kills them silently.
* **Reset on return** — rollback uncommitted work, restore auto-commit, isolation level, read-only flag, so the next borrower gets a clean connection.

### Spring Boot configuration

```yaml
spring:
  datasource:
    url: jdbc:postgresql://db:5432/app
    hikari:
      maximum-pool-size: 10        # fixed size: minimum-idle defaults to the same value
      connection-timeout: 2000     # fail fast (ms) instead of piling up requests for 30 s
      max-lifetime: 1680000        # 28 min: shorter than any infra idle cutoff
      leak-detection-threshold: 20000  # log stack trace if a connection is held > 20 s
      pool-name: app-pool
```

### Other pooled resources
* Threads (`ThreadPoolExecutor`) — pooling execution contexts.
* HTTP connections (Apache HttpClient `PoolingHttpClientConnectionManager`, Reactor Netty `ConnectionProvider`).
* Byte buffers (Netty `PooledByteBufAllocator`) to reduce GC pressure for off-heap memory.

### When *not* to pool
Pooling cheap objects (DTOs, `StringBuilder`, small collections) is an anti-pattern on modern JVMs: allocation in the TLAB is a pointer bump, and young-generation GC of short-lived objects is nearly free. Pooled objects live long, get promoted to the old generation, and add synchronization plus reset bugs.

## 🔴 Senior Level

### How HikariCP stays fast
* **`ConcurrentBag`** — each thread first checks a `ThreadLocal` list of connections it used before (lock-free reuse), then a shared `CopyOnWriteArrayList` scanned with CAS on each entry's state, and only then waits on a `SynchronousQueue` hand-off.
* **Bytecode-level proxies** — `ProxyConnection`/`ProxyStatement` are generated with Javassist at build time to minimize call overhead and track open statements for cleanup.
* **`FastList`** — an `ArrayList` without range checks that removes from the tail first, because statements are usually closed in reverse order of opening.

### Sizing: smaller than you think
A database executes roughly as many queries in parallel as it has CPU cores plus effective disk spindles. Beyond that, extra connections only add context switching and lock contention. The PostgreSQL wiki/HikariCP starting point:

```
connections = (core_count * 2) + effective_spindle_count
```

Then reason about the *whole fleet*: 20 pods × pool size 10 = 200 connections; PostgreSQL's `max_connections` default is 100 and each backend costs several MB of RAM. This is why large deployments put **PgBouncer** (transaction pooling) in front of PostgreSQL — the application pool becomes a pool of connections to PgBouncer, which multiplexes them onto a small number of server connections. Caveat: in transaction mode, session state (`SET`, advisory locks, server-side prepared statements) does not survive between transactions; use `prepareThreshold=0` with older PgBouncer versions.

### Pool deadlock
If one request needs **two** connections at once (e.g. `REQUIRES_NEW` inside an open transaction) and the pool size is `N`, then `N` concurrent requests can each hold one connection and wait forever for a second:

```java
@Transactional                          // holds connection #1
public void placeOrder(Order o) {
    orders.save(o);
    auditService.recordInNewTx(o);      // @Transactional(propagation = REQUIRES_NEW) needs connection #2
}
```

Mitigations: avoid nested `REQUIRES_NEW` on hot paths, size the pool as `threads × (maxConnectionsPerRequest − 1) + 1`, and keep `connectionTimeout` short so the failure is visible.

### Diagnosing pool exhaustion
Symptoms: latency spikes, then `Connection is not available, request timed out after 2000ms`. Check, in this order:
1. Hikari metrics via Micrometer: `hikaricp_connections_active`, `_pending`, `_usage_seconds`, `_acquire_seconds`.
2. `leak-detection-threshold` stack traces — code holding a connection during a slow HTTP call is the classic cause.
3. Slow queries in `pg_stat_activity` (`state = 'active'`, long `now() - query_start`) or lock waits (`wait_event_type = 'Lock'`).
4. Open Session in View (`spring.jpa.open-in-view=true`, the default) keeps the connection for the whole web request including view rendering — disable it.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Object Pool reuses expensive objects by borrowing and returning them. Connection pools are the canonical case: they amortize connection setup, cap concurrency to protect the database, validate and retire connections, and reset state on return. Keep pools small and fail fast on exhaustion.

**Must know:**
* `close()` on a pooled connection returns it, it does not disconnect.
* Key Hikari settings: `maximumPoolSize`, `connectionTimeout`, `maxLifetime`, `leakDetectionThreshold`.
* Size from database capacity and fleet size, not from request rate.
* Don't pool cheap objects on modern JVMs.
* Nested transactions needing a second connection can deadlock the pool.

**Common follow-ups:**
* What happens when the pool is exhausted?
* Why is a pool of 100 often slower than a pool of 10?
* What does PgBouncer transaction mode break?

**Red flags:** "set the pool to 200 to handle more traffic"; holding a connection while calling external services; leaving open-in-view on.
