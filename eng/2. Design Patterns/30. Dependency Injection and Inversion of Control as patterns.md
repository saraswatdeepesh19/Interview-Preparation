# Dependency Injection and Inversion of Control as patterns

---

## 🟢 Junior Level

**Inversion of Control (IoC)** is a principle: a component does not create or look up its own collaborators — something outside it decides what it gets. **Dependency Injection (DI)** is the most common way to apply IoC: collaborators are *passed in* (through a constructor, setter, or field) instead of being created with `new` inside the class.

### Real-world analogy
A restaurant chef does not grow vegetables or forge knives. The kitchen manager hands the chef the tools and ingredients for the shift. The chef only knows *what* a knife must do, not which factory made it. Swapping the supplier does not require retraining the chef.

### Without and with DI

```java
// Tight coupling: the service decides which repository and clock to use
public class InvoiceService {
    private final InvoiceRepository repo = new JdbcInvoiceRepository("jdbc:postgresql://prod/db");
    private final Clock clock = Clock.systemUTC();

    public Invoice issue(Order order) {
        Invoice invoice = new Invoice(order.id(), order.total(), LocalDate.now(clock));
        return repo.save(invoice);
    }
}
```

```java
// Dependency Injection: collaborators come from outside
public class InvoiceService {
    private final InvoiceRepository repo;
    private final Clock clock;

    public InvoiceService(InvoiceRepository repo, Clock clock) {
        this.repo = repo;
        this.clock = clock;
    }

    public Invoice issue(Order order) {
        Invoice invoice = new Invoice(order.id(), order.total(), LocalDate.now(clock));
        return repo.save(invoice);
    }
}

// Wiring ("composition root") happens in one place
InvoiceService service = new InvoiceService(new JdbcInvoiceRepository(dataSource), Clock.systemUTC());
```

The second version can be unit-tested with an in-memory repository and a fixed clock — no database, no time-dependent flakiness.

## 🟡 Middle Level

### IoC is broader than DI
IoC shows up in several patterns — DI is just one:

| Mechanism | Who is in control | Example |
| --- | --- | --- |
| Dependency Injection | Container/composition root supplies dependencies | Spring constructor injection |
| Service Locator | Component *asks* a registry | `ServiceLoader.load(Driver.class)`, JNDI |
| Template Method | Framework calls your hook methods | `HttpServlet.doGet`, `JdbcTemplate` callbacks |
| Callbacks / events | Framework calls your listener | `@EventListener`, `Runnable` passed to an executor |

The "Hollywood principle" — *don't call us, we'll call you* — is the common idea.

### Injection styles and their trade-offs

```java
@Service
public class PaymentService {
    private final PaymentGateway gateway;            // constructor injection: required, immutable
    private FraudScorer fraudScorer;                 // setter injection: optional, replaceable

    public PaymentService(PaymentGateway gateway) {  // single constructor: @Autowired not needed
        this.gateway = gateway;
    }

    @Autowired(required = false)
    public void setFraudScorer(FraudScorer fraudScorer) {
        this.fraudScorer = fraudScorer;
    }
}
```

* **Constructor injection** — preferred. Dependencies are `final`, the object is valid immediately after construction, missing beans fail at startup, and tests can call `new` directly.
* **Setter injection** — for genuinely optional dependencies or reconfiguration.
* **Field injection** (`@Autowired private Foo foo;`) — hides dependencies, prevents `final`, requires reflection in tests. Avoid in production code.

### DI vs Service Locator

```java
// Service Locator: dependency is hidden inside the method body
public class ReportJob {
    public void run() {
        ReportRepository repo = ServiceLocator.get(ReportRepository.class); // hidden coupling
        repo.findDue().forEach(this::send);
    }
}
```

Service Locator still inverts creation, but the API of `ReportJob` lies: its constructor says it needs nothing. Tests must configure a global registry, and missing registrations fail at *call* time instead of startup. DI makes the dependency graph explicit in signatures.

### Common mistakes
* **Too many constructor parameters** (7+) — the DI container did not cause the problem, it exposed it: the class has too many responsibilities.
* **Injecting the container** (`ApplicationContext`) into business code — that is a Service Locator in disguise.
* **Circular dependencies** — `A → B → A`. Spring Boot 2.6+ forbids them by default (`spring.main.allow-circular-references=false`); redesign instead of switching to field injection.

## 🔴 Senior Level

### How a DI container actually builds the graph
Spring builds the object graph in two phases:

1. **Bean definition phase** — component scanning, `@Configuration` classes and auto-configuration register `BeanDefinition`s (class, scope, constructor args, qualifiers). `BeanFactoryPostProcessor`s (e.g. `PropertySourcesPlaceholderConfigurer`, `ConfigurationClassPostProcessor`) can still change definitions.
2. **Instantiation phase** — for each singleton, `AbstractAutowireCapableBeanFactory.createBean()` resolves constructor arguments (recursively), instantiates, populates properties, runs `Aware` callbacks, `BeanPostProcessor.postProcessBeforeInitialization`, `@PostConstruct`/`afterPropertiesSet`, then `postProcessAfterInitialization` — where AOP proxies are created.

Because proxies are created *after* initialization, the bean you inject may be a JDK dynamic proxy or CGLIB subclass, not your class. That is why self-invocation bypasses `@Transactional`.

### Resolution rules worth knowing

```java
public interface Notifier { void send(String msg); }

@Component @Primary class EmailNotifier implements Notifier { /* ... */ }
@Component("sms") class SmsNotifier implements Notifier { /* ... */ }

@Service
class AlertService {
    AlertService(Notifier primary,                       // EmailNotifier (@Primary)
                 @Qualifier("sms") Notifier sms,         // SmsNotifier
                 List<Notifier> all,                     // both, ordered by @Order/Ordered
                 ObjectProvider<AuditSink> audit) {      // lazy and optional: no failure if absent
        // ...
    }
}
```

* Ambiguity without `@Primary`/`@Qualifier` fails at startup with `NoUniqueBeanDefinitionException` — a feature, not a bug.
* `ObjectProvider<T>` gives lazy, optional and prototype-safe access (`getIfAvailable()`, `stream()`), replacing most uses of `@Lazy` and `Optional<T>` injection.
* Injecting a **prototype** into a singleton gives you *one* instance forever; use `ObjectProvider<T>.getObject()` or `@Lookup` methods to get a fresh one per call.

### DI without a container
DI is a pattern, not a framework. In libraries, CLIs, and AWS Lambda functions (where cold start matters), a hand-written composition root is often better:

```java
public final class Main {
    public static void main(String[] args) {
        HikariDataSource ds = new HikariDataSource(DbConfig.fromEnv());
        Clock clock = Clock.systemUTC();
        InvoiceRepository repo = new JdbcInvoiceRepository(ds);
        InvoiceService invoices = new InvoiceService(repo, clock);
        new HttpServer(new InvoiceController(invoices)).start(8080);
    }
}
```

Compile-time DI frameworks (Dagger, Micronaut, Quarkus ArC, Spring AOT) generate this wiring code at build time: no reflection or classpath scanning at startup, which also makes GraalVM native images possible.

### Design consequences at scale
* **The composition root is architecture.** Keeping all wiring in configuration (not scattered `new` calls) is what makes hexagonal architecture practical: adapters are swapped at the root.
* **Depend on abstractions you own.** Injecting `JpaRepository<Order, Long>` into the domain couples it to Spring Data; injecting your own `Orders` port keeps the domain framework-free.
* **Startup cost** grows with the number of beans and auto-configurations. Use `spring.main.lazy-initialization=true` carefully (it hides wiring errors until first use) and measure with `ApplicationStartup`/`BufferingApplicationStartup`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** IoC means a component gives up control over creating its collaborators; DI is the most common form of IoC, where dependencies are passed in, ideally through the constructor. It makes dependencies explicit, enables testing with fakes, and lets one composition root decide which implementations are used.

**Must know:**
* IoC is the principle; DI, Service Locator, Template Method and callbacks are mechanisms.
* Prefer constructor injection: immutability, fail-fast, testability.
* Spring resolves by type, then `@Primary`, then `@Qualifier`/bean name.
* Injected beans may be proxies; self-invocation bypasses them.
* DI does not need a container; compile-time DI avoids reflection.

**Common follow-ups:**
* Why is field injection discouraged?
* How do you inject a prototype bean into a singleton?
* What is the difference between DI and Service Locator?
* How does Spring detect circular dependencies?

**Red flags:** "DI means using `@Autowired`"; injecting `ApplicationContext` everywhere; solving circular dependencies with field injection.
