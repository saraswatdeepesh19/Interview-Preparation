# Choosing the right pattern and avoiding pattern overuse

---

## 🟢 Junior Level

Design patterns are **names for proven solutions to recurring problems**. They are useful when the problem actually exists. Applying them "just in case" produces code that is harder to read, slower to change, and full of indirection nobody needs. This is called **pattern overuse** or *patternitis*.

### Real-world analogy
A professional kitchen has a dozen knife types. Using a cleaver to peel a grape is still the wrong choice. Knowing the tools is good; picking the smallest one that does the job is the skill.

### Start from the problem, not the pattern

| You notice... | Consider... |
| --- | --- |
| A growing `switch` on a type code that changes behavior | Strategy or polymorphism |
| Object construction with 8 optional parameters | Builder (or a record + factory method) |
| You must call a legacy API with an incompatible interface | Adapter |
| Several objects must react when something happens | Observer / domain events |
| Cross-cutting behavior (logging, caching, retries) around calls | Decorator / Proxy |
| Complex subsystem used from many places | Facade |
| None of the above | Plain code. No pattern. |

### Over-engineered vs enough

```java
// Overuse: an interface, a factory and a strategy for one fixed formula
interface TaxStrategy { BigDecimal tax(BigDecimal amount); }
class DefaultTaxStrategy implements TaxStrategy { /* 20% */ }
class TaxStrategyFactory { static TaxStrategy create() { return new DefaultTaxStrategy(); } }

// Enough: one rule, one method. Extract a strategy when a second rule actually appears.
static BigDecimal tax(BigDecimal amount) {
    return amount.multiply(new BigDecimal("0.20")).setScale(2, RoundingMode.HALF_EVEN);
}
```

## 🟡 Middle Level

### Heuristics that prevent overuse
* **Rule of three** — extract an abstraction on the third occurrence, not the first.
* **YAGNI** — "You Aren't Gonna Need It": do not add extension points for requirements nobody has stated.
* **Count the hops** — if reading one behavior requires jumping through interface → factory → abstract class → implementation, the indirection has a cost every time someone debugs it.
* **Prefer language features** — Java 8+ lambdas replace many one-method Strategy/Command classes; records replace many Builders for small value objects; sealed interfaces + pattern matching replace many Visitors; `enum` with methods replaces State for small finite machines.

```java
// Strategy as a lambda map instead of a class hierarchy
private static final Map<ShippingMethod, Function<Parcel, Money>> PRICING = Map.of(
        ShippingMethod.STANDARD, p -> Money.eur(4.90),
        ShippingMethod.EXPRESS,  p -> Money.eur(9.90).plus(p.weightKg() * 0.5),
        ShippingMethod.PICKUP,   p -> Money.ZERO);

Money price(Parcel p) { return PRICING.get(p.method()).apply(p); }
```

### Pattern smells in code review
* `*Factory` classes with exactly one `create()` that calls `new` on exactly one implementation.
* Interfaces with a single implementation and no test double — "header interfaces" added by habit.
* `AbstractBaseService<T, ID, DTO, MAPPER>` hierarchies that every service must extend.
* Singletons used as global mutable state.
* Visitor over a hierarchy that changes more often than its operations.

### When patterns *are* the right call
* Public library or framework APIs, where callers need stable extension points.
* Boundaries to unstable external systems (Adapter, Anti-Corruption Layer).
* Behavior variations that already exist in production and keep growing.

## 🔴 Senior Level

### A decision process you can defend
1. **Name the force.** What varies, and how often? Who changes it — developers, configuration, or end users?
2. **Locate the volatility.** Put the seam (interface, function, event) exactly where change happens, nowhere else.
3. **Price the indirection.** Each abstraction costs readability, navigation, and runtime (megamorphic call sites, allocation, reflection-based proxies). Is the cost paid back by real flexibility?
4. **Prefer reversible choices.** Inline code is easy to refactor into a pattern later; removing a widely used abstraction is expensive. Keep it simple while the cost of change is low.
5. **Write it down.** For architectural patterns (CQRS, event sourcing, hexagonal), record the decision and its trade-offs in an ADR.

### Runtime cost is real at scale
* **Megamorphic dispatch**: HotSpot inlines call sites with one or two receiver types (monomorphic/bimorphic inline caches). With three or more implementations at a hot call site, the JIT falls back to a vtable/itable call and can't inline, which blocks escape analysis and other optimizations. A deep Strategy/Decorator stack on a hot path can show up in profiles.
* **Proxy layers**: each Spring AOP proxy adds an interceptor chain; stacking `@Transactional`, `@Cacheable`, `@Retryable`, `@Timed` on hot methods costs allocations and stack depth — measure with JFR before and after.
* **Reflection and dynamic proxies** slow startup and complicate GraalVM native images (need reflection configuration).

### Organizational patterns of overuse
* **Speculative generality** at service level: a "generic rules engine" built for one rule set. Ten rules in code are cheaper than a DSL nobody else uses.
* **Copying architecture from big tech**: microservices + CQRS + event sourcing for a team of four building a CRUD app. Choose the architecture for your scale, team size and domain complexity, not for the conference talk.
* **Inconsistent pattern vocabulary**: a class named `OrderStrategy` that is actually a State confuses everyone; naming accuracy matters as much as the code.

### How to answer in an interview
Show judgment, not memorization: "I'd start with a simple conditional. When the second payment provider arrived, I extracted a `PaymentGateway` interface with one adapter per provider, because each provider changed independently and needed its own error mapping. I did not add a factory — Spring injects a `Map<String, PaymentGateway>` keyed by bean name, which covers selection."

## 🎯 Interview Cheat Sheet

**30-second pitch:** Patterns are tools for specific forces, not goals. I start from the problem — what varies and how often — put the abstraction exactly at that seam, prefer modern language features over class hierarchies, and introduce patterns when duplication or volatility is real, not speculative.

**Must know:**
* YAGNI, rule of three, KISS.
* Lambdas, records, enums and sealed types replace many classic GoF implementations.
* Indirection has readability and runtime costs (megamorphic calls, proxies).
* Patterns pay off at unstable boundaries and in public APIs.

**Common follow-ups:**
* Give an example where you removed a pattern.
* When is an interface with one implementation justified?
* How would you refactor a huge `switch` safely?

**Red flags:** listing patterns used "because it's best practice"; factories for everything; refusing any pattern on principle.
