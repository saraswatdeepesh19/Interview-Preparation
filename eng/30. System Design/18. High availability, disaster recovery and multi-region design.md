# High availability, disaster recovery and multi-region design

---

## 🟢 Junior Level

* **High availability (HA)** — the system keeps working when *components* fail (a server, a disk, an availability zone). Measured as uptime: 99.9% ≈ 8.8 hours of downtime per year, 99.99% ≈ 53 minutes.
* **Disaster recovery (DR)** — the ability to restore service after a *large-scale* failure (region outage, data corruption, ransomware, accidental deletion).

Two numbers define DR requirements:
* **RPO (Recovery Point Objective)** — how much data you can afford to lose (e.g. 5 minutes of writes).
* **RTO (Recovery Time Objective)** — how long you can be down (e.g. 1 hour).

### Building blocks of HA
* **Redundancy** — at least two instances of every component, spread across **availability zones** (separate data centers in one region).
* **Health checks and automatic failover** — load balancers stop sending traffic to unhealthy instances; databases fail over to a standby.
* **Stateless services** — any instance can serve any request; state lives in replicated databases/caches.
* **No single points of failure** — including DNS, load balancers, secrets stores, and CI/CD needed for recovery.

---

## 🟡 Middle Level

### DR strategies (cost vs RTO/RPO)

| Strategy | Setup | RTO | RPO | Cost |
| --- | --- | --- | --- | --- |
| **Backup & restore** | Regular backups copied to another region | Hours–days | Hours (last backup) / minutes with PITR | $ |
| **Pilot light** | Core data replicated; minimal infra off or tiny in DR region | Tens of minutes–hours | Minutes | $$ |
| **Warm standby** | Scaled-down full stack running in DR region | Minutes | Seconds–minutes | $$$ |
| **Multi-site active-active** | Full capacity in 2+ regions serving traffic | ~0 (traffic shift) | ~0–seconds | $$$$ |

### Data is the hard part
* Stateless compute is easy to replicate; **data** needs asynchronous cross-region replication (e.g. Aurora Global Database < 1 s typical lag, PostgreSQL streaming replicas, DynamoDB Global Tables, S3 cross-region replication).
* **Async replication** means a region loss can lose the last seconds of writes (RPO > 0). Synchronous cross-region replication costs ~50–150 ms per write (speed of light) — rarely acceptable for OLTP.
* **Backups are still required**: replication faithfully copies corruption and `DROP TABLE`. Keep point-in-time recovery, immutable backups (object lock) and **test restores** regularly.

### Within one region: multi-AZ by default
Spread pods with topology spread constraints / anti-affinity, run databases in Multi-AZ mode, use zone-redundant load balancers. Capacity planning: with 3 AZs, each AZ should handle ~50% of peak so losing one still leaves ≥ 100% (N+1).

## 🔴 Senior Level

### Active-active multi-region design questions
1. **Routing** — latency-based DNS (Route 53), anycast/global load balancers (Cloudflare, Google GLB), with health-checked failover. DNS TTLs and client caching delay failover; global anycast reacts faster.
2. **Data ownership** — which region accepts writes for which data?
   * *Single-writer per record* (home region per user/tenant): writes routed to the home region; reads served locally from replicas. Avoids conflicts, keeps strong consistency per entity.
   * *Multi-writer*: any region accepts writes; requires conflict resolution (last-writer-wins, CRDTs, application merge). Suitable for commutative data (likes, carts) — dangerous for balances or inventory.
   * *Globally consistent database* (Spanner, CockroachDB, YugabyteDB): consensus across regions gives serializable transactions at the cost of cross-region write latency.
3. **Consistency expectations** — read-your-writes after failover? Session stickiness to a region?
4. **Dependencies** — every dependency (auth, payments, config, secrets, queues) must also be multi-region or have a fallback; a "multi-region" app depending on a single-region IdP is single-region.
5. **Failover mechanics** — automatic vs manual promotion; fencing the old primary region to avoid split brain; runbooks; data reconciliation after failback.

### Cell-based architecture
Partition customers into independent **cells** (complete stacks, each serving a subset of tenants), possibly per region. A bad deploy, poison input or overload affects one cell. A thin routing layer maps tenant → cell. This limits blast radius far more than "one big multi-region system".

### Testing and operations
* **Game days**: fail over a region on purpose (start with read traffic, then writes); measure actual RTO/RPO against targets.
* **Static stability**: the surviving region must not need to *provision* capacity during the event (control planes may be overwhelmed) — pre-provision or keep warm capacity.
* **Dependency mapping**: identify hidden single-region dependencies (container registry, CI, DNS provider, certificate issuance).
* **Cost awareness**: active-active roughly doubles infrastructure and adds cross-region data transfer costs; justify with business impact of downtime.

### DNS failover between regions (Terraform)

```hcl
resource "aws_route53_health_check" "primary" {
  fqdn              = "api.eu-central-1.shop.com"
  type              = "HTTPS"
  resource_path     = "/actuator/health/readiness"
  failure_threshold = 3
  request_interval  = 10
}

resource "aws_route53_record" "api_primary" {
  zone_id         = var.zone_id
  name            = "api.shop.com"
  type            = "CNAME"
  ttl             = 30                               # short TTL so clients follow failover quickly
  records         = ["api.eu-central-1.shop.com"]
  set_identifier  = "primary"
  health_check_id = aws_route53_health_check.primary.id
  failover_routing_policy { type = "PRIMARY" }
}

resource "aws_route53_record" "api_secondary" {
  zone_id        = var.zone_id
  name           = "api.shop.com"
  type           = "CNAME"
  ttl            = 30
  records        = ["api.eu-west-1.shop.com"]        # warm standby region
  set_identifier = "secondary"
  failover_routing_policy { type = "SECONDARY" }
}
```

DNS failover only moves traffic; the standby region still needs replicated data (for example Aurora Global Database promotion) and enough warm capacity — rehearse the whole sequence in game days.

## 🎯 Interview Cheat Sheet

**30-second pitch:** HA handles component failures through redundancy across availability zones, stateless services and automatic failover; DR handles regional disasters and data loss, sized by RPO and RTO from backup-and-restore through pilot light and warm standby to active-active. Data replication is the hard part — async cross-region replication loses some writes, backups are still needed, and active-active requires a write-ownership model such as home regions, conflict resolution, or a globally consistent database.

**Must know:**
* Nines → downtime; RPO vs RTO.
* Multi-AZ N+1 capacity.
* DR strategy ladder and costs.
* Async replication lag, PITR, immutable backups, restore tests.
* Active-active data ownership options; cells; static stability.

**Common follow-ups:**
* Design checkout to survive a region outage.
* How do you avoid split brain on regional failover?
* Why isn't replication a backup?

**Red flags:** "multi-region" with single-region dependencies; never-tested backups; multi-writer for financial balances with LWW.
