# Distributed ID generation with Snowflake, UUID and ULID

---

## 🟢 Junior Level

A single database can hand out IDs with an auto-increment sequence. In a distributed system — many services, many database shards, offline clients — you need IDs that are **unique without coordination**, and ideally **sortable by time** and **compact**.

| Scheme | Size | Sortable by time | Coordination | Notes |
| --- | --- | --- | --- | --- |
| DB sequence / auto-increment | 64-bit | Yes (roughly) | Central DB | Simple; a bottleneck/SPOF across shards |
| UUIDv4 (random) | 128-bit | No | None | Universally supported; bad B-tree locality |
| **UUIDv7** (RFC 9562) | 128-bit | **Yes** (ms timestamp prefix) | None | Modern default for DB keys |
| ULID | 128-bit (26-char Crockford base32) | Yes | None | Like UUIDv7, URL-friendly text form |
| **Snowflake** | 64-bit | Yes | Worker ID assignment | Twitter-style; fits in `bigint` |

```java
UUID random = UUID.randomUUID();   // v4: 122 random bits, e.g. 3b241101-e2bb-4255-8caf-4136c566a962
```

The JDK has no built-in UUIDv7 generator yet; libraries such as `java-uuid-generator` (`Generators.timeBasedEpochGenerator()`) or `uuid-creator` provide one, and recent Hibernate versions offer time-based styles for `@UuidGenerator` — check your version's documentation.

## 🟡 Middle Level

### Why random UUIDs hurt databases
B-tree primary key indexes keep keys sorted. Random v4 UUIDs insert at **random positions**, causing page splits, poor cache locality (the "hot" index pages are everywhere), write amplification and index bloat — very noticeable in MySQL/InnoDB (clustered primary key) and visible in PostgreSQL at high insert rates. **Time-ordered IDs** (UUIDv7, ULID, Snowflake) append near the end of the index like a sequence.

### UUIDv7 layout

```
 48 bits unix_ts_ms | 4 bits version (7) | 12 bits rand_a | 2 bits variant | 62 bits rand_b
```

Monotonic within a millisecond if the generator uses a counter in `rand_a` (RFC 9562 method 1/3). Store as PostgreSQL `uuid` (16 bytes), not as text (36 bytes).

### Snowflake layout (Twitter)

```
 1 bit sign | 41 bits timestamp (ms since custom epoch) | 10 bits worker id | 12 bits sequence
```

* 41 bits of milliseconds ≈ 69 years from the chosen epoch.
* 10 bits → 1,024 workers; 12 bits → 4,096 IDs per millisecond per worker (≈ 4M/s per worker).

```java
public final class Snowflake {
    private static final long EPOCH = 1_704_067_200_000L;          // 2024-01-01T00:00:00Z
    private final long workerId;
    private long lastMs = -1, seq = 0;

    public Snowflake(long workerId) {
        if (workerId < 0 || workerId > 1023) throw new IllegalArgumentException("workerId 0..1023");
        this.workerId = workerId;
    }

    public synchronized long next() {
        long now = System.currentTimeMillis();
        if (now < lastMs) throw new IllegalStateException("clock moved backwards by " + (lastMs - now) + " ms");
        if (now == lastMs) {
            seq = (seq + 1) & 0xFFF;                                 // 12-bit sequence
            if (seq == 0) while ((now = System.currentTimeMillis()) <= lastMs) Thread.onSpinWait();  // wait next ms
        } else {
            seq = 0;
        }
        lastMs = now;
        return ((now - EPOCH) << 22) | (workerId << 12) | seq;
    }
}
```

## 🔴 Senior Level

### Operational concerns
* **Worker ID assignment** (Snowflake): must be unique among *live* generators. Options: Kubernetes StatefulSet ordinal, a lease in ZooKeeper/etcd, a Redis `INCR` with TTL refresh, or a database table of leases. Reusing a worker ID while the old instance still runs causes duplicates.
* **Clock going backwards** (NTP step adjustments, VM migration): refuse to generate (as above), wait until the clock catches up, or keep a logical clock (`max(lastMs, now)`). Use `chronyd`/NTP slewing rather than stepping on servers.
* **Throughput limits**: 4,096 per ms per worker; under extreme bursts the generator spins to the next millisecond.
* **Information leakage**: time-ordered IDs reveal creation time and (Snowflake) worker identity and volume. For public identifiers (order numbers in URLs), consider a separate random public ID or an encoded/encrypted form, while keeping time-ordered IDs internally.

### Choosing in practice
* **Single relational database**: a `bigint` identity/sequence is simplest and smallest; use `allocationSize`/sequence caching (Hibernate `pooled` optimizer) to avoid a round trip per insert.
* **Multiple services/shards, IDs generated in application code, DB-friendly**: **UUIDv7** — no coordination, sortable, standardized, 16 bytes.
* **Need 64-bit IDs** (compact indexes, numeric APIs, Kafka keys, legacy schemas): **Snowflake**-style with managed worker IDs (Sonyflake, Baidu UidGenerator, Discord/Instagram variants).
* **Client-generated IDs for offline/idempotent creation** (mobile apps): UUIDv7/ULID — the client can create the ID before the server sees the entity, which doubles as an idempotency key.
* **Human-facing codes** (vouchers, short links): base32/base62 encodings of random or permuted IDs, avoiding ambiguous characters.

### Database-specific tips
* PostgreSQL 18 adds a built-in `uuidv7()` function; earlier versions use extensions (`pg_uuidv7`) or app-side generation.
* MySQL InnoDB clusters rows by primary key — random UUIDs as PK are especially costly; if you must store UUIDs, use `BINARY(16)` with time-ordered layouts (`UUID_TO_BIN(uuid, 1)` swaps time fields for v1).
* Don't expose auto-increment IDs in multi-tenant APIs without authorization checks — enumeration (IDOR) risk.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Distributed IDs must be unique without coordination; I prefer time-ordered ones because random UUIDv4 fragments B-tree indexes. UUIDv7 or ULID give 128-bit, sortable, coordination-free IDs; Snowflake gives 64-bit IDs from timestamp, worker ID and sequence but needs unique worker assignment and protection against clock rollback. For a single database, a sequence is still simplest.

**Must know:**
* UUIDv4 vs UUIDv7 vs ULID vs Snowflake trade-offs.
* Index locality problem with random keys.
* Snowflake bit layout and limits (41/10/12 bits).
* Worker ID leasing; clock rollback handling.
* Time/volume leakage of sortable IDs.

**Common follow-ups:**
* What happens if two Snowflake generators share a worker ID?
* Why not just use UUIDv4 everywhere?
* How do you generate IDs on mobile clients offline?

**Red flags:** UUIDs stored as `varchar(36)` primary keys; ignoring clock rollback; exposing sequential IDs without authorization checks.
