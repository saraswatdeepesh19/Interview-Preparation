# Designing a URL shortener

---

## 🟢 Junior Level

**Goal:** turn a long URL into a short one (`https://sho.rt/aZ3kQ9`) and redirect visitors to the original. Classic interview problem because it touches ID generation, storage, caching, and read-heavy scaling.

### Requirements
* **Functional**: create a short link (optionally custom alias, expiry), redirect, basic click analytics.
* **Non-functional**: very low redirect latency (p99 < 50 ms), high availability (redirects must work even if creation is degraded), links never collide, read-heavy (≈ 100 reads per write).

### Back-of-the-envelope
* 100M new links/month ≈ 40 writes/s average (peak ×10 → 400/s).
* 100:1 read ratio → 4,000 redirects/s average, ~40k/s peak.
* Storage: 100M × 12 months × 5 years = 6B links × ~500 bytes ≈ 3 TB.
* Key space: base62 with 7 characters = 62⁷ ≈ 3.5 × 10¹² — plenty for 6B links.

### API

```http
POST /api/links
{"url": "https://example.com/very/long/path?x=1", "expiresAt": "2027-01-01T00:00:00Z"}
→ 201 Created  {"code": "aZ3kQ9", "shortUrl": "https://sho.rt/aZ3kQ9"}

GET /aZ3kQ9
→ 301/302 Location: https://example.com/very/long/path?x=1
```

## 🟡 Middle Level

### Generating the short code
1. **Hash the URL** (e.g. first 7 base62 chars of SHA-256): deterministic dedupe of identical URLs, but collisions must be checked and resolved (append a salt and retry).
2. **Counter + base62 encoding** (recommended): a unique 64-bit ID from a sequence/ID generator, encoded in base62. No collisions by construction.

```java
private static final char[] ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();

static String base62(long id) {
    StringBuilder sb = new StringBuilder();
    do { sb.append(ALPHABET[(int) (id % 62)]); id /= 62; } while (id > 0);
    return sb.reverse().toString();
}
```

Sequential IDs produce guessable codes (enumeration of private links). Mitigate by encoding a **shuffled/encrypted** ID (e.g. a format-preserving permutation such as a Feistel network over the ID space) or by drawing IDs from pre-allocated random ranges.

3. **Pre-generated key pool**: a Key Generation Service fills a table of unused random codes; app servers grab batches (e.g. 1,000) to assign locally. Fast, but needs careful handling so batches aren't reused after crashes.

### Storage
A simple key-value access pattern: `code → (long_url, owner, created_at, expires_at)`. Options: PostgreSQL with a primary key on `code` (fine for billions of rows with partitioning), DynamoDB or Cassandra for effortless horizontal scale. Index `long_url` only if dedupe is required.

### Redirect status code
* **301 Moved Permanently** — browsers and CDNs cache it; fewer hits to your servers but you lose per-click analytics and can't change the target.
* **302 Found / 307** — not cached by default; every click hits you (analytics, editable links). Most shorteners use 302 or 301 with short `Cache-Control`.

## 🔴 Senior Level

### Scaling reads
* **Cache** hot codes in Redis (or a local Caffeine cache in redirect servers): link popularity follows a power law, so a small cache serves most traffic. Cache negative results (unknown codes) briefly to absorb scanners — or use a **Bloom filter** of existing codes.
* **CDN/edge** redirects for the most popular links (edge workers with a KV store) give global low latency.
* Redirect servers are stateless and scale horizontally behind a load balancer; database read replicas or a cache-heavy design handle read QPS.

### Analytics without slowing redirects
Never write click events synchronously to the main database. Emit an event (`ClickRecorded{code, ts, country, referrer, ua}`) to Kafka/Kinesis asynchronously (fire-and-forget with a bounded local buffer), aggregate with a stream processor into per-link counters, and store raw events in a columnar store (ClickHouse/BigQuery) for reporting. Redirect latency stays unaffected even if analytics lag.

### Correctness and abuse
* **Custom aliases**: uniqueness via a unique constraint / conditional write; reserve words (`api`, `admin`, `login`).
* **Expiry**: TTL in the data store (DynamoDB TTL, Cassandra TTL) or a cleanup job; redirect returns 410 Gone for expired links.
* **Malicious URLs**: check against Safe Browsing APIs at creation and asynchronously over time; allow takedowns; rate-limit creation per user/IP.
* **Availability split**: redirects are the critical path — keep them independent of the creation service and analytics pipeline (separate deployments, read-only fallback mode).

### Multi-region
Replicate the link store globally (DynamoDB Global Tables, Cassandra multi-DC): links are immutable after creation, so conflicts are rare (only custom aliases need coordination — route alias creation to a home region or use conditional writes against a strongly consistent store).

## 🎯 Interview Cheat Sheet

**30-second pitch:** It's a read-heavy key-value system: generate collision-free short codes from a unique 64-bit ID encoded in base62 — permuted to avoid enumeration — store `code → URL` in a horizontally scalable store, and serve redirects from stateless servers backed by Redis or a local cache and a CDN for hot links. Analytics go asynchronously through a stream, and redirects are isolated from creation and analytics for availability.

**Must know:**
* Capacity estimate and 62⁷ key space.
* Hash vs counter + base62 vs pre-generated keys; enumeration risk.
* 301 vs 302 trade-off.
* Caching hot links, negative caching/Bloom filter.
* Async click analytics; abuse and expiry handling.

**Common follow-ups:**
* How do you support custom aliases safely?
* How would you shorten the same URL twice — same code or new?
* How do you make redirects work if the database is down?

**Red flags:** synchronous analytics writes on redirect; random codes without collision handling; single database without caching at 40k req/s.
