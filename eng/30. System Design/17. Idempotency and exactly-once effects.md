# Idempotency and exactly-once effects

---

## 🟢 Junior Level

In distributed systems, messages and requests can be **lost**, **delayed** or **duplicated**, and after a timeout you don't know whether the other side processed your request. Retrying is the only way to make progress — so the system must tolerate seeing the same request more than once.

* **Exactly-once delivery** over an unreliable network is impossible in general (the Two Generals problem: the sender can never be sure the final acknowledgment arrived).
* **Exactly-once *effect*** is achievable: deliver **at least once** and make processing **idempotent**, so duplicates have no additional effect.

```text
exactly-once effect = at-least-once delivery + idempotent processing (deduplication)
```

### Idempotent by nature vs made idempotent
* Naturally idempotent: "set order 42 status to PAID", "delete item 7", `PUT /profile` with the full body.
* Not idempotent: "add 10 € to balance", "create an order", `POST /payments`. Make them idempotent with a unique request/message ID that the receiver remembers.

## 🟡 Middle Level

### Techniques

| Technique | How | Example |
| --- | --- | --- |
| Idempotency key (API) | Client sends a unique key; server stores key → result | `Idempotency-Key` header on `POST /payments` |
| Inbox / dedup table (messaging) | Store processed message IDs in the same transaction as the side effect | `insert into inbox(message_id) ... on conflict do nothing` |
| Conditional writes | Only apply if state matches expectation | `update orders set status='PAID' where id=? and status='PENDING'` |
| Upserts with natural keys | Insert-or-ignore on a unique business key | One invoice per `(order_id)` |
| Versioning / sequence numbers | Ignore events with version ≤ last applied | Projections tracking per-aggregate version |
| Commutative operations | Design so order/duplication doesn't matter | Set membership instead of increments, CRDT counters |

### Inbox pattern for consumers

```java
@Transactional
public void on(PaymentCaptured msg) {
    int inserted = jdbc.update("""
            insert into inbox(message_id, received_at) values (?, now())
            on conflict (message_id) do nothing
            """, msg.messageId());
    if (inserted == 0) return;                       // duplicate: already processed
    orders.markPaid(msg.orderId());                  // side effect in the SAME transaction
}
```

If the transaction rolls back, the inbox row is rolled back too, so a redelivery processes the message again — exactly the desired behavior.

## 🔴 Senior Level

### End-to-end reasoning
Exactly-once effect must hold across **every hop**:
1. **Client → API**: idempotency key + stored response.
2. **API → database**: single transaction for state change + outbox row.
3. **Outbox → broker**: relay publishes at-least-once; message carries a stable ID (the outbox row ID).
4. **Broker → consumer**: inbox dedup in the consumer's transaction.
5. **Consumer → external system** (payment provider, email): pass a derived idempotency key; providers deduplicate on it. If the external system doesn't support idempotency, you need a "check status before retry" query or accept rare duplicates and reconcile.

### Kafka's "exactly-once semantics" in context
Kafka's idempotent producer (no duplicates from producer retries within a partition) and transactions (atomically write output records and commit consumer offsets) provide exactly-once **within Kafka** for read-process-write pipelines (`isolation.level=read_committed`, Kafka Streams `processing.guarantee=exactly_once_v2`). The moment a side effect leaves Kafka (a database write, an HTTP call), you're back to idempotency at that boundary — unless the database write and offset commit are combined (store offsets in the same DB transaction as the results).

### Dedup storage design
* **Key scope**: per client/tenant (`(tenant_id, key)`), to avoid collisions and cross-tenant probing.
* **Retention**: at least as long as the maximum retry/redelivery window (broker retention, client retry horizon) — e.g. 24 h for API keys, 7 days for messages; purge with partitions or TTL.
* **Ordering**: dedup tables answer "seen before?", not "in order?" — combine with per-aggregate version checks when order matters.
* **Performance**: an extra indexed insert per message; for very high throughput use time-partitioned tables or a fast store (Redis `SET NX` with TTL) — accepting the weaker guarantee that the dedup record and the side effect aren't in one transaction.

### Testing exactly-once effects
Deliberately inject duplicates and crashes: deliver each message twice in integration tests, kill consumers after the side effect but before offset commit, replay a topic from the beginning, and assert business state is unchanged (balances, counts, emails sent).

## 🎯 Interview Cheat Sheet

**30-second pitch:** Exactly-once delivery isn't achievable over unreliable networks, but exactly-once effects are: deliver at least once and make processing idempotent. I use idempotency keys with stored responses for APIs, the outbox for publishing, inbox tables or conditional writes for consumers, version checks for ordering, and forward idempotency keys to external providers; Kafka's EOS covers only Kafka-to-Kafka pipelines.

**Must know:**
* Two Generals; at-least-once + idempotency.
* Idempotency keys, inbox, conditional updates, upserts, versioning.
* Dedup record and side effect in the same transaction.
* Kafka idempotent producer and transactions — scope and limits.
* Dedup key scope and retention.

**Common follow-ups:**
* How would you guarantee a payment is charged once?
* Does Kafka exactly-once solve duplicate database writes?
* How long should you keep idempotency keys?

**Red flags:** "we use exactly-once delivery so no dedup needed"; dedup checks outside the transaction; new keys per retry.
