# DevOps culture and DORA metrics

---

## 🟢 Junior Level

**DevOps** is a culture and set of practices that removes the wall between people who *build* software and people who *run* it. Instead of developers "throwing code over the wall" to operations, teams own their services end to end — "**you build it, you run it**".

Core ideas (often summarized as **CALMS**):
* **Culture** — shared ownership, blameless learning from failure.
* **Automation** — builds, tests, deployments, infrastructure (infrastructure as code).
* **Lean** — small batches, limit work in progress, remove waste and handoffs.
* **Measurement** — decisions based on data (delivery and reliability metrics).
* **Sharing** — knowledge, tools, and responsibility across teams.

### The four DORA metrics
Research by DORA (DevOps Research and Assessment, *Accelerate*) found four metrics that predict software delivery performance and organizational outcomes:

| Metric | Measures | Elite-level example |
| --- | --- | --- |
| **Deployment frequency** | How often you deploy to production | On demand, multiple times per day |
| **Lead time for changes** | Commit → running in production | Less than a day |
| **Change failure rate** | % of deployments causing a failure needing remediation | Low (≈ 0–15%) |
| **Failed deployment recovery time** (formerly time to restore / MTTR) | How quickly you recover from a failed change | Less than an hour |

The first two measure **throughput**, the last two **stability** — and high performers excel at both.

## 🟡 Middle Level

### Measuring the metrics honestly
* **Deployment frequency**: count production deployments per service from the CD system (Argo CD sync events, pipeline runs).
* **Lead time**: timestamp of the commit (or PR merge) vs timestamp of the production deployment containing it — computed per change, reported as a median.
* **Change failure rate**: deployments followed by rollback, hotfix, or incident attributed to the change ÷ total deployments. Requires linking incidents to deployments (deployment markers, incident tooling).
* **Recovery time**: incident start (detection) → service restored.

Tools: DORA's Four Keys project, Sleuth, LinearB, GitLab/GitHub/Atlassian insights, or a simple pipeline that emits events to a data warehouse.

### Practices that move the metrics
* **Throughput**: trunk-based development, small PRs, fast CI (< 10 min), automated deployments, decoupled architectures, feature flags.
* **Stability**: automated tests at the right levels, progressive delivery with automated rollback, good observability, practiced incident response, blameless postmortems.
* **Both**: loosely coupled teams and architecture so teams can deploy independently.

## 🔴 Senior Level

### Using metrics without gaming them
* Metrics are for **teams to improve themselves**, not for ranking teams or individuals — Goodhart's law applies: if deploy count is a target, people split deploys meaninglessly; if change failure rate is punished, incidents stop being reported.
* Look at **trends** per service/team and at **distributions** (p50 and p90 lead time), not single numbers.
* Pair DORA with **reliability** (SLO attainment — DORA added operational performance as a fifth capability) and **developer experience** (SPACE framework: satisfaction, performance, activity, communication, efficiency).

### Diagnosing bottlenecks with lead time breakdown
Split lead time into stages: coding time → PR wait for review → review time → CI time → wait for deploy window → deployment duration. Usually the biggest chunks are **waiting** (reviews, approvals, release trains), not working. Fixes: review SLAs, smaller PRs, pair/mob programming, removing manual approvals for low-risk changes, continuous deployment.

### Organizational patterns
* **Platform teams** build paved roads (golden paths: service templates, pipelines, observability, deploy tooling) so stream-aligned teams ship without becoming infrastructure experts (Team Topologies).
* **SRE** practices (error budgets, toil reduction, SLOs) give "you run it" teams a framework for reliability decisions.
* **On-call** done humanely: owned by the team that deploys, with reasonable rotation sizes, compensated, and with toil-reducing follow-ups after every page.
* **Change approval**: DORA research found heavyweight external change approval boards correlate with *worse* performance without improving stability; peer review plus automated checks work better.

### What to say in an interview
Give concrete examples: "We cut lead time from 9 days to under 1 day by moving to trunk-based development, reducing the CI pipeline from 40 to 9 minutes with parallelization and Testcontainers reuse, and replacing the weekly release train with canary deployments and automatic rollback. Change failure rate went from 22% to 8% because changes became smaller."

### Computing DORA metrics from deployment data (PostgreSQL)

```sql
-- deployments(service, deployed_at, commit_sha, failed boolean, restored_at timestamptz)
-- commits(sha, committed_at)
select d.service,
       count(*) filter (where d.deployed_at > now() - interval '30 days')            as deploys_30d,
       percentile_cont(0.5) within group (order by d.deployed_at - c.committed_at)  as median_lead_time,
       round(100.0 * avg(case when d.failed then 1 else 0 end), 1)                  as change_failure_pct,
       percentile_cont(0.5) within group (order by d.restored_at - d.deployed_at)
           filter (where d.failed)                                                  as median_recovery_time
from deployments d
join commits c on c.sha = d.commit_sha
where d.deployed_at > now() - interval '90 days'
group by d.service
order by median_lead_time desc;
```

Emitting a deployment event from the pipeline (and linking incidents to the deployment that caused them) is usually all the instrumentation you need.

## 🎯 Interview Cheat Sheet

**30-second pitch:** DevOps is a culture of shared ownership — you build it, you run it — supported by automation, small batches, measurement and sharing. The DORA metrics — deployment frequency, lead time for changes, change failure rate and failed deployment recovery time — measure throughput and stability together, and elite teams are good at both. I use them for team-level improvement, break down lead time to find waiting, and avoid turning them into targets that get gamed.

**Must know:**
* CALMS; you build it, you run it.
* Four DORA metrics and how to measure each.
* Practices that improve throughput and stability.
* Goodhart's law; SPACE; SLOs alongside DORA.
* Platform teams, SRE, change approval findings.

**Common follow-ups:**
* How would you measure change failure rate in our company?
* Your lead time is two weeks — where would you look?
* Is a CAB (change advisory board) a good idea?

**Red flags:** ranking engineers by commits/deploys; "DevOps engineer" as the only person who deploys; no link between incidents and changes.
