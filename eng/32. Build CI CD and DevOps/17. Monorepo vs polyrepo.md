# Monorepo vs polyrepo

---

## 🟢 Junior Level

* **Monorepo** — many projects (services, libraries, frontends) live in **one** version-control repository. Used by Google, Meta, Microsoft (parts), Uber.
* **Polyrepo** — each service or library has **its own** repository. Common in microservice organizations.

Monorepo ≠ monolith: a monorepo can contain many independently deployed services.

| Aspect | Monorepo | Polyrepo |
| --- | --- | --- |
| Code sharing | Direct source dependencies; atomic changes across projects | Published artifacts (Maven packages) with versions |
| Cross-cutting refactors | One PR changes the API and all callers | Coordinated PRs and releases across repos |
| Ownership boundaries | Need CODEOWNERS/tooling to enforce | Natural repository boundaries and permissions |
| CI | Must build/test only what changed | Simple per-repo pipelines |
| Tooling scale | Needs build tools that scale (Bazel, Gradle, Nx) | Standard tooling works |
| Dependency versions | Usually one version per library ("one version rule") | Each repo picks versions; drift |

## 🟡 Middle Level

### A Java monorepo layout

```text
repo/
  build-logic/               # shared Gradle convention plugins (java, testing, publishing)
  platform/                  # version catalog / BOM: one version per dependency
  libs/
    shop-commons/            # shared library (money, ids, error model)
    shop-events/             # event schemas (Avro/Protobuf) + generated code
  services/
    orders/
    payments/
    catalog/
  web/
    storefront/              # frontend (pnpm workspace)
  .github/CODEOWNERS
```

```kotlin
// services/orders/build.gradle.kts
plugins { id("shop.spring-service") }          // convention plugin from build-logic
dependencies {
    implementation(project(":libs:shop-commons"))
    implementation(project(":libs:shop-events"))
    implementation(libs.spring.boot.starter.web) // from the version catalog
}
```

### Making CI scale in a monorepo
* **Affected detection**: build and test only projects changed by the commit and their dependents (Gradle with configuration-on-demand and build cache, Bazel's dependency graph, Nx/Turborepo for JS, or path-filtered CI jobs).
* **Remote build cache**: unchanged modules are fetched, not rebuilt (Gradle Develocity, Bazel remote cache).
* **Independent deployment**: each service still has its own deployable artifact and pipeline trigger.

### Polyrepo needs a substitute for atomic changes
* Shared libraries published with semantic versioning; consumers upgrade at their own pace (Renovate automates bumps).
* Breaking changes require deprecation periods and support for old versions.
* Service templates/"golden path" generators to keep repos consistent; drift is the main polyrepo cost.

## 🔴 Senior Level

### The real trade-off: coupling management
* **Monorepo** makes coupling cheap — which is great for refactoring and keeping everyone on current versions, and dangerous because teams can reach into each other's internals. Enforce boundaries: module visibility rules (Bazel visibility, Gradle `api` vs `implementation`, ArchUnit tests), CODEOWNERS for review routing, and published API modules separated from implementation.
* **Polyrepo** makes coupling expensive — forcing explicit, versioned contracts, but making organization-wide changes (security patch to a shared library, framework upgrade) slow: dozens of repos, each with its own PR, review and release. Organizations often build automation (bulk PR tools, Renovate presets, OpenRewrite recipes run across repos) to compensate.

### Version strategy
* Monorepo **one-version rule** avoids diamond-dependency hell and makes upgrades atomic — but one team's upgrade affects everyone, so the upgrade owner must fix all breakages (or the platform team does).
* Polyrepo allows divergence — useful for legacy services, harmful when a critical CVE requires upgrading 80 repos quickly.

### Operational considerations
* **Repository size**: Git performance degrades with very large histories and file counts; partial clone, sparse checkout, `git maintenance`, and Scalar help. Most company monorepos are far from Google scale and work fine with plain Git.
* **CI cost and flakiness**: in a monorepo, one flaky test in a shared library can block everyone — strong test hygiene and ownership are mandatory.
* **Access control**: monorepos expose all code to all engineers (usually fine; some regulated components need separate repos).
* **Release management**: monorepo still needs per-service versioning/changelogs (tags per service, Changesets/semantic-release with scopes).

### Practical guidance
* A small-to-mid organization (≤ ~100 engineers) with one main language gets most benefits from a monorepo with Gradle/Maven multi-module builds and affected-only CI.
* Polyrepo fits independent teams with different stacks, strong API contracts, and a mature platform providing templates and automated upgrades.
* Hybrid is common: one monorepo per domain or per team cluster.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A monorepo holds many projects in one repository, enabling atomic cross-project changes, one dependency version and easy refactoring, but it needs scalable tooling — affected-only builds, remote caches — and enforced module boundaries. Polyrepos give natural ownership and simple pipelines but require versioned libraries and automation to fight drift and slow organization-wide upgrades. The choice is about how you want to manage coupling.

**Must know:**
* Monorepo vs monolith distinction.
* Affected detection, build cache, independent deployability.
* One-version rule vs per-repo versions.
* Boundary enforcement: CODEOWNERS, visibility, ArchUnit.
* Polyrepo upgrade automation (Renovate, OpenRewrite).

**Common follow-ups:**
* How do you keep monorepo CI fast?
* How would you roll out a security fix to 60 polyrepos?
* Which would you choose for a 30-person team?

**Red flags:** monorepo with full rebuilds on every commit; polyrepo with copy-pasted shared code; no ownership model.
