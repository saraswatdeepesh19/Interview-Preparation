# What is the difference between Maven and Gradle

---

## 🟢 Junior Level

### 1. Plain Definition

**Maven** and **Gradle** are the two dominant *build tools* for the JVM. A build tool automates everything between "I changed a `.java` file" and "I have a runnable artifact": downloading libraries, compiling, running tests, packaging a JAR/WAR, and publishing it.

- **Maven** (2004) is *declarative* and *convention-based*. You describe **what** the project is in an XML file (`pom.xml`) and Maven applies a fixed lifecycle.
- **Gradle** (2008) is *programmable*. You describe a graph of **tasks** in a Groovy or Kotlin DSL (`build.gradle` / `build.gradle.kts`) and Gradle executes only what is required.

### 2. Real-World Analogy

Maven is a **franchise restaurant**: every branch has the same menu, the same kitchen layout and the same steps. You can walk into any branch and know where things are. Gradle is a **professional kitchen with a flexible workflow**: you can design any recipe, and the kitchen skips dishes that are already prepared.

### 3. Minimal Working Examples

**Maven – `pom.xml`:**
```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>demo</artifactId>
  <version>1.0.0</version>
  <properties>
    <maven.compiler.release>21</maven.compiler.release>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.10.2</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
```

**Gradle – `build.gradle.kts`:**
```kotlin
plugins { java }

repositories { mavenCentral() }

java { toolchain { languageVersion.set(JavaLanguageVersion.of(21)) } }

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}

tasks.test { useJUnitPlatform() }
```

Both are run from the command line:
```bash
mvn clean package      # Maven
./gradlew clean build  # Gradle (via the wrapper)
```

### 4. Quick Comparison

| Aspect | Maven | Gradle |
| :--- | :--- | :--- |
| Config format | XML (`pom.xml`) | Groovy / Kotlin DSL |
| Model | Fixed lifecycle of phases | Directed acyclic graph of tasks |
| Learning curve | Gentle, very predictable | Steeper, more power |
| Speed | Good, limited incremental support | Faster: incremental, build cache, daemon |
| Typical users | Enterprise Java, Spring shops | Android, large monorepos, Kotlin |

> [!TIP]
> Always commit the wrapper (`mvnw` / `gradlew`). It pins the tool version so every developer and the CI server build with exactly the same version.

```mermaid

    A[Source code] --> B[Build tool]
    B --> C[Resolve dependencies]
    C --> D[Compile]
    D --> E[Test]
    E --> F[Package JAR]
```

## 🟡 Middle Level

### 1. Philosophy: Convention vs Configuration

Maven forces a standard directory layout (`src/main/java`, `src/test/resources`, `target/`) and a standard lifecycle (`validate → compile → test → package → verify → install → deploy`). Customisation happens through **plugins bound to phases**. This makes any Maven project readable by any Java developer, but non-standard builds (generate code, conditional steps, custom pipelines) are awkward and require writing a plugin.

Gradle has the same default layout via the `java` plugin, but build logic is **real code**. A custom step is a ten-line task rather than a plugin:

```kotlin
tasks.register("printVersion") {
    doLast { println("Building ${project.name} ${project.version}") }
}

tasks.register<Copy>("collectDocs") {
    from("docs")
    into(layout.buildDirectory.dir("site"))
}
```

### 2. Performance Model

| Feature | Maven | Gradle |
| :--- | :--- | :--- |
| Daemon (warm JVM) | `mvnd` (separate project) | Built in, on by default |
| Incremental compile | Limited (`maven-compiler-plugin` incremental detection) | Per-task, per-class |
| Up-to-date checks | No – every phase re-runs | Yes – inputs/outputs hashed |
| Build cache | Third-party extension (Maven Build Cache) | Built in, local and remote |
| Parallel | `-T 1C` for modules | `--parallel`, task-level |

On a clean build the difference is small. On the **second** build after changing one file, Gradle is often 2–10x faster because untouched tasks are `UP-TO-DATE` or `FROM-CACHE`.

### 3. Dependency Declaration Differences

Maven has scopes (`compile`, `provided`, `runtime`, `test`). Gradle has *configurations* that separate the API a library exposes from its internals:

```kotlin
dependencies {
    api("org.apache.commons:commons-lang3:3.14.0")          // leaks to consumers
    implementation("com.fasterxml.jackson.core:jackson-databind:2.17.0") // hidden
    compileOnly("org.projectlombok:lombok:1.18.32")          // like Maven provided
    runtimeOnly("org.postgresql:postgresql:42.7.3")
    testImplementation("org.mockito:mockito-core:5.11.0")
}
```
`implementation` shrinks recompilation: if an internal dependency changes, consumers of your module are not recompiled.

### 4. Common Mistakes

- **Using `latest` / dynamic versions** (`1.+`, `LATEST`, `RELEASE`): builds stop being reproducible.
- **Not using the wrapper** and relying on whatever `mvn` happens to be installed.
- **Putting business logic in `build.gradle`** instead of `buildSrc` or convention plugins, which makes builds unmaintainable.
- **Copy-pasting plugin config** across Maven modules instead of using `pluginManagement` in a parent POM.
- **Mixing both tools** in one repo without a clear owner.

### 5. When to Choose Which

| Situation | Recommendation |
| :--- | :--- |
| Standard Spring Boot microservice, team new to builds | Maven |
| Android, Kotlin Multiplatform | Gradle (only option) |
| Large multi-module repo, slow CI | Gradle with remote cache |
| Heavily customised build logic | Gradle |
| Regulated environments needing very predictable builds | Maven |

## 🔴 Senior Level

### 1. Execution Model Internals

**Maven** executes plugin *goals* bound to *phases*. Running `mvn verify` runs every earlier phase in order for every module. There is no concept of "this goal's inputs did not change", so `maven-surefire-plugin` re-runs all tests unless you skip them.

**Gradle** has three phases: **initialization** (`settings.gradle.kts` decides which projects exist), **configuration** (all build scripts are evaluated to build the task graph) and **execution** (only requested tasks and their dependencies run). Every task declares inputs and outputs; Gradle hashes them to decide `UP-TO-DATE`, `FROM-CACHE` or `EXECUTED`.

Consequence: Gradle's **configuration time** can dominate in huge builds. Enable the *configuration cache* and *configure on demand*:

```properties
# gradle.properties
org.gradle.caching=true
org.gradle.parallel=true
org.gradle.configuration-cache=true
org.gradle.jvmargs=-Xmx2g -XX:+UseParallelGC
```

### 2. Making Maven Fast

Maven is not slow by necessity. Senior engineers apply:

```bash
mvn -T 1C -B -ntp -DskipTests=false verify     # parallel modules, batch mode, no transfer progress
mvn -pl :orders-service -am verify             # build one module plus what it depends on
mvn -rf :orders-service verify                 # resume from failed module
```

and `.mvn/maven.config` plus `.mvn/extensions.xml` (Maven Build Cache Extension) to get Gradle-like caching.

### 3. Production Scenarios

**Scenario – CI takes 40 minutes on a 60-module Maven monorepo.** Steps: (1) enable `-T 1C`; (2) cache `~/.m2/repository` between CI runs; (3) build only changed modules with `-pl` and `-amd` (also-make-dependents) computed from `git diff`; (4) separate fast `test` jobs from slow `verify` integration jobs; (5) consider migrating hot modules to Gradle or enabling the Maven Build Cache extension.

**Scenario – dependency version drift in Gradle.** Use a *version catalog* and *dependency locking*:

```toml
# gradle/libs.versions.toml
[versions]
spring-boot = "3.3.0"
[libraries]
spring-boot-starter-web = { module = "org.springframework.boot:spring-boot-starter-web" }
[plugins]
spring-boot = { id = "org.springframework.boot", version.ref = "spring-boot" }
```
```bash
./gradlew dependencies --write-locks
```

### 4. Edge Cases and Pitfalls

- **Non-deterministic outputs** (timestamps in JARs) defeat Gradle's build cache and cause cache misses. Disable with `preserveFileTimestamps = false` and `reproducibleFileOrder = true` on archive tasks.
- **Gradle's `--no-daemon` in CI** costs several seconds per invocation; prefer an ephemeral agent *with* the daemon and a cache restored beforehand.
- **Maven `SNAPSHOT` resolution** hits remote repositories on every build by default (`-o` offline or update policy `never`/`daily` helps).
- **Plugin version drift**: Maven warns when plugins have no explicit version; always pin in `pluginManagement`.
- **Migration**: `gradle init` can convert a POM, but BOM imports, profiles and plugin executions need manual attention. Migrate module-by-module, never big-bang.

### 5. Governance

Large organisations keep a **parent POM / convention plugin** that enforces Java version, compiler flags, static analysis and publishing. In Gradle this is a *convention plugin* in `build-logic`; in Maven it is a corporate parent POM published to the internal repository.

## 🎯 Interview Cheat Sheet

### ⏱️ 30-Second Elevator Pitch

> "Maven is declarative XML with a fixed lifecycle and strong conventions – predictable and universally understood. Gradle is a task-graph engine with a Groovy/Kotlin DSL, incremental builds, a daemon and build cache, so it is faster and more flexible but demands more discipline. I choose Maven for standard services and Gradle for large, customised or Android builds, and in both I use the wrapper, pinned versions and a shared parent/convention plugin."

### ✅ Must-Know Bullets

- Maven: `pom.xml`, lifecycle phases, plugins bound to phases, `~/.m2` local repo.
- Gradle: tasks with inputs/outputs, `UP-TO-DATE`, build cache, daemon, configuration cache.
- `api` vs `implementation` in Gradle; `compile/provided/runtime/test` scopes in Maven.
- Always use `mvnw` / `gradlew` wrappers.
- Never use dynamic versions in production builds.

### ❓ Common Follow-Up Questions

1. Why is Gradle usually faster for incremental builds?
2. What is the difference between `api` and `implementation`?
3. How would you speed up a slow Maven CI build?
4. How do you share build logic across modules in each tool?
5. How would you migrate Maven to Gradle safely?

### 🚩 Red Flags

- "Gradle is always better" or "Maven is outdated" without trade-offs.
- Not knowing what the wrapper is.
- Using `1.+` or `LATEST` dependency versions.
- Checking `target/` or `build/` directories into Git.
