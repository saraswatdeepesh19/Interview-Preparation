# Deployment strategies rolling blue-green canary and feature flags

---

## 🟢 Junior Level

How you replace the old version with the new one determines downtime, risk and rollback speed.

| Strategy | How it works | Downtime | Rollback | Extra capacity |
| --- | --- | --- | --- | --- |
| **Recreate** | Stop all old, start all new | Yes | Redeploy old | None |
| **Rolling** | Replace instances gradually (Kubernetes default) | No | Roll back gradually | Small surge |
| **Blue-green** | Run new version (green) alongside old (blue); switch all traffic at once | No | Instant switch back | 2× during switch |
| **Canary** | Send a small % of traffic to the new version, increase if healthy | No | Shift traffic back | Small |
| **Shadow / dark launch** | Mirror traffic to the new version, discard its responses | No | Nothing to roll back | Extra for shadow |

**Feature flags** are different: they separate **deployment** (code in production) from **release** (feature visible to users). New code ships "off" and is turned on per user group without a deploy.

### Kubernetes rolling update

```yaml
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # up to 2 extra pods during the rollout
      maxUnavailable: 0      # never drop below 6 ready pods
  minReadySeconds: 20        # a new pod must stay ready 20 s before counting as available
```

Readiness probes gate the rollout: unhealthy new pods stop it.

## 🟡 Middle Level

### Canary with automated analysis (Argo Rollouts)

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: orders }
spec:
  replicas: 10
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 5m }
        - analysis:
            templates: [ { templateName: error-rate-and-latency } ]
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
      trafficRouting:
        istio: { virtualService: { name: orders } }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: error-rate-and-latency }
spec:
  metrics:
    - name: error-rate
      interval: 1m
      failureLimit: 2
      successCondition: result[0] < 0.01
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_server_requests_seconds_count{app="orders",version="canary",outcome="SERVER_ERROR"}[2m]))
            / sum(rate(http_server_requests_seconds_count{app="orders",version="canary"}[2m]))
```

If analysis fails, the rollout aborts and traffic returns to the stable version automatically.

### Feature flags in Spring

```java
@Service
class CheckoutService {
    private final FeatureFlags flags;           // e.g. OpenFeature client backed by Unleash/LaunchDarkly/flagd

    Receipt checkout(Cart cart, User user) {
        if (flags.isEnabled("new-pricing-engine", user)) {      // targeting: % rollout, beta users, tenants
            return newPricing.checkout(cart);
        }
        return legacyPricing.checkout(cart);
    }
}
```

Flag types: **release** flags (temporary, removed after rollout), **ops/kill switches** (disable expensive features under load), **experiment** flags (A/B tests), **permission** flags (entitlements — often better modeled as real authorization).

## 🔴 Senior Level

### Choosing a strategy
* **Rolling** is the sensible default for stateless services with backward-compatible changes.
* **Blue-green** when you need instant, all-or-nothing switches (e.g. major dependency changes) and can afford double capacity; also useful for non-Kubernetes VMs behind load balancers. Watch for long-lived connections and caches on the old stack.
* **Canary** for high-traffic services where the risk of a bad release is costly — it limits blast radius and gives real-traffic signal. Needs good metrics segmented by version and enough traffic for statistical significance.
* **Shadow traffic** for rewrites (new pricing engine) where you compare responses without user impact — careful with side effects (shadow must not send emails or charge cards).

### Compatibility is the hard part
During any non-recreate rollout, **two versions run at once**:
* **API compatibility** — new version must accept old clients' requests and old consumers must accept new responses/events (additive changes).
* **Database schema** — use **expand/contract**: (1) add new column/table (compatible with old code), (2) deploy code writing both, (3) backfill, (4) switch reads, (5) remove old column in a later release. Never deploy a migration that breaks the currently running version.
* **Message formats** — consumers on the old version must tolerate new fields; versioned events for breaking changes.
* **Sessions and caches** — serialized objects in Redis/session stores must be readable by both versions.

### Feature flag hygiene
* Flags are technical debt: each adds a code path to test. Set an expiry/owner, alert on stale flags, and remove them after full rollout.
* Evaluate flags **locally** from a cached ruleset (OpenFeature providers with streaming updates) — a remote call per evaluation adds latency and a failure mode; define safe defaults when the flag service is unreachable.
* Combine with canaries: deploy dark, canary the binary, then gradually enable the flag — two independent safety levers.
* Audit flag changes (who enabled what, when) — a flag flip is a production change and appears in incident timelines.

### Rollback vs roll forward
Fast, automated rollback is the default mitigation. Roll forward (hotfix) only when rollback is impossible (irreversible migrations, data format changes already consumed) — which is exactly why expand/contract and backward-compatible changes matter.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Rolling updates replace instances gradually and are the default; blue-green switches all traffic between two full environments for instant rollback; canary shifts a small percentage of real traffic and promotes based on automated metric analysis; shadowing mirrors traffic without user impact. Feature flags decouple deploy from release. Whatever the strategy, two versions coexist, so APIs, schemas — via expand/contract — and messages must be backward-compatible.

**Must know:**
* Strategy comparison: downtime, rollback, capacity.
* Kubernetes `maxSurge`/`maxUnavailable`, readiness gating.
* Argo Rollouts/Flagger canary analysis with Prometheus.
* Feature flag types, local evaluation, cleanup.
* Expand/contract migrations; rollback vs roll forward.

**Common follow-ups:**
* How do you canary a change that includes a DB migration?
* Blue-green with a shared database — any problems?
* How do you prevent feature flag sprawl?

**Red flags:** breaking schema migrations deployed with rolling updates; flags that live forever; canaries without per-version metrics.
