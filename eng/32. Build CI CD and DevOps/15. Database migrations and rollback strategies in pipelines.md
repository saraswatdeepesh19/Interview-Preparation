# Database migrations and rollback strategies in pipelines

---

## 🟢 Junior Level

Application code is easy to roll back — redeploy the previous image. **Database changes are not**: once a column is dropped or data is transformed, the previous version may no longer work, and the data may be gone. That's why schema changes need their own discipline in CI/CD.

### Principles
1. **Migrations are versioned code** (Flyway/Liquibase) in the same repository as the application.
2. **Run automatically** in the pipeline, never by hand in production.
3. **Every migration is backward-compatible** with the version currently running (because during a rolling deploy, old and new versions run at the same time).
4. **Prefer roll-forward** fixes over down-migrations.
5. **Test migrations** against a production-like database before production.

```text
src/main/resources/db/migration/
  V1__create_orders.sql
  V2__add_order_status.sql
  V3__index_orders_customer.sql
```

## 🟡 Middle Level

### Expand / contract (parallel change)
Example: rename `orders.amount` to `orders.total`.

| Release | Database | Application |
| --- | --- | --- |
| 1 (expand) | Add `total` (nullable) | Writes `amount` **and** `total`; reads `amount` |
| 2 | Backfill `total` from `amount` (batched) | Reads `total`, still writes both |
| 3 | Add `NOT NULL` to `total` | Reads/writes only `total` |
| 4 (contract) | Drop `amount` | — |

Each step is deployable and rollback-safe on its own: rolling back release N only goes to N−1, which works with the schema at step N.

### Where migrations run
* **Separate pipeline step / Kubernetes Job** before the new app version rolls out: clear ordering, one runner, failures stop the deploy.
* **App startup** (Spring Boot runs Flyway on startup): simple, but with many replicas they race (Flyway's schema history table lock serializes them), long migrations delay readiness or exceed startup probes, and failing migrations crash-loop all pods. Fine for small services; prefer a dedicated step at scale.

```yaml
# Kubernetes Job running Flyway with the same image tag as the release
apiVersion: batch/v1
kind: Job
metadata: { name: orders-migrate-3f2a9c1 }
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: flyway
          image: flyway/flyway:10
          args: ["-url=$(DB_URL)", "-user=$(DB_USER)", "-password=$(DB_PASSWORD)", "-locations=filesystem:/migrations", "migrate"]
          envFrom: [ { secretRef: { name: orders-migrator } } ]   # separate DDL-privileged user
          volumeMounts: [ { name: migrations, mountPath: /migrations } ]
```

### Pipeline checks
* `flyway validate` (checksums of applied migrations unchanged; no edited history).
* Apply all migrations to a fresh database in CI (Testcontainers) **and** to a copy/snapshot of production-like data in staging (catches slow migrations and data-dependent failures).
* Lint migrations for dangerous operations (Squawk for PostgreSQL flags `ALTER TABLE ... ADD COLUMN ... DEFAULT` on old versions, non-concurrent index creation, `NOT NULL` without default, type changes).

## 🔴 Senior Level

### Dangerous operations and safe alternatives (PostgreSQL)

| Risky | Why | Safer |
| --- | --- | --- |
| `CREATE INDEX` | Blocks writes for the duration | `CREATE INDEX CONCURRENTLY` in its own migration, run outside a transaction (Flyway: script config file `V7__idx.sql.conf` with `executeInTransaction=false`; Liquibase: `runInTransaction="false"`) |
| `ALTER TABLE ... ADD COLUMN ... NOT NULL` | Needs table rewrite/scan in some cases; blocks | Add nullable → backfill → add `NOT NULL` via `CHECK (...) NOT VALID` + `VALIDATE CONSTRAINT` |
| Changing a column type | Full table rewrite with `ACCESS EXCLUSIVE` lock | New column + dual writes + backfill + switch |
| Big `UPDATE` backfill | Long transaction, bloat, replication lag | Batched updates (e.g. 10k rows per transaction) in a job, with throttling |
| Adding a foreign key | Validates all rows under lock | `ADD CONSTRAINT ... NOT VALID`, then `VALIDATE CONSTRAINT` |
| Any DDL on a busy table | Waits for locks and blocks the queue behind it | `SET lock_timeout = '3s'` and retry |

### Rollback strategies
* **Roll back the app, keep the schema**: works when migrations are backward-compatible (the norm with expand/contract).
* **Roll forward**: fix with a new migration — the default for data issues.
* **Down migrations** (Liquibase rollback, Flyway undo in paid editions): rarely trustworthy for data-destructive changes; useful for purely additive changes in lower environments.
* **Point-in-time recovery / snapshots**: last resort for catastrophic mistakes; loses data written since the snapshot — rehearse it.
* **Feature flags** for code paths depending on new schema elements, so behavior can be turned off without touching the database.

### Multiple services and environments
* One schema owner per database; other services integrate via APIs/events, not by migrating someone else's tables.
* Migration ordering across services is a smell — design changes so each service's migrations are independent and compatible with neighbors' current versions.
* Keep migrations **idempotent where possible** (`CREATE TABLE IF NOT EXISTS` is fine for repeatable bootstrap, but versioned migrations should be exact and immutable once applied).
* Never edit an applied migration — add a new one; Flyway's checksum validation enforces this.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Database changes can't be rolled back like code, so migrations are versioned with Flyway or Liquibase, run automatically as a dedicated pipeline step before the rollout, and are always backward-compatible with the running version using expand/contract. I lint and test migrations against realistic data, use online-safe operations — concurrent indexes, NOT VALID constraints, batched backfills, lock timeouts — and prefer rolling the app back or rolling forward over down-migrations.

**Must know:**
* Expand/contract steps and why each release is rollback-safe.
* Job vs app-startup migrations.
* `flyway validate`, CI on fresh DB + staging on prod-like data, migration linting.
* PostgreSQL-safe DDL patterns.
* Rollback options and their limits.

**Common follow-ups:**
* How do you rename a column with zero downtime?
* What if a migration takes 2 hours?
* Should migrations run at application startup?

**Red flags:** `DROP COLUMN` in the same release that stops using it; manual production DDL; editing applied migrations.
