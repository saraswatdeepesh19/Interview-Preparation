# Environment configuration and secrets management

---

## 🟢 Junior Level

The **Twelve-Factor App** rule: *store config in the environment, not in code*. The same artifact (JAR/image) runs in dev, staging and production; only **configuration** changes — URLs, feature toggles, pool sizes, credentials.

### Spring Boot configuration sources (higher wins)
1. Command-line arguments (`--server.port=9090`)
2. `SPRING_APPLICATION_JSON` and OS environment variables (`SPRING_DATASOURCE_URL`)
3. External files: `application-{profile}.yml`, `application.yml` outside the JAR, `spring.config.import` sources (config trees, Vault, AWS, Config Server)
4. Packaged `application.yml` inside the JAR (defaults)

```yaml
# application.yml — safe defaults, no secrets
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/orders}
    username: ${DB_USER:orders}
    password: ${DB_PASSWORD}            # must be provided by the environment
app:
  payment:
    base-url: ${PAYMENT_URL:http://localhost:8089}
    timeout: 2s
```

### Typed configuration

```java
@ConfigurationProperties(prefix = "app.payment")
@Validated
public record PaymentProperties(@NotNull URI baseUrl, @NotNull Duration timeout) {}
```

Validation at startup turns a missing or invalid setting into a clear failure instead of a 3 a.m. runtime error.

## 🟡 Middle Level

### Profiles: use sparingly
`application-prod.yml` files inside the artifact couple the build to environments and tend to accumulate secrets and drift. Prefer:
* **Defaults** in `application.yml` suitable for local development.
* **Environment-specific values** injected by the platform (Kubernetes ConfigMaps/Secrets, Helm values, Parameter Store).
* Profiles for **behavioral** differences that are genuinely environment-independent (`local`, `test`), not for URLs and passwords.

### Kubernetes ConfigMaps and Secrets

```yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: orders-config }
data:
  application.yaml: |
    app:
      payment:
        base-url: https://payments.internal
        timeout: 1500ms
---
# Deployment excerpt
env:
  - name: DB_PASSWORD
    valueFrom: { secretKeyRef: { name: orders-db, key: password } }
  - name: SPRING_CONFIG_ADDITIONAL_LOCATION
    value: optional:file:/etc/orders/                # tell Boot where the mounted file lives
volumeMounts:
  - { name: config, mountPath: /etc/orders, readOnly: true }   # ConfigMap mounted as /etc/orders/application.yaml
```

Spring Boot's default external locations are `./` and `./config/` relative to the working directory; anything else needs `SPRING_CONFIG_ADDITIONAL_LOCATION` (as above). For mounted secrets with one file per value, use `spring.config.import=optional:configtree:/etc/secrets/`.

### Secrets: what not to do
* No secrets in Git, Docker images, Helm `values.yaml` committed in plain text, CI logs, or URLs.
* No shared credentials across environments or services.
* Don't print the effective configuration on startup; Actuator `/env` masks sensitive keys by default (Boot 3: values hidden unless `show-values` is configured) — keep it that way.

## 🔴 Senior Level

### Secret delivery architectures
| Approach | Pros | Cons |
| --- | --- | --- |
| Kubernetes Secrets (env/file) | Native, simple | Base64 only; need etcd encryption + strict RBAC; rotation needs restarts for env vars |
| External Secrets Operator → K8s Secrets | Source of truth in AWS/GCP/Vault; GitOps-friendly | Still lands as K8s Secrets |
| Secrets Store CSI driver | Mounts directly from the vault; can avoid K8s Secret objects | Per-pod mounts, provider-specific |
| App fetches at startup (Spring Cloud Vault / AWS) | Dynamic secrets, leases, fine-grained IAM | App coupled to the secret store; startup dependency |
| Workload identity (IRSA, Workload Identity) | No static cloud credentials at all | Cloud-specific setup |

### Rotation without downtime
* Mount secrets as **files** (updated in place by kubelet/CSI within ~1 minute) rather than env vars (fixed for the process lifetime).
* Support **two valid credentials** during rotation (database users A/B, dual API keys) so old and new pods both work.
* For JDBC, connection pools must pick up new passwords for new connections; `maxLifetime` shorter than the rotation window ensures old connections are replaced. Vault's dynamic database credentials automate creation and revocation.

### Configuration change management
* **Configuration is code**: versioned (GitOps repo), reviewed, validated in CI (schema validation for YAML, `@Validated` startup tests with production-like values).
* **Runtime-changeable settings** (timeouts, feature flags, rate limits) via a config service or flags with audit logs; most other settings change only with a deploy (immutable, reproducible).
* **Drift detection**: Argo CD/Flux show differences between Git and cluster; alert on manual `kubectl edit`.
* **Secrets in GitOps**: store references (External Secrets `ExternalSecret` CRs) or encrypted values (SOPS with KMS/age, Sealed Secrets) — never plaintext.

### Failure modes
* App can't reach the secret store at startup → crash loop. Use retries with backoff and a startup probe budget; cache the last known secret where acceptable.
* Secret store outage during a scale-out → new pods can't start: static stability argues for pre-fetched secrets (K8s Secret sync) for critical services.
* Config typo deployed to all regions at once → stage config changes like code (canary/progressive rollout).

## 🎯 Interview Cheat Sheet

**30-second pitch:** I build one artifact and inject environment-specific configuration at deploy time — environment variables, ConfigMaps, mounted secrets via `configtree:`, or `spring.config.import` from Vault or AWS — with typed, validated `@ConfigurationProperties`. Secrets never live in Git or images; they come from a secret manager via External Secrets, CSI or workload identity, are mounted as files for rotation, and configuration changes go through Git, review and progressive rollout.

**Must know:**
* Spring Boot property source precedence; relaxed binding (`SPRING_DATASOURCE_URL`).
* `@ConfigurationProperties` + `@Validated`.
* Profiles for behavior, not for environments' values.
* `configtree:`, External Secrets Operator, CSI driver, workload identity.
* Rotation: files over env vars, dual credentials, pool `maxLifetime`.

**Common follow-ups:**
* How do you rotate the DB password without downtime?
* How do you keep secrets in a GitOps repo?
* What happens if Vault is down at startup?

**Red flags:** `application-prod.yml` with passwords in the JAR; secrets in env vars printed in logs; manual `kubectl edit` in production.
