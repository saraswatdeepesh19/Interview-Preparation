# Reproducible builds

---

## 🟢 Junior Level

A build is **reproducible** when the same source code, built with the same tools, always produces **bit-for-bit identical** artifacts — no matter who builds it, where, or when.

### Why it matters
* **Trust / supply-chain security** — anyone can rebuild from source and verify that a published JAR or image wasn't tampered with.
* **Debuggability** — "works on my machine" disappears; a production artifact can be recreated exactly.
* **Caching** — identical inputs → identical outputs means build caches and layer caches actually hit.
* **Auditing** — regulated industries must show exactly what was shipped.

### Common sources of non-reproducibility
* **Timestamps** inside JAR entries (`MANIFEST.MF`, file modification times) and build info.
* **Unpinned dependencies** — version ranges, `SNAPSHOT`s, `latest` Docker base images, unpinned CI actions.
* **Environment differences** — different JDK vendor/version, locale, time zone, file ordering of the filesystem, line endings.
* **Generated content** — build numbers, git info, random values embedded in resources.

## 🟡 Middle Level

### Maven
Since Maven 3.6.x+ with recent plugins, set a fixed output timestamp; plugins (jar, war, assembly, source, javadoc) then normalize entry timestamps and ordering:

```xml
<properties>
  <!-- Set by the release plugin; for regular builds use the last commit time -->
  <project.build.outputTimestamp>2026-10-16T08:00:00Z</project.build.outputTimestamp>
</properties>
```

Verify with the artifact plugin:

```bash
mvn clean install                          # build once
mvn clean verify artifact:compare          # rebuild and compare with the installed artifacts
```

Spring Boot's `spring-boot-maven-plugin` respects `project.build.outputTimestamp` for executable JARs; `build-info` should then use the same timestamp instead of "now".

### Gradle

```kotlin
tasks.withType<AbstractArchiveTask>().configureEach {
    isPreserveFileTimestamps = false
    isReproducibleFileOrder = true
}
```

### Pin everything
* Exact dependency versions (no ranges), a BOM/version catalog, and **dependency locking** (`gradle dependencies --write-locks`; Maven has no native lockfile, but enforcer rules `requireReleaseDeps`/`banDynamicVersions` and checksum verification help).
* **Checksum/signature verification** of downloaded dependencies (Gradle `verification-metadata.xml`; Maven `--strict-checksums`).
* **Toolchains**: pin the JDK (`maven-toolchains-plugin`, Gradle Java toolchains with vendor), Maven/Gradle wrapper versions.
* **Container base images by digest** (`FROM eclipse-temurin:21-jre@sha256:...`), CI actions by commit SHA.

## 🔴 Senior Level

### Reproducible container images
Docker builds embed timestamps and layer metadata. Options:
* **Jib** (Maven/Gradle) builds images without Docker, deterministically by default (fixed file timestamps at epoch + 1 s, sorted entries) — same inputs → same image digest.
* **Cloud Native Buildpacks** (`spring-boot:build-image`) set fixed timestamps (1980-01-01) for reproducibility.
* Dockerfile builds with BuildKit: `SOURCE_DATE_EPOCH` support (`--build-arg SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)` and `rewrite-timestamp` options in recent BuildKit) plus pinned base digests.

### Supply chain frameworks
* **SLSA** (Supply-chain Levels for Software Artifacts) defines levels of build integrity: scripted builds → hosted, provenance-generating builds → hardened, isolated builders. **Provenance attestations** (in-toto/SLSA format) record which source, commit, builder and parameters produced an artifact.
* **Sigstore** (cosign, Rekor transparency log) signs artifacts and attestations keylessly with OIDC identities from CI.
* **SBOMs** (CycloneDX/SPDX) list components; combined with reproducibility, third parties can verify both *what* is inside and *that* it came from the claimed source.
* The **Reproducible Central** initiative tracks reproducibility of Maven Central artifacts; publishing reproducible libraries lets consumers verify you.

### Hermetic builds
Bazel (and Gradle with strict settings) aim for **hermetic** builds: all inputs declared, no network access during build steps except through controlled caches, sandboxed actions. This is the strongest guarantee and enables remote execution and caching across thousands of machines.

### Practical checklist for a Java service
1. `project.build.outputTimestamp` from commit time; reproducible archive settings.
2. Pinned dependencies with checksum verification; no SNAPSHOTs in releases.
3. Pinned JDK via toolchains and wrapper versions; consistent `LANG`/`TZ` in CI.
4. Images via Jib/Buildpacks or pinned Dockerfile base digests.
5. Verify in CI: build twice (different runners), compare checksums/digests; fail on mismatch.
6. Publish provenance and SBOM; sign artifacts.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A reproducible build produces bit-identical artifacts from the same sources, which enables supply-chain verification, reliable caching and exact recreation of what's in production. In Java I set `project.build.outputTimestamp`, use reproducible archive settings in Gradle, pin dependencies, JDK toolchains, base images by digest and CI actions by SHA, verify dependency checksums, build images with Jib or Buildpacks, and add SLSA provenance, SBOMs and Sigstore signatures.

**Must know:**
* Sources of non-determinism: timestamps, unpinned deps, environment, generated metadata.
* Maven `outputTimestamp` + `artifact:compare`; Gradle archive settings.
* Dependency locking and checksum verification.
* Jib/Buildpacks deterministic images; `SOURCE_DATE_EPOCH`.
* SLSA, provenance, cosign, SBOM, hermetic builds.

**Common follow-ups:**
* How would you prove a production JAR matches a Git commit?
* Why do two builds of the same commit have different image digests?
* What is SLSA level 3?

**Red flags:** `latest` base images; version ranges; embedding build time in artifacts without control.
