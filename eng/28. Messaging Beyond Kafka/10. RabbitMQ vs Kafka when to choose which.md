# RabbitMQ vs Kafka when to choose which

---

## 🟢 Junior Level

Both move messages between services asynchronously, but they are built on different models:

* **RabbitMQ** is a **message broker** (AMQP): producers send messages to **exchanges**, which route them to **queues**; consumers take messages from queues and **acknowledge** them; acknowledged messages are **deleted**. Think *smart broker, simple consumers*.
* **Apache Kafka** is a **distributed commit log**: producers append records to **partitioned topics**; records are **retained** for a configured time regardless of consumption; each consumer group tracks its own **offset**. Think *simple broker, smart consumers*.

| | RabbitMQ | Kafka |
| --- | --- | --- |
| Model | Queues, routing via exchanges | Append-only partitioned log |
| After consumption | Message removed | Message retained (replayable) |
| Ordering | Per queue (with one consumer) | Per partition |
| Routing | Rich: direct, topic, fanout, headers | By topic + partition key |
| Typical throughput | Tens of thousands msg/s per node | Hundreds of thousands to millions msg/s per cluster |
| Replay old messages | No (Streams feature aside) | Yes, by resetting offsets |

### Quick rule
* Need **task distribution, complex routing, per-message acknowledgment, priorities, delayed retries** → RabbitMQ.
* Need **event streaming, high throughput, replay, multiple independent consumers of the same history, stream processing** → Kafka.

---

## 🟡 Middle Level

### Same use case, two shapes

**Work queue (send invoice emails)** — RabbitMQ fits naturally: competing consumers pull from one queue, prefetch limits in-flight work, failed messages go to a dead-letter exchange, and you can scale consumers freely without partition constraints.

```java
@RabbitListener(queues = "emails.invoice", concurrency = "4-16")
public void send(InvoiceEmail cmd) { mailer.send(cmd); }   // ack on success (AUTO mode), nack/DLQ on exception
```

**Event stream (order lifecycle consumed by billing, analytics, search)** — Kafka fits: each service is its own consumer group reading the same topic at its own pace; new services can replay from the beginning; ordering per order ID via the partition key.

```java
kafkaTemplate.send("orders", order.id(), new OrderPlaced(order.id(), order.total()));

@KafkaListener(topics = "orders", groupId = "billing")
public void onOrder(OrderPlaced e) { billing.open(e); }
```

### Consumer scaling differences
* RabbitMQ: add consumers to a queue any time; the broker distributes messages round-robin (respecting prefetch).
* Kafka: parallelism is capped by the **number of partitions** in a consumer group; more consumers than partitions sit idle. Choosing partition counts is a capacity decision.

## 🔴 Senior Level

### Deeper trade-offs

| Concern | RabbitMQ | Kafka |
| --- | --- | --- |
| Durability/HA | Quorum queues (Raft) replicated across nodes | Partition replication with ISR, `acks=all`, `min.insync.replicas` |
| Delivery semantics | At-least-once with publisher confirms + manual acks | At-least-once by default; idempotent producer + transactions for exactly-once *within Kafka* |
| Per-message features | TTL, priorities, delayed messages (plugin), per-message routing | None per message; time-based retention, compaction per topic |
| Backpressure | Prefetch, flow control, queue length limits | Consumers pull at their own pace; lag grows |
| Retry patterns | DLX + TTL queues, requeue | Retry topics, DLT (Spring Kafka `@RetryableTopic`) |
| Large backlogs | Performance degrades with very deep queues (lazy/quorum queues help) | Designed for large retained logs |
| Stream processing | Not built in | Kafka Streams, ksqlDB, Flink integration |
| Ops | Simpler for small/medium setups | Needs capacity planning (partitions, retention, disk); KRaft removed ZooKeeper |

RabbitMQ **Streams** (3.9+) add a Kafka-like append-only log with replay to RabbitMQ, narrowing the gap; Kafka **share groups** (KIP-932, queues for Kafka) add queue-like consumption without partition-bound parallelism. Check versions when comparing.

### Decision questions for an interview
1. Do multiple independent consumers need the **same** messages, possibly later (replay)? → Kafka.
2. Is it **commands/tasks** that exactly one worker should process, with retries and priorities? → RabbitMQ (or SQS).
3. Throughput beyond ~100k msg/s sustained, or long retention (days/weeks) as a source of truth for events? → Kafka.
4. Complex routing by attributes, request-reply, per-message TTL? → RabbitMQ.
5. Team and platform: is there already a managed Kafka (MSK, Confluent) or RabbitMQ (Amazon MQ, CloudAMQP)? Operational familiarity often decides.

Many organizations run **both**: Kafka as the event backbone between domains, RabbitMQ/SQS for task queues inside a service.

## 🎯 Interview Cheat Sheet

**30-second pitch:** RabbitMQ is a smart broker with exchanges routing to queues, per-message acks and deletion — great for task distribution, complex routing, priorities and retries. Kafka is a partitioned, replicated log with retention and consumer offsets — great for high-throughput event streaming, replay, multiple independent consumers and stream processing. Ordering is per queue vs per partition, and Kafka's parallelism is bounded by partitions.

**Must know:**
* Delete-on-ack vs retain-and-offset.
* Exchanges/bindings vs topics/partitions/keys.
* Consumer scaling: free vs partition-bound.
* Quorum queues vs ISR replication.
* DLX/TTL retries vs retry topics/DLT.

**Common follow-ups:**
* Can Kafka be used as a work queue?
* How do you guarantee ordering in each?
* Which would you choose for sending emails? For an audit event stream?

**Red flags:** "Kafka is just a faster RabbitMQ"; ignoring partition counts; using RabbitMQ as a long-term event store.
