# Transactional outbox pattern

---

## 🟢 Junior Level

A service often needs to **update its database and publish an event** — "order saved" and "OrderPlaced sent to the broker". Doing both directly is the **dual-write problem**: the database and the broker can't share a transaction, so one can succeed while the other fails.

```java
@Transactional
public void place(Order order) {
    orders.save(order);
    kafka.send("orders", new OrderPlaced(order.id()));   // what if this fails? or the TX rolls back after sending?
}
```

* Publish succeeds, transaction rolls back → consumers act on an order that doesn't exist.
* Transaction commits, publish fails (broker down, process crash) → the event is lost forever.

### The outbox solution
Write the event into an **outbox table in the same database transaction** as the business change. A separate **relay** reads the outbox and publishes to the broker, retrying until it succeeds.

```sql
create table outbox (
    id             uuid primary key,
    aggregate_type text        not null,
    aggregate_id   text        not null,
    event_type     text        not null,
    payload        jsonb       not null,
    created_at     timestamptz not null default now(),
    published_at   timestamptz
);
```

```java
@Transactional
public void place(Order order) {
    orders.save(order);
    outbox.save(OutboxEvent.of("Order", order.id(), "OrderPlaced", toJson(new OrderPlaced(order.id()))));
}   // both rows commit or neither does
```

## 🟡 Middle Level

### Relay option 1: polling publisher

```java
@Scheduled(fixedDelay = 500)
@SchedulerLock(name = "outbox-relay", lockAtMostFor = "PT1M")   // or SKIP LOCKED for parallel relays
public void relay() {
    List<OutboxEvent> batch = jdbc.query("""
            select * from outbox where published_at is null
            order by created_at limit 100
            for update skip locked
            """, mapper);
    for (OutboxEvent e : batch) {
        kafka.send(topicFor(e), e.aggregateId(), e.payload()).get();   // wait for broker ack
        jdbc.update("update outbox set published_at = now() where id = ?", e.id());
    }
}
```

Simple and portable; adds polling latency (hundreds of ms) and database load. Clean up published rows periodically (or delete on publish).

### Relay option 2: Change Data Capture (CDC)
**Debezium** reads the database's transaction log (PostgreSQL WAL via logical replication, MySQL binlog) and streams outbox inserts to Kafka. Its **Outbox Event Router** turns rows into messages: topic from `aggregate_type`, key from `aggregate_id`, payload from `payload`.

* Near-real-time, no polling queries, order follows commit order.
* Requires running Kafka Connect + Debezium and replication slots (watch slot lag — an inactive slot makes PostgreSQL retain WAL and fill the disk).

### Guarantees
The outbox gives **at-least-once** publishing: the relay may publish and crash before marking the row → it publishes again. Consumers must be **idempotent** (use the outbox `id` as message ID and deduplicate with an inbox table).

## 🔴 Senior Level

### Ordering
* Use `aggregate_id` as the Kafka key so all events of one aggregate land in the same partition and keep order.
* With a polling relay, `order by created_at` isn't commit order under concurrency (a transaction that started earlier may commit later). If strict per-aggregate order matters, process per aggregate sequentially (lock per aggregate, or a per-aggregate sequence number checked by consumers). CDC preserves commit order naturally.

### Throughput and table hygiene
* Index `(published_at) where published_at is null` (partial index) for the polling query.
* Delete or partition the outbox (`partition by range (created_at)`, drop old partitions) — an ever-growing outbox slows inserts and polling and bloats vacuum.
* With Debezium, you can **insert and immediately delete** the outbox row in the same transaction: the WAL still contains the insert, so CDC sees it, and the table stays empty.

### Variants and related patterns
* **Inbox pattern** on the consumer side: `insert into inbox(message_id) ... on conflict do nothing` in the same transaction as the side effect; if 0 rows inserted, skip as duplicate.
* **Event sourcing** stores events as the source of truth, so the "outbox" is the event store itself.
* **Listen to yourself**: publish first (Kafka as source of truth), and update your own database by consuming your own events — gives consistency through the log but makes reads-after-writes eventually consistent.
* **Transactional messaging in one system**: if the broker is the database (e.g. PostgreSQL-based queues like pgmq) or both support XA, you can use a real transaction — XA/2PC is rarely worth its complexity and performance cost in microservices.

### Spring ecosystem
* **Spring Modulith** has an event publication registry (persists events published inside transactions and re-publishes incomplete ones) — an outbox for in-process listeners, with externalization to Kafka/AMQP/SQS.
* Libraries: Debezium Outbox Event Router (CDC-based), Eventuate Tram (polling or CDC), or a small hand-written relay — the pattern is simple enough that many teams own it.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The transactional outbox solves the dual-write problem by inserting the event into an outbox table in the same transaction as the business change; a relay — a polling publisher or CDC with Debezium — publishes it to the broker with retries. It guarantees at-least-once publishing, so consumers must be idempotent, typically with an inbox table; partition by aggregate ID for ordering.

**Must know:**
* Why save + send is broken in both directions.
* Outbox table schema; same transaction.
* Polling (`FOR UPDATE SKIP LOCKED`) vs CDC (Debezium Outbox Event Router).
* At-least-once → idempotent consumers / inbox.
* Ordering by aggregate key; outbox cleanup; replication slot lag.

**Common follow-ups:**
* Why not use `@TransactionalEventListener(AFTER_COMMIT)` to send?
* How do you guarantee ordering per aggregate?
* What happens if Kafka is down for an hour?

**Red flags:** publishing inside the transaction "and hoping"; XA transactions across DB and Kafka; no deduplication on consumers.
