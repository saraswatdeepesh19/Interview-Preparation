# Testing messaging code with Testcontainers

---

## 🟢 Junior Level

Messaging code has many things that unit tests with mocks can't verify: serialization, topic/queue configuration, acknowledgments, retries, dead-letter routing, ordering, and how your listener behaves when the broker redelivers. **Testcontainers** runs a real broker (Kafka, RabbitMQ, ActiveMQ Artemis, LocalStack for SQS/SNS) in Docker for integration tests.

```java
@SpringBootTest
@Testcontainers
class OrderEventsIT {
    @Container @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("apache/kafka-native:3.8.0"));

    @Autowired KafkaTemplate<String, OrderPlaced> kafkaTemplate;
    @Autowired BillingRepository billing;

    @Test
    void createsInvoiceWhenOrderIsPlaced() {
        kafkaTemplate.send("orders", "o-1", new OrderPlaced("o-1", new BigDecimal("49.90")));

        await().atMost(Duration.ofSeconds(10))
               .untilAsserted(() -> assertThat(billing.findByOrderId("o-1")).isPresent());
    }
}
```

Key techniques: a **real broker**, **asynchronous assertions** with Awaitility (never `Thread.sleep`), and `@ServiceConnection` to wire connection properties automatically.

## 🟡 Middle Level

### RabbitMQ: verifying DLQ routing

```java
@SpringBootTest
@Testcontainers
class InvoiceEmailListenerIT {
    @Container @ServiceConnection
    static RabbitMQContainer rabbit = new RabbitMQContainer("rabbitmq:3.13-management-alpine");

    @Autowired RabbitTemplate rabbitTemplate;
    @MockitoBean Mailer mailer;

    @Test
    void poisonMessageEndsInDlqAfterRetries() {
        doThrow(new MailServerDownException()).when(mailer).send(any());

        rabbitTemplate.convertAndSend("emails", "invoice", new InvoiceEmail("i-1", "ada@example.com"));

        await().atMost(Duration.ofSeconds(15)).untilAsserted(() -> {
            Message dead = rabbitTemplate.receive("emails.invoice.dlq");
            assertThat(dead).isNotNull();
            assertThat(dead.getMessageProperties().getHeaders()).containsKey("x-death");
        });
        verify(mailer, times(3)).send(any());     // retried exactly as configured
    }
}
```

### Testing producers: consume what you sent

```java
@Test
void publishesOrderPlacedWithKeyAndHeaders() {
    orderService.place(newOrder("o-2"));

    try (Consumer<String, String> consumer = testConsumer("orders")) {
        ConsumerRecord<String, String> rec = KafkaTestUtils.getSingleRecord(consumer, "orders", Duration.ofSeconds(10));
        assertThat(rec.key()).isEqualTo("o-2");                               // partitioning by aggregate id
        assertThat(new String(rec.headers().lastHeader("traceparent").value())).startsWith("00-");
        assertThatJson(rec.value()).node("type").isEqualTo("OrderPlaced");
    }
}
```

### What to cover
* Serialization round trip with the **real** configured serializers (and schema registry if used — there's a Testcontainers module approach with a `GenericContainer` for Confluent Schema Registry).
* Error handling: retries, DLQ/DLT, non-retryable exceptions skipping retries.
* Idempotency: send the **same message twice** and assert the side effect happened once.
* Outbox relay: write a business change and assert the event appears on the broker.

## 🔴 Senior Level

### Testing redelivery and crash scenarios
* **Duplicate delivery** — produce the same record twice (same ID) or reset the consumer group offset and replay; verify the inbox deduplicates.
* **Crash before ack/commit** — stop the listener container mid-processing (`registry.getListenerContainer("billing").stop()` from a test hook after the side effect but before commit), restart it, and assert exactly-once *effect*.
* **Rebalance** — start two consumer instances in the same group (two containers or two app contexts) and check partition ownership changes don't cause duplicates beyond what idempotency handles.
* **Broker failures** — Toxiproxy between app and broker to inject latency or cut connections; assert producers handle `TimeoutException` and recover, listeners reconnect, and no messages are lost (publisher confirms / `acks=all`).

### Making tests fast and stable
* **One broker per JVM** (singleton container) and **unique topic/queue names per test** (`orders-" + UUID`) so tests don't interfere; auto-create topics or create them with `AdminClient` in `@BeforeEach`.
* `auto.offset.reset=earliest` for test consumers; unique `group.id` per test.
* Faster images: `apache/kafka-native` (GraalVM) starts in about a second; RabbitMQ Alpine images.
* Tune listener settings in tests (short backoffs, fewer retries) via test properties rather than waiting for production-length delays.
* Awaitility with generous `atMost` and short `pollInterval`; the test finishes as soon as the condition holds.

### Embedded alternatives and when they're OK
* `@EmbeddedKafka` (spring-kafka-test) — in-JVM Kafka; fast but not identical to production versions/configs, and can complicate classpaths. Fine for library-level tests.
* Spring Cloud Stream **test binder** — no broker at all; good for function logic, not for broker semantics.
* Use real brokers (Testcontainers) for anything involving acknowledgment, DLQ, partitioning, transactions or serialization configuration.

### Contract tests for messages
Complement integration tests with **message contract tests** (Pact message pacts, Spring Cloud Contract messaging) so producers can't break consumers' expectations without a failing build — integration tests in one service don't catch cross-team schema drift.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I test messaging against a real broker started with Testcontainers and `@ServiceConnection`, assert asynchronously with Awaitility, and verify what mocks can't: serialization, keys and headers, retries and DLQ routing, idempotent handling of duplicates, and recovery from crashes, rebalances and broker faults injected with Toxiproxy. Tests share one broker per JVM with unique topics per test, and message contract tests cover cross-team schemas.

**Must know:**
* Kafka/RabbitMQ/LocalStack containers; `@ServiceConnection`.
* Awaitility instead of sleeps.
* Testing DLQ (`x-death` headers), retries count, non-retryable exceptions.
* Duplicate and crash-before-commit scenarios.
* Embedded Kafka/test binder limitations.

**Common follow-ups:**
* How do you test exactly-once effects?
* How do you keep messaging tests from interfering with each other?
* Embedded Kafka or Testcontainers?

**Red flags:** `Thread.sleep(5000)` in tests; shared topics across tests; mocking `KafkaTemplate` as the only test.
