# Event-driven architecture and message types

---

## 🟢 Junior Level

In an **event-driven architecture (EDA)**, services communicate by producing and reacting to **messages** instead of calling each other synchronously. It decouples services in time (the consumer can be down), in scale (consumers process at their own pace), and in knowledge (the producer doesn't need to know who consumes).

### Three kinds of messages

| Type | Meaning | Naming | Example | Consumers |
| --- | --- | --- | --- | --- |
| **Command** | "Please do this" — intent directed at one handler | Imperative | `ChargeCard`, `SendInvoiceEmail` | Exactly one logical handler |
| **Event** | "This happened" — a fact in the past | Past tense | `OrderPlaced`, `PaymentFailed` | Zero to many |
| **Query / request-reply** | "Tell me something" | Question | `GetCreditScore` | One, which replies |

```java
// Event: the order service announces a fact; it doesn't know or care who listens
public record OrderPlaced(String orderId, String customerId, BigDecimal total, Instant occurredAt) {}

// Command: the checkout process asks the payment service to do something
public record ChargeCard(String paymentId, String orderId, Money amount, String idempotencyKey) {}
```

### Why the distinction matters
Commands create **coupling** to a specific receiver and can be rejected ("card declined"). Events can't be rejected — they already happened — and adding a new consumer requires no change to the producer.

## 🟡 Middle Level

### Event styles
* **Event notification** — thin event with IDs only (`OrderPlaced{orderId}`); consumers call back for details. Small payloads, but creates runtime coupling and load on the producer.
* **Event-carried state transfer** — fat event with the data consumers need (`OrderPlaced{orderId, lines, address, total}`). Consumers keep local copies, no callbacks; larger messages and more schema surface.
* **Event sourcing** — events are the system of record internally (different concern from integration events).

Choose fat events for integration between bounded contexts when consumers need the data anyway; avoid leaking internal fields — events are a **public contract**.

### Choreography vs orchestration
* **Choreography** — each service reacts to events and emits its own (`OrderPlaced → PaymentCaptured → StockReserved → OrderConfirmed`). Loose coupling; the overall flow is implicit and harder to see and change.
* **Orchestration** — a coordinator (saga orchestrator, workflow engine like Temporal/Camunda) sends commands and waits for replies. Explicit flow, easier to monitor; the orchestrator knows all participants.

### Envelope and metadata
Standardize metadata (CloudEvents is a good template):

```json
{
  "specversion": "1.0",
  "id": "8f0c3a8e-0b7c-4c1b-9a8f-d3a1f1f7a6e2",
  "source": "/orders",
  "type": "com.shop.order.placed.v1",
  "time": "2026-10-16T10:15:00Z",
  "subject": "o-42",
  "traceparent": "00-4bf92f35...-00f067aa...-01",
  "data": { "orderId": "o-42", "customerId": "c-7", "total": "49.90" }
}
```

A unique `id` enables deduplication; `type` with a version enables evolution; trace context links async flows in tracing tools.

## 🔴 Senior Level

### Trade-offs to state honestly
* **Eventual consistency** — consumers see changes later; UIs and APIs must handle "pending" states.
* **Debuggability** — flows span services and time; you need correlation IDs, tracing through brokers, and event catalogs (AsyncAPI, schema registry).
* **Ordering and duplicates** — at-least-once delivery and partition-level ordering mean idempotent consumers and tolerance of reordering across keys.
* **Hidden coupling** — consumers depend on event schemas and semantics; changing them is as hard as changing an API.
* **Error handling** — a failed consumer doesn't fail the producer's request; you need DLQs, alerting, and reprocessing tools.

### Design guidelines
* **Domain events vs integration events**: internal domain events (rich, change often) are translated into stable integration events at the boundary (anti-corruption layer for outgoing data).
* **Publish facts, not intentions disguised as events** (`SendEmailRequested` is really a command).
* **Make events self-contained enough** that consumers don't need synchronous callbacks for the common path.
* **Schema evolution rules**: additive changes only; new event type/version for breaking changes; schemas in a registry with compatibility checks.
* **Reliable publication**: transactional outbox; **reliable consumption**: idempotency + inbox; **replayability**: consumers can rebuild state from retained events (Kafka retention/compaction).
* **Event granularity**: one event per meaningful business state change; avoid CRUD-style `OrderUpdated` with everything — consumers can't tell what changed.

### When not to go event-driven
Simple request/response interactions needing an immediate answer (validation, read APIs), small systems with one team, and flows needing strong consistency across steps — synchronous calls or a modular monolith are simpler there.

## 🎯 Interview Cheat Sheet

**30-second pitch:** In event-driven architecture, services exchange messages: commands ask one handler to do something and can fail, events announce facts to any number of consumers, and queries request data. I use fat events for integration with a stable, versioned public contract and metadata like ID, type and trace context, choose choreography or orchestration per flow, and design for eventual consistency, duplicates and ordering.

**Must know:**
* Command vs event vs query; naming conventions.
* Event notification vs event-carried state transfer vs event sourcing.
* Choreography vs orchestration.
* CloudEvents-style envelope; idempotency via event ID.
* Domain vs integration events; outbox + inbox.

**Common follow-ups:**
* When would you use orchestration instead of choreography?
* How do you evolve an event schema?
* How do you debug a flow across five services?

**Red flags:** "events" that are really commands; generic `EntityUpdated` events; synchronous callbacks for every event.
