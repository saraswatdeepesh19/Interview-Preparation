# JMS API with ActiveMQ and Artemis

---

## 🟢 Junior Level

### 1. What is JMS?

**JMS (Jakarta Messaging, formerly Java Message Service)** is a **Java API specification** — not a wire protocol and not a product. It defines the interfaces (`ConnectionFactory`, `Connection`, `Session`, `Destination`, `MessageProducer`, `MessageConsumer`, `Message`) that Java code uses to talk to a message broker. Brokers such as **Apache ActiveMQ Classic**, **Apache ActiveMQ Artemis**, **IBM MQ** and **Oracle AQ** provide implementations ("JMS providers").

**Analogy:** JMS is like JDBC. JDBC is the common Java interface; Oracle, PostgreSQL and MySQL are the drivers. Switch the driver, keep the code.

> [!NOTE]
> Since Jakarta EE 9 the package changed from `javax.jms` to `jakarta.jms`. Spring Boot 3 uses `jakarta.jms`.

### 2. Two destination types

- `Queue` — point-to-point, one consumer gets each message.
- `Topic` — publish/subscribe, all active subscribers get each message.

### 3. Five message types

`TextMessage`, `ObjectMessage` (avoid — Java serialization is a security risk), `MapMessage`, `BytesMessage`, `StreamMessage`. In practice use `TextMessage` carrying JSON.

### 4. Minimal example with the JMS 2.0 simplified API

```java
import jakarta.jms.ConnectionFactory;
import jakarta.jms.JMSContext;
import jakarta.jms.Queue;
import org.apache.activemq.artemis.jms.client.ActiveMQConnectionFactory;

public class HelloJms {
    public static void main(String[] args) {
        ConnectionFactory cf = new ActiveMQConnectionFactory("tcp://localhost:61616", "artemis", "artemis");
        try (JMSContext ctx = cf.createContext()) {
            Queue queue = ctx.createQueue("hello.queue");
            ctx.createProducer().send(queue, "Hello, Artemis!");
            String received = ctx.createConsumer(queue).receiveBody(String.class, 2000);
            System.out.println("Got: " + received);
        }
    }
}
```

`JMSContext` combines `Connection` + `Session` and is `AutoCloseable`, which removes the boilerplate of JMS 1.1.

### 5. Spring Boot way

```java
import org.springframework.jms.annotation.JmsListener;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Component;

@Component
class JmsDemo {
    private final JmsTemplate jmsTemplate;

    JmsDemo(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    void send(String text) {
        jmsTemplate.convertAndSend("orders.in", text);
    }

    @JmsListener(destination = "orders.in")
    void receive(String text) {
        System.out.println("Received: " + text);
    }
}
```

With `spring-boot-starter-artemis` and `spring.artemis.broker-url=tcp://localhost:61616` Boot auto-configures the `ConnectionFactory`, `JmsTemplate` and the listener container.

## 🟡 Middle Level

### 1. ActiveMQ Classic vs Artemis

| Aspect | ActiveMQ Classic 5.x | ActiveMQ Artemis |
| :--- | :--- | :--- |
| Architecture | Older design, KahaDB store | Non-blocking Netty core, append-only journal (AIO on Linux / NIO) |
| Protocols | OpenWire, AMQP 1.0, STOMP, MQTT | Core, OpenWire, AMQP 1.0, STOMP, MQTT |
| Direction | Mature, maintenance-oriented | The strategic broker (basis of Red Hat AMQ) |
| HA | Network of brokers, JDBC/KahaDB failover | Live/backup pairs with shared store or replication, clustering with message redistribution |
| Address model | Queue/Topic | Addresses with `ANYCAST` (queue semantics) and `MULTICAST` (topic) routing types |

### 2. Session acknowledgement modes

| Mode | Meaning |
| :--- | :--- |
| `AUTO_ACKNOWLEDGE` | Ack automatically when listener returns normally (default) |
| `CLIENT_ACKNOWLEDGE` | You call `message.acknowledge()` (acks *all* consumed on the session so far) |
| `DUPS_OK_ACKNOWLEDGE` | Lazy ack, duplicates possible, higher throughput |
| `SESSION_TRANSACTED` | Ack/commit on `session.commit()`; rollback causes redelivery |

In Spring, `DefaultJmsListenerContainerFactory` with `setSessionTransacted(true)` makes the listener transactional: an exception → rollback → redelivery. That is how you get at-least-once semantics.

### 3. Durable subscriptions

A normal topic subscriber misses messages published while it is offline. A **durable subscription** is identified by `clientId + subscriptionName`, and the broker stores messages for it. JMS 2.0 adds **shared subscriptions** so several consumers share one subscription (load-balancing on a topic):

```java
import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.stereotype.Component;

@Configuration
class JmsConfig {
    @Bean
    DefaultJmsListenerContainerFactory durableTopicFactory(ConnectionFactory cf) {
        DefaultJmsListenerContainerFactory f = new DefaultJmsListenerContainerFactory();
        f.setConnectionFactory(cf);
        f.setPubSubDomain(true);
        f.setSubscriptionDurable(true);
        f.setSubscriptionShared(true);   // JMS 2.0 shared durable subscription
        f.setSessionTransacted(true);
        f.setConcurrency("3-5");
        return f;
    }
}

@Component
class ShippingListener {
    @JmsListener(destination = "orders.placed", containerFactory = "durableTopicFactory",
                 subscription = "shipping-service")
    void onOrder(String json) { /* ship */ }
}
```

### 4. Selectors, priority, TTL

- **Message selector** — SQL-92-like filter evaluated by the broker on *headers/properties*: `@JmsListener(destination="q", selector="region = 'EU' AND amount > 100")`. Cheap but not a substitute for proper routing; heavy selector use degrades performance.
- **Priority** (0-9) — ordering is best effort and breaks strict FIFO.
- **TimeToLive** — expired messages go to the expiry address.

### 5. JmsTemplate pitfalls

`JmsTemplate` opens connection+session+producer for **every send** unless the `ConnectionFactory` is pooled or caching. Without it, throughput collapses. Spring Boot wraps the factory in a `CachingConnectionFactory` by default (`spring.jms.cache.enabled=true`), or you can use the pooled factory (`spring.artemis.pool.enabled=true`).

Also, `JmsTemplate.receive()` is blocking and synchronous; for consumption prefer message-driven listeners.

### 6. Common mistakes

- Using `ObjectMessage` (deserialization gadgets; classpath coupling). Use JSON via `MappingJackson2MessageConverter`.
- Forgetting `setPubSubDomain(true)` and wondering why a topic acts like a queue.
- Mixing transacted and non-transacted sessions, then wondering why rollback does not redeliver.
- Unbounded concurrency causing broker connection exhaustion.

JSON converter bean:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.support.converter.MappingJackson2MessageConverter;
import org.springframework.jms.support.converter.MessageConverter;
import org.springframework.jms.support.converter.MessageType;

@Configuration
class JmsJsonConfig {
    @Bean
    MessageConverter jacksonJmsMessageConverter() {
        MappingJackson2MessageConverter c = new MappingJackson2MessageConverter();
        c.setTargetType(MessageType.TEXT);
        c.setTypeIdPropertyName("_type"); // class id carried as a property
        return c;
    }
}
```

## 🔴 Senior Level

### 1. Redelivery and poison handling in JMS

On rollback the broker increments `JMSXDeliveryCount`. Artemis address settings define `max-delivery-attempts` (default 10), `redelivery-delay`, `redelivery-delay-multiplier`, and a `dead-letter-address`. Example in `broker.xml`:

```xml
<address-setting match="orders.#">
   <dead-letter-address>DLQ.orders</dead-letter-address>
   <max-delivery-attempts>5</max-delivery-attempts>
   <redelivery-delay>2000</redelivery-delay>
   <redelivery-delay-multiplier>2.0</redelivery-delay-multiplier>
   <max-redelivery-delay>60000</max-redelivery-delay>
   <expiry-address>ExpiryQueue</expiry-address>
   <max-size-bytes>104857600</max-size-bytes>
   <address-full-policy>PAGE</address-full-policy>
</address-setting>
```

Broker-side redelivery is better than catching exceptions in the listener because it survives consumer restarts. See [Dead letter queues retries and poison messages](06.%20Dead%20letter%20queues%20retries%20and%20poison%20messages.md).

### 2. Persistence and flow control internals (Artemis)

Artemis writes to an **append-only journal** of preallocated files, using Linux **libaio** (`journal-type=ASYNCIO`) for asynchronous direct I/O, falling back to NIO. Paging: when an address exceeds `max-size-bytes`, messages are *paged* to disk; `address-full-policy` can be `PAGE`, `BLOCK`, `DROP` or `FAIL`. **Credit-based flow control** on the client (`consumerWindowSize`, default 1 MiB) acts like prefetch; for slow consumers with large messages set `consumerWindowSize=0` to avoid hoarding.

### 3. Exactly-once in JMS?

JMS offers local transactions and, via JTA/XA (`XAConnectionFactory`), two-phase commit with a database. XA can atomically consume a message and write a row, but it is slow, requires a transaction manager (Atomikos, Narayana), has recovery complexity and is disliked in cloud-native designs. The modern approach: local JMS transaction + **idempotent consumer** (see [Idempotent consumers deduplication and the inbox pattern](08.%20Idempotent%20consumers%20deduplication%20and%20the%20inbox%20pattern.md)). Artemis also offers duplicate detection via the `_AMQ_DUPL_ID` header, a producer-side dedupe cache.

```java
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;
import java.util.UUID;

@Service
class DedupAwareSender {
    private final JmsTemplate jms;

    DedupAwareSender(JmsTemplate jms) {
        this.jms = jms;
    }

    void send(String destination, String body, String businessKey) {
        jms.send(destination, session -> {
            var msg = session.createTextMessage(body);
            msg.setStringProperty("_AMQ_DUPL_ID", businessKey);   // Artemis duplicate detection
            msg.setStringProperty("messageId", UUID.randomUUID().toString());
            return msg;
        });
    }
}
```

### 4. Scaling and threading

`DefaultMessageListenerContainer` polls using a thread pool; `concurrency="3-10"` scales between 3 and 10 consumers dynamically. Concurrent consumers on one queue break strict ordering; for order-sensitive flows use **message groups** (`JMSXGroupID`) so all messages with the same group id go to a single consumer, giving per-key ordering plus parallelism across keys. Compare with partitioning in [Message ordering partitioning and competing consumers](09.%20Message%20ordering%20partitioning%20and%20competing%20consumers.md).

### 5. Production diagnostics

- Artemis management console and Prometheus metrics plugin: message count, delivering count, scheduled count, consumer count.
- `artemis queue stat --url tcp://host:61616` from the CLI.
- Thread dumps: many `DefaultMessageListenerContainer` threads waiting in `receive` is normal; threads stuck in your own code are not.
- Watch for **consumer hoarding**: one consumer holds a large window of messages while others idle, producing apparent starvation.

### 6. When to pick JMS at all

JMS is a strong choice for enterprise/Jakarta EE shops, IBM MQ estates, XA scenarios and teams needing a standard Java API. Since Artemis speaks AMQP 1.0 and MQTT, non-Java clients can interoperate. For polyglot-first designs with rich routing, [RabbitMQ with AMQP 0-9-1](03.%20AMQP%20and%20RabbitMQ%20exchanges%20queues%20and%20bindings.md) is more common.

## 🎯 Interview Cheat Sheet

**30-second elevator pitch:** JMS (now Jakarta Messaging) is the standard Java API for brokers, like JDBC for messaging. ActiveMQ Classic and Artemis are open-source providers; Artemis is the modern, high-performance one with a journal and multi-protocol support. In Spring you use `JmsTemplate` for sending and `@JmsListener` for consuming, with transacted sessions for at-least-once delivery and broker-side redelivery/DLQ for poison messages.

**Must-know bullets:**
- JMS is an API, not a protocol; `javax.jms` → `jakarta.jms` in Boot 3.
- Queue vs topic; durable and shared subscriptions for offline subscribers and scaling.
- Ack modes: AUTO, CLIENT, DUPS_OK, SESSION_TRANSACTED.
- Pool/cache connections for `JmsTemplate`.
- Avoid `ObjectMessage`; use JSON with a type property.
- Message groups give ordering per key.

**Common follow-up questions:**
- What is the difference between a durable and a non-durable subscription?
- How do you get load-balancing on a topic in JMS?
- How does Artemis persist messages?
- How do you achieve exactly-once with JMS and a database?

**🚩 Red flags:**
- Saying JMS is a protocol.
- Creating a connection per message.
- Using Java serialization for message bodies.
