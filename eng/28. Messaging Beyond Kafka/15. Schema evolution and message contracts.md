# Schema evolution and message contracts

---

## 🟢 Junior Level

A message's structure is a **contract** between producer and consumers. Unlike a synchronous API, you can't deploy producer and consumers at the same instant, and old messages may sit in queues or logs for days. So schemas must **evolve compatibly**: new producers and old consumers (and vice versa) must keep working.

### Safe vs breaking changes

| Change | Usually safe? |
| --- | --- |
| Add an **optional** field with a default | ✅ |
| Remove an optional field consumers don't use | ⚠️ only if no consumer reads it |
| Rename a field | ❌ (looks like remove + add) |
| Change a field's type (`int` → `string`) | ❌ |
| Make an optional field required | ❌ |
| Change meaning/units (`amount` cents → euros) | ❌ worst kind — silently wrong |

### Tolerant reader
Consumers should **ignore unknown fields** and use defaults for missing ones:

```java
@JsonIgnoreProperties(ignoreUnknown = true)       // or mapper.configure(FAIL_ON_UNKNOWN_PROPERTIES, false)
public record OrderPlaced(String orderId, BigDecimal total, String currency) {
    public OrderPlaced {
        if (currency == null) currency = "EUR";   // default for messages from older producers
    }
}
```

## 🟡 Middle Level

### Compatibility modes (Schema Registry terminology)
* **Backward** — consumers using the **new** schema can read data written with the **old** one. (Upgrade consumers first.)
* **Forward** — consumers using the **old** schema can read data written with the **new** one. (Upgrade producers first.)
* **Full** — both directions.
* `*_TRANSITIVE` variants check against **all** previous versions, not just the latest — important when topics retain old data.

### Avro with Confluent Schema Registry

```json
{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "com.shop.events",
  "fields": [
    { "name": "orderId",  "type": "string" },
    { "name": "total",    "type": { "type": "bytes", "logicalType": "decimal", "precision": 12, "scale": 2 } },
    { "name": "currency", "type": "string", "default": "EUR" },
    { "name": "channel",  "type": ["null", "string"], "default": null }
  ]
}
```

The producer serializer registers the schema and prefixes each message with a schema ID; consumers fetch the writer's schema by ID and resolve it against their reader schema. The registry **rejects** incompatible schema versions at registration time — CI should test compatibility before deployment (`mvn schema-registry:test-compatibility`).

### Format comparison

| Format | Schema | Evolution rules | Size/speed | Notes |
| --- | --- | --- | --- | --- |
| JSON (+ JSON Schema) | Optional | Convention-based; tolerant readers | Larger, slower | Human-readable; easy debugging |
| Avro | Required | Defaults, unions; resolution by writer/reader schema | Compact | Kafka ecosystem standard |
| Protobuf | Required | Field numbers; never reuse numbers; `reserved` | Compact, fast | gRPC standard; good tooling |

## 🔴 Senior Level

### Protobuf rules worth knowing

```protobuf
message OrderPlaced {
  string order_id = 1;
  string total    = 2;    // decimal as string to avoid float issues
  string currency = 3;
  reserved 4;             // removed field "coupon" — number can never be reused
  reserved "coupon";
  optional string channel = 5;
}
```

Wire compatibility depends on **field numbers**, not names; renaming a field is wire-compatible but breaks JSON mapping and code. Changing `int32` ↔ `int64` is compatible on the wire for some ranges, `string` ↔ `bytes` only for valid UTF-8 — avoid type changes entirely.

### Breaking changes: version the event, not the field
When semantics change, publish a **new event type** (`OrderPlaced.v2` / `com.shop.order.placed.v2`), possibly on a new topic, and run both for a migration period:
1. Producer publishes v1 and v2 (or a translator publishes v1 from v2).
2. Consumers migrate to v2 one by one.
3. Monitor v1 consumption (consumer group lag/activity); retire v1.

Alternatively an **upcaster** in consumers converts old versions to the new model on read — useful for replaying retained history.

### Contract governance
* **Ownership**: the producing team owns the schema; consumers contribute via PRs.
* **Catalog**: AsyncAPI documents channels, messages and schemas; schema registry subjects per topic (`TopicNameStrategy`) or per record type (`RecordNameStrategy`) when a topic carries multiple event types.
* **Consumer-driven contract tests for messages** (Pact message pacts, Spring Cloud Contract messaging) verify that producers still emit what consumers rely on.
* **Semantic documentation**: units, currencies, time zones, nullability, ordering and idempotency guarantees — the parts a schema can't express.

### Operational traps
* Compacted topics keep the latest value per key **forever** — every historical schema version must stay readable (`FULL_TRANSITIVE`).
* `TopicNameStrategy` with mixed event types in one topic forces a union schema; choose the strategy deliberately.
* Deleting a schema version in the registry breaks consumers of old messages that reference its ID.
* Dead-letter topics often contain messages that failed due to schema problems — keep their schema IDs/headers for replay after fixes.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Message schemas are long-lived contracts because producers and consumers deploy independently and old messages persist. I allow only compatible changes — optional fields with defaults, tolerant readers that ignore unknown fields — enforce compatibility with a schema registry using Avro or Protobuf in CI, and introduce a new versioned event type for breaking or semantic changes with a migration period.

**Must know:**
* Backward vs forward vs full (transitive) compatibility.
* Avro defaults/unions; Protobuf field numbers and `reserved`.
* Tolerant reader; never change meaning or units silently.
* New event version + parallel publishing for breaking changes; upcasters.
* AsyncAPI, schema registry subject strategies, message contract tests.

**Common follow-ups:**
* Which side upgrades first under backward compatibility?
* How do you rename a field safely?
* How do you evolve events in a compacted topic?

**Red flags:** `FAIL_ON_UNKNOWN_PROPERTIES=true` in consumers; reusing Protobuf field numbers; changing units without a new version.
