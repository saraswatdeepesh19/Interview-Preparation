# Operating brokers clustering and quorum queues

---

## 🟢 Junior Level

A single broker node is a single point of failure. Production brokers run as **clusters** with **replicated** queues/partitions so that losing a node doesn't lose messages or availability.

### RabbitMQ
* A RabbitMQ **cluster** shares users, vhosts, exchanges and bindings across nodes; **queue contents** live on specific nodes unless the queue is replicated.
* **Quorum queues** (RabbitMQ 3.8+) are the recommended replicated queue type: each queue is replicated across (typically) 3 or 5 nodes using the **Raft** consensus protocol. A message is confirmed once a majority stored it.
* Classic mirrored queues are **deprecated and removed in RabbitMQ 4.0** — migrate to quorum queues (or Streams).

```java
@Bean
Queue invoiceQueue() {
    return QueueBuilder.durable("emails.invoice")
            .quorum()                                     // x-queue-type=quorum
            .deliveryLimit(5)                             // poison-message protection
            .deadLetterExchange("emails.dlx")
            .build();
}
```

### Kafka
* Each partition has a **leader** and **followers** on different brokers (`replication.factor=3`).
* Producers with `acks=all` wait until all **in-sync replicas (ISR)** have the record; `min.insync.replicas=2` makes writes fail rather than accept data that only one broker holds.
* Since Kafka 3.3+/4.0, **KRaft** (Raft-based controller quorum) replaces ZooKeeper.

## 🟡 Middle Level

### Durability checklist

| Concern | RabbitMQ | Kafka |
| --- | --- | --- |
| Replication | Quorum queues, 3 or 5 replicas, spread across AZs | `replication.factor=3`, rack awareness (`broker.rack`) |
| Write acknowledgement | Publisher confirms (`spring.rabbitmq.publisher-confirm-type=correlated`) | `acks=all` + idempotent producer (default since 3.0) |
| Majority requirement | Raft majority | `min.insync.replicas=2` |
| Message persistence | Durable queues + persistent messages (quorum queues are always durable) | Segments on disk; `unclean.leader.election.enable=false` |
| Consumer safety | Manual ack after processing | Commit offsets after processing |

### Odd numbers and AZs
Raft-based systems need a majority: 3 nodes tolerate 1 failure, 5 tolerate 2. Spread nodes across **three availability zones** — with two AZs, losing the AZ holding the majority stops the cluster.

### Quorum queue behavior to know
* **Delivery limit** (`x-delivery-limit`) dead-letters messages redelivered too many times — protection against poison messages looping forever. (RabbitMQ 4.0 sets a default delivery limit of 20.)
* Quorum queues keep messages on disk and in memory up to limits; very long queues increase memory/disk and slow recovery. Set `x-max-length`/`x-max-length-bytes` with `overflow: reject-publish` to apply backpressure instead of growing unbounded.
* Leader per queue: distribute queue leaders across nodes (`queue-leader-locator: balanced`) so one node doesn't do all the work.

## 🔴 Senior Level

### Failure modes and operations
* **Network partitions (RabbitMQ)** — classic clusters needed a partition handling strategy (`pause_minority` recommended); quorum queues handle partitions via Raft (minority side stops serving those queues). Avoid stretching one cluster across regions; use **federation** or **shovel** for cross-region links.
* **Memory/disk alarms** — RabbitMQ blocks publishers when memory exceeds `vm_memory_high_watermark` (default 0.6 of RAM, or an absolute value) or free disk drops below `disk_free_limit`. Publishers in request threads then block — decouple with an outbox or timeouts on publish.
* **Kafka under-replicated partitions** — the key health metric (`UnderReplicatedPartitions` > 0, `UnderMinIsrPartitionCount`). Causes: slow disks, broker down, network saturation. With `min.insync.replicas=2` and two replicas down, producers with `acks=all` get `NotEnoughReplicasException` — correct behavior: availability traded for durability.
* **Rolling upgrades** — Kafka: one broker at a time, wait for under-replicated partitions to return to zero; controlled shutdown moves leadership first. RabbitMQ: quorum queues tolerate rolling restarts if a majority stays up; check `rabbitmq-upgrade await_online_quorum_plus_one` before stopping a node.
* **Capacity** — Kafka throughput is mostly disk and network bound; plan for retention × produce rate × replication factor of disk, and for consumer catch-up reads (which hit disk when not in page cache). RabbitMQ is CPU/memory bound per queue; very hot single queues bottleneck on one Raft leader — shard into multiple queues (consistent-hash exchange or sharding plugin).

### Monitoring essentials
* RabbitMQ (Prometheus plugin): queue depth (`rabbitmq_queue_messages_ready`), unacked messages, publish/deliver/ack rates, consumer count per queue, memory/disk alarms, Raft leader/followers health, connection churn.
* Kafka: under-replicated and offline partitions, request latency (produce/fetch p99), ISR shrink/expand rate, consumer lag (time-based), disk usage per broker, controller health.
* Alerts tied to business SLOs: oldest message age per critical queue/topic.

### Managed options
Amazon MQ (RabbitMQ/ActiveMQ), CloudAMQP, Amazon MSK (including MSK Serverless), Confluent Cloud, Aiven, and the Strimzi operator on Kubernetes reduce operational load; you still own topic/queue design, client configuration (acks, confirms, retries, idempotency) and capacity planning.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Production brokers run as clusters with replication: RabbitMQ quorum queues replicate each queue with Raft across 3 or 5 nodes and replace deprecated mirrored queues; Kafka replicates partitions with leaders and ISR, using `acks=all`, `min.insync.replicas=2` and no unclean leader election. I spread nodes across three AZs, use publisher confirms and manual acks, set delivery limits and length limits, and monitor under-replicated partitions, alarms and message age.

**Must know:**
* Quorum queues (Raft), delivery limit, mirrored queues removed in 4.0.
* Kafka RF=3, ISR, `min.insync.replicas`, KRaft.
* Odd-sized quorums across three AZs.
* RabbitMQ memory/disk alarms block publishers.
* Rolling upgrade procedures; key health metrics.

**Common follow-ups:**
* What happens if two of three Kafka replicas are down?
* Why not stretch a RabbitMQ cluster across regions?
* How do you prevent poison messages from looping forever?

**Red flags:** single-node brokers in production; `acks=1` for important data; unbounded queues.
