# Spring Cloud Stream binder model

---

## 🟢 Junior Level

**Spring Cloud Stream** lets you write message-driven microservices as **plain Java functions** and connect them to a broker through **binders** — Kafka, RabbitMQ, Kinesis, Pulsar, Solace, Azure Event Hubs, and others. Your code doesn't use broker APIs; configuration decides where messages come from and go to.

```java
@SpringBootApplication
public class EnrichmentApp {
    @Bean
    public Function<OrderPlaced, EnrichedOrder> enrich(CustomerClient customers) {   // consumer + producer
        return order -> new EnrichedOrder(order, customers.get(order.customerId()));
    }

    @Bean
    public Consumer<EnrichedOrder> audit() {                                     // consumer only
        return e -> log.info("audited {}", e.orderId());
    }

    @Bean
    public Supplier<Heartbeat> heartbeat() {                                     // producer, polled every 1 s by default
        return () -> new Heartbeat(Instant.now());
    }
}
```

```yaml
spring:
  cloud:
    function:
      definition: enrich;audit;heartbeat
    stream:
      bindings:
        enrich-in-0:  { destination: orders,          group: enrichment }
        enrich-out-0: { destination: orders-enriched }
        audit-in-0:   { destination: orders-enriched, group: audit }
        heartbeat-out-0: { destination: heartbeats }
```

Swapping Kafka for RabbitMQ is (mostly) a dependency change: `spring-cloud-stream-binder-kafka` → `spring-cloud-stream-binder-rabbit`.

## 🟡 Middle Level

### Core concepts
* **Binding** — the connection between a function's input/output and a destination; named `<function>-in-<index>` / `-out-<index>`.
* **Destination** — Kafka topic or RabbitMQ exchange.
* **Consumer group** — `group` makes instances compete for messages (one instance processes each message) and makes subscriptions durable. Without a group, each instance gets an anonymous, non-durable subscription (every instance receives every message, and messages are lost while it's down).
* **Partitioning** — `producer.partition-key-expression: headers['orderId']` and `partition-count` for ordered processing per key across instances (Kafka uses native partitions; RabbitMQ binder emulates partitions with multiple queues).
* **Message conversion** — content-type negotiation (`application/json` default) with Jackson; Avro/Protobuf via schema registry converters.

### Error handling and retries

```yaml
spring:
  cloud:
    stream:
      bindings:
        enrich-in-0:
          consumer:
            max-attempts: 3            # in-memory retries (blocking), default 3
            back-off-initial-interval: 500
            back-off-multiplier: 2.0
      kafka:
        bindings:
          enrich-in-0:
            consumer:
              enable-dlq: true
              dlq-name: orders.enrichment.dlq
```

After retries are exhausted, the message goes to the DLQ (Kafka binder: dead-letter topic; Rabbit binder: DLX/DLQ with `auto-bind-dlq: true`).

### Dynamic destinations
`StreamBridge` sends to destinations decided at runtime (e.g. from a REST controller):

```java
@RestController
class OrderController {
    private final StreamBridge bridge;
    @PostMapping("/orders")
    void place(@RequestBody OrderPlaced e) { bridge.send("orders-out-0", e); }
}
```

For transactional guarantees with your database, still use an **outbox** — `StreamBridge.send` inside `@Transactional` is a dual write.

## 🔴 Senior Level

### Abstraction trade-offs
**Pros**: very little boilerplate; consistent configuration, retries, DLQ, metrics across brokers; easy testing with the **test binder**; functions compose (`spring.cloud.function.definition: enrich|validate`) and also run in serverless platforms (Spring Cloud Function adapters for AWS Lambda/Azure Functions).

**Cons**: lowest-common-denominator semantics. Broker-specific features — Kafka transactions and exactly-once processing, idempotent producers, cooperative rebalancing tuning, RabbitMQ quorum queue arguments, publisher confirms — require binder-specific properties (`spring.cloud.stream.kafka.binder.*`, `spring.cloud.stream.rabbit.bindings.*`) and understanding the underlying client anyway. Debugging goes through more layers.

If you deeply depend on one broker's semantics, using **Spring Kafka** or **Spring AMQP** directly is often clearer.

### Kafka Streams binder
A separate binder (`spring-cloud-stream-binder-kafka-streams`) maps functions to Kafka Streams topologies with `KStream`/`KTable` types:

```java
@Bean
public Function<KStream<String, OrderPlaced>, KStream<String, Long>> ordersPerCustomer() {
    return orders -> orders
            .groupBy((k, v) -> v.customerId())
            .count(Materialized.as("orders-per-customer"))      // state store backed by a changelog topic
            .toStream();
}
```

State stores, interactive queries, exactly-once (`processing.guarantee=exactly_once_v2`) and windowing come from Kafka Streams itself.

### Testing

```java
@SpringBootTest
@Import(TestChannelBinderConfiguration.class)
class EnrichmentTest {
    @Autowired InputDestination input;
    @Autowired OutputDestination output;

    @Test
    void enriches() {
        input.send(MessageBuilder.withPayload(new OrderPlaced("o-1", "c-7")).build(), "orders");
        Message<byte[]> out = output.receive(1_000, "orders-enriched");
        assertThat(new String(out.getPayload())).contains("\"orderId\":\"o-1\"");
    }
}
```

Use the test binder for fast unit-level checks, and Testcontainers with the real broker for integration tests of DLQ, partitioning and serialization.

### Observability
Bindings expose health (`/actuator/health` binders), metrics (`spring.cloud.stream.binder.kafka.offset` lag, Micrometer consumer/producer metrics) and, with Micrometer Tracing, propagate trace headers through messages (`spring.cloud.stream.kafka.binder.enable-observation=true` / Rabbit equivalents).

## 🎯 Interview Cheat Sheet

**30-second pitch:** Spring Cloud Stream maps `Supplier`, `Function` and `Consumer` beans to broker destinations through binders, so business code is broker-agnostic. Bindings, destinations and consumer groups are configuration; it adds conversion, retries, DLQs, partitioning and a test binder. The trade-off is a lowest-common-denominator abstraction — broker-specific semantics still need binder properties or direct Spring Kafka/AMQP.

**Must know:**
* Binding names `fn-in-0` / `fn-out-0`; `spring.cloud.function.definition`.
* `group` for competing, durable consumers.
* Partition key expressions for ordering.
* Retries + DLQ; `StreamBridge` (still needs outbox for transactions).
* Kafka Streams binder; test binder.

**Common follow-ups:**
* What happens without a consumer group?
* When would you use Spring Kafka directly instead?
* How do you test a stream function?

**Red flags:** assuming identical semantics across binders; `StreamBridge` in transactions as a reliable publish.
