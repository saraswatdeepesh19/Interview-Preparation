# What are WebFlux functional endpoints

---

## 🟢 Junior Level

Spring WebFlux supports two programming models for HTTP endpoints:

1. **Annotated controllers** — `@RestController`, `@GetMapping`, the same style as Spring MVC.
2. **Functional endpoints** — routes are declared as **code**: a `RouterFunction` maps requests to `HandlerFunction`s, which take a `ServerRequest` and return `Mono<ServerResponse>`.

```java
@Configuration
class OrderRoutes {
    @Bean
    RouterFunction<ServerResponse> routes(OrderHandler h) {
        return RouterFunctions.route()
                .path("/api/orders", b -> b
                        .GET("/{id}", h::get)
                        .GET("", h::list)
                        .POST("", contentType(MediaType.APPLICATION_JSON), h::create))
                .build();
    }
}

@Component
class OrderHandler {
    private final OrderService service;
    OrderHandler(OrderService service) { this.service = service; }

    Mono<ServerResponse> get(ServerRequest req) {
        return service.find(req.pathVariable("id"))
                .flatMap(o -> ServerResponse.ok().bodyValue(o))
                .switchIfEmpty(ServerResponse.notFound().build());
    }

    Mono<ServerResponse> list(ServerRequest req) {
        return ServerResponse.ok().body(service.all(), Order.class);   // streams a Flux<Order>
    }

    Mono<ServerResponse> create(ServerRequest req) {
        return req.bodyToMono(CreateOrder.class)
                .flatMap(service::create)
                .flatMap(o -> ServerResponse.created(URI.create("/api/orders/" + o.id())).bodyValue(o));
    }
}
```

Spring MVC has the same model too (`RouterFunction<ServerResponse>` from `org.springframework.web.servlet.function`), with blocking handlers.

## 🟡 Middle Level

### Why use the functional style?
* **Explicit routing** — all routes in one place, easy to see and compose; no annotation scanning or reflection at request time.
* **Lightweight and testable** — handlers are plain functions; routes can be tested with `WebTestClient.bindToRouterFunction(routes)`.
* **Composable filters** per route group:

```java
RouterFunctions.route()
    .nest(path("/admin"), b -> b.GET("/stats", stats::get))
    .filter((req, next) -> req.headers().header("X-Admin-Token").isEmpty()
            ? ServerResponse.status(HttpStatus.UNAUTHORIZED).build()
            : next.handle(req))
    .before(req -> ServerRequest.from(req).attribute("start", System.nanoTime()).build())
    .after((req, res) -> { log.info("{} {}", req.path(), res.statusCode()); return res; })
    .onError(OrderNotFound.class, (e, req) -> ServerResponse.notFound().build())
    .build();
```

### Validation is manual
Annotated controllers validate `@Valid @RequestBody` automatically. In functional endpoints, inject a `Validator` and validate yourself:

```java
Mono<ServerResponse> create(ServerRequest req) {
    return req.bodyToMono(CreateOrder.class)
            .doOnNext(this::validate)                        // throws ServerWebInputException with errors
            .flatMap(service::create)
            .flatMap(o -> ServerResponse.status(HttpStatus.CREATED).bodyValue(o));
}

private void validate(CreateOrder cmd) {
    Errors errors = new BeanPropertyBindingResult(cmd, "createOrder");
    validator.validate(cmd, errors);
    if (errors.hasErrors()) throw new ServerWebInputException(errors.getAllErrors().toString());
}
```

### Annotated vs functional

| | Annotated controllers | Functional endpoints |
| --- | --- | --- |
| Routing | Spread across classes via annotations | Centralized in code |
| Validation, binding | Automatic (`@Valid`, `@RequestParam`) | Manual |
| Familiarity | Same as MVC | New style |
| OpenAPI generation | Automatic with springdoc | Needs `@RouterOperation` annotations or builders |
| Startup/reflection | Scans annotations | Minimal reflection — friendlier to native images |

## 🔴 Senior Level

### Request handling pipeline
In WebFlux, `DispatcherHandler` consults `HandlerMapping`s in order: `RouterFunctionMapping` (functional) has a higher priority than `RequestMappingHandlerMapping` (annotated) by default, so a functional route can shadow an annotated one on the same path. Both models can coexist in one app — useful during migration, confusing if routes overlap.

### Error handling strategy
* Route-level `onError` for domain exceptions specific to a route group.
* Global: a `WebExceptionHandler` or Spring Boot's `ErrorWebExceptionHandler` (extend `AbstractErrorWebExceptionHandler`) to produce RFC 9457 `ProblemDetail` consistently for both models.
* Remember that errors are signals: an exception thrown synchronously in a handler before returning a `Mono` becomes an error signal only if it happens inside the reactive chain; prefer `Mono.error(...)` or operators like `flatMap` so error handling composes.

### Performance notes
Functional endpoints avoid per-request reflection and argument resolvers, which helps in microbenchmarks, but real latency is dominated by I/O and serialization. Choose the style for *readability and composability*, not speed. Where it does matter: GraalVM native images and very small services (startup time and memory), and large route tables composed programmatically (feature-flagged routes, multi-tenant route registration).

### Testing

```java
WebTestClient client = WebTestClient.bindToRouterFunction(new OrderRoutes().routes(handler)).build();

client.get().uri("/api/orders/42").exchange()
      .expectStatus().isOk()
      .expectBody(Order.class).value(o -> assertThat(o.id()).isEqualTo("42"));
```

No server, no Spring context — handlers are tested as functions with mocked services, plus a slice test (`@WebFluxTest` with `@Import(OrderRoutes.class)`) for security and codecs.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Functional endpoints define routes as code with `RouterFunction`s mapping to handler functions that take a `ServerRequest` and return `Mono<ServerResponse>`. They give centralized, composable routing and filters with little reflection, at the cost of manual validation and binding. They coexist with annotated controllers and exist in both WebFlux and MVC.

**Must know:**
* `RouterFunctions.route().GET(...).nest(...).filter(...).build()`.
* Handlers: `ServerRequest` → `Mono<ServerResponse>`.
* Validation is explicit; errors via `onError` or global handlers.
* Test with `WebTestClient.bindToRouterFunction`.

**Common follow-ups:**
* When would you choose functional over annotated?
* How do you document functional endpoints in OpenAPI?
* What happens if a functional route and a controller share a path?

**Red flags:** blocking calls inside handlers; mixing both styles on overlapping paths; skipping validation because it isn't automatic.
