# How does Project Reactor compare with RxJava

---

## 🟢 Junior Level

**Project Reactor** and **RxJava** are the two main reactive libraries on the JVM. Both implement the **ReactiveX** ideas (observable streams + operators) and both support the **Reactive Streams** specification, so they can interoperate.

| | Project Reactor | RxJava 3 |
| --- | --- | --- |
| Main types | `Mono<T>` (0..1), `Flux<T>` (0..N) | `Single`, `Maybe`, `Completable`, `Observable`, `Flowable` |
| Backpressure | Always (both types) | Only `Flowable`; `Observable` has none |
| Ecosystem | Spring WebFlux, Spring Data reactive, Reactor Netty, R2DBC | Android (historically), Retrofit, Room, many standalone libs |
| Java baseline | Java 8+ (Reactor 3.x), designed around Java 8 APIs | Java 8+ (RxJava 3) |
| Maintainer | VMware/Broadcom (Spring team) | ReactiveX community |

```java
// Reactor
Flux.fromIterable(ids)
    .flatMap(id -> client.fetch(id), 8)
    .filter(Order::isPaid)
    .collectList();

// RxJava
Flowable.fromIterable(ids)
    .flatMap(id -> client.fetchRx(id).toFlowable(), false, 8)
    .filter(Order::isPaid)
    .toList();
```

## 🟡 Middle Level

### Type design differences
RxJava splits cardinality into five types, which makes intent explicit (`Completable` = no value, only completion/error; `Maybe` = 0 or 1) but means more conversion calls. Reactor keeps two types: `Mono` covers `Single`/`Maybe`/`Completable` (`Mono<Void>` for completion only), and `Flux` covers the rest — always with backpressure.

### Schedulers

| Purpose | Reactor | RxJava |
| --- | --- | --- |
| CPU-bound | `Schedulers.parallel()` | `Schedulers.computation()` |
| Blocking I/O | `Schedulers.boundedElastic()` | `Schedulers.io()` (unbounded!) |
| Single thread | `Schedulers.single()` | `Schedulers.single()` |
| Custom executor | `Schedulers.fromExecutorService(...)` | `Schedulers.from(executor)` |

RxJava's `io()` scheduler grows without limit — under load, blocking calls can create thousands of threads. Reactor's `boundedElastic` caps threads (10 × cores) and queues tasks.

### Interop through Reactive Streams

```java
Flux<Order> fromRx = Flux.from(rxFlowable);                 // Flowable is a Publisher
Flowable<Order> fromReactor = Flowable.fromPublisher(flux);
Mono<Order> mono = Mono.from(rxSingle.toFlowable());
```

Spring's `ReactiveAdapterRegistry` lets WebFlux controllers return RxJava types directly (`Single<Order>`, `Flowable<Order>`), converting them automatically.

## 🔴 Senior Level

### Context and observability
* Reactor has a built-in **`Context`** tied to subscriptions, which Spring uses for security, transactions and tracing, plus Micrometer integration (`Micrometer.observation`, automatic context propagation for ThreadLocals).
* RxJava has no equivalent subscription context; propagation relies on `RxJavaPlugins` hooks (`setScheduleHandler`) to wrap tasks and copy ThreadLocals.

That's the decisive factor in Spring applications: security (`ReactiveSecurityContextHolder`), reactive transactions and tracing all assume Reactor's Context.

### Operator semantics worth knowing
* Both implement **operator fusion** (macro fusion at assembly — e.g. `just().map()` collapses — and micro fusion via queue sharing between operators) to reduce allocation and synchronization; performance is comparable in benchmarks, usually dominated by user code and I/O.
* `flatMap` concurrency defaults: Reactor 256 (`Queues.SMALL_BUFFER_SIZE`), RxJava `bufferSize()` = 128. Both deserve an explicit value for remote calls.
* Error handling: Reactor `onErrorResume`/`onErrorReturn`/`onErrorContinue` (use the last one with care — it relies on operator support and can be surprising); RxJava `onErrorResumeNext`/`onErrorReturn`. RxJava routes undeliverable errors (after dispose) to `RxJavaPlugins.onError`, which crashes Android apps by default; Reactor drops them to `Hooks.onErrorDropped` (logged).
* `null` is forbidden as a value in both (Reactive Streams rule §2.13).

### Kotlin coroutines and Mutiny
On the JVM there are more options now:
* **Kotlin coroutines + Flow** — Spring supports `suspend` controllers and `Flow` return types; bridges via `kotlinx-coroutines-reactor` (`mono { }`, `.awaitSingle()`).
* **SmallRye Mutiny** (`Uni`, `Multi`) — Quarkus' reactive API, also Reactive Streams compatible.
* **Virtual threads** reduce the need for any reactive library for request/response code.

### Choosing in practice
* Spring Boot / WebFlux service → **Reactor** (first-class integration).
* Library that must be framework-neutral → expose `org.reactivestreams.Publisher` or `java.util.concurrent.Flow.Publisher` (Java 9) in the API, implement with whichever library you like; adapters (`JdkFlowAdapter`, `FlowAdapters`) bridge the two interfaces.
* Existing RxJava codebase (Android, Retrofit) → keep RxJava; adapt at boundaries.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Reactor and RxJava both implement ReactiveX and Reactive Streams. Reactor has two types, Mono and Flux, both backpressured, a subscription Context and deep Spring integration; RxJava has five types, backpressure only on Flowable, and is common on Android. They interoperate through Publisher, but in Spring apps Reactor is the natural choice because security, transactions and tracing depend on its Context.

**Must know:**
* Mono/Flux vs Single/Maybe/Completable/Observable/Flowable.
* `boundedElastic` (capped) vs RxJava `io()` (unbounded).
* Interop: `Flux.from(publisher)`, `Flowable.fromPublisher(flux)`.
* Reactor Context is used by Spring Security/transactions/tracing.
* Both forbid `null` values; both fuse operators.

**Common follow-ups:**
* Can WebFlux controllers return RxJava types?
* Which library should a framework-neutral SDK expose?
* What happens to errors after disposal?

**Red flags:** mixing both libraries throughout one codebase; using RxJava `Observable` where backpressure is needed.
