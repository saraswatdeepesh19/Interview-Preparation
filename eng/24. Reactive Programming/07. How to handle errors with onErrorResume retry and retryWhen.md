# How to handle errors with onErrorResume retry and retryWhen

---

## 🟢 Junior Level

### 1. Plain definition

In Reactor an exception is not thrown up the call stack – it becomes an **`onError` signal** that travels *downstream* and **terminates** the stream. A `try/catch` around `subscribe()` will not catch it. You handle errors with operators placed in the pipeline.

| Operator | Meaning | Analogy |
| :--- | :--- | :--- |
| `onErrorReturn(value)` | Replace the error with a fixed value | "If the shop is closed, bring bread from the freezer" |
| `onErrorResume(fn)` | Replace the error with another publisher | "Call a different shop" |
| `onErrorMap(fn)` | Translate one exception into another | Wrap in a domain exception |
| `retry(n)` | Re-subscribe to the source up to *n* times | "Try the door again" |
| `doOnError(fn)` | Side effect (log), error still propagates | Take a note, keep going |

### 2. Minimal example

```java
import reactor.core.publisher.Mono;

public class ErrorBasics {
    static Mono<String> risky(boolean fail) {
        return fail ? Mono.error(new IllegalStateException("backend down")) : Mono.just("ok");
    }

    public static void main(String[] args) {
        risky(true)
            .onErrorReturn("default")
            .subscribe(System.out::println);                  // default

        risky(true)
            .onErrorResume(e -> Mono.just("from cache"))
            .subscribe(System.out::println);                  // from cache

        risky(true).subscribe(
            v -> System.out.println("value " + v),
            e -> System.out.println("error handler: " + e.getMessage()));   // error handler: backend down
    }
}
```

> [!IMPORTANT]
> If you call `subscribe(consumer)` without an error consumer, an error ends up in `Exceptions.errorCallbackNotImplemented` and is logged as `ErrorCallbackNotImplemented`. Always supply an error handler or handle errors upstream.

## 🟡 Middle Level

### 1. Targeted recovery

```java
Mono<User> findUser(String id) {
    return client.get().uri("/users/{id}", id).retrieve().bodyToMono(User.class)
        .onErrorResume(WebClientResponseException.NotFound.class, e -> Mono.empty())          // 404 -> empty
        .onErrorMap(WebClientResponseException.class,
                    e -> new UpstreamException("user-service " + e.getStatusCode(), e))        // translate
        .onErrorResume(java.util.concurrent.TimeoutException.class, e -> cachedUser(id));      // fallback on timeout
}
```

Overloads accept an exception type or a `Predicate<Throwable>`; order matters – the first matching handler wins and handlers below only see what the upper one produced.

### 2. Retry basics and why plain `retry` is dangerous

```java
mono.retry(3);   // immediate resubscription, no delay, retries ALL exceptions, including 400 validation errors
```

Retrying immediately against a failing backend creates a **retry storm**. Use `retryWhen` with a `Retry` spec.

### 3. `retryWhen` with backoff

```java
import reactor.util.retry.Retry;
import java.time.Duration;

Mono<Price> price = client.get().uri("/price").retrieve().bodyToMono(Price.class)
    .retryWhen(Retry.backoff(3, Duration.ofMillis(200))      // 200ms, 400ms, 800ms (+ jitter 50% by default)
        .maxBackoff(Duration.ofSeconds(2))
        .jitter(0.3)
        .filter(ex -> ex instanceof java.io.IOException
                   || (ex instanceof WebClientResponseException w && w.getStatusCode().is5xxServerError()))
        .onRetryExhaustedThrow((spec, signal) ->
                new UpstreamUnavailable("price service gave up after " + signal.totalRetries() + " retries",
                                        signal.failure())));
```

Specs: `Retry.max(n)`, `Retry.fixedDelay(n, d)`, `Retry.backoff(n, min)`, `Retry.indefinitely()`, plus `.transientErrors(true)` to reset the counter after a successful item in long-lived streams.

Without `onRetryExhaustedThrow` the final error is `Exceptions.RetryExhaustedException` with the last failure as its cause – a frequent surprise in logs and `@ExceptionHandler`s.

### 4. Retry only idempotent operations

Retrying `POST /payments` may charge twice. Retry safe methods (GET, PUT with idempotency key), or put an **Idempotency-Key** header in place first.

### 5. `doOnError`, `onErrorComplete`, `onErrorContinue`

```java
flux.doOnError(e -> log.warn("failed", e));       // observe only
flux.onErrorComplete();                           // swallow error, complete (Reactor 3.5.? / 3.4.x+)
flux.onErrorResume(e -> Flux.empty());            // equivalent for most cases
```

`onErrorContinue` makes the stream *skip the failing element and keep going*, but it is **operator-support dependent, has surprising semantics and is discouraged** (even the Reactor docs advise against it). Prefer handling errors inside `flatMap`:

```java
Flux.fromIterable(ids)
    .flatMap(id -> process(id)
            .onErrorResume(e -> { log.warn("skip {}", id, e); return Mono.empty(); }))
    .subscribe();
```

### 6. Errors in `Flux`: the stream dies

After `onError`, a `Flux` is terminated; `onErrorResume` swaps the **remainder** for a fallback, it cannot "continue the original". To keep a long-lived stream alive wrap the *inner* operation per element (above) or use `retry` on the whole source (resubscribes from the start for cold sources).

### 7. Mapping to HTTP in WebFlux

```java
@RestControllerAdvice
class Errors {
    @ExceptionHandler(OrderNotFound.class)
    ResponseEntity<ProblemDetail> notFound(OrderNotFound e) {
        return ResponseEntity.status(404).body(ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage()));
    }
}
```

`ProblemDetail` (RFC 7807) is built into Spring 6 / Boot 3; enable `spring.webflux.problemdetails.enabled=true` (Boot 3.x) for standard exceptions.

## 🔴 Senior Level

### 1. Semantics and internals

- `onErrorResume` (`FluxOnErrorResume`) cancels the upstream subscription state, then subscribes to the fallback **using the downstream's outstanding demand**; if some items were already requested/emitted, the fallback continues from the remaining demand.
- `retry`/`retryWhen` (`FluxRetryWhen`) resubscribes to the **original source**; for cold publishers this *re-executes* the work (re-issues the HTTP call), for hot publishers the new subscription just joins the live stream and has lost anything missed in between.
- Fatal errors (`OutOfMemoryError`, `StackOverflowError`, `LinkageError`, `ThreadDeath`, `VirtualMachineError`) are rethrown via `Exceptions.throwIfJvmFatal` and are **not** converted to signals.
- `Exceptions.propagate(e)` wraps checked exceptions in `ReactiveException`; unwrap with `Exceptions.unwrap(e)` in handlers.
- Errors thrown after cancellation or after terminal signal go to `Hooks.onErrorDropped` – by default logged at ERROR with "Operator called default onErrorDropped". Install a hook to count them in metrics:

```java
Hooks.onErrorDropped(e -> meterRegistry.counter("reactor.errors.dropped").increment());
Hooks.onNextDropped(v -> meterRegistry.counter("reactor.next.dropped").increment());
```

### 2. Timeouts, circuit breakers, and retry budgets

Order of operators matters:

```java
Mono<Resp> call = client.call()
    .timeout(Duration.ofSeconds(1))                                   // per attempt
    .retryWhen(Retry.backoff(2, Duration.ofMillis(100)))              // retries re-apply timeout
    .timeout(Duration.ofSeconds(3))                                   // overall deadline
    .transformDeferred(CircuitBreakerOperator.of(breaker))            // Resilience4j: stop hammering a dead dependency
    .onErrorResume(CallNotPermittedException.class, e -> fallback());
```

Pitfalls:
- Retries multiply load: 3 layers each retrying 3× = 27 calls per user request. Use a **retry budget** (e.g. cap at 10 % of traffic; Resilience4j `RateLimiter`/bulkhead or service-mesh retries instead of app-level).
- Always add **jitter** to avoid synchronized thundering herds.
- Respect `Retry-After` for 429/503 by computing the delay in a custom `Retry.from(companion -> ...)`.

### 3. Custom retry with `Retry.from`

```java
Retry retryAfterHeader = Retry.from(signals -> signals.flatMap(rs -> {
    Throwable failure = rs.failure();
    if (rs.totalRetries() >= 3 || !(failure instanceof WebClientResponseException w) || w.getStatusCode().value() != 429) {
        return Mono.<Long>error(failure);                              // stop retrying: propagate original error
    }
    long seconds = Optional.ofNullable(w.getHeaders().getFirst("Retry-After")).map(Long::parseLong).orElse(1L);
    return Mono.delay(Duration.ofSeconds(seconds));                    // emitting = retry after delay
}));
```

### 4. Testing error paths

```java
StepVerifier.withVirtualTime(() ->
        failingTwiceThenOk().retryWhen(Retry.backoff(3, Duration.ofSeconds(1)).jitter(0)))
    .expectSubscription()
    .thenAwait(Duration.ofSeconds(1))
    .thenAwait(Duration.ofSeconds(2))
    .expectNext("ok")
    .verifyComplete();
```

`jitter(0)` makes virtual-time tests deterministic.

### 5. Observability

Log the cause chain *once*, at the boundary: `doOnError` at every layer duplicates stack traces. Use `ProblemDetail` + trace id for clients, structured logs with the Reactor `Context` for correlation ([How to propagate context with Reactor Context and MDC](16.%20How%20to%20propagate%20context%20with%20Reactor%20Context%20and%20MDC.md)). Expose Micrometer `resilience4j.retry.calls` and timer metrics.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Errors in Reactor are terminal `onError` signals, handled with operators: `onErrorReturn` (static fallback), `onErrorResume` (fallback publisher), `onErrorMap` (translate), and `retry`/`retryWhen` (resubscribe, ideally with `Retry.backoff`, jitter, filter and exhaustion mapping). Retry only idempotent calls and combine with timeouts and circuit breakers.

**Must-know bullets**
- try/catch around `subscribe` does not catch pipeline errors.
- `onError` terminates the stream; `onErrorResume` replaces the remainder.
- `retry(n)` is immediate – prefer `retryWhen(Retry.backoff(...))`.
- Final failure is `RetryExhaustedException` unless mapped.
- Handle per-element errors *inside* `flatMap` to keep the stream alive.
- `onErrorContinue` is discouraged.
- `Hooks.onErrorDropped` catches late errors.

**Common follow-ups**
- Difference between `onErrorReturn` and `onErrorResume`? (Value vs publisher, lazy computation.)
- How to retry only on 5xx? (`filter` in the `Retry` spec.)
- What happens to a `Flux` after an error? (Terminated; need resubscription.)

**Red flags**
- Blind `retry()` (infinite) on a failing dependency.
- Retrying non-idempotent POSTs.
- Swallowing errors with `onErrorResume(e -> Mono.empty())` everywhere without logging.
