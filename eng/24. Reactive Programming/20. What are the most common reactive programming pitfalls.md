# What are the most common reactive programming pitfalls

---

## 🟢 Junior Level

Reactive code fails in ways imperative code doesn't. The most frequent mistakes:

1. **Nothing happens** — a `Mono`/`Flux` is created but never subscribed.
2. **Blocking inside the pipeline** — JDBC, `Thread.sleep`, `.block()` on event-loop threads.
3. **Side effects in the wrong place** — doing work in `map` that should be async (`flatMap`).
4. **Subscribing manually inside operators** — losing errors, context and backpressure.
5. **Unbounded concurrency** — `flatMap` over 10,000 items fires 256+ calls at once.

### Pitfall 1: the lazy pipeline

```java
// BUG: save() returns a Mono that nobody subscribes to — nothing is written
public Mono<Order> place(Order o) {
    repository.save(o);
    auditRepository.save(new Audit(o.id()));
    return Mono.just(o);
}

// FIX: compose and return
public Mono<Order> place(Order o) {
    return repository.save(o)
            .flatMap(saved -> auditRepository.save(new Audit(saved.id())).thenReturn(saved));
}
```

"Nothing happens until you subscribe" is the first rule of Reactor. In WebFlux, the framework subscribes to what your controller **returns** — so everything must be part of that returned chain.

## 🟡 Middle Level

### Pitfall 2: `map` vs `flatMap`

```java
// map with a Mono inside returns Mono<Mono<Customer>> — the inner Mono is never subscribed
Mono<Mono<Customer>> wrong = orderMono.map(o -> customerClient.get(o.customerId()));

// flatMap subscribes to the inner publisher and flattens
Mono<Customer> right = orderMono.flatMap(o -> customerClient.get(o.customerId()));
```

Rule: `map` for synchronous, non-blocking transformations; `flatMap` (or `concatMap`/`flatMapSequential`) when the function returns a publisher.

### Pitfall 3: subscribing inside operators

```java
// BUG: fire-and-forget subscription — errors are lost, no backpressure, no context, no cancellation
.doOnNext(order -> notificationService.send(order).subscribe())

// FIX: make it part of the chain (or explicitly decide it's fire-and-forget with error handling)
.flatMap(order -> notificationService.send(order).thenReturn(order))
```

### Pitfall 4: `Mono.just` evaluates eagerly

```java
Mono.just(expensiveLookup())              // expensiveLookup() runs NOW, at assembly, even if never subscribed
Mono.fromCallable(this::expensiveLookup)  // runs at subscription — and per subscription
Mono.defer(() -> Mono.just(expensiveLookup()))

// Classic bug: switchIfEmpty with an eager argument
repo.findById(id).switchIfEmpty(createDefault(id));                   // createDefault runs every time!
repo.findById(id).switchIfEmpty(Mono.defer(() -> createDefault(id)));  // only when empty
```

### Pitfall 5: unbounded `flatMap`

```java
Flux.fromIterable(tenThousandIds)
    .flatMap(client::fetch)        // default concurrency 256 — floods the downstream service and pool
    .flatMap(client::fetch, 16)    // explicit limit matching the downstream's capacity
```

## 🔴 Senior Level

### Pitfall 6: multiple subscriptions to cold publishers

```java
Mono<Report> report = reportService.generate(id);   // expensive, cold
return Mono.zip(report.map(Report::summary), report.map(Report::details));  // generates the report TWICE
```

Each subscriber triggers its own execution. Use `.cache()` (replay to later subscribers), `.share()` (hot multicast), or restructure (`report.map(r -> new View(r.summary(), r.details()))`). The reverse also bites: `.cache()` on a `Mono` that holds an error caches the error forever unless you use `cache(ttlForValue, ttlForError, ttlForEmpty)`.

### Pitfall 7: error handling that swallows or hides
* `onErrorResume(e -> Mono.empty())` everywhere — turns failures into silent "no data".
* `onErrorContinue` — non-standard; only supported by some operators and can leak state or behave unexpectedly with `flatMap`. Prefer per-element handling inside `flatMap`:
  ```java
  .flatMap(id -> client.fetch(id).onErrorResume(e -> { log.warn("skip {}", id, e); return Mono.empty(); }))
  ```
* Throwing checked exceptions inside lambdas by wrapping them in `RuntimeException`, then not unwrapping them in error mappers — the API returns 500 instead of the intended 4xx.

### Pitfall 8: `ThreadLocal` assumptions
MDC, security context, Hibernate sessions, `@Transactional` with JPA, and `RequestContextHolder` don't work across reactive thread hops. Use Reactor Context, reactive security, reactive transactions — and keep JPA out of reactive pipelines.

### Pitfall 9: timeouts and cancellation semantics
`timeout()` cancels upstream — but a blocking call wrapped in `fromCallable(...).subscribeOn(boundedElastic())` keeps running on its thread after cancellation (it can't be interrupted unless the code checks interrupts). Similarly, cancelling an HTTP request with WebClient closes the connection (no reuse). Design for idempotency and put timeouts on the I/O client itself, not only on the pipeline.

### Pitfall 10: debugging and metrics blind spots
No `checkpoint()`, no named sequences, no metrics on subscriptions and errors — production incidents become archaeology. Add `checkpoint` at boundaries, `ReactorDebugAgent` in production, and `.name().tag().tap(Micrometer.metrics(...))` on critical pipelines.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The classic reactive bugs are: publishers never subscribed, blocking calls on event loops, `map` where `flatMap` is needed, manual `subscribe()` inside operators, eager `Mono.just` and `switchIfEmpty` arguments, unbounded `flatMap`, repeated subscription to cold publishers, swallowed errors, and ThreadLocal assumptions. I compose everything into the returned chain, bound concurrency, use `defer`, and add checkpoints and metrics.

**Must know:**
* Nothing happens until subscribe; return the chain.
* `map` vs `flatMap`; `Mono.just` vs `fromCallable`/`defer`.
* `switchIfEmpty(Mono.defer(...))`.
* `flatMap(fn, concurrency)`.
* `.cache()`/`.share()` and their error semantics.

**Common follow-ups:**
* Why is my save not persisted?
* Why is a service called twice?
* What's wrong with `onErrorContinue`?

**Red flags:** `.subscribe()` inside `doOnNext`; `.block()` in services; catching everything with `onErrorResume(Mono.empty())`.
