# How to propagate context with Reactor Context and MDC

---

## 🟢 Junior Level

In classic Spring MVC, request-scoped data — the current user, a trace ID, a tenant, the logging **MDC** — lives in **`ThreadLocal`s**, because one thread handles the whole request.

In reactive code, one request hops between **many threads** (event loop → `boundedElastic` → another event loop), and one thread serves many requests interleaved. `ThreadLocal` values are therefore **wrong or missing**. Reactor's answer is the **`Context`**: an immutable key-value map that travels with the *subscription*, not with the thread.

```java
Mono<String> greeting = Mono.deferContextual(ctx ->
        Mono.just("Hello " + ctx.get("user")));

greeting.contextWrite(Context.of("user", "Ada"))   // written at the subscriber side
        .subscribe(System.out::println);           // Hello Ada
```

### The direction rule
Context flows **from the subscriber up to the source**. `contextWrite` affects operators *above* it in the chain, so put it at the end (the outermost point, near the subscriber), e.g. in a `WebFilter`.

## 🟡 Middle Level

### Writing context in a WebFilter

```java
@Component
class TenantFilter implements WebFilter {
    static final String TENANT = "tenant";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String tenant = Optional.ofNullable(exchange.getRequest().getHeaders().getFirst("X-Tenant"))
                                .orElse("public");
        return chain.filter(exchange).contextWrite(Context.of(TENANT, tenant));
    }
}

// Anywhere downstream in the request
Mono<List<Order>> orders() {
    return Mono.deferContextual(ctx -> repo.findByTenant(ctx.get(TenantFilter.TENANT)).collectList());
}
```

Spring Security does the same: `ReactiveSecurityContextHolder.getContext()` reads the `SecurityContext` from the Reactor Context; reactive transactions (`TransactionalOperator`) store the transaction there too.

### Why MDC logging breaks
Logback/Log4j MDC is a `ThreadLocal`. A log statement inside `map()` executes on whatever thread delivers the signal — often without your `traceId`:

```text
2026-10-16 10:00:01 [reactor-http-nio-3] traceId=       INFO  OrderService - loading order 42
```

### The modern fix: automatic context propagation
Reactor 3.5.3+ with **Micrometer Context Propagation** can restore `ThreadLocal`s from the Context on every operator:

```java
// once, at startup (Spring Boot 3.2+: spring.reactor.context-propagation=auto)
Hooks.enableAutomaticContextPropagation();
```

Micrometer Tracing registers `ThreadLocalAccessor`s for the tracing context (and therefore MDC `traceId`/`spanId`), so logs inside reactive operators get correct IDs. Your own `ThreadLocal`s can participate:

```java
ContextRegistry.getInstance().registerThreadLocalAccessor(
        "tenant",                     // key in the Reactor Context
        TenantHolder::get,            // read ThreadLocal
        TenantHolder::set,            // restore ThreadLocal
        TenantHolder::clear);         // reset after the operator
```

## 🔴 Senior Level

### How automatic propagation works and what it costs
With `enableAutomaticContextPropagation()`, Reactor decorates subscribers so that before delivering each signal (`onNext`, `onError`, `onComplete`, `request`) it sets the registered `ThreadLocal`s from the subscriber's Context and restores the previous values afterwards. Costs and caveats:
* Overhead per signal (small, but visible in very high-throughput pipelines — benchmark).
* It only restores values that are **in the Context**. Writing a `ThreadLocal` inside a `map` does not propagate anywhere; write to the Context with `contextWrite` instead.
* Non-Reactor async boundaries (a raw `CompletableFuture`, a callback API, a custom executor) need `ContextSnapshot` capture/restore manually:

```java
ContextSnapshot snapshot = ContextSnapshotFactory.builder().build().captureAll();
executor.execute(snapshot.wrap(() -> log.info("still has traceId")));
```

### Context vs ThreadLocal design rules
* Context is **immutable**; `contextWrite` returns a new view. It's per subscription — two subscribers to the same `Mono` can have different contexts.
* Keep the Context small: keys for correlation IDs, tenant, security, locale — not request payloads.
* Use typed keys (a `static final Object TENANT_KEY = new Object()` or a class) to avoid collisions between libraries.
* Prefer passing business data as **method parameters**; use Context for cross-cutting concerns only.

### Interop with blocking and virtual threads
When a reactive pipeline calls blocking code on `boundedElastic`, automatic propagation restores the `ThreadLocal`s on that worker for the duration of the operator — so a blocking library that reads MDC works. Conversely, with **virtual threads and `ScopedValue`** (preview in 21, final later), structured, immutable per-task context returns to a thread-based model; `ThreadLocal`-heavy designs remain a memory concern with millions of virtual threads.

### Debugging missing context
1. Check the order: `contextWrite` must be *downstream* (later in the code) of the operator reading it.
2. Look for `.subscribe()` calls inside operators — a nested subscription starts a new chain with an **empty** Context. Use `flatMap` instead of manual subscribes.
3. Look for `Mono.fromFuture`/callback bridges and non-Reactor executors that lose the context.
4. Log `ctx` explicitly in a `deferContextual` to verify what's present.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Reactive pipelines hop threads, so ThreadLocal-based context like MDC or security breaks. Reactor's Context is an immutable map attached to the subscription that flows from the subscriber upward; you write it with `contextWrite`, typically in a WebFilter, and read it with `deferContextual`. Micrometer Context Propagation with `Hooks.enableAutomaticContextPropagation()` restores ThreadLocals like MDC and tracing on each operator.

**Must know:**
* Context flows subscriber → source; place `contextWrite` at the end.
* `ReactiveSecurityContextHolder` and reactive transactions use the Context.
* `spring.reactor.context-propagation=auto` (Boot 3.2+).
* `ThreadLocalAccessor` registration for custom ThreadLocals.
* Nested `.subscribe()` loses context.

**Common follow-ups:**
* Why is my traceId missing in logs inside `flatMap`?
* How does Spring Security find the current user in WebFlux?
* Context vs passing parameters?

**Red flags:** setting ThreadLocals inside operators; huge objects in Context; manual `subscribe()` within pipelines.
