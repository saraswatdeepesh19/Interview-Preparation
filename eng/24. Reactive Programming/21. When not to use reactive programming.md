# When not to use reactive programming

---

## 🟢 Junior Level

Reactive programming is a tool for a specific problem: **high concurrency with mostly I/O-bound work, streaming, and backpressure**. It is the wrong default for many applications because it makes code harder to write, read, debug and test.

### Signs reactive is the wrong choice
* **Most dependencies are blocking** — JDBC/JPA, legacy SOAP clients, file-based SDKs. You'd wrap everything in `boundedElastic` and gain nothing.
* **Moderate traffic** — a few hundred requests per second fit easily into a thread-per-request model (and Java 21 virtual threads raise that ceiling enormously).
* **CPU-bound work** — reports, PDF generation, image processing, heavy computation. Non-blocking I/O doesn't help CPU work.
* **Team experience** — nobody on the team has debugged reactive code in production.
* **Simple CRUD** — the business logic is straightforward request → database → response.

### The cost in one example

```java
// Imperative: obvious control flow, try/catch, normal stack traces
Order place(PlaceOrder cmd) {
    Customer c = customers.get(cmd.customerId());
    if (!c.active()) throw new InactiveCustomerException(c.id());
    Order o = orders.save(Order.from(cmd, c));
    payments.authorize(o);
    return o;
}

// Reactive: same logic, more concepts (defer, flatMap, error signals), harder to debug
Mono<Order> place(PlaceOrder cmd) {
    return customers.get(cmd.customerId())
            .filter(Customer::active)
            .switchIfEmpty(Mono.defer(() -> Mono.error(new InactiveCustomerException(cmd.customerId()))))
            .flatMap(c -> orders.save(Order.from(cmd, c)))
            .flatMap(o -> payments.authorize(o).thenReturn(o));
}
```

## 🟡 Middle Level

### The "reactive everywhere or nowhere" problem
Reactive only pays off if the **whole request path** is non-blocking: web layer, database driver, HTTP clients, messaging, caches, logging appenders. A single blocking call on an event loop degrades the entire server. Partial adoption — WebFlux on top of JPA — is the worst of both worlds: complexity without scalability.

### Better alternatives for common goals

| Goal | Simpler option |
| --- | --- |
| Handle many concurrent blocking requests | Spring MVC + virtual threads (`spring.threads.virtual.enabled=true`) |
| Call several services in parallel | `CompletableFuture` with an executor, or virtual threads / structured concurrency |
| Async background processing | `@Async`, a message queue, or a job scheduler |
| Event processing pipelines | Kafka consumers / Kafka Streams / Spring Cloud Stream (functional, not necessarily reactive) |
| Server push to browsers | SSE with `SseEmitter` in MVC works for moderate numbers of clients |

### Hidden costs
* **Debugging**: fragmented stack traces, context loss, "nothing happens" bugs.
* **Testing**: StepVerifier, virtual time — more to learn.
* **Libraries**: fewer reactive options and less mature tooling (APM support, ORMs).
* **Hiring/onboarding**: steep learning curve; subtle bugs pass code review.

## 🔴 Senior Level

### When reactive *is* the right tool
Be specific in interviews about where it shines:
* **API gateways and proxies** — mostly waiting on network I/O, high connection counts, streaming bodies through (Spring Cloud Gateway is built on WebFlux for this reason).
* **Streaming and push** — SSE/WebSocket fan-out to tens of thousands of clients, live dashboards, chat, bridging Kafka topics to browsers with backpressure.
* **Huge numbers of mostly idle connections** — IoT, long-polling, notification services.
* **Composition-heavy orchestration** — many concurrent calls with per-call timeouts, retries, fallbacks and cancellation of losers (`firstWithValue`, `zip`, `timeout`) where operators express intent concisely.

### Quantify before choosing
Model the workload with Little's law: concurrency = throughput × latency. A service at 2,000 req/s with 50 ms latency needs ~100 concurrent requests — trivial for a thread pool. At 50,000 req/s with 500 ms upstream latency (25,000 in flight), thread-per-request with platform threads breaks; virtual threads or reactive are both candidates, and the decision then depends on streaming/backpressure needs and team skills.

Benchmark the *real* bottleneck: database connection pools, downstream rate limits and CPU often cap throughput long before thread counts do.

### Exit strategy
If a reactive service turned out to be a poor fit:
1. Keep the external API (HTTP contract) stable.
2. Rewrite internals to MVC + virtual threads endpoint by endpoint in a new service version behind the same route, or in place if the codebase is small.
3. Replace R2DBC with JDBC/JPA, WebClient with RestClient, reactive Kafka/Redis with their blocking clients.
4. Compare latency percentiles and resource usage before switching traffic fully.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I avoid reactive when dependencies are blocking, traffic is moderate, work is CPU-bound, the domain is simple CRUD, or the team lacks reactive experience — the complexity cost isn't repaid. Virtual threads now cover most high-concurrency request/response needs. Reactive is the right tool for gateways, streaming and push with backpressure, huge numbers of idle connections and complex async composition.

**Must know:**
* Reactive only helps if the whole path is non-blocking.
* WebFlux + JPA is the worst combination.
* Virtual threads as the simpler scalability option.
* Little's law to size concurrency needs.
* Concrete good fits: gateways, SSE/WebSockets, streaming.

**Common follow-ups:**
* Your team wants WebFlux "for performance" — how do you respond?
* How would you migrate away from reactive?
* What metrics would justify going reactive?

**Red flags:** choosing reactive because it's "modern"; `subscribeOn(boundedElastic())` around every repository call.
