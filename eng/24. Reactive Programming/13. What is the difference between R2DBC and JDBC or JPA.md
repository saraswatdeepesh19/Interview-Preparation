# What is the difference between R2DBC and JDBC or JPA

---

## 🟢 Junior Level

* **JDBC** — the standard *blocking* Java database API. A thread sends a query and waits for the result.
* **JPA/Hibernate** — an ORM on top of JDBC: entities, relationships, lazy loading, dirty checking. Also blocking.
* **R2DBC (Reactive Relational Database Connectivity)** — a *non-blocking* database API built on Reactive Streams. Queries return `Publisher`s (`Mono`/`Flux`), and no thread waits for the database.

```java
// Spring Data JDBC/JPA (blocking)
interface CustomerRepository extends CrudRepository<Customer, Long> {
    List<Customer> findByCity(String city);
}

// Spring Data R2DBC (reactive)
interface CustomerRepository extends ReactiveCrudRepository<Customer, Long> {
    Flux<Customer> findByCity(String city);
}
```

### Why it matters
In a WebFlux application, calling JDBC blocks an event-loop thread — and with only a few event-loop threads, a handful of slow queries can freeze the whole server. R2DBC keeps the entire request path non-blocking.

---

## 🟡 Middle Level

### What R2DBC is *not*
R2DBC is a low-level driver API (like JDBC), and **Spring Data R2DBC is not an ORM**:
* No lazy loading, no `@OneToMany` relationship mapping, no persistence context or dirty checking, no second-level cache.
* You load aggregates explicitly and write joins yourself (`DatabaseClient` or `@Query`).

```java
@Table("orders")
record OrderRow(@Id Long id, Long customerId, BigDecimal total, @Version Long version) {}

Flux<OrderWithLines> ordersWithLines(long customerId) {
    return orders.findByCustomerId(customerId)
            .flatMap(o -> lines.findByOrderId(o.id()).collectList()
                    .map(ls -> new OrderWithLines(o, ls)), 8);      // bounded concurrency: 8 queries in flight
}

// Or one query with DatabaseClient
Flux<CustomerTotal> totals = client.sql("""
        select c.id, c.name, sum(o.total) as total
        from customer c join orders o on o.customer_id = c.id
        group by c.id, c.name
        """)
    .map((row, meta) -> new CustomerTotal(row.get("id", Long.class), row.get("name", String.class),
                                          row.get("total", BigDecimal.class)))
    .all();
```

### Transactions

```java
@Transactional                                        // R2dbcTransactionManager (ReactiveTransactionManager)
public Mono<Void> transfer(long from, long to, BigDecimal amount) {
    return accounts.debit(from, amount)
            .then(accounts.credit(to, amount))
            .then();
}
```

Reactive transactions are bound to the **Reactor Context**, not a `ThreadLocal` — the work can hop threads and still belong to the same transaction. `TransactionalOperator` offers programmatic control (`.as(operator::transactional)`).

### Drivers and pooling
Drivers exist for PostgreSQL (`r2dbc-postgresql`), MySQL/MariaDB, SQL Server, Oracle, H2. Use `r2dbc-pool` (Spring Boot auto-configures it) — R2DBC connections are still physical database connections and still limited by `max_connections`.

## 🔴 Senior Level

### Throughput reality check
Non-blocking drivers do not make the **database** faster. PostgreSQL still executes one query per connection at a time; throughput is bounded by the server's CPU, I/O and locks. What R2DBC buys you:
* the **application** can handle many concurrent requests with few threads while waiting on the database,
* backpressure from result streaming (rows are requested as consumed, in principle),
* a single non-blocking stack end-to-end in WebFlux.

With **virtual threads** (Java 21), blocking JDBC + HikariCP achieves similar application-side concurrency, with the full JPA/Hibernate feature set and mature tooling. For new servlet/virtual-thread apps, JDBC/JPA is usually the pragmatic choice; R2DBC makes sense when you're already committed to WebFlux.

### Operational gotchas
* **Pool sizing** still matters — `spring.r2dbc.pool.max-size` (default 10). Unbounded `flatMap` over thousands of elements, each issuing a query, simply queues on the pool; set `concurrency` in `flatMap` to match.
* **Large results**: PostgreSQL's driver streams results using the extended protocol; set `fetchSize` (`Statement.fetchSize(n)`) to avoid buffering huge results, and remember that cancelling a `Flux` mid-stream cancels the query.
* **Blocking leaks**: libraries that call JDBC under the hood (Flyway, Liquibase, some multi-tenancy helpers) need a JDBC `DataSource` too — Spring Boot runs Flyway over JDBC even in R2DBC apps; that's fine at startup, never on request paths.
* **Tooling gaps**: fewer query builders support R2DBC (jOOQ does, via `R2DBC` connection factories), less mature tracing in some APMs, and no Hibernate-level features like `@BatchSize` or entity graphs.
* **Hibernate Reactive** is a separate project (Vert.x SQL client based) that brings an ORM to reactive stacks; it's mostly used with Quarkus, not Spring.

### Choosing

| Situation | Choice |
| --- | --- |
| Spring MVC, complex domain model | JPA/Hibernate on JDBC (+ virtual threads if needed) |
| Simple aggregates, want SQL control, blocking | Spring Data JDBC or jOOQ |
| Spring WebFlux end-to-end, streaming results | Spring Data R2DBC / `DatabaseClient`, or jOOQ with R2DBC |
| Mixed: WebFlux but heavy JPA logic | Isolate blocking calls on `Schedulers.boundedElastic()` — and question the WebFlux choice |

## 🎯 Interview Cheat Sheet

**30-second pitch:** JDBC and JPA are blocking; R2DBC is a non-blocking, Reactive Streams-based driver API returning Mono/Flux. Spring Data R2DBC is a data mapper, not an ORM — no lazy loading or relationships. It keeps WebFlux apps fully non-blocking, but it doesn't make the database faster, and with virtual threads JDBC/JPA is often the simpler choice.

**Must know:**
* R2DBC vs JDBC vs JPA responsibilities.
* No ORM features in Spring Data R2DBC.
* Reactive transactions via `R2dbcTransactionManager` and Reactor Context.
* Pool size still limits concurrency; bound `flatMap`.
* Blocking JDBC on event loops is a critical bug.

**Common follow-ups:**
* Can you use JPA with WebFlux?
* How do reactive transactions work without ThreadLocal?
* Does R2DBC improve database throughput?

**Red flags:** "R2DBC makes queries faster"; calling a JPA repository from a WebFlux handler; unbounded `flatMap` issuing queries.
