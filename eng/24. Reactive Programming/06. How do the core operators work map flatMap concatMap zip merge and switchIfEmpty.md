# How do the core operators work map flatMap concatMap zip merge and switchIfEmpty

---

## 🟢 Junior Level

### 1. Plain definition

Operators are methods on `Mono`/`Flux` that return a **new publisher** describing a transformation. They are chained into a pipeline (like the Stream API) but work asynchronously and over time.

| Operator | What it does | Analogy |
| :--- | :--- | :--- |
| `map` | Transform each item 1:1, synchronously | Stamping each parcel |
| `filter` | Keep items matching a predicate | Quality-control gate |
| `flatMap` | Turn each item into a **publisher** and merge results (async, may interleave) | Sending each parcel to a different courier at once |
| `concatMap` | Same, but one inner publisher at a time (order kept) | Couriers one after another |
| `zip` | Pair items from several sources by position | Zip fastener |
| `merge` | Interleave several sources as items arrive | Lanes joining a highway |
| `switchIfEmpty` | Use a fallback if the source was empty | Plan B |

### 2. Minimal example

```java
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;
import java.time.Duration;

public class OperatorsBasics {
    static Mono<String> lookupName(int id) {
        return Mono.just("user-" + id).delayElement(Duration.ofMillis(100 * (4 - id)));
    }

    public static void main(String[] args) throws InterruptedException {
        Flux.range(1, 3).map(i -> i * 10).subscribe(System.out::println);     // 10 20 30

        Flux.range(1, 3).flatMap(OperatorsBasics::lookupName)                  // fastest first: user-3, user-2, user-1
            .subscribe(s -> System.out.println("flatMap " + s));
        Thread.sleep(500);

        Flux.range(1, 3).concatMap(OperatorsBasics::lookupName)                // user-1, user-2, user-3
            .subscribe(s -> System.out.println("concatMap " + s));
        Thread.sleep(1000);

        Flux.zip(Flux.just("a", "b"), Flux.just(1, 2, 3), (s, n) -> s + n)      // a1 b2 (stops at shortest)
            .subscribe(System.out::println);

        Mono.<String>empty().switchIfEmpty(Mono.just("fallback")).subscribe(System.out::println);
    }
}
```

> [!IMPORTANT]
> Use `map` for a plain function `T -> R`. Use `flatMap` when your function returns a `Mono`/`Flux` (like a DB or HTTP call). Using `map` there produces `Mono<Mono<R>>`, a classic beginner bug.

## 🟡 Middle Level

### 1. `map` vs `flatMap` in typical service code

```java
Mono<OrderView> view(String orderId) {
    return orderRepo.findById(orderId)                                   // Mono<Order>
        .switchIfEmpty(Mono.error(new OrderNotFound(orderId)))
        .flatMap(order -> customerClient.get(order.customerId())          // Mono<Customer>
                .map(customer -> new OrderView(order, customer)));        // map: pure transformation
}
```

### 2. `flatMap` vs `concatMap` vs `flatMapSequential`

| Operator | Subscribes inner | Output order | Concurrency |
| :--- | :--- | :--- | :--- |
| `flatMap` | Eagerly, many at once | Interleaved as results arrive | default 256 (`Queues.SMALL_BUFFER_SIZE`), configurable `flatMap(fn, concurrency)` |
| `concatMap` | One at a time | Source order | 1 |
| `flatMapSequential` | Eagerly, many at once | Source order (buffers early results) | configurable |

```java
Flux.fromIterable(ids)
    .flatMap(id -> client.fetch(id), 8)             // at most 8 concurrent HTTP calls
    .collectList();

Flux.fromIterable(ids)
    .flatMapSequential(id -> client.fetch(id), 8)   // parallel calls, results in id order
    .collectList();
```

### 3. `zip`, `zipWith`, `combineLatest`, `merge`, `concat`

```java
// Fan-out to three services in parallel and combine
Mono<Dashboard> dashboard = Mono.zip(
        userClient.profile(id),
        orderClient.recent(id).collectList(),
        notificationClient.unread(id))
    .map(t -> new Dashboard(t.getT1(), t.getT2(), t.getT3()));
```

- `zip` emits when **all** sources have emitted an item for that position; **completes empty if one source is empty**; errors immediately if any errors (others cancelled). `Mono.zipDelayError` waits for all before propagating.
- `merge(a, b)` subscribes to both at once and interleaves; `concat(a, b)` subscribes to `b` after `a` completes.
- `combineLatest` emits whenever *any* source emits, using the latest of the others – UI-style state aggregation.
- `zipWith` is the instance version for two sources; `Mono.zip(...)` supports up to 8 typed sources and `zip(Iterable, combinator)`.

### 4. `switchIfEmpty`, `defaultIfEmpty`, `Mono.defer`

```java
Mono<User> user = cache.get(id)                     // Mono<User>, empty on miss
        .switchIfEmpty(db.findById(id)              // PITFALL: argument is built eagerly (assembly), but only SUBSCRIBED when empty
                .flatMap(u -> cache.put(id, u).thenReturn(u)));

Mono<User> expensiveFallback = cache.get(id)
        .switchIfEmpty(Mono.defer(() -> loadFromRemote(id)));  // defer when constructing the fallback has side effects
```

`defaultIfEmpty(value)` takes a plain value (eager); `switchIfEmpty` takes a publisher.

**Classic bug**: `switchIfEmpty(Mono.just(createAndSaveUser()))` – `createAndSaveUser()` runs **even when the source is non-empty**, because the argument expression is evaluated when the pipeline is assembled. Use `Mono.defer` / `fromSupplier`.

### 5. Other operators worth knowing

```java
flux.take(10).skip(2).distinct().sort();
flux.buffer(100);                        // List<T> of up to 100
flux.window(Duration.ofSeconds(1));      // Flux<Flux<T>>
flux.groupBy(Order::customerId).flatMap(g -> g.reduce(...));
flux.reduce(0, Integer::sum);            // Mono
flux.scan(0, Integer::sum);              // running totals as Flux
flux.doOnNext(x -> log.debug("{}", x));  // side effects: logging/metrics only
flux.then();                             // Mono<Void>
flux.collectList();
flux.timeout(Duration.ofSeconds(2));
flux.delayElements(Duration.ofMillis(50));
flux.limitRate(100);
flux.sample(Duration.ofSeconds(1));      // latest item each second
```

### 6. Common mistakes

- `flatMap` for ordered side effects (e.g. writing events in order) – use `concatMap`.
- Uncontrolled `flatMap` concurrency against a rate-limited API → pass a concurrency argument.
- `map` with a blocking call (`map(x -> jdbc.query(x))`) – blocks the event loop.
- Throwing checked exceptions in lambdas – wrap with `Exceptions.propagate` or use `handle`.
- Modifying shared mutable state in `doOnNext`.

## 🔴 Senior Level

### 1. How `flatMap` works internally

`FluxFlatMap` keeps:
- an array of active `FlatMapInner` subscribers (up to `maxConcurrency`),
- an MPSC queue (`prefetch` = inner buffer, default 32 `XS_BUFFER_SIZE`) per inner,
- a `drain` loop with WIP counter, emitting to the downstream respecting its demand.

Upstream demand: it requests `maxConcurrency` initially, then 1 more each time an inner completes. Hence **`flatMap` concurrency also controls how far upstream is consumed**: a `Flux.fromIterable` of 1M ids with concurrency 8 won't be materialised eagerly.

Because inners can emit on *different threads* but the drain loop serialises downstream delivery, `flatMap` is the usual place where you cross threads without writing locks.

### 2. Ordering and completion semantics

- `flatMap`: **no ordering guarantee**; completes when source and all inners complete.
- An error in any inner cancels the others and propagates (use `flatMapDelayError` to finish others first, or inner `onErrorResume` to isolate).
- `concatMap(fn, prefetch)` prefetches the *source*, not inner; `concatMapDelayError` collects errors.
- `switchMap` (cancel previous inner on new item) is the right tool for type-ahead search: `searchTerms.switchMap(this::search)`.

```java
Flux<Result> r = ids.flatMap(id -> client.call(id)
                                       .onErrorResume(e -> Mono.empty()),   // isolate failures per item
                           16);
```

### 3. Operator fusion and cost

`map`, `filter`, `take`, `Flux.range`, `fromIterable` and `publishOn` can be **fused**, sharing a queue or evaluating synchronously in `poll()`; `Flux.range(1,N).map().filter().subscribe` performs near loop speed (~100M items/s on modern HW). `flatMap` breaks fusion and costs ~100–300 ns/item overhead due to inner subscriber creation. For CPU-only pure transformations prefer `map`; reserve `flatMap` for async boundaries. For scalar inner (`Mono.just`, `Mono.fromCallable`) `flatMap` short-circuits subscription.

### 4. `handle` – map + filter + exception-friendly

```java
Flux<Integer> parsed = Flux.just("1", "x", "3")
    .<Integer>handle((s, sink) -> {
        try { sink.next(Integer.parseInt(s)); }
        catch (NumberFormatException e) { /* skip */ }       // not calling next filters the item
    });
```

### 5. Pitfall: `zip` with hot/cold and parallelism

`Mono.zip(a, b)` subscribes to `a` then `b` *sequentially on the subscribing thread*; true parallelism requires the sources to be async (HTTP) or to use `subscribeOn(Schedulers.parallel())` each:

```java
Mono<Integer> cpuA = Mono.fromCallable(() -> heavy(1)).subscribeOn(Schedulers.parallel());
Mono<Integer> cpuB = Mono.fromCallable(() -> heavy(2)).subscribeOn(Schedulers.parallel());
Mono.zip(cpuA, cpuB, Integer::sum);
```

### 6. Debugging an operator chain

Use `log()`, `checkpoint("after flatMap")`, `name("...")` + `tag(...)` with Micrometer metrics (`.metrics()`), and `Hooks.onOperatorDebug()` (see [How to debug reactive stacks with checkpoint and Hooks.onOperatorDebug](18.%20How%20to%20debug%20reactive%20stacks%20with%20checkpoint%20and%20Hooks.onOperatorDebug.md)).

## 🎯 Interview Cheat Sheet

**30-second pitch:** `map` transforms synchronously 1:1; `flatMap` maps to a publisher and merges results concurrently without order; `concatMap` does it sequentially keeping order; `flatMapSequential` runs concurrently but emits in order; `zip` pairs by position; `merge` interleaves; `switchIfEmpty` supplies a fallback publisher when the source is empty.

**Must-know bullets**
- `map` = function; `flatMap` = function returning publisher.
- `flatMap` default concurrency 256 – set a limit for rate-limited services.
- `concatMap` preserves order, concurrency 1.
- `zip` completes empty if any source is empty.
- `switchIfEmpty(Mono.just(compute()))` evaluates `compute()` eagerly – use `defer`.
- `doOnNext` is for side effects only, not for transformations.

**Common follow-ups**
- Which operator for type-ahead search? (`switchMap`.)
- How to call 3 services in parallel and combine? (`Mono.zip`.)
- How to process 10k ids with max 20 concurrent calls? (`flatMap(fn, 20)`.)
- Difference between `merge` and `concat`? (Concurrent vs sequential subscription.)

**Red flags**
- `Mono<Mono<T>>` in a signature.
- Blocking calls in `map`.
- `flatMap` on a 1M-element Flux without concurrency limit against an external API.
