# How to debug reactive stacks with checkpoint and Hooks.onOperatorDebug

---

## 🟢 Junior Level

In imperative code, a stack trace shows the chain of method calls that led to an error. In reactive code, the pipeline is **assembled** in one place and **executed** later on other threads. The stack trace shows Reactor's internal operator classes, not *your* code:

```text
java.lang.IndexOutOfBoundsException: Source emitted more than one item
    at reactor.core.publisher.MonoSingle$SingleSubscriber.onNext(MonoSingle.java:134)
    at reactor.core.publisher.FluxFlatMap$FlatMapMain.tryEmitScalar(FluxFlatMap.java:488)
    at reactor.core.publisher.FluxFlatMap$FlatMapMain.onNext(FluxFlatMap.java:421)
    ... 40 more Reactor frames, no line from your code
```

Reactor offers three tools to recover the missing information:

1. **`checkpoint("description")`** — mark a point in your pipeline; errors passing through it carry that description.
2. **`Hooks.onOperatorDebug()`** — record where *every* operator was assembled (expensive, dev only).
3. **`ReactorDebugAgent`** (`reactor-tools`) — the same information via bytecode instrumentation with low runtime cost (usable in production).

```java
return orders.findByCustomer(id)
        .checkpoint("orders.findByCustomer")
        .single()
        .checkpoint("expect single order", true);   // 'true' also captures a stack trace (more expensive)
```

## 🟡 Middle Level

### What the enhanced trace looks like
With assembly information, Reactor appends a *suppressed* exception describing the operators the error traversed:

```text
Error has been observed at the following site(s):
    *__checkpoint ⇢ orders.findByCustomer
    *__Mono.single ⇢ at com.shop.OrderService.latest(OrderService.java:57)
    |_   Mono.map ⇢ at com.shop.OrderService.latest(OrderService.java:58)
    *__checkpoint ⇢ Handler com.shop.OrderController#latest(String) [DispatcherHandler]
Original Stack Trace:
    ...
```

Now you see the exact line where `single()` was declared.

### Choosing the tool

| Tool | Cost | Where |
| --- | --- | --- |
| `checkpoint("desc")` | Tiny (no stack capture) | Production — at module boundaries |
| `checkpoint("desc", true)` | Captures one stack trace per assembly | Hot spots you're investigating |
| `Hooks.onOperatorDebug()` | Captures a stack trace for **every** operator at assembly → big CPU/allocation overhead | Local dev/tests only |
| `ReactorDebugAgent.init()` | Bytecode instrumentation at class load; ~no per-request cost | Production-safe |

```java
public static void main(String[] args) {
    ReactorDebugAgent.init();             // before Reactor classes are loaded; needs reactor-tools
    SpringApplication.run(App.class, args);
}
```

Spring Boot users can add `reactor-tools` with `spring.reactor.debug-agent.enabled=true` (default true when on the classpath).

### Logging signals
`.log("orders")` logs every Reactive Streams signal (`onSubscribe`, `request(n)`, `onNext`, `onComplete`, `cancel`) — excellent for understanding demand and cancellation, very noisy in production. Use a category and level: `.log("com.shop.orders", Level.FINE, SignalType.ON_ERROR)`.

## 🔴 Senior Level

### How assembly tracing works
* `Hooks.onOperatorDebug()` installs an `onEachOperator` hook; every operator created afterwards is wrapped with an `OnAssembly` operator holding a `Throwable` captured at assembly time. On error, the `FluxOnAssembly` adds a suppressed `OnAssemblyException` with the collected traceback. Capturing a stack trace for every `map`/`flatMap` in every request explains the large overhead.
* `ReactorDebugAgent` rewrites bytecode at class-load time: every call site that returns a `Flux`/`Mono` is wrapped with `.checkpoint("Class.method(File.java:line)")` using the *static* call-site information — no stack walking at runtime.

### Debugging non-error problems
Most hard reactive bugs aren't exceptions:
* **Nothing happens** — nobody subscribed (a `Mono` returned and dropped, `then()` missing, a `void` method calling `repo.save(x)` without subscribing). Fix: return the publisher up the chain; enable `.log()` to see whether `onSubscribe` occurs.
* **Hang** — a `Mono.never()`-like source, missing completion, or demand never requested. `log()` shows `request(n)` and whether `onComplete` arrives; add `timeout()` as a guard.
* **Duplicate execution** — the same cold `Mono` subscribed twice (e.g. once by `zip`, once by a log statement). Use `.cache()` or `.share()` deliberately.
* **Lost context / MDC** — see Context propagation; log `contextView` with `deferContextual`.

### Metrics and tags
Name sequences and record metrics with Micrometer: `.name("orders.fetch").tag("source", "db").tap(Micrometer.metrics(registry))` (reactor-core-micrometer) gives per-pipeline subscription counts, latency and error rates, and `Micrometer.observation(registry)` creates spans for tracing.

### A production playbook
1. Keep `checkpoint()` at service and adapter boundaries permanently.
2. Run with `ReactorDebugAgent` in production (low cost, line-level tracebacks).
3. Use `log()` with targeted signal types temporarily behind a feature flag or log level.
4. For hangs: thread dumps are less useful (threads aren't blocked); instead check metrics for subscriptions without completion, and add `timeout()` with descriptive errors at boundaries.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Reactive stack traces show Reactor internals because assembly and execution are separated. I add `checkpoint()` at boundaries for cheap, descriptive tracebacks, use `Hooks.onOperatorDebug()` only locally because it captures a stack trace per operator, and run `ReactorDebugAgent` in production for line-level assembly info via bytecode instrumentation. `log()` helps debug subscription, demand and cancellation problems.

**Must know:**
* Assembly time vs subscription/execution time.
* `checkpoint(desc)` vs `checkpoint(desc, true)`.
* `onOperatorDebug` is expensive; `ReactorDebugAgent` is production-safe.
* `log()` shows onSubscribe/request/onNext/cancel.
* "Nothing happens" = nobody subscribed.

**Common follow-ups:**
* Why can't you rely on regular stack traces?
* How do you debug a reactive endpoint that never responds?
* What does `reactor-tools` do?

**Red flags:** `Hooks.onOperatorDebug()` in production; sprinkling `.log()` everywhere permanently; debugging with `block()`.
