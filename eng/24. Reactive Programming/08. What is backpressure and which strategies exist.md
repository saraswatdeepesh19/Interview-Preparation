# What is backpressure and which strategies exist

---

## 🟢 Junior Level

### 1. Plain definition

**Backpressure** is the mechanism by which a **slow consumer tells a fast producer to slow down**. Without it a fast producer floods memory (unbounded queues) or crashes the consumer. In Reactive Streams the consumer controls the rate by calling `Subscription.request(n)` – "I can take *n* more items".

### 2. Analogy

A **sushi conveyor belt**: if the chef puts plates on faster than guests eat, plates pile up and fall off. Backpressure = the guests tell the chef "only 2 plates at a time". Or the chef decides what to do with surplus: stop, drop plates, or store them in a fridge.

### 3. Minimal example

```java
import reactor.core.publisher.Flux;
import reactor.core.publisher.BaseSubscriber;
import org.reactivestreams.Subscription;

public class BackpressureHello {
    public static void main(String[] args) {
        Flux.range(1, 10)
            .log()                                          // shows request(2), onNext..., request(2)
            .subscribe(new BaseSubscriber<Integer>() {
                @Override protected void hookOnSubscribe(Subscription s) { request(2); }
                @Override protected void hookOnNext(Integer v) {
                    System.out.println("processing " + v);
                    if (v % 2 == 0) request(2);
                }
            });
    }
}
```

The source never produces more items than requested, so a slow subscriber is safe.

## 🟡 Middle Level

### 1. When is it a problem?

Backpressure works automatically while the whole chain honours demand (`Flux.range`, `fromIterable`, R2DBC, `WebClient` body). It breaks down with **sources that cannot be slowed**: timers (`Flux.interval`), UI/IoT events, message brokers pushing, `Sinks`, `Flux.create` callbacks. Then you need an explicit strategy; otherwise you get `OverflowException: Could not emit tick 256 due to lack of requests`.

### 2. The strategies

| Strategy | Operator | Behaviour | Use when |
| :--- | :--- | :--- | :--- |
| **Request in bounds** | `limitRate(n)`, `BaseSubscriber`, `take(n)`, `delayElements` | Consumer pulls in batches | Source honours demand |
| **Buffer** | `onBackpressureBuffer()`, `onBackpressureBuffer(max, overflowStrategy)` | Queue surplus (unbounded by default!) | Short bursts, no loss allowed |
| **Drop** | `onBackpressureDrop(consumer)` | Discard items arriving without demand | Metrics, sensor ticks, "latest is enough" |
| **Latest** | `onBackpressureLatest()` | Keep only the newest item | Prices, positions, UI state |
| **Error** | `onBackpressureError()` | Signal `OverflowException` | Fail fast, loss unacceptable and no buffer |
| **Sample/Throttle** | `sample(Duration)`, `window`, `buffer(Duration)`, `throttleFirst` equivalent via `sampleFirst` | Reduce rate | High-frequency input |
| **Block upstream** | `Flux.create(..., OverflowStrategy.*)` | Bridge policy chosen at creation | Callback APIs |

```java
Flux<Long> ticks = Flux.interval(Duration.ofMillis(1));            // produces every ms, ignores demand

ticks.onBackpressureDrop(t -> log.debug("dropped {}", t))
     .publishOn(Schedulers.single())                               // adds an async boundary with 256 prefetch
     .subscribe(t -> slowWork(t));

ticks.onBackpressureBuffer(1_000, dropped -> log.warn("overflow {}", dropped),
                           BufferOverflowStrategy.DROP_OLDEST)     // bounded buffer
     .publishOn(Schedulers.single())
     .subscribe(t -> slowWork(t));
```

`BufferOverflowStrategy`: `ERROR`, `DROP_LATEST`, `DROP_OLDEST`.

### 3. `limitRate` and prefetch

```java
repo.findAll()                       // R2DBC may fetch aggressively
    .limitRate(100)                  // request 100, replenish at 75 (75%) -> predictable memory
    .flatMap(this::enrich, 16)
    .subscribe();
```

`publishOn(scheduler, prefetch)`, `flatMap(fn, concurrency, prefetch)`, `concatMap(fn, prefetch)` all expose prefetch knobs; defaults: 256 for `publishOn`, 32 per inner for `flatMap`.

### 4. `Flux.create` bridging a callback API

```java
Flux<Message> messages = Flux.create(sink -> {
    MessageListener l = sink::next;                      // callback pushes regardless of demand
    broker.register(l);
    sink.onDispose(() -> broker.unregister(l));          // cleanup on cancel/complete
    sink.onRequest(n -> log.debug("downstream wants {}", n));
}, FluxSink.OverflowStrategy.LATEST);                    // BUFFER (default), DROP, ERROR, IGNORE, LATEST
```

`IGNORE` is dangerous (violates spec); `BUFFER` is the default and unbounded.

### 5. Common mistakes

- Believing backpressure is automatic everywhere – it isn't for push-based sources.
- `onBackpressureBuffer()` with no bound → hidden OOM.
- Using `request(Long.MAX_VALUE)` (the default for `subscribe(Consumer)`) with a slow consumer; then only operator-level strategies help.
- Confusing backpressure with rate limiting (that is about *external* quotas – use `delayElements`, `Bucket4j`, `Resilience4j RateLimiter`).

## 🔴 Senior Level

### 1. Backpressure is *demand propagation*, not a magic buffer

Each operator translates downstream demand into upstream demand:
- `map`/`filter`: pass through (filter requests +1 for each dropped item).
- `flatMap`: requests `maxConcurrency` from upstream; downstream demand is satisfied from inner queues.
- `publishOn`: requests `prefetch` from upstream, replenishes at 75 %.
- `buffer(n)`: requests `n × demand`.
- `onBackpressureXxx`: requests **unbounded** from upstream, protects downstream by dropping/buffering – hence it *terminates* the backpressure chain at that point.

Consequently `flux.onBackpressureBuffer().publishOn(...)` effectively has unlimited memory for bursts, while `publishOn` alone has at most `prefetch` items buffered and propagates demand to the source.

### 2. End-to-end backpressure across the network

| Boundary | Backpressure mechanism |
| :--- | :--- |
| WebClient/Reactor Netty reading | Demand toggles `autoRead` on the channel → TCP window shrinks → server slows |
| WebFlux server writing | Netty channel writability (`isWritable`, high/low watermark 32/64 KB) |
| R2DBC drivers | Cursor fetch / protocol-level (Postgres `r2dbc-postgresql` uses fetch size) |
| Kafka (reactor-kafka) | `pause()/resume()` on partitions, `prefetch`; `receive(prefetch)` |
| RabbitMQ (reactor-rabbitmq) | consumer `prefetch` (QoS) |
| HTTP/1.1 SSE to browser | TCP only; slow clients cause server buffers → use `onBackpressureLatest/Drop` |
| WebSocket | Spring's `WebSocketSession.send(Publisher)` honours writability |

### 3. Detecting backpressure problems

```java
flux.name("orders.in").tag("source", "kafka").metrics()    // Micrometer: reactor.flow.duration, reactor.requested
```

Metrics to watch: queue sizes (`reactor.netty.connection.provider.pending.connections`), `reactor.onNextDropped` via `Hooks.onNextDropped`, GC and heap growth in `char[]`/`byte[]`/`DataBuffer` pools (Netty `PooledByteBufAllocator` metrics, `-Dio.netty.leakDetection.level=PARANOID` in test).

```java
Hooks.onNextDropped(v -> {
    dropped.increment();
    ReferenceCountUtil.release(v);            // if v is a Netty/DataBuffer, avoid leaks on drop
});
```

### 4. Designing a bounded pipeline: example with Kafka-like source

```java
Flux<ConsumerRecord<String, String>> source = kafkaReceiver.receive();       // honours demand through poll pausing

source.limitRate(200)                                                         // bounded memory
      .groupBy(r -> r.partition())                                            // preserve per-partition order
      .flatMap(group -> group
              .concatMap(r -> handle(r).thenReturn(r), 1)                     // sequential per partition
              .doOnNext(r -> r.receiverOffset().acknowledge()),
          /* concurrency = partitions */ 8)
      .subscribe();
```

Rules: (1) every hot or push boundary gets an explicit bounded policy, (2) every `flatMap` gets a concurrency cap, (3) every async hop picks a prefetch, (4) `collectList`/`buffer` get an upper bound, (5) you test with a slow consumer and watch heap.

### 5. Microbenchmark thinking

Prefetch trades latency vs throughput: `publishOn(scheduler, 1)` gives lowest buffering but a queue hand-off per item; the default 256 amortises it. JMH numbers typically show a 3–10× throughput difference between `prefetch=1` and `256` for cheap items.

### 6. Edge cases

- `onBackpressureBuffer(maxSize)` without an overflow strategy throws `IllegalStateException: The receiver is overrun by more signals than expected (bounded queue...)`.
- `Flux.interval` throws `OverflowException` when downstream isn't keeping up; fix with `onBackpressureDrop()` or `.onBackpressureLatest()`.
- `Sinks.many().multicast().onBackpressureBuffer()` stops accepting when full (`FAIL_OVERFLOW`); handle `EmitResult`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Backpressure lets a subscriber control demand via `request(n)` so producers never overwhelm consumers. It's automatic with demand-aware sources; for push sources use explicit strategies – buffer (bounded!), drop, latest, error, sample – or bound demand with `limitRate`/prefetch. It reaches the network through TCP flow control in Reactor Netty.

**Must-know bullets**
- `request(n)` is demand; `Long.MAX_VALUE` means unbounded.
- `onBackpressureBuffer` unbounded by default → OOM risk.
- `limitRate`, `publishOn` prefetch, `flatMap` concurrency bound memory.
- `Flux.interval` and `Sinks` don't slow down – need strategies.
- `onBackpressure*` operators request unbounded upstream.
- Not the same as rate limiting.

**Common follow-ups**
- What happens when overflow occurs with no strategy? (`OverflowException`.)
- Drop vs latest? (Drop discards new items without demand; latest keeps only the newest for the next request.)
- Does HTTP support backpressure? (Via TCP window; HTTP/2 stream flow control.)

**Red flags**
- "Reactive means no OOM, backpressure handles everything."
- Unbounded `buffer()` or `collectList()` on infinite sources.
- `Flux.create` with `IGNORE` overflow strategy.
