# Virtual threads vs reactive programming and when to choose which

---

## 🟢 Junior Level

Both solve the same problem: **serving many concurrent requests that mostly wait on I/O** without needing one expensive OS thread per request.

* **Reactive programming** (Project Reactor, WebFlux) — never wait: describe the work as a pipeline of `Mono`/`Flux` operators; a few event-loop threads handle all requests.
* **Virtual threads** (Java 21, Project Loom) — keep writing normal blocking code; each request gets a **virtual thread** that is so cheap (a few hundred bytes of stack initially, created in ~1 µs) that you can have millions. When it blocks on I/O, the JVM unmounts it from the carrier OS thread, which then runs other virtual threads.

```java
// Reactive
Mono<Dashboard> dashboard(String id) {
    return Mono.zip(profiles.get(id), orders.recent(id), loyalty.points(id))
               .map(t -> new Dashboard(t.getT1(), t.getT2(), t.getT3()));
}

// Virtual threads: plain blocking code, parallel with an executor
Dashboard dashboard(String id) throws Exception {
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
        Future<Profile> p = exec.submit(() -> profiles.get(id));
        Future<List<Order>> o = exec.submit(() -> orders.recent(id));
        Future<Integer> l = exec.submit(() -> loyalty.points(id));
        return new Dashboard(p.get(), o.get(), l.get());
    }
}
```

Spring Boot 3.2+: `spring.threads.virtual.enabled=true` runs Tomcat request handling, `@Async`, scheduling and more on virtual threads.

## 🟡 Middle Level

### Comparison

| Aspect | Reactive (WebFlux) | Virtual threads (MVC) |
| --- | --- | --- |
| Programming model | Functional pipelines, operators | Imperative, sequential |
| Debugging | Fragmented stack traces | Normal stack traces, debuggers, profilers |
| Libraries | Need non-blocking drivers (R2DBC, reactive Mongo/Redis/Kafka) | Any blocking library: JDBC, JPA, RestClient |
| ThreadLocal/MDC | Needs Context propagation | Works (but beware memory with millions of threads) |
| Backpressure | Built-in (Reactive Streams demand) | Not built-in — use semaphores, bounded queues, pools |
| Streaming (SSE, WebSockets, huge payloads) | Natural | Possible, less elegant |
| Cancellation | Automatic on unsubscribe | Interrupts / structured concurrency |
| Learning curve | Steep | Low |

### What virtual threads do **not** fix
* **Downstream capacity**: if 10,000 virtual threads each call the database, they all wait on a pool of 20 connections. Throughput is still bounded by the slowest resource. Use bulkheads/semaphores to fail fast instead of queuing forever.
* **CPU-bound work**: virtual threads don't add CPU. For computation, use a bounded platform-thread pool.
* **Pinning** (JDK 21–23): blocking inside `synchronized` or native frames pins the carrier thread; with few carriers (= cores), a few pinned threads stall everything. Prefer `ReentrantLock`; JDK 24 (JEP 491) removed pinning for `synchronized`.

## 🔴 Senior Level

### Under the hood
* A virtual thread is a `Continuation` scheduled on a `ForkJoinPool` of carrier threads (`jdk.virtualThreadScheduler.parallelism`, default = cores). When it hits a blocking operation that the JDK has made Loom-aware (socket I/O, `LockSupport.park`, `Thread.sleep`, most `java.util.concurrent`), the continuation's stack frames are copied to the heap and the carrier is freed.
* File I/O and some native calls can't unmount; the JDK compensates by temporarily adding carrier threads (`jdk.virtualThreadScheduler.maxPoolSize`).
* Stack frames live on the heap — deep stacks × many threads become GC pressure.

### Decision framework
Choose **virtual threads + Spring MVC** when:
* the service is request/response with blocking dependencies (JDBC, JPA, legacy SDKs),
* the team values debuggability and simple code,
* concurrency is moderate-to-high but downstream limits are what really cap throughput (the common case).

Choose **reactive/WebFlux** when:
* you need **streaming** with backpressure end-to-end (SSE fan-out, Kafka-to-WebSocket bridges, large file proxying),
* you compose many async sources with timeouts, retries and cancellation as first-class operators,
* the whole stack is already non-blocking (Spring Cloud Gateway is built on WebFlux for this reason),
* you need fine-grained control over event-loop behavior and memory per connection (100k+ mostly idle connections).

### Migration notes
* Moving a WebFlux service to MVC + virtual threads is often a simplification win; do it endpoint by endpoint only if both stacks don't need to coexist in one app (they can't share one server: choose `spring-boot-starter-web` *or* `-webflux`).
* With virtual threads, audit: `synchronized` around I/O (until JDK 24), libraries pooling threads internally, large `ThreadLocal` caches (e.g. per-thread `SimpleDateFormat`, Jackson `ObjectMapper` buffers), and thread pools now unnecessary (don't pool virtual threads — create one per task).
* Monitor with JFR events `jdk.VirtualThreadPinned`, `jdk.VirtualThreadSubmitFailed`, and Hikari pool metrics — the bottleneck moves to connection pools.

### Structured concurrency
`StructuredTaskScope` (preview in 21+) gives virtual threads what reactive operators give pipelines: a parent waits for children, failures cancel siblings, and thread dumps show the hierarchy (`jcmd <pid> Thread.dump_to_file -format=json`):

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {     // preview API (Java 21-24 shape)
    Subtask<Profile> p = scope.fork(() -> profiles.get(id));
    Subtask<List<Order>> o = scope.fork(() -> orders.recent(id));
    scope.joinUntil(Instant.now().plusSeconds(2));
    scope.throwIfFailed();
    return new Dashboard(p.get(), o.get());
}
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** Both target I/O-bound concurrency. Reactive uses non-blocking pipelines on a few event loops with built-in backpressure but a steep learning curve and a non-blocking-only ecosystem. Virtual threads let ordinary blocking code scale by unmounting cheap threads while they wait. For typical request/response services I'd pick MVC with virtual threads; for streaming, backpressure-heavy or gateway workloads, reactive.

**Must know:**
* Virtual threads unmount on blocking I/O; carriers = cores.
* Pinning with `synchronized` until JDK 24; prefer `ReentrantLock`.
* Neither increases database or CPU capacity — bulkheads still needed.
* Reactive advantages: backpressure, streaming, cancellation, composition.
* `spring.threads.virtual.enabled=true`.

**Common follow-ups:**
* Do virtual threads make WebFlux obsolete?
* Should you pool virtual threads?
* What happens to ThreadLocals?

**Red flags:** "virtual threads make everything faster"; pooling virtual threads; rewriting a working WebFlux service without a reason.
