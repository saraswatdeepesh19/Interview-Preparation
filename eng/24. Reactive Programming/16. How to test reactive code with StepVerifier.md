# How to test reactive code with StepVerifier

---

## 🟢 Junior Level

A `Mono` or `Flux` does nothing until someone subscribes, and its results arrive asynchronously. **`StepVerifier`** (from `reactor-test`) subscribes for you and checks the sequence of signals **step by step**: which elements arrive, in what order, and how the stream ends.

```java
@Test
void filtersEvenNumbers() {
    Flux<Integer> evens = Flux.range(1, 6).filter(i -> i % 2 == 0);

    StepVerifier.create(evens)
            .expectNext(2, 4, 6)
            .verifyComplete();          // subscribes, waits, and asserts completion
}

@Test
void propagatesErrors() {
    Mono<Order> missing = service.find("does-not-exist");

    StepVerifier.create(missing)
            .expectError(OrderNotFoundException.class)
            .verify();
}
```

### Why not just `.block()`?
`block()` hides *how* the stream behaves: you can't easily check that it emits exactly three elements, that it completes rather than hangs, or that an error happens after the second element. And blocking in tests encourages blocking in production code.

## 🟡 Middle Level

### Richer assertions

```java
StepVerifier.create(orderService.recent(customerId))
        .expectSubscription()
        .assertNext(o -> assertThat(o.status()).isEqualTo(Status.PAID))
        .expectNextMatches(o -> o.total().compareTo(BigDecimal.ZERO) > 0)
        .thenConsumeWhile(o -> o.customerId().equals(customerId))     // rest of the elements
        .expectComplete()
        .verify(Duration.ofSeconds(2));                                // fail instead of hanging forever

StepVerifier.create(service.stream())
        .expectNextCount(100)
        .thenCancel()                                                  // test cancellation behavior
        .verify();

StepVerifier.create(client.fetch())
        .expectErrorSatisfies(e -> assertThat(e)
                .isInstanceOf(WebClientResponseException.class)
                .hasMessageContaining("503"))
        .verify();
```

### Testing backpressure

```java
StepVerifier.create(Flux.range(1, 1000), 10)   // initial request of 10
        .expectNextCount(10)
        .thenRequest(5)
        .expectNextCount(5)
        .thenCancel()
        .verify();
```

This verifies the publisher respects demand (doesn't overflow a slow subscriber).

### Testing Context

```java
StepVerifier.create(service.ordersForTenant(), StepVerifierOptions.create()
                .withInitialContext(Context.of("tenant", "acme")))
        .expectNextCount(3)
        .verifyComplete();
```

## 🔴 Senior Level

### Virtual time for time-based operators
Testing `delayElements`, `interval`, `timeout` or `retryWhen(backoff)` with real time makes tests slow and flaky. **Virtual time** replaces the time source:

```java
@Test
void retriesWithBackoff() {
    AtomicInteger attempts = new AtomicInteger();

    StepVerifier.withVirtualTime(() ->                       // the publisher MUST be created inside the supplier
            Mono.defer(() -> attempts.incrementAndGet() < 3
                            ? Mono.error(new IOException("boom"))
                            : Mono.just("ok"))
                .retryWhen(Retry.backoff(5, Duration.ofSeconds(1))))
        .expectSubscription()
        .thenAwait(Duration.ofSeconds(10))                  // advances virtual clock instantly
        .expectNext("ok")
        .verifyComplete();

    assertThat(attempts).hasValue(3);
}

@Test
void timesOut() {
    StepVerifier.withVirtualTime(() -> Mono.never().timeout(Duration.ofMinutes(5)))
        .expectSubscription()
        .expectNoEvent(Duration.ofMinutes(5))               // nothing happens for 5 virtual minutes
        .expectError(TimeoutException.class)
        .verify();
}
```

Rules: create the publisher **inside** the supplier lambda (so its operators pick up the `VirtualTimeScheduler`), and remember `expectNoEvent` counts subscription as an event — call `expectSubscription()` first.

### TestPublisher: control the source

```java
TestPublisher<Price> prices = TestPublisher.create();

StepVerifier.create(pricingService.withFallback(prices.flux()))
        .then(() -> prices.next(new Price("A", 10)))
        .expectNext(new Price("A", 10))
        .then(() -> prices.error(new IOException("feed down")))
        .expectNext(Price.UNKNOWN)                          // fallback emitted
        .verifyComplete();

prices.assertWasSubscribed();
prices.assertWasCancelled();                            // operator cancelled upstream after error
```

`TestPublisher.createNoncompliant(...)` deliberately violates the Reactive Streams spec (emitting `null`, ignoring demand) to test robustness of custom operators.

### Integration level
* `WebTestClient` for WebFlux endpoints (`@WebFluxTest` or bound to router functions).
* `PublisherProbe` to assert that a fallback branch (`switchIfEmpty(probe.mono())`) was or wasn't subscribed.
* Combine with **BlockHound** in the test JVM to catch blocking calls that StepVerifier alone won't notice.

## 🎯 Interview Cheat Sheet

**30-second pitch:** StepVerifier subscribes to a Mono or Flux and asserts each signal — elements, errors, completion, cancellation, backpressure — with a timeout so tests don't hang. Virtual time makes delay, timeout and retry tests instant, and TestPublisher or PublisherProbe give full control over sources and branches. It's far more precise than `block()`.

**Must know:**
* `create(...).expectNext/assertNext/expectError/verifyComplete`.
* `verify(Duration)` to avoid hanging tests.
* `withVirtualTime(() -> ...)` + `thenAwait`/`expectNoEvent`.
* Initial request for backpressure tests; `thenRequest`, `thenCancel`.
* `TestPublisher`, `PublisherProbe`, `withInitialContext`.

**Common follow-ups:**
* Why must the publisher be created inside the virtual-time supplier?
* How do you test that a fallback was not called?
* How do you test a hot publisher?

**Red flags:** `block()` everywhere in tests; real `Thread.sleep` for delays; `verify()` without timeout on infinite fluxes.
