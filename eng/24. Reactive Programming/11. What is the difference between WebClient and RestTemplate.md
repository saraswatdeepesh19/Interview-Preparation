# What is the difference between WebClient and RestTemplate

---

## 🟢 Junior Level

Both are Spring HTTP clients:

* **`RestTemplate`** (Spring 3) — **blocking**: the calling thread waits until the response arrives. Simple, synchronous API. In maintenance mode.
* **`WebClient`** (Spring 5, WebFlux) — **non-blocking and reactive**: returns `Mono`/`Flux` immediately; the response is processed when it arrives, without holding a thread.
* **`RestClient`** (Spring 6.1) — the modern **blocking** client with a fluent API like `WebClient`. It is the recommended replacement for `RestTemplate` in Spring MVC apps.

```java
// RestTemplate (blocking)
Order order = restTemplate.getForObject("http://orders/api/orders/{id}", Order.class, id);

// RestClient (blocking, modern)
Order order = restClient.get().uri("/api/orders/{id}", id).retrieve().body(Order.class);

// WebClient (non-blocking)
Mono<Order> order = webClient.get().uri("/api/orders/{id}", id).retrieve().bodyToMono(Order.class);
```

### Which one to pick
* Spring MVC app (servlet, maybe virtual threads) → **`RestClient`**.
* Spring WebFlux app, or you need streaming/high fan-out concurrency without threads → **`WebClient`**.
* Existing code with `RestTemplate` → keep it, migrate opportunistically to `RestClient`.

## 🟡 Middle Level

### Concurrency: fan-out example

```java
// Blocking: 3 calls in sequence = sum of latencies (unless you add an executor)
Profile p = rest.get().uri("/profiles/{id}", id).retrieve().body(Profile.class);
List<Order> o = rest.get().uri("/orders?customer={id}", id).retrieve().body(new ParameterizedTypeReference<>() {});
Loyalty l = rest.get().uri("/loyalty/{id}", id).retrieve().body(Loyalty.class);

// Reactive: 3 calls in parallel = max of latencies, no extra threads
Mono<Dashboard> dashboard = Mono.zip(
        web.get().uri("/profiles/{id}", id).retrieve().bodyToMono(Profile.class),
        web.get().uri("/orders?customer={id}", id).retrieve().bodyToFlux(Order.class).collectList(),
        web.get().uri("/loyalty/{id}", id).retrieve().bodyToMono(Loyalty.class))
    .map(t -> new Dashboard(t.getT1(), t.getT2(), t.getT3()));
```

### Error handling

```java
web.get().uri("/orders/{id}", id)
   .retrieve()
   .onStatus(HttpStatusCode::is4xxClientError, r -> r.bodyToMono(ProblemDetail.class)
           .map(pd -> new OrderClientException(pd.getDetail())))
   .bodyToMono(Order.class)
   .timeout(Duration.ofSeconds(2))
   .retryWhen(Retry.backoff(2, Duration.ofMillis(200)).filter(this::isTransient));
```

`RestTemplate` throws `HttpClientErrorException`/`HttpServerErrorException` synchronously; `RestClient` uses the same `onStatus` style as `WebClient`.

### Using WebClient inside Spring MVC
You *can* call `.block()` in a servlet app, but then you get WebClient's complexity with RestTemplate's blocking. Never call `block()` inside a reactive pipeline or on a Netty event-loop thread — Reactor throws `IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2`.

## 🔴 Senior Level

### Underlying HTTP stacks and connection pools
* `RestTemplate`/`RestClient` delegate to a `ClientHttpRequestFactory`: JDK `HttpClient` (default in Boot 3.2+ when no other library is present), Apache HttpClient 5, Jetty, Reactor Netty, or `SimpleClientHttpRequestFactory` (`HttpURLConnection` — no real pooling configuration, avoid in production).
* `WebClient` uses a `ClientHttpConnector`, usually **Reactor Netty**, with a shared event-loop group (≈ number of CPU cores) and a `ConnectionProvider` pool (default max connections `2 × cores`, min 16, pending acquire queue `2 × max`).

Production configuration for WebClient:

```java
ConnectionProvider pool = ConnectionProvider.builder("orders")
        .maxConnections(200)
        .pendingAcquireMaxCount(1000)
        .pendingAcquireTimeout(Duration.ofSeconds(2))
        .maxIdleTime(Duration.ofSeconds(30))           // below the server/LB idle timeout
        .evictInBackground(Duration.ofSeconds(60))
        .build();

HttpClient http = HttpClient.create(pool)
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 1_000)
        .responseTimeout(Duration.ofSeconds(3));

WebClient web = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(http))
        .baseUrl("http://orders")
        .build();
```

`maxIdleTime` below the server's keep-alive prevents the classic `PrematureCloseException: Connection prematurely closed BEFORE response` when a load balancer silently drops idle connections.

### Memory and streaming
* `bodyToMono(String.class)` buffers the whole body; WebClient limits in-memory buffering to **256 KB** by default (`DataBufferLimitException`). Raise it with `codecs(c -> c.defaultCodecs().maxInMemorySize(...))` — or better, stream with `bodyToFlux` or `DataBuffer`s for large payloads.
* Reactor Netty uses pooled direct (off-heap) buffers; leaking them (e.g. not consuming a response body in `exchangeToMono`) shows up as `LEAK: ByteBuf.release() was not called` and growing direct memory. Always consume or release the body.

### Virtual threads change the calculus
With Java 21 and `spring.threads.virtual.enabled=true`, a blocking `RestClient` call parks a cheap virtual thread instead of a platform thread. Fan-out can be written with `StructuredTaskScope` or a virtual-thread executor and plain blocking calls. Reactive `WebClient` still wins for streaming (SSE, large downloads), backpressure-aware pipelines, and when you're already in WebFlux — but "we need WebClient for scalability" is no longer automatically true.

### Observability
Both clients are instrumented through the builders Spring Boot provides (`RestClient.Builder`, `WebClient.Builder` beans): metrics `http.client.requests` and trace propagation (`traceparent`) only work if you build clients from the injected builder, not with `RestClient.create()` or `WebClient.create()`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** RestTemplate is the old blocking client, now in maintenance mode; RestClient is its modern blocking replacement; WebClient is non-blocking and returns Mono/Flux, ideal for WebFlux, streaming and high-concurrency fan-out. With virtual threads, RestClient covers most servlet-app needs; WebClient needs careful connection-pool, timeout and buffer configuration.

**Must know:**
* Blocking vs non-blocking; `RestClient` since Spring 6.1.
* `Mono.zip` for parallel calls; never `block()` on event-loop threads.
* Reactor Netty `ConnectionProvider`: max connections, pending acquire, `maxIdleTime`.
* 256 KB default in-memory buffer limit.
* Use Boot-provided builders for metrics and tracing.

**Common follow-ups:**
* Is RestTemplate deprecated?
* What causes `PrematureCloseException`?
* WebClient in an MVC app — good idea?

**Red flags:** `WebClient.create()` per request; `.block()` inside reactive chains; no timeouts.
