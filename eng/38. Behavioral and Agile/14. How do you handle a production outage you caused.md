# How do you handle a production outage you caused

---

## 🟢 Junior Level

This question tests **ownership, honesty and calm under pressure**. Everyone who ships software eventually breaks production. Interviewers want to hear that you:
1. **Acted fast to restore service** (not to hide the mistake).
2. **Communicated openly** — told the team immediately what you changed.
3. **Learned and improved the system** so it can't easily happen again.

### What to do in the moment
* **Say it early**: "I deployed X ten minutes ago; this might be related." Speed of disclosure directly shortens the outage.
* **Mitigate first**: roll back, disable the feature flag, revert the config.
* **Follow the incident process**: let the incident commander coordinate; provide facts.
* **Don't panic or freeze**; don't try risky "fix-forward" experiments alone.

### What to do afterwards
* Write or contribute to the **blameless postmortem**: timeline, impact, causes, contributing factors.
* Propose **system-level fixes** (tests, safeguards, alerts), not just "I'll be more careful".

## 🟡 Middle Level

### STAR example

**Situation**: I added a Flyway migration that created an index on the `orders` table (about 80M rows) as part of a feature release. In staging the table was small, so it ran in seconds.

**Task**: Ship the feature without impacting checkout.

**Action / what went wrong**: The migration used `CREATE INDEX` (not `CONCURRENTLY`), which took a lock blocking writes. Ten minutes into the deploy, checkout error rates spiked. I recognized my change in the deploy log, posted in the incident channel "My migration V87 is likely holding a write lock on orders", and with the DBA we cancelled the index build (`pg_cancel_backend`), which released the lock; we rolled the application back to the previous version. Checkout recovered after 14 minutes of degraded writes.

In the postmortem I described the timeline and contributing factors: staging data was 1,000× smaller, our migration review didn't check locking behavior, and there was no `lock_timeout` on migrations.

**Result / improvements**:
* Added **Squawk** migration linting to CI (it flags non-concurrent index creation).
* Set `lock_timeout = '5s'` for the migration user so blocked DDL fails fast instead of queuing writes.
* Created a staging database refreshed weekly with production-scale anonymized data for migration rehearsal.
* Wrote a short guide on safe PostgreSQL migrations that became part of onboarding.
No migration-related incidents in the following year.

### Elements that make the answer strong
* Clear **impact** (duration, what users saw) — no minimizing.
* Your **own role** stated plainly ("my migration"), without self-flagellation.
* **Fast detection and mitigation** steps.
* **Systemic fixes** with measurable effect.

## 🔴 Senior Level

### Show that you think in systems
A senior answer explains why the failure was **possible**, not just what you did wrong:
* Missing guardrails (linting, timeouts, canaries, automated rollback).
* Gaps in environments (unrealistic staging data), observability (alert latency), or process (risky changes deployed at peak).
* How you **reduced the blast radius** for the future: progressive delivery, feature flags, safe defaults, better runbooks.

### Handling the human side
* Own it without excessive apology; focus on facts and improvement.
* Support others in similar situations — model the blameless culture you want ("thanks for flagging it so quickly").
* If you lead a team: protect the engineer who caused the incident from blame, make sure the postmortem focuses on contributing factors, and track action items.

### Questions you might get and how to answer
* *"Did you face consequences?"* — Talk about the learning culture; if there were consequences, describe them honestly and what you changed.
* *"What would you do differently?"* — Concrete technical and process changes (e.g. rehearse migrations on production-sized data; deploy risky DB changes separately from app changes, outside peak hours).
* *"How do you prevent this class of error in general?"* — Defense in depth: automated checks, staged rollouts, monitoring, quick rollback, and practiced incident response.

### What a good first message in the incident channel looks like

```text
[10:09 UTC] I deployed migration V87 (CREATE INDEX on orders) at 10:02 as part of release 2026.10.16-3.
It is very likely holding a SHARE lock that blocks inserts into orders.
Proposal: cancel the index build (pid 48213) and roll back the app to 2026.10.16-2.
I'm on the bridge; DBA please confirm before I cancel.
```

```sql
-- The guardrail added afterwards: blocked DDL fails fast instead of queuing all writes
alter role migrator set lock_timeout = '5s';
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** When I cause an outage, I disclose my change immediately, help mitigate through rollback, flags or reverts within the incident process, and communicate facts. Afterwards I write a blameless postmortem with impact, timeline and contributing factors, and drive systemic fixes — linting, timeouts, realistic staging data, canaries, alerts — so that class of failure is prevented or contained, with measurable results.

**Must know:**
* Disclose early; mitigate first; follow the incident process.
* Blameless postmortem structure.
* Systemic action items over "be careful".
* A concrete STAR story with impact and improvements.
* Leadership angle: protecting people, tracking actions.

**Common follow-ups:**
* What did you learn?
* How did you communicate with stakeholders?
* What would you change in your team's process?

**Red flags:** blaming others or tools; minimizing impact; "I've never caused an incident".
