# How do you give and receive code review feedback

---

## 🟢 Junior Level

### What the interviewer is really testing
- Are you **open to feedback** without being defensive?
- Can you give feedback that is **kind, specific and actionable**?
- Do you understand that reviews are about **code quality and shared learning**, not about people?

### Receiving feedback
1. Read all comments before replying.
2. Assume good intent.
3. Ask questions if you don't understand: "Could you show me an example of what you'd prefer?"
4. Fix, or explain your reasoning politely.
5. Say thanks, and note repeated comments to learn from them.

### Giving feedback
Use: **Observation → Impact → Suggestion**.

```text
Bad : "This is wrong."
Good: "This loop calls the repository on each iteration (observation), which will make N queries
       for N orders (impact). Could we fetch them with one findAllById call? (suggestion)"
```

### Sample junior answer (STAR)
> **S:** "My first PR in the team got 17 comments, mostly about naming and missing tests.
> **T:** I needed to respond professionally and learn quickly.
> **A:** I didn't take it personally. I made a checklist from the repeated comments, fixed everything, and asked the reviewer a clarifying question about a design comment I didn't understand. We had a 10-minute call.
> **R:** My next PR had only 3 comments, and the reviewer told me the tests were the best part. I now self-review my PR before requesting a review."

### Real-world analogy
A review is a **second pair of eyes before the plane takes off**. Pilots don't feel insulted by a checklist.

## 🟡 Middle Level

### A good review comment prefix system

| Prefix | Meaning | Blocks merge? |
|---|---|---|
| `blocker:` | Bug, security, data loss | Yes |
| `suggestion:` | Better option, but optional | No |
| `nit:` | Style, naming | No |
| `question:` | I need to understand | Depends |
| `praise:` | This is great | No |

### Example review comments on Spring code

```java
@Service
public class OrderService {

    @Transactional
    public void process(Long id) {
        Order order = orderRepository.findById(id).get();   // review target
        emailClient.send(order.getCustomerEmail());          // review target
        order.setStatus(PAID);
    }
}
```

> **blocker:** `findById(id).get()` throws `NoSuchElementException` with no useful message; please use `orElseThrow(() -> new OrderNotFoundException(id))`, so that the API returns a 404.
>
> **blocker:** The email is sent inside the transaction. If the commit fails the customer still gets an email, and if the SMTP call is slow it holds a DB connection. Could we publish an event and send it `@TransactionalEventListener(phase = AFTER_COMMIT)`?
>
> **praise:** Nice use of a dedicated exception type in the last method.

### Deeper example: receiving hard feedback
> **S:** "A reviewer rejected my caching approach, saying it would produce stale prices.
> **T:** I believed my TTL was enough, but I needed to verify rather than defend.
> **A:** I wrote a test that simulated a price change and discovered a 5-minute window in which wrong prices could be served. I thanked the reviewer, switched to event-based invalidation, and added the test.
> **R:** We avoided a pricing incident, and the reviewer started asking me to review his PRs."

### Common mistakes
- **Nitpicking** formatting that a linter (Checkstyle, Spotless) should enforce.
- Reviewing for hours: big PRs get shallow reviews. Keep PRs under ~400 lines.
- Using "you" ("you forgot...") rather than "we" or "this".
- Silent approvals ("LGTM") without actually reading.
- Arguing for the sake of being right.

## 🔴 Senior Level

### Lead-level answer
Seniors **shape the review culture**. The goal is a system where feedback is fast, safe, and focused on what matters.

> "In my team average review turnaround was two days and PRs were huge. I introduced a lightweight working agreement: PRs below 300 lines, review within 4 working hours, automated checks (Spotless, SpotBugs, ArchUnit, Sonar) for everything mechanical, and a comment-prefix convention. I also paired seniors with juniors for reviews, and asked seniors to explain *why* in comments, linking to docs. Lead time dropped from 5 days to 1.5, and in the retro juniors said reviews had become 'where I learn most'."

### A review working agreement

```markdown
## Code Review Working Agreement
1. Author self-reviews first and describes WHY in the PR description.
2. PRs under 300 changed lines; split otherwise.
3. First review response within 4 working hours.
4. Automation handles style; humans review design, correctness, tests, security.
5. Use prefixes: blocker / suggestion / nit / question / praise.
6. Disagreement not resolved in 2 rounds -> 10-minute call, then decide.
7. Approve when "good enough to ship", not when "I would write it this way".
```

### Advanced scenarios
- **Reviewing a senior's or lead's code**: ask questions, not accusations: "What happens if this call times out?"
- **Giving hard feedback to a peer repeatedly making the same mistake**: move from comments to a pairing session or a 1:1; document patterns in team guidelines.
- **Dealing with a toxic reviewer**: private feedback, then team norms; escalate if needed.
- **AI-generated code**: review for understanding; the author remains responsible.

### Red flags
- Using reviews to show superiority.
- Rubber-stamping to avoid conflict.
- A single gatekeeper for all reviews (bus factor, bottleneck).
- Reviewing only style and never the tests or design.

## 🎯 Interview Cheat Sheet

### 30-second elevator pitch
"I see code review as a collaborative learning tool. When receiving I stay curious and verify; when giving I'm specific, kind and explain why, with clear levels of severity, and I let automation deal with style."

### Must-know bullets
- Observation → impact → suggestion.
- Label comments (blocker, nit, suggestion, question, praise).
- Keep PRs small and reviews fast.
- Automate style, humans review design and risks.
- Approve working code that meets standards; don't demand your own style.

### Common follow-up questions
- "Tell me about a time you disagreed with a review comment."
- "How do you review a huge PR?"
- "What do you look for first in a review?"
- "How do you give feedback to a more senior colleague?"

### Red flags (things NOT to say)
- "I don't need reviews."
- "I just approve to be quick."
- "My reviewer was an idiot."
- "I fix everything immediately without questions."
