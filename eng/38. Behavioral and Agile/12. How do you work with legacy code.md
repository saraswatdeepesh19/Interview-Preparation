# How do you work with legacy code

---

## 🟢 Junior Level

This behavioral question checks your **attitude and method**: do you complain and want to rewrite everything, or do you understand, respect and improve the code safely while delivering?

### A good mindset
* Legacy code is code that **makes money** — it encodes years of business rules and edge cases, many undocumented.
* The people who wrote it made reasonable decisions under the constraints they had.
* Your job is to change it **safely**: understand, protect with tests, improve incrementally.

### A practical approach
1. **Read before changing**: trace the flow you need to modify (debugger, logs, call hierarchy), read git history (`git log -p`, `git blame`) for context, ask long-time team members.
2. **Add a safety net**: characterization tests that capture current behavior around the change.
3. **Make the smallest safe change**, then refactor in small steps with tests passing.
4. **Leave it better** (boy scout rule): clearer names, extracted methods, a missing test — not a rewrite.

## 🟡 Middle Level

### Techniques worth naming
* **Characterization / approval tests** to pin current behavior.
* **Seams**: parameterize constructors, extract interfaces, inject `Clock` and dependencies to make code testable (Michael Feathers, *Working Effectively with Legacy Code*).
* **Sprout method/class**: put new logic in a new, tested unit called from the old code.
* **IDE-automated refactorings** (rename, extract method, inline) which are safe even without tests.
* **Strangler fig** for replacing larger components; **branch by abstraction** for swapping implementations on trunk.
* **Feature flags** and **parallel runs** to de-risk behavioral changes.

### STAR example

**Situation**: I had to add a new discount type to a 4,000-line `PriceCalculator` class from 2014 with no tests; two earlier changes had caused production incidents.

**Task**: Add the discount within the sprint without breaking existing pricing.

**Action**:
* Captured 300 real anonymized carts from production logs and wrote approval tests recording the current prices for each.
* Used IDE refactorings to extract the discount section into a `DiscountRules` class behind an interface, keeping behavior identical (approval tests green after each step).
* Implemented the new discount as a separate, unit-tested `DiscountRule` (sprout class), behind a feature flag.
* Ran the new code in shadow mode for a week, comparing results with the old path in logs.

**Result**: Released with zero pricing incidents; the extracted `DiscountRules` made the next two discount features take days instead of weeks, and the approval-test suite became the team's safety net for further refactoring.

## 🔴 Senior Level

### What distinguishes senior answers
* **Risk-based prioritization** — improving the parts that change often or cause incidents (hotspots), leaving stable legacy alone.
* **Making the case** for investment with data: lead time in that module, incident counts, onboarding time, CVE exposure from old dependencies.
* **Incremental modernization plans** with milestones (upgrade Java/framework in place, add CI and tests, modularize, extract only where justified) instead of rewrite proposals.
* **Knowledge transfer** — documenting discovered behavior (ADRs, C4 diagrams), pairing with domain experts, spreading ownership so the system doesn't depend on one person.
* **Respectful communication** — no blaming previous developers; framing improvements as evolution.

### Things to avoid saying
* "The code was terrible, so I rewrote it." (Unless you explain risk management, scope, and results — and even then it's a red flag.)
* "I didn't touch anything I didn't understand." (Too passive — you need to learn it.)
* Refactoring and changing behavior in the same step without tests.

### Possible follow-up and answer sketch
*"What if there's no time for tests?"* — "I still add the minimal safety net for the change I'm making — a few characterization tests around the modified path — because the cost of a pricing incident is far higher. If it's truly an emergency fix, I make the smallest change possible, ship it behind a flag if I can, and add the tests immediately after, tracked as a follow-up."

### Pinning legacy behavior before changing it

```java
@ParameterizedTest
@MethodSource("recordedCarts")                       // 300 anonymized carts captured from production logs
void pricingStaysIdentical(RecordedCart cart) {
    Money actual = new PriceCalculator(fixedClock, legacyConfig).calculate(cart.input());
    assertThat(actual).isEqualTo(cart.expectedPrice());   // approval test: current behavior is the spec
}

static Stream<RecordedCart> recordedCarts() {
    return RecordedCarts.load("src/test/resources/pricing/recorded-carts.json").stream();
}
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** I treat legacy code as valuable and change it safely: understand it through reading, debugging, git history and the people who know it, pin current behavior with characterization tests, introduce seams, put new logic in tested sprout classes behind flags, refactor in small steps, and modernize incrementally — prioritizing hotspots and backing investments with data rather than proposing rewrites.

**Must know:**
* Respectful mindset; legacy code encodes business rules.
* Characterization/approval tests; seams; sprout; IDE refactorings.
* Strangler fig, branch by abstraction, parallel runs, flags.
* Hotspot-based prioritization; data-driven investment case.
* A STAR story with measurable outcomes.

**Common follow-ups:**
* When would you rewrite instead?
* How do you convince management to invest in legacy improvements?
* How do you learn an unfamiliar legacy system quickly?

**Red flags:** contempt for previous developers; big-bang rewrites; changes without any safety net.
