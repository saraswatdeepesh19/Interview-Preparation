# What are the common pitfalls when migrating to a newer Java version

---

## 🟢 Junior Level

Upgrading Java (for example 8 → 17 or 17 → 21) is usually easy for *your* code and hard for your **dependencies and build tools**. Most failures come from:

* **Removed APIs** — classes that used to ship with the JDK are gone (JAXB, `javax.annotation`, Nashorn).
* **Strong encapsulation** — libraries that used JDK internals via reflection break.
* **Old tools** — build plugins, bytecode libraries (ByteBuddy, ASM, Lombok, Mockito) that don't understand the new class file version.
* **Framework requirements** — Spring Boot 3 needs Java 17 and moves from `javax.*` to `jakarta.*`.

### A safe order of work
1. Upgrade build tools (Maven 3.9+, Gradle 8.5+ for 21) and plugins.
2. Upgrade libraries to versions that support the target JDK.
3. Compile and run tests on the new JDK *without* changing `--release`.
4. Fix warnings, then raise `--release` to the new version.
5. Roll out to production gradually and compare metrics.

```xml
<!-- Maven: compile for a specific Java API level -->
<properties>
  <maven.compiler.release>21</maven.compiler.release>
</properties>
```

`--release` (not `-source`/`-target`) also checks you don't use APIs missing in that version.

## 🟡 Middle Level

### 8 → 11: removed Java EE modules

```
java.lang.NoClassDefFoundError: javax/xml/bind/JAXBException
```

Add explicit dependencies (and on Spring Boot 3, their Jakarta versions):

```xml
<dependency>
  <groupId>jakarta.xml.bind</groupId>
  <artifactId>jakarta.xml.bind-api</artifactId>
</dependency>
<dependency>
  <groupId>org.glassfish.jaxb</groupId>
  <artifactId>jaxb-runtime</artifactId>
</dependency>
```

Also gone: `javax.annotation.PostConstruct` (use `jakarta.annotation-api`), `javax.activation`, CORBA, `javax.transaction` from the JDK.

### 11 → 17: strong encapsulation

```
java.lang.reflect.InaccessibleObjectException: Unable to make field private final ... accessible:
module java.base does not "opens java.util" to unnamed module
```

Fix by upgrading the offending library. Use `jdeps --jdk-internals target/app.jar` to find internal API usage. Temporary escape hatch: `--add-opens java.base/java.util=ALL-UNNAMED` in `JAVA_TOOL_OPTIONS` — track it as tech debt.

### Removed and changed JVM flags
The JVM refuses to start with removed options:

```
Unrecognized VM option 'UseConcMarkSweepGC'
Error: Could not create the Java Virtual Machine.
```

CMS (removed 14), `-XX:MaxPermSize` (8, ignored), `-XX:+AggressiveOpts` (removed 12), and old GC logging flags (`-XX:+PrintGCDetails` → unified logging `-Xlog:gc*:file=gc.log:time,uptime,level,tags`). Audit Dockerfiles, Helm charts and `JAVA_OPTS`.

### Behavior changes that pass tests and fail in production
* **Default charset UTF-8** (18): code using `new String(bytes)` or `FileReader` without a charset behaves differently on Windows servers.
* **TLS**: older protocols (TLS 1.0/1.1) and weak algorithms disabled by default; connections to legacy systems fail with `SSLHandshakeException`.
* **Locale data**: CLDR became the default locale provider (9) — date/number formatting (e.g. `Locale.GERMANY` month abbreviations) can change.
* **`HashMap`/`HashSet` iteration order** is unspecified — tests asserting a particular order may break between versions.

## 🔴 Senior Level

### Plan the migration as a project
* **Inventory**: `jdeps --multi-release 21 --print-module-deps --ignore-missing-deps`, list of JVM flags across environments, dependency tree (`mvn dependency:tree`), agents (APM, profilers) and their supported JDKs.
* **Multi-JDK CI**: run the test suite on both current and target JDK for weeks before switching (`toolchains` in Maven/Gradle). Use `--release` to keep producing old-version bytecode while testing on the new runtime.
* **Canary in production**: switch one deployment group, compare p50/p99 latency, GC pause histogram, RSS memory, CPU and error rates for at least one full traffic cycle.

### The Jakarta rename (Spring Boot 2 → 3)
Mechanical but wide: `javax.persistence` → `jakarta.persistence`, `javax.servlet` → `jakarta.servlet`, `javax.validation` → `jakarta.validation`. Use OpenRewrite (`org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_0`) to automate source changes. Watch for libraries that still ship `javax.*` (old Swagger, old Jersey) — they fail at run time, not compile time, when Spring scans them.

### Memory and GC differences after upgrade
* Containers: modern JDKs size the heap from the cgroup limit (default `MaxRAMPercentage=25`). If you removed a fixed `-Xmx` and kept the default, the heap may shrink dramatically. Set `-XX:MaxRAMPercentage=70..75` explicitly.
* G1 behavior evolves; re-validate any tuned flags (`-XX:G1HeapRegionSize`, `-XX:InitiatingHeapOccupancyPercent`). Often the best tuning is to delete old flags.
* Metaspace and code cache sizes can differ; native memory tracking (`-XX:NativeMemoryTracking=summary`, `jcmd <pid> VM.native_memory summary`) explains RSS changes.

### Virtual-thread specific pitfalls (21)
* **Pinning** — `synchronized` blocks or native frames around blocking I/O pin the carrier thread (fixed for `synchronized` in JDK 24). Detect with `-Djdk.tracePinnedThreads=full` (21–23) or JFR event `jdk.VirtualThreadPinned`.
* **ThreadLocal-heavy libraries** — millions of virtual threads × large ThreadLocals = memory blow-up.
* **Pool sizing assumptions** — with unlimited threads, the bottleneck moves to the JDBC pool; protect downstreams with semaphores/bulkheads.

### Agents, bytecode and the "new class file version" problem
Java 21 class files are version 65. Tools built on old ASM/ByteBuddy fail with `Unsupported class file major version 65` (Jacoco, old Mockito inline mock maker, APM agents). Upgrade them first. Since JDK 21, dynamically loading agents prints a warning (JEP 451) and will be disallowed by default in the future; load agents with `-javaagent` at startup, and for Mockito configure its agent explicitly in the test JVM arguments.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Java upgrades fail mostly because of the ecosystem: removed Java EE modules (8→11), strong encapsulation (→17), removed JVM flags, old bytecode tools and agents, and the Jakarta rename for Spring Boot 3. I upgrade tools and libraries first, run CI on both JDKs, use `--release`, and canary in production while comparing GC and latency metrics.

**Must know:**
* JAXB/`javax.annotation` removal; add explicit dependencies.
* `InaccessibleObjectException` → upgrade library; `--add-opens` only as a stopgap.
* `jdeps` to find internal API usage.
* Removed GC flags stop the JVM from starting.
* UTF-8 default (18), TLS defaults, container heap sizing.

**Common follow-ups:**
* How would you migrate 50 services from Java 11 to 21?
* What is OpenRewrite?
* What virtual-thread risks appear after moving to 21?

**Red flags:** big-bang upgrades without dual-JDK CI; sprinkling `--add-opens` without tracking; keeping years-old JVM tuning flags.
