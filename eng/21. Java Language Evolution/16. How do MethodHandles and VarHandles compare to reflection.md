# How do MethodHandles and VarHandles compare to reflection

---

## 🟢 Junior Level

* A **`MethodHandle`** (`java.lang.invoke`, Java 7) is a typed, directly executable reference to a method, constructor or field accessor. Think of it as a fast, strongly typed function pointer.
* A **`VarHandle`** (Java 9) is a typed reference to a variable — a field, array element or off-heap memory location — that supports plain, volatile, and **atomic** operations (`compareAndSet`, `getAndAdd`).

Both are alternatives to reflection's `Method.invoke` and `Field.get/set`, designed so the JIT can optimize them like normal code.

```java
MethodHandles.Lookup lookup = MethodHandles.lookup();

// Reflection
Method m = String.class.getMethod("repeat", int.class);
String r1 = (String) m.invoke("ab", 3);                       // boxes 3, Object[] varargs

// MethodHandle
MethodHandle mh = lookup.findVirtual(String.class, "repeat",
        MethodType.methodType(String.class, int.class));
String r2 = (String) mh.invokeExact("ab", 3);                 // exact types, no boxing
```

### Real-world analogy
Reflection is looking up a phone number in a directory each time and asking the operator to connect you. A method handle is a saved speed-dial button: checked once, then direct.

---

## 🟡 Middle Level

### Access checks happen once
`Method.invoke` checks access on every call (unless `setAccessible`). A `MethodHandle` is checked when the **`Lookup`** creates it: if your code could call the method directly, it can get a handle. `MethodHandles.privateLookupIn(Target.class, lookup)` gives deep access, but only when the module `opens` the package to you.

### `invokeExact` vs `invoke`
* `invokeExact` requires the call site's static types to match the handle's `MethodType` *exactly* — including the cast of the return value. A mismatch throws `WrongMethodTypeException`.
* `invoke` adapts types (boxing, widening, casting) via `asType`, at a small cost.

### Combinators

```java
MethodHandle trim = lookup.findVirtual(String.class, "trim", MethodType.methodType(String.class));
MethodHandle upper = lookup.findVirtual(String.class, "toUpperCase", MethodType.methodType(String.class));

MethodHandle normalize = MethodHandles.filterReturnValue(trim, upper);   // upper(trim(s))
String out = (String) normalize.invokeExact("  java  ");               // "JAVA"
```

`insertArguments`, `dropArguments`, `guardWithTest`, `catchException`, `foldArguments` build small programs out of handles — this is how `invokedynamic`-based features (lambdas, string concatenation, records' `toString`/`equals`/`hashCode`, pattern switch) are wired.

### VarHandle for lock-free code

```java
public final class Counter {
    private volatile long value;
    private static final VarHandle VALUE;
    static {
        try {
            VALUE = MethodHandles.lookup().findVarHandle(Counter.class, "value", long.class);
        } catch (ReflectiveOperationException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    public long increment() { return (long) VALUE.getAndAdd(this, 1L) + 1; }

    public boolean setIfIdle(long expected, long next) {
        return VALUE.compareAndSet(this, expected, next);
    }
}
```

This replaces `AtomicLongFieldUpdater` and `sun.misc.Unsafe` CAS operations, with type safety and without allocating an `AtomicLong` per object (useful when you have millions of instances).

## 🔴 Senior Level

### Why handles are fast
A `MethodHandle` stored in a `static final` field is a **constant** to the JIT. C2 (and Graal) can inline through it into the target method, then apply escape analysis, constant folding and so on — so `invokeExact` on a constant handle performs like a direct call. A handle in a non-final instance field is not constant: calls go through the handle's `LambdaForm` interpreter-like adapter, which is slower (but still usually faster than old reflection).

Rule of thumb for hot paths:
1. `static final MethodHandle` + `invokeExact` → near-direct performance.
2. Need a reusable interface instead? Spin a lambda with `LambdaMetafactory`:

```java
MethodHandle getter = lookup.findVirtual(Order.class, "total", MethodType.methodType(BigDecimal.class));
@SuppressWarnings("unchecked")
Function<Order, BigDecimal> fn = (Function<Order, BigDecimal>) LambdaMetafactory.metafactory(
        lookup, "apply",
        MethodType.methodType(Function.class),
        MethodType.methodType(Object.class, Object.class),   // erased SAM signature
        getter,
        MethodType.methodType(BigDecimal.class, Order.class)) // instantiated signature
    .getTarget().invokeExact();
```

Frameworks use this to turn discovered getters into plain functional objects once at startup.

### Memory ordering modes of VarHandle
VarHandles expose the Java Memory Model explicitly:

| Mode | Methods | Guarantee |
| --- | --- | --- |
| Plain | `get`, `set` | No ordering (like a non-volatile field) |
| Opaque | `getOpaque`, `setOpaque` | Coherence per variable, no cross-variable ordering |
| Acquire/Release | `getAcquire`, `setRelease` | One-way fences: cheaper than volatile, enough for single-producer handoffs |
| Volatile | `getVolatile`, `setVolatile`, CAS ops | Sequential consistency |

`setRelease` is the basis of lazy-set/`ordered` writes in queues (as in the JCTools/Disruptor style), saving a full `StoreLoad` fence on x86 compared with a volatile write. Use weaker modes only with a clear happens-before argument — they are expert tools.

### Off-heap and arrays
`MethodHandles.arrayElementVarHandle(int[].class)` gives atomic operations on array elements; `byteArrayViewVarHandle(long[].class, ByteOrder.LITTLE_ENDIAN)` reads multi-byte values from byte arrays efficiently (used in serializers). The Foreign Function & Memory API (final in Java 22) builds memory access to `MemorySegment`s on VarHandles too.

### Comparison summary

| | Reflection | MethodHandle | VarHandle |
| --- | --- | --- | --- |
| Typing | `Object...` at call | `MethodType`, exact or adapted | Typed access modes |
| Access check | Per call (unless accessible) | At lookup | At lookup |
| JIT inlining | Limited (better since JDK 18) | Yes when constant | Yes when constant |
| Atomic operations | No | No | Yes (CAS, getAndAdd, fences) |
| Typical users | Frameworks, tools | Language runtime, fast frameworks | Concurrency libraries |

## 🎯 Interview Cheat Sheet

**30-second pitch:** MethodHandles are typed, JIT-friendly references to methods and fields, checked once at lookup and composable; VarHandles add typed access to variables with explicit memory-ordering and atomic operations, replacing `Unsafe` and field updaters. Reflection is for discovery; handles are for fast invocation.

**Must know:**
* `Lookup` controls access; checks happen at creation.
* `invokeExact` requires exact types; `static final` handles inline.
* `LambdaMetafactory` turns handles into functional interfaces.
* VarHandle modes: plain, opaque, acquire/release, volatile; CAS and getAndAdd.
* Lambdas, string concat, records and pattern switch are wired with `invokedynamic` + method handles.

**Common follow-ups:**
* Why is `invokeExact` with a wrong cast an error?
* When would you use `setRelease` instead of a volatile write?
* How did JDK 18 change reflection performance?

**Red flags:** storing handles in non-final fields on hot paths and expecting direct-call speed; using weak memory modes without a happens-before argument.
