# What is pattern matching for switch

---

## 🟢 Junior Level

**Pattern matching for `switch`** (final in **Java 21**, JEP 441) lets a `switch` test the *type and shape* of a value, not just compare it to constants. Each `case` can declare a pattern that both checks the type and binds a variable.

### Before and after

```java
// Before: instanceof chain with casts
static String describe(Object o) {
    if (o instanceof Integer i) return "int " + i;
    else if (o instanceof String s) return "string of length " + s.length();
    else if (o == null) return "null";
    else return "something else";
}

// Java 21: type patterns in switch
static String describe(Object o) {
    return switch (o) {
        case null      -> "null";
        case Integer i -> "int " + i;
        case String s  -> "string of length " + s.length();
        default        -> "something else";
    };
}
```

### Real-world analogy
A mail sorter who looks at each item and acts by *shape*: "if it's a parcel heavier than 2 kg, send to freight; if it's a letter, send to the letter belt". The sorter both recognizes the kind of item and grabs it in one move.

## 🟡 Middle Level

### Guards with `when`

```java
sealed interface Shape permits Circle, Rect, Square {}
record Circle(double r) implements Shape {}
record Rect(double w, double h) implements Shape {}
record Square(double side) implements Shape {}

static String classify(Shape s) {
    return switch (s) {
        case Circle c when c.r() > 100      -> "large circle";
        case Circle c                       -> "circle";
        case Rect r when r.w() == r.h()     -> "square-shaped rect";
        case Rect r                         -> "rect";
        case Square sq                      -> "square";
    };   // no default: the compiler knows Shape is sealed and every subtype is covered
}
```

### Rules the compiler enforces
* **Exhaustiveness** — a pattern `switch` must cover all possible values. With a sealed hierarchy, listing every permitted subtype is enough; otherwise you need `default` or a total pattern (`case Object o`).
* **Dominance** — a more general pattern cannot precede a more specific one. `case CharSequence cs` before `case String s` is a compile error (the second can never match).
* **Null handling** — traditionally `switch` throws `NullPointerException` on `null`. A pattern switch still does, *unless* it has `case null` (you can combine: `case null, default ->`).
* **Guarded cases don't count** for exhaustiveness: `case Circle c when ...` alone does not cover `Circle`.

### Switch over enums and strings still works
Constant labels and patterns can coexist; qualified enum constants are allowed in Java 21 (`case Color.RED ->`), which helps when switching over a sealed interface implemented by several enums.

## 🔴 Senior Level

### Algebraic data types in Java
Sealed interfaces + records + pattern switch give Java *algebraic data types*. This replaces the Visitor pattern for many use cases — with the bonus that adding a new subtype breaks compilation everywhere a switch is no longer exhaustive:

```java
sealed interface Expr permits Num, Add, Mul, Neg {}
record Num(int value) implements Expr {}
record Add(Expr left, Expr right) implements Expr {}
record Mul(Expr left, Expr right) implements Expr {}
record Neg(Expr inner) implements Expr {}

static int eval(Expr e) {
    return switch (e) {
        case Num n          -> n.value();
        case Add(var l, var r) -> eval(l) + eval(r);      // record pattern (deconstruction)
        case Mul(var l, var r) -> eval(l) * eval(r);
        case Neg(Num(var v))   -> -v;                      // nested pattern
        case Neg(var inner)    -> -eval(inner);
    };
}
```

Exhaustiveness is checked at compile time **and** at run time: if a class file of a new permitted subtype appears at run time that the compiled switch didn't know (separate compilation), the switch throws `MatchException` instead of silently falling through.

### How it compiles
`javac` translates a pattern switch into an `invokedynamic` call to `java.lang.runtime.SwitchBootstraps.typeSwitch`. The bootstrap returns the index of the first matching label given the target and a restart index; guards are evaluated in the generated code, and on a failed guard the switch re-invokes `typeSwitch` starting after that label. The JDK can optimize the bootstrap's strategy without recompiling user code. Performance for a handful of cases is comparable to an `instanceof` chain; for long chains, the indy bootstrap can use class-based lookups.

### Practical guidance
* Model closed domains (payment results, commands, AST nodes, API responses) as sealed interfaces with records; avoid `default` so the compiler tells you every place to update.
* Keep business decisions in the switch *readable*: one line per case, delegate to methods for complex branches.
* Use `default` deliberately for *open* hierarchies (e.g. `Object`, external types), and log or fail loudly rather than returning a silent fallback.
* Migration path: Java 16 pattern matching for `instanceof` (JEP 394), Java 21 for `switch` and record patterns; unnamed patterns `_` are final in Java 22 (JEP 456): `case Add(Num _, var r) -> ...`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Pattern matching for switch (Java 21) lets `case` labels test a value's type and structure and bind variables, with `when` guards. Combined with sealed types and records, the compiler checks exhaustiveness, which makes it a type-safe replacement for instanceof chains and many Visitor implementations.

**Must know:**
* Type patterns, record patterns, guards (`when`), `case null`.
* Exhaustiveness for sealed hierarchies; no `default` needed.
* Dominance: specific patterns before general ones.
* `MatchException` on unexpected subtypes at run time.
* Compiled via `invokedynamic` + `SwitchBootstraps.typeSwitch`.

**Common follow-ups:**
* How is this different from Visitor?
* What happens with `null`?
* Why don't guarded cases count toward exhaustiveness?

**Red flags:** adding `default` to sealed switches "just in case" (it hides missing cases); using pattern switch on open hierarchies you don't own without handling unknowns.
