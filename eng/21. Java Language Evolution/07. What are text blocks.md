# What are text blocks

---

## 🟢 Junior Level

### What is it?

A **text block** (final in Java 15, preview in 13/14) is a multi-line string literal delimited by triple quotes `"""`. It lets you embed JSON, SQL, HTML or XML without a forest of `\n`, `+` and escaped quotes.

**Analogy:** Instead of typing a letter on a typewriter line-by-line with manual carriage returns, you paste the whole paragraph as-is.

```java
public class TextBlockIntro {
    public static void main(String[] args) {
        // Before
        String old = "{\n" +
                     "  \"name\": \"Duke\",\n" +
                     "  \"age\": 30\n" +
                     "}";

        // After
        String json = """
                {
                  "name": "Duke",
                  "age": 30
                }
                """;

        System.out.println(old.equals(json.stripTrailing())); // true
        System.out.println(json);
    }
}
```

### Basic rules

- The opening `"""` must be followed by a **line terminator** (content starts on the next line).
- Double quotes inside need no escaping (unless you want three in a row).
- The string ends with a newline if the closing `"""` is on its own line; put the closing delimiter at the end of the last content line to avoid the trailing newline.
- Result is a regular `java.lang.String` — no new type.

## 🟡 Middle Level

### 1. Indentation stripping (incidental whitespace)

The compiler removes **incidental** whitespace: it finds the minimum indentation across all non-blank lines **and the closing delimiter line**, and strips that many leading spaces. The closing delimiter position is therefore a tool for controlling indentation:

```java
String a = """
        hello
          world
        """;          // closing at col 8 -> "hello\n  world\n"

String b = """
        hello
          world
    """;              // closing at col 4 -> "    hello\n      world\n"
```

Trailing spaces on each line are removed as well. To keep significant trailing spaces use `\s` (a space escape) or `\040`.

### 2. New escape sequences

| Escape | Meaning |
| :--- | :--- |
| `\<line-terminator>` | line continuation: join with next line (no newline inserted) |
| `\s` | a single space (preserved from trimming) |
| `\"""` | three quote characters inside a block |

```java
String sql = """
        SELECT id, name, email \
        FROM users \
        WHERE active = true \
        ORDER BY name""";
// single-line SQL: "SELECT id, name, email FROM users WHERE active = true ORDER BY name"

String table = """
        | col1 |\s
        | x    |\s
        """;
```

### 3. Combining with formatting

Text blocks do not interpolate. Use `String.formatted` (Java 15) or `String.format`:

```java
String name = "Ann";
int total = 3;
String body = """
        Dear %s,
        you have %d new messages.
        """.formatted(name, total);
```

Java 21 has **String Templates** as a *preview* (JEP 430; they were later withdrawn/redesigned in Java 23), so do not depend on them in production.

### 4. Related String methods (Java 11–15)

```java
"  hi ".strip();           // "hi"   (Unicode aware; trim() is not)
"".isBlank();              // true
"a\nb\n".lines().count();  // 2
"ab".repeat(3);            // "ababab"
text.stripIndent();        // apply the same indentation algorithm at runtime
text.translateEscapes();   // process \n, \t escapes at runtime
```

### 5. Practical use cases

```java
// JPA / JDBC native SQL
@Query(nativeQuery = true, value = """
        SELECT o.id, c.name
        FROM orders o
        JOIN customers c ON c.id = o.customer_id
        WHERE o.status = :status
        """)
List<Object[]> findByStatus(@Param("status") String status);

// Tests: inline JSON expected payloads
String expected = """
        {"id":1,"name":"Ann"}
        """;
```

Annotations accept text blocks as long as the result is a compile-time constant, which is why they work in `@Query` and `@Sql` in Spring.

### 6. Common mistakes

- Putting content on the same line as the opening `"""` → compile error.
- Mixed tabs and spaces: the algorithm counts each whitespace char as one, so mixing leads to uneven stripping. Use one style (IDE normalisation).
- Forgetting the trailing newline when comparing with expected strings.
- Relying on line endings: normalised to `\n` regardless of the source file's OS line endings — usually desirable.
- Embedding user input into SQL text blocks → still SQL injection; use parameters.

## 🔴 Senior Level

### 1. Compile-time processing

Text blocks are processed in three steps by the compiler:
1. Line terminators are normalised to `\n`.
2. Incidental whitespace is stripped (same algorithm as `String.stripIndent`).
3. Escape sequences are interpreted (**after** stripping, which is why `\s` and `\n` don't affect indentation computation).

The result is a regular constant in the class file's constant pool, interned like any literal, and usable in `switch` case labels and annotation values. There is **zero runtime overhead** vs concatenated literals. Note that constant concatenation (`"a" + "b"`) was already folded by `javac`, so performance never differed; only readability did.

```java
static final String QUERY = """
        select 1""";
switch (input) {
    case QUERY -> System.out.println("matched");   // text block constant is a valid case label
    default -> {}
}
```

### 2. Pitfalls with indentation algorithm in tooling

- Auto-formatters (IDE reformat, Spotless/google-java-format) may re-indent the block's *source* lines; the result is stable as long as the closing delimiter moves with the content. Verify with a unit test if the exact string matters (checksum, signature, golden files).
- Windows `\r\n` vs Linux `\n` sources compile to the same string — good for reproducible builds.
- Non-trivial: the **last line** with only whitespace before `"""` counts for indentation; a line with only whitespace elsewhere does not.

### 3. Security and correctness

- Never build SQL/HTML/shell via `.formatted()` with untrusted data. Use `PreparedStatement`, templating engines with auto-escaping, or `ProcessBuilder` argument lists.
- Embedding secrets (private keys, tokens) as text blocks in source code is the same hazard as before — use a secret manager.
- For JSON generation, prefer Jackson/records; use text blocks for fixtures only.

### 4. Testing pattern with text blocks

```java
@Test
void rendersReport() {
    String expected = """
            ID  NAME
            1   Ann
            2   Bob
            """;
    assertEquals(expected, renderer.render(List.of(new Row(1, "Ann"), new Row(2, "Bob"))));
}
```

Pair with `stripIndent()` when loading text from resource files to apply the same normalisation.

### 5. Diagnostics

- Inspect constant pool: `javap -v Class | grep -A3 "String"`.
- Static-analysis: Error Prone `StringConcatToTextBlock`, IntelliJ "Convert concatenation to text block" quick fix.
- Observability: text-block SQL gets logged with newlines; configure log patterns (e.g. P6Spy, Hibernate `format_sql`) so multi-line statements don't break line-based log shipping, or squash with `.lines().map(String::strip).collect(Collectors.joining(" "))`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Text blocks (`"""`, final in Java 15) are multi-line string literals with automatic removal of incidental indentation, no need to escape quotes, `\` for line continuation and `\s` for a preserved space. They produce plain `String` constants at compile time — no runtime cost.

**Must-know:**
- Opening delimiter followed by newline.
- Closing delimiter position controls indentation and trailing newline.
- `\<newline>` and `\s` escapes.
- `formatted()`, `stripIndent()`, `translateEscapes()`.
- Still a `String`; no interpolation (string templates were only preview).

**Common follow-ups:**
- How is indentation determined?
- How to avoid the trailing newline?
- Are text blocks safe for SQL? (Only with bound parameters.)
- Difference between `strip()` and `trim()`?

**🚩 Red flags:**
- Concatenating user input into text-block SQL.
- Mixed tabs/spaces in block bodies.
