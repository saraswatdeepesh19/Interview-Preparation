# What are record patterns

---

## 🟢 Junior Level

A **record pattern** (final in **Java 21**, JEP 440) checks that a value is a given record type **and pulls out its components** into variables in one step — this is called *deconstruction*.

```java
record Point(int x, int y) {}

Object o = new Point(3, 4);

// Before: type pattern, then call accessors
if (o instanceof Point p) {
    System.out.println(p.x() + p.y());
}

// Record pattern: match and deconstruct at once
if (o instanceof Point(int x, int y)) {
    System.out.println(x + y);
}
```

### Real-world analogy
Opening a parcel and immediately laying out its contents on the table, instead of first saying "this is a parcel" and then asking it "what's your first item? what's your second item?".

## 🟡 Middle Level

### Nesting and `var`

```java
record Customer(String name, Address address) {}
record Address(String city, String country) {}
record Order(Customer customer, BigDecimal total) {}

static String region(Object o) {
    return switch (o) {
        case Order(Customer(var name, Address(var city, var country)), var total)
                when country.equals("DE") && total.compareTo(new BigDecimal("1000")) > 0
                -> "large German order from " + city;
        case Order(Customer(_, Address(_, var country)), _) -> "order from " + country;   // Java 22+: unnamed patterns
        default -> "unknown";
    };
}
```

* Components can use explicit types, `var`, or nested patterns.
* Constants are **not** patterns: you cannot write `Address(var city, "DE")`. Test values in a `when` guard instead.
* `_` (unnamed pattern, Java 22, JEP 456) ignores a component you don't need. On Java 21, use `var ignored`.

### Generic records and inference

```java
record Pair<A, B>(A first, B second) {}

static String show(Pair<String, Integer> p) {
    if (p instanceof Pair(var s, var n)) {    // type arguments inferred: String, Integer
        return s.repeat(n);
    }
    return "";
}
```

### How it calls accessors
Deconstruction invokes the record's **accessor methods**, not the fields. If you override an accessor (e.g. to return a defensive copy), the pattern uses your override. Accessors run in declaration order of the pattern; they should be side-effect free.

## 🔴 Senior Level

### Data-oriented programming
Record patterns complete the trio *records + sealed interfaces + pattern matching*. The style is called **data-oriented programming**: model data as immutable, transparent carriers; model alternatives as sealed sums; put behavior in exhaustive switches over the data.

```java
sealed interface PaymentResult permits Approved, Declined, ThreeDsRequired {}
record Approved(String authCode, Instant at) implements PaymentResult {}
record Declined(String reason, boolean retryable) implements PaymentResult {}
record ThreeDsRequired(URI challengeUrl) implements PaymentResult {}

ResponseEntity<?> toHttp(PaymentResult r) {
    return switch (r) {
        case Approved(var code, var at)                       -> ResponseEntity.ok(Map.of("authCode", code));
        case Declined(var reason, var retryable) when retryable -> ResponseEntity.status(503).body(reason);
        case Declined(var reason, var retryable)              -> ResponseEntity.unprocessableEntity().body(reason);
        case ThreeDsRequired(var url)                         -> ResponseEntity.status(303).location(url).build();
    };
}
```

The unguarded `Declined(...)` case is required: guarded cases never count toward exhaustiveness.

### Exhaustiveness with nested patterns
The compiler reasons about nested sealed components: `case Wrapper(A a)` + `case Wrapper(B b)` is exhaustive if `sealed interface X permits A, B` and `record Wrapper(X x)`. Guards break this reasoning, so the switch then needs an unguarded fallback.

### Null semantics
A nested record pattern does **not** match `null` components: `case Order(Customer(var n, var a), var t)` fails to match an `Order` whose `customer` is `null`; a `var`/type pattern on a component *does* match `null`. If no case matches and there is no `default`, the switch throws `MatchException` (for sealed/exhaustive switches) — design records to reject nulls in their compact constructor:

```java
record Customer(String name, Address address) {
    Customer {
        Objects.requireNonNull(name);
        Objects.requireNonNull(address);
    }
}
```

### Where it helps in backends
* Mapping domain results to HTTP responses or Kafka messages (as above).
* Interpreting commands/events in event-sourced aggregates (`apply` methods).
* Parsing/validating JSON trees after Jackson converts them into sealed record hierarchies (`@JsonTypeInfo` + `@JsonSubTypes`).
* Replacing nested `if (x != null && x.getA() != null && x.getA().getB() ...)` navigation with a single pattern.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Record patterns (Java 21) match a record type and deconstruct its components in one step, and they nest. With sealed interfaces and pattern switch, they enable data-oriented programming with compile-time exhaustiveness checks.

**Must know:**
* Syntax `case Point(var x, var y)`; nesting allowed; `_` for unused (Java 22).
* Deconstruction calls accessors.
* Nested record patterns don't match `null` components.
* Guards don't contribute to exhaustiveness.

**Common follow-ups:**
* Can you deconstruct regular classes? (Not yet — only records.)
* How does generic type inference work in record patterns?
* What is data-oriented programming?

**Red flags:** expecting deconstruction to bypass accessor logic; using record patterns on mutable data with side-effecting accessors.
