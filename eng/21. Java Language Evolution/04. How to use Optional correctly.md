# How to use Optional correctly

---

## 🟢 Junior Level

### What is it?

`Optional<T>` (Java 8) is a container that either holds one non-null value or is empty. It makes the statement "this method might not return a result" part of the method signature, instead of hiding it behind `null` and a surprise `NullPointerException`.

**Analogy:** A gift box that may be empty. Instead of handing you "nothing" (null) and letting you reach for something that is not there, the giver hands you a labelled box — you must open it deliberately.

```java
import java.util.*;

public class OptionalIntro {
    static Optional<String> findNickname(String user) {
        Map<String, String> db = Map.of("alice", "Ally");
        return Optional.ofNullable(db.get(user));
    }

    public static void main(String[] args) {
        // create
        Optional<String> some = Optional.of("hi");          // NPE if argument is null
        Optional<String> maybe = Optional.ofNullable(null); // empty when null
        Optional<String> none = Optional.empty();

        // consume
        String nick = findNickname("bob").orElse("anonymous");
        System.out.println(nick); // anonymous

        findNickname("alice").ifPresent(n -> System.out.println("Nick: " + n));
    }
}
```

### Core API

| Method | Purpose |
| :--- | :--- |
| `of`, `ofNullable`, `empty` | creation |
| `isPresent()` / `isEmpty()` (11) | check |
| `ifPresent(Consumer)` | act if value exists |
| `orElse`, `orElseGet`, `orElseThrow` | unwrap with fallback |
| `map`, `flatMap`, `filter` | transform |
| `or(Supplier)` (9), `ifPresentOrElse` (9), `stream()` (9) | additions in Java 9 |

## 🟡 Middle Level

### 1. Chain, do not unwrap

Bad: `if (o.isPresent()) { return o.get().foo(); }` — that is just a null-check with extra steps. Good:

```java
record Address(String city) {}
record User(Optional<Address> address) {}   // see anti-patterns below: shown only for illustration

String city = findUser(id)                           // Optional<User>
        .flatMap(User::address)                      // Optional<Address>
        .map(Address::city)
        .filter(c -> !c.isBlank())
        .orElse("Unknown");
```

`map` wraps the result (and turns a `null` result into empty); `flatMap` is used when the function itself returns an `Optional`.

### 2. `orElse` vs `orElseGet`

`orElse(expr)` evaluates `expr` **always**; `orElseGet(supplier)` only when empty.

```java
User u = repo.findById(id).orElse(createDefaultUser());        // createDefaultUser() runs EVERY time (maybe a DB write!)
User v = repo.findById(id).orElseGet(() -> createDefaultUser()); // only if absent
User w = repo.findById(id).orElseThrow(() -> new NotFoundException(id)); // fail-fast
```

Java 10 added a no-arg `orElseThrow()` (throws `NoSuchElementException`) — prefer it over `get()`; static analysers flag bare `get()` as it hides the same risk.

### 3. Where Optional belongs — and where not

Brian Goetz's guideline: Optional is designed for **return types** where "no result" is a valid outcome.

| Use | Verdict |
| :--- | :--- |
| Method return type | ✅ Intended use |
| Method parameter | ❌ Forces callers to wrap; use overloads or `@Nullable` |
| Entity/DTO field | ❌ Not `Serializable`; poor JPA/Jackson support |
| Collection element / Map value | ❌ Use absence from the collection |
| Returning `Optional<List<T>>` | ❌ Return an empty list |
| `Optional.get()` without a check | ❌ Same bug as `null` |

### 4. Spring and persistence

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);   // Spring Data supports Optional returns
}

@GetMapping("/users/{id}")
public ResponseEntity<UserDto> get(@PathVariable Long id) {
    return repo.findById(id)
               .map(UserDto::from)
               .map(ResponseEntity::ok)
               .orElseGet(() -> ResponseEntity.notFound().build());
}
```

### 5. Java 9+ helpers

```java
// or(): lazily fall back to another Optional (cache -> db)
Optional<User> user = cache.get(id).or(() -> db.find(id));

// ifPresentOrElse
user.ifPresentOrElse(u -> log.info("found {}", u), () -> log.warn("missing"));

// stream(): flatten a list of optionals
List<String> names = ids.stream().map(this::findName).flatMap(Optional::stream).toList();
```

### 6. Common mistakes

- `Optional.of(maybeNull)` → NPE. Use `ofNullable`.
- Returning `null` from a method whose return type is `Optional` — the worst of both worlds.
- Wrapping to immediately unwrap: `Optional.ofNullable(x).orElse(y)` is just `x != null ? x : y` (or `Objects.requireNonNullElse`).
- Comparing with `==` — Optionals are value-based; use `equals`.

## 🔴 Senior Level

### 1. Value-based class semantics

`Optional` is documented as a **value-based class**: identity-sensitive operations (`==`, `synchronized`, `System.identityHashCode`) are discouraged and flagged by `javac -Xlint:synchronization` (Java 16+, warning `[synchronization]`). It is `final`, immutable, and `Optional.empty()` is a shared singleton.

### 2. Allocation and performance

`Optional.of(x)` allocates a 16-byte object per call unless **escape analysis** scalar-replaces it, which usually works when the Optional is created and consumed inside one inlined method chain. It frequently fails across non-inlined call boundaries (large methods, megamorphic calls, interface returns in cold code). Consequences:

- In ordinary service code the allocation is irrelevant.
- In hot paths (parsers, per-element loops over millions of items, low-latency trading), return a sentinel/nullable with `@Nullable`, or use primitive variants `OptionalInt`, `OptionalLong`, `OptionalDouble` which avoid boxing the value.

Check with JMH: `-prof gc` shows `gc.alloc.rate.norm` per op.

```java
// avoid allocating Optional<Integer> + Integer in a tight loop
OptionalInt max = java.util.Arrays.stream(data).max();
int m = max.orElse(Integer.MIN_VALUE);
```

### 3. Not a monad in the strict sense — and exceptions

`Optional` models absence only; it carries no error cause. For failures with a reason, use exceptions or a dedicated `Result<T,E>` type. Do not use `Optional` as a control-flow replacement for exceptions across layers:

```java
sealed interface Result<T> permits Result.Ok, Result.Err {
    record Ok<T>(T value) implements Result<T> {}
    record Err<T>(String reason) implements Result<T> {}
}
```

### 4. Serialization, Jackson, JPA

`Optional` is intentionally not `Serializable`. Jackson needs `jackson-datatype-jdk8` (auto-registered in Spring Boot) to serialise `Optional` fields as value/null; Hibernate does not map `Optional` attributes. The accepted pattern is a nullable field with an `Optional` **getter**:

```java
@Entity
class Customer {
    @Column private String middleName;                  // nullable column
    public Optional<String> getMiddleName() { return Optional.ofNullable(middleName); }
}
```

### 5. API evolution and testing

- Changing a return type from `T` to `Optional<T>` is binary-incompatible; plan a deprecation cycle.
- Test both branches explicitly; AssertJ gives fluent assertions: `assertThat(opt).isPresent().get().isEqualTo(x)`, `assertThat(opt).isEmpty()`.
- Add static analysis (SpotBugs `NP_OPTIONAL_RETURN_NULL`, Sonar S2789, S3655 for unchecked `get`) to CI.

### 6. Lazy composition in async code

```java
CompletableFuture<Optional<User>> f = CompletableFuture.supplyAsync(() -> repo.findById(1L));
String name = f.thenApply(o -> o.map(User::name).orElse("n/a")).join();
```

Avoid `Optional<CompletableFuture<T>>`; that is a type-level smell (a future already represents "might not be there yet").

## 🎯 Interview Cheat Sheet

**30-second pitch:** `Optional<T>` is a return-type container signalling "may have no value". Use `map/flatMap/filter` and `orElseGet/orElseThrow` rather than `isPresent()+get()`. Do not use it for fields, parameters or collections. It is a value-based, non-serializable class; allocation is normally optimised away, but use `OptionalInt` etc. for primitives.

**Must-know:**
- `of` vs `ofNullable` vs `empty`.
- `orElse` (eager) vs `orElseGet` (lazy).
- `map` vs `flatMap`.
- Java 9: `or`, `ifPresentOrElse`, `stream`; Java 10: `orElseThrow()`; Java 11: `isEmpty()`.
- Guideline: return types only.

**Common follow-ups:**
- Why is Optional not Serializable?
- How would you map `Optional<User>` to a REST response?
- Is `Optional.get()` bad? (Yes, when unguarded.)
- Performance cost of Optional?

**🚩 Red flags:**
- `Optional` as a field, parameter or `Optional<List<T>>`.
- `if (opt.isPresent()) opt.get()` everywhere.
- `orElse(expensiveCall())`.
