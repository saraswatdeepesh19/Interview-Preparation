# What are default and static methods in interfaces

---

## 🟢 Junior Level

### What is it?

Since Java 8 an interface may contain **method bodies**:

- `default` methods — an implementation inherited by all implementing classes unless they override it.
- `static` methods — utility methods that belong to the interface itself and are called as `InterfaceName.method()`.

**Why?** To evolve APIs without breaking existing implementers. Java 8 needed to add `forEach`, `stream()`, `sort` to `Collection`/`List`; adding abstract methods would have broken every third-party implementation overnight.

**Analogy:** A building code adds a new rule ("install a smoke detector"). Default methods are the landlord installing a basic detector in every flat; tenants may upgrade it, but nobody is in violation on day one.

```java
public interface Greeter {
    String name();

    // default: inherited behaviour
    default String greet() {
        return "Hello, " + name() + "!";
    }

    // static: helper tied to the interface
    static Greeter of(String name) {
        return () -> name;   // Greeter has one abstract method -> lambda works
    }
}

class Demo {
    public static void main(String[] args) {
        Greeter g = Greeter.of("Duke");
        System.out.println(g.greet()); // Hello, Duke!
    }
}
```

## 🟡 Middle Level

### 1. The diamond problem and resolution rules

If a class inherits the same default method signature from two interfaces, the compiler forces you to resolve it. The rules, in priority order:

1. **Classes win**: a method from the class hierarchy (even abstract) beats any interface default.
2. **More specific interface wins**: a sub-interface's default overrides the super-interface's.
3. Otherwise, **you must override** and may delegate using `Interface.super.method()`.

```java
interface Walker { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }

class Duck implements Walker, Swimmer {
    @Override
    public String move() {
        return Walker.super.move() + " and " + Swimmer.super.move();
    }
}
```

### 2. Interface evolution in the JDK

```java
List<Integer> list = new ArrayList<>(List.of(3, 1, 2));
list.sort(null);               // List.sort is a default method (Java 8)
list.removeIf(n -> n > 2);     // Collection.removeIf default
Map<String,Integer> m = new HashMap<>();
m.merge("a", 1, Integer::sum); // Map.merge default
```

`Comparator.reversed()`, `Comparator.comparing()` (static), `Function.identity()` (static) are everyday examples.

### 3. Default methods vs abstract classes

| Aspect | Interface with defaults | Abstract class |
| :--- | :--- | :--- |
| State (instance fields) | No (only constants) | Yes |
| Multiple inheritance | Yes (of behaviour) | No |
| Constructors | No | Yes |
| Access modifiers | public (and private helpers since 9) | any |
| Typical use | Capability/contract with optional behaviour | Shared state + template method |

### 4. Private interface methods (Java 9)

Share code between default methods without exposing it:

```java
interface Validator<T> {
    boolean isValid(T value);

    default boolean allValid(java.util.Collection<? extends T> items) {
        return items.stream().allMatch(this::check);
    }

    default boolean anyValid(java.util.Collection<? extends T> items) {
        return items.stream().anyMatch(this::check);
    }

    private boolean check(T t) {         // Java 9+
        return t != null && isValid(t);
    }
}
```

### 5. Common mistakes

- **Cannot override `Object` methods as defaults**: `default boolean equals(Object o)` is a compile error.
- **Static interface methods are not inherited**: `Impl.helper()` does not compile; call `Iface.helper()`.
- **Turning interfaces into god-classes** with logic and implicit coupling to `this` abstract methods.
- **Adding a default method to a published interface can still break** clients: a class that already has a conflicting method with the same signature but a different return type, or two interfaces now clashing.

## 🔴 Senior Level

### 1. Bytecode and dispatch

Default methods are compiled as non-abstract `public` instance methods in the interface class file (class-file version 52+). Calls use `invokeinterface`; `Iface.super.m()` compiles to `invokespecial` on the interface method reference. The JVM's method resolution picks the **maximally specific** method, which is why conflicts become `IncompatibleClassChangeError` at runtime if a library is upgraded without recompiling dependents (binary compatibility surprise).

```java
// Binary-compatibility scenario
// lib v1: interface A { }               lib v2: interface A { default void m() {} }
// app: class X implements A, B {}       B (other lib) also has default void m() {}
// X compiled against v1 loads fine; at runtime with v2 -> IncompatibleClassChangeError
```

### 2. API design guidance

Use defaults when:
- Adding a method to an existing published interface (the original purpose).
- Providing **derived** operations in terms of the abstract core (`Comparator.reversed`, `Iterator.forEachRemaining`).
- Implementing the **trait-like mixin** pattern: small capability interfaces composed into classes.

Avoid when:
- The default needs state — it will end up with hidden, ill-defined coupling.
- The method is not meaningful for all implementers; throwing `UnsupportedOperationException` from a default is an API smell, not a model.

Document the contract with `@implSpec` in Javadoc so implementers know what the default guarantees.

### 3. Mixin / decorator pattern

```java
interface Auditable {
    String id();
    default void audit(String action) {
        System.out.printf("[%s] %s%n", id(), action);
    }
}
interface Timestamped {
    default java.time.Instant now() { return java.time.Instant.now(); }
}
final class Order implements Auditable, Timestamped {
    public String id() { return "ORD-1"; }
}
```

Frameworks use this heavily: Spring `WebMvcConfigurer`/`HandlerInterceptor` (all-default callback interfaces replacing `Adapter` abstract classes since Spring 5), Spring Data repository fragments, JUnit 5 interface-based test templates.

### 4. Testing default methods

Test the interface contract through a minimal implementation and make a reusable abstract contract test:

```java
abstract class GreeterContract {
    abstract Greeter create(String name);

    @org.junit.jupiter.api.Test
    void greetsByName() {
        org.junit.jupiter.api.Assertions.assertEquals("Hello, Ann!", create("Ann").greet());
    }
}
```

### 5. Reflection and proxies

`Method.isDefault()` identifies default methods. Dynamic proxies (`java.lang.reflect.Proxy`) can invoke default methods via `InvocationHandler.invokeDefault` (Java 16+) — before that, one needed `MethodHandles.privateLookupIn` hacks that differ between Java 8 and 9+. Spring Data's proxy infrastructure had to implement exactly this.

```java
Object proxy = java.lang.reflect.Proxy.newProxyInstance(
        Greeter.class.getClassLoader(), new Class<?>[]{Greeter.class},
        (p, method, args) -> method.isDefault()
                ? java.lang.reflect.InvocationHandler.invokeDefault(p, method, args)
                : "proxied");
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** Java 8 allowed bodies in interfaces: `default` methods (inheritable behaviour, enabling API evolution without breaking implementers) and `static` methods (helpers on the interface). Java 9 added `private` methods. Class methods beat interface defaults; if two interfaces clash, you must override and can call `X.super.m()`.

**Must-know:**
- Why they exist: `forEach`, `stream`, `sort` on old interfaces.
- Three conflict-resolution rules.
- `Iface.super.method()` syntax.
- Interfaces still have no instance state.
- Static interface methods are not inherited.
- Private interface methods (Java 9).

**Common follow-ups:**
- Interface with defaults vs abstract class — which to choose?
- Can a default method override `equals`/`hashCode`? (No.)
- What happens when two interfaces provide the same default? (Compile error until resolved.)
- Is Java now supporting multiple inheritance? (Of behaviour, not state.)

**🚩 Red flags:**
- Putting business logic with hidden dependencies in defaults.
- Believing default methods remove the need for abstract classes.
