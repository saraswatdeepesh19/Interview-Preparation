# What are ClassLoaders and the parent delegation model

---

## 🟢 Junior Level

A **ClassLoader** finds the bytes of a class (in a JAR, a directory, the network) and turns them into a `Class` object the JVM can use. Classes are loaded **lazily** — the first time they are needed.

Java has a hierarchy of class loaders:

| Loader | Loads | Since Java 9 |
| --- | --- | --- |
| **Bootstrap** | Core JDK classes (`java.lang.*`, `java.util.*`) | Native, shows as `null` |
| **Platform** (was *Extension*) | Other JDK modules (`java.sql`, `java.xml`) | `ClassLoader.getPlatformClassLoader()` |
| **Application / System** | Your classpath/module path | `ClassLoader.getSystemClassLoader()` |

### Parent delegation
When a loader is asked for a class, it first asks its **parent**. Only if the parent cannot find it does it look itself.

```java
public class WhoLoadedMe {
    public static void main(String[] args) {
        System.out.println(String.class.getClassLoader());       // null (bootstrap)
        System.out.println(java.sql.Connection.class.getClassLoader()); // PlatformClassLoader
        System.out.println(WhoLoadedMe.class.getClassLoader());  // AppClassLoader
    }
}
```

### Real-world analogy
A junior employee asked a question first escalates to their manager, who escalates further up. Only if nobody above knows does the junior answer. That way everyone gives the *same* answer to "what is `java.lang.String`?".

## 🟡 Middle Level

### Why delegation exists
* **Security and consistency** — your JAR cannot replace `java.lang.String` with a malicious version: the bootstrap loader always wins.
* **Uniqueness** — a class is identified by **(fully qualified name, defining class loader)**. The same `.class` bytes loaded by two loaders produce two *different* runtime classes.

### The loading algorithm (`ClassLoader.loadClass`)

```java
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);            // 1. already loaded by me?
        if (c == null) {
            try {
                c = parent != null ? parent.loadClass(name, false)   // 2. delegate up
                                   : findBootstrapClassOrNull(name);
            } catch (ClassNotFoundException ignored) { }
            if (c == null) c = findClass(name);         // 3. look myself
        }
        if (resolve) resolveClass(c);
        return c;
    }
}
```

Custom loaders normally override `findClass`, not `loadClass`, to keep delegation intact.

### Loading, linking, initialization
1. **Loading** — read bytes, create `Class`.
2. **Linking** — *verify* bytecode, *prepare* static fields with defaults, optionally *resolve* symbolic references.
3. **Initialization** — run static initializers (`<clinit>`), triggered by first active use (new instance, static method call, non-constant static field access). It's thread-safe: the JVM holds an init lock, which is why the holder-class Singleton idiom works.

### Classic errors
* `ClassNotFoundException` — explicit loading (`Class.forName`, `loadClass`) failed to find the class.
* `NoClassDefFoundError` — the class was present at compile time but is missing at run time, *or* its static initializer previously failed (`ExceptionInInitializerError` the first time).
* `ClassCastException: com.acme.Foo cannot be cast to com.acme.Foo` — two loaders loaded the same class name.
* `LinkageError: loader constraint violation` — two loaders disagree about the identity of a type used in a method signature.

## 🔴 Senior Level

### Where delegation is deliberately broken
* **Servlet containers** (Tomcat) use *child-first* for web apps: `WebappClassLoader` looks in `WEB-INF/classes` and `WEB-INF/lib` before the parent (except for `java.*` and Servlet API classes), so each app can ship its own library versions.
* **Thread context class loader (TCCL)** — SPI frameworks in the bootstrap/platform layer (JDBC `DriverManager`, JNDI, JAXP, `ServiceLoader`) must load *your* implementation classes. They use `Thread.currentThread().getContextClassLoader()` to reach "down" the hierarchy. Forgetting to set the TCCL in custom thread pools is a classic cause of `ServiceConfigurationError`.
* **OSGi / JBoss Modules / Java modules layers** use graph-based delegation: each bundle/module sees only what it imports.
* **Spring Boot fat JARs** use `LaunchedClassLoader` (formerly `LaunchedURLClassLoader`) to load nested JARs from `BOOT-INF/lib` — standard `URLClassLoader` can't read JARs inside JARs.

### Class loader leaks
A class is unloaded only when its defining class loader becomes unreachable, along with every class and instance it defined. In app servers and hot-reload tools, one stray reference keeps the whole loader (and Metaspace) alive:
* a `ThreadLocal` on a pooled thread holding an app object,
* a JDBC driver registered in `DriverManager` (bootstrap-level static) and never deregistered,
* a running thread or `Timer` started by the app,
* a static cache in a shared library pointing at app classes.

Symptom: `OutOfMemoryError: Metaspace` after several redeploys. Diagnose with a heap dump: find instances of `WebappClassLoader` with `started=false` and follow "path to GC roots" in Eclipse MAT.

### Building a plugin system correctly

```java
Path pluginJar = Path.of("plugins/pricing-v2.jar");
try (URLClassLoader loader = new URLClassLoader(
        new URL[]{pluginJar.toUri().toURL()},
        PricingPlugin.class.getClassLoader())) {        // parent sees the shared API interface

    ServiceLoader<PricingPlugin> plugins = ServiceLoader.load(PricingPlugin.class, loader);
    plugins.findFirst().ifPresent(p -> p.price(order));
}   // close() releases JAR file handles; classes unload once nothing references them
```

Rules: the plugin API interface must be loaded by the **parent** (so host and plugin agree on its identity); plugin implementations come from the child; never let plugin objects leak into long-lived host caches.

### Performance notes
Class loading is a large share of startup time in Spring Boot apps (thousands of classes). Mitigations: AppCDS/CDS archives (`-XX:SharedArchiveFile`, Spring Boot's `-Dspring.context.exit=onRefresh` training run), fewer dependencies, Spring AOT, or GraalVM native image (classes are resolved at build time; no dynamic class loading at run time).

## 🎯 Interview Cheat Sheet

**30-second pitch:** ClassLoaders turn bytes into `Class` objects lazily. The default model is parent delegation — bootstrap, platform, application — which keeps core classes authoritative and consistent. A class's identity is its name plus defining loader, which explains `ClassCastException` between identical classes and loader leaks in redeploy scenarios.

**Must know:**
* Bootstrap → Platform → Application hierarchy (Java 9+).
* Load → link (verify, prepare, resolve) → initialize; `<clinit>` is thread-safe.
* `ClassNotFoundException` vs `NoClassDefFoundError`.
* Child-first in Tomcat; TCCL for SPIs; Spring Boot's nested-jar loader.
* Metaspace leaks from lingering references to app class loaders.

**Common follow-ups:**
* Why can't you replace `java.lang.String`?
* How does JDBC `DriverManager` find your driver?
* How do you unload a class?

**Red flags:** overriding `loadClass` and breaking delegation without reason; thinking classes are loaded at JVM startup.
