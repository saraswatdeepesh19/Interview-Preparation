# Streams and the Date-Time API recap from Java 8

---

## 🟢 Junior Level

### What is it?

Java 8 shipped two major library upgrades alongside lambdas:

1. **Streams** — a declarative pipeline for processing sequences of data (filter, map, reduce) without manual loops.
2. **`java.time`** — a modern, immutable, thread-safe Date-Time API replacing the broken `java.util.Date`, `Calendar` and `SimpleDateFormat`.

> [!NOTE]
> This is a **recap**. The Stream API is covered in depth in section 8 and collections in section 4. Here we focus on what the Java 8 addition means for language evolution and the Date-Time API essentials.

**Analogy:** A stream is a factory conveyor belt: items go through stations (filter, transform) and end in a box (collect). `java.time` is a set of precise instruments — a calendar (`LocalDate`), a wall clock (`LocalTime`), a global timestamp (`Instant`) — rather than one ambiguous `Date` that is all of them at once.

### Streams in 30 seconds

```java
import java.util.*;
import java.util.stream.*;

public class StreamRecap {
    public static void main(String[] args) {
        List<String> names = List.of("Anna", "Bob", "Christopher", "Dan");

        List<String> shortUpper = names.stream()
                .filter(n -> n.length() <= 4)
                .map(String::toUpperCase)
                .sorted()
                .collect(Collectors.toList());     // Java 16+: .toList()

        System.out.println(shortUpper);            // [ANNA, BOB, DAN]
        System.out.println(IntStream.rangeClosed(1, 5).sum()); // 15
    }
}
```

### Date-Time in 30 seconds

```java
import java.time.*;
import java.time.format.DateTimeFormatter;

public class TimeRecap {
    public static void main(String[] args) {
        LocalDate date = LocalDate.of(2024, Month.FEBRUARY, 28);
        System.out.println(date.plusDays(2));                    // 2024-03-01 (leap year)

        LocalDateTime meeting = LocalDateTime.of(2024, 5, 20, 14, 30);
        ZonedDateTime inTokyo = meeting.atZone(ZoneId.of("Europe/Berlin"))
                                       .withZoneSameInstant(ZoneId.of("Asia/Tokyo"));
        System.out.println(inTokyo);

        System.out.println(date.format(DateTimeFormatter.ofPattern("dd/MM/yyyy"))); // 28/02/2024
        System.out.println(Duration.ofMinutes(135));             // PT2H15M
        System.out.println(Period.between(date, LocalDate.of(2025, 1, 1)));
    }
}
```

| Type | Represents | Example |
| :--- | :--- | :--- |
| `LocalDate` | date without time/zone | birthday |
| `LocalTime` | time without date/zone | shop opening hour |
| `LocalDateTime` | date+time, no zone | "meeting at 14:30" (zone unknown) |
| `ZonedDateTime` | date+time+zone rules | flight departure |
| `OffsetDateTime` | date+time+fixed offset | DB/API with `+02:00` |
| `Instant` | point on the UTC timeline | audit timestamp |
| `Duration` / `Period` | time-based / date-based amount | 2h15m / 3 months |

## 🟡 Middle Level

### 1. Stream pipeline anatomy

A pipeline = **source** → zero or more **lazy intermediate** operations (`filter`, `map`, `flatMap`, `sorted`, `distinct`, `limit`) → one **terminal** operation (`collect`, `reduce`, `forEach`, `count`, `findFirst`). Nothing executes until the terminal operation runs, and a stream cannot be reused.

```java
record Order(String customer, double amount) {}

Map<String, Double> totalByCustomer = orders.stream()
        .filter(o -> o.amount() > 0)
        .collect(Collectors.groupingBy(Order::customer, Collectors.summingDouble(Order::amount)));

var stats = orders.stream().mapToDouble(Order::amount).summaryStatistics();
```

Stream additions since 8: `takeWhile`, `dropWhile`, `iterate` with predicate, `ofNullable` (9); `Collectors.toUnmodifiableList`, (10); `toList()` (16); `mapMulti` (16); `Collectors.teeing` (12).

### 2. Pitfalls with streams

- **Reusing a stream** → `IllegalStateException: stream has already been operated upon or closed`.
- **Side effects in `map`/`filter`** — behaviour under lazy/parallel evaluation is undefined.
- **`parallelStream()` by default** — uses the common ForkJoinPool; blocking I/O inside starves the whole JVM's parallel work. See section 9.
- **Using streams for tiny, simple loops** where a `for` is clearer and faster.
- **Mutable reduction misuse**: `reduce(new ArrayList<>(), …)` — use `collect`.

### 3. Date-Time: immutability and migration

All `java.time` types are immutable; "mutators" return new instances, so always assign the result:

```java
LocalDate d = LocalDate.of(2024, 1, 31);
d.plusMonths(1);                 // ignored! d is unchanged
LocalDate next = d.plusMonths(1); // 2024-02-29 (end-of-month clamped)
```

Bridging legacy code:

```java
java.util.Date legacy = new java.util.Date();
Instant instant = legacy.toInstant();
java.sql.Timestamp ts = java.sql.Timestamp.from(instant);
LocalDateTime ldt = LocalDateTime.ofInstant(instant, ZoneId.systemDefault());
```

JDBC 4.2 and Hibernate 5.2+ / JPA 2.2 map `LocalDate`, `LocalDateTime`, `Instant`, `OffsetDateTime` directly. Jackson needs `jackson-datatype-jsr310` (auto-configured in Spring Boot) and `WRITE_DATES_AS_TIMESTAMPS` disabled for ISO output.

### 4. Time zone and DST rules of thumb

- Store and transmit **`Instant` / UTC** (or `OffsetDateTime`); convert to a `ZoneId` (region like `Europe/Paris`, never a fixed abbreviation like `CET`) only at the edge for display.
- `LocalDateTime` has **no zone** — do not use it for events happening at an absolute moment.
- Inject a `Clock` for testability:

```java
class TokenService {
    private final Clock clock;
    TokenService(Clock clock) { this.clock = clock; }
    boolean expired(Instant issued) { return Instant.now(clock).isAfter(issued.plus(Duration.ofHours(1))); }
}
// test: new TokenService(Clock.fixed(Instant.parse("2024-01-01T00:00:00Z"), ZoneOffset.UTC))
```

### 5. Formatting is thread-safe now

`DateTimeFormatter` is immutable and thread-safe — share it as a `static final`. `SimpleDateFormat` is not; sharing it across threads caused notorious corrupt-date bugs.

## 🔴 Senior Level

### 1. Stream internals

A pipeline is a linked list of `AbstractPipeline` stages. The terminal operation builds a chain of `Sink`s and the source `Spliterator` pushes elements through (`forEachRemaining`) — one pass, element-at-a-time, with **short-circuiting** operations (`limit`, `findFirst`, `anyMatch`) using `Sink.cancellationRequested()`. Stateful operations (`sorted`, `distinct`) are barriers that buffer. Parallel execution uses `Spliterator.trySplit` and ForkJoin; splittability depends on the source: `ArrayList`/arrays/`IntStream.range` split well, `LinkedList`/`Stream.iterate` do not.

Performance guidance:
- Primitive streams (`IntStream`) avoid boxing; `mapToInt(...).sum()` beats `map(...).reduce(0, Integer::sum)`.
- Streams add ~tens of ns overhead per pipeline setup — irrelevant for large data, visible for 3-element lists in hot code.
- Parallel only when: large N, CPU-bound, stateless, splittable source, and measured with JMH.

### 2. Date-Time internals and traps

- `Instant` = seconds (long) + nanos (int); `LocalDate` = year, month, day — compact value objects. They are candidates for Valhalla value classes.
- `ZoneRules` come from the tzdata shipped in the JDK (`tzdb.dat`). **Government timezone changes** require updating the JDK or the tzupdater tool; containers with stale JDKs have shown wrong offsets in production.
- `ChronoUnit.DAYS.between` vs `Period.between` vs `Duration` differ around DST: `ZonedDateTime.plusDays(1)` keeps local time (23- or 25-hour day), `plus(Duration.ofHours(24))` adds exact elapsed time.

```java
ZonedDateTime beforeDst = ZonedDateTime.of(2024, 3, 30, 12, 0, 0, 0, ZoneId.of("Europe/Berlin"));
System.out.println(beforeDst.plusDays(1));                 // 2024-03-31T12:00+02:00 (same wall time)
System.out.println(beforeDst.plus(Duration.ofHours(24)));  // 2024-03-31T13:00+02:00 (24 real hours)
```

- Parsing ambiguity: `yyyy` vs `YYYY` (week-based year!) in patterns gives wrong years around New Year. Prefer `DateTimeFormatter.ISO_*` constants.
- Overlap/gap on DST transitions: `ZonedDateTime.ofLocal` resolves via `ZoneOffsetTransition` rules (earlier offset on overlap, shifts forward on gap).

### 3. Diagnostics

- Stream debugging: `peek` for temporary inspection only; IntelliJ's "Trace Current Stream Chain".
- Detecting parallel-stream contention: JFR thread view on `ForkJoinPool.commonPool-worker-*`; use a custom pool via `pool.submit(() -> list.parallelStream()...)` (implementation-dependent trick) or prefer explicit executors.
- Detect legacy date usage with ArchUnit or Checkstyle rules banning `java.util.Date`/`Calendar`/`SimpleDateFormat` in new code.

### 4. Advanced collector example

```java
record Sale(String region, String product, double amount) {}

Map<String, Map<String, Double>> pivot = sales.stream()
    .collect(Collectors.groupingBy(Sale::region, TreeMap::new,
             Collectors.groupingBy(Sale::product, TreeMap::new,
                                   Collectors.summingDouble(Sale::amount))));

// teeing (Java 12): two collectors in one pass
var result = sales.stream().collect(Collectors.teeing(
        Collectors.summingDouble(Sale::amount),
        Collectors.counting(),
        (sum, n) -> n == 0 ? 0.0 : sum / n));
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** Java 8 gave us lazy, single-use stream pipelines (source → intermediate → terminal) and an immutable, thread-safe `java.time` API with distinct types for dates, times, instants, zones and amounts. Store `Instant`/UTC, use `Clock` for tests, and avoid parallel streams unless measured.

**Must-know:**
- Intermediate ops are lazy; terminal triggers execution; streams are single-use.
- Never mutate external state from stream lambdas.
- `LocalDateTime` ≠ moment in time; `Instant`/`ZonedDateTime` are.
- All `java.time` types are immutable and thread-safe; `SimpleDateFormat` is not.
- Legacy bridges: `Date.toInstant()`, `Timestamp.toLocalDateTime()`.

**Common follow-ups:**
- `map` vs `flatMap`? `reduce` vs `collect`?
- How do you handle DST when adding a day?
- How would you test time-dependent code? (`Clock`)
- When is `parallelStream` harmful?

**🚩 Red flags:**
- Calling `plusDays` without assigning the result.
- Using `LocalDateTime` to store audit timestamps.
- `yyyy` vs `YYYY` confusion.
