# What are sealed classes and interfaces

---

## 🟢 Junior Level

### What is it?

A **sealed** class or interface (final in Java 17, preview in 15/16) restricts **which other classes may extend or implement it**. You list the allowed subtypes in a `permits` clause. Anyone else who tries to extend it gets a compile error.

**Analogy:** A VIP guest list at a club. Normal (non-sealed) classes are open doors — anybody can walk in and extend. A sealed class has a bouncer with a closed list of names.

```java
public sealed interface Shape permits Circle, Rectangle, Triangle {}

public record Circle(double radius) implements Shape {}
public record Rectangle(double width, double height) implements Shape {}
public final class Triangle implements Shape {
    final double base, height;
    public Triangle(double base, double height) { this.base = base; this.height = height; }
}

// public class Hexagon implements Shape {}   // compile error: not in the permits list
```

### Rules for permitted subclasses

Each permitted subclass must declare one of three modifiers:

| Modifier | Meaning |
| :--- | :--- |
| `final` | cannot be extended further (records and enums are implicitly final) |
| `sealed` | continues the restriction with its own `permits` |
| `non-sealed` | re-opens the hierarchy: anyone can extend this branch |

```java
public sealed class Vehicle permits Car, Truck, Bike {}
final class Car extends Vehicle {}
sealed class Truck extends Vehicle permits PickupTruck {}
final class PickupTruck extends Truck {}
non-sealed class Bike extends Vehicle {}    // open to subclassing
class Ebike extends Bike {}                 // OK
```

## 🟡 Middle Level

### 1. Why? Modelling closed domains (algebraic data types)

Sealed types + records give Java **sum types**. A payment is *exactly* a card, a bank transfer or a wallet — never anything else:

```java
public sealed interface Payment permits CardPayment, BankTransfer, Wallet {}
public record CardPayment(String pan, int cvv) implements Payment {}
public record BankTransfer(String iban) implements Payment {}
public record Wallet(String provider, String token) implements Payment {}

static String describe(Payment p) {
    return switch (p) {                       // exhaustive WITHOUT default (Java 21)
        case CardPayment c   -> "Card ending " + c.pan().substring(c.pan().length() - 4);
        case BankTransfer b  -> "Transfer to " + b.iban();
        case Wallet w        -> w.provider() + " wallet";
    };
}
```

Add a new `Payment` subtype and every non-defaulted switch fails to compile: the compiler becomes a refactoring tool. See [What is pattern matching for switch](11.%20What%20is%20pattern%20matching%20for%20switch.md).

### 2. `permits` can be omitted

If all subtypes are in the **same compilation unit** (same source file), the compiler infers `permits`:

```java
sealed interface Expr {
    record Num(int v) implements Expr {}
    record Add(Expr l, Expr r) implements Expr {}
    record Mul(Expr l, Expr r) implements Expr {}
}
```

Otherwise the permitted subclasses must be in the same package (unnamed module) or the same **module** (named module).

### 3. Sealed vs enum vs `final` vs package-private constructors

| Technique | Fixed set of | State per variant | Extensible by outsiders |
| :--- | :--- | :--- | :--- |
| `enum` | instances | same shape | no |
| `sealed` | types | different shape per type | no |
| package-private ctor | types (hack) | different | no, but no compiler exhaustiveness |
| `abstract class` / interface | open | any | yes |

### 4. Evaluating an expression tree

```java
static int eval(Expr e) {
    return switch (e) {
        case Expr.Num n -> n.v();
        case Expr.Add a -> eval(a.l()) + eval(a.r());
        case Expr.Mul m -> eval(m.l()) * eval(m.r());
    };
}
```

### 5. Common mistakes

- Forgetting that each subclass **must** be `final`, `sealed` or `non-sealed` (compile error otherwise).
- A permitted subclass in a different package of the unnamed module → error.
- Believing `sealed` is a security feature. It is primarily an **API design** tool, though the JVM does also check `PermittedSubclasses` at class load (`IncompatibleClassChangeError`), so hand-crafted bytecode cannot bypass it.
- Making everything `non-sealed` — defeats exhaustiveness.
- Sealing types that frameworks must proxy (Hibernate entities, Spring `@Configuration` CGLIB subclasses, Mockito mocks of sealed types need inline mock maker).

## 🔴 Senior Level

### 1. Class-file representation

`javac` emits a **`PermittedSubclasses`** attribute in the sealed class file listing the allowed subclasses. When the JVM loads a class that names a sealed superclass/interface, it verifies the subclass appears in that list (and in the same module / package). Violation throws `IncompatibleClassChangeError`. Reflection API (Java 17):

```java
Class<?> c = Payment.class;
System.out.println(c.isSealed());                       // true
for (Class<?> p : c.getPermittedSubclasses()) System.out.println(p.getSimpleName());
```

### 2. Exhaustiveness, generics and the `default` trade-off

The compiler computes exhaustiveness by checking that the permitted subtypes (recursively) are all covered, including generic sealed hierarchies with type argument inference:

```java
sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value) implements Result<T> {}
record Err<T>(String message) implements Result<T> {}

static <T> T unwrap(Result<T> r) {
    return switch (r) {
        case Ok<T> ok -> ok.value();
        case Err<T> err -> throw new IllegalStateException(err.message());
    };
}
```

At runtime a synthetic `default` throws `MatchException` (Java 21) if a separately-compiled new subtype appears: another reason to keep modules and their consumers rebuilt together. Adding a permitted subtype is therefore a **source-incompatible change** for consumers with exhaustive switches — design public sealed APIs knowing this. For libraries meant to be evolved, prefer non-sealed interfaces or document the hierarchy as closed-but-evolving.

### 3. Sealed hierarchies versus Visitor

Visitor needs `accept` boilerplate and a visitor interface bump per new variant, but gives double-dispatch on open hierarchies. Sealed + pattern switch is shorter, adds operations without touching the hierarchy and gets compiler checks. Visitor remains useful when the hierarchy is **open** or when you need polymorphism across modules.

### 4. Ecosystem and tooling

- **Jackson 2.12+** supports records; polymorphic deserialisation of sealed types needs `@JsonTypeInfo` + `@JsonSubTypes` (Jackson 2.x does not auto-discover permitted subclasses; helpers exist in newer versions).
- **JPA**: sealed entity hierarchies work if subclasses are in the persistence unit, but proxies for lazy loading cannot subclass `final` types — avoid `final` entities.
- **Mockito 5** defaults to the inline mock maker and can mock sealed types; with the subclass maker it cannot.
- **Kotlin** `sealed` and Scala `sealed` are the same idea; interop is direct.
- **Spring**: `@Configuration` classes are CGLIB-subclassed — never sealed.

### 5. Diagnostics and testing

Test each variant against a switch-based function and add one exhaustive test that uses reflection to assert permitted subtypes match your expectations:

```java
@Test
void allPaymentsHandled() {
    var types = java.util.Set.of(Payment.class.getPermittedSubclasses());
    assertEquals(java.util.Set.of(CardPayment.class, BankTransfer.class, Wallet.class), types);
}
```

Use `javap -v Payment` to inspect the `PermittedSubclasses` attribute. For API compatibility, tools like japicmp/revapi flag adding a permitted subclass as a breaking change (configure accordingly).

## 🎯 Interview Cheat Sheet

**30-second pitch:** `sealed` (Java 17) restricts which classes can extend/implement a type via `permits`. Each permitted subtype is `final`, `sealed` or `non-sealed`. Combined with records and pattern-matching `switch`, it models closed hierarchies (sum types) with compiler-checked exhaustiveness, without `default`.

**Must-know:**
- Syntax: `sealed ... permits`, `final` / `sealed` / `non-sealed`.
- `permits` may be omitted in the same compilation unit.
- Same package (classpath) or same module (JPMS).
- Enforced by the JVM via the `PermittedSubclasses` attribute.
- Foundation for exhaustive pattern switch.
- Adding a subtype is a breaking change for exhaustive switches.

**Common follow-ups:**
- Sealed vs enum vs final?
- How does it replace the Visitor pattern?
- Can records implement sealed interfaces? (Yes, and are implicitly final.)
- `non-sealed` — when and why?

**🚩 Red flags:**
- Sealing framework-proxied types (entities, configuration classes).
- Adding `default` in every switch over a sealed type.
