# What is var and local variable type inference

---

## 🟢 Junior Level

### What is it?

`var` (Java 10) lets the compiler **infer the type of a local variable** from its initializer. The variable is still **statically typed**; you just do not repeat the type name.

**Analogy:** Writing "Sam" instead of "Sam, the 34-year-old accountant from Leeds" every time. The compiler already knows who Sam is from the introduction.

```java
import java.util.*;

public class VarIntro {
    public static void main(String[] args) {
        var name = "Duke";                       // String
        var count = 42;                          // int
        var prices = new ArrayList<Double>();    // ArrayList<Double>
        var map = new HashMap<String, List<Integer>>();

        prices.add(9.99);
        for (var p : prices) {                   // p is Double
            System.out.println(p);
        }
        // name = 10;  // compile error: still a String
    }
}
```

### Where you can use `var`

- Local variables with an initializer
- Enhanced `for` loop variables and classic `for` index variables
- `try-with-resources` variables
- Lambda parameters (Java 11): `(var a, var b) -> a + b`

### Where you cannot

- Fields, method parameters, return types
- Without initializer (`var x;`), with `null` (`var x = null;`), with array initializer (`var a = {1,2};`)
- Self-referencing initializer, or a lambda/method reference without a target type (`var f = () -> 1;`)

## 🟡 Middle Level

### 1. Inference rules and surprises

`var` infers the **declared (static) type of the initializer expression**, not the loosest supertype you might want.

```java
var list = new ArrayList<String>();   // ArrayList<String>, NOT List<String>
list.trimToSize();                     // available, because the type is ArrayList

List<String> l2 = new ArrayList<>();   // intent: program to the interface

var diamond = new ArrayList<>();       // ArrayList<Object> — diamond with no target infers Object!
var ints = List.of(1, 2, 3);           // List<Integer>
var mixed = List.of(1, "a");           // List<Serializable & Comparable<...>> intersection type
```

Numeric literals follow normal rules: `var x = 1` is `int`, `var y = 1L` is `long`, `var z = 1 / 2` is `int` 0.

### 2. Non-denotable types

`var` can name types you could never write: anonymous classes and intersection/capture types.

```java
var anon = new Object() {
    int x = 10;
    void hello() { System.out.println("hi " + x); }
};
anon.hello();      // legal with var; impossible with 'Object anon'
System.out.println(anon.x);
```

Also handy for local record/class declarations in stream chains:

```java
var grouped = people.stream().collect(Collectors.groupingBy(Person::city, Collectors.counting()));
```

### 3. Style guidance (from OpenJDK's LVTI style guide)

1. Choose variable names that carry meaning — `var u = getUser();` is bad, `var user = getUser();` good.
2. Use `var` when the type is obvious from the right-hand side (`new`, a cast, a factory named clearly).
3. Do **not** use it when the type is not obvious from a method name (`var result = service.process();`).
4. Keep scopes small; `var` is more tolerable in short methods.
5. Don't use it with primitives when a precise width matters (`var b = (byte) 1` is fine but `var x = 0` hides `int` vs `long` intent).
6. Do not rely on `var` to change the API: since `var` is not allowed in signatures, public APIs are unchanged.

### 4. `var` in lambdas (Java 11)

Useful only to attach annotations while staying inferred:

```java
BiFunction<Integer, Integer, Integer> add = (@NonNull var a, @NonNull var b) -> a + b;
```

All parameters must be `var` or none — mixing is a compile error.

### 5. Common mistakes

- Using `var` with diamond and expecting a specific generic type.
- Reducing readability in chains: `var x = a.b().c().d();`.
- Assuming `var` makes code dynamically typed — it does not (this is not JavaScript).
- Forgetting that `var` is a **reserved type name**, not a keyword: `var var = 1;` compiles, but a class named `var` is forbidden.

## 🔴 Senior Level

### 1. Compilation

`var` is purely a **compile-time** feature. `javac` replaces it with the inferred type in the attributed AST; bytecode is identical to writing the type explicitly. There is no runtime, reflection or performance difference. The `LocalVariableTable` / `LocalVariableTypeTable` debug attributes record the real type.

```bash
javap -l -c VarIntro   # shows the inferred types in LocalVariableTable
```

### 2. Inference with generics and ternaries

```java
var a = flag ? 1 : "text";           // type: Serializable & Comparable<? extends ...> & Constable...
var b = flag ? 1 : 2.0;              // double (binary numeric promotion!)
var c = flag ? Integer.valueOf(1) : null; // Integer, NPE trap if unboxed later
```

Capture variables: `var x = someWildcardList.get(0);` gets an anonymous capture type that is projected to its upper bound when stored in a field or returned, so the code remains sound.

### 3. API and refactoring implications

- **Source compatibility trap:** if a method return type changes (e.g. `List<String>` → `Stream<String>`), `var` silently adapts and downstream calls may fail to compile elsewhere, or — worse with overload resolution — pick a different overload at the call site.
- **Code reviews on GitHub/GitLab** show no type info; reviewers lose IDE hints. Teams often enforce `var` only where RHS makes type obvious (Checkstyle / Error Prone / PMD `UseDiamondOperator`, IntelliJ inspection "var can be replaced with explicit type").
- Binary compatibility is unaffected: the descriptor uses the inferred type.
- Spring/Jakarta injection is irrelevant (fields cannot be `var`).

### 4. Pattern: stream teeing / intermediate records

Local records plus `var` allow ad-hoc structures without public classes:

```java
public Map<String, Double> averageByDept(List<Employee> emps) {
    record Acc(double sum, long n) {
        Acc plus(double v) { return new Acc(sum + v, n + 1); }
    }
    var tmp = emps.stream().collect(java.util.stream.Collectors.groupingBy(
            Employee::dept,
            java.util.stream.Collectors.collectingAndThen(
                java.util.stream.Collectors.reducing(new Acc(0, 0),
                        e -> new Acc(e.salary(), 1),
                        (x, y) -> new Acc(x.sum() + y.sum(), x.n() + y.n())),
                a -> a.sum() / a.n())));
    return tmp;
}
record Employee(String dept, double salary) {}
```

### 4b. Try-with-resources

```java
try (var in = java.nio.file.Files.newBufferedReader(path);
     var out = java.nio.file.Files.newBufferedWriter(target)) {
    in.transferTo(out);
}
```

### 5. Production guidance

- Adopt `var` where it removes redundancy (`var conn = dataSource.getConnection();`).
- Keep the interface type for fields and returns; consider `List<String> items = new ArrayList<>();` when intent matters.
- Make this a team-level rule in `.editorconfig`/Checkstyle rather than debating in reviews.
- Beware of `var` in **tests with mocks**: `var mock = mock(Foo.class)` is fine; type is `Foo`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `var` infers the type of a local variable from its initializer at compile time — still static typing, identical bytecode. Allowed for locals, loop variables, try-resources, and (Java 11) lambda parameters; not for fields, parameters, returns, or `null`/uninitialised declarations. Use when the type is obvious; avoid when it obscures meaning.

**Must-know:**
- Introduced in Java 10; `var` in lambdas in 11.
- Not dynamic typing, not a keyword (reserved type name).
- `var list = new ArrayList<String>()` is `ArrayList`, not `List`.
- `new ArrayList<>()` with `var` → `ArrayList<Object>`.
- Allows anonymous-class types.

**Common follow-ups:**
- Can `var` be used for fields? (No.)
- Does `var` affect performance? (No.)
- When would you not use it?
- What is the inferred type of `var x = cond ? 1 : "a"`?

**🚩 Red flags:**
- Meaningless names with `var` (`var x = process();`).
- Claiming `var` is like `Object` or JavaScript `var`.
