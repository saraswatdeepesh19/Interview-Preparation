# What are method references and what kinds exist

---

## 🟢 Junior Level

### What is it?

A **method reference** is a shorthand for a lambda that does nothing except call an existing method. Syntax: `ClassOrObject::methodName` (no parentheses, because you are not calling it — you are pointing at it).

**Analogy:** Instead of writing "when asked, please phone Bob at number X", you just say "call Bob". The instruction already exists as a contact; you refer to it.

```java
import java.util.*;

public class MethodRefIntro {
    public static void main(String[] args) {
        List<String> words = List.of("kiwi", "apple", "fig");

        words.forEach(w -> System.out.println(w));   // lambda
        words.forEach(System.out::println);          // method reference

        List<Integer> lengths = words.stream().map(String::length).toList();
        System.out.println(lengths); // [4, 5, 3]
    }
}
```

### Rule of thumb

If your lambda looks like `x -> something(x)` or `(a, b) -> a.something(b)`, try a method reference. If the reader finds it clearer, keep it; if not, keep the lambda.

## 🟡 Middle Level

### The four kinds

| # | Kind | Syntax | Equivalent lambda |
| :-- | :--- | :--- | :--- |
| 1 | Static method | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| 2 | Bound instance method (specific object) | `logger::info` | `msg -> logger.info(msg)` |
| 3 | Unbound instance method (arbitrary object of a type) | `String::toUpperCase` | `s -> s.toUpperCase()` |
| 4 | Constructor | `ArrayList::new` | `() -> new ArrayList<>()` |

```java
import java.util.*;
import java.util.function.*;

public class FourKinds {
    private final String prefix = ">> ";

    String decorate(String s) { return prefix + s; }

    public static void main(String[] args) {
        // 1. static
        Function<String, Integer> parse = Integer::parseInt;

        // 2. bound: receiver captured at creation time
        FourKinds self = new FourKinds();
        Function<String, String> deco = self::decorate;

        // 3. unbound: first parameter becomes the receiver
        BiFunction<String, String, Boolean> startsWith = String::startsWith;
        System.out.println(startsWith.apply("hello", "he")); // true

        // 4. constructor, including arrays
        Supplier<List<String>> listFactory = ArrayList::new;
        IntFunction<int[]> arrayFactory = int[]::new;

        System.out.println(parse.apply("42") + " " + deco.apply("x")
                + " " + listFactory.get() + " " + arrayFactory.apply(3).length);
    }
}
```

### Practical use

```java
import java.util.*;
import java.util.stream.*;

record Person(String name, int age) {}

class People {
    static void demo() {
        List<Person> people = List.of(new Person("Ann", 31), new Person("Bob", 25));

        // Comparator building blocks
        List<Person> sorted = people.stream()
                .sorted(Comparator.comparing(Person::name).thenComparingInt(Person::age))
                .toList();

        // Collectors
        Map<Integer, List<String>> byAge = people.stream()
                .collect(Collectors.groupingBy(Person::age,
                        Collectors.mapping(Person::name, Collectors.toList())));

        // Stream to array with typed constructor
        String[] names = people.stream().map(Person::name).toArray(String[]::new);
    }
}
```

Spring examples: `.stream().map(UserDto::from)`, `Optional.map(this::toResponse)`, `CompletableFuture.thenApply(Mapper::convert)`.

### Common mistakes

- **Ambiguity with overloads.** `Integer::toString` is ambiguous for `Function<Integer,String>`: it could be the static `Integer.toString(int)` or the instance `toString()`. The compiler rejects it; use `String::valueOf` or a lambda.
- **Bound reference evaluates the receiver once.** `getService()::call` calls `getService()` immediately; a lambda `x -> getService().call(x)` calls it every time. And `null::foo` throws NPE at creation time.
- **Side-effect hiding:** `list.forEach(map::remove)` looks tidy but `Map.remove` has overloads and returns a value — readability suffers.
- **Using `this::method` in constructors** can leak a partially constructed object.

## 🔴 Senior Level

### 1. Bytecode

Method references are compiled with the same `invokedynamic` + `LambdaMetafactory` mechanism as lambdas, but often **without a synthetic bridge method**: the metafactory receives a `MethodHandle` directly to the target (`REF_invokeStatic`, `REF_invokeVirtual`, `REF_newInvokeSpecial`, …). Hence a method reference is typically marginally leaner than the equivalent lambda, but the difference is rarely measurable after JIT.

```bash
javap -p -c -v MethodRefIntro | grep -A6 "BootstrapMethods"
```

Exceptions where javac still generates a synthetic lambda: varargs methods, `super::method`, protected members from a different package, and some intersection-type or inaccessible-class cases.

### 2. Capture semantics and memory

```java
class Handler {
    private final byte[] bigBuffer = new byte[10_000_000];
    void process(String s) { /* ... */ }

    java.util.function.Consumer<String> leaky() {
        return this::process; // holds the whole Handler (and buffer) alive
    }
}
```

A bound method reference captures its receiver strongly. Storing it in a static registry or a listener list without deregistration is a classic **memory leak**. Prefer weak references, or explicit unsubscribe tokens (`AutoCloseable`).

### 3. Stack traces and debugging

Frames look like `Handler$$Lambda/0x0000000800c03000.accept`. With method references, the stack contains the target method directly, which is somewhat easier to read than `lambda$leaky$0`. Hidden frames are filtered by default; show them with `-XX:+ShowHiddenFrames`.

### 4. Generic methods and inference

```java
import java.util.*;
import java.util.function.*;

Function<List<String>, Integer> size = List<String>::size; // type args on the qualifying type
Supplier<Map<String, List<Integer>>> factory = HashMap::new; // diamond inferred
Supplier<List<String>> empty = Collections::<String>emptyList; // explicit type witness
```

### 5. Performance and megamorphism

A method reference passed to a shared utility behaves like any lambda: a single hot call site is inlined; a heavily reused generic helper turns megamorphic. In latency-critical code (parsers, codecs), prefer plain loops and primitive specialisations (`IntUnaryOperator`) over `Function<Integer,Integer>` chains.

### 6. Tooling

Static analysis (IntelliJ "Replace lambda with method reference", SonarLint S1612) automates the conversion; accept it only when it improves clarity. Unit-test behaviour, not syntax.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A method reference (`Type::method`) is a compact lambda that delegates to an existing method. There are four kinds: static, bound instance, unbound instance (first argument is the receiver), and constructor. They compile via `invokedynamic` like lambdas.

**Must-know:**
- The four kinds and the lambda each corresponds to.
- Unbound refs shift the first parameter into the receiver (`String::length`).
- Bound refs evaluate the receiver eagerly and keep it alive.
- `ArrayList::new`, `String[]::new` for constructors and arrays.
- Ambiguity with overloads (`Integer::toString`).

**Common follow-ups:**
- Difference between `System.out::println` and `s -> System.out.println(s)`? (receiver `System.out` evaluated once vs each call.)
- Can a method reference refer to a private method? (Yes, if accessible from that location.)
- Why does `Integer::toString` not compile as `Function<Integer,String>`?

**🚩 Red flags:**
- Using method references that hide complex logic.
- Storing bound method references in long-lived collections without cleanup.
