# DynamoDB basics

---

## 🟢 Junior Level

**Amazon DynamoDB** is AWS's serverless NoSQL key-value/document database. You create a table, define its primary key, and AWS handles servers, replication across three Availability Zones, patching and scaling. This article focuses on **using DynamoDB from a Java/AWS perspective**; data modeling is covered in the NoSQL section.

### Key facts
* Primary key: partition key, or partition + sort key.
* Item size limit **400 KB**; single-digit-millisecond latency.
* Data replicated across 3 AZs automatically; durable on write acknowledgment.
* Access controlled by **IAM** (no database users/passwords).
* Billing: **on-demand** (per request) or **provisioned** capacity (RCU/WCU) with auto scaling.

### Java SDK v2 (enhanced client)

```java
DynamoDbClient ddb = DynamoDbClient.builder()
        .region(Region.EU_CENTRAL_1)
        .build();                                      // credentials from the default provider chain (IAM role)
DynamoDbEnhancedClient enhanced = DynamoDbEnhancedClient.builder().dynamoDbClient(ddb).build();

// Customer is a @DynamoDbBean with a no-arg constructor, getters/setters and @DynamoDbPartitionKey on getId()
DynamoDbTable<Customer> customers = enhanced.table("customers", TableSchema.fromBean(Customer.class));

customers.putItem(new Customer("c-7", "Ada", "ada@example.com"));
Customer c = customers.getItem(Key.builder().partitionValue("c-7").build());
```

Spring Cloud AWS 3.x provides `DynamoDbTemplate` with Spring Boot auto-configuration on top of the same SDK.

## 🟡 Middle Level

### IAM least privilege for a service

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:UpdateItem", "dynamodb:Query"],
    "Resource": [
      "arn:aws:dynamodb:eu-central-1:123456789012:table/customers",
      "arn:aws:dynamodb:eu-central-1:123456789012:table/customers/index/*"
    ]
  }]
}
```

Attach it to the workload's role (EKS Pod Identity/IRSA, ECS task role, Lambda execution role). Fine-grained access with `dynamodb:LeadingKeys` conditions can restrict a tenant to items whose partition key equals its ID.

### Capacity, throttling and retries
* Exceeding capacity (or a hot partition's limit of ~3,000 RCU / 1,000 WCU) returns `ProvisionedThroughputExceededException` / `ThrottlingException`; the SDK retries with exponential backoff automatically (standard retry mode: 3 attempts). Monitor `ThrottledRequests` in CloudWatch.
* On-demand tables scale instantly up to double the previous peak; sudden 10× spikes can still throttle briefly — pre-warm by switching to provisioned with high capacity before known events, or design for retry.

### Operations
* **Point-in-time recovery (PITR)** — continuous backups for the last 35 days; enable it for every production table.
* **On-demand backups** and **export to S3** (no capacity impact) for analytics with Athena.
* **TTL** for automatic expiry; **Streams** for change data capture into Lambda/Kinesis.
* **Global Tables** for multi-Region active-active replication.

## 🔴 Senior Level

### Performance features
* **DAX** (DynamoDB Accelerator) — an in-memory, write-through cache cluster with microsecond reads, API-compatible with DynamoDB (use the DAX client). Helps read-heavy, hot-key workloads; adds eventual consistency for cached reads and a cluster to operate.
* **Batch APIs** (`BatchGetItem` up to 100 items/16 MB, `BatchWriteItem` up to 25 items) reduce round trips; handle `UnprocessedItems`/`UnprocessedKeys` with retries.
* **Parallel scans** for bulk exports when you can't use S3 export — throttle them to avoid consuming production capacity.
* Use the **CRT-based async HTTP client** or tuned Apache client connection pool for high-throughput services; reuse one SDK client per application (they're thread-safe and expensive to create).

### Cost model gotchas
* Reads are billed per 4 KB, writes per 1 KB — **item size directly drives cost**; store large attributes in S3.
* Every GSI is billed for its own writes (each base-table write that touches indexed attributes costs again per index).
* Strongly consistent reads cost 2×; transactions cost 2×.
* Scans read every item — a single "search" feature built on Scan can dominate the bill.
* On-demand is ~5–7× more expensive per request than well-utilized provisioned capacity; switch steady workloads to provisioned + auto scaling (or reserved capacity).

### Local development and testing
* **DynamoDB Local** (Docker image `amazon/dynamodb-local`) or **LocalStack** with Testcontainers for integration tests; create tables in test setup from the same definitions used in IaC (CDK/Terraform) to avoid drift.
* Remember emulators don't reproduce throttling, partition limits or exact consistency timing — load-test against real AWS for capacity validation.

## 🎯 Interview Cheat Sheet

**30-second pitch:** DynamoDB is AWS's managed key-value/document store, replicated across three AZs, accessed with IAM-authorized SDK calls rather than database users. From Java I use one shared SDK v2 enhanced client, least-privilege IAM roles per workload, PITR for backups, Streams for change events and TTL for expiry. Costs depend on item size, indexes, consistency and capacity mode, throttling is handled by SDK retries plus good partition design, and DAX adds a microsecond cache.

**Must know:**
* Keys, 400 KB items, 3-AZ replication, IAM access.
* SDK v2 enhanced client; Spring Cloud AWS `DynamoDbTemplate`.
* On-demand vs provisioned; throttling exceptions; partition limits.
* PITR, export to S3, Streams, TTL, Global Tables.
* Cost drivers; DAX; batch APIs; DynamoDB Local/LocalStack.

**Common follow-ups:**
* Why is our DynamoDB bill so high?
* How do you restrict a tenant to its own items?
* When would you add DAX?

**Red flags:** Scan-based queries; creating SDK clients per request; no PITR on production tables.
