# High availability and the Well-Architected Framework

---

## 🟢 Junior Level

The **AWS Well-Architected Framework** is a set of best practices organized into **six pillars**, used to review and improve workloads:

| Pillar | Key question |
| --- | --- |
| **Operational Excellence** | Can we run, monitor and improve the system safely (automation, small changes, runbooks, learning from incidents)? |
| **Security** | Are identities, data, networks and changes protected and audited? |
| **Reliability** | Does it recover from failures and meet demand (redundancy, scaling, backups, tested recovery)? |
| **Performance Efficiency** | Are resources the right type and size, and do we evolve with new options? |
| **Cost Optimization** | Do we avoid waste and pay only for value? |
| **Sustainability** | Do we minimize the environmental impact (utilization, efficient regions/hardware)? |

The **Well-Architected Tool** in the console walks through questions per pillar and records improvement plans.

### High availability on AWS: the basics
* Deploy across **at least two, preferably three Availability Zones** (physically separate data centers in a region).
* **Load balancers** (ALB/NLB) are zone-redundant; **Auto Scaling groups**/ECS services/EKS node groups spread instances across AZs.
* **Managed data stores** with Multi-AZ: RDS Multi-AZ (synchronous standby, automatic failover), Aurora (storage replicated 6 ways across 3 AZs), DynamoDB and S3 (multi-AZ by default), ElastiCache Multi-AZ.
* **Health checks** and automatic replacement of failed instances.

## 🟡 Middle Level

### Reliability pillar design principles
1. **Automatically recover from failure** — health checks, auto scaling, managed failover; alarms trigger automation, not only humans.
2. **Test recovery procedures** — game days, AWS Fault Injection Service.
3. **Scale horizontally** — many small instances instead of one large one; remove single points of failure.
4. **Stop guessing capacity** — autoscaling based on metrics.
5. **Manage change through automation** — IaC (CloudFormation/CDK/Terraform), pipelines, no manual changes.

### Availability math for a typical three-tier service
* ALB (zone-redundant) + app instances in 3 AZs + Aurora Multi-AZ + ElastiCache Multi-AZ.
* With N+1 capacity per AZ (each AZ can lose one, or the system can lose an entire AZ and keep ≥ 100% capacity), an AZ outage causes no user impact beyond in-flight requests and failover seconds.
* Weak spots: single NAT Gateway (it's zonal — deploy one per AZ), a single-AZ cache or broker, hardcoded AZ-specific endpoints, and dependencies outside the region.

### Static stability
Design so that during an AZ failure, the system doesn't need to *launch* new resources to survive (control-plane operations may be slow or impaired during large events). Pre-provision enough capacity in the remaining AZs (over-provision by ~50% with three AZs) rather than relying on autoscaling during the event.

## 🔴 Senior Level

### Beyond a single region
Region-level resilience is a business decision (cost and complexity roughly double):
* **Backup & restore** to another region (AWS Backup cross-region copies) — cheapest, hours of RTO.
* **Pilot light / warm standby** — replicated data (Aurora Global Database, DynamoDB Global Tables, S3 CRR) with minimal or scaled-down compute in the DR region; **Route 53 health checks and failover records**, or **Application Recovery Controller** (routing controls and readiness checks) for controlled failover.
* **Active-active** — multi-region writes with conflict-aware data design; Global Accelerator or latency-based routing.

### Fault isolation boundaries
AWS designs services with **cells** and **shuffle sharding** to limit blast radius; apply the same idea:
* Separate **accounts** per environment and per team/workload (AWS Organizations) — limits blast radius of mistakes and quotas.
* **Cell-based architecture** for large multi-tenant systems — each cell is a full stack serving a subset of tenants.
* **Zonal isolation** — keep request paths within an AZ where possible (zonal endpoints, topology-aware routing) so an impaired AZ can be evacuated (Route 53 ARC **zonal shift** moves traffic away from an AZ for ALB/NLB).

### Running Well-Architected reviews effectively
* Review **per workload**, early in design and periodically (e.g. yearly or after major changes), with the team that owns it.
* Prioritize **high-risk issues (HRIs)** with owners and deadlines — the value is in the improvement backlog, not the questionnaire.
* Use the **lenses** relevant to the workload (Serverless, SaaS, Financial Services, Container Build).
* Tie findings to evidence: SLO data, game day results, incident history, cost reports.

### Common gaps found in reviews of Java services on AWS
* No tested restore of RDS snapshots / PITR.
* Single NAT Gateway or single-AZ ElastiCache.
* Static IAM access keys in configuration.
* No timeouts/retries tuned for AWS SDK calls; SDK clients created per request.
* Autoscaling based only on CPU while the bottleneck is DB connections or queue depth.
* Missing alarms on key symptoms (5xx ratio, p99 latency, queue age) and log retention set to never expire.

### Spreading a service across AZs in Kubernetes (EKS)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 6
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone     # spread evenly across AZs
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: orders } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders }
spec:
  minAvailable: 4                                      # node drains/upgrades never drop below 4 pods
  selector: { matchLabels: { app: orders } }
```

With 6 replicas over 3 AZs, losing one AZ leaves 4 pods — size each pod so 4 can carry peak load (static stability).

## 🎯 Interview Cheat Sheet

**30-second pitch:** The Well-Architected Framework reviews workloads across six pillars — operational excellence, security, reliability, performance efficiency, cost optimization and sustainability. For high availability I deploy across three AZs with zone-redundant load balancers, autoscaled stateless services and Multi-AZ managed data stores, keep N+1 capacity for static stability, remove zonal single points of failure like single NAT gateways, and extend to multi-region only when business RTO/RPO justify it.

**Must know:**
* Six pillars and their focus.
* Multi-AZ building blocks: ALB, ASG/ECS/EKS spread, RDS Multi-AZ, Aurora storage, DynamoDB/S3.
* Reliability design principles; static stability.
* DR options; Route 53 failover; ARC zonal shift.
* Account separation, cells, review practice (HRIs, lenses).

**Common follow-ups:**
* What breaks in your architecture if one AZ fails?
* How do you test a region failover?
* What's static stability?

**Red flags:** single-AZ production; untested backups; "AWS handles HA for us".
