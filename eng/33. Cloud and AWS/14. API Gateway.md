# API Gateway

---

## 🟢 Junior Level

**Amazon API Gateway** is a managed service to publish, secure and operate APIs in front of Lambda functions, HTTP backends, or AWS services. It handles TLS, routing, authentication, throttling, request validation, and monitoring without servers.

### Three API types

| Type | Best for | Highlights |
| --- | --- | --- |
| **HTTP API** | Most new REST-style APIs in front of Lambda/HTTP backends | Cheaper (~70% less than REST APIs), lower latency, JWT authorizers built in, simpler |
| **REST API** | APIs needing advanced features | Usage plans & API keys, request/response transformation, caching, WAF integration, private APIs, request validation |
| **WebSocket API** | Real-time bidirectional apps (chat, live updates) | Connection management, routes by message content |

### Typical serverless setup

```mermaid
flowchart LR
    C[Client] -->|HTTPS + JWT| AG[API Gateway HTTP API]
    AG -->|JWT authorizer validates token from Cognito/OIDC| AG
    AG -->|GET /orders/{id}| L1[Lambda: getOrder]
    AG -->|POST /orders| L2[Lambda: createOrder]
    AG -->|/legacy/*| ALB[Private ALB via VPC link] --> SVC[ECS service]
```

## 🟡 Middle Level

### Security options
* **JWT authorizer** (HTTP API) — validates tokens from any OIDC provider (Cognito, Auth0, Keycloak): issuer, audience, expiry, scopes per route.
* **Lambda authorizer** — custom logic (API keys in your DB, legacy tokens, fine-grained checks); cache results by token for a TTL to avoid invoking it on every request.
* **IAM authorization** (SigV4) — for service-to-service calls from AWS workloads.
* **Resource policies** and **private APIs** (REST) — reachable only from specific VPC endpoints.
* **AWS WAF** (REST API, or in front via CloudFront) for IP reputation, rate-based rules, SQL injection/XSS signatures.

### Throttling and quotas
* Account-level default throttle (e.g. 10,000 requests/s with burst 5,000 per region — soft limits) shared by all APIs.
* Per-route/stage throttles; **usage plans** with API keys (REST) for per-client quotas and rate limits.
* Excess requests get **429**; clients should back off.

### Integration patterns
* **Lambda proxy integration** — the whole request is passed to Lambda; the function returns status, headers, body.
* **HTTP proxy / private integration** — forward to HTTP backends; **VPC link** to reach private ALBs/NLBs/Cloud Map services.
* **AWS service integrations** — e.g. `POST /events` → `SQS:SendMessage` or `EventBridge:PutEvents` directly, without a Lambda in between (cheaper, fewer moving parts).

## 🔴 Senior Level

### Limits that shape designs
* **Integration timeout** — historically 29 seconds maximum for REST and HTTP APIs (REST regional/private APIs can now request higher timeouts at the cost of throttle quota) — long-running operations should use async patterns (202 + status polling, or WebSockets/callbacks).
* **Payload size** — 10 MB for REST/HTTP APIs; WebSocket frames 32 KB (messages up to 128 KB).
* **Lambda response size** — 6 MB synchronous; larger downloads via S3 presigned URLs.
* **Cold starts** of Lambda backends add to API latency — SnapStart/provisioned concurrency for latency-sensitive routes.

### API Gateway vs alternatives
* **ALB in front of containers** — cheaper at high constant volume, supports long-lived connections, but lacks API management features (keys, usage plans, transformations).
* **Spring Cloud Gateway / Kong / Envoy** in the cluster — full control, routing logic in code, same behavior across clouds; you operate it.
* **CloudFront** in front of API Gateway — edge TLS termination, global caching of GET responses, WAF; regional API Gateway endpoints behind it are a common pattern.

Rule of thumb: API Gateway shines for serverless backends, public APIs needing managed auth/throttling/keys, and teams without capacity to run a gateway; at sustained very high RPS, per-request pricing makes ALB or self-managed gateways cheaper.

### Operations
* **Stages** and **stage variables** for environments; **canary deployments** on REST API stages (percentage of traffic to a new deployment).
* **Access logs** (JSON with request ID, latency, integration latency, status, authorizer errors) to CloudWatch or Firehose; **X-Ray tracing** end to end.
* Key metrics: `Count`, `4XXError`, `5XXError`, `Latency` vs `IntegrationLatency` (the difference is gateway overhead including authorizers).
* Define APIs as **OpenAPI** with extensions (`x-amazon-apigateway-integration`) or IaC (CDK/SAM/Terraform) — never click-ops in production.

## 🎯 Interview Cheat Sheet

**30-second pitch:** API Gateway is AWS's managed front door for APIs: HTTP APIs are cheaper and simpler with built-in JWT authorizers; REST APIs add usage plans, API keys, transformations, caching, WAF and private APIs; WebSocket APIs handle real-time connections. It integrates with Lambda, HTTP backends via VPC links, and AWS services directly. I design around its timeout and payload limits with async patterns, and prefer ALB or a self-managed gateway for sustained high-volume container traffic.

**Must know:**
* HTTP vs REST vs WebSocket APIs.
* JWT, Lambda, and IAM authorizers; WAF; resource policies.
* Throttling, usage plans, 429.
* Lambda proxy, HTTP/VPC link, direct service integrations.
* Timeout (≈29 s) and payload limits; Latency vs IntegrationLatency.

**Common follow-ups:**
* How do you expose a private ECS service through API Gateway?
* How would you implement per-customer quotas?
* API Gateway or ALB for a container service at 20k req/s?

**Red flags:** synchronous long-running operations through API Gateway; uncached Lambda authorizers on hot paths; APIs defined by hand in the console.
