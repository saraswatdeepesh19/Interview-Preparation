# Secrets Manager Parameter Store and KMS

---

## 🟢 Junior Level

Three AWS services handle configuration, secrets and keys:

| Service | Stores | Key features | Cost |
| --- | --- | --- | --- |
| **SSM Parameter Store** | Configuration values and secrets (`SecureString`) in a hierarchy (`/orders/prod/db/url`) | Free standard tier, versioning, IAM per path, KMS encryption for SecureString | Standard params free; advanced/higher throughput paid |
| **Secrets Manager** | Secrets (DB credentials, API keys) | **Automatic rotation** (Lambda-based, native for RDS/Aurora/Redshift/DocumentDB), cross-region replication, resource policies | Per secret per month + API calls |
| **KMS** (Key Management Service) | **Encryption keys** (never leave KMS/HSMs in plaintext) | Encrypt/decrypt, data keys for envelope encryption, key policies, rotation, CloudTrail audit | Per key per month + requests |

Rule of thumb: plain configuration → Parameter Store; credentials that should rotate → Secrets Manager; encryption → KMS (both other services use KMS under the hood).

### Reading them in Spring Boot (Spring Cloud AWS 3.x)

```yaml
spring:
  config:
    import:
      - aws-parameterstore:/orders/prod/          # /orders/prod/app/payment-url -> app.payment-url
      - aws-secretsmanager:orders/prod/db         # JSON secret {"username":"..","password":".."} -> username, password
  datasource:
    url: ${app.db-url}
    username: ${username}
    password: ${password}
```

Credentials for these calls come from the workload's IAM role — no AWS keys in configuration.

## 🟡 Middle Level

### IAM: least privilege per service

```json
{
  "Effect": "Allow",
  "Action": ["secretsmanager:GetSecretValue"],
  "Resource": "arn:aws:secretsmanager:eu-central-1:123456789012:secret:orders/prod/db-*"
},
{
  "Effect": "Allow",
  "Action": ["ssm:GetParametersByPath", "ssm:GetParameter"],
  "Resource": "arn:aws:ssm:eu-central-1:123456789012:parameter/orders/prod/*"
},
{
  "Effect": "Allow",
  "Action": ["kms:Decrypt"],
  "Resource": "arn:aws:kms:eu-central-1:123456789012:key/1111-2222-...",
  "Condition": { "StringEquals": { "kms:ViaService": "secretsmanager.eu-central-1.amazonaws.com" } }
}
```

The KMS condition allows decrypting only through Secrets Manager, not arbitrary direct KMS calls.

### Rotation with Secrets Manager
* For RDS/Aurora, **managed rotation** changes the password on a schedule (e.g. every 30 days). The **alternating users** strategy rotates between two DB users so existing connections keep working while the other user's password changes.
* Applications must re-read secrets: cache with a refresh interval (AWS Secrets Manager caching client for Java, or Spring Cloud AWS refresh) and handle authentication failures by refetching.
* HikariCP: set `maxLifetime` shorter than the rotation grace period so old connections are recycled with new credentials.

### Containers and Lambda
* **ECS**: `secrets` in the task definition inject values from Secrets Manager/Parameter Store as env vars at task start (restart tasks to pick up rotations).
* **EKS**: External Secrets Operator or the Secrets Store CSI driver (AWS provider) sync/mount secrets; Pod Identity/IRSA for IAM.
* **Lambda**: Parameters and Secrets Lambda Extension caches values locally over HTTP (`localhost:2773`), avoiding SDK calls on every invocation.

## 🔴 Senior Level

### KMS and envelope encryption
KMS encrypts at most 4 KB directly; for real data use **envelope encryption**:

```java
GenerateDataKeyResponse dk = kms.generateDataKey(r -> r.keyId(KEY_ARN).keySpec(DataKeySpec.AES_256)
        .encryptionContext(Map.of("tenant", tenantId)));                 // binds ciphertext to context

SecretKey dataKey = new SecretKeySpec(dk.plaintext().asByteArray(), "AES");
byte[] iv = new byte[12];
SECURE_RANDOM.nextBytes(iv);
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, dataKey, new GCMParameterSpec(128, iv));
cipher.updateAAD(tenantId.getBytes(StandardCharsets.UTF_8));
byte[] ciphertext = cipher.doFinal(plaintext);

store(ciphertext, iv, dk.ciphertextBlob().asByteArray());              // keep the ENCRYPTED data key with the data
// discard dk.plaintext() — decrypt later with kms.decrypt(ciphertextBlob, sameEncryptionContext)
```

The **AWS Encryption SDK** implements this (key commitment, caching of data keys, multi-key wrapping) — prefer it to hand-rolled crypto. **Encryption context** is authenticated metadata: decryption fails if it differs, and it appears in CloudTrail for auditing.

### Key management decisions
* **AWS managed keys** (`aws/s3`, `aws/rds`) — zero effort, limited control.
* **Customer managed keys (CMK)** — your key policies, grants, automatic yearly rotation (or custom periods), cross-account sharing, ability to disable/schedule deletion (7–30 day waiting period — deleting a key makes its data unrecoverable).
* **Multi-Region keys** for data replicated across regions (same key material, different regions).
* **External key store / CloudHSM** for regulatory requirements to control key material.
* Per-tenant keys enable **crypto-shredding** (delete the key → that tenant's data is unreadable).

### Operational gotchas
* KMS request quotas (thousands to tens of thousands per second per region depending on key type and operation) — high-throughput encryption needs data-key caching.
* Parameter Store standard tier has a lower throughput limit (`GetParameter` TPS) — bulk fetch with `GetParametersByPath` at startup and cache; enable higher throughput if needed.
* Secret values in CloudFormation/Terraform state: use dynamic references or generate secrets in Secrets Manager rather than passing plaintext through IaC.
* Audit with CloudTrail: alert on `GetSecretValue` from unexpected principals and on KMS key policy changes or scheduled deletions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Parameter Store holds hierarchical configuration and SecureString secrets cheaply; Secrets Manager adds automatic rotation, replication and resource policies for credentials; KMS manages encryption keys and powers envelope encryption for everything else. Apps read them via IAM roles — Spring Cloud AWS `spring.config.import`, ECS secrets, the CSI driver or the Lambda extension — with caching and refresh for rotation, least-privilege policies and CloudTrail auditing.

**Must know:**
* When to use each service.
* `spring.config.import=aws-parameterstore:` / `aws-secretsmanager:`.
* Rotation strategies (alternating users) and app refresh + Hikari `maxLifetime`.
* Envelope encryption, encryption context, AWS Encryption SDK.
* AWS managed vs customer managed keys; deletion waiting period; quotas.

**Common follow-ups:**
* How does an app pick up a rotated DB password?
* Why not encrypt files directly with KMS?
* How would you implement crypto-shredding per tenant?

**Red flags:** secrets in task definition environment variables as plaintext; one IAM policy granting `secretsmanager:*`; hand-rolled AES without authenticated encryption.
