# ElastiCache

---

## 🟢 Junior Level

**Amazon ElastiCache** is AWS's managed in-memory cache service, running **Redis OSS**, **Valkey** (the open-source Redis fork) or **Memcached**. AWS provisions nodes, handles patching, monitoring, backups (Redis/Valkey), failover and scaling; you connect with standard clients (Lettuce, Jedis, Redisson).

| | Redis OSS / Valkey | Memcached |
| --- | --- | --- |
| Data structures | Strings, hashes, lists, sets, sorted sets, streams, … | Strings only |
| Replication & failover | Yes (replicas, Multi-AZ automatic failover) | No |
| Persistence/backups | Snapshots | No |
| Sharding | Cluster mode (up to hundreds of shards) | Client-side across nodes |
| Threads | Mostly single-threaded command execution (I/O threads help) | Multi-threaded |
| Typical use | Caching, sessions, rate limits, leaderboards, locks, queues | Simple, large, ephemeral object caches |

There's also **ElastiCache Serverless** (scales automatically, pay per data stored and ECPUs consumed) and **MemoryDB** (Redis-compatible with durable, multi-AZ transaction log — usable as a primary database).

### Connecting from Spring Boot

```yaml
spring:
  data:
    redis:
      host: my-cache.xxxxxx.euc1.cache.amazonaws.com   # configuration endpoint (cluster mode)
      port: 6379
      ssl:
        enabled: true                                   # in-transit encryption
      password: ${REDIS_AUTH_TOKEN}                     # or IAM authentication
      timeout: 300ms
      cluster:
        nodes: my-cache.xxxxxx.clustercfg.euc1.cache.amazonaws.com:6379
```

## 🟡 Middle Level

### Network and security
* ElastiCache lives **inside your VPC**; it's not reachable from the internet. Allow access via **security groups** (app security group → cache security group on port 6379).
* Enable **in-transit encryption** (TLS) and **at-rest encryption**; use **AUTH tokens** or **IAM authentication** (Redis 7+/Valkey) with RBAC user groups for least privilege per application.
* Put nodes in **subnets across multiple AZs** and enable **Multi-AZ** with automatic failover for production.

### Topologies (Redis OSS/Valkey)
* **Cluster mode disabled**: one primary + up to 5 replicas; vertical scaling; all keys on one shard. Use the **primary endpoint** for writes and the **reader endpoint** for replica reads.
* **Cluster mode enabled**: data sharded across up to 500 shards; online resharding; clients must be cluster-aware (Lettuce with topology refresh) and use the configuration endpoint.

### Client settings that matter on AWS
* **Topology refresh** (Lettuce adaptive refresh) so failovers and resharding are picked up quickly.
* Short **command timeouts** and fast-fail when disconnected — caches should degrade to the database, not stall requests.
* Connection count: each app pod opens connections to each shard; thousands of pods × shards can exceed node limits — Lettuce's connection multiplexing helps.

## 🔴 Senior Level

### Failover behavior and testing
On primary failure, ElastiCache promotes a replica (typically tens of seconds) and updates DNS for the primary endpoint. Clients must:
* respect short DNS TTLs (JVM `networkaddress.cache.ttl`), or use cluster topology discovery,
* handle `READONLY`/`MOVED` errors and reconnect,
* tolerate lost writes acknowledged only by the old primary (async replication).

Use the **Test Failover** API in staging under load to verify application recovery time and error behavior.

### Sizing and memory management
* Choose node types by **memory** (dataset + replication buffers + overhead; keep ~25% headroom for `reserved-memory-percent` and fragmentation) and **network bandwidth** (large values saturate NICs before CPU).
* Set `maxmemory-policy` for cache use cases (`allkeys-lfu` or `allkeys-lru`; default on ElastiCache is `volatile-lru`, which evicts only keys with TTLs — a common surprise when keys without TTL fill memory and writes fail).
* Monitor CloudWatch: `EngineCPUUtilization` (the Redis thread) rather than host `CPUUtilization`, `DatabaseMemoryUsagePercentage`, `Evictions`, `CurrConnections`, `ReplicationLag`, `CacheHitRate`.

### Cost and alternatives
* Reserved nodes for steady clusters; Graviton node types are cheaper per GB; Valkey engine pricing is lower than Redis OSS on ElastiCache.
* Serverless for spiky or unknown workloads; provisioned clusters for steady, high-throughput ones (serverless ECPU pricing can be expensive at constant high load).
* A local in-process cache (Caffeine) in front of ElastiCache for hot keys can cut both latency and cache cost dramatically.

## 🎯 Interview Cheat Sheet

**30-second pitch:** ElastiCache is AWS's managed Redis OSS/Valkey or Memcached inside your VPC. For production I use Redis/Valkey with Multi-AZ automatic failover, cluster mode for scale, TLS and IAM or AUTH-token authentication, security groups for access, and cluster-aware clients with topology refresh and short timeouts. I size by memory and bandwidth, set an `allkeys-*` eviction policy for caches, and watch engine CPU, memory, evictions and hit rate.

**Must know:**
* Redis/Valkey vs Memcached; Serverless; MemoryDB for durability.
* VPC-only, security groups, TLS, IAM auth.
* Cluster mode disabled vs enabled; endpoints.
* Failover mechanics; Test Failover; DNS TTL.
* `maxmemory-policy` default pitfall; key CloudWatch metrics.

**Common follow-ups:**
* Writes fail with OOM errors although it's "just a cache" — why?
* How do you connect a Lambda to ElastiCache?
* When would you choose MemoryDB?

**Red flags:** public endpoints; no Multi-AZ in production; `volatile-lru` with keys lacking TTLs.
