# ECS Fargate EKS and Elastic Beanstalk

---

## 🟢 Junior Level

AWS offers several ways to run a containerized (or plain JAR) Java service. They differ in **how much you manage**:

| Option | What it is | You manage | Good for |
| --- | --- | --- | --- |
| **Elastic Beanstalk** | PaaS: upload a JAR or Docker image, Beanstalk provisions EC2, load balancer, auto scaling | Application + some config | Simple apps, small teams, quick start |
| **ECS on EC2** | AWS's own container orchestrator; tasks run on EC2 instances you provide | Instances (AMIs, patching, capacity) + tasks | Cost control, special instance needs |
| **ECS on Fargate** | ECS without servers: each task gets its own managed micro-VM | Tasks only (CPU/memory, image, IAM role) | Most container services on AWS with minimal ops |
| **EKS** | Managed Kubernetes control plane; nodes via managed node groups, Karpenter, or Fargate | Kubernetes resources, add-ons, (nodes) | Kubernetes portability, ecosystem (Helm, operators, service mesh), large platforms |
| **App Runner** | Fully managed web service from an image or repo | Almost nothing | Simple HTTP services, prototypes |

### ECS vocabulary
* **Task definition** — image(s), CPU/memory, ports, environment, secrets, IAM **task role**, logging.
* **Service** — keeps N tasks running, integrates with load balancers, does rolling or blue/green deployments.
* **Cluster** — logical grouping; capacity from Fargate or EC2 capacity providers.

## 🟡 Middle Level

### ECS Fargate task definition (excerpt)

```json
{
  "family": "orders",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "1024",
  "memory": "2048",
  "runtimePlatform": { "cpuArchitecture": "ARM64", "operatingSystemFamily": "LINUX" },
  "taskRoleArn": "arn:aws:iam::123456789012:role/orders-task",
  "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole",
  "containerDefinitions": [{
    "name": "orders",
    "image": "123456789012.dkr.ecr.eu-central-1.amazonaws.com/orders@sha256:3f2a...",
    "portMappings": [{ "containerPort": 8080 }],
    "environment": [{ "name": "JAVA_TOOL_OPTIONS", "value": "-XX:MaxRAMPercentage=75" }],
    "secrets": [{ "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:eu-central-1:123456789012:secret:orders-db" }],
    "healthCheck": { "command": ["CMD-SHELL", "curl -f http://localhost:8080/actuator/health/liveness || exit 1"] },
    "logConfiguration": { "logDriver": "awslogs", "options": {
        "awslogs-group": "/ecs/orders", "awslogs-region": "eu-central-1", "awslogs-stream-prefix": "orders" } }
  }]
}
```

* **Task role** = permissions for your app (DynamoDB, S3); **execution role** = permissions for ECS to pull the image and read secrets.
* `awsvpc` gives each task its own ENI and security group — fine-grained network control.
* Graviton (`ARM64`) is typically ~20% cheaper; build multi-arch images.

### ECS vs EKS decision
* Choose **ECS (Fargate)** when you're all-in on AWS, want simplicity, and don't need Kubernetes-specific tooling. Fewer moving parts, no cluster upgrades, deep AWS integration.
* Choose **EKS** when you need Kubernetes portability, the CNCF ecosystem (Argo CD, Istio, operators like Strimzi/CloudNativePG), many teams on a shared platform, or multi-cloud consistency — and you have (or will build) a platform team to run it.

## 🔴 Senior Level

### Operational details that matter for Java
* **Memory**: set the JVM heap relative to the task/pod limit (`-XX:MaxRAMPercentage=70–75`) and leave room for metaspace, thread stacks, direct buffers and the OS; exceeding the limit gets the container OOM-killed (exit code 137) without a Java `OutOfMemoryError`.
* **CPU**: Fargate CPU is a hard allocation; on EKS, CPU *limits* cause CFS throttling and latency spikes during GC/JIT — many teams set requests but no CPU limits for latency-sensitive JVMs. Java ≥ 11 reads container CPU quotas for `availableProcessors()`, which sizes GC threads and common pools.
* **Startup**: Fargate tasks pull the full image each start (no node cache), so big images slow scaling; use slim JRE images, layered JARs, and consider **Seekable OCI (SOCI)** lazy loading on Fargate.
* **Health checks**: ALB target group health checks + ECS container health checks (or Kubernetes probes) pointing at Actuator liveness/readiness; set `healthCheckGracePeriodSeconds` for slow starts.

### Scaling
* **ECS Service Auto Scaling**: target tracking on CPU, memory, or ALB `RequestCountPerTarget`; step scaling on custom CloudWatch metrics (queue depth).
* **EKS**: HPA (CPU/memory/custom metrics via Prometheus Adapter or KEDA for queue-based scaling) + **Karpenter** for fast, right-sized node provisioning (including Spot and Graviton).
* **Spot capacity** (Fargate Spot / EC2 Spot) for fault-tolerant workloads with graceful shutdown handling (2-minute interruption notice → SIGTERM).

### Deployments
* ECS: rolling updates with **deployment circuit breaker** (auto-rollback on failing tasks), or **blue/green** via CodeDeploy with traffic shifting and alarms.
* EKS: Kubernetes rolling updates, Argo Rollouts/Flagger canaries, GitOps with Argo CD/Flux.
* Elastic Beanstalk: rolling, immutable, and traffic-splitting deployment policies — fine for simple apps, but configuration drift and limited flexibility push growing teams to ECS/EKS.

### Cost comparison sketch
Fargate charges per vCPU-hour and GB-hour of task size (simple, no idle node waste, but a premium per unit); EC2-backed ECS/EKS is cheaper at high, steady utilization if you bin-pack well (and use Savings Plans/Spot); EKS adds a control-plane fee per cluster. Compute Savings Plans apply to Fargate, EC2 and Lambda alike.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Elastic Beanstalk is a simple PaaS, ECS is AWS's native orchestrator — on EC2 or serverless on Fargate — and EKS is managed Kubernetes. I'd default to ECS on Fargate for AWS-only teams wanting minimal operations, and EKS when Kubernetes portability and ecosystem matter and a platform team exists. For Java I size the heap relative to the container limit, watch CPU throttling, keep images slim for fast scaling, use task roles for IAM, and enable deployment circuit breakers or canaries.

**Must know:**
* Beanstalk vs ECS (EC2/Fargate) vs EKS vs App Runner.
* Task definition, service, task role vs execution role, `awsvpc`.
* JVM memory/CPU in containers; exit 137.
* Scaling: target tracking, HPA, KEDA, Karpenter, Spot.
* Deployment options and cost trade-offs.

**Common follow-ups:**
* Why is our Fargate service slow to scale out?
* ECS or EKS for a 5-person team?
* How do containers get AWS credentials?

**Red flags:** `-Xmx` equal to the container memory; static AWS keys in task definitions; picking EKS without anyone to operate it.
