# Lambda and serverless Java

---

## 🟢 Junior Level

**AWS Lambda** runs your code in response to events — HTTP requests via API Gateway, SQS messages, S3 uploads, EventBridge rules, DynamoDB Streams — without managing servers. You pay per request and per millisecond of execution × memory; scaling is automatic, down to zero.

```java
// Plain handler: smallest dependency footprint
public class ThumbnailHandler implements RequestHandler<S3Event, Void> {
    private static final S3Client S3 = S3Client.create();            // created once per execution environment

    @Override
    public Void handleRequest(S3Event event, Context ctx) {
        event.getRecords().forEach(r -> {
            String bucket = r.getS3().getBucket().getName();
            String key = r.getS3().getObject().getUrlDecodedKey();
            ctx.getLogger().log("processing " + bucket + "/" + key);
            createThumbnail(bucket, key);
        });
        return null;
    }
}
```

### Lifecycle
1. **Cold start** — Lambda creates an execution environment, downloads your package, starts the JVM, loads classes and runs static initialization.
2. **Warm invocations** — the same environment handles further requests (one at a time per environment); static fields (SDK clients, connection pools) are reused.
3. Environments are frozen between invocations and eventually recycled.

Java's cold start (JVM startup + class loading + framework init) is the main challenge: plain Java ~0.5–1 s, Spring Boot without tuning several seconds.

## 🟡 Middle Level

### Reducing cold starts
* **SnapStart** (Java 11+ managed runtimes): Lambda snapshots the initialized execution environment (Firecracker microVM memory) after `init` and restores from it — cold starts drop to a few hundred ms. Make code snapshot-safe: re-seed randomness, refresh credentials/connections after restore using CRaC hooks (`org.crac.Resource.afterRestore`), avoid caching time-sensitive values during init.
* **Small deployment package**: avoid fat frameworks; use the AWS SDK v2 with only the needed modules, `UrlConnectionHttpClient` or AWS CRT client instead of Netty, exclude unused dependencies.
* **Tiered compilation tuning**: `JAVA_TOOL_OPTIONS=-XX:+TieredCompilation -XX:TieredStopAtLevel=1` speeds startup for short functions.
* **More memory = more CPU**: Lambda allocates CPU proportional to memory; 1,769 MB ≈ 1 vCPU. Init and execution often get *cheaper* overall with more memory.
* **GraalVM native image** (custom runtime) for ~100 ms cold starts, at the cost of build complexity and reflection configuration (Spring Boot 3 AOT, Quarkus, Micronaut support it).
* **Provisioned concurrency** keeps environments warm (pay for them continuously) for latency-critical APIs.

### Spring on Lambda
* **Spring Cloud Function** with the AWS adapter: write `Function<Order, Receipt>` beans; the adapter maps events.
* **AWS Serverless Java Container** runs existing Spring Boot REST controllers behind API Gateway.
* Use SnapStart or native images with Spring; keep the context small (no unnecessary auto-configuration).

### Event source behavior
* **SQS**: Lambda polls, batches up to 10,000 messages (with batching window), scales concurrency; return **partial batch failures** (`SQSBatchResponse`) so only failed messages are retried.
* **API Gateway**: synchronous; 29 s default integration timeout (raisable for REST/regional APIs in recent updates — check quotas).
* **Async invocations** (S3, EventBridge): Lambda retries twice; configure **on-failure destinations**/DLQ.

## 🔴 Senior Level

### Concurrency and downstream protection
* Each concurrent request uses its own environment; a burst can create thousands of environments within seconds → thousands of **database connections**. Use **RDS Proxy** (connection pooling and IAM auth for RDS/Aurora), DynamoDB (HTTP-based, no connections), or limit with **reserved concurrency** per function.
* Account-level concurrency quota (default 1,000 per region, raisable) is shared by all functions — set reserved concurrency for critical ones so a noisy function can't starve them.
* Scaling rate limits: Lambda adds concurrency per function at a bounded rate (1,000 additional environments every 10 seconds per function under the current scaling model); plan for spikes.

### Idempotency and retries
At-least-once invocation semantics (async retries, SQS redelivery) mean handlers must be idempotent. **Powertools for AWS Lambda (Java)** provides idempotency (DynamoDB-backed), structured logging with correlation IDs, metrics via CloudWatch EMF, and tracing helpers.

### Cost model
Cost ≈ requests × $0.20/M + GB-seconds × price. A function with 1 GB memory running 200 ms costs ~0.2 GB-s per call; at sustained high throughput (hundreds of req/s 24/7), containers on Fargate/EKS are usually cheaper than Lambda. Lambda wins for spiky, event-driven, low-to-medium volume workloads and glue code. Graviton (arm64) functions are ~20% cheaper per GB-s.

### When not to use Lambda for Java
* Long-running work (> 15 min hard limit) → ECS/Fargate, Batch, Step Functions orchestration.
* Steady high-throughput APIs with tight p99 latency and large frameworks → containers.
* Workloads needing large local state, persistent connections (WebSockets → API Gateway WebSocket APIs can help), or GPUs.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Lambda runs code per event with automatic scaling and per-millisecond billing. For Java the main issue is cold start, which I reduce with SnapStart plus snapshot-safe init, small packages, more memory, tiered-compilation tuning, native images or provisioned concurrency. I reuse SDK clients across invocations, return partial batch failures for SQS, make handlers idempotent, protect databases with RDS Proxy and reserved concurrency, and choose containers instead for long-running or steady high-throughput work.

**Must know:**
* Init vs invoke; static reuse across warm invocations.
* SnapStart, CRaC restore hooks; memory ↔ CPU.
* Spring Cloud Function / Serverless Java Container.
* SQS partial batch response; async retries + destinations.
* Concurrency limits, RDS Proxy, Powertools idempotency, cost break-even.

**Common follow-ups:**
* How do you connect Lambda to PostgreSQL at scale?
* Why did increasing memory make it cheaper?
* What breaks with SnapStart?

**Red flags:** opening a DB connection per invocation without a proxy; huge Spring Boot fat JARs without SnapStart; non-idempotent handlers.
