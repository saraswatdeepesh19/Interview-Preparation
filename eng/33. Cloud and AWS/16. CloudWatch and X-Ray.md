# CloudWatch and X-Ray

---

## 🟢 Junior Level

* **Amazon CloudWatch** — AWS's monitoring service: **metrics** (from AWS services and your apps), **logs** (CloudWatch Logs), **alarms**, **dashboards**, plus features like Logs Insights queries, Synthetics canaries, RUM, Container Insights and Application Signals.
* **AWS X-Ray** — distributed tracing for requests across Lambda, API Gateway, ECS/EKS services, SDK calls to DynamoDB/SQS/S3 and your own code. Increasingly used through **OpenTelemetry** (AWS Distro for OpenTelemetry, ADOT) and surfaced in CloudWatch.

### Built-in metrics you get for free (examples)
* Lambda: `Invocations`, `Errors`, `Duration`, `Throttles`, `ConcurrentExecutions`.
* ALB: `RequestCount`, `TargetResponseTime`, `HTTPCode_Target_5XX_Count`.
* RDS: `CPUUtilization`, `DatabaseConnections`, `FreeableMemory`, `ReadLatency`.
* SQS: `ApproximateAgeOfOldestMessage`, `ApproximateNumberOfMessagesVisible`.

### An alarm (CDK, Java)

```java
Alarm.Builder.create(this, "Orders5xx")
        .metric(alb.getMetrics().httpCodeTarget(HttpCodeTarget.TARGET_5XX_COUNT,
                MetricOptions.builder().period(Duration.minutes(1)).statistic("Sum").build()))
        .threshold(50)
        .evaluationPeriods(3)
        .datapointsToAlarm(2)                               // 2 of 3 minutes over threshold
        .treatMissingData(TreatMissingData.NOT_BREACHING)
        .build()
        .addAlarmAction(new SnsAction(onCallTopic));
```

## 🟡 Middle Level

### Application metrics from Spring Boot
* **Micrometer CloudWatch registry** (`micrometer-registry-cloudwatch2`) publishes meters via `PutMetricData` on a step interval — simple, but each metric/dimension combination is billed as a custom metric.
* **Embedded Metric Format (EMF)**: write structured JSON logs; CloudWatch extracts metrics asynchronously — cheaper and no API calls from the app (Powertools for Lambda uses it).
* Or keep **Prometheus** (Amazon Managed Service for Prometheus + Managed Grafana), common for EKS.

### Logs and Logs Insights
Ship JSON logs (stdout → awslogs driver / Fluent Bit / CloudWatch agent). Query them:

```text
fields @timestamp, level, message, traceId, uri, durationMs
| filter level = "ERROR" and service = "orders"
| stats count(*) as errors by bin(5m), exception
| sort errors desc
```

Set **retention** per log group (never "never expire" by default) and use subscription filters to stream to OpenSearch or S3 for long-term analysis.

### Tracing with ADOT / X-Ray
* Lambda: enable active tracing (X-Ray) or the ADOT Lambda layer.
* ECS/EKS: run the **ADOT Collector** (sidecar or DaemonSet); apps use the OpenTelemetry Java agent exporting OTLP to the collector, which exports to X-Ray (and optionally other backends).
* Propagation: X-Ray uses the `X-Amzn-Trace-Id` header; OTel uses W3C `traceparent` — configure the propagators (`otel.propagators=tracecontext,baggage,xray`) when mixing.

## 🔴 Senior Level

### Alarm design on AWS
* Prefer **SLO-style alarms**: metric math for error ratios (`5xx / RequestCount`), latency percentiles (`p99` statistics on `TargetResponseTime`), and **composite alarms** to combine symptoms and suppress noise (page only if error ratio high AND request count meaningful).
* **Anomaly detection** bands for metrics with seasonality (traffic), but keep static thresholds for hard limits.
* Use **M of N datapoints** to avoid flapping; set `TreatMissingData` deliberately (missing data from a crashed service should alarm, not be ignored).
* **CloudWatch Application Signals** (SLOs and service maps from OTel data) and **Synthetics canaries** for user-journey checks from outside.

### Cost control
CloudWatch costs come mainly from:
* **Custom metrics** (per metric per month; high-cardinality dimensions explode cost — don't put user IDs or full paths in dimensions),
* **Log ingestion** (per GB) and storage — DEBUG logs in production are expensive; sample, reduce verbosity, use Infrequent Access log class for less-queried logs,
* **Logs Insights** scanned data, **GetMetricData** API calls by dashboards/tools,
* **X-Ray traces** recorded/scanned — use sampling rules (centralized in X-Ray, e.g. 1 request/s reservoir + 5%).

### Cross-account observability
Organizations centralize monitoring with **CloudWatch cross-account observability** (a monitoring account linked to source accounts) so on-call engineers see metrics, logs and traces across accounts in one place.

### Correlation
Include `traceId` in logs (OTel agent MDC injection), link X-Ray traces to log groups, and add deployment annotations; during incidents, jump from an alarm → dashboard → trace → logs of the same request.

## 🎯 Interview Cheat Sheet

**30-second pitch:** CloudWatch provides AWS and custom metrics, logs with Logs Insights, alarms and dashboards; X-Ray — today usually fed via OpenTelemetry and the ADOT Collector — provides distributed tracing. I publish app metrics via Micrometer or EMF, ship structured logs with retention policies, build SLO-style alarms with metric math, percentiles and composite alarms, and keep costs down by limiting metric cardinality, log volume and trace sampling.

**Must know:**
* Key built-in metrics for Lambda, ALB, RDS, SQS.
* Micrometer CloudWatch registry vs EMF vs Prometheus.
* Logs Insights queries; log retention.
* ADOT Collector, OTel agent, X-Ray propagation header.
* Composite alarms, M of N, missing data handling, cost drivers.

**Common follow-ups:**
* Why is our CloudWatch bill higher than our EC2 bill?
* How do you trace a request from API Gateway through Lambda to DynamoDB?
* How do you avoid noisy alarms?

**Red flags:** log groups with infinite retention and DEBUG logs; per-user metric dimensions; alarms on single datapoints.
