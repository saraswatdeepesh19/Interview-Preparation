# Cloud cost optimization and FinOps

---

## 🟢 Junior Level

Cloud bills grow quietly: every forgotten instance, oversized database, verbose log and cross-zone byte costs money. **FinOps** is the practice of making engineering, finance and product share responsibility for cloud spend — with visibility, accountability and continuous optimization — so cost becomes an engineering metric like latency.

### The biggest levers (usually in this order)
1. **Turn off what you don't use** — idle dev environments at night, orphaned volumes/snapshots, unattached Elastic IPs, old load balancers.
2. **Right-size** — most instances and containers are over-provisioned (CPU at 10%).
3. **Commitment discounts** — Savings Plans and Reserved Instances (up to ~70% off on-demand for steady workloads).
4. **Spot capacity** for fault-tolerant workloads (up to ~90% off).
5. **Architecture choices** — data transfer, storage classes, managed vs self-run, serverless vs always-on.

### Visibility first
* **Tag everything** (`team`, `service`, `environment`, `cost-center`) and activate cost allocation tags; enforce with tag policies / IaC checks.
* **AWS Cost Explorer**, **Cost and Usage Report (CUR)** queried with Athena, **Budgets** with alerts, **Cost Anomaly Detection**.
* Show each team **their** cost per service per month (showback/chargeback) and **unit costs** (cost per order, per active user).

## 🟡 Middle Level

### Compute
* **Right-size** with Compute Optimizer recommendations and real utilization (p95 CPU/memory over weeks). For JVM services, size memory from heap-after-GC plus overhead, not peak RSS during startup.
* **Graviton (ARM)** instances/containers/Lambda: typically ~20% cheaper with similar or better performance for Java (Temurin and Corretto ship ARM builds; build multi-arch images).
* **Savings Plans**: Compute Savings Plans apply across EC2, Fargate and Lambda; commit to a baseline $/hour you're sure to use, leave peaks on-demand/Spot.
* **Spot**: batch jobs, CI runners, stateless services with enough replicas and graceful shutdown; diversify instance types (Karpenter, EC2 Fleet).
* **Autoscaling to zero** for non-production (scheduled scale-down, Karpenter consolidation, Lambda/Fargate for spiky internal tools).

### Data and storage
* **S3 storage classes and lifecycle policies**: Standard → Standard-IA → Glacier Instant/Flexible/Deep Archive based on access; **Intelligent-Tiering** for unknown patterns; expire old versions and incomplete multipart uploads.
* **EBS**: gp3 instead of gp2 (cheaper, independently provisioned IOPS/throughput); delete unattached volumes and old snapshots.
* **Databases**: right-size RDS/Aurora instances, use Aurora Serverless v2 for spiky workloads, reserved instances for steady ones, read replicas only when used; archive cold data instead of keeping it on expensive primary storage.
* **Logs and metrics**: retention policies, sampling, lower log levels, Infrequent Access log class — observability can become 10–20% of the bill.

### Network (the hidden cost)
* **Inter-AZ traffic** is billed in both directions; chatty services across AZs, Kafka replication and cross-AZ load balancing add up. Use topology-aware routing where safe.
* **NAT Gateway** processing charges per GB: use **VPC gateway endpoints** for S3 and DynamoDB (free) and interface endpoints for other AWS services with heavy traffic.
* **Internet egress**: CloudFront in front of origins reduces egress cost and latency.

## 🔴 Senior Level

### Engineering for cost (architecture-level)
* **Unit economics**: track cost per business transaction (e.g. $0.0021 per order). It reveals inefficiency regardless of growth and lets you evaluate features ("search suggestions cost $4k/month — worth it?").
* **Efficiency work as backlog items** with expected savings, just like performance work: removing N+1 queries reduces DB size; caching reduces DynamoDB RCUs; batching reduces SQS/Lambda requests; compression reduces egress.
* **Serverless vs containers break-even**: Lambda is cheap at low/spiky utilization; for steady high throughput, containers on Savings Plans win. Re-evaluate as traffic changes.
* **Managed services trade money for people time**: self-hosting Kafka or Elasticsearch on EC2 can look cheaper on the invoice but cost more in engineering and incidents. Include operational cost in decisions.
* **Multi-AZ/multi-region is a business decision**: active-active doubles cost; match it to the actual availability requirement per service.

### FinOps operating model
* **Inform** (visibility, allocation, forecasting) → **Optimize** (rates and usage) → **Operate** (governance, continuous improvement) — the FinOps Foundation lifecycle.
* Central team manages commitments (Savings Plans portfolio, coverage and utilization targets) and tooling; product teams own usage optimization for their services.
* Guardrails: Service Control Policies to block expensive instance families in sandbox accounts, budgets per account with automated actions, IaC policy checks (Infracost in PRs shows the cost delta of a Terraform change).

```text
Infracost PR comment (example):
  + aws_db_instance.orders (db.r6g.2xlarge -> db.r6g.4xlarge)   +$812/month
  Monthly cost will increase by $812 (+14%)
```

### Common anti-patterns
* Cost reviews once a year; nobody owns the bill.
* Buying 3-year reservations for workloads that will be re-architected.
* Optimizing tiny line items while a 40% data transfer cost goes unnoticed.
* Turning off redundancy in production to save money without discussing the availability trade-off.

## 🎯 Interview Cheat Sheet

**30-second pitch:** FinOps makes cloud cost a shared, measured engineering concern. I start with visibility — tagging, cost allocation, budgets, anomaly detection and unit costs — then remove waste, right-size (including Graviton), cover the steady baseline with Savings Plans, use Spot for tolerant workloads, and fix architecture-level costs like storage tiers, log volume, NAT and cross-AZ data transfer. Cost changes are visible in PRs and owned by the teams that cause them.

**Must know:**
* Tagging and allocation; Cost Explorer, CUR, Budgets, anomaly detection.
* Right-sizing, Graviton, Savings Plans vs RIs, Spot.
* S3 lifecycle/Intelligent-Tiering, gp3, log retention.
* NAT and inter-AZ data transfer; VPC endpoints; CloudFront.
* Unit economics; FinOps lifecycle; Infracost.

**Common follow-ups:**
* Our bill doubled last month — how do you find out why?
* When would you not buy Savings Plans?
* Why is our NAT Gateway so expensive?

**Red flags:** no tags; no owner for spend; ignoring data transfer; cutting redundancy without a decision.
