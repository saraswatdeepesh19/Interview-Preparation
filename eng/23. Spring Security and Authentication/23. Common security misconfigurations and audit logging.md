# Common security misconfigurations and audit logging

---

## 🟢 Junior Level

Many breaches don't need clever exploits — they use **misconfigurations**: an exposed admin endpoint, a default password, verbose errors, a public storage bucket. **Audit logging** is how you find out who did what, and whether something went wrong.

### Top misconfigurations in Spring Boot apps
* **Actuator exposed publicly** — `/actuator/env` (configuration), `/actuator/heapdump` (memory with secrets and tokens), `/actuator/loggers` (change log levels), `/actuator/shutdown`.
* **`permitAll()` too broad** — a matcher like `/api/**` added "temporarily".
* **CSRF disabled** in a cookie-session application.
* **Stack traces and SQL errors returned** to clients.
* **Default or shared credentials** for databases, admin consoles (H2 console enabled in production!).
* **Debug features left on**: Swagger UI with "try it out" against production, `spring.devtools` on the classpath, `logging.level.root=DEBUG` logging request bodies.

### Safe actuator baseline

```yaml
management:
  server:
    port: 8081                         # separate port, not routed through the public ingress
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      show-details: when-authorized
server:
  error:
    include-stacktrace: never
    include-message: never
```

## 🟡 Middle Level

### What to audit
An **audit log** answers *who did what, to which resource, when, from where, and with what result*. Log at least:
* Authentication events: login success/failure, MFA, logout, password reset, token issuance.
* Authorization failures (403s) — patterns reveal probing.
* Privileged actions: role changes, user deletion, configuration changes, data exports, refunds.
* Access to sensitive data (viewing another customer's record as support staff).

### Spring Security events

```java
@Component
class SecurityAuditListener {
    private static final Logger AUDIT = LoggerFactory.getLogger("AUDIT");

    @EventListener
    void onSuccess(AuthenticationSuccessEvent e) {
        AUDIT.info("auth.success principal={}", e.getAuthentication().getName());
    }

    @EventListener
    void onFailure(AbstractAuthenticationFailureEvent e) {
        AUDIT.warn("auth.failure principal={} reason={}", e.getAuthentication().getName(),
                   e.getException().getClass().getSimpleName());
    }

    @EventListener
    void onDenied(AuthorizationDeniedEvent<?> e) {     // requires an AuthorizationEventPublisher bean
        AUDIT.warn("authz.denied principal={} decision={}", e.getAuthentication().get().getName(),
                   e.getAuthorizationDecision());
    }
}
```

`DefaultAuthenticationEventPublisher` is auto-configured; authorization events need `@Bean AuthorizationEventPublisher publisher(ApplicationEventPublisher p) { return new SpringAuthorizationEventPublisher(p); }`.

### Structured, correlated logs

```json
{"ts":"2026-10-16T08:12:45.120Z","type":"audit","action":"refund.created","actor":"support-17",
 "subject":"order/9f2c","result":"success","amount":"49.90","ip":"203.0.113.9",
 "traceId":"4bf92f3577b34da6a3ce929d0e0e4736"}
```

Use JSON logs (Spring Boot 3.4 `logging.structured.format.console=ecs`), include `traceId` from Micrometer Tracing, and ship audit events to a separate index/stream with longer retention.

### Never log
Passwords, full tokens (JWTs, API keys, session IDs), card numbers (PCI DSS), secrets, and unnecessary personal data. Mask or hash identifiers where possible, and beware frameworks logging full request bodies at DEBUG.

## 🔴 Senior Level

### Tamper resistance and integrity
An attacker with admin access will try to delete their traces:
* Ship audit logs off the host immediately (Fluent Bit → SIEM / write-once storage). Local files are not an audit trail.
* Use append-only stores (S3 Object Lock in compliance mode, WORM storage) and restrict delete permissions to a break-glass role.
* For high-assurance domains, chain records with hashes (each entry includes the hash of the previous one) so gaps or edits are detectable.

### Database-level auditing
Application audit logs miss changes made directly in the database (migrations, manual fixes, compromised credentials). Complement them with:
* **Hibernate Envers** — revision tables for entity history (`@Audited`), with a custom `RevisionListener` storing the actor.
* **PostgreSQL** `pgaudit` extension, or CDC (Debezium) into an audit topic.
* Separate DB roles for humans, with session logging for production access.

### Detecting misconfigurations automatically
* **Policy as code** in CI: Checkov/tfsec for Terraform, kube-score/Kyverno/OPA Gatekeeper for Kubernetes (no `privileged`, read-only root filesystem, no secrets in env vars, resource limits set).
* **Spring configuration tests**: assert that `management.endpoints.web.exposure.include` contains only allowed endpoints in the production profile, that `spring.h2.console.enabled` is false, that the `SecurityFilterChain` denies unknown paths.
* **Runtime scanning**: periodic DAST, cloud security posture management (AWS Security Hub, GuardDuty), alert on new public buckets or security group rules opening `0.0.0.0/0`.

### Turning logs into detection
Audit logs are only useful if someone looks. Define alerts:
* N failed logins per account/IP within a window (credential stuffing).
* Authorization denials spike for one principal (IDOR probing).
* Privileged actions outside business hours or from new locations.
* Access to `/actuator/*` from public IPs (should be impossible).
Retention and access to audit logs are themselves regulated (GDPR, SOX, PCI DSS); document them.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The most common real-world security failures are misconfigurations — public actuators, overly broad `permitAll`, verbose errors, debug consoles, default credentials. I lock down management endpoints on a separate port, deny by default, and test configuration in CI. Audit logging records who did what to which resource with what result, in structured, correlated, tamper-resistant logs that feed real alerts — and never contains secrets.

**Must know:**
* Dangerous actuator endpoints: env, heapdump, loggers, shutdown.
* `include-stacktrace: never`, H2 console off, devtools out of prod.
* Spring Security authentication and authorization events.
* Structured JSON logs with trace IDs; separate audit stream.
* Off-host, append-only storage; Envers/pgaudit for DB changes.

**Common follow-ups:**
* What would an attacker do with `/actuator/heapdump`?
* What should never appear in logs?
* How do you prove audit logs weren't modified?

**Red flags:** audit logs only on local disk; logging JWTs "for debugging"; no alerting on authentication failures.
