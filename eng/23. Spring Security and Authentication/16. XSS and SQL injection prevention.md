# XSS and SQL injection prevention

---

## 🟢 Junior Level

Both are **injection** attacks: untrusted input is interpreted as code.

* **SQL injection** — input becomes part of a SQL statement. `' OR '1'='1` turns a login check into "always true"; `'; DROP TABLE users; --` destroys data.
* **XSS (Cross-Site Scripting)** — input becomes part of an HTML page and runs as JavaScript in other users' browsers, stealing sessions or performing actions as them.

### SQL injection: never concatenate

```java
// VULNERABLE
String sql = "select * from users where email = '" + email + "'";
jdbcTemplate.queryForList(sql);

// SAFE: parameters are sent separately from the SQL text
jdbcTemplate.queryForList("select * from users where email = ?", email);

// SAFE with JPA
em.createQuery("select u from User u where u.email = :email", User.class)
  .setParameter("email", email)
  .getResultList();
```

With a **prepared statement**, the database parses the SQL *before* seeing the value, so the value can never change the structure of the query.

### XSS: encode output

```html
<!-- Thymeleaf: th:text escapes HTML (safe) -->
<p th:text="${comment.body}">...</p>

<!-- th:utext renders raw HTML (dangerous with user content) -->
<p th:utext="${comment.body}">...</p>
```

React, Angular and Vue also escape by default; the dangerous escape hatches are `dangerouslySetInnerHTML`, `[innerHTML]`, and `v-html`.

## 🟡 Middle Level

### Places where SQL injection still happens in "safe" stacks
* **Dynamic `ORDER BY` / column names** — identifiers can't be bound as parameters:

```java
// VULNERABLE: sort comes from the query string
String sql = "select * from orders order by " + sort;

// SAFE: allow-list identifiers
private static final Map<String, String> SORTABLE = Map.of("date", "created_at", "total", "total_amount");
String column = Optional.ofNullable(SORTABLE.get(sort)).orElse("created_at");
String sql = "select * from orders order by " + column + " desc";
```

  Spring Data's `Sort` validates property names against the entity, which is why `PageRequest.of(page, size, Sort.by(sort))` is safe for JPA but not for native queries.
* **JPQL/HQL string concatenation** — `createQuery("... where name = '" + name + "'")` is injectable too (HQL injection).
* **Native queries with `@Query(nativeQuery = true)` built from SpEL or string templates.**
* **`LIKE` patterns** — bound parameters are safe, but escape `%` and `_` if users shouldn't use wildcards (a `%%%%`-style input can force full scans).

### XSS types
* **Stored** — malicious script saved in the database (comment, profile name) and shown to others.
* **Reflected** — script in the URL echoed back in the response (`/search?q=<script>...`).
* **DOM-based** — client-side JS writes untrusted data into the DOM (`element.innerHTML = location.hash`).

### Context-aware encoding
HTML body, HTML attributes, JavaScript strings, URLs and CSS each need different encoding. Use the **OWASP Java Encoder**:

```java
import org.owasp.encoder.Encode;

String safeHtml = Encode.forHtml(userInput);
String safeAttr = Encode.forHtmlAttribute(userInput);
String safeJs   = Encode.forJavaScript(userInput);
String safeUrl  = Encode.forUriComponent(userInput);
```

When you must accept rich text (a WYSIWYG editor), **sanitize** with an allow-list (OWASP Java HTML Sanitizer), not a regex blacklist:

```java
PolicyFactory policy = Sanitizers.FORMATTING.and(Sanitizers.LINKS).and(Sanitizers.BLOCKS);
String clean = policy.sanitize(untrustedHtml);
```

## 🔴 Senior Level

### Defense in depth for XSS
1. **Output encoding** by default in templates/frameworks (primary defense).
2. **Content Security Policy** — forbids inline scripts and restricts script sources; with nonces, even an injected `<script>` won't execute:

```java
http.headers(h -> h.contentSecurityPolicy(csp -> csp.policyDirectives(
        "default-src 'self'; script-src 'self' 'nonce-{nonce}'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'")));
```

   (Nonce generation requires a filter that sets a per-request random value and passes it to templates.)
3. **`HttpOnly` cookies** — XSS can't read session cookies via `document.cookie` (it can still make requests as the user, so this limits, not prevents, damage).
4. **Trusted Types** (`require-trusted-types-for 'script'`) in modern browsers block DOM XSS sinks like `innerHTML` unless values pass through a policy.
5. **JSON APIs**: return `Content-Type: application/json` and `X-Content-Type-Options: nosniff` so browsers never interpret JSON as HTML.

### Defense in depth for SQL injection
1. **Parameterized queries everywhere** (JDBC `?`, JPA named parameters, jOOQ bind values, MyBatis `#{}` — never `${}` with user input).
2. **Least-privilege database users** — the application role can't `DROP`, can't read other schemas, and migrations run with a separate role.
3. **Allow-lists for identifiers**, and type-safe query builders (jOOQ, QueryDSL, Criteria API) for dynamic queries.
4. **Static analysis** in CI (SpotBugs + Find Security Bugs `SQL_INJECTION_*`, Semgrep, CodeQL) to catch concatenation.
5. **Monitoring** — WAF rules and database audit logs as detection, not as the main defense.

### Related injection families to mention
* **Second-order SQL injection** — safely stored input later concatenated into a query by a batch job.
* **Expression language injection** — evaluating user input with SpEL (`parser.parseExpression(userInput)`) gives remote code execution; use `SimpleEvaluationContext` and never evaluate untrusted expressions.
* **Log injection / Log4Shell** — untrusted input in log messages interpreted by the logging framework (JNDI lookups in Log4j 2 < 2.15). Keep logging libraries patched and avoid message lookups.
* **Header/CRLF injection** — user input in response headers (`Location`, `Set-Cookie`) without validation.

---

## 🎯 Interview Cheat Sheet

**30-second pitch:** SQL injection is prevented with parameterized queries everywhere, allow-lists for identifiers like sort columns, and least-privilege DB accounts. XSS is prevented with context-aware output encoding by default, allow-list sanitizing for rich text, and defense in depth: CSP with nonces, HttpOnly cookies, correct content types and Trusted Types.

**Must know:**
* Prepared statements separate code from data.
* `ORDER BY`/column names can't be bound — allow-list them.
* Stored, reflected, DOM XSS; `th:text` vs `th:utext`, `dangerouslySetInnerHTML`.
* OWASP Java Encoder / HTML Sanitizer.
* CSP, HttpOnly, nosniff as additional layers.

**Common follow-ups:**
* Is JPA immune to SQL injection?
* How does CSP stop XSS?
* What is second-order injection?

**Red flags:** input "sanitizing" with regex blacklists; escaping SQL manually; trusting front-end validation.
