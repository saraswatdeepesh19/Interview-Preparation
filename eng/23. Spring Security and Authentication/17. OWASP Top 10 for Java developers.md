# OWASP Top 10 for Java developers

---

## 🟢 Junior Level

The **OWASP Top 10** is a regularly updated list of the most critical web application security risks. The 2021 edition:

| # | Risk | One-line Java example |
| --- | --- | --- |
| A01 | Broken Access Control | `GET /api/orders/123` returns another user's order |
| A02 | Cryptographic Failures | Passwords hashed with MD5, TLS disabled internally |
| A03 | Injection | SQL concatenation, SpEL from user input, XSS |
| A04 | Insecure Design | No rate limit on password reset, missing business limits |
| A05 | Security Misconfiguration | Actuator `/env` and `/heapdump` exposed publicly |
| A06 | Vulnerable and Outdated Components | Log4j 2.14 (Log4Shell), old Spring with known CVEs |
| A07 | Identification and Authentication Failures | No brute-force protection, weak session handling |
| A08 | Software and Data Integrity Failures | Unsafe Java deserialization, unsigned build artifacts |
| A09 | Security Logging and Monitoring Failures | No audit log for admin actions, no alerting |
| A10 | Server-Side Request Forgery (SSRF) | Server fetches any user-supplied URL, e.g. cloud metadata |

### The #1 risk in practice: object-level authorization

```java
// VULNERABLE: authenticated, but any user can read any order (IDOR)
@GetMapping("/api/orders/{id}")
OrderDto get(@PathVariable UUID id) {
    return orders.findById(id).map(OrderDto::from).orElseThrow();
}

// FIXED: ownership is part of the query
@GetMapping("/api/orders/{id}")
OrderDto get(@PathVariable UUID id, @AuthenticationPrincipal Jwt jwt) {
    return orders.findByIdAndCustomerId(id, jwt.getSubject()).map(OrderDto::from)
                 .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND)); // 404, don't leak existence
}
```

## 🟡 Middle Level

### Java-specific mitigations per category
* **A01 Access control** — deny by default (`anyRequest().authenticated()` last), method security (`@PreAuthorize("@orderAccess.canRead(#id, authentication)")`), object-level checks in queries, tests for every role per endpoint.
* **A02 Crypto** — `BCryptPasswordEncoder`/`Argon2PasswordEncoder` via `DelegatingPasswordEncoder`; TLS everywhere; AES-GCM for data encryption with keys from a KMS; never `Random` for tokens (use `SecureRandom`).
* **A03 Injection** — parameterized queries, output encoding, no `Runtime.exec` with user input, `SimpleEvaluationContext` for SpEL.
* **A04 Insecure design** — threat modeling, abuse cases ("what if someone calls reset 10,000 times?"), rate limits and quotas.
* **A05 Misconfiguration** — expose only `health`/`info` actuator endpoints publicly (`management.endpoints.web.exposure.include=health,info`), separate management port, no stack traces in responses (`server.error.include-stacktrace=never`), secure defaults in every environment.
* **A06 Components** — Dependabot/Renovate, OWASP Dependency-Check or Snyk in CI, Spring Boot BOM upgrades monthly, SBOM (CycloneDX) per build.
* **A07 Authentication** — delegate to an IdP (OIDC), MFA, account lockout/backoff, session fixation protection (Spring default), short-lived tokens.
* **A08 Integrity** — no native Java deserialization of untrusted data (`ObjectInputStream`); if unavoidable, `ObjectInputFilter` allow-lists (JEP 290/415); Jackson without default typing; signed artifacts and pinned CI actions.
* **A09 Logging** — log authentication events, authorization failures, admin actions with user and correlation ID; never log passwords or tokens; alert on anomalies.
* **A10 SSRF** — allow-list target hosts, resolve and block private/link-local ranges (`169.254.169.254`), disable redirects, use IMDSv2 on AWS.

## 🔴 Senior Level

### SSRF in detail
SSRF is especially dangerous in cloud environments: a server-side URL fetch can reach the instance metadata endpoint and steal IAM credentials (the Capital One breach pattern).

```java
private static final Set<String> ALLOWED_HOSTS = Set.of("images.partner-cdn.com");

byte[] fetchImage(String url) throws Exception {
    URI uri = URI.create(url);
    if (!"https".equals(uri.getScheme()) || !ALLOWED_HOSTS.contains(uri.getHost())) {
        throw new IllegalArgumentException("host not allowed");
    }
    for (InetAddress addr : InetAddress.getAllByName(uri.getHost())) {      // block DNS rebinding to internal IPs
        if (addr.isLoopbackAddress() || addr.isSiteLocalAddress() || addr.isLinkLocalAddress() || addr.isAnyLocalAddress()) {
            throw new IllegalArgumentException("internal address");
        }
    }
    HttpClient client = HttpClient.newBuilder().followRedirects(HttpClient.Redirect.NEVER)
                                  .connectTimeout(Duration.ofSeconds(2)).build();
    return client.send(HttpRequest.newBuilder(uri).timeout(Duration.ofSeconds(5)).build(),
                       HttpResponse.BodyHandlers.ofByteArray()).body();
}
```

Residual risk: DNS can change between check and connect (TOCTOU). Stronger: route outbound fetches through an egress proxy with an allow-list, and enforce network policies so application pods can't reach metadata or internal admin services at all.

### Deserialization (A08)
Native Java serialization executes code during `readObject` via gadget chains in common libraries (Commons Collections, Spring, Groovy). Fixes, in order of strength:
1. Don't accept Java serialized data from untrusted sources (use JSON/Protobuf with explicit schemas).
2. Set a JVM-wide filter: `-Djdk.serialFilter=com.shop.dto.*;!*` or a context-specific `ObjectInputFilter` factory (Java 17).
3. For Jackson polymorphism, use `@JsonTypeInfo(use = Id.NAME)` with registered subtypes or a `BasicPolymorphicTypeValidator`, never `activateDefaultTyping` on untrusted input.

### Making it systematic
* **Threat modeling** per feature (STRIDE) for anything involving money, identity or file handling.
* **ASVS** (Application Security Verification Standard) as a checklist — the Top 10 is an awareness document, not a complete standard.
* **SAST + SCA + DAST** in the pipeline: CodeQL/Semgrep (code), Dependency-Check/Snyk/Trivy (dependencies and images), OWASP ZAP baseline scan against a test deployment.
* **Security tests as unit tests**: an access-control matrix test that calls every endpoint with every role and asserts expected status codes catches most A01 regressions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The OWASP Top 10 lists the most critical web risks; for Java backends the big ones are broken access control (IDOR), injection, misconfiguration such as exposed actuators, vulnerable dependencies, unsafe deserialization and SSRF. I mitigate with deny-by-default authorization and object-level checks, parameterized queries, secure defaults, automated dependency scanning, no native deserialization, and outbound allow-lists.

**Must know:**
* A01 broken access control is #1; IDOR via path IDs.
* Actuator exposure and stack traces as misconfiguration.
* Log4Shell as the canonical A06 example.
* `ObjectInputFilter`, Jackson default typing risks.
* SSRF to cloud metadata; IMDSv2; egress allow-lists.

**Common follow-ups:**
* How do you test access control systematically?
* What would you check first in a security review of a Spring Boot app?
* Top 10 vs ASVS?

**Red flags:** "we're behind a firewall"; returning 403 vs 404 that leaks existence of resources inconsistently; no dependency scanning.
