# CORS configuration

---

## 🟢 Junior Level

Browsers enforce the **same-origin policy**: JavaScript loaded from `https://app.shop.com` may not read responses from `https://api.shop.com` (a different origin = scheme + host + port). **CORS (Cross-Origin Resource Sharing)** is how the *server* tells the browser which other origins are allowed.

```http
GET /api/orders HTTP/1.1
Origin: https://app.shop.com

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.shop.com
Vary: Origin
```

If the header is missing or doesn't match, the request may reach your server, but the **browser hides the response** from the JavaScript and shows a CORS error in the console.

### Key point
CORS is **not** a server-side security mechanism. It protects *users' browsers* from malicious websites reading data with the user's cookies. `curl`, Postman, and other servers ignore CORS entirely.

## 🟡 Middle Level

### Preflight requests
For "non-simple" requests — methods other than GET/HEAD/POST, `Content-Type: application/json`, or custom headers like `Authorization` — the browser first sends an `OPTIONS` **preflight**:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.shop.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.shop.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 3600
Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers
```

Only if the preflight succeeds does the browser send the real `PUT`.

### Spring Security + Spring MVC configuration

```java
@Configuration
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .cors(Customizer.withDefaults())        // use the CorsConfigurationSource bean below
            .csrf(csrf -> csrf.disable())            // stateless token API (see CSRF article)
            .authorizeHttpRequests(a -> a.anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
            .build();
    }

    @Bean
    CorsConfigurationSource corsConfigurationSource(@Value("${app.cors.origins}") List<String> origins) {
        CorsConfiguration cfg = new CorsConfiguration();
        cfg.setAllowedOrigins(origins);                       // exact origins, from configuration
        cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE"));
        cfg.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Request-Id"));
        cfg.setExposedHeaders(List.of("Location", "ETag"));   // readable by JS
        cfg.setAllowCredentials(false);
        cfg.setMaxAge(Duration.ofHours(1));
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", cfg);
        return source;
    }
}
```

**Why `http.cors()` matters:** preflight requests carry no credentials. If CORS is only configured in Spring MVC (`WebMvcConfigurer.addCorsMappings`), Spring Security rejects the unauthenticated `OPTIONS` with 401 *before* MVC ever sees it. Enabling CORS in the security chain puts `CorsFilter` early enough.

## 🔴 Senior Level

### Credentials and wildcards
* `Access-Control-Allow-Origin: *` cannot be combined with `Access-Control-Allow-Credentials: true` — browsers reject it. Spring enforces this: `allowCredentials(true)` with `allowedOrigins("*")` throws at startup.
* **Never reflect the `Origin` header blindly** while allowing credentials. That turns CORS into "any website can read authenticated responses using the victim's cookies" — a real-world data-exfiltration bug. If you need patterns, use `setAllowedOriginPatterns(List.of("https://*.shop.com"))` and make sure the pattern can't match attacker-controlled domains (`https://shop.com.evil.io` must not match).
* `Origin: null` (sandboxed iframes, `file://`, some redirects) must never be allow-listed.

### `Vary: Origin` and caching
When the allowed origin differs per request, the response must carry `Vary: Origin`; otherwise a CDN or proxy can cache a response with `Access-Control-Allow-Origin: https://a.com` and serve it to `https://b.com`. Spring's `DefaultCorsProcessor` adds `Vary` headers automatically — keep them when CDNs or API gateways rewrite headers.

### Where to terminate CORS
In a microservice landscape, configure CORS in **one** place — usually the API gateway or BFF. Duplicated headers (gateway *and* service each add `Access-Control-Allow-Origin`) produce `The 'Access-Control-Allow-Origin' header contains multiple values`, which browsers reject. Spring Cloud Gateway offers `spring.cloud.gateway.globalcors` and the `DedupeResponseHeader` filter for this.

### Often the best CORS config is none
If the SPA and API share an origin — serve the frontend and route `/api` through the same domain via a reverse proxy, CDN path routing, or a BFF — there is no cross-origin request, no preflight latency (one extra round trip per new URL/method combination), and no CORS misconfiguration risk. Cookie-based sessions with `SameSite=Lax/Strict` work naturally in that setup.

### Debugging checklist
1. Look at the **preflight** in browser dev tools (Network tab, filter `OPTIONS`) — most failures are there.
2. Is the request reaching the app? Check gateway/ingress logs; some ingress controllers answer `OPTIONS` themselves.
3. Does an error response (401/500) include CORS headers? If not, the browser shows a CORS error that hides the real status code.

## 🎯 Interview Cheat Sheet

**30-second pitch:** CORS is a browser mechanism that lets a server relax the same-origin policy for specific origins. Non-simple requests trigger an `OPTIONS` preflight. In Spring, I configure a `CorsConfigurationSource` with exact origins and enable `http.cors()` so the security filter chain handles preflights before authentication, and I never combine wildcard or reflected origins with credentials.

**Must know:**
* Origin = scheme + host + port; CORS protects browsers, not servers.
* Simple vs preflighted requests; `Access-Control-Max-Age`.
* `allowCredentials` forbids `*`; don't reflect `Origin`.
* `http.cors()` so preflights aren't rejected with 401.
* `Vary: Origin`; configure CORS in one layer only.

**Common follow-ups:**
* Why does Postman work but the browser doesn't?
* Why do I get 401 on OPTIONS?
* CORS vs CSRF?

**Red flags:** "CORS protects my API from other servers"; `allowedOriginPatterns("*")` with credentials; disabling security for OPTIONS globally.
