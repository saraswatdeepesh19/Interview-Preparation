# How to store passwords securely with PasswordEncoder

---

## 🟢 Junior Level

### 1. Golden Rule

**Never store passwords in plain text, and never encrypt them reversibly. Store a salted, slow, one-way hash.** If the database leaks, attackers should not be able to recover passwords.

### 2. Analogy

A meat grinder: you can turn a steak into mince (hash), but you can't turn mince back into a steak. To check a password, you grind the attempt the same way and compare the mince.

### 3. Why Not MD5/SHA-256?

They are *fast*. A GPU computes billions of SHA-256 hashes per second, so attackers brute-force weak passwords quickly. Password hashing must be **deliberately slow** and **salted** (random per-user value so identical passwords produce different hashes and rainbow tables are useless).

### 4. Spring's `PasswordEncoder`

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

public class PasswordDemo {
    public static void main(String[] args) {
        PasswordEncoder encoder = new BCryptPasswordEncoder();        // default strength 10
        String hash = encoder.encode("MyS3cret!");
        System.out.println(hash);                                      // $2a$10$...  (different every run)
        System.out.println(encoder.matches("MyS3cret!", hash));        // true
        System.out.println(encoder.matches("wrong", hash));            // false
    }
}
```

```java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}
```

Interface methods: `encode`, `matches(raw, encoded)`, `upgradeEncoding(encoded)`.

## 🟡 Middle Level

### 1. Algorithm Comparison

| Algorithm | Spring class | Defence | Notes |
| :--- | :--- | :--- | :--- |
| **BCrypt** | `BCryptPasswordEncoder` | CPU-hard, salted | Default choice; 72-byte input limit; cost 10-14 |
| **Argon2id** | `Argon2PasswordEncoder` | Memory-hard (resists GPUs/ASICs) | OWASP first choice; needs Bouncy Castle |
| **SCrypt** | `SCryptPasswordEncoder` | Memory-hard | Good, less common |
| **PBKDF2** | `Pbkdf2PasswordEncoder` | Iterated HMAC | FIPS-approved; choose when compliance demands |
| MD5/SHA-1/SHA-256, `NoOp` | removed/deprecated | none | Never for passwords |

### 2. Cost Tuning

Target **~250-500 ms** per hash on production hardware for interactive login. BCrypt strength 12 ≈ 250 ms on a modern core. Each +1 doubles time.

```java
@Bean
PasswordEncoder encoder() {
    // OWASP minimum for Argon2id: m=19 MiB, t=2, p=1 (Spring 6.x defaults are similar to this profile)
    return Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
}
```

Dependency for Argon2: `org.bouncycastle:bcpkix-jdk18on`.

### 3. DelegatingPasswordEncoder

Stored values carry the algorithm id prefix: `{bcrypt}$2a$12$...`, `{argon2@SpringSecurity_v5_8}...`. This allows:
- migrating algorithms without a flag day;
- verifying old hashes while encoding new ones with the current default.

```java
Map<String, PasswordEncoder> encoders = new HashMap<>();
encoders.put("bcrypt", new BCryptPasswordEncoder(12));
encoders.put("argon2@SpringSecurity_v5_8", Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8());
DelegatingPasswordEncoder delegating = new DelegatingPasswordEncoder("argon2@SpringSecurity_v5_8", encoders);
```

If the stored hash has no `{id}`, Spring throws `There is no PasswordEncoder mapped for the id "null"` - the most common error after importing legacy hashes (fix: `setDefaultPasswordEncoderForMatches`).

### 4. Registration & Login Example

```java
@Service
public class RegistrationService {
    private final UserRepository users;
    private final PasswordEncoder encoder;

    public RegistrationService(UserRepository users, PasswordEncoder encoder) {
        this.users = users;
        this.encoder = encoder;
    }

    public void register(String email, char[] rawPassword) {
        if (rawPassword.length < 12) throw new IllegalArgumentException("Password too short");
        users.save(new AppUser(email, encoder.encode(new String(rawPassword))));
        java.util.Arrays.fill(rawPassword, '\0');
    }
}
```

### 5. Common Mistakes

- Hashing in the browser *instead of* server-side (the hash becomes the password).
- Truncation: BCrypt ignores bytes after 72 - pre-hashing with SHA-256 is a known workaround but must be base64-encoded to avoid NUL bytes; or choose Argon2.
- Logging passwords in request logs or `toString()` of DTOs.
- Using `NoOpPasswordEncoder` "temporarily".
- Applying password complexity rules while ignoring length and breached-password checks (NIST 800-63B recommends length >= 8-15, check against breach lists, no forced rotation).

## 🔴 Senior Level

### 1. Threat Model

Offline cracking after a DB leak. Defender levers: algorithm hardness, per-user salt (embedded in BCrypt/Argon2 output), cost, and an optional **pepper** - a secret key held outside the database (HSM/Vault/KMS) mixed with the password (e.g. HMAC-SHA256(pepper, password) before BCrypt). It protects against DB-only leaks but complicates rotation (version the pepper id in the stored value).

### 2. Event-Loop and Capacity Impact

A 300 ms hash pins a CPU core. At 100 logins/s you need ~30 cores. DoS vector: attacker floods `/login` to burn CPU. Defences: rate limit per IP and account ([API keys and rate limiting](20.%20API%20keys%20and%20rate%20limiting.md)), a dedicated bounded executor for authentication, CAPTCHA after failures. With Argon2 memory cost multiplies per concurrent hash (19 MiB x concurrency) - cap parallel hashing with a semaphore to avoid OOM.

### 3. Benchmarking Cost

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

public class CostBench {
    public static void main(String[] args) {
        for (int cost = 10; cost <= 14; cost++) {
            var enc = new BCryptPasswordEncoder(cost);
            enc.encode("warmup");
            long t = System.nanoTime();
            enc.encode("benchmark-pass");
            System.out.printf("cost=%d -> %d ms%n", cost, (System.nanoTime() - t) / 1_000_000);
        }
    }
}
```

Run on production-like hardware and re-tune every couple of years. Use `upgradeEncoding()` to rehash when cost increases:

```java
if (encoder.matches(raw, stored) && encoder.upgradeEncoding(stored)) {
    user.setPasswordHash(encoder.encode(raw));
}
```

### 4. Secure Handling in the JVM

`String` is immutable and stays in the heap until GC; heap dumps expose it. Prefer `char[]` at API edges where feasible and wipe it, disable heap dumps in prod or encrypt them, and mask password fields in JSON logging (`@JsonIgnore`/custom serializer).

### 5. Other Credential Aspects

- **Password reset tokens**: 128+ bit random (`SecureRandom`), stored hashed (SHA-256 is fine for high-entropy tokens), single-use, short TTL.
- **Constant-time compare** for tokens: `MessageDigest.isEqual`.
- **Breach checks**: k-anonymity API (Have I Been Pwned) on registration.
- **Passwordless**: prefer passkeys (WebAuthn) where possible; Spring Security 6.4 added WebAuthn support.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
Store passwords only as salted, adaptive, one-way hashes - BCrypt or Argon2id - through Spring's `PasswordEncoder`. Use `DelegatingPasswordEncoder` so you can change algorithms and costs later, tune the cost to about a quarter second, and protect login endpoints against brute force.

### Must-Know Bullets
- Hash != encrypt; salt is automatic in BCrypt/Argon2.
- Fast hashes (SHA-*, MD5) are wrong for passwords.
- `{id}` prefix enables migration.
- BCrypt 72-byte limit; Argon2id preferred (OWASP).
- Rate-limit login; the hash itself is a DoS target.

### Common Follow-Up Questions
1. Salt vs pepper?
2. How do you migrate from MD5 to BCrypt without resetting everyone?
3. Why BCrypt over SHA-256?
4. What does `DelegatingPasswordEncoder` do?
5. How do you choose the work factor?

### 🚩 Red Flags
- `NoOpPasswordEncoder`, MD5, SHA-1 "with salt".
- Storing passwords encrypted (reversible).
- Emailing the existing password to users.
