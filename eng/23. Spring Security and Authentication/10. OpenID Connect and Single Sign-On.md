# OpenID Connect and Single Sign-On

---

## 🟢 Junior Level

### 1. Definitions

- **OpenID Connect (OIDC)** is a thin **identity layer on top of OAuth 2.0**. OAuth says what an app may *access*; OIDC adds a standard way to say *who the user is* ("Sign in with Google").
- **Single Sign-On (SSO)** means logging in **once** with a central identity provider (IdP) and gaining access to many applications without typing credentials again.

### 2. Analogy

A company badge. You get it once at the main desk (IdP). Every office door (application) trusts that badge; you don't register separately at each door.

### 3. What OIDC Adds

| Addition | Meaning |
| :--- | :--- |
| **ID token** | A JWT proving the authentication event: `sub`, `iss`, `aud`, `exp`, `iat`, `nonce`, `auth_time` |
| `openid` scope | Triggers OIDC; plus `profile`, `email` |
| **UserInfo endpoint** | Returns profile claims using the access token |
| **Discovery** | `/.well-known/openid-configuration` lists all endpoints and the JWKS URI |

### 4. Minimal Spring Boot SSO Login

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: shop-web
            client-secret: ${KEYCLOAK_SECRET}
            scope: openid,profile,email
        provider:
          keycloak:
            issuer-uri: https://sso.example.com/realms/company
```

```java
@Bean
SecurityFilterChain web(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2Login(Customizer.withDefaults())
        .build();
}

@RestController
class ProfileController {
    @GetMapping("/profile")
    Map<String, Object> profile(@AuthenticationPrincipal OidcUser user) {
        return Map.of("name", user.getFullName(), "email", user.getEmail(), "subject", user.getSubject());
    }
}
```

Spring discovers endpoints from `issuer-uri` automatically.

## 🟡 Middle Level

### 1. OAuth 2.0 vs OIDC

| | OAuth 2.0 | OIDC |
| :--- | :--- | :--- |
| Purpose | Authorization (access to APIs) | Authentication (user identity) |
| Primary artifact | Access token (any format) | **ID token (always JWT)** |
| Consumer of token | Resource server | **The client app itself** |
| Standard scopes | custom | `openid profile email address phone` |

Rule: **never send the ID token to an API** as an access token; the audience of an ID token is the client, not the API.

### 2. ID Token Validation (done by Spring, but know it)

1. Signature against the IdP's JWKS.
2. `iss` equals configured issuer.
3. `aud` contains your `client_id`.
4. `exp` not past; `iat` sane.
5. `nonce` equals the one sent in the authorization request (replay protection).
6. If `max_age`/`auth_time` requested, check freshness.

### 3. SSO Protocols

| Protocol | Format | Typical home |
| :--- | :--- | :--- |
| **OIDC** | JSON/JWT | Modern web, mobile, SPA |
| **SAML 2.0** | XML assertions | Enterprise/legacy (ADFS, Okta SAML). Spring: `spring-security-saml2-service-provider` |
| Kerberos/SPNEGO | Tickets | Intranet Windows domain |
| CAS | Ticket-based | Universities |

### 4. Mapping IdP Roles to Spring Authorities

Keycloak puts roles in `realm_access.roles`, Azure AD in `roles`, Okta in `groups`. Map them explicitly:

```java
@Bean
GrantedAuthoritiesMapper authoritiesMapper() {
    return authorities -> {
        Set<GrantedAuthority> mapped = new HashSet<>();
        for (GrantedAuthority a : authorities) {
            if (a instanceof OidcUserAuthority oidc) {
                Map<String, Object> realm = oidc.getIdToken().getClaim("realm_access");
                if (realm != null && realm.get("roles") instanceof Collection<?> roles) {
                    roles.forEach(r -> mapped.add(new SimpleGrantedAuthority("ROLE_" + r)));
                }
            }
            mapped.add(a);
        }
        return mapped;
    };
}
```

### 5. Logout

Local logout only ends your app's session; the IdP session survives, so the next click logs the user straight back in. Implement **RP-Initiated Logout**:

```java
OidcClientInitiatedLogoutSuccessHandler h = new OidcClientInitiatedLogoutSuccessHandler(clientRegistrationRepository);
h.setPostLogoutRedirectUri("{baseUrl}/");
http.logout(l -> l.logoutSuccessHandler(h));
```

### 6. Common Mistakes

- Using `email` as a stable identifier (it can change or be unverified); key users by `iss` + `sub`.
- Trusting `email` without checking `email_verified`.
- Auto-linking accounts across IdPs by e-mail (account takeover).
- Not handling IdP outages (login page dead): plan fallbacks.
- Expecting single logout to "just work".

## 🔴 Senior Level

### 1. Flow Variants and Session Layers

In an SSO ecosystem there are **three** sessions: the IdP session (cookie at IdP), each app's session, and tokens' lifetimes. Silent re-authentication uses `prompt=none` in a hidden iframe or redirect, which third-party-cookie restrictions increasingly break; prefer refresh tokens in a BFF or top-level redirects.

### 2. Single Logout Options

| Mechanism | How | Caveat |
| :--- | :--- | :--- |
| RP-initiated | App redirects to IdP `end_session_endpoint` | Only the initiating app notified |
| **Back-channel logout** | IdP POSTs a signed `logout_token` to each app | Apps need session registry keyed by `sid`/`sub` |
| Front-channel | IdP loads iframes of each app's logout URL | Blocked by cookie policies |

Spring Security 6.2+ supports OIDC back-channel logout:

```java
http.oauth2Login(Customizer.withDefaults())
    .oidcLogout(l -> l.backChannel(Customizer.withDefaults()));
```

### 3. Multi-Tenant / Multiple IdPs

Resolve the registration per request (`ClientRegistrationRepository` implementation keyed by tenant or e-mail domain, "home realm discovery"); for resource servers use `JwtIssuerAuthenticationManagerResolver` with a **trusted issuer allow-list** (never accept arbitrary `iss`: SSRF and token forgery risk).

```java
JwtIssuerAuthenticationManagerResolver resolver =
    JwtIssuerAuthenticationManagerResolver.fromTrustedIssuers(
        "https://sso.example.com/realms/a", "https://sso.example.com/realms/b");
http.oauth2ResourceServer(o -> o.authenticationManagerResolver(resolver));
```

### 4. Federation Hazards

- **Identity mapping**: first login provisioning (JIT) vs SCIM; handle email change, duplicate accounts, deprovisioning (disable user when IdP says so - session may outlive employment unless back-channel logout or short sessions).
- **Claims size**: big group claims overflow cookies (4 KB) - Azure AD "groups overage" returns a link instead; call Graph API.
- **Step-up / MFA**: request `acr_values`/`max_age`, then verify `acr` and `auth_time` claims for sensitive operations.
- **Token binding of session to ID token** `sid` to correlate logout events.

### 5. Debugging

`curl https://sso.example.com/realms/company/.well-known/openid-configuration | jq`; decode the ID token (jwt.io offline or `jq`) and compare `iss`/`aud`; enable TRACE on `org.springframework.security.oauth2.client`. Behind a reverse proxy, a wrong `redirect_uri` (http vs https) is the #1 failure - set `server.forward-headers-strategy=framework` and register the exact URI `{baseUrl}/login/oauth2/code/{registrationId}`.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
OIDC extends OAuth 2.0 with an ID token (a signed JWT about the authentication event), the `openid` scope, UserInfo and discovery, so apps can delegate login to an IdP. SSO is the result: one IdP session, many relying parties. In Spring Boot, `oauth2Login` plus an `issuer-uri` gives you OIDC login; use `sub` as identity and handle logout properly.

### Must-Know Bullets
- ID token for the client; access token for APIs.
- Validate `iss`, `aud`, `exp`, `nonce`.
- Identify users by `iss + sub`.
- SAML is the legacy enterprise alternative.
- Logout needs RP-initiated or back-channel flows.

### Common Follow-Up Questions
1. Difference between OAuth 2.0 and OIDC?
2. What is in an ID token and who validates it?
3. How does SSO work across multiple apps?
4. How do you implement logout from all apps?
5. How do you map IdP groups to roles?

### 🚩 Red Flags
- Sending the ID token to APIs.
- Keying users by e-mail only.
- Accepting tokens from any issuer.
