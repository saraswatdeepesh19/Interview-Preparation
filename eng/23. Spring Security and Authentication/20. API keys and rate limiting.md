# API keys and rate limiting

---

## 🟢 Junior Level

* An **API key** is a long random string that identifies a calling *application* (not a user). The client sends it with each request, e.g. `X-API-Key: sk_live_...`.
* **Rate limiting** restricts how many requests a client may make in a time window (e.g. 100 requests per minute). Excess requests get **`429 Too Many Requests`**.

They usually go together: the API key identifies *who* is calling, and the rate limit is applied *per key*.

```http
GET /v1/products HTTP/1.1
X-API-Key: sk_live_2bT9...q8

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Policy: 100;w=60
RateLimit: limit=100, remaining=0, reset=30
```

### API keys vs OAuth tokens
API keys are simple and good for server-to-server integrations and public developer APIs. They don't expire by themselves, don't carry user identity or scopes in a standard way, and are bearer credentials — anyone holding the key can use it. For user-facing access or fine-grained permissions, prefer OAuth 2.0 (client credentials or authorization code).

## 🟡 Middle Level

### Storing and validating API keys
Treat keys like passwords: **store only a hash**, show the full key once at creation.

```java
public record ApiKey(String prefix, String hash, String clientId, Set<String> scopes, Instant expiresAt) {}

String issue(String clientId, Set<String> scopes) {
    byte[] random = new byte[32];
    SECURE_RANDOM.nextBytes(random);
    String secret = "sk_live_" + Base64.getUrlEncoder().withoutPadding().encodeToString(random);
    String prefix = secret.substring(0, 12);                         // indexed lookup + shown in UI ("sk_live_2bT9…")
    repo.save(new ApiKey(prefix, sha256Hex(secret), clientId, scopes, Instant.now().plus(365, DAYS)));
    return secret;                                                   // shown once
}
```

A fast hash (SHA-256) is fine here because keys have 256 bits of entropy (unlike human passwords); compare with `MessageDigest.isEqual` to avoid timing leaks.

### A Spring Security filter for API keys

```java
class ApiKeyAuthFilter extends OncePerRequestFilter {
    private final ApiKeyService keys;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String header = req.getHeader("X-API-Key");
        if (header == null) {                       // no key: let other mechanisms (or the 401 entry point) decide
            chain.doFilter(req, res);
            return;
        }
        Optional<ApiClient> client = keys.authenticate(header);
        if (client.isEmpty()) {
            res.sendError(HttpServletResponse.SC_UNAUTHORIZED);   // invalid key: stop here
            return;
        }
        var authorities = client.get().scopes().stream().map(s -> new SimpleGrantedAuthority("SCOPE_" + s)).toList();
        var auth = UsernamePasswordAuthenticationToken.authenticated(client.get().id(), null, authorities);
        SecurityContext ctx = SecurityContextHolder.createEmptyContext();
        ctx.setAuthentication(auth);
        SecurityContextHolder.setContext(ctx);
        chain.doFilter(req, res);
    }
}
// http.addFilterBefore(new ApiKeyAuthFilter(keys), AuthorizationFilter.class)
```

### Rate-limiting algorithms

| Algorithm | Idea | Trade-off |
| --- | --- | --- |
| Fixed window | Count per minute bucket | Simple; allows 2× burst at window edges |
| Sliding window log | Store timestamps | Accurate; memory per request |
| Sliding window counter | Weighted current + previous window | Good accuracy, O(1) memory |
| **Token bucket** | Bucket refills at rate r, capacity b | Allows controlled bursts; most common |
| Leaky bucket | Queue drained at constant rate | Smooths traffic; adds latency |

### In-process token bucket with Bucket4j

```java
Bucket bucket = Bucket.builder()
        .addLimit(limit -> limit.capacity(100).refillGreedy(100, Duration.ofMinutes(1)))
        .build();

ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
if (!probe.isConsumed()) {
    response.setHeader("Retry-After", String.valueOf(TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill())));
    response.setStatus(429);
}
```

## 🔴 Senior Level

### Distributed rate limiting
With 10 replicas, a local limit of 100/min becomes 1,000/min. Options:
* **Central store** — Redis with an atomic Lua script (token bucket or sliding window) or Bucket4j's Redis/JCache backends. One round trip per request (~0.2–1 ms in-region).
* **Gateway-level** — Spring Cloud Gateway `RequestRateLimiter` with `RedisRateLimiter` (token bucket in Lua), Envoy/Istio global rate limit service, AWS API Gateway usage plans.
* **Approximate local limits** — limit/replicas per instance; cheap, inaccurate during scaling.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: products
          uri: lb://product-service
          predicates: [ Path=/v1/products/** ]
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10     # tokens per second
                redis-rate-limiter.burstCapacity: 20
                key-resolver: "#{@apiKeyResolver}"       # bean resolving the key from X-API-Key
```

Failure mode decision: if Redis is down, **fail open** (allow traffic, risk overload) or **fail closed** (reject, risk outage)? Most public APIs fail open with a conservative local fallback limiter.

### Layered limits
* **Edge** (CDN/WAF): IP-based limits against floods and credential stuffing.
* **Gateway**: per API key / tenant quotas, plans (free 1k/day, pro 100k/day).
* **Service**: concurrency limits (bulkheads) protecting expensive endpoints and downstream databases — a request-count limit doesn't protect you from 50 concurrent 30-second report queries.
* **Cost-based limits**: weight requests (a search costs 10 tokens, a GET costs 1) or GraphQL query complexity.

### Key lifecycle and abuse handling
* Prefix keys by environment and type (`sk_live_`, `pk_test_`) so scanners (GitHub secret scanning partner program) can detect leaks and you can auto-revoke.
* Support **multiple active keys** per client for zero-downtime rotation; record `last_used_at` to find dead keys.
* Scope keys (read-only vs write) and bind them to allowed IP ranges or mTLS client certificates for high-value integrations.
* Log rate-limit rejections per key; sustained 429s suggest a misbehaving integration (or a leaked key being abused).

## 🎯 Interview Cheat Sheet

**30-second pitch:** API keys identify calling applications; store them hashed, scope them, support rotation, and transmit only over TLS in headers. Rate limiting — typically token bucket — protects capacity and enforces plans, returning 429 with `Retry-After`. In a multi-instance deployment I enforce limits at the gateway or with an atomic Redis script, layered with IP limits at the edge and concurrency limits in services.

**Must know:**
* API key vs OAuth: identity of app vs delegated user/scope-based access.
* Hash keys (SHA-256 fine due to entropy), show once, prefix for lookup.
* Fixed window vs sliding window vs token bucket vs leaky bucket.
* Distributed limits need shared state (Redis Lua, gateway).
* 429 + `Retry-After`, `RateLimit` headers.

**Common follow-ups:**
* How do you rate-limit across 20 pods?
* Fail open or fail closed?
* How do you prevent burst at window boundaries?

**Red flags:** API keys in query strings; storing keys in plaintext; per-instance limits presented as global quotas.
