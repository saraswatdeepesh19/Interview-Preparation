# JWT structure signing and common pitfalls

---

## 🟢 Junior Level

### 1. What Is a JWT?

A **JSON Web Token (RFC 7519)** is a compact, URL-safe string that carries claims (facts about a user) and is **signed** so that tampering is detectable. It looks like three Base64URL parts separated by dots:

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJhbGljZSIsInJvbGVzIjpbIlVTRVIiXX0 . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
        header                                  payload                                  signature
```

- **Header:** algorithm (`alg`) and key id (`kid`).
- **Payload:** claims: `sub` (subject), `iss` (issuer), `aud` (audience), `exp` (expiry), `iat`, `nbf`, `jti` (id), plus custom ones (`roles`, `tenant`).
- **Signature:** proves the header+payload were produced by the holder of the key.

### 2. Key Point

**A JWT is signed, not encrypted.** Anyone can Base64-decode the payload. Never put passwords or sensitive personal data inside.

### 3. Analogy

A passport: it contains readable data, and a hologram/seal (signature) proves it wasn't forged. Anyone can read it; only the government can issue it.

### 4. Decoding Without Libraries (to see it's readable)

```java
import java.nio.charset.StandardCharsets;
import java.util.Base64;

public class JwtPeek {
    public static void main(String[] args) {
        String jwt = "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.sig";
        String payload = jwt.split("\\.")[1];
        System.out.println(new String(Base64.getUrlDecoder().decode(payload), StandardCharsets.UTF_8));
        // {"sub":"alice"}
    }
}
```

## 🟡 Middle Level

### 1. Signing Algorithms

| Alg | Type | Key | When |
| :--- | :--- | :--- | :--- |
| HS256 | HMAC, symmetric | Shared secret (>= 256 bit) | Single service that both issues and verifies |
| **RS256** | RSA, asymmetric | Private signs, public verifies | Many verifying services; publish JWKS |
| **ES256 / EdDSA** | ECDSA / Ed25519 | Smaller keys, fast | Modern default for new systems |
| `none` | no signature | - | **Must be rejected** |

Asymmetric keys let resource servers verify without being able to mint tokens.

### 2. Issuing and Verifying with Spring (Nimbus)

```java
import com.nimbusds.jose.jwk.JWKSet;
import com.nimbusds.jose.jwk.RSAKey;
import com.nimbusds.jose.jwk.source.ImmutableJWKSet;
import com.nimbusds.jose.proc.SecurityContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.oauth2.jwt.*;

import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.interfaces.RSAPrivateKey;
import java.security.interfaces.RSAPublicKey;
import java.time.Instant;
import java.util.UUID;

@Configuration
public class JwtConfig {

    private final RSAKey rsaKey = generate();

    private static RSAKey generate() {
        try {
            KeyPairGenerator g = KeyPairGenerator.getInstance("RSA");
            g.initialize(2048);
            KeyPair kp = g.generateKeyPair();
            return new RSAKey.Builder((RSAPublicKey) kp.getPublic())
                    .privateKey((RSAPrivateKey) kp.getPrivate())
                    .keyID(UUID.randomUUID().toString()).build();
        } catch (Exception e) { throw new IllegalStateException(e); }
    }

    @Bean
    JwtEncoder jwtEncoder() {
        return new NimbusJwtEncoder(new ImmutableJWKSet<SecurityContext>(new JWKSet(rsaKey)));
    }

    @Bean
    JwtDecoder jwtDecoder() throws Exception {
        NimbusJwtDecoder decoder = NimbusJwtDecoder.withPublicKey(rsaKey.toRSAPublicKey()).build();
        decoder.setJwtValidator(JwtValidators.createDefaultWithIssuer("https://auth.example.com"));
        return decoder;
    }

    public static String issue(JwtEncoder enc, String user, java.util.List<String> roles) {
        Instant now = Instant.now();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer("https://auth.example.com")
                .subject(user)
                .audience(java.util.List.of("orders-api"))
                .issuedAt(now).expiresAt(now.plusSeconds(600))
                .id(UUID.randomUUID().toString())
                .claim("roles", roles).build();
        return enc.encode(JwtEncoderParameters.from(
                JwsHeader.with(org.springframework.security.oauth2.jose.jws.SignatureAlgorithm.RS256).build(), claims))
                .getTokenValue();
    }
}
```

In production, keys are loaded from a keystore/KMS and **rotated** (publish old + new in JWKS; `kid` selects the key).

### 3. Mapping Claims to Authorities

```java
@Bean
JwtAuthenticationConverter jwtAuthConverter() {
    JwtGrantedAuthoritiesConverter c = new JwtGrantedAuthoritiesConverter();
    c.setAuthoritiesClaimName("roles");
    c.setAuthorityPrefix("ROLE_");
    JwtAuthenticationConverter jc = new JwtAuthenticationConverter();
    jc.setJwtGrantedAuthoritiesConverter(c);
    return jc;
}
```

### 4. Pitfalls Checklist

| Pitfall | Consequence | Fix |
| :--- | :--- | :--- |
| Accepting `alg: none` | Forged tokens | Library defaults reject; pin the expected algorithm |
| **Algorithm confusion** (RS256 token verified as HS256 using the public key as secret) | Full forgery | Configure verifier with a fixed algorithm and key type |
| Not validating `exp`, `iss`, `aud` | Replay, token from another app accepted | Use `JwtValidators`, add an audience validator |
| Weak HS256 secret (`"secret"`) | Offline brute-force | >= 32 random bytes |
| Sensitive data in payload | Disclosure | Keep claims minimal |
| Long expiry | Large exposure window | 5-15 min access tokens |
| Storing in `localStorage` | XSS theft | HttpOnly cookie or BFF |
| Trusting `kid`/`jku`/`x5u` headers from the token | SSRF / key injection | Only use pre-configured JWKS URI |
| Large tokens | Header size limits | Store permissions server-side, keep claims small |

### 5. Audience Validation

```java
OAuth2TokenValidator<Jwt> audience = jwt ->
    jwt.getAudience().contains("orders-api")
        ? OAuth2TokenValidatorResult.success()
        : OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Wrong audience", null));
decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(JwtValidators.createDefaultWithIssuer(issuer), audience));
```

## 🔴 Senior Level

### 1. Internals of Verification

`NimbusJwtDecoder` parses the compact serialization, selects the key by `kid` from a `JWKSource` (remote JWKS cached with `RemoteJWKSet`, refreshed on unknown `kid` with rate limit), verifies the JWS with a `JWSVerifier` (RSASSA-PKCS1-v1_5 / ECDSA), then runs the `OAuth2TokenValidator` chain. Default validators: `JwtTimestampValidator` (60 s clock skew) and issuer. Failures become `JwtException` -> `BearerTokenAuthenticationFilter` -> 401 with `WWW-Authenticate: Bearer error="invalid_token"`.

### 2. Performance

RS256 verification of a 2048-bit key ~ 30-60 microseconds on modern CPUs; signing ~1-2 ms (so signing is the expensive side, which is why issuance is centralized). ES256 signs faster and has smaller tokens (64-byte signature vs 256). Measure with JMH rather than guessing; parsing JSON and base64 usually dominates verification.

### 3. Key Rotation Strategy

1. Generate key B; add to JWKS alongside A (both published).
2. Start signing with B (`kid=B`).
3. After `max token lifetime + cache TTL`, remove A.

Resource servers using a remote JWKS tolerate this; those with a statically configured key do not - another reason to use JWKS.

### 4. Encrypted and Nested Tokens

When the payload itself must be confidential, use **JWE** (RFC 7516) - or avoid putting the data in a token at all. Often an opaque token + introspection is the better design.

### 5. Token Binding (Sender-Constrained)

Bearer tokens are stolen = usable. **DPoP** (RFC 9449) or **mTLS-bound** tokens (RFC 8705, `cnf` claim) bind the token to a key held by the client. Spring Authorization Server supports these; consider for high-value APIs.

### 6. Testing for Weaknesses

Use `jwt_tool`-style tests: `alg=none`, altered `exp`, key confusion, changed `aud`. Add integration tests that assert 401 for each (see [Testing secured endpoints](22.%20Testing%20secured%20endpoints.md)).

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
A JWT is `header.payload.signature`, Base64URL-encoded JSON signed with HMAC or an asymmetric key. It is integrity-protected but readable. A verifier must check the signature with a pinned algorithm and key, then `exp`, `iss`, `aud`. Keep tokens short-lived and small, prefer RS256/ES256 with JWKS and key rotation, and don't store them where XSS can read them.

### Must-Know Bullets
- Signed != encrypted.
- Reject `none`; pin the algorithm.
- Validate `iss`, `aud`, `exp`, `nbf`.
- Asymmetric keys for multi-service verification.
- Rotate keys via `kid` and JWKS.

### 🚩 Red Flags
- Secret `"secret"` committed to git.
- No expiration claim.
- Decoding without verifying ("I just parse the payload").
