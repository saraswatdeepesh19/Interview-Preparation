# Roles vs authorities

---

## 🟢 Junior Level

### 1. Definitions

In Spring Security everything a user "has" is a **`GrantedAuthority`** - a simple string. A **role** is just an authority whose string starts with the prefix `ROLE_`.

| Concept | Example string | Meaning |
| :--- | :--- | :--- |
| Role | `ROLE_ADMIN` | Coarse "job title" - what kind of user |
| Authority (permission) | `order:write`, `SCOPE_orders.read` | Fine-grained "action" - what they may do |

### 2. Analogy

A **role** is a job title on a badge ("Nurse"); **authorities** are the individual keys on the keyring ("open pharmacy", "read patient chart"). A role is a bundle of keys, but Spring treats both as keys.

### 3. Using Them

```java
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;

UserDetails alice = User.withUsername("alice")
        .password("{noop}pw")
        .roles("ADMIN")                          // stored as ROLE_ADMIN
        .build();

UserDetails bob = User.withUsername("bob")
        .password("{noop}pw")
        .authorities("order:read", "order:write")  // stored exactly as given
        .build();
```

```java
http.authorizeHttpRequests(a -> a
    .requestMatchers("/admin/**").hasRole("ADMIN")                    // checks ROLE_ADMIN
    .requestMatchers(HttpMethod.GET, "/orders/**").hasAuthority("order:read")
    .requestMatchers(HttpMethod.POST, "/orders/**").hasAuthority("order:write")
    .anyRequest().authenticated());
```

**Key rule:** `hasRole("ADMIN")` automatically prepends `ROLE_`; `hasAuthority("ROLE_ADMIN")` is the same check.

## 🟡 Middle Level

### 1. Comparison

| Aspect | Role | Authority/Permission |
| :--- | :--- | :--- |
| Granularity | Coarse | Fine |
| Prefix | `ROLE_` (configurable) | none |
| Changes when | Org structure changes | Features change |
| Risk | Role explosion (`ROLE_MANAGER_EU_READONLY`) | Many strings to manage |
| Best for | UI navigation, broad access | Code-level checks, APIs, OAuth scopes |

### 2. Recommended Model: Role -> Permissions

Code checks **permissions**; administrators assign **roles**; roles map to permissions in the database. This decouples code from organisation changes ("add the `report:export` permission to Managers" without deploying).

```java
public enum Permission { ORDER_READ, ORDER_WRITE, REPORT_EXPORT }

public enum Role {
    VIEWER(Set.of(Permission.ORDER_READ)),
    MANAGER(Set.of(Permission.ORDER_READ, Permission.ORDER_WRITE, Permission.REPORT_EXPORT));

    private final Set<Permission> permissions;
    Role(Set<Permission> p) { this.permissions = p; }

    public List<GrantedAuthority> toAuthorities() {
        List<GrantedAuthority> list = new ArrayList<>();
        list.add(new SimpleGrantedAuthority("ROLE_" + name()));
        permissions.forEach(p -> list.add(new SimpleGrantedAuthority(p.name())));
        return list;
    }
}
```

```java
@PreAuthorize("hasAuthority('REPORT_EXPORT')")
public byte[] exportReport() { return new byte[0]; }
```

### 3. Role Hierarchy

```java
@Bean
RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("""
        ROLE_ADMIN > ROLE_MANAGER
        ROLE_MANAGER > ROLE_USER
        """);
}

@Bean
static MethodSecurityExpressionHandler methodSecurityExpressionHandler(RoleHierarchy hierarchy) {
    DefaultMethodSecurityExpressionHandler h = new DefaultMethodSecurityExpressionHandler();
    h.setRoleHierarchy(hierarchy);
    return h;
}
```

`RoleHierarchyImpl.fromHierarchy` is the Spring Security 6.3+ builder; earlier use `setHierarchy(String)`. For **URL** rules in Security 6.x, the `RoleHierarchy` bean is picked up by `authorizeHttpRequests` automatically only in newer versions (6.3+); otherwise set it on the `AuthorityAuthorizationManager`.

### 4. Where Authorities Come From

| Authentication type | Source |
| :--- | :--- |
| Username/password | `UserDetails.getAuthorities()` from DB |
| JWT resource server | `JwtGrantedAuthoritiesConverter` (`scope`, `roles` claim) |
| OIDC login | `OidcUserAuthority` + `GrantedAuthoritiesMapper` (`OIDC_USER`, `SCOPE_*`) |

### 5. Common Mistakes

- Storing `ROLE_ADMIN` in DB and calling `hasRole("ROLE_ADMIN")`: works in some versions, throws "role should not start with ROLE_" in `@PreAuthorize` checks elsewhere. Be consistent: store with prefix, check without.
- Case sensitivity: `ROLE_admin` != `ROLE_ADMIN`.
- Putting too many authorities into a JWT/session (thousands) - bloats tokens.
- Using roles for what are really object-level decisions ("editor of document 17").
- Customizing the prefix with `GrantedAuthorityDefaults` bean and forgetting JWT converters have their own prefix.

## 🔴 Senior Level

### 1. Authorization Models

| Model | Idea | Fit |
| :--- | :--- | :--- |
| **RBAC** | Users -> roles -> permissions | Most business apps |
| **ABAC** | Policy over attributes (user dept, resource sensitivity, time, IP) | Compliance-heavy, contextual rules |
| **ReBAC** | Relationships (Zanzibar, OpenFGA, SpiceDB): "viewer of folder containing doc" | Sharing/collaboration products |
| **ACL** | Per-object entries (`spring-security-acl`) | Few objects, explicit sharing |

Senior answer: start with RBAC for coarse access, add ownership predicates in code/queries; adopt a policy engine (OPA, Cedar, OpenFGA) when rules change often or span services, enforcing via a PEP (Spring `AuthorizationManager`) and PDP (policy service). Cache decisions per request; define timeouts and a fail-closed behaviour.

### 2. Dynamic Authorities and Staleness

Authorities stored in a session or JWT are a **snapshot**. If an admin revokes a permission, the user keeps it until the session/token ends. Options: shorten TTL; reload authorities per request from a cached store (`UserDetailsService` cache + eviction event); keep only roles in the token and resolve permissions server-side from a cache keyed by role version.

```java
@Component
class PermissionService {
    private final LoadingCache<String, Set<String>> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofSeconds(30)).maximumSize(50_000)
        .build(this::loadFromDb);

    Set<String> permissionsOf(String userId) { return cache.get(userId); }
    private Set<String> loadFromDb(String userId) { return Set.of(); /* query */ }
}
```

### 3. Converting at the Edge

A single place for mapping is important: put it in `JwtAuthenticationConverter` / `GrantedAuthoritiesMapper`, normalising to one namespace (`ROLE_*` for roles, `perm:*` or plain permissions for rights). Internal code then never looks at raw IdP claims, so changing the IdP doesn't touch business code.

### 4. Testing Matrix

Write parameterized tests over (role x endpoint x expected status). With `@WithMockUser(authorities = {...})` for permissions and `jwt().authorities(...)` for resource servers ([Testing secured endpoints](23.%20Testing%20secured%20endpoints.md)). A forbidden-by-default matrix catches accidental `permitAll`.

### 5. Performance and Scale

`hasAuthority` is an O(k) scan over a collection of authorities (set-based in `SecurityExpressionRoot`: `AuthorityUtils.authorityListToSet` is computed lazily and cached per root). With <100 authorities it's irrelevant; with thousands (flattened ACLs) move to object-level checks.

## 🎯 Interview Cheat Sheet

### 30-Second Elevator Pitch
Spring models both as `GrantedAuthority` strings; a role is simply an authority prefixed with `ROLE_`. `hasRole("X")` checks `ROLE_X`, `hasAuthority("X")` checks `X` exactly. Use roles as coarse groupings assigned to users and fine-grained permissions in the code, map IdP claims into this model in one converter, and use object-level or policy-based checks when rules depend on the resource.

### Must-Know Bullets
- Role = authority with `ROLE_` prefix.
- `hasRole` adds the prefix; `hasAuthority` does not.
- Check permissions in code, assign roles to users.
- JWT/session authorities can be stale.
- Role hierarchies avoid duplication.

### Common Follow-Up Questions
1. Why does `hasRole('ROLE_ADMIN')` sometimes fail?
2. How would you implement role hierarchy?
3. RBAC vs ABAC vs ReBAC?
4. How do OAuth scopes relate to authorities?
5. How to reflect revoked permissions immediately?

### 🚩 Red Flags
- Dozens of hardcoded role strings in code.
- Using roles to model per-record ownership.
- Trusting client-sent role headers.
