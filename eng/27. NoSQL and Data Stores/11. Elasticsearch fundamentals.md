# Elasticsearch fundamentals

---

## 🟢 Junior Level

### 1. What is Elasticsearch?

**Elasticsearch** is a distributed **search and analytics engine** built on Apache Lucene. You send it JSON documents over a REST API; it indexes every field so you can run fast full-text search, filters and aggregations. It is not a primary database: it is the specialised "search box" of your system.

**Analogy:** the index at the back of a textbook. Instead of reading every page to find "replication", you look the word up and get the page numbers. That's an **inverted index**.

### 2. Key vocabulary

| Elasticsearch | Relational analogy |
| :--- | :--- |
| Index | Table |
| Document | Row (a JSON object) |
| Field | Column |
| Mapping | Schema |
| Shard | Partition |
| Node / Cluster | Server / group of servers |

(Types were removed; each index holds one kind of document.)

### 3. Hello world

```bash
# Index a document
curl -X PUT "localhost:9200/articles/_doc/1" -H "Content-Type: application/json" -d '
{ "title": "Introduction to Elasticsearch", "body": "Search made fast and easy", "views": 10 }'

# Search it
curl -X GET "localhost:9200/articles/_search" -H "Content-Type: application/json" -d '
{ "query": { "match": { "body": "fast search" } } }'
```

```java
// Java API Client (co.elastic.clients:elasticsearch-java)
record Article(String title, String body, int views) {}

ElasticsearchClient client = new ElasticsearchClient(new RestClientTransport(
        RestClient.builder(new HttpHost("localhost", 9200)).build(), new JacksonJsonpMapper()));

client.index(i -> i.index("articles").id("1").document(new Article("Intro", "Search made fast", 10)));
SearchResponse<Article> res = client.search(s -> s.index("articles")
        .query(q -> q.match(m -> m.field("body").query("fast"))), Article.class);
res.hits().hits().forEach(h -> System.out.println(h.source() + " score=" + h.score()));
```

## 🟡 Middle Level

### 1. The inverted index

For each term the index stores the list of documents containing it (a **postings list**) with frequency and positions.

| Term | Postings (docId) |
| :--- | :--- |
| fast | 1, 3 |
| search | 1, 2, 3 |
| easy | 1 |

A query for `fast AND search` intersects the lists - a very fast operation regardless of how many documents exist. Lucene stores the term dictionary as a **finite state transducer (FST)** in memory and postings compressed (frame-of-reference / roaring bitmaps). Numeric/range fields use **BKD trees**; sorting and aggregations use **doc values** (columnar on-disk structure).

### 2. Analysis: analyzers

An **analyzer** = zero or more **character filters** + exactly one **tokenizer** + zero or more **token filters**. It runs at index time (on the document) and at search time (on the query).

```
"The QUICK Foxes!"  --standard analyzer-->  [the, quick, foxes]
"The QUICK Foxes!"  --english analyzer -->  [quick, fox]     (lowercase, stopwords, stemming)
```

Test any analyzer:

```bash
curl -X POST "localhost:9200/_analyze" -H "Content-Type: application/json" -d '{"analyzer":"english","text":"The QUICK Foxes!"}'
```

Common bug: indexing with one analyzer and searching with another so terms never match.

### 3. Shards and replicas

- An index is split into **primary shards** (fixed at creation; changeable only by split/shrink/reindex). Each is a Lucene index.
- Each primary has **replica shards** on other nodes for HA and read throughput.
- Routing: `shard = hash(_routing or _id) % number_of_primary_shards`.
- A search is **scatter-gather**: coordinating node asks every shard (query phase), merges top-N, then fetches documents (fetch phase).

```json
PUT /articles
{ "settings": { "number_of_shards": 3, "number_of_replicas": 1 } }
```

Cluster health: `green` (all shards allocated), `yellow` (replicas missing), `red` (a primary missing).

### 4. Relevance scoring

Default scoring is **BM25** (since 5.0), improving on TF-IDF:

- **Term frequency**: more occurrences = higher score, with saturation (`k1`, default 1.2).
- **Inverse document frequency**: rare terms matter more.
- **Field-length normalisation** (`b`, default 0.75): matches in short fields score higher.

Use `explain: true` to see the score computation. Boost fields (`title^3`), use `function_score`, or `rank_feature` for business signals (popularity, recency).

### 5. Near real-time (NRT)

Writes go to an in-memory buffer and the **translog**; a **refresh** (default every 1 s) creates a new searchable **segment**; a **flush** commits segments to disk and truncates the translog. Segments are immutable; updates are delete-marker + re-insert; background **merges** combine segments and purge deletes.

### 6. Common mistakes

- Using Elasticsearch as the **system of record** (no cross-document transactions, historical data-loss cases under misconfiguration).
- **Too many shards**: each shard has overhead (heap, file handles). Aim for 10-50 GB per shard, < ~20 shards per GB of heap.
- Default **dynamic mapping** causing mapping explosions or wrong field types.
- Deep pagination with `from + size` (limit 10,000).
- Running a single node in production with replicas set to 1 (permanently yellow).

## 🔴 Senior Level

### 1. Lucene segment mechanics and performance

- Each shard = N immutable segments; each query hits every segment, so too many small segments hurt. Tune `refresh_interval` to `30s` or `-1` during bulk loads, and call `_forcemerge` only on read-only (e.g., rolled-over) indices.
- Heap: keep at most ~50% of RAM, and under ~31 GB (compressed oops). The rest is used by the **OS page cache** which Lucene relies on heavily.
- `fielddata` on `text` fields loads into heap - avoid; use `keyword` with doc values or `.keyword` sub-fields for aggregations.

### 2. Cluster topology and resiliency

| Role | Purpose |
| :--- | :--- |
| Master-eligible | Cluster state, shard allocation (3 dedicated for quorum) |
| Data (hot / warm / cold / frozen) | Tiered storage with ILM |
| Coordinating | Routes/reduces requests |
| Ingest | Pipelines (grok, enrich) |

- Master election uses a Raft-like coordination layer (7.x+) and needs a majority; use 3 master-eligible nodes to avoid split brain.
- Shard allocation awareness (zone attribute) puts replicas in other AZs.
- **Index Lifecycle Management (ILM)** + data streams + rollover handle log/time-series retention.

### 3. Bulk indexing in Java

```java
BulkRequest.Builder br = new BulkRequest.Builder();
for (Article a : batch) {
    br.operations(op -> op.index(i -> i.index("articles").id(a.id()).document(a)));
}
BulkResponse resp = client.bulk(br.build());
if (resp.errors()) {
    resp.items().stream().filter(it -> it.error() != null)
        .forEach(it -> log.warn("Failed {}: {}", it.id(), it.error().reason()));
}
```

Batch ~5-15 MB per request, tune concurrency, handle 429 (`es_rejected_execution_exception`) with backoff; prefer `BulkIngester` helper.

### 4. Diagnostics

| Tool | Use |
| :--- | :--- |
| `GET _cluster/health`, `_cat/shards?v`, `_cat/indices?v` | State and sizes |
| `GET _cluster/allocation/explain` | Why a shard is unassigned |
| `GET _nodes/hot_threads`, `_nodes/stats` | CPU/heap/GC |
| Slow log (`index.search.slowlog.threshold.query.warn`) | Slow queries |
| Profile API (`"profile": true`) | Per-clause timing |

### 5. Edge cases and consistency

- **Near-real-time** means a doc is not searchable until refresh; use `refresh=wait_for` sparingly (kills throughput).
- Optimistic concurrency via `if_seq_no` and `if_primary_term`.
- Replicas: writes go to primary then in-sync replicas (`wait_for_active_shards`); a primary failure promotes a replica with sequence-number-based recovery.
- **Mapping is mostly immutable**: changing field type requires reindex; use index aliases for zero-downtime swaps.
- **Relevance tuning** needs offline evaluation (ranking evaluation API, NDCG), not guesswork.

## 🎯 Interview Cheat Sheet

### 30-second pitch
"Elasticsearch is a distributed Lucene-based search engine. Documents are analyzed into an inverted index, split into primary shards with replicas, searched scatter-gather, and ranked with BM25. It is near-real-time and excellent for search and log analytics, but it should be a derived index, not the source of truth."

### Must-know bullets
- Inverted index maps terms to documents; analyzers = char filters + tokenizer + token filters.
- Primary shard count is fixed at creation; replicas give HA and read scale.
- BM25: TF saturation, IDF, field-length normalisation.
- Refresh (1 s) makes data searchable; translog gives durability.
- Keep heap <= 31 GB; avoid oversharding and mapping explosion.

### Common follow-ups
- Why can't I change the number of primary shards?
- text vs keyword field?
- What does yellow status mean?
- How does a distributed search work?
- How would you keep Elasticsearch in sync with your database?

### 🚩 Red flags
- Elasticsearch as the only copy of business data.
- Hundreds of tiny shards.
- Deep pagination using `from/size`.
