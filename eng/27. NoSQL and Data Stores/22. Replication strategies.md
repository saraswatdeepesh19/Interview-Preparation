# Replication strategies

---

## 🟢 Junior Level

**Replication** keeps copies of the same data on multiple machines. Reasons:
* **High availability** — if one node dies, another has the data.
* **Read scaling** — spread reads across replicas.
* **Latency** — place copies close to users (other regions).
* **Disaster recovery** — survive the loss of a data center.

### Three basic topologies

| Topology | Writes go to | Examples |
| --- | --- | --- |
| **Single-leader** (primary/replica) | One leader; replicas follow | PostgreSQL streaming replication, MySQL, MongoDB replica sets, Redis |
| **Multi-leader** | Several leaders (often one per region) | MySQL/PostgreSQL multi-master tools, CouchDB, DynamoDB Global Tables |
| **Leaderless** | Any replica; quorum reads/writes | Cassandra, ScyllaDB, Riak, (Dynamo-style) |

### Synchronous vs asynchronous
* **Synchronous** — the leader waits for replica acknowledgment before confirming the write: no data loss on failover, higher latency, writes stall if the replica is slow.
* **Asynchronous** — the leader confirms immediately: low latency, but recent writes can be **lost** on failover, and replicas **lag**.

## 🟡 Middle Level

### Replication lag and its anomalies
With asynchronous replicas, a read from a replica may return old data:
* **Read-your-writes violation** — a user updates their profile, refreshes, and sees the old value (read hit a lagging replica).
* **Monotonic reads violation** — two reads hit different replicas; the second shows older data than the first.
* **Consistent prefix violation** — causally related writes appear out of order.

Fixes: read from the leader for a short time after a user's write, pin a user's session to one replica, or track the write's position (PostgreSQL LSN, MongoDB `operationTime` with causally consistent sessions) and only read from replicas that have caught up.

### Routing reads in Spring

```java
// Route @Transactional(readOnly = true) to replicas, everything else to the primary
public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}
// Wrap it in LazyConnectionDataSourceProxy so the routing decision happens when the
// connection is actually used (after the transaction's read-only flag is set).
```

Watch out: "read-only" code paths that must see fresh data (right after a write) should still go to the primary.

### Quorums in leaderless systems
With `N` replicas, writes acknowledged by `W` nodes and reads querying `R` nodes, **`R + W > N`** ensures read and write sets overlap, so a read sees the latest acknowledged write (assuming no concurrent conflicts and correct repair). Cassandra example with `N = 3`: `QUORUM` writes (2) + `QUORUM` reads (2) = 4 > 3.

## 🔴 Senior Level

### Failover is where replication bites
* **Data loss window** — async replica promoted → writes not yet replicated are gone. PostgreSQL `synchronous_commit` with `synchronous_standby_names = 'ANY 1 (s1, s2)'` trades latency for zero-loss failover to a synchronous standby.
* **Split brain** — two nodes both believe they are primary and accept writes. Prevent with consensus-based failover (Patroni + etcd, MongoDB's Raft-like elections, Redis Sentinel quorum) and **fencing** (STONITH, or blocking the old primary's connections).
* **Client failover** — connection strings with multiple hosts (`jdbc:postgresql://a,b/db?targetServerType=primary`), DNS TTLs short enough (and JVM `networkaddress.cache.ttl` not infinite), connection pools that evict dead connections (`maxLifetime`, validation).

### Multi-leader and conflict resolution
When two regions accept writes to the same record concurrently, conflicts are inevitable:
* **Last-writer-wins (LWW)** by timestamp — simple, silently loses updates; clock skew decides winners (DynamoDB Global Tables, Cassandra cells).
* **Application-level merge** — custom resolution (union shopping carts, max of counters).
* **CRDTs** — data types designed to merge deterministically (G-Counters, OR-Sets); used in Riak, Redis Enterprise Active-Active, collaborative editors.
* **Avoid conflicts by design** — route each entity's writes to a "home" region (per-user home region), giving multi-region availability for reads and single-leader semantics per entity.

### Consensus-based replication
Distributed SQL databases (Spanner, CockroachDB, YugabyteDB) and coordination systems (etcd, ZooKeeper, Kafka KRaft) replicate each range/partition with **Raft/Paxos**: a write commits when a majority acknowledges. This gives strong consistency and automatic failover without split brain, at the cost of latency bound by the round trip to a majority (cross-region writes pay inter-region RTT).

### Practical checklist
* Define RPO (acceptable data loss) and RTO (recovery time) per dataset; choose sync/async accordingly.
* Monitor replication lag (`pg_stat_replication.replay_lag`, MongoDB `rs.printSecondaryReplicationInfo()`, Cassandra hints/repair status) and alert on it.
* Test failover regularly (game days) including application reconnection behavior.
* Replicas are not backups: a `DELETE` without `WHERE` replicates instantly. Keep point-in-time recovery backups.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Replication copies data for availability, read scaling, latency and DR. Single-leader is simplest; multi-leader enables multi-region writes but needs conflict resolution; leaderless uses quorums with R + W > N. Async replication causes lag anomalies like read-your-writes violations and possible data loss on failover; consensus-based systems avoid split brain at the cost of majority round trips.

**Must know:**
* Single-leader vs multi-leader vs leaderless.
* Sync vs async; RPO trade-off.
* Lag anomalies and fixes (leader reads, session pinning, LSN tracking).
* Quorums `R + W > N`.
* Split brain, fencing, LWW vs CRDTs, Raft.

**Common follow-ups:**
* A user doesn't see their own update — why?
* How would you route reads to replicas in Spring?
* How does Cassandra stay consistent with QUORUM?

**Red flags:** "replicas are our backup"; reading critical data from async replicas right after writes; LWW for money.
