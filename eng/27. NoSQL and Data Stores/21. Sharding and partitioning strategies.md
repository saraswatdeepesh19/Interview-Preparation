# Sharding and partitioning strategies

---

## 🟢 Junior Level

* **Partitioning** splits a large dataset into smaller pieces.
* **Sharding** is horizontal partitioning across **multiple machines**: each shard holds a subset of rows and handles its part of the load.

You shard when one machine can no longer hold the data or serve the read/write throughput. The **shard key** (partition key) decides which shard a row belongs to.

### Main strategies

| Strategy | How a key maps to a shard | Pros | Cons |
| --- | --- | --- | --- |
| **Range** | `customer_id 1–1M → shard A, 1M–2M → B` | Efficient range scans | Hotspots on recent/sequential keys |
| **Hash** | `hash(customer_id) mod N` | Even distribution | Range queries hit all shards; changing N reshuffles |
| **Consistent hashing** | Keys and nodes on a hash ring | Adding a node moves ~1/N of keys | Needs virtual nodes for balance |
| **Directory / lookup** | A mapping service says where each key lives | Flexible moves, per-tenant placement | Extra lookup, mapping service must be HA |
| **Geographic** | By region/country | Data residency, locality | Uneven sizes; cross-region queries |

## 🟡 Middle Level

### Choosing a shard key
A good shard key:
1. Has **high cardinality** (many distinct values).
2. Spreads **load evenly** (not only data — traffic too).
3. Matches the **dominant access pattern**, so most queries hit one shard.
4. Rarely changes for an entity (moving a row between shards is expensive).

Examples: `tenant_id` for B2B SaaS (queries are per tenant), `user_id` for social apps, `order_id` hash for order processing. Bad: `country` (a few huge values), `created_at` alone (all writes go to the newest range).

### Within one database: PostgreSQL partitioning
Partitioning a single big table on one server helps maintenance and query pruning even without sharding:

```sql
create table events (
  tenant_id  bigint      not null,
  created_at timestamptz not null,
  payload    jsonb
) partition by range (created_at);

create table events_2026_10 partition of events
  for values from ('2026-10-01') to ('2026-11-01');

-- queries with created_at predicates scan only matching partitions (partition pruning);
-- old data is removed by dropping a partition instead of a massive DELETE
```

### Distributed SQL and NoSQL do it for you
* Cassandra/ScyllaDB, DynamoDB: hash partitioning by partition key with automatic rebalancing.
* MongoDB: range or hashed shard keys with a balancer moving chunks.
* Citus (PostgreSQL extension), Vitess (MySQL), CockroachDB, YugabyteDB, Spanner: distributed SQL with sharding and (varying) distributed transactions.

## 🔴 Senior Level

### The hard parts
* **Cross-shard queries** — scatter-gather to all shards, then merge/sort/paginate in the router. Latency is the slowest shard (tail latency amplification). Design so hot queries are single-shard; send analytics to a warehouse.
* **Cross-shard transactions** — either avoid (co-locate data that changes together under the same shard key, e.g. all of a tenant's data), use a database with distributed transactions (2PC/consensus — slower), or use sagas with compensations.
* **Global uniqueness and IDs** — auto-increment per shard collides; use UUIDv7/ULID or Snowflake-style IDs, and enforce uniqueness of non-key attributes with a dedicated lookup table/shard.
* **Rebalancing** — `hash mod N` remaps almost every key when N changes. Use consistent hashing, or a fixed large number of **logical shards** (e.g. 4,096 slots like Redis Cluster's 16,384) mapped to physical nodes, so rebalancing moves whole slots.
* **Hot shards** — one tenant 100× bigger than others. Options: dedicated shard for big tenants (directory-based placement), sub-sharding a tenant by a secondary key, or salting keys.

### Online resharding playbook
1. Introduce logical shards / a routing layer early, even if all logical shards start on one physical database.
2. To move a logical shard: copy a snapshot, stream ongoing changes (CDC/logical replication), verify checksums, briefly block writes for that shard (or use dual-write with versioning), flip the routing entry, resume.
3. Keep the old copy read-only until verified, then drop it.

### Interview answer structure
"I'd shard by `tenant_id` because 95% of queries are tenant-scoped and tenants' data changes together, which keeps transactions single-shard. I'd use 1,024 logical shards mapped to 8 physical PostgreSQL clusters via a routing table, give the three largest tenants dedicated shards, generate IDs with UUIDv7, and run cross-tenant reports from a warehouse fed by CDC."

## 🎯 Interview Cheat Sheet

**30-second pitch:** Sharding splits data across machines by a shard key using range, hash, consistent hashing, directory or geo strategies. I pick a high-cardinality key matching the dominant access pattern so queries and transactions stay on one shard, use many logical shards over fewer physical ones for easy rebalancing, and handle cross-shard queries, global IDs and hot tenants explicitly.

**Must know:**
* Range vs hash vs consistent hashing vs directory.
* Shard key criteria: cardinality, even load, access pattern, stability.
* PostgreSQL declarative partitioning and pruning.
* Cross-shard queries/transactions; global IDs.
* Logical shards and online resharding with CDC.

**Common follow-ups:**
* What happens when you add a shard with `mod N`?
* How do you handle one huge tenant?
* Partitioning vs sharding?

**Red flags:** sharding before exhausting vertical scaling, read replicas and partitioning; timestamp-only shard keys; scatter-gather on hot paths.
