# Data modeling for access patterns and SQL to NoSQL migration pitfalls

---

## 🟢 Junior Level

Relational modeling starts from the **data**: normalize entities into tables, then write whatever queries you need with joins. NoSQL modeling (DynamoDB, Cassandra, MongoDB to a lesser degree) starts from the **queries**: list the access patterns first, then shape the data so each pattern is one cheap lookup.

### Example: orders
Access patterns:
1. Get an order by ID with its lines.
2. List a customer's orders, newest first, paginated.
3. List orders by status for a warehouse dashboard.

```text
Relational (normalized)              Query-first (Cassandra-style)
customers(id, ...)                   orders_by_id(order_id PK, customer_id, status, lines frozen<list<line>>, ...)
orders(id, customer_id, status, ...) orders_by_customer((customer_id), created_at DESC, order_id, total)
order_lines(order_id, sku, qty)      orders_by_status((status, day), created_at, order_id)
```

The same order is written to **three** tables (denormalization), so each read is a single-partition query. Writes become more complex; reads become fast and predictable.

## 🟡 Middle Level

### Modeling principles for wide-column / key-value stores
* **One query, one table (or index)** — duplicate data freely; storage is cheap, cross-partition queries are not.
* **Partition key = how you look it up; clustering/sort key = how you order and range-scan within it.**
* **Bound partitions** — a partition that grows forever (all events of a device) must be bucketed: `((device_id, month), ts)`.
* **Precompute aggregates** you'd otherwise compute with `GROUP BY` (counters, daily totals).

### Document stores (MongoDB)
Embed what you read together and what has bounded size; reference what is shared, unbounded, or updated independently:

```javascript
// Embedded lines: read with the order, bounded size, owned by the order
{ _id: "o-42", customerId: "c-7", status: "PAID",
  lines: [ { sku: "A1", qty: 2, price: 10.0 }, { sku: "B2", qty: 1, price: 25.0 } ] }

// Referenced customer: shared by many orders, updated independently
{ _id: "c-7", name: "Ada", email: "ada@example.com" }
```

The 16 MB document limit and update patterns (concurrent edits to one big document) decide where embedding stops.

## 🔴 Senior Level

### Migration pitfalls from SQL to NoSQL
1. **Lifting tables 1:1** — copying normalized tables into DynamoDB/Cassandra and doing "joins" in application code: N+1 network calls, no transactions, worse than the original.
2. **Unknown access patterns** — NoSQL models are optimized for known queries. Ad-hoc reporting ("revenue by region by week") that SQL answered with one query now needs an export to an analytics store. Plan that pipeline up front (CDC → data lake/warehouse).
3. **Lost constraints** — no foreign keys, no `UNIQUE` across items, no `CHECK`. Uniqueness needs explicit patterns (DynamoDB: a separate `EMAIL#ada@x.com` item written in the same transaction with `attribute_not_exists`; Cassandra: lightweight transactions `IF NOT EXISTS`, which are Paxos-based and slow).
4. **Lost transactions** — multi-entity invariants (debit A, credit B) now need conditional writes, limited transactions, or sagas. Some invariants become eventually consistent — the business must accept that.
5. **Denormalization drift** — the same customer name stored in 5 tables; updates miss some. Decide which copies may be stale, update via events, and accept or design for staleness.
6. **Hot partitions** — low-cardinality keys (`status`, `country`, `date`) concentrate load. Add bucketing or composite keys.
7. **Tombstones and deletes** (Cassandra) — delete-heavy queue-like tables create tombstones that slow reads and can hit `tombstone_failure_threshold`. Model queues in a queue, not in Cassandra.
8. **Pagination semantics** — no `OFFSET`; use the store's continuation tokens (`LastEvaluatedKey`, paging state), which also changes your API design.
9. **Schema evolution** — "schemaless" still has a schema in the code. Version documents (`schemaVersion` field), write readers that handle old versions, migrate lazily or with backfill jobs.
10. **Cost model surprises** — paying per read/write unit (DynamoDB) or per node; full scans and large items become expensive.

### Safe migration strategy
* Write down all access patterns with expected QPS and latency **before** designing the model; review them with the business for missing reports.
* **Dual-run**: keep SQL as the source of truth, stream changes via CDC into the new store, compare query results (shadow reads) until confident.
* Switch reads first, then writes; keep a rollback path (reverse CDC or dual writes behind a flag) until the old system is retired.
* Move **only** the parts that need NoSQL characteristics; keep transactional core data relational if it doesn't.

## 🎯 Interview Cheat Sheet

**30-second pitch:** In NoSQL you model from access patterns: one cheap single-partition lookup per query, with denormalized copies and precomputed aggregates, bounded partitions and well-distributed keys. Migrating from SQL fails when teams copy tables 1:1, forget ad-hoc reporting, lose constraints and transactions, create hot partitions or ignore denormalization drift. I list access patterns first, dual-run via CDC with shadow reads, and only move workloads that need NoSQL properties.

**Must know:**
* Query-first design; partition vs clustering/sort key.
* Denormalization and its consistency cost.
* Bucketing unbounded partitions.
* Uniqueness and invariants without constraints.
* CDC-based dual-run migration.

**Common follow-ups:**
* How do you enforce unique emails in DynamoDB?
* How do you support analytics after moving to Cassandra?
* Embed or reference in MongoDB?

**Red flags:** "NoSQL is schemaless so no design needed"; joins in application loops; low-cardinality partition keys.
