# Graph databases and Neo4j basics

---

## 🟢 Junior Level

A **graph database** stores data as **nodes** (entities) and **relationships** (edges) between them, both of which can have properties. It is designed for queries that follow connections: "friends of friends", "which accounts share a device with this fraudulent one", "shortest route between two stations".

**Neo4j** is the most widely used graph database. It uses the **labeled property graph** model and the **Cypher** query language.

```cypher
// Create data
CREATE (ada:Person {name: 'Ada'})-[:FOLLOWS {since: 2024}]->(bob:Person {name: 'Bob'}),
       (bob)-[:FOLLOWS]->(cy:Person {name: 'Cy'}),
       (ada)-[:LIKES]->(:Product {sku: 'A1', name: 'Keyboard'});

// Who do the people Ada follows follow (friend-of-friend recommendations)?
MATCH (me:Person {name: 'Ada'})-[:FOLLOWS]->(:Person)-[:FOLLOWS]->(suggestion:Person)
WHERE NOT (me)-[:FOLLOWS]->(suggestion) AND me <> suggestion
RETURN suggestion.name, count(*) AS mutuals
ORDER BY mutuals DESC LIMIT 10;
```

### When graphs shine
Highly connected data where relationships are first-class and queries traverse a variable number of hops: social networks, recommendations, fraud rings, network/IT topology, knowledge graphs, access control (who can reach what through group nesting), supply chains.

## 🟡 Middle Level

### Why not just SQL joins?
In a relational database, each hop is a join over an index: cost grows with table sizes (`O(log n)` index lookups per hop, repeated). Variable-depth traversals need recursive CTEs that get slow and hard to optimize. Graph databases use **index-free adjacency**: each node stores direct pointers to its relationships, so a hop costs roughly `O(degree)` regardless of total graph size.

```sql
-- 3-hop "friends of friends of friends" in SQL: recursive CTE, expensive at scale
with recursive reach(person_id, depth) as (
  select followee_id, 1 from follows where follower_id = :me
  union
  select f.followee_id, r.depth + 1 from follows f join reach r on f.follower_id = r.person_id where r.depth < 3
)
select distinct person_id from reach;
```

```cypher
MATCH (me:Person {id: $me})-[:FOLLOWS*1..3]->(p:Person) RETURN DISTINCT p;
```

### Modeling tips
* **Nodes** for entities, **relationships** with verbs (`:PURCHASED`, `:MEMBER_OF`); relationship types are cheap — be specific instead of a generic `:RELATED_TO {type:...}`.
* Put properties needed for filtering traversals on relationships (`since`, `weight`).
* Create **indexes/constraints** on lookup properties used to find starting nodes: `CREATE CONSTRAINT person_id FOR (p:Person) REQUIRE p.id IS UNIQUE`.

### Spring Data Neo4j

```java
@Node("Person")
public class Person {
    @Id private String id;
    private String name;
    @Relationship(type = "FOLLOWS", direction = Relationship.Direction.OUTGOING)
    private Set<Person> follows = new HashSet<>();
}

public interface PersonRepository extends Neo4jRepository<Person, String> {
    @Query("MATCH (me:Person {id: $id})-[:FOLLOWS]->()-[:FOLLOWS]->(s:Person) " +
           "WHERE NOT (me)-[:FOLLOWS]->(s) AND me <> s RETURN s, count(*) AS c ORDER BY c DESC LIMIT 10")
    List<Person> suggestions(String id);
}
```

Be careful with mapped relationships: loading a `Person` with all `follows` can pull huge subgraphs — use projections and custom queries.

## 🔴 Senior Level

### Performance realities
* **Supernodes** — nodes with millions of relationships (a celebrity, a "country = US" node) make traversals through them expensive. Mitigate by relationship-type specificity, splitting by time or category, or avoiding modeling low-cardinality attributes as nodes.
* **Unbounded variable-length patterns** (`[:FOLLOWS*]`) can explode combinatorially; always bound depth and filter early. Use `PROFILE`/`EXPLAIN` to inspect plans (db hits, rows per operator).
* **Write scaling**: Neo4j's clustering (causal clustering / Autonomous Clustering in v5) replicates for reads and HA; writes go through a leader per database. Sharding a graph is fundamentally hard (cross-shard traversals); Neo4j Fabric/composite databases help for naturally partitioned graphs.

### Graph algorithms
The Graph Data Science library runs algorithms in memory on projected graphs: PageRank (influence), Louvain/Leiden (community detection, fraud rings), shortest path/A*, node similarity, link prediction. A common architecture: OLTP in a relational/document store, periodically projected into a graph for analysis and recommendations, results written back.

### Alternatives and the decision
* RDF triple stores (SPARQL) for semantic web/ontology use cases.
* Amazon Neptune (property graph with openCypher/Gremlin and RDF), JanusGraph, TigerGraph, Memgraph.
* PostgreSQL with recursive CTEs or Apache AGE for modest graph needs inside an existing relational system.

Choose a graph database when traversals of variable depth are the **core** of the workload. If relationships are mostly 1–2 fixed hops (orders → lines → products), a relational database with indexes is simpler and faster to operate.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Graph databases store nodes and relationships with properties and use index-free adjacency, so traversals cost per hop rather than per table size. Neo4j uses the labeled property graph model and Cypher. They excel at recommendations, fraud rings, access paths and topology; the risks are supernodes, unbounded traversals and limited write sharding.

**Must know:**
* Nodes, relationships, labels, properties; Cypher `MATCH` patterns.
* Index-free adjacency vs join cost.
* Variable-length paths `*1..3` with bounded depth.
* Constraints/indexes for starting nodes; `PROFILE`.
* Supernodes; GDS algorithms.

**Common follow-ups:**
* How would you detect fraud rings?
* Graph DB vs recursive CTEs in PostgreSQL?
* How does a graph database scale writes?

**Red flags:** modeling everything as a graph "because relationships"; unbounded `*` traversals; loading entire subgraphs into Java objects.
