# DynamoDB basics

---

## 🟢 Junior Level

**Amazon DynamoDB** is a fully managed, serverless **key-value and document database**. You don't run servers, choose instance sizes or patch anything; you create a **table** and read/write **items** by key with single-digit-millisecond latency at virtually any scale.

### Core concepts
* **Table** — collection of items (no fixed schema except the key).
* **Item** — a record, up to **400 KB**, made of attributes (string, number, binary, boolean, list, map, set).
* **Primary key**, one of:
  * **Partition key** only (`userId`), or
  * **Partition key + sort key** (`customerId` + `orderDate`) — items with the same partition key are stored together, sorted by the sort key.

```java
// AWS SDK v2 enhanced client
@DynamoDbBean
public class Order {
    private String customerId;   // partition key
    private String orderId;      // sort key, e.g. "2026-10-16#o-42"
    private BigDecimal total;

    @DynamoDbPartitionKey public String getCustomerId() { return customerId; }
    @DynamoDbSortKey      public String getOrderId()    { return orderId; }
    // getters/setters...
}

DynamoDbTable<Order> orders = enhanced.table("orders", TableSchema.fromBean(Order.class));
orders.putItem(order);

// All orders of a customer in October 2026, newest first
QueryConditional q = QueryConditional.sortBeginsWith(
        Key.builder().partitionValue("c-7").sortValue("2026-10").build());
orders.query(r -> r.queryConditional(q).scanIndexForward(false)).items().forEach(System.out::println);
```

## 🟡 Middle Level

### Access-pattern-first modeling
DynamoDB has no joins and no ad-hoc queries over non-key attributes (a **Scan** reads the whole table — expensive and slow). You design keys around the queries you need:
* `Query` — by partition key, optionally with a sort-key condition (`=`, `<`, `between`, `begins_with`). Efficient.
* `GetItem` / `BatchGetItem` — by full primary key.
* **Global Secondary Index (GSI)** — a different partition/sort key over the same data, maintained asynchronously (eventually consistent), with its own capacity.
* **Local Secondary Index (LSI)** — same partition key, different sort key; must be defined at table creation; strongly consistent reads possible; 10 GB limit per partition key value.

### Capacity modes
* **On-demand** — pay per request; scales instantly to traffic (with limits on sudden spikes relative to previous peaks). Good default for unpredictable workloads.
* **Provisioned** — you set read/write capacity units (RCU/WCU), optionally with auto scaling; cheaper for steady traffic.
  * 1 WCU = one write/s of an item up to 1 KB.
  * 1 RCU = one strongly consistent read/s (or two eventually consistent reads) of up to 4 KB.

### Consistency and transactions
* Reads are **eventually consistent** by default; `ConsistentRead=true` gives strong consistency on the base table (not on GSIs), at 2× read cost.
* **Conditional writes** (`attribute_not_exists(pk)`, `version = :expected`) give optimistic locking and uniqueness.
* **TransactWriteItems** — ACID across up to 100 items (in the same Region), at 2× the cost of normal writes.

## 🔴 Senior Level

### Partitions and hot keys
DynamoDB splits data into partitions by hashing the partition key. Each partition supports roughly **3,000 RCU and 1,000 WCU per second**; adaptive capacity shifts throughput to hot partitions, but a single partition key value can't exceed those limits. Design partition keys with high cardinality and even access; for hot keys use **write sharding** (`counter#<0..9>`) and aggregate on read.

### Single-table design
Experienced teams often store multiple entity types in one table with generic keys (`PK`, `SK`) so related items can be fetched in one `Query`:

| PK | SK | Attributes |
| --- | --- | --- |
| `CUSTOMER#c-7` | `PROFILE` | name, email |
| `CUSTOMER#c-7` | `ORDER#2026-10-16#o-42` | total, status |
| `ORDER#o-42` | `LINE#1` | sku, qty |
| GSI1PK=`STATUS#SHIPPED` | GSI1SK=`2026-10-16#o-42` | (overloaded GSI for "orders by status") |

Pros: fewer round trips, transactional updates across related items. Cons: harder to understand, migrations are painful, analytics need exports (DynamoDB → S3 export, then Athena). For simpler domains, one table per entity is fine.

### Streams, TTL and integration
* **DynamoDB Streams** — ordered change log per partition key (24 h retention), consumed by Lambda or Kinesis adapters: build outbox-style event publishing, materialized views, search indexing (OpenSearch), or cross-region replication.
* **TTL** attribute — items expire automatically (deletion happens asynchronously, typically within a couple of days of expiry; filter expired items in queries).
* **Global Tables** — multi-Region, multi-active replication with last-writer-wins conflict resolution; design for idempotent, commutative updates if writes may hit two Regions.

### Pitfalls
* Using `Scan` with `FilterExpression` for application queries — you pay for every item read before filtering.
* Large items (approaching 400 KB) inflate RCU/WCU costs; store blobs in S3 and keep a pointer.
* Unbounded item collections under one partition key (time series of years) — bucket by time (`sensor#42#2026-10`).
* Pagination: queries return at most 1 MB per page; always follow `LastEvaluatedKey`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** DynamoDB is a managed, serverless key-value/document store with predictable millisecond latency. You model by access patterns: partition key (+ sort key) for primary queries, GSIs for alternative ones, no joins, and avoid scans. Capacity is on-demand or provisioned in RCU/WCU; it offers conditional writes, transactions, streams, TTL and global tables, and hot partition keys are the main scaling risk.

**Must know:**
* Partition key vs partition + sort key; `Query` vs `Scan`.
* GSI (eventually consistent, any time) vs LSI (creation time, strongly consistent).
* RCU/WCU math; on-demand vs provisioned.
* Conditional writes, `TransactWriteItems`.
* Partition throughput limits; write sharding; single-table design.

**Common follow-ups:**
* How would you model orders by customer and by status?
* How do you implement optimistic locking?
* When is DynamoDB a bad fit?

**Red flags:** designing tables like normalized SQL; scans in request paths; low-cardinality partition keys like `status`.
