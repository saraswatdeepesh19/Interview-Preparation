# What are binary search trees and balanced trees

---

## 🟢 Junior Level

A **binary search tree (BST)** is a binary tree with an ordering rule: for every node, all values in its **left** subtree are smaller and all values in its **right** subtree are larger. That makes search, insert and delete work like binary search:

```java
TreeNode search(TreeNode node, int target) {
    while (node != null && node.val != target) {
        node = target < node.val ? node.left : node.right;
    }
    return node;
}

TreeNode insert(TreeNode node, int val) {
    if (node == null) return new TreeNode(val);
    if (val < node.val) node.left = insert(node.left, val);
    else if (val > node.val) node.right = insert(node.right, val);
    return node;                                  // duplicates ignored
}
```

Operations cost **O(h)** where h is the height:
* **Balanced** tree: h ≈ log₂ n → about 20 steps for a million nodes.
* **Degenerate** tree (inserting sorted data 1, 2, 3, ...): h = n → it's a linked list, O(n) per operation.

**Balanced BSTs** (AVL, red-black trees) automatically restructure on insert/delete to keep h = O(log n).

## 🟡 Middle Level

### Delete (three cases)

```java
TreeNode delete(TreeNode node, int key) {
    if (node == null) return null;
    if (key < node.val) node.left = delete(node.left, key);
    else if (key > node.val) node.right = delete(node.right, key);
    else {
        if (node.left == null) return node.right;          // 0 or 1 child
        if (node.right == null) return node.left;
        TreeNode succ = node.right;                         // 2 children: inorder successor
        while (succ.left != null) succ = succ.left;
        node.val = succ.val;
        node.right = delete(node.right, succ.val);
    }
    return node;
}
```

### Validating a BST
Comparing each node with its children isn't enough — the rule applies to whole subtrees. Pass bounds down:

```java
boolean isValid(TreeNode n, Long lo, Long hi) {
    if (n == null) return true;
    if ((lo != null && n.val <= lo) || (hi != null && n.val >= hi)) return false;
    return isValid(n.left, lo, (long) n.val) && isValid(n.right, (long) n.val, hi);
}
// isValid(root, null, null)
```

### BSTs in the JDK
`TreeMap` and `TreeSet` are **red-black trees**: O(log n) `put`, `get`, `remove`, plus ordered operations a `HashMap` can't do:

```java
TreeMap<Integer, String> prices = new TreeMap<>();
prices.put(100, "basic"); prices.put(250, "pro"); prices.put(500, "enterprise");

prices.floorKey(300);          // 250 — largest key ≤ 300
prices.ceilingEntry(260);      // 500=enterprise — smallest key ≥ 260
prices.headMap(250);           // {100=basic} — keys < 250
prices.subMap(100, true, 300, true);   // range view
prices.firstKey(); prices.pollLastEntry();
```

Use them for range queries, "nearest" lookups, sliding-window ordered sets, and leaderboards.

## 🔴 Senior Level

### AVL vs red-black trees

| | AVL | Red-black |
| --- | --- | --- |
| Balance rule | Height difference of children ≤ 1 at every node | Coloring rules; longest path ≤ 2 × shortest |
| Height | ≤ ~1.44 log₂ n | ≤ 2 log₂(n+1) |
| Lookups | Slightly faster (shorter trees) | Slightly slower |
| Insert/delete | More rotations | ≤ 2 rotations per insert, ≤ 3 per delete |
| Used in | Databases/in-memory indexes needing fast reads | `TreeMap`, `HashMap` bins (treeified), Linux CFS scheduler, C++ `std::map` |

Rotations are local pointer rewirings that preserve inorder order; interviewers rarely ask for full red-black code but may ask how a rotation works or why `HashMap` treeifies buckets with ≥ 8 entries (to bound worst-case lookups at O(log n) under many collisions).

### Order-statistic and augmented trees
Augment each node with subtree size to answer "k-th smallest" and "rank of x" in O(log n); augment with max endpoint for **interval trees** (find overlapping intervals). The JDK has no order-statistic tree — in interviews, mention the augmentation; in production, use a skip list, Fenwick tree, or database index depending on the need.

### B-trees: BSTs for disks
Databases (PostgreSQL, MySQL InnoDB) use **B+ trees**, not binary trees: each node holds hundreds of keys sized to a disk/memory page (8–16 KB), so height stays at 3–4 for billions of rows, minimizing page reads. Leaves are linked for efficient range scans. Binary trees would need ~30 page reads per lookup for a billion keys.

### Concurrency
`TreeMap` isn't thread-safe. `ConcurrentSkipListMap` provides a sorted, concurrent `NavigableMap` with expected O(log n) operations using lock-free skip lists — preferred over synchronizing a `TreeMap` in concurrent code.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A BST keeps smaller values left and larger right, giving O(h) search, insert and delete; unbalanced trees degrade to O(n), so AVL and red-black trees rebalance with rotations to keep O(log n). Java's `TreeMap`/`TreeSet` are red-black trees with floor/ceiling/range operations, `ConcurrentSkipListMap` is the concurrent sorted map, and databases use B+ trees optimized for pages.

**Must know:**
* BST property applies to whole subtrees; validate with bounds.
* Delete cases: leaf, one child, two children (successor).
* Balanced vs degenerate height.
* `TreeMap` navigation methods.
* AVL vs red-black trade-off; B+ trees in databases.

**Common follow-ups:**
* Find the k-th smallest element in a BST.
* Why does `HashMap` use red-black trees?
* Why do databases use B+ trees instead of binary trees?

**Red flags:** validating a BST by checking only immediate children; assuming BST operations are always O(log n).
