# What are consistent hashing bloom filters and skip lists

---

## 🟢 Junior Level

Three data structures that show up constantly in distributed systems and databases:

* **Consistent hashing** — distributes keys across servers so that adding or removing a server moves only a **small fraction** of keys (≈ 1/N), not almost all of them as with `hash(key) % N`.
* **Bloom filter** — a compact bit array that answers "is this element **possibly** in the set?" with **no false negatives** and a tunable rate of **false positives**. Used to skip expensive lookups.
* **Skip list** — a sorted linked list with extra "express lanes" of pointers at multiple levels, giving O(log n) expected search, insert and delete — a simpler alternative to balanced trees that's easy to make concurrent.

| Structure | Used in |
| --- | --- |
| Consistent hashing | Cassandra/DynamoDB partitioning, Memcached clients, load balancers, Akka/Envoy ring hash |
| Bloom filter | Cassandra/RocksDB SSTables, HBase, CDN caches, Chrome safe browsing, PostgreSQL bloom index |
| Skip list | Redis sorted sets (`ZSET`), Java `ConcurrentSkipListMap`, LevelDB/RocksDB memtables |

## 🟡 Middle Level

### Consistent hashing with virtual nodes

```java
public class ConsistentHashRing<N> {
    private final NavigableMap<Long, N> ring = new TreeMap<>();
    private final int virtualNodes;

    public ConsistentHashRing(Collection<N> nodes, int virtualNodes) {
        this.virtualNodes = virtualNodes;
        nodes.forEach(this::add);
    }

    public void add(N node) {
        for (int i = 0; i < virtualNodes; i++) ring.put(hash(node + "#" + i), node);
    }

    public void remove(N node) {
        for (int i = 0; i < virtualNodes; i++) ring.remove(hash(node + "#" + i));
    }

    public N nodeFor(String key) {
        Map.Entry<Long, N> e = ring.ceilingEntry(hash(key));      // first node clockwise
        return (e != null ? e : ring.firstEntry()).getValue();    // wrap around
    }

    private static long hash(String s) {                            // 64-bit hash (e.g. Murmur3/xxHash in practice)
        byte[] d = sha256(s);
        return ByteBuffer.wrap(d).getLong();
    }
}
```

**Virtual nodes** (100–200 per physical node) smooth out the distribution and let heterogeneous servers take proportional load (more virtual nodes for bigger machines).

### Bloom filter basics
A bit array of size *m* and *k* hash functions. Add: set the *k* bit positions. Query: if any of the *k* bits is 0 → **definitely not present**; if all are 1 → **probably present**.

```java
BloomFilter<String> seen = BloomFilter.create(
        Funnels.stringFunnel(StandardCharsets.UTF_8), 10_000_000, 0.01);   // Guava: 10M items, 1% FPP
seen.put("user:42");
seen.mightContain("user:42");   // true
seen.mightContain("user:99");   // false (or rarely true)
```

Sizing: `m ≈ -n·ln(p) / (ln 2)²` bits and `k ≈ (m/n)·ln 2`. For 1% false positives you need about **9.6 bits per element** and 7 hash functions — 10 million items in ~12 MB.

### Skip list intuition
Level 0 is a sorted linked list of all elements; each element is promoted to the next level with probability ½ (or ¼). Search starts at the top level, moves right while the next key is smaller, then drops down. Expected height is O(log n), so search is O(log n).

## 🔴 Senior Level

### Consistent hashing in production
* **Replication**: store each key on the next R distinct physical nodes clockwise (Dynamo/Cassandra style).
* **Alternatives**: **rendezvous (HRW) hashing** — pick the node with the highest `hash(key, node)`; simple, no ring, O(N) per lookup; **jump consistent hash** (Google) — O(log N), no memory, but nodes must be numbered and removed only from the end; **Maglev hashing** for load balancers (fast lookup tables with minimal disruption).
* **Bounded loads**: "consistent hashing with bounded loads" caps any node at (1 + ε) × average to handle hot keys (used in HAProxy, Vimeo's load balancing).
* **Cassandra** now uses token allocation algorithms rather than purely random vnodes (`num_tokens` lowered to 16 with a smarter allocator) to balance ownership with fewer tokens.

### Bloom filter limitations and variants
* No deletion in a standard Bloom filter (clearing a bit could remove other elements). **Counting Bloom filters** (counters instead of bits) or **Cuckoo filters** support deletes and have better space efficiency at low FPP.
* False-positive rate increases as the filter fills beyond its design capacity — size for the expected maximum, or use **scalable Bloom filters**.
* Use cases in backend design: avoid DB lookups for non-existent keys (cache penetration attacks: requests for random IDs that bypass the cache), "has this user seen this item?" for feeds, deduplicating crawled URLs, LSM-tree read optimization (Cassandra's `bloom_filter_fp_chance` per table). RedisBloom provides server-side filters (`BF.ADD`, `BF.EXISTS`).

### Why Redis and `ConcurrentSkipListMap` use skip lists
* **Range operations** (`ZRANGEBYSCORE`, `subMap`) are natural: find the start, walk level 0.
* **Simpler code** than red-black trees, with comparable performance; Redis augments level pointers with *span* counts to get O(log n) **rank** queries (`ZRANK`).
* **Concurrency**: lock-free skip lists (CAS on next pointers, logical deletion markers) are much easier to implement than lock-free balanced trees — that's why the JDK's concurrent sorted map is a skip list.
* Trade-off: more pointers per node (memory) and probabilistic, not worst-case, guarantees.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Consistent hashing places nodes and keys on a hash ring so adding or removing a node moves only about 1/N of keys; virtual nodes balance load. Bloom filters answer set membership with no false negatives and a tunable false-positive rate — about 10 bits per element for 1% — to skip expensive lookups. Skip lists are probabilistic sorted structures with O(log n) operations and easy range queries and concurrency, used by Redis sorted sets and `ConcurrentSkipListMap`.

**Must know:**
* `hash % N` reshuffling problem; ring + `TreeMap.ceilingEntry`; virtual nodes.
* Rendezvous and jump hashing alternatives.
* Bloom sizing formulas; no deletes; counting/cuckoo filters.
* Skip list levels and expected O(log n).
* Where each is used (Cassandra, RocksDB, Redis, JDK).

**Common follow-ups:**
* How do you handle a hot key with consistent hashing?
* How would you prevent cache penetration?
* Why does Redis use a skip list instead of a balanced tree?

**Red flags:** `hash % N` sharding for a cluster that scales; thinking Bloom filters can give false negatives.
