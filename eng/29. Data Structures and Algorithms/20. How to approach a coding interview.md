# How to approach a coding interview

---

## 🟢 Junior Level

A coding interview evaluates **how you think and communicate**, not just whether the final code compiles. Interviewers typically score: problem understanding, approach, correctness, code quality, testing, and communication.

### A reliable six-step process (≈ 45 minutes)

| Step | Time | What to do |
| --- | --- | --- |
| 1. Clarify | 3–5 min | Restate the problem, ask about input size, constraints, edge cases, expected output |
| 2. Examples | 2–3 min | Work through 1–2 small examples by hand, including an edge case |
| 3. Brute force | 2–3 min | State the obvious solution and its complexity — even if you won't code it |
| 4. Optimize | 5–10 min | Find the bottleneck; pick a pattern/data structure; agree on the approach |
| 5. Code | 15–20 min | Write clean code, narrating key decisions |
| 6. Test | 5 min | Walk through your examples, edge cases; state time/space complexity |

### Questions worth asking
* How large is the input? (n = 10³ allows O(n²); n = 10⁶ needs O(n log n) or better.)
* Can values be negative, duplicated, null, empty?
* Is the input sorted? Can I modify it?
* What should happen on invalid input?
* Should I optimize for time or memory?

## 🟡 Middle Level

### Map constraints to target complexity

| n | Acceptable complexity |
| --- | --- |
| ≤ 20 | O(2ⁿ), O(n!) — backtracking, bitmask DP |
| ≤ 500 | O(n³) |
| ≤ 5,000 | O(n²) |
| ≤ 10⁶ | O(n log n), O(n) |
| ≤ 10⁹ or streaming | O(log n), O(1) per element, or math |

### Pattern recognition cheat sheet

| Signal in the problem | Try |
| --- | --- |
| Sorted array, "find target/boundary" | Binary search |
| Contiguous subarray/substring with a condition | Sliding window, prefix sums |
| Pairs/triplets in sorted data | Two pointers |
| "Have I seen this before?", counting | HashMap/HashSet |
| Top-K, k-th largest, merge sorted streams | Heap |
| Nested structure, undo/next greater element | Stack / monotonic stack |
| Tree | DFS (pre/in/post) or BFS by level |
| Dependencies, connectivity, shortest path | Graph BFS/DFS, topological sort, Dijkstra, Union-Find |
| All combinations/permutations | Backtracking |
| Optimal value with overlapping subproblems | Dynamic programming |
| Intervals | Sort by start/end + sweep |

### Writing interview-quality Java
* Use meaningful names (`left`, `right`, `windowCount`), not `i2`, `tmp3`.
* Extract helpers (`inBounds`, `swap`) instead of copy-paste.
* Prefer `ArrayDeque`, `HashMap.merge`, `getOrDefault`, `Arrays.fill`, `Comparator.comparingInt`.
* Handle edge cases explicitly at the top (`if (nums == null || nums.length == 0) return 0;`).
* Avoid overflow: `long` for sums/products, `left + (right - left) / 2` for midpoints.

## 🔴 Senior Level

### What distinguishes strong candidates
* **Driving the conversation** — proposing an approach, stating trade-offs ("hash map gives O(n) time at O(n) memory; sorting gives O(1) extra memory at O(n log n)"), and confirming before coding.
* **Incremental correctness** — writing the core loop first, then edge cases; testing with a dry run, *finding their own bug* and fixing it calmly. Interviewers value self-correction.
* **Complexity precision** — including space for recursion stacks, output size, and hidden costs (`String +=` in loops is O(n²); `list.remove(0)` on `ArrayList` is O(n); `contains` on a `List` is O(n)).
* **Production instincts when relevant** — "in a real service I'd stream this rather than load 10 GB", "this recursion could overflow for deep inputs".

### When you're stuck
1. Go back to examples; solve a smaller case by hand and observe what you're doing.
2. Ask which pattern from the table fits; try "what if the input were sorted?" or "what do I need to know at each step?".
3. Say what you're thinking — interviewers can only help if they hear it; a hint taken well beats silence.
4. Deliver a working brute force rather than an unfinished optimal solution.

### Practice strategy
* Learn **patterns**, not individual problems: 8–10 problems per pattern until the template is automatic.
* Time-box practice to 30–40 minutes and review optimal solutions afterwards.
* Practice **out loud** and in a plain editor without autocomplete if the interview uses one.
* Mock interviews with peers to rehearse communication.

### Online/automated rounds
For platforms with hidden test cases: read input formats carefully, use fast I/O for large inputs (`BufferedReader`, `StreamTokenizer` instead of `Scanner`), watch for `int` overflow and recursion limits, and test boundary sizes (n = 1, maximum n).

### A solution skeleton that keeps you structured

```java
/**
 * Problem: longest substring without repeating characters.
 * Clarified: ASCII input, length up to 10^5, empty string -> 0.
 * Brute force: check all substrings O(n^3). Target: O(n) sliding window.
 */
public int lengthOfLongestSubstring(String s) {
    if (s == null || s.isEmpty()) return 0;          // edge cases first
    int[] lastSeen = new int[128];                   // ASCII: last index + 1 of each char
    int best = 0;
    for (int left = 0, right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        left = Math.max(left, lastSeen[c]);          // jump past the previous occurrence
        lastSeen[c] = right + 1;
        best = Math.max(best, right - left + 1);
    }
    return best;                                     // O(n) time, O(1) space (fixed alphabet)
}
// Dry run aloud: "abcabcbb" -> 3, "bbbbb" -> 1, "" -> 0, "pwwkew" -> 3
```

## 🎯 Interview Cheat Sheet

**30-second pitch:** I clarify the problem and constraints, work through examples, state a brute force with its complexity, then optimize by matching the problem to a pattern and agreeing on the approach before coding. I write clean, well-named Java with explicit edge cases, then dry-run tests and state time and space complexity — thinking aloud throughout.

**Must know:**
* Clarify → examples → brute force → optimize → code → test.
* Constraints → target complexity table.
* Pattern signals table.
* Java idioms and overflow-safe code.
* Self-testing and communicating trade-offs.

**Common follow-ups:**
* What if the input doesn't fit in memory?
* Can you reduce the space complexity?
* How would you test this function in production code?

**Red flags:** coding immediately without clarifying; silence; claiming complexity without justification; refusing hints.
