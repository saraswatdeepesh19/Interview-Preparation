# Mutation testing with PIT

---

## 🟢 Junior Level

**Mutation testing** checks how good your tests are by deliberately introducing small bugs (**mutants**) into the code and running the tests against each one:

* If at least one test **fails**, the mutant is **killed** — good, your tests noticed the bug.
* If all tests still **pass**, the mutant **survived** — your tests would not catch that bug.

**PIT (pitest)** is the standard mutation testing tool for Java.

```java
// Production code
boolean isAdult(int age) { return age >= 18; }

// A weak test: only checks one side
@Test void adult() { assertThat(isAdult(30)).isTrue(); }
```

PIT mutates `>=` into `>`. `isAdult(30)` is still true, so the test passes and the mutant **survives**. It reveals a missing boundary test:

```java
@Test void boundary() {
    assertThat(isAdult(18)).isTrue();
    assertThat(isAdult(17)).isFalse();
}
```

### Real-world analogy
A fire drill where someone secretly sets off one alarm at a time. If nobody reacts to an alarm, you've found a part of the building that isn't monitored.

## 🟡 Middle Level

### Running PIT with Maven and JUnit 5

```xml
<plugin>
  <groupId>org.pitest</groupId>
  <artifactId>pitest-maven</artifactId>
  <version>1.17.0</version>
  <dependencies>
    <dependency>
      <groupId>org.pitest</groupId>
      <artifactId>pitest-junit5-plugin</artifactId>
      <version>1.2.1</version>
    </dependency>
  </dependencies>
  <configuration>
    <targetClasses><param>com.shop.pricing.*</param></targetClasses>
    <targetTests><param>com.shop.pricing.*Test</param></targetTests>
    <mutators><mutator>STRONGER</mutator></mutators>
    <threads>4</threads>
    <mutationThreshold>75</mutationThreshold>
    <timestampedReports>false</timestampedReports>
  </configuration>
</plugin>
```

`mvn test-compile org.pitest:pitest-maven:mutationCoverage` produces an HTML report showing each surviving mutant inline in the source.

### Common mutators
* `CONDITIONALS_BOUNDARY` — `<` ↔ `<=`, `>` ↔ `>=`.
* `NEGATE_CONDITIONALS` — `==` ↔ `!=`, `<` ↔ `>=`.
* `MATH` — `+` ↔ `-`, `*` ↔ `/`.
* `VOID_METHOD_CALLS` — remove a call to a `void` method (e.g. `audit.log(...)`).
* Return value mutators — `return true` → `false`, empty collections, `null`, `0`.
* `INCREMENTS`, `INVERT_NEGS`, `REMOVE_CONDITIONALS` (in STRONGER/ALL groups).

### Reading the results
* **Line coverage vs mutation coverage**: PIT reports both. 95% line coverage with 50% mutation score means the tests execute code but don't assert enough.
* **Survived** mutants need either a better assertion or a decision that the mutated behavior is irrelevant.
* **No coverage** mutants are in code no test even runs.
* **Timed out** mutants (e.g. a loop condition became infinite) count as killed.

## 🔴 Senior Level

### How PIT stays practical
Naively, N mutants × full suite runs is prohibitively slow. PIT optimizes:
1. **Coverage analysis first** — it records which tests execute which lines, and runs only those tests against a mutant.
2. **Bytecode mutation in memory** — mutants are created by rewriting bytecode with ASM inside forked minion JVMs; no recompilation.
3. **Test prioritization** — fastest covering tests run first; the first failure kills the mutant and stops.
4. **Incremental analysis** — `withHistory=true` reuses results for unchanged classes/tests between runs.

Even so, run full mutation analysis nightly or on critical modules; in PRs, run only on changed code (`pitest` with `features=+GIT(from[HEAD~1])` via the Arcmutate git plugin, or scope `targetClasses` to changed packages).

### Equivalent mutants
Some mutants cannot be killed because they don't change observable behavior:

```java
for (int i = 0; i < list.size(); i++) { ... }   // mutating to i != list.size() is equivalent here
```

PIT can't detect equivalence in general (undecidable), so 100% mutation score is rarely realistic. Treat survivors as review prompts, not mandatory work; mark known-acceptable ones by excluding methods (`excludedMethods`) such as `toString`, `hashCode`, logging helpers.

### Where mutation testing pays off most
* Pricing, tax, interest and fee calculations (boundaries, rounding).
* Authorization rules (`hasRole` checks — a removed condition is a security bug).
* State machines and validation logic.
* Libraries used by many teams.

Low value: controllers, DTO mapping, configuration, code already covered by contract tests.

### Typical findings in mature codebases
* `verify()` missing on side-effect calls — `VOID_METHOD_CALLS` mutants survive (the audit log call can be deleted without failing a test).
* Tests asserting only `isNotNull()` — return-value mutants survive.
* Boundary values untested (`>` vs `>=` on limits and dates).
* Exceptions caught and ignored in tests via `assertThatCode(...).doesNotThrowAnyException()` without checking state.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Mutation testing injects small bugs and checks whether the test suite fails; PIT does this at bytecode level and runs only covering tests per mutant. The mutation score measures assertion strength, which line coverage can't. I use it on critical business logic, ideally incrementally on changed code.

**Must know:**
* Killed vs survived vs no coverage vs timed out.
* Common mutators: boundaries, negated conditionals, math, removed void calls, return values.
* Equivalent mutants make 100% unrealistic.
* Performance: coverage-targeted test selection, incremental history.

**Common follow-ups:**
* Coverage 90% but mutation score 40% — what does it mean?
* How do you run PIT in CI without slowing every build?
* What's an equivalent mutant?

**Red flags:** treating mutation score as a vanity metric; running full PIT on the whole monolith on every commit.
