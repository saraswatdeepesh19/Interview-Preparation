# JUnit 5 parameterized tests nested classes and extensions

---

## 🟢 Junior Level

JUnit 5 has three features that remove boilerplate and structure large test suites:

1. **Parameterized tests** - run one test method with many inputs.
2. **Nested tests** (`@Nested`) - group related tests in inner classes that mirror scenarios.
3. **Extensions** (`@ExtendWith`) - plug reusable behaviour (setup, parameter injection, conditions) into tests.

### Analogy
A parameterized test is a recipe cooked with different ingredients. `@Nested` is chapters of a cookbook (starters, desserts). An extension is a kitchen assistant who prepares the oven and cleans up every time.

### Parameterized test example
Dependency: `org.junit.jupiter:junit-jupiter-params` (included in the aggregate `junit-jupiter`).

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import static org.junit.jupiter.api.Assertions.assertTrue;

class PalindromeTest {

    static boolean isPalindrome(String s) {
        return new StringBuilder(s).reverse().toString().equals(s);
    }

    @ParameterizedTest
    @ValueSource(strings = {"level", "noon", "a", ""})
    void detectsPalindromes(String candidate) {
        assertTrue(isPalindrome(candidate));
    }
}
```

Each value appears as its own test in the report. Failing for `"x"` shows exactly which input broke.

### Nested example

```java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class StackBehaviourTest {

    Deque<Integer> stack;

    interface Deque<T> { boolean isEmpty(); void push(T t); }

    @Nested
    @DisplayName("when new")
    class WhenNew {
        java.util.ArrayDeque<Integer> d = new java.util.ArrayDeque<>();

        @Test void isEmpty() { assertTrue(d.isEmpty()); }

        @Nested
        @DisplayName("after push")
        class AfterPush {
            @BeforeEach void push() { d.push(1); }
            @Test void isNotEmpty() { assertFalse(d.isEmpty()); }
        }
    }
}
```

## 🟡 Middle Level

### Argument sources

| Source | Use |
|---|---|
| `@ValueSource` | single primitive/String/Class values |
| `@EnumSource` | enum constants (`names`, `mode = EXCLUDE`) |
| `@NullSource`, `@EmptySource`, `@NullAndEmptySource` | null/empty edge cases |
| `@CsvSource` | inline CSV rows |
| `@CsvFileSource` | CSV in `src/test/resources` |
| `@MethodSource` | any `Stream<Arguments>` from a factory method |
| `@ArgumentsSource` | custom `ArgumentsProvider` |

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.*;
import java.util.stream.Stream;
import static org.assertj.core.api.Assertions.assertThat;

class DiscountTest {

    static int discount(int age) { return age < 12 ? 50 : age >= 65 ? 30 : 0; }

    @ParameterizedTest(name = "age {0} -> {1}% discount")
    @CsvSource({"5,50", "11,50", "12,0", "64,0", "65,30", "90,30"})
    void discountByAge(int age, int expected) {
        assertThat(discount(age)).isEqualTo(expected);
    }

    @ParameterizedTest
    @MethodSource("invalidAges")
    void rejectsInvalid(int age) {
        org.junit.jupiter.api.Assertions.assertThrows(IllegalArgumentException.class, () -> validate(age));
    }

    static Stream<Integer> invalidAges() { return Stream.of(-1, 151, Integer.MIN_VALUE); }

    static void validate(int age) { if (age < 0 || age > 150) throw new IllegalArgumentException(); }
}
```

Implicit conversion handles `String -> int, LocalDate, enum, Duration`; use `@ConvertWith` or `ArgumentsAccessor`/`@AggregateWith` for custom objects.

### `@Nested` rules and tips
* Only **non-static inner classes** can be `@Nested`; lifecycle callbacks of the outer class run before the inner ones' (outer `@BeforeEach` -> inner `@BeforeEach` -> test).
* Great for the *"given a state / when an action / then"* hierarchy. Name classes after the context (`WhenEmpty`, `WithExpiredToken`).
* Avoid more than ~2 levels deep; readability drops.
* `@BeforeAll` in nested classes requires `PER_CLASS` lifecycle (inner classes cannot have static methods before Java 16; since 16 they can).

### Extensions: the model
Extension points are interfaces: `BeforeEachCallback`, `AfterEachCallback`, `ParameterResolver`, `TestExecutionExceptionHandler`, `ExecutionCondition`, `TestInstancePostProcessor`, `InvocationInterceptor`, `TestWatcher`, ...

```java
import org.junit.jupiter.api.extension.*;

public class TimingExtension implements BeforeTestExecutionCallback, AfterTestExecutionCallback {

    private static final ExtensionContext.Namespace NS =
            ExtensionContext.Namespace.create(TimingExtension.class);

    @Override
    public void beforeTestExecution(ExtensionContext ctx) {
        ctx.getStore(NS).put("start", System.nanoTime());
    }

    @Override
    public void afterTestExecution(ExtensionContext ctx) {
        long start = ctx.getStore(NS).remove("start", long.class);
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.printf("%s took %d ms%n", ctx.getDisplayName(), ms);
    }
}
```

Register:
* Declaratively: `@ExtendWith(TimingExtension.class)` on class/method/parameter.
* Programmatically: `@RegisterExtension static TimingExtension t = new TimingExtension();` (can have configuration).
* Globally via ServiceLoader with `junit.jupiter.extensions.autodetection.enabled=true`.

### Parameter resolver example

```java
public class RandomPortResolver implements ParameterResolver {
    @Override
    public boolean supportsParameter(ParameterContext p, ExtensionContext c) {
        return p.getParameter().getType() == int.class
                && p.isAnnotated(FreePort.class);
    }

    @Override
    public Object resolveParameter(ParameterContext p, ExtensionContext c) {
        try (var s = new java.net.ServerSocket(0)) { return s.getLocalPort(); }
        catch (java.io.IOException e) { throw new ParameterResolutionException("no port", e); }
    }
}

@java.lang.annotation.Retention(java.lang.annotation.RetentionPolicy.RUNTIME)
@interface FreePort {}
```

### Common mistakes
* Using `@ValueSource` for objects; use `@MethodSource`.
* `@MethodSource` factory not `static` (unless `PER_CLASS`).
* Writing logic inside parameterized tests (`if (param == X)`) - split the test instead.
* Using inheritance base classes with `@BeforeEach` chains instead of extensions.

## 🔴 Senior Level

### Extension internals
Each extension is instantiated once per registration and must be **stateless**; state belongs in `ExtensionContext.Store` (hierarchical: method -> class -> engine root). Stores use namespaces to prevent collisions. A store value implementing `ExtensionContext.Store.CloseableResource` (or `AutoCloseable` in 5.13+) is closed when the context ends - the ideal way to manage shared expensive resources (e.g. a Testcontainers container for the whole run, started lazily via the root store):

```java
public class SharedPostgres implements BeforeAllCallback {
    @Override
    public void beforeAll(ExtensionContext ctx) {
        ctx.getRoot().getStore(ExtensionContext.Namespace.GLOBAL)
           .getOrComputeIfAbsent("pg", k -> new StartedContainer(), StartedContainer.class);
    }

    static class StartedContainer implements ExtensionContext.Store.CloseableResource {
        StartedContainer() { /* start container */ }
        @Override public void close() { /* stop container */ }
    }
}
```

The Spring TestContext integration is itself an extension (`SpringExtension`), as are `MockitoExtension`, `@TempDir` support, `@Timeout`, and `@RepeatedTest`.

### Parameterized test performance and pitfalls
* Each invocation is a separate test with full lifecycle callbacks: with a Spring context or `@BeforeEach` creating heavy objects, 500 rows can be slow. Move pure logic into plain unit tests or keep fixtures cheap.
* Parameter resolution order: indexed arguments first, then resolver-provided ones (`TestInfo`, mocks) - put resolved ones *after* the arguments.
* Use `@ParameterizedTest(name = "{displayName} [{index}] {argumentsWithNames}")` for debuggable names. Argument `Named.of(...)`/`Arguments.argumentSet(...)` (5.11) gives readable labels.
* Combine with **property-based testing** (jqwik) when the input space is large; parameterized tests cover known edge cases, properties explore unknown ones.

### Test templates
`@TestTemplate` + `TestTemplateInvocationContextProvider` is the primitive behind `@ParameterizedTest` and `@RepeatedTest`. Use it to run a test under different *contexts* (e.g. for each DB vendor or each locale), registering different extensions per invocation.

### Design guidance
* Prefer extensions over abstract base test classes: composable, no fixed hierarchy.
* Use `@Nested` to model state machines in domain tests, but keep production-like objects in outer fields initialised in `@BeforeEach`.
* Keep custom extensions in a shared `test-support` module; version and test them like production code.
* `@AggregateWith` / `ArgumentsAccessor` for DTO-heavy CSV tables; for large tables prefer `@CsvFileSource` with `useHeadersInDisplayName = true`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Parameterized tests run one method over many inputs (`@ValueSource`, `@CsvSource`, `@MethodSource`), `@Nested` organises tests by scenario with layered setup, and extensions (`@ExtendWith`) add reusable lifecycle, parameter resolution, and conditional behaviour, replacing JUnit 4 runners and rules.

**Must know:**
* Sources and their limits; `@MethodSource` must be static (or `PER_CLASS`).
* Display name patterns.
* Extension points and `ExtensionContext.Store`.
* `@ExtendWith` vs `@RegisterExtension`.
* Nested lifecycle ordering.

**Common follow-ups:**
* How would you write an extension that starts a container once per run?
* Difference between `@RepeatedTest`, `@ParameterizedTest`, `@TestFactory`?
* How did JUnit 4 `@Rule` map to JUnit 5?

**Red flags:** conditionals inside parameterized tests; stateful extensions; deep nested pyramids.
