# Flaky tests

---

## 🟢 Junior Level

A **flaky test** sometimes passes and sometimes fails **without any code change**. Flaky tests are dangerous because people learn to ignore red builds — and then real failures are ignored too.

### Typical causes
* **Timing** — `Thread.sleep(500)` hoping async work is done.
* **Order dependence** — test B passes only if test A ran first and left data behind.
* **Shared state** — static fields, singletons, a shared database without cleanup.
* **Time and randomness** — `LocalDate.now()`, `UUID.randomUUID()` in assertions, time zones.
* **External systems** — real network calls, third-party sandboxes, DNS.
* **Unordered collections** — asserting the order of a `HashSet` or a `findAll()` without `ORDER BY`.

### Fixing the classic sleep

```java
// Flaky: may pass on a fast laptop and fail on a busy CI agent
orderService.placeAsync(order);
Thread.sleep(500);
assertThat(mailbox.received()).hasSize(1);

// Stable: wait for the condition, with an upper bound
orderService.placeAsync(order);
await().atMost(Duration.ofSeconds(5))
       .untilAsserted(() -> assertThat(mailbox.received()).hasSize(1));
```

(`await()` comes from the **Awaitility** library.)

## 🟡 Middle Level

### Control time

```java
class SubscriptionService {
    private final Clock clock;
    SubscriptionService(Clock clock) { this.clock = clock; }
    boolean isExpired(Subscription s) { return s.endsAt().isBefore(clock.instant()); }
}

@Test
void expiresAtMidnight() {
    Clock clock = Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);
    var service = new SubscriptionService(clock);
    assertThat(service.isExpired(new Subscription(Instant.parse("2025-12-31T23:59:59Z")))).isTrue();
}
```

Inject `Clock` instead of calling `Instant.now()`; never depend on the machine's default time zone (`TimeZone.getDefault()` differs between developer laptops and CI containers).

### Isolate state
* Each test creates the data it needs with unique identifiers (`"user-" + UUID.randomUUID()`), and asserts only on that data.
* Reset singletons, caches (`cacheManager.getCacheNames().forEach(n -> cacheManager.getCache(n).clear())`), WireMock stubs and MockMvc state in `@AfterEach`.
* Avoid `@DirtiesContext` as a fix — it hides the problem and makes the suite slow.

### Detecting order dependence
Randomize test order to expose hidden coupling:

```properties
# src/test/resources/junit-platform.properties
junit.jupiter.testmethod.order.default=org.junit.jupiter.api.MethodOrderer$Random
junit.jupiter.testclass.order.default=org.junit.jupiter.api.ClassOrderer$Random
```

When a failure appears, the logged seed (`junit.jupiter.execution.order.random.seed`) reproduces the exact order.

### Quarantine, don't ignore
Tag known-flaky tests (`@Tag("flaky")`), run them in a separate non-blocking CI job, create a ticket with an owner and a deadline. A permanent `@Disabled` is deleted coverage.

## 🔴 Senior Level

### Measure flakiness
You can't fix what you don't measure:
* Record every test result (JUnit XML) per CI run in a store (Gradle Develocity, BuildPulse, Datadog CI Visibility, or your own table).
* **Flake rate** per test = failures that passed on retry / total runs. Track the top 20.
* Re-running failing tests automatically (`surefire.rerunFailingTestsCount=2`, Gradle `test-retry` plugin) keeps pipelines green **only if** retried passes are reported as flaky, not silently hidden.

### Root causes in concurrent and distributed code
* **Missing happens-before** — test reads a field written by another thread without synchronization; it passes on x86 most of the time. Use concurrent structures or latches.
* **Thread pool saturation in CI** — tests share `ForkJoinPool.commonPool()` (used by parallel streams and `CompletableFuture.supplyAsync` without an executor); under parallel test execution, timeouts appear. Give components injectable executors and use a direct executor in unit tests.
* **Port collisions** — fixed ports in parallel builds; always use port 0 / random ports.
* **Eventual consistency** — asserting on a Kafka-consumer side effect or Elasticsearch index right after a write. Use Awaitility, and for Elasticsearch call `refresh` in tests.
* **Resource leaks** — a test leaves a container, thread or file handle open; later tests fail with "too many open files" or timeouts. JUnit 5 extensions can assert no extra non-daemon threads remain after each class.

### Hard-to-see flakiness sources
* `@Async` methods with Spring's default `SimpleAsyncTaskExecutor` behaving differently from production pools.
* `@Scheduled` jobs firing during tests — disable scheduling in the test profile.
* Hibernate `Instant` precision: PostgreSQL stores microseconds, Java has nanoseconds — `assertThat(reloaded.createdAt()).isEqualTo(original)` fails intermittently depending on the nanosecond part. Truncate (`truncatedTo(ChronoUnit.MICROS)`) or compare with tolerance.
* Locale-dependent formatting (`String.format("%.2f")` gives `1,50` under German locale).

### Organizational practice
Treat flaky tests like production incidents with an error budget: if the flake rate of the main branch exceeds a threshold (e.g. > 1% of runs fail due to flakes), the owning team prioritizes fixes over features. Engineers trusting the build is worth more than any single test.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Flaky tests are non-deterministic failures caused by timing, shared state, order dependence, time and randomness, or external systems. I replace sleeps with Awaitility, inject `Clock`, isolate data per test, randomize test order to find coupling, measure flake rates in CI, and quarantine flaky tests with an owner instead of ignoring them.

**Must know:**
* Awaitility instead of `Thread.sleep`.
* `Clock` injection and explicit time zones.
* Random test ordering with a reproducible seed.
* Retries must surface flakiness, not hide it.
* Concurrency, ports, eventual consistency, timestamp precision.

**Common follow-ups:**
* How do you find which test leaves state behind?
* Should CI automatically retry failed tests?
* How do you test async code deterministically?

**Red flags:** "just rerun the pipeline"; permanent `@Disabled`; `@DirtiesContext` everywhere to make tests pass.
