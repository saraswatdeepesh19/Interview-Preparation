# Test doubles mock stub and fake

---

## 🟢 Junior Level

A **test double** is a stand-in object used instead of a real dependency during a test (the term comes from "stunt double" in movies). We replace real collaborators (database, payment gateway, e-mail server) because they are slow, non-deterministic, costly, or hard to trigger (e.g. "the bank is down").

Gerard Meszaros' classification:

| Double | What it does | Example |
|---|---|---|
| **Dummy** | Passed but never used | `null` or `new Object()` to fill a parameter |
| **Stub** | Returns canned answers | `findById(1)` always returns Ann |
| **Spy** | A real or recording object that also tracks calls | counts how many mails were sent |
| **Mock** | Pre-programmed with *expectations*; verifies interactions | "`send()` must be called exactly once" |
| **Fake** | A *working* lightweight implementation | in-memory repository backed by a `HashMap` |

### Analogy
Rehearsing a play: a **dummy** is a cardboard cut-out standing in for an actor, a **stub** reads fixed lines, a **fake** is an understudy who really performs (but isn't the star), a **mock** is a director with a clipboard checking that every cue was hit.

### Minimal example

```java
import java.util.*;

interface UserRepository {
    Optional<String> findNameById(long id);
    void save(long id, String name);
}

// Stub: canned answer
class StubUserRepository implements UserRepository {
    public Optional<String> findNameById(long id) { return Optional.of("Ann"); }
    public void save(long id, String name) { throw new UnsupportedOperationException(); }
}

// Fake: real behaviour, simplified storage
class InMemoryUserRepository implements UserRepository {
    private final Map<Long, String> data = new HashMap<>();
    public Optional<String> findNameById(long id) { return Optional.ofNullable(data.get(id)); }
    public void save(long id, String name) { data.put(id, name); }
}

class Greeter {
    private final UserRepository repo;
    Greeter(UserRepository repo) { this.repo = repo; }
    String greet(long id) {
        return repo.findNameById(id).map(n -> "Hello, " + n).orElse("Hello, stranger");
    }
}
```

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class GreeterTest {
    @Test
    void greetsKnownUser() {
        assertEquals("Hello, Ann", new Greeter(new StubUserRepository()).greet(1));
    }

    @Test
    void greetsStrangerWhenMissing() {
        assertEquals("Hello, stranger", new Greeter(new InMemoryUserRepository()).greet(99));
    }
}
```

## 🟡 Middle Level

### State verification vs behaviour verification
* **Stubs and fakes** support **state verification**: run the code, then check the *result* or resulting state.
* **Mocks and spies** support **behaviour verification**: check *how the unit talked* to its collaborators.

Prefer state verification when you can; it is less coupled to implementation. Use behaviour verification for outgoing side effects with no observable return (send e-mail, publish event, call payment API).

### Mockito terminology is loose
In Mockito, everything created with `mock()` is technically a configurable double: `when(...).thenReturn(...)` makes it behave as a **stub**; `verify(...)` makes it act as a **mock**; `spy()` wraps a real object. Same object, different usage:

```java
import static org.mockito.Mockito.*;

PaymentGateway gateway = mock(PaymentGateway.class);
when(gateway.charge("card-1", 100)).thenReturn(true);   // stub role

boolean ok = new CheckoutService(gateway).pay("card-1", 100);

assertTrue(ok);                                         // state check
verify(gateway).charge("card-1", 100);                  // mock role
```

### Fake vs stub trade-offs

| | Stub | Fake |
|---|---|---|
| Effort | trivial | moderate (must be maintained) |
| Realism | low | high |
| Stateful flows (save then load) | awkward | natural |
| Risk | divergence is obvious | divergence from real impl is **silent** |

Fakes need their own tests, ideally **contract tests** run against both fake and real implementation:

```java
abstract class UserRepositoryContract {
    abstract UserRepository create();

    @org.junit.jupiter.api.Test
    void savedUserCanBeFound() {
        UserRepository repo = create();
        repo.save(1, "Ann");
        org.junit.jupiter.api.Assertions.assertEquals("Ann", repo.findNameById(1).orElseThrow());
    }
}

class InMemoryUserRepositoryTest extends UserRepositoryContract {
    UserRepository create() { return new InMemoryUserRepository(); }
}
// JdbcUserRepositoryTest extends the same contract with a Testcontainers DB
```

### Real-world fakes in the Java ecosystem
* **H2 / HSQLDB** as fake database (beware dialect differences - see [Testcontainers for integration tests](15.%20Testcontainers%20for%20integration%20tests.md)).
* **Embedded Kafka** / `MockWebServer` / **WireMock** as fake HTTP servers.
* `Clock.fixed(...)` as a fake clock; `MockMultipartFile`, `MockHttpServletRequest` from Spring.

### When to use which
1. Need a value from a dependency -> **stub**.
2. Dependency has behaviour across multiple calls (CRUD) -> **fake**.
3. Need to assert an outgoing command -> **mock** (`verify`).
4. Need to wrap real code but override one method / record calls -> **spy** (use sparingly).
5. Parameter required but irrelevant -> **dummy**.

### Common mistakes
* Mocking value objects or types you don't own (`List`, `String`, third-party clients): create thin adapters you own and mock those.
* Mocking so deeply (`RETURNS_DEEP_STUBS`) that tests mirror implementation (Law of Demeter violation).
* Verifying every call - brittle tests.
* Mocking the class under test with a spy "to make it testable".

## 🔴 Senior Level

### Design implications
The need for many doubles signals a design problem. If a class needs 8 mocks, it has too many responsibilities. If you must mock static calls or `new` inside methods, dependencies are hidden - inject them. "Don't mock types you don't own" (Freeman & Pryce) - wrap `RestTemplate`/SDK clients in your own port interface, and test the adapter against a fake server (WireMock / Testcontainers), so you test your assumptions about the third party for real.

### London vs Detroit again
Mockist TDD uses mocks to *discover* collaborator interfaces (outside-in). The cost: tests are coupled to the call graph, and refactoring between collaborators breaks tests even if behaviour is unchanged. Classicist testing with fakes survives refactoring better but relies on well-maintained fakes. Senior engineers choose per boundary: **fakes for persistence and queues you own, mocks for fire-and-forget commands, real objects for domain logic**.

### Writing a robust fake

```java
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

interface OrderRepository {
    Order save(Order o);
    Optional<Order> findById(long id);
}

record Order(Long id, String customer) {}

class FakeOrderRepository implements OrderRepository {
    private final Map<Long, Order> store = new ConcurrentHashMap<>();
    private final AtomicLong seq = new AtomicLong();

    @Override
    public Order save(Order o) {
        long id = o.id() != null ? o.id() : seq.incrementAndGet();
        Order saved = new Order(id, o.customer());
        store.put(id, saved);
        return saved;
    }

    @Override
    public Optional<Order> findById(long id) { return Optional.ofNullable(store.get(id)); }
}
```

Fakes can also simulate failure: add `failNextSaveWith(RuntimeException)` to test retry/rollback logic, something mocks do equally but fakes do reusably.

### Mocks and concurrency
Mockito mocks are thread-safe for stubbing/invocation recording, but stubbing while other threads invoke is racy. In async tests, use `verify(mock, timeout(500))` or Awaitility rather than sleeping.

### Mock maker internals
Mockito 5 uses the **inline mock maker** by default (ByteBuddy + instrumentation via `java.lang.instrument` / the JVM's attach mechanism), which lets it mock final classes, records and static methods. On JDK 21+ you may see a warning about dynamic agent loading; configure Mockito as a `-javaagent` in Surefire's `argLine` to be future-proof:

```xml
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <argLine>-javaagent:${settings.localRepository}/org/mockito/mockito-core/5.12.0/mockito-core-5.12.0.jar -Xshare:off</argLine>
  </configuration>
</plugin>
```

(Version must match your Mockito dependency; this is typically wired with the `maven-dependency-plugin:properties` goal.)

### Production-relevant patterns
* **Test doubles in the Spring context:** use `@TestConfiguration` with a `@Primary` fake bean, or `@MockitoBean` for mocks - see [SpringBootTest and MockBean vs MockitoBean](12.%20SpringBootTest%20and%20MockBean%20vs%20MockitoBean.md).
* **Chaos at the boundary:** doubles that inject latency/errors (WireMock fault injection, Toxiproxy) validate timeouts, retries, circuit breakers that mocks cannot.
* **Contracts:** keep doubles honest with contract tests (see [Contract testing with Pact and Spring Cloud Contract](21.%20Contract%20testing%20with%20Pact%20and%20Spring%20Cloud%20Contract.md)). A mock that returns data the real service never returns is a false green.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Test doubles replace real dependencies. Dummies fill parameters, stubs return canned data, fakes are lightweight working implementations, spies record real calls, and mocks verify expected interactions. Prefer state verification with stubs/fakes; use mocks for outgoing side effects.

**Must know:**
* Meszaros' five kinds; stub vs mock difference (state vs behaviour verification).
* In Mockito one `mock()` can play stub and mock.
* Fakes need contract tests to avoid drifting from reality.
* Don't mock types you don't own; wrap them.
* Many mocks = design smell.

**Common follow-ups:**
* Mock vs stub vs spy?
* Is H2 a fake? Is it safe to use for tests?
* When is a fake better than a mock?

**Red flags:** mocking everything including POJOs; verifying every call; spy on the class under test.
