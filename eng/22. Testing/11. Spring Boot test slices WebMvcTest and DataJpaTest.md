# Spring Boot test slices WebMvcTest and DataJpaTest

---

## 🟢 Junior Level

Booting the whole Spring application in every test is slow. **Test slices** load only the part of the application context needed for one layer. Spring Boot provides annotations for each:

| Annotation | Loads | Typical target |
|---|---|---|
| `@WebMvcTest` | MVC infrastructure: controllers, `@ControllerAdvice`, filters, Jackson, validation | REST controllers |
| `@DataJpaTest` | JPA entities, Spring Data repositories, `TestEntityManager`, embedded/test DB | Repositories |
| `@JsonTest` | Jackson/Gson only | JSON (de)serialization |
| `@RestClientTest` | `RestTemplate`/`RestClient` + `MockRestServiceServer` | HTTP clients |
| `@DataMongoTest`, `@JdbcTest`, `@DataRedisTest` | respective data layer | persistence |
| `@WebFluxTest` | WebFlux controllers | reactive controllers |

Services and other `@Component`s are **not** loaded in a slice - you provide them as mocks.

### Analogy
A slice is a cross-section of a cake: you taste only the layer you are testing instead of eating the whole cake.

### Minimal `@WebMvcTest`

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(GreetingController.class)
class GreetingControllerTest {

    @Autowired MockMvc mvc;
    @MockitoBean GreetingService service;     // Spring Boot 3.4+; use @MockBean before

    @Test
    void returnsGreeting() throws Exception {
        when(service.greet("Ann")).thenReturn("Hello Ann");

        mvc.perform(get("/greet").param("name", "Ann"))
           .andExpect(status().isOk())
           .andExpect(content().string("Hello Ann"));
    }
}
```

```java
@org.springframework.web.bind.annotation.RestController
class GreetingController {
    private final GreetingService service;
    GreetingController(GreetingService service) { this.service = service; }

    @org.springframework.web.bind.annotation.GetMapping("/greet")
    String greet(@org.springframework.web.bind.annotation.RequestParam String name) {
        return service.greet(name);
    }
}

interface GreetingService { String greet(String name); }
```

## 🟡 Middle Level

### `@DataJpaTest`

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE) // use the real configured DB (e.g. Testcontainers)
class CustomerRepositoryTest {

    @Autowired TestEntityManager em;
    @Autowired CustomerRepository repo;

    @Test
    void findsByEmailIgnoringCase() {
        em.persist(new Customer("ann@example.com"));
        em.flush();
        em.clear();                       // force a real SELECT, not first-level cache

        assertThat(repo.findByEmailIgnoreCase("ANN@example.com")).isPresent();
    }
}
```

Key facts:
* Each test runs in a **transaction that is rolled back** at the end (isolation for free).
* By default an **embedded DB (H2)** replaces your DataSource; set `Replace.NONE` to test against the real engine (recommended - see [Testcontainers for integration tests](15.%20Testcontainers%20for%20integration%20tests.md)).
* `flush()` + `clear()` ensure SQL really runs and mappings are verified; otherwise Hibernate may satisfy queries from its cache and defer SQL.
* `@Import` your custom repositories/config used by the slice; `@Service` beans are not scanned.

### What `@WebMvcTest` verifies
* URL mapping, HTTP method, params, headers, content negotiation.
* Request/response JSON (Jackson config), validation (`@Valid` -> 400), exception handlers (`@ControllerAdvice`).
* Spring Security filter chain (with `spring-security-test`: `@WithMockUser`, `csrf()`).
Not verified: service logic, transactions, real DB.

```java
mvc.perform(post("/customers")
        .contentType("application/json")
        .content("""
                {"email": "not-an-email"}
                """))
   .andExpect(status().isBadRequest())
   .andExpect(jsonPath("$.errors[0].field").value("email"));
```

### Slice vs `@SpringBootTest`

| | Slice | `@SpringBootTest` |
|---|---|---|
| Startup | ~0.5-2 s | 3-30 s+ |
| Scope | one layer | whole app |
| Collaborators | mocked | real |
| Failure locality | precise | broader |
| Context cache | per config combo | per config combo |

### `@JsonTest`

```java
@JsonTest
class OrderJsonTest {
    @Autowired JacksonTester<Order> json;

    @Test
    void serializes() throws Exception {
        assertThat(json.write(new Order("A1", 3)))
                .extractingJsonPathStringValue("$.id").isEqualTo("A1");
    }
}
```

### Common mistakes
* Forgetting the mock for a controller's dependency -> `NoSuchBeanDefinitionException`.
* `@WebMvcTest` without a controller class -> loads *all* controllers.
* In `@DataJpaTest`, not flushing so constraint violations/queries never run.
* H2 hides PostgreSQL-specific behaviour (JSONB, window functions, case sensitivity, locking).
* Component-scanning too broadly: `@SpringBootApplication` annotated with extra `@EnableXyz`/`@ComponentScan` filters pulls extra beans into every slice. Put such config in separate `@Configuration` classes.

## 🔴 Senior Level

### How slices work
Each slice annotation is meta-annotated with `@BootstrapWith(SpringBootTestContextBootstrapper.class)`, `@TypeExcludeFilters(WebMvcTypeExcludeFilter.class)`, and `@AutoConfigureXxx` + `@ImportAutoConfiguration`. The **TypeExcludeFilter** filters component scanning to only include relevant stereotypes (`@Controller`, `@ControllerAdvice`, `Converter`, `HandlerInterceptor`, `WebMvcConfigurer`, ...); the **`spring.factories`/`AutoConfiguration.imports`** of the `@AutoConfigureXxx` lists the auto-configurations to apply. Finding the full list: `META-INF/spring/org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureWebMvc.imports` in `spring-boot-test-autoconfigure`.

### Context caching
Spring's `ContextCache` keys a context by: configuration classes, active profiles, property sources, context initialisers, `@MockitoBean`/`@MockBean` definitions, `@DynamicPropertySource`, etc. Every distinct combination boots a new context. Mixed `@MockBean` sets across test classes are the #1 reason for slow suites: standardise a few base configurations. Inspect with the logger `org.springframework.test.context.cache` at DEBUG (shows hits/misses and the cache size; default max 32, LRU).

### Performance checklist
1. Prefer slices to `@SpringBootTest`.
2. Share mocks via a common `@TestConfiguration` to maximise cache hits.
3. `spring.jpa.open-in-view=false`, lazy init for tests: `spring.main.lazy-initialization=true` in `application-test.properties` (watch for hidden wiring errors).
4. Use `@DirtiesContext` only as a last resort - it destroys the cache.
5. Parallel forks: `forkCount=1C` with Surefire - each fork keeps its own context cache.

### Testing security and method security in slices

```java
@WebMvcTest(AdminController.class)
@Import(SecurityConfig.class)
class AdminControllerSecurityTest {

    @Autowired MockMvc mvc;
    @MockitoBean AdminService service;

    @Test
    @org.springframework.security.test.context.support.WithMockUser(roles = "USER")
    void userIsForbidden() throws Exception {
        mvc.perform(get("/admin/stats")).andExpect(status().isForbidden());
    }

    @Test
    @org.springframework.security.test.context.support.WithMockUser(roles = "ADMIN")
    void adminAllowed() throws Exception {
        mvc.perform(get("/admin/stats")).andExpect(status().isOk());
    }
}
```

### Custom slices
Create your own `@MyModuleTest` by composing `@ExtendWith(SpringExtension.class)`, `@TypeExcludeFilters`, `@ImportAutoConfiguration` or simply `@ContextConfiguration(classes = ...)` + `@Import` for a handpicked set of beans - useful in modular monoliths so each module tests itself without everything else.

### Diagnostics
* `--debug` or `debug=true` in test properties prints the **auto-configuration report** (positive/negative matches) - tells which auto-config a slice applied.
* `ApplicationContextRunner` (`spring-boot-test`) tests auto-configuration classes and `@Conditional` behaviour in milliseconds without a full context.
* `@DataJpaTest` plus `spring.jpa.show-sql=true` and `logging.level.org.hibernate.orm.jdbc.bind=trace` to validate N+1 queries; assert statement counts with `datasource-proxy` or Hibernate `Statistics`.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Test slices load only one layer of the Spring context: `@WebMvcTest` for controllers/MVC with MockMvc (services mocked), `@DataJpaTest` for JPA repositories on a rolled-back transaction, `@JsonTest`, `@RestClientTest`, etc. They are much faster and more focused than `@SpringBootTest`.

**Must know:**
* What each slice loads and what it excludes.
* Mock collaborators with `@MockitoBean` (Boot 3.4+) / `@MockBean`.
* `@DataJpaTest` is transactional, replaces the DataSource with embedded by default; `Replace.NONE` for real DB.
* Flush + clear in JPA tests.
* Context caching and what breaks it.

**Common follow-ups:**
* Difference between `@WebMvcTest` and `@SpringBootTest(webEnvironment=MOCK)`?
* Why do my `@WebMvcTest` tests fail with missing bean errors?
* How do you test auto-configuration?

**Red flags:** `@SpringBootTest` for every test; H2 only for a PostgreSQL production; `@DirtiesContext` sprinkled everywhere.
