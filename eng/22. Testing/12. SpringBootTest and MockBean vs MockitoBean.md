# SpringBootTest and MockBean vs MockitoBean

---

## 🟢 Junior Level

`@SpringBootTest` starts the **full application context** (all beans, auto-configuration, properties) so you can test the application as a whole - the closest thing to running the real app inside JUnit.

Sometimes you still want to replace *one* real bean (e.g. a payment gateway) with a Mockito mock. Spring provides:

* **`@MockBean`** (Spring Boot 1.4 - 3.3, deprecated since 3.4, removal planned for 4.0) and **`@SpyBean`**.
* **`@MockitoBean`** / **`@MockitoSpyBean`** (Spring Framework 6.2 / Spring Boot 3.4+, package `org.springframework.test.context.bean.override.mockito`) - the modern replacements.

Both create a Mockito mock and **register it in the ApplicationContext, replacing any existing bean of that type**, so every component that injects it receives the mock.

### Analogy
`@SpringBootTest` opens the whole restaurant. `@MockitoBean` swaps the real (expensive, unpredictable) supplier for a stand-in delivery guy, while the kitchen and waiters stay real.

### Example

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.bean.override.mockito.MockitoBean;

import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.Mockito.when;

@SpringBootTest
class CheckoutIntegrationTest {

    @Autowired CheckoutService checkout;     // real bean, wired with real collaborators
    @MockitoBean PaymentGateway gateway;     // replaced by a mock

    @Test
    void checkoutSucceedsWhenGatewayApproves() {
        when(gateway.charge("card-1", 1000)).thenReturn(true);

        assertThat(checkout.pay("card-1", 1000)).isTrue();
    }
}
```

Mocks are **reset after each test method** automatically.

## 🟡 Middle Level

### `@SpringBootTest` options

| `webEnvironment` | Behaviour |
|---|---|
| `MOCK` (default) | Mock servlet environment; use with `MockMvc` (`@AutoConfigureMockMvc`) |
| `RANDOM_PORT` | Real embedded server on a random port; use `TestRestTemplate`/`WebTestClient`/RestAssured with `@LocalServerPort` |
| `DEFINED_PORT` | Real server on configured port (risky in CI) |
| `NONE` | No web environment |

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class FullStackTest {

    @org.springframework.boot.test.web.server.LocalServerPort int port;
    @Autowired org.springframework.boot.test.web.client.TestRestTemplate rest;

    @Test
    void healthEndpoint() {
        var response = rest.getForEntity("http://localhost:" + port + "/actuator/health", String.class);
        assertThat(response.getStatusCode().is2xxSuccessful()).isTrue();
    }
}
```

(In Boot 3.x `@LocalServerPort` lives in `org.springframework.boot.test.web.server`; before 3.4 it was `org.springframework.boot.web.server.LocalServerPort`.)

Also: `@SpringBootTest(properties = "feature.x=true")`, `@ActiveProfiles("test")`, `@TestPropertySource`, `@DynamicPropertySource` (for container ports), `@Import(TestConfig.class)`.

### `@MockBean` vs `@MockitoBean`

| Aspect | `@MockBean` / `@SpyBean` | `@MockitoBean` / `@MockitoSpyBean` |
|---|---|---|
| Origin | Spring Boot | Spring Framework 6.2 (Bean Override mechanism) |
| Package | `org.springframework.boot.test.mock.mockito` | `org.springframework.test.context.bean.override.mockito` |
| Status | Deprecated in Boot 3.4 for removal | Recommended |
| Usable on | test class fields (+ class-level repeatable) | fields; in Boot 3.4 not on `@Configuration` classes |
| Non-singleton / scoped | limited | `@MockitoSpyBean` supports non-singleton beans |
| By name | `name` attribute | `name` attribute / field name |
| Context cache key | included | included |

Migration is mostly a mechanical rename plus import change. Differences to watch: `@MockitoBean` fields can be declared in an abstract/parent class, cannot be used on `@Configuration` classes, and nested test class inheritance (`@NestedTestConfiguration`) follows the standard rules.

### Spy on a real bean

```java
@MockitoSpyBean AuditService audit;       // real implementation, but verifiable

@Test
void auditsPayment() {
    checkout.pay("card-1", 1000);
    verify(audit).record(contains("card-1"));
}
```

### Common mistakes
* Using `@SpringBootTest` where a slice would do.
* Using `@MockBean`/`@MockitoBean` with different mock sets in each test class -> a new context per class (slow). Centralise in a shared abstract class or `@TestConfiguration`.
* `@DirtiesContext` as the default clean-up: nukes the cache; instead reset state explicitly.
* Using `DEFINED_PORT` -> port clashes in parallel CI.
* `@Transactional` on a `RANDOM_PORT` test: the server runs in another thread, so test-managed transactions do **not** wrap the server-side work; the rollback does not apply (see [Testing the database layer and transaction isolation](14.%20Testing%20the%20database%20layer%20and%20transaction%20isolation.md)).
* Overriding beans by defining a second `@Bean` of the same name (needs `spring.main.allow-bean-definition-overriding=true`); prefer `@Primary` in a `@TestConfiguration`.

## 🔴 Senior Level

### Under the hood
`SpringBootTestContextBootstrapper` finds the `@SpringBootConfiguration` by searching upward through packages (so keep tests in the same package tree), builds a `MergedContextConfiguration`, and `DefaultCacheAwareContextLoaderDelegate` looks it up in the `ContextCache` (static, LRU, max 32). `@MockBean` is implemented via `MockitoPostProcessor` (a `BeanFactoryPostProcessor` that registers mock definitions and replaces/wraps beans) plus `MockitoTestExecutionListener` (injects fields and resets mocks). The new `@MockitoBean` uses the **Bean Override SPI** (`BeanOverrideTestExecutionListener`, `BeanOverrideProcessor`, `BeanOverrideHandler`) - also used for `@TestBean` (replace a bean with a static factory method result), giving you a non-Mockito way to substitute beans:

```java
@SpringBootTest
class TestBeanExample {

    @org.springframework.test.context.bean.override.convention.TestBean
    Clock clock;

    static Clock clock() { return Clock.fixed(Instant.parse("2025-01-01T00:00:00Z"), ZoneOffset.UTC); }
}
```

(imports: `java.time.*`.) `@TestBean` is available from Spring Framework 6.2.

### Cost model and strategy
Typical numbers: slice context 0.5-2 s, small full context 3-6 s, large enterprise context 20-60 s with JPA, security, Kafka. With 50 distinct context configurations you pay that 50 times. Strategies:
1. **One shared base configuration** for integration tests, all external systems via Testcontainers (singleton containers) so the context is identical and cached.
2. **Do not vary `@MockitoBean`** across classes unless required; move variance into per-test stubbing/resets instead.
3. `@SpringBootTest(classes = {OnlyNeeded.class})` for narrower tests.
4. Reduce context start time: lazy init, exclude unneeded auto-configs, AOT/CDS (JDK 13+ AppCDS), disable banner/JMX, small connection pools.
5. Parallel test execution with JUnit 5 requires care: shared contexts + mocks reset on each method are **not** thread safe for `@MockitoBean` (same mock used by concurrent tests). Prefer forked JVMs for parallelism.

### Testing slice of behaviour with real infra

```java
@SpringBootTest
@org.testcontainers.junit.jupiter.Testcontainers
class OrderFlowIT {

    @org.testcontainers.junit.jupiter.Container
    @org.springframework.boot.testcontainers.service.connection.ServiceConnection
    static org.testcontainers.containers.PostgreSQLContainer<?> pg =
            new org.testcontainers.containers.PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired OrderService orders;
    @MockitoBean PaymentGateway gateway;   // only the third-party edge is mocked

    @Test
    void persistsOrderWhenPaymentApproved() {
        when(gateway.charge(any(), anyLong())).thenReturn(true);
        assertThat(orders.place("cust-1", 500).status()).isEqualTo("PAID");
    }
}
```

(`@ServiceConnection`, Boot 3.1+, auto-wires datasource properties; see [Testcontainers for integration tests](15.%20Testcontainers%20for%20integration%20tests.md).)

### Diagnostics
* `logging.level.org.springframework.test.context.cache=DEBUG` - see cache hit/miss statistics.
* `logging.level.org.springframework.boot.test=DEBUG`.
* `@SpringBootTest(properties = "debug=true")` for the auto-configuration report.
* Look for beans created per context via `ApplicationContext#getBeanDefinitionNames()` when investigating unexpectedly high startup time; use Spring Boot's `BufferingApplicationStartup` + `/actuator/startup` to profile bean creation.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `@SpringBootTest` boots the full context for integration tests (MOCK, RANDOM_PORT, ...). `@MockBean`/`@SpyBean` (Boot) were replaced by `@MockitoBean`/`@MockitoSpyBean` (Spring Framework 6.2, Boot 3.4+), which put Mockito mocks into the context replacing real beans. Different mock sets change the context cache key, so keep them consistent to keep suites fast.

**Must know:**
* Web environment modes; `@LocalServerPort`, `TestRestTemplate`, `MockMvc`.
* `@MockBean` deprecated -> `@MockitoBean`; `@TestBean`.
* Context cache key and `@DirtiesContext` cost.
* Mocks reset after each test.
* `@Transactional` rollback doesn't apply with a real server thread.

**Common follow-ups:**
* Why are my Spring tests slow? (Context proliferation.)
* `@Mock` vs `@MockBean` - when each?
* How do you change properties per test? (`@DynamicPropertySource`, `@TestPropertySource`.)

**Red flags:** every test uses `@SpringBootTest` + `@DirtiesContext`; `Thread.sleep` for startup; `DEFINED_PORT`.
