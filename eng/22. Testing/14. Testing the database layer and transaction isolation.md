# Testing the database layer and transaction isolation

---

## 🟢 Junior Level

Database tests check that your **queries, mappings and constraints** behave correctly against a real database. In Spring Boot, `@DataJpaTest` starts only JPA components (entities, repositories, `EntityManager`) and wraps every test in a transaction that is **rolled back** at the end, so tests don't leave data behind.

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE) // use the real DB below
@Testcontainers
class CustomerRepositoryTest {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired CustomerRepository customers;

    @Test
    void findsByEmailIgnoringCase() {
        customers.save(new Customer("Ada", "ADA@example.com"));
        assertThat(customers.findByEmailIgnoreCase("ada@example.com")).isPresent();
    }
}
```

### Why not H2?
An in-memory database is fast but speaks a different SQL dialect. JSONB, `ON CONFLICT`, window functions, partial indexes, sequences and locking behave differently. Tests that pass on H2 can fail on PostgreSQL in production. Prefer the same engine and version as production (Testcontainers).

## 🟡 Middle Level

### The rollback trap: forcing SQL to run
With JPA, `save()` usually only schedules an `INSERT`; it reaches the database at **flush** time. Because the test rolls back, the flush may never happen — and constraint violations go unnoticed.

```java
@Autowired TestEntityManager em;

@Test
void uniqueEmailIsEnforced() {
    customers.save(new Customer("Ada", "ada@example.com"));
    customers.save(new Customer("Ada 2", "ada@example.com"));

    assertThatThrownBy(() -> em.flush())               // force SQL now
            .isInstanceOf(ConstraintViolationException.class); // Hibernate wraps the DB error
}

@Test
void mapsLinesCorrectly() {
    Order saved = orders.save(orderWithTwoLines());
    em.flush();
    em.clear();                                       // drop the 1st-level cache
    Order reloaded = orders.findById(saved.getId()).orElseThrow(); // really SELECTs
    assertThat(reloaded.getLines()).hasSize(2);
}
```

Without `em.clear()`, `findById` returns the **same object** from the persistence context and you are testing Java, not your mapping.

### Asserting query counts (N+1)

```java
@Test
void loadsOrdersWithLinesInOneQuery() {
    Statistics stats = em.getEntityManager().getEntityManagerFactory()
                         .unwrap(SessionFactory.class).getStatistics();
    stats.setStatisticsEnabled(true);
    stats.clear();

    List<Order> result = orders.findAllWithLines();      // @EntityGraph or join fetch
    result.forEach(o -> o.getLines().size());

    assertThat(stats.getPrepareStatementCount()).isEqualTo(1);
}
```

Libraries like `datasource-proxy` or Hypersistence `SQLStatementCountValidator` make this a one-liner.

### Schema from migrations, not from Hibernate
Run Flyway/Liquibase in tests (`spring.jpa.hibernate.ddl-auto=validate`) so the schema under test is exactly what production uses, and Hibernate verifies that entities match it.

## 🔴 Senior Level

### Testing transaction isolation and concurrency
The default test transaction makes everything happen in **one** transaction on **one** connection — so you cannot observe isolation anomalies. To test them, disable the test-managed transaction and use separate transactions explicitly:

```java
@SpringBootTest
@Transactional(propagation = Propagation.NOT_SUPPORTED)   // no wrapping test transaction
class StockConcurrencyIT {
    @Autowired TransactionTemplate tx;
    @Autowired JdbcTemplate jdbc;

    @Test
    void optimisticLockPreventsLostUpdate() throws Exception {
        long id = tx.execute(s -> stock.save(new Stock("SKU-1", 10)).getId());

        CountDownLatch bothRead = new CountDownLatch(2);
        Callable<Void> reserve = () -> {
            tx.executeWithoutResult(s -> {
                Stock st = stock.findById(id).orElseThrow();
                bothRead.countDown();
                awaitUninterruptibly(bothRead);         // both transactions have read version 0
                st.reserve(1);
            });
            return null;
        };

        ExecutorService pool = Executors.newFixedThreadPool(2);
        List<Future<Void>> results = pool.invokeAll(List.of(reserve, reserve));

        long failures = results.stream().filter(f -> failed(f, ObjectOptimisticLockingFailureException.class)).count();
        assertThat(failures).isEqualTo(1);
        assertThat(jdbc.queryForObject("select quantity from stock where id = ?", Integer.class, id)).isEqualTo(9);
    }
}
```

The latch forces the interleaving that causes a lost update; `@Version` must make exactly one commit fail. The same harness tests `SELECT ... FOR UPDATE` (pessimistic) blocking, `SERIALIZABLE` serialization failures (`SQLState 40001`), and your retry logic around them.

### Things the rollback-per-test model hides
* `@TransactionalEventListener(AFTER_COMMIT)` listeners never fire (nothing commits).
* `REQUIRES_NEW` code commits in a separate transaction and is **not** rolled back — test data leaks into other tests.
* Database triggers or deferred constraints (`DEFERRABLE INITIALLY DEFERRED`) only run at commit.
* Behavior across connections: advisory locks, `LISTEN/NOTIFY`, isolation.

For those, use non-transactional tests and clean up explicitly — truncate tables in `@AfterEach` (`TRUNCATE ... RESTART IDENTITY CASCADE`) or recreate the schema per test class.

### Keeping DB suites fast
* One container per JVM (static field or Testcontainers *singleton pattern*), reused across test classes; `testcontainers.reuse.enable=true` locally.
* Avoid dirtying the Spring context; share configuration so the context cache works.
* Run DB tests in parallel only with isolated schemas/databases per worker (e.g. one database per Surefire fork, created from a template database: `CREATE DATABASE test_3 TEMPLATE test_template`).

## 🎯 Interview Cheat Sheet

**30-second pitch:** I test repositories against the same database engine as production with Testcontainers and real migrations. I flush and clear the persistence context so SQL actually runs, assert query counts to catch N+1, and test concurrency and isolation with explicit transactions outside the default rollback-per-test model.

**Must know:**
* `@DataJpaTest` rolls back each test; flush to surface constraint errors.
* `em.clear()` before reloading, or you test the 1st-level cache.
* H2 hides dialect, locking and constraint differences.
* `NOT_SUPPORTED` + `TransactionTemplate` to test isolation, locking, `AFTER_COMMIT` listeners.
* `ddl-auto=validate` with Flyway/Liquibase.

**Common follow-ups:**
* How do you test optimistic locking?
* Why does my `@TransactionalEventListener` not fire in tests?
* How do you keep Testcontainers suites fast?

**Red flags:** tests passing only on H2; never flushing; tests depending on execution order because `REQUIRES_NEW` data leaked.
