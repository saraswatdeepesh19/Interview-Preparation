# CI test strategy

---

## 🟢 Junior Level

A **CI test strategy** decides *which tests run when* so developers get fast, trustworthy feedback without waiting an hour per push. The principle: **fast checks early and often, slow checks later and less often**.

| Stage | Runs on | Typical content | Target time |
| --- | --- | --- | --- |
| Pre-commit / local | Developer machine | Compile, formatting, unit tests of the module | < 1 min |
| Pull request | Every push | All unit tests, static analysis, key integration tests | < 10 min |
| Main branch | Every merge | Full integration + contract tests, build image | < 20 min |
| Nightly / pre-release | Schedule | E2E, performance, mutation testing, security scans | Hours OK |

### Separating fast and slow tests in Maven

```xml
<!-- Unit tests: *Test.java, run in the test phase -->
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
</plugin>
<!-- Integration tests: *IT.java, run in integration-test/verify phases -->
<plugin>
  <artifactId>maven-failsafe-plugin</artifactId>
  <executions><execution><goals><goal>integration-test</goal><goal>verify</goal></goals></execution></executions>
</plugin>
```

`mvn test` → fast feedback; `mvn verify` → everything.

## 🟡 Middle Level

### Pipeline example (GitHub Actions)

```yaml
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - run: ./mvnw -B -ntp verify -DskipITs
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: unit-reports, path: "**/target/surefire-reports/*.xml" }

  integration:
    needs: unit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - run: ./mvnw -B -ntp verify -Dsurefire.skip=true     # Testcontainers: Docker is available on ubuntu runners
```

### Rules that keep CI trustworthy
* **Main must stay green.** A red main branch blocks everyone; revert first, debug second.
* **No skipping flaky tests silently** — quarantine with an owner (see flaky tests).
* **Same commands locally and in CI** (`./mvnw verify`), pinned tool versions (Maven wrapper, JDK version).
* **Fail fast**: compilation and unit tests before slow stages; `-T 1C` parallel module builds.
* **Publish test reports** (JUnit XML) so failures are readable in the PR, not buried in logs.

### Choosing tests per stage
* Unit tests: always, everywhere.
* Integration tests with Testcontainers: in PRs, at least for changed modules.
* Contract verification: in the provider's pipeline on every change, and triggered by consumer pact changes.
* E2E: a small smoke suite after deploying to a test environment; the full suite nightly.

## 🔴 Senior Level

### Speeding up large suites
* **Test impact analysis / selective testing** — run only tests affected by the change. Gradle's build cache and incremental test tasks skip unchanged work; Maven can use `gitflow-incremental-builder` or build tools like Bazel; commercial tools (Develocity Predictive Test Selection) use ML on historical results.
* **Sharding** — split the suite across N machines by historical duration (GitHub Actions `matrix`, Gradle Develocity test distribution, `circleci tests split --split-by=timings`).
* **Parallelism inside the JVM** — JUnit 5 `junit.jupiter.execution.parallel.enabled=true` with `@ResourceLock` for shared resources; Surefire `forkCount=1C` with `reuseForks=true` for process isolation.
* **Spring context reuse** — most Spring suites are slow because of dozens of distinct contexts; consolidating test configurations often halves runtime.
* **Caching** — dependency cache (`~/.m2`), Docker image cache for Testcontainers, remote build cache for Gradle.

### Quality gates that mean something
* **Diff coverage** ≥ threshold on changed lines (not global coverage).
* **Static analysis** with zero *new* critical issues (SonarQube quality gate on new code, Error Prone, SpotBugs).
* **Dependency and container scanning** (OWASP Dependency-Check, Trivy, GitHub Dependabot alerts) failing on new critical CVEs.
* **Contract `can-i-deploy`** before each environment promotion.
* **Performance regression check** on key endpoints for main-branch builds (JMH or Gatling against a baseline, alert on > X% regression).

### Test environments and data
* Prefer **ephemeral environments** per PR (namespace per branch in Kubernetes) over a shared, drifting "staging" that every team breaks.
* Seed data via migrations and APIs, not database dumps of production (privacy, size). Mask data if production-like volume is needed.
* Run E2E tests against the **same artifact** (container image digest) that will go to production — never rebuild between stages.

### Metrics for the pipeline itself
Track and review monthly:
* PR feedback time (p50/p90) — the developer-experience number that matters.
* Main-branch failure rate and mean time to green.
* Flake rate per test and per team.
* Cost per pipeline run (CI minutes are real money at scale).

These connect directly to DORA metrics: slow or untrusted pipelines lower deployment frequency and increase lead time for changes.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I layer tests by speed: unit tests and static analysis on every push, integration and contract tests on PRs and main, E2E and performance suites after deployment or nightly. I keep main green, separate Surefire and Failsafe, shard and cache to keep PR feedback under ten minutes, and gate on diff coverage, new static-analysis issues and contract compatibility.

**Must know:**
* Surefire (`*Test`) vs Failsafe (`*IT`).
* Fail fast; same commands locally and in CI.
* Sharding, parallel execution, Spring context reuse, build caches.
* Test the same artifact through all stages.
* Measure feedback time and flake rate.

**Common follow-ups:**
* Your PR build takes 45 minutes — what do you do?
* Where do E2E tests run?
* How do you prevent a broken main branch?

**Red flags:** one giant pipeline running everything on every push; rebuilding artifacts per environment; disabling failing tests to merge.
