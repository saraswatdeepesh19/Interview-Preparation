# Test data builders and object mothers

---

## 🟢 Junior Level

Tests need objects: a `User`, an `Order` with items, an `Address`. Creating them with long constructors in every test creates noise and breaks every test when the constructor changes.

Two patterns solve this:

* **Object Mother** - a class with static factory methods that return ready-made, *named* objects (`Users.activeAdmin()`).
* **Test Data Builder** - a fluent builder with sensible defaults; each test overrides only what matters (`aUser().withAge(17).build()`).

### Analogy
An Object Mother is a menu of pre-made combo meals. A Test Data Builder is a build-your-own sandwich where every ingredient has a default, and you only say "no onions".

### Minimal example

```java
public record User(String name, int age, String email, boolean active) {}
```

```java
public final class UserBuilder {
    private String name = "Default Name";
    private int age = 30;
    private String email = "default@example.com";
    private boolean active = true;

    public static UserBuilder aUser() { return new UserBuilder(); }

    public UserBuilder withName(String name)   { this.name = name;   return this; }
    public UserBuilder withAge(int age)        { this.age = age;     return this; }
    public UserBuilder withEmail(String email) { this.email = email; return this; }
    public UserBuilder inactive()              { this.active = false; return this; }

    public User build() { return new User(name, age, email, active); }
}
```

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertFalse;

class MembershipPolicyTest {

    static boolean canVote(User u) { return u.active() && u.age() >= 18; }

    @Test
    void minorCannotVote() {
        User minor = UserBuilder.aUser().withAge(17).build();   // only the relevant detail is visible
        assertFalse(canVote(minor));
    }
}
```

The test states *why* the user is special (age 17), and nothing else.

## 🟡 Middle Level

### Object Mother vs Builder

| Aspect | Object Mother | Test Data Builder |
|---|---|---|
| API | `Users.adult()`, `Users.minor()` | `aUser().withAge(17)` |
| Customisation | explosion of factory methods | flexible by design |
| Readability | very high for stable archetypes | high; shows deviations |
| Maintenance | grows into a "god class" | one builder per type |
| Best for | few well-known personas | many combinations |

They combine well: a mother returns a *builder*, so tests can tweak it:

```java
public final class Users {
    private Users() {}
    public static UserBuilder adult()  { return UserBuilder.aUser().withAge(30); }
    public static UserBuilder minor()  { return UserBuilder.aUser().withAge(15); }
    public static UserBuilder admin()  { return adult().withName("Admin"); }
}

// Users.minor().inactive().build()
```

### Nested builders and defaults for aggregates

```java
import java.util.ArrayList;
import java.util.List;
import java.math.BigDecimal;

record Item(String sku, int qty, BigDecimal price) {}
record Order(String id, User customer, List<Item> items) {}

final class OrderBuilder {
    private String id = "ORD-1";
    private User customer = UserBuilder.aUser().build();
    private final List<Item> items = new ArrayList<>(List.of(new Item("SKU-1", 1, new BigDecimal("9.99"))));

    static OrderBuilder anOrder() { return new OrderBuilder(); }

    OrderBuilder forCustomer(UserBuilder b) { this.customer = b.build(); return this; }
    OrderBuilder withItems(Item... i)       { items.clear(); items.addAll(List.of(i)); return this; }
    OrderBuilder empty()                    { items.clear(); return this; }

    Order build() { return new Order(id, customer, List.copyOf(items)); }
}
```

### Best practices
1. **Defaults must be valid** - `build()` returns an object that passes domain validation, so tests are only failing for the thing under test.
2. **Defaults must be unique where needed** - generate unique e-mails/IDs (`UUID`/counter) to avoid unique-constraint collisions in DB tests.
3. **No randomness** unless seeded and logged.
4. **Builders live in test source set** (or a shared `testFixtures` module in Gradle `java-test-fixtures`).
5. **Do not add test-only constructors/setters to production classes**; the builder should use the public API (or the persistence layer's own mapping).
6. Name the entry point `aUser()`/`anOrder()` for natural reading.

### Lombok / libraries
* Lombok `@Builder` on production classes works but pollutes domain classes with test convenience and defaults; typically a separate test builder is cleaner.
* **Instancio**, **EasyRandom**, **Podam** auto-populate objects with random values - fine for "any valid object" cases and mapping tests, but weak when a specific scenario must be readable. Instancio example:

```java
import org.instancio.Instancio;
import static org.instancio.Select.field;

User u = Instancio.of(User.class)
        .set(field(User::age), 17)
        .create();
```

### Common mistakes
* Builders replicating production logic (computing totals) - tests then repeat bugs.
* A single mega fixture used by hundreds of tests: changing it breaks everything and hides intent.
* Defaults tied to environment (`LocalDate.now()`) causing non-determinism.

## 🔴 Senior Level

### Persisting builders for integration tests
For DB tests, a builder produces a *transient* object; a **persister** saves it and returns the managed entity. A common design uses a `TestEntityManager` (Spring) or a repository to keep tests short:

```java
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;

public class TestData {
    private final TestEntityManager em;

    public TestData(TestEntityManager em) { this.em = em; }

    public User persist(UserBuilder b) {
        return em.persistFlushFind(b.build());   // flush so constraints are checked immediately
    }
}
```

Use unique-value generators in the builder (`AtomicLong` sequence) so repeated persists in one transaction/DB don't clash.

### Generics-based builder with self-type for hierarchies

```java
abstract class AbstractBuilder<T, B extends AbstractBuilder<T, B>> {
    protected String id = "id";

    @SuppressWarnings("unchecked")
    protected B self() { return (B) this; }

    public B withId(String id) { this.id = id; return self(); }
    public abstract T build();
}

final class CustomerBuilder extends AbstractBuilder<String, CustomerBuilder> {
    private String tier = "STANDARD";
    public CustomerBuilder vip() { this.tier = "VIP"; return this; }
    @Override public String build() { return id + ":" + tier; }
}
```

### Immutability and copy-on-write
Make builders *immutable* (each `withX` returns a new builder) when you share a base builder among tests via constants:

```java
record UserBuilderV2(String name, int age) {
    static final UserBuilderV2 BASE = new UserBuilderV2("Ann", 30);
    UserBuilderV2 withAge(int a) { return new UserBuilderV2(name, a); }
    User build() { return new User(name, age, name.toLowerCase() + "@x.com", true); }
}
```

A shared **mutable** builder constant is a classic source of cross-test leakage and flakiness under parallel execution.

### Scaling across a codebase
* Provide builders via a **test-fixtures module** (Maven `test-jar`, Gradle `java-test-fixtures`) so other modules reuse them.
* Generate builders for DTOs/JSON from OpenAPI schemas; for JSON payloads, keep fixtures as files in `src/test/resources` plus a patch helper (`JsonPath.set`), or builders producing `Map` structures.
* For event-driven systems keep *event builders* with valid correlation IDs and timestamps from an injected `Clock`.
* Evaluate **property-based generators** (jqwik `Arbitraries`) when the invariant must hold for every valid object - builders produce the *examples*, generators the *domain*.

### Trade-offs and diagnostics
* If you need >5 `with...` overrides in most tests, the domain object is probably too large - consider splitting aggregates.
* Builders can hide that a constructor now requires an invalid combination; keep domain validation in the object so the builder's `build()` fails loudly.
* Measure fixture cost: thousands of object graphs per test class (nested defaults creating whole trees) can add seconds; lazily build nested defaults.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Test Data Builders provide valid default objects with fluent overrides so each test shows only what is relevant, and survive constructor changes. Object Mothers provide named archetypes; combining them (mothers returning builders) gives both readability and flexibility.

**Must know:**
* Builder defaults are always valid and deterministic.
* Mother = static factories; Builder = fluent customisation.
* Keep in test source set or test-fixtures module.
* Unique values for DB tests.
* Beware shared mutable builders.

**Common follow-ups:**
* Builder vs Lombok `@Builder` vs Instancio?
* How do you create data for 20 integration tests without duplication?
* How do you keep test data consistent with schema changes?

**Red flags:** giant shared fixture objects; random data without seed; test-only setters in production code.
