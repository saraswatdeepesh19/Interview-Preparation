# What makes a good test

---

## 🟢 Junior Level

A good test is one you can **trust**, **read**, and **run quickly**. When it fails, it should tell you *what* broke without a debugger. When it passes, you should be confident the feature works.

The classic acronym is **F.I.R.S.T.**:

| Letter | Meaning | Example violation |
|---|---|---|
| **F**ast | Runs in milliseconds | `Thread.sleep(5000)` |
| **I**ndependent | Does not depend on other tests or order | test B needs data from test A |
| **R**epeatable | Same result everywhere, every time | depends on `LocalDate.now()` |
| **S**elf-validating | Pass/fail without manual inspection | prints to console |
| **T**imely | Written close to the code (ideally before) | tests added months later |

### Analogy
A smoke detector: it must be sensitive (detects real fires), quiet when nothing burns (no false alarms), and its signal must be unambiguous. A test that cries wolf gets ignored.

### The Arrange–Act–Assert structure

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class ShoppingCartTest {

    @Test
    void totalIsSumOfItemPrices() {
        // Arrange
        ShoppingCart cart = new ShoppingCart();
        cart.add("book", 10);
        cart.add("pen", 5);

        // Act
        int total = cart.total();

        // Assert
        assertEquals(15, total);
    }
}

class ShoppingCart {
    private final java.util.Map<String, Integer> items = new java.util.LinkedHashMap<>();
    void add(String name, int price) { items.put(name, price); }
    int total() { return items.values().stream().mapToInt(Integer::intValue).sum(); }
}
```

Also called *Given–When–Then*. One test = one behaviour = (usually) one logical assertion.

### Naming
A good name states the **behaviour and condition**: `totalIsZeroForEmptyCart`, `rejectsNegativePrice`. Not `test1` or `testAdd`.

## 🟡 Middle Level

### Test behaviour, not implementation
A test coupled to private structure breaks on every refactoring, which kills the main value of tests: *allowing safe refactoring*.

```java
// Brittle: verifies HOW
verify(repository).findById(1L);
verify(mapper).toDto(any());
verifyNoMoreInteractions(repository, mapper);

// Robust: verifies WHAT
assertThat(service.getUser(1L).name()).isEqualTo("Ann");
```

Rule of thumb: assert on **outputs and observable side effects at the boundary** (return value, persisted state, message sent), and use `verify` only for side effects that are the point of the behaviour (e.g., an email was sent).

### Properties of a high-quality test suite

| Property | Why it matters | How to achieve |
|---|---|---|
| Readable | Tests are documentation | descriptive names, builders, `@DisplayName` |
| Deterministic | Trust | inject `Clock`, fixed seeds, no shared state |
| Isolated | Parallel runs, any order | fresh fixtures per test, `@BeforeEach` |
| Focused | Pinpoint failure | one behaviour per test |
| Maintainable | Cost of change | test data builders, no copy/paste |
| Meaningful failures | Quick diagnosis | AssertJ messages, `as("...")` |

### Anti-patterns
1. **Logic in tests** – loops/ifs/duplicated production algorithm. Tests should be dumb and obvious.
2. **Over-mocking** – the test only proves the mock returns what you told it.
3. **The Giant** – 200 lines, 15 asserts; first failure hides the others.
4. **The Inspector** – uses reflection to read private fields.
5. **The Liar** – passes but asserts nothing (no assertion, or assertion in a swallowed exception).
6. **Shared mutable state** – `static` lists reused across tests.
7. **Sleeping** – `Thread.sleep` to wait for async work.

### Descriptive failure messages

```java
import static org.assertj.core.api.Assertions.assertThat;

assertThat(invoice.total())
        .as("total for invoice %s", invoice.id())
        .isEqualByComparingTo("120.00");
```

### Arrange phase should be short
If setup takes 30 lines, the code is hard to use – a design smell – or you need a [test data builder](08.%20Test%20data%20builders%20and%20object%20mothers.md).

### Test one thing, but cover the edges
Use equivalence classes and boundary values: for an age check `>= 18` test 17, 18, and maybe `-1`, `Integer.MAX_VALUE`. Combine with [parameterized tests](07.%20JUnit%205%20parameterized%20tests%20nested%20classes%20and%20extensions.md).

## 🔴 Senior Level

### Test design as a feedback signal
If a test is painful to write, production design is usually the cause: too many collaborators (SRP violation), static singletons, hidden time/randomness, deep inheritance. Treat test pain as design feedback instead of reaching for `PowerMock`.

### Sensitivity vs. specificity of a suite
A good suite is **sensitive** (catches regressions: low false negatives) and **specific** (does not fail for irrelevant changes: low false positives). Over-specified tests (verifying call order, exact SQL strings, full JSON equality including irrelevant fields) hurt specificity. Under-asserting tests hurt sensitivity. Measure sensitivity with [mutation testing](18.%20Mutation%20testing%20with%20PIT.md), not coverage.

### Determinism in practice

```java
import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;
import java.util.Random;

class DeterministicFixtures {
    static final Clock FIXED_CLOCK =
            Clock.fixed(Instant.parse("2025-03-01T10:15:30Z"), ZoneOffset.UTC);

    static Random seeded() { return new Random(42L); }
}
```

If a test uses randomised data (property-based testing with jqwik or generated data), *always print the seed* so failures can be reproduced.

### Test effort by risk, not by layer
Allocate test effort by **risk x change frequency**. A payment calculation with many branches deserves exhaustive parameterized tests and mutation testing; a getter does not deserve any.

### Parallel execution
JUnit 5 supports parallelism via `junit-platform.properties`:

```properties
junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.default = concurrent
junit.jupiter.execution.parallel.mode.classes.default = concurrent
```

Only independent tests survive this. Shared static state, shared DB rows, fixed ports all reveal themselves immediately. Use `@ResourceLock` for genuinely shared resources and `@Isolated` for tests that need exclusive execution.

### Test code is production code
* Review it with the same rigour; apply DRY **in helpers** but keep each test *DAMP* (Descriptive And Meaningful Phrases) - some duplication is fine if it keeps the test readable top-to-bottom.
* Delete tests that no longer express a requirement. A test suite is not an archive.
* Quarantine, then fix or delete flaky tests (see [Flaky tests](19.%20Flaky%20tests.md)).

### Diagnostics checklist for a bad suite
1. Slowest 10 tests – accidental integration?
2. Tests with no assertions (PIT shows survivors, static analysis flags them).
3. Tests failing when run alone vs. in suite (order dependency) – run periodically with `MethodOrderer.Random`.
4. Mock-to-assert ratio.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A good test is fast, isolated, deterministic, readable, and verifies observable behaviour, not implementation. It follows Arrange–Act–Assert, has a name that states the behaviour, fails with a clear message, and survives refactoring.

**Must know:**
* F.I.R.S.T. principles.
* AAA / Given-When-Then.
* Behaviour over implementation; avoid over-verifying mocks.
* Inject time and randomness for determinism.
* Test pain = design feedback.
* DAMP over DRY inside tests.

**Common follow-ups:**
* How many assertions per test?
* How do you test private methods? (Don't – test via public behaviour.)
* How do you know your tests are good? (Mutation testing, not coverage.)

**Red flags:** `Thread.sleep` in tests, tests without assertions, tests that depend on execution order, "we fix flaky tests by re-running".
