# Testing concurrent and async code

---

## 🟢 Junior Level

Concurrent and asynchronous code is hard to test because the **order of events is not fixed**. A test that passes 999 times can fail the 1000th time. The goals are:

1. **Make async code synchronous in unit tests** when possible.
2. **Wait for conditions**, never for fixed time, when the code must stay async.
3. **Force interleavings** deliberately to test race conditions.

### Testing a `CompletableFuture`

```java
@Test
void enrichesOrder() {
    CompletableFuture<EnrichedOrder> future = enricher.enrich(order);   // async

    EnrichedOrder result = future.orTimeout(2, TimeUnit.SECONDS).join(); // bounded wait
    assertThat(result.customerName()).isEqualTo("Ada");
}
```

### Injecting the executor

```java
class Enricher {
    private final Executor executor;
    Enricher(Executor executor) { this.executor = executor; }

    CompletableFuture<EnrichedOrder> enrich(Order o) {
        return CompletableFuture.supplyAsync(() -> lookup(o), executor);
    }
}

// In unit tests: run everything on the calling thread — deterministic, no waiting
Enricher enricher = new Enricher(Runnable::run);
```

## 🟡 Middle Level

### Awaitility for eventually-true conditions

```java
@Test
void consumerProcessesEvent() {
    kafkaTemplate.send("orders", "o-1", new OrderPlaced("o-1"));

    await().atMost(Duration.ofSeconds(10))
           .pollInterval(Duration.ofMillis(100))
           .untilAsserted(() -> assertThat(projection.find("o-1")).hasValueSatisfying(
                   p -> assertThat(p.status()).isEqualTo("PLACED")));
}
```

### Latches and barriers to control interleaving

```java
@Test
void counterIsThreadSafe() throws Exception {
    int threads = 16, perThread = 10_000;
    Counter counter = new Counter();
    CountDownLatch start = new CountDownLatch(1);

    try (ExecutorService pool = Executors.newFixedThreadPool(threads)) {   // AutoCloseable since 19
        for (int t = 0; t < threads; t++) {
            pool.submit(() -> {
                start.await();                               // release all threads at once
                for (int i = 0; i < perThread; i++) counter.increment();
                return null;
            });
        }
        start.countDown();
    }                                                        // close() waits for completion
    assertThat(counter.value()).isEqualTo((long) threads * perThread);
}
```

A non-thread-safe counter (`value++` on a plain field) usually fails this test quickly — but "usually" is the key word: stress tests raise confidence, they don't prove correctness.

### Testing `@Async` and scheduled code in Spring
* Replace the async executor in tests with a `SyncTaskExecutor` bean, or test the class directly without Spring proxies.
* Disable `@Scheduled` in tests (`spring.task.scheduling.enabled` is not a Boot property — use a profile-conditional `@EnableScheduling` configuration) and invoke the job method directly.

## 🔴 Senior Level

### Systematic concurrency testing with jcstress
For low-level code (lock-free structures, double-checked locking, publication), the **Java Concurrency Stress (jcstress)** harness runs actors concurrently millions of times and classifies observed outcomes:

```java
@JCStressTest
@Outcome(id = "1, 1", expect = Expect.ACCEPTABLE, desc = "both see each other")
@Outcome(id = "0, 1", expect = Expect.ACCEPTABLE)
@Outcome(id = "1, 0", expect = Expect.ACCEPTABLE)
@Outcome(id = "0, 0", expect = Expect.ACCEPTABLE_INTERESTING, desc = "store buffering reordering")
@State
public class StoreBuffering {
    int x, y;                      // make them volatile and 0, 0 becomes forbidden

    @Actor public void actor1(II_Result r) { x = 1; r.r1 = y; }
    @Actor public void actor2(II_Result r) { y = 1; r.r2 = x; }
}
```

It demonstrates Java Memory Model behavior that ordinary unit tests can never reliably trigger.

### Deterministic simulation
For application-level concurrency, design for testability:
* **Virtual time**: inject a `Clock` and a scheduler abstraction; in tests, advance time manually (`TestScheduler` in RxJava, `VirtualTimeScheduler` in Reactor's `StepVerifier.withVirtualTime`).
* **Explicit hooks**: allow tests to pause a component at a specific point (a test-only `CyclicBarrier` injected through a seam) to reproduce a race found in production.
* **Lincheck** (JetBrains, works for Java) explores many interleavings and checks linearizability of concurrent data structures against a sequential specification.

### Testing virtual-thread code (Java 21)
* Detect **pinning** in tests: run with `-Djdk.tracePinnedThreads=full` (21–23) or assert no `jdk.VirtualThreadPinned` JFR events in a JUnit extension using `RecordingStream`.
* Structured concurrency (`StructuredTaskScope`, preview) makes cancellation testable: assert that when one subtask fails, siblings are interrupted and no threads leak.

### Common mistakes
* Assertions inside a background thread: a failing `assertThat` throws in the worker thread and is swallowed; the test passes. Collect results and assert in the test thread, or propagate via `Future.get()`.
* `ExecutorService` never shut down: threads leak across tests, causing later timeouts.
* Timeouts that are too tight for CI (`atMost(200ms)`) — use generous upper bounds; a passing test returns as soon as the condition holds anyway.
* Using `parallelStream()` in production code under test, which uses the shared common pool — contention with other tests causes sporadic slowness.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I make async code deterministic in unit tests by injecting executors (a direct executor) and clocks, use Awaitility with bounded waits where code must stay async, use latches to force interleavings for race tests, and use jcstress or Lincheck for low-level concurrent structures. Assertions always happen on the test thread.

**Must know:**
* `Runnable::run` direct executor; `orTimeout`/`get(timeout)`.
* Awaitility `untilAsserted` instead of `sleep`.
* `CountDownLatch`/`CyclicBarrier` to start threads together.
* jcstress for JMM-level behavior; virtual time schedulers.
* Exceptions in worker threads are lost unless propagated.

**Common follow-ups:**
* How do you prove a class is thread-safe?
* How do you test a scheduled job?
* How do you test reactive pipelines with time?

**Red flags:** `Thread.sleep` in tests; asserting in background threads; executors never closed.
