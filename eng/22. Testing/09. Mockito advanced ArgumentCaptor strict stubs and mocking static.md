# Mockito advanced ArgumentCaptor strict stubs and mocking static

---

## 🟢 Junior Level

Beyond `mock`/`when`/`verify`, Mockito offers three advanced tools that every serious Java tester meets sooner or later:

* **`ArgumentCaptor`** - grabs the *actual argument* passed to a mock so you can assert on its details.
* **Strict stubs** - Mockito fails the test if you configured a stub that was never used (dead setup) or used it with different arguments.
* **Static mocking** - `mockStatic(...)` temporarily replaces `static` methods such as `UUID.randomUUID()` or `LocalDate.now()`.

### Analogy
`ArgumentCaptor` is a parcel scanner: instead of asking "was *a* parcel sent?", you open the parcel and check what is inside. Strict stubs is a tidy-workshop rule: any tool you took out and never used is reported.

### Minimal example: capturing an argument

```java
import org.junit.jupiter.api.Test;
import org.mockito.ArgumentCaptor;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.*;

interface EmailSender { void send(Email email); }
record Email(String to, String subject, String body) {}

class RegistrationService {
    private final EmailSender sender;
    RegistrationService(EmailSender sender) { this.sender = sender; }

    void register(String userName, String address) {
        sender.send(new Email(address, "Welcome " + userName, "Thanks for joining!"));
    }
}

class RegistrationServiceTest {

    @Test
    void sendsWelcomeEmail() {
        EmailSender sender = mock(EmailSender.class);
        ArgumentCaptor<Email> captor = ArgumentCaptor.forClass(Email.class);

        new RegistrationService(sender).register("Ann", "ann@example.com");

        verify(sender).send(captor.capture());
        Email sent = captor.getValue();
        assertEquals("ann@example.com", sent.to());
        assertEquals("Welcome Ann", sent.subject());
    }
}
```

Without the captor you would have to implement `equals` on `Email` and build an identical expected object - the captor lets you check just the fields you care about.

## 🟡 Middle Level

### ArgumentCaptor details
* `captor.getValue()` - last captured argument; `captor.getAllValues()` - all, in call order.
* Annotation form: `@Captor ArgumentCaptor<Email> captor;` (works with `MockitoExtension`; avoids generics warnings for `List<String>`).
* Capture only in `verify(...)`. Using captors in `when(...)` stubbing is discouraged (undefined behaviour: captors capture during stubbing too).
* Alternative: `argThat(email -> email.to().equals("ann@example.com"))` when you only need a boolean check; or `assertArg(a -> ...)` (Mockito 5.3+), which performs assertions inline:

```java
verify(sender).send(assertArg(e -> assertEquals("Welcome Ann", e.subject())));
```

### Strict stubs
With `@ExtendWith(MockitoExtension.class)` (or `MockitoJUnitRunner.StrictStubs` / `Mockito.mockitoSession().strictness(STRICT_STUBS)`):

1. **Unused stubs** -> `UnnecessaryStubbingException` at the end of the test.
2. **Argument mismatch** -> `PotentialStubbingProblem` when a stubbed method is invoked with different arguments than stubbed (helps find typos).
3. `verifyNoMoreInteractions` also ignores stubbed invocations already verified implicitly (stubs count as verified in strict mode).

```java
@ExtendWith(MockitoExtension.class)
class StrictTest {

    @Mock PriceService prices;

    @Test
    void failsBecauseStubIsUnused() {
        when(prices.priceOf("A")).thenReturn(10);   // never called -> UnnecessaryStubbingException
    }

    @Test
    void lenientWhenReallyNeeded() {
        lenient().when(prices.priceOf("B")).thenReturn(20);   // OK even if unused
    }

    interface PriceService { int priceOf(String sku); }
}
```

Configure per class with `@MockitoSettings(strictness = Strictness.LENIENT)` - use only for legacy suites. Strict stubs keep tests honest: dead stubs usually point to behaviour that changed.

### Mocking static methods
Needs the inline mock maker (default since Mockito 5; `mockito-inline` artifact in 3/4). The returned `MockedStatic` is **thread-local** and must be closed:

```java
import org.mockito.MockedStatic;
import java.time.LocalDate;
import java.util.UUID;

@Test
void staticMock() {
    UUID fixed = UUID.fromString("00000000-0000-0000-0000-000000000001");

    try (MockedStatic<UUID> uuid = mockStatic(UUID.class)) {
        uuid.when(UUID::randomUUID).thenReturn(fixed);

        assertEquals(fixed, UUID.randomUUID());
        uuid.verify(UUID::randomUUID);
    }
    // outside the block: real UUID again
    assertNotEquals(fixed, UUID.randomUUID());
}
```

Partial static mock: `mockStatic(Util.class, CALLS_REAL_METHODS)` then stub only one method. Constructors: `try (MockedConstruction<Client> mc = mockConstruction(Client.class, (mock, ctx) -> when(mock.get()).thenReturn("x")))`.

### Common mistakes
* Forgetting `try-with-resources` -> `MockitoException: static mocking is already registered in the current thread`.
* Using `mockStatic` on `System` or `Thread` core methods -> JVM instability.
* Capturing with `any()` instead of captor (nothing to assert).
* Making stubs lenient globally to "make red tests green".

## 🔴 Senior Level

### When mocking static is the wrong answer
Static mocking papers over a design flaw: a hidden dependency. Prefer **injection**:

```java
import java.time.Clock;
import java.time.Instant;
import java.util.function.Supplier;
import java.util.UUID;

class Invoicing {
    private final Clock clock;
    private final Supplier<UUID> ids;

    Invoicing(Clock clock, Supplier<UUID> ids) { this.clock = clock; this.ids = ids; }

    Invoice issue(long amount) { return new Invoice(ids.get(), Instant.now(clock), amount); }

    record Invoice(UUID id, Instant at, long amount) {}
}
// production: new Invoicing(Clock.systemUTC(), UUID::randomUUID)
// test:       new Invoicing(Clock.fixed(...), () -> fixedId)
```

Reserve `mockStatic` for legacy code you cannot refactor yet (see [Testing legacy code](22.%20Testing%20legacy%20code.md)) or third-party static APIs (`Files`, `LocalDate.now()` in vendor code). Mark such tests with a comment and a refactoring ticket.

### How the inline mock maker works
Mockito's inline maker uses a Java agent (`Instrumentation.retransformClasses`) to **rewrite the bytecode of the target class** so every method starts with an advice hook: "if a mock/stub exists for this call in this thread, delegate to Mockito; otherwise run the original body". That is how it can mock `final`, `static`, `private` (still unstubbable by API), and constructors. Consequences:
* **Thread-local scope** of static/constructor mocks - other threads (executors, parallel streams) see the *real* behaviour. A static mock will not affect code running on a `ForkJoinPool` thread.
* **Cost**: retransformation of core classes slows the first call; massive static mocking of JDK classes can degrade JIT-inlining for those classes during the test JVM's life.
* **JDK 21+**: dynamic self-attach prints a warning and will be restricted in future releases; register the agent explicitly with `-javaagent:` in Surefire's `argLine` (Mockito docs recommend this).

### Capturing in complex flows
```java
@Captor ArgumentCaptor<List<Email>> batchCaptor;   // generic type safe via annotation

verify(sender, times(3)).send(captor.capture());
assertThat(captor.getAllValues())
        .extracting(Email::to)
        .containsExactlyInAnyOrder("a@x.com", "b@x.com", "c@x.com");
```

For *event publication* in Spring, prefer `ApplicationEvents` (`@RecordApplicationEvents`) rather than mocking `ApplicationEventPublisher`.

### Strictness strategy at scale
* Keep `STRICT_STUBS` default for new code - reports dead stubs early.
* For legacy modules, set `mockito-extensions` or `@MockitoSettings(strictness = WARN)` to log first, then fix and tighten gradually.
* Avoid `lenient()` in `@BeforeEach` unless the stub is genuinely shared; leniency hides test rot.
* With Spring `@MockitoBean`, strictness is not applied automatically; use `MockitoExtension` for pure unit tests.

### Verifying order and async
```java
InOrder order = inOrder(audit, sender);
order.verify(audit).log("start");
order.verify(sender).send(any());
order.verify(audit).log("end");
```
For async: `verify(sender, timeout(2000).times(1)).send(any())` polls until satisfied or fails at timeout - prefer Awaitility for complex conditions.

### Diagnostics
* `Mockito.framework().addListener(...)` / `MockitoListener` for custom reporting.
* `mockingDetails(mock).printInvocations()` prints all stubbings, used/unused, and invocations - gold for debugging "why isn't my stub matching?".
* `Mockito.validateMockitoUsage()` at the end of tests (done automatically by the extension) catches incomplete stubbing.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `ArgumentCaptor` extracts the real argument passed to a mock so you can assert on its fields; strict stubs fail tests with unused or mismatched stubs, keeping tests honest; `mockStatic`/`mockConstruction` (inline mock maker, thread-local, must be closed) mock statics and constructors but should be a last resort - inject `Clock`/`Supplier` instead.

**Must know:**
* `@Captor`, `getValue`/`getAllValues`, `assertArg`, `argThat`.
* `UnnecessaryStubbingException`, `PotentialStubbingProblem`, `lenient()`.
* `try (MockedStatic<T> m = mockStatic(T.class))` - thread-local scope.
* Mockito 5 uses inline mock maker by default.
* JDK 21+ agent warning and `-javaagent` configuration.

**Common follow-ups:**
* How can Mockito mock `final` classes?
* Why doesn't my static mock work inside `CompletableFuture.supplyAsync`?
* When would you use `lenient()`?

**Red flags:** global leniency; `mockStatic` everywhere; no `try-with-resources`; mocking `System`.
