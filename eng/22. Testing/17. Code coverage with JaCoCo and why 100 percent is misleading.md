# Code coverage with JaCoCo and why 100 percent is misleading

---

## 🟢 Junior Level

**Code coverage** measures which parts of your code were *executed* while tests ran. **JaCoCo** is the standard Java tool: it instruments bytecode, runs your tests, and reports which lines and branches were hit.

### The key insight
Coverage tells you what is **not tested**. It does not tell you that covered code is tested **well**. A test with no assertions can reach 100% coverage:

```java
@Test
void coversEverythingAssertsNothing() {
    discountService.discountFor(customer, cart);   // executed => "covered", but nothing is checked
}
```

### Maven setup

```xml
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.12</version>
  <executions>
    <execution><goals><goal>prepare-agent</goal></goals></execution>          <!-- sets argLine with -javaagent -->
    <execution><id>report</id><phase>verify</phase><goals><goal>report</goal></goals></execution>
  </executions>
</plugin>
```

`mvn verify` produces `target/site/jacoco/index.html`.

## 🟡 Middle Level

### Metrics JaCoCo reports

| Counter | Meaning |
| --- | --- |
| Instructions | Bytecode instructions executed — the most precise unit |
| **Branches** | Each outcome of `if`, `switch`, `?:`, `&&`/`||` — the most useful metric |
| Lines | A line is covered if at least one instruction ran (partially covered = yellow) |
| Methods / Classes | Entered at least once |
| Cyclomatic complexity | Missed complexity = number of independent paths not exercised |

Prefer **branch coverage** over line coverage: `if (a && b)` on one line can be "100% line covered" while the `b == false` path never ran.

### Enforcing a floor (ratchet, not target)

```xml
<execution>
  <id>check</id>
  <goals><goal>check</goal></goals>
  <configuration>
    <rules>
      <rule>
        <element>BUNDLE</element>
        <limits>
          <limit><counter>BRANCH</counter><value>COVEREDRATIO</value><minimum>0.70</minimum></limit>
        </limits>
      </rule>
    </rules>
    <excludes>
      <exclude>**/config/**</exclude>
      <exclude>**/*Application.class</exclude>
      <exclude>**/dto/**</exclude>
    </excludes>
  </configuration>
</execution>
```

Better than a global target: **diff coverage** on changed lines in a pull request (SonarQube "coverage on new code", `diff-cover`), so new code is tested without forcing busywork on legacy code.

### Merging unit and integration coverage
Surefire and Failsafe produce separate `.exec` files. Use `prepare-agent-integration` and `report-aggregate` (multi-module) or `merge`, otherwise your integration-tested repositories look uncovered.

## 🔴 Senior Level

### How JaCoCo measures
JaCoCo attaches as a Java agent and **instruments classes on the fly** when they are loaded: it inserts *probes* (boolean array writes) at control-flow edges, so overhead is small (typically a few percent). On JVM exit it dumps execution data, and the report step maps probes back to bytecode and then to source lines using debug info. Consequences:
* Code compiled without debug information can't be mapped to lines.
* Classes must be byte-identical between test run and report generation — rebuilding in between makes classes "not matching" execution data.
* Other agents that rewrite bytecode (some APMs, Mockito inline mocks, PowerMock) can conflict; JaCoCo filters synthetic code generated by `javac` and Kotlin (lambdas, `switch` on strings, try-with-resources), and Lombok code annotated `@Generated` when `lombok.addLombokGeneratedAnnotation = true`.

### Why 100% is the wrong goal (Goodhart's law)
Once coverage becomes a target, it stops measuring quality:
* People write assertion-free tests, test getters/setters, or test `toString()` to move the number.
* Tests become coupled to implementation details, so refactoring breaks them without catching bugs.
* The last 10–20% (defensive branches, framework glue, `catch (InterruptedException)`) is the most expensive to cover and least likely to contain business bugs.
* Coverage can't detect **missing code** — a requirement nobody implemented has no line to cover.

### What to use instead or in addition
* **Mutation testing** (PIT) — measures whether tests *detect* changes, i.e. the strength of assertions.
* **Risk-based targets** — very high branch coverage on pricing, permissions, money movement; moderate elsewhere; none for generated code.
* **Coverage trends** per module, and **uncovered critical paths** reviewed explicitly in PRs.
* **Production coverage** — tools that record which code actually runs in production (JaCoCo agent in a canary, or tools like Codekvast) help find dead code to delete, which is the cheapest way to raise coverage.

### A useful team policy
1. Every bug fix comes with a test that fails without the fix.
2. New/changed code: ≥ 80% branch coverage on the diff, reviewed by humans.
3. Critical domain packages: mutation score threshold (e.g. ≥ 70% with PIT).
4. No global 100% requirement; exclusions documented in the build file.

## 🎯 Interview Cheat Sheet

**30-second pitch:** JaCoCo instruments bytecode with probes to report instruction, branch and line coverage. Coverage is great at finding untested code but says nothing about assertion quality, so making 100% a target backfires. I enforce diff coverage on new code, prefer branch coverage, and use mutation testing on critical code.

**Must know:**
* `prepare-agent` + `report` + `check`; merge unit and IT data.
* Branch coverage > line coverage.
* Goodhart's law: a coverage target invites assertion-free tests.
* Coverage can't show missing requirements.
* Diff coverage and mutation score are better quality gates.

**Common follow-ups:**
* What coverage threshold would you set?
* Why does a `&&` condition show as partially covered?
* How does JaCoCo work with integration tests?

**Red flags:** "we have 100% coverage so we have no bugs"; testing getters for coverage; blocking all PRs on a global number for a legacy codebase.
