# Testing legacy code

---

## 🟢 Junior Level

Michael Feathers defines **legacy code** as *code without tests*. You can't change it confidently because you don't know what you'll break. The strategy is:

1. **Find the change point** — where you need to modify code.
2. **Find a test point** — where you can observe behavior.
3. **Break dependencies** just enough to get the code under test.
4. **Write characterization tests** that record what the code *currently* does.
5. **Make your change**, then refactor under the safety net.

### Characterization test
You don't assert what the code *should* do — you capture what it *does*:

```java
@Test
void characterizeInvoiceTotal() {
    LegacyInvoiceCalculator calc = new LegacyInvoiceCalculator();
    BigDecimal total = calc.total(sampleOrderWithThreeLines());

    // First run: assert something obviously wrong, read the failure, then pin the real value
    assertThat(total).isEqualByComparingTo("118.37");
}
```

If the current behavior looks like a bug, still pin it (and file a ticket). Changing behavior and refactoring at the same time is how regressions happen.

## 🟡 Middle Level

### Breaking dependencies: seams
A **seam** is a place where you can change behavior without editing the code at that point.

```java
// Legacy: hard-wired dependencies, impossible to unit test
public class ReportService {
    public void sendDailyReport() {
        List<Sale> sales = new SalesDao().findForDate(LocalDate.now());   // DB + current time
        String html = render(sales);
        new SmtpMailer("smtp.corp.local").send("boss@corp.local", html);  // real email
    }
}
```

Minimal, safe refactorings (often IDE-automated):

```java
public class ReportService {
    private final SalesDao dao;
    private final Mailer mailer;
    private final Clock clock;

    public ReportService() {                                  // keep old constructor: callers unchanged
        this(new SalesDao(), new SmtpMailer("smtp.corp.local"), Clock.systemDefaultZone());
    }

    ReportService(SalesDao dao, Mailer mailer, Clock clock) { // new seam for tests
        this.dao = dao; this.mailer = mailer; this.clock = clock;
    }

    public void sendDailyReport() {
        List<Sale> sales = dao.findForDate(LocalDate.now(clock));
        mailer.send("boss@corp.local", render(sales));
    }
}
```

Techniques from *Working Effectively with Legacy Code*: **Parameterize Constructor**, **Extract Interface**, **Extract and Override Call** (subclass in test overrides a protected method), **Introduce Static Setter** for singletons (temporary), **Sprout Method/Class** (write new logic in a new, tested unit and call it from the old code), **Wrap Method**.

### Approval (golden master) testing
For code producing large outputs (reports, XML, PDFs-as-text), capture the full output once and compare future runs to it:

```java
@Test
void reportMatchesApprovedOutput() {
    String html = new ReportRenderer().render(fixtureSales());
    Approvals.verify(html);          // ApprovalTests: stores *.approved.txt, diffs on change
}
```

Combine with many generated inputs (combination approvals) to cover a wide input space quickly.

## 🔴 Senior Level

### A playbook for a large untested service
1. **Outside-in safety net first** — record real traffic or build HTTP-level tests (RestAssured + Testcontainers) around the endpoints you'll touch. They're slow but don't depend on internal structure, so they survive refactoring.
2. **Characterize with production data shapes** — sample anonymized production inputs; for batch jobs, diff the outputs of old vs new code on yesterday's data (*parallel run*).
3. **Refactor toward seams** — move I/O to the edges (hexagonal style), inject `Clock`, random sources and executors.
4. **Push tests down** — as units become isolated, replace slow characterization tests with fast unit tests and delete redundant ones.
5. **Measure** — coverage on touched code, mutation score on critical classes, and production error rates.

### Dealing with statics, singletons and `final`
* Mockito's inline mock maker (default since Mockito 5) can mock `final` classes and, with `mockStatic`, static methods inside a try-with-resources scope. Use it as a **temporary** crutch to get tests in place, then refactor toward injection:

```java
try (MockedStatic<LegacyConfig> cfg = mockStatic(LegacyConfig.class)) {
    cfg.when(() -> LegacyConfig.get("tax.rate")).thenReturn("0.19");
    assertThat(calculator.tax(new BigDecimal("100"))).isEqualByComparingTo("19.00");
}
```

* PowerMock is effectively dead (no JUnit 5 / modern JDK support); don't introduce it.

### Shadow traffic and branch by abstraction
For risky rewrites of a legacy component:
* **Branch by abstraction** — introduce an interface over the old implementation, implement the new version behind it, switch with a feature flag, delete the old one.
* **Shadowing / dark launch** — send production requests to both implementations, return the old result, and log differences (GitHub's *Scientist* pattern). This is characterization testing at production scale and finds edge cases no fixture would.

```java
Price price(Order o) {
    Price legacy = legacyPricer.price(o);
    if (flags.isEnabled("pricing-shadow")) {
        shadowExecutor.execute(() -> {
            Price candidate = newPricer.price(o);
            if (!candidate.equals(legacy)) mismatches.record(o.id(), legacy, candidate);
        });
    }
    return legacy;
}
```

### Avoid the traps
* Big-bang "let's write tests for everything first" — never finishes. Test what you're changing (the *boy scout rule*).
* Over-mocking legacy internals — tests lock in the current structure and block the refactoring they were meant to enable.
* Fixing bugs while characterizing — first pin, then change in a separate, reviewed step.

## 🎯 Interview Cheat Sheet

**30-second pitch:** For legacy code I first pin current behavior with characterization or approval tests at a stable boundary, then break dependencies through seams — parameterized constructors, extracted interfaces, injected clocks — make the change, and push tests down to fast unit level as the design improves. For risky rewrites I use branch by abstraction and shadow traffic.

**Must know:**
* Feathers: legacy code = code without tests; change point / test point / seams.
* Characterization tests pin *actual* behavior.
* Sprout/Wrap Method to add new code safely.
* Approval/golden master tests for large outputs.
* `mockStatic` as a temporary crutch; PowerMock is obsolete.

**Common follow-ups:**
* What do you do if the characterization test reveals a bug?
* How do you test code that calls `new Date()` everywhere?
* How do you decide what to test first in a 200k-line monolith?

**Red flags:** "rewrite it from scratch"; refactoring without any safety net; mixing behavior changes with refactoring.
