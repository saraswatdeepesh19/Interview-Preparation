# BDD and Cucumber

---

## 🟢 Junior Level

**Behavior-Driven Development (BDD)** is a way of agreeing on *what* the software should do by writing concrete examples in plain language before coding. **Cucumber** is a tool that turns those examples — written in **Gherkin** — into automated tests.

```gherkin
Feature: Free shipping

  Scenario: Orders above the threshold ship for free
    Given a customer in "DE"
    And a cart worth 60.00 EUR
    When the customer checks out
    Then the shipping cost is 0.00 EUR

  Scenario: Orders below the threshold pay standard shipping
    Given a customer in "DE"
    And a cart worth 30.00 EUR
    When the customer checks out
    Then the shipping cost is 4.90 EUR
```

Each line maps to a Java **step definition**:

```java
public class ShippingSteps {
    private Customer customer;
    private Cart cart;
    private Checkout result;

    @Given("a customer in {string}")
    public void customerIn(String country) { customer = new Customer(country); }

    @Given("a cart worth {bigdecimal} EUR")
    public void cartWorth(BigDecimal amount) { cart = Cart.worth(Money.eur(amount)); }

    @When("the customer checks out")
    public void checkout() { result = checkoutService.checkout(customer, cart); }

    @Then("the shipping cost is {bigdecimal} EUR")
    public void shippingCost(BigDecimal expected) {
        assertThat(result.shipping()).isEqualTo(Money.eur(expected));
    }
}
```

### Real-world analogy
Before building a house, the owner and builder walk through scenarios: "when I enter from the garage, I should reach the kitchen without crossing the living room". Those scenarios become checks during construction.

## 🟡 Middle Level

### BDD is about conversations, not the tool
The core practice is the **"three amigos"** session — product owner, developer and tester discuss a story and write examples together (*Example Mapping*: rules, examples, questions). Cucumber only automates the result. Teams that adopt Cucumber without the conversation get expensive, unreadable end-to-end scripts.

### Gherkin features worth knowing

```gherkin
Feature: Discounts
  Background:
    Given the catalog contains:
      | sku | price |
      | A1  | 10.00 |
      | B2  | 25.00 |

  Scenario Outline: Volume discount
    Given a cart with <qty> of "A1"
    When the customer checks out
    Then the discount is <discount> %

    Examples:
      | qty | discount |
      | 1   | 0        |
      | 10  | 5        |
      | 50  | 10       |
```

* `Background` — steps shared by every scenario in the feature.
* `Scenario Outline` + `Examples` — data-driven scenarios.
* Data tables and doc strings for structured inputs; tags (`@smoke`, `@wip`) to filter runs.

### Wiring with JUnit 5 and Spring

```java
@Suite
@IncludeEngines("cucumber")
@SelectClasspathResource("features")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "com.shop.bdd")
@ConfigurationParameter(key = PLUGIN_PROPERTY_NAME, value = "pretty, html:target/cucumber.html")
public class CucumberIT { }

@CucumberContextConfiguration
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
public class CucumberSpringConfig { }
```

Steps classes are instantiated per scenario (scenario-scoped), so share state through injected beans or a `@ScenarioScope` context object — never through static fields.

## 🔴 Senior Level

### Write declarative, not imperative, scenarios

```gherkin
# Imperative (bad): describes UI mechanics, breaks on every UI change
When I click "Add to cart"
And I fill "#qty" with "2"
And I press the button with id "checkout-btn"

# Declarative (good): describes behavior in domain language
When the customer buys 2 units of "A1"
```

Declarative steps survive UI and API redesigns; the step implementation absorbs the mechanics.

### Choose the lowest layer that proves the behavior
A Gherkin scenario does not have to drive a browser. Step definitions can call:
1. **The domain/application layer directly** — milliseconds per scenario, ideal for business rules.
2. **The HTTP API** (RestAssured) — validates contracts and wiring.
3. **The UI** (Playwright/Selenium) — only for a handful of critical journeys.

Many teams run the *same* feature files at different layers by swapping step implementations (the "screenplay"/ports idea), keeping the specification stable while the expensive layer runs nightly.

### Keeping step libraries maintainable
* Cucumber Expressions (`{int}`, `{string}`, custom `@ParameterType` for `Money`, `Sku`) instead of fragile regexes.
* One step-definition class per domain concept, not per feature — avoids duplicated steps (Cucumber fails on ambiguous matches anyway).
* Fail fast on undefined steps in CI: `cucumber.execution.strict` is the default in modern versions; keep it.
* Generate living documentation from feature files and reports; it's only "living" if the scenarios run on every build.

### When BDD/Cucumber is not worth it
* Technical components without business stakeholders (a caching library) — JUnit with good names (`@DisplayName`, `@Nested`) is clearer.
* Teams where nobody outside engineering reads the features — Gherkin then becomes an extra translation layer with no audience.
* Highly combinatorial rules — property-based tests (jqwik) or parameterized tests cover more cases with less text.

## 🎯 Interview Cheat Sheet

**30-second pitch:** BDD is a collaboration practice where the team agrees on behavior through concrete examples; Cucumber automates those examples written in Gherkin by mapping steps to Java code. It pays off when business people actually read the scenarios and when scenarios are declarative and run at the lowest layer that proves the behavior.

**Must know:**
* Given/When/Then, Background, Scenario Outline, data tables, tags.
* Three amigos / example mapping is the real BDD.
* `@Suite` + `@IncludeEngines("cucumber")` with JUnit Platform; `@CucumberContextConfiguration` for Spring.
* Declarative over imperative steps.

**Common follow-ups:**
* BDD vs TDD?
* How do you share state between steps?
* Should Cucumber tests go through the UI?

**Red flags:** Gherkin describing clicks and CSS selectors; hundreds of slow UI scenarios as the main test suite; features nobody outside dev reads.
