# Distributed locks with Redis, SETNX and Redlock

---

## 🟢 Junior Level

A **distributed lock** ensures that only one process across many machines does something at a time — e.g. only one pod runs the nightly invoice job, or only one worker recomputes a cache entry.

### The correct basic Redis lock

```bash
SET lock:invoice-job <random-token> NX PX 30000
```

* `NX` — only set if the key doesn't exist (this is what the old `SETNX` command did, but `SETNX` can't set an expiry atomically).
* `PX 30000` — auto-expire after 30 s, so a crashed holder doesn't block forever.
* `<random-token>` — a unique value identifying the owner.

### Releasing safely
Only the owner may release, and the check + delete must be atomic (Lua):

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

Without the check, a slow process whose lock already expired could delete **someone else's** lock.

```java
String token = UUID.randomUUID().toString();
Boolean ok = redis.opsForValue().setIfAbsent("lock:invoice-job", token, Duration.ofSeconds(30));
if (Boolean.TRUE.equals(ok)) {
    try { runInvoiceJob(); }
    finally {
        redis.execute(RELEASE_SCRIPT, List.of("lock:invoice-job"), token);   // DefaultRedisScript<Long>
    }
}
```

## 🟡 Middle Level

### The lease problem
The lock expires after 30 s, but what if the work takes 45 s — or the JVM pauses for GC, or the network stalls? Another process acquires the lock while the first still thinks it holds it. Options:
* **Watchdog renewal**: a background thread extends the TTL while work is running (Redisson's `RLock` does this every `lockWatchdogTimeout / 3`, default 30 s). If the process dies, renewal stops and the lock expires.
* **Bounded work**: design jobs to finish well within the TTL, and check `stillOwner()` before committing results.

### Redisson

```java
RLock lock = redisson.getLock("lock:invoice-job");
if (lock.tryLock(0, TimeUnit.SECONDS)) {        // wait 0 s; watchdog keeps renewing while held
    try { runInvoiceJob(); }
    finally { lock.unlock(); }
}
```

Redisson also offers fair locks, read-write locks, semaphores and `RLock` via Pub/Sub notifications instead of polling.

### Scheduled jobs: ShedLock
For "run this `@Scheduled` job on one instance only", **ShedLock** is the common choice (with Redis, JDBC, Mongo... providers):

```java
@Scheduled(cron = "0 0 2 * * *")
@SchedulerLock(name = "invoiceJob", lockAtMostFor = "PT30M", lockAtLeastFor = "PT1M")
public void invoiceJob() { ... }
```

`lockAtLeastFor` prevents the job from running twice when clocks differ slightly between nodes.

## 🔴 Senior Level

### Redlock and the controversy
With a single Redis primary and async replication, a lock can be lost on failover: the client acquires the lock on the primary, the primary crashes before replicating, a replica is promoted without the key, and a second client acquires the same lock.

**Redlock** (proposed by Redis' author) uses N independent Redis masters (typically 5): acquire the lock on a majority (≥ 3) within a time much shorter than the TTL; the lock validity is TTL minus elapsed time minus clock drift.

Martin Kleppmann's critique ("How to do distributed locking"): Redlock depends on **timing assumptions** (bounded clock drift, bounded process pauses and network delay). A GC pause or clock jump can still let two clients believe they hold the lock. For **correctness** (not just efficiency), timing-based locks are unsafe without **fencing**.

### Fencing tokens
The lock service issues a monotonically increasing token with each grant; the protected resource rejects writes with a token lower than one it has already seen:

```sql
-- the resource (database) enforces fencing
update invoices_run
set    status = 'DONE', fencing_token = :token
where  run_date = :date and (fencing_token is null or fencing_token < :token);
-- 0 rows updated => a newer lock holder exists; abort
```

Redis can generate tokens with `INCR`, but true safety needs the *resource* to check them. ZooKeeper (zxid / sequential znodes) and etcd (revision numbers, leases) provide this naturally, which is why they're preferred for leader election and correctness-critical locks.

### Choosing the right tool

| Need | Choice |
| --- | --- |
| Efficiency (avoid duplicate work; occasional double execution is harmless) | Single Redis `SET NX PX` + owner-checked release, or ShedLock |
| Correctness (double execution corrupts data or double-charges) | Database constraints / row locks (`SELECT ... FOR UPDATE SKIP LOCKED`), idempotent operations, or etcd/ZooKeeper with fencing |
| Leader election for a long-running process | Kubernetes Lease objects, etcd, ZooKeeper (Curator `LeaderLatch`), Spring Integration `LockRegistryLeaderInitiator` |

Often the best "lock" is no lock: make the operation **idempotent** and protected by a unique constraint, so concurrent executions can't produce duplicates.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A correct Redis lock is `SET key token NX PX ttl` with an owner-checked Lua release, plus renewal or bounded work for long tasks. Redlock acquires a majority across independent masters but still depends on timing assumptions, so for correctness-critical work I add fencing tokens checked by the resource, or use database constraints, etcd or ZooKeeper. For single-instance scheduled jobs I use ShedLock.

**Must know:**
* `SETNX` vs `SET NX PX`; random owner token; Lua compare-and-delete.
* Lease expiry vs GC pauses; watchdog renewal (Redisson).
* Failover can lose locks with async replication.
* Redlock majority + Kleppmann critique.
* Fencing tokens; efficiency vs correctness locks.

**Common follow-ups:**
* What happens if the lock holder crashes?
* Why can't you just `DEL` the key in `finally`?
* How would you elect a leader in Kubernetes?

**Red flags:** `SETNX` + separate `EXPIRE`; locks without TTL; relying on Redis locks for money movement without fencing or idempotency.
