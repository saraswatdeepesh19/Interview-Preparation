# Cache invalidation strategies

---

## 🟢 Junior Level

*"There are only two hard things in computer science: cache invalidation and naming things."* (Phil Karlton)

**Cache invalidation** means making sure the cache doesn't serve data that is wrong (stale) for longer than the business can tolerate. The main strategies:

| Strategy | How it works | Staleness |
| --- | --- | --- |
| **TTL (time-to-live)** | Entries expire after a fixed time | Up to TTL |
| **Explicit eviction on write** | When data changes, delete the cache key | Small race window |
| **Write-through update** | Write the new value to cache and DB together | Small race window |
| **Event-driven invalidation** | Data changes publish events; consumers evict keys | Event propagation delay |
| **Versioned keys** | Key includes a version; new version = new key | None for readers of the new version |

### Spring Cache example

```java
@Service
class ProductService {
    @Cacheable(cacheNames = "products", key = "#id")
    public Product get(long id) { return repo.findById(id).orElseThrow(); }

    @CacheEvict(cacheNames = "products", key = "#product.id")
    @Transactional
    public Product update(Product product) { return repo.save(product); }
}
```

```yaml
spring:
  cache:
    redis:
      time-to-live: 10m          # TTL as a safety net even with explicit eviction
```

## 🟡 Middle Level

### Always have a TTL
Even with explicit eviction, bugs, missed events and race conditions happen. A TTL bounds the damage: wrong data heals itself after at most TTL. Add **jitter** to TTLs (e.g. 10 min ± 10%) so keys written together don't expire together.

### Delete, don't update
On writes, **deleting** the key is usually safer than writing the new value into the cache:

```text
Thread A (writer 1): update DB → v1 ......................... set cache v1
Thread B (writer 2):          update DB → v2 → set cache v2
Result: DB = v2, cache = v1  (stale until TTL)
```

With delete-on-write, the next read repopulates from the database. Remaining race: a reader loads the old value, a writer updates and deletes, then the reader puts the old value back. Mitigations below.

### `@CacheEvict` and transactions
`@CacheEvict` runs when the method returns — *before* the transaction commits if the method is inside a larger transaction. A concurrent reader can repopulate the cache with the old value between eviction and commit. Spring's `TransactionAwareCacheManagerProxy` (or `RedisCacheManager.builder(...).transactionAware()`) defers cache puts/evicts until **after commit**.

### Granularity
* Evicting one key per entity is precise but misses derived caches (lists, search results, aggregates).
* `@CacheEvict(allEntries = true)` is simple but causes miss storms on large caches.
* Prefer caching **entities by ID** and composing lists from IDs (cache the list of IDs with a short TTL, fetch entities from the entity cache).

## 🔴 Senior Level

### Closing the race windows
1. **Delayed double delete** — delete before the DB write, write, then delete again after a short delay (longer than a typical read-repopulate cycle). Cheap and reduces (not eliminates) the stale-read window.
2. **Versioning / compare-and-set** — store a version with the value; only set the cache if the version is newer than what's there (Lua script or `WATCH`/`MULTI`), so a slow reader can't overwrite fresh data with stale data:

```lua
-- KEYS[1] = cache key, ARGV[1] = version, ARGV[2] = payload, ARGV[3] = ttl seconds
local current = redis.call('HGET', KEYS[1], 'v')
if (not current) or (tonumber(ARGV[1]) > tonumber(current)) then
  redis.call('HSET', KEYS[1], 'v', ARGV[1], 'data', ARGV[2])
  redis.call('EXPIRE', KEYS[1], ARGV[3])
  return 1
end
return 0
```

3. **CDC-driven invalidation** — capture database changes (Debezium reading the PostgreSQL WAL) and evict keys from a consumer. The source of truth's commit log drives invalidation, so no application path can "forget" to evict, and it covers changes made by other services, batch jobs or manual SQL. Lag is typically sub-second.

### Multi-level caches
With a local cache (Caffeine) in each pod plus Redis:
* Redis eviction alone leaves stale entries in every pod's local cache.
* Broadcast invalidations (Redis Pub/Sub or Kafka topic `cache-invalidation`) to all pods, and keep local TTLs short (seconds) as a safety net.
* Or use Redis 6 **client-side caching** (`CLIENT TRACKING`) where Redis itself notifies clients of changed keys.

### Choosing staleness by business impact
* Product descriptions: minutes of staleness are fine → TTL + event eviction.
* Prices at checkout: never trust the cache for the final decision → read through to the source (or validate a version) when placing orders.
* Permissions/roles: stale grants are security issues → short TTL (≤ 1 min), explicit eviction on change, and re-check on sensitive operations.
* Inventory: approximate display from cache; authoritative reservation in the database.

### Observability
Track hit ratio per cache, eviction counts, and **staleness** (sample cached values and compare with the database in the background). Alert when the hit ratio drops (invalidation bug or key explosion) or staleness exceeds the business limit.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I combine explicit eviction on writes with a jittered TTL as a safety net, prefer deleting keys over updating them, and make eviction transaction-aware so it happens after commit. To close remaining races I use versioned compare-and-set or CDC-driven invalidation from the database log, broadcast invalidations to local caches, and choose acceptable staleness per data type based on business impact.

**Must know:**
* TTL, evict-on-write, write-through, events, versioned keys.
* Delete vs update and the concurrent-writer race.
* `@CacheEvict` before commit problem; transaction-aware cache manager.
* CDC (Debezium) invalidation.
* Multi-level cache invalidation via Pub/Sub or client tracking.

**Common follow-ups:**
* How can a cache end up stale forever?
* How do you invalidate list/search caches?
* Which data should never be served from cache?

**Red flags:** caches without TTL; `allEntries = true` on every write; relying on the cache for authorization decisions.
