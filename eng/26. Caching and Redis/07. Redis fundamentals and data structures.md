# Redis fundamentals and data structures

---

## 🟢 Junior Level

**Redis** (REmote DIctionary Server) is an open-source, in-memory data store used as a cache, database, message broker and more. Unlike a plain key-value cache, values can be rich **data structures** with server-side operations. Data lives in RAM (hence microsecond-level operations) and can be persisted to disk.

### Simple Real-World Analogy
Think of Redis as a super-fast set of labelled drawers. Each drawer (key) holds not just a sheet of paper but possibly a list, a contact book, a leaderboard — and the clerk can do work inside the drawer (add item, sort, count) without you taking it out.

### Core data structures

| Type | Example commands | Typical use |
|---|---|---|
| **String** | `SET`, `GET`, `INCR`, `SETEX`, `SET NX` | Caching blobs/JSON, counters, locks |
| **Hash** | `HSET`, `HGET`, `HGETALL`, `HINCRBY` | Object fields (user profile), partial updates |
| **List** | `LPUSH`, `RPOP`, `BRPOP`, `LRANGE` | Queues, recent items, timelines |
| **Set** | `SADD`, `SISMEMBER`, `SINTER`, `SUNION` | Unique tags, followers, dedup |
| **Sorted Set** (ZSET) | `ZADD`, `ZRANGE`, `ZRANK`, `ZRANGEBYSCORE` | Leaderboards, delayed queues, sliding windows |
| **Stream** | `XADD`, `XREAD`, `XGROUP`, `XREADGROUP`, `XACK` | Durable event log, consumer groups |
| **Bitmap** | `SETBIT`, `GETBIT`, `BITCOUNT` | Daily active user flags, feature flags |
| **HyperLogLog** | `PFADD`, `PFCOUNT`, `PFMERGE` | Approximate unique counts (~0.81% error, 12 KB) |
| **Geo** | `GEOADD`, `GEOSEARCH` | Nearby search |

### Quick redis-cli session
```
SET page:home:views 0
INCR page:home:views            -> 1
SETEX session:abc 1800 "user-42"   (expires in 30 min)
HSET user:42 name "Alice" age 30
ZADD leaderboard 1500 alice 1200 bob
ZREVRANGE leaderboard 0 2 WITHSCORES
```

### Minimal Java example (Jedis)

```java
import redis.clients.jedis.JedisPooled;

public class RedisHello {
    public static void main(String[] args) {
        try (JedisPooled jedis = new JedisPooled("localhost", 6379)) {
            jedis.set("greeting", "hello");
            jedis.expire("greeting", 60);
            System.out.println(jedis.get("greeting"));   // hello
            System.out.println(jedis.incr("counter"));   // 1, 2, 3 ...
        }
    }
}
```

## 🟡 Middle Level

### Key design and expiration
- Use namespaced keys: `app:env:entity:id` (`shop:prod:user:42`), include version when the format changes.
- Expiry: `EXPIRE`, `SET key v EX 60`, `PEXPIRE`; `TTL`/`PTTL` to inspect (`-1` no expiry, `-2` no key). Overwriting with `SET` **removes** the TTL unless `KEEPTTL` is given.
- Never use `KEYS *` in production (O(N), blocks the server). Use `SCAN` with `MATCH`/`COUNT` (cursor-based, non-blocking, may return duplicates).

### Choosing the right structure

**Strings vs Hash for objects:** a JSON string is simple and atomic to read as one unit, but updating a single field rewrites the whole value. A hash allows `HSET user:42 email x` and `HINCRBY` on single fields, and small hashes use a compact encoding (`listpack`) saving memory. Spring's `Jackson2JsonRedisSerializer` with strings is the pragmatic default.

**Sorted set leaderboard** (O(log N) per update/rank):
```java
import redis.clients.jedis.JedisPooled;
import redis.clients.jedis.resps.Tuple;
import java.util.List;

public class Leaderboard {
    private final JedisPooled jedis = new JedisPooled("localhost", 6379);

    public void addScore(String player, double delta) {
        jedis.zincrby("lb:2026-10", delta, player);
    }

    public List<Tuple> top(int n) {
        return jedis.zrevrangeWithScores("lb:2026-10", 0, n - 1);
    }

    public Long rank(String player) {
        return jedis.zrevrank("lb:2026-10", player); // 0-based, null if absent
    }
}
```

**Bitmaps** for daily activity: `SETBIT active:2026-10-14 <userId> 1`, count with `BITCOUNT`, intersect days with `BITOP AND` — 100M users ≈ 12.5 MB per day.
**HyperLogLog** for unique visitors: `PFADD uv:page1 userId` → `PFCOUNT` returns ~±0.81% accuracy with fixed 12 KB regardless of cardinality. It stores no members — you can't list or remove them.
**Streams** are an append-only log with IDs (`1697270000000-0`), consumer groups, pending entries list (PEL) for at-least-once processing, `XAUTOCLAIM` for stuck consumers, and `MAXLEN ~ 1000000` trimming. They are lighter than Kafka but don't offer the same partitioned scale/retention tooling.

```java
import redis.clients.jedis.JedisPooled;
import redis.clients.jedis.StreamEntryID;
import redis.clients.jedis.params.XAddParams;
import java.util.Map;

public class StreamProducer {
    public static void main(String[] args) {
        JedisPooled jedis = new JedisPooled("localhost", 6379);
        StreamEntryID id = jedis.xadd("orders", XAddParams.xAddParams().maxLen(100_000).approximateTrimming(),
                Map.of("orderId", "1001", "status", "CREATED"));
        System.out.println("added " + id);
    }
}
```

### Pub/Sub vs Streams
Pub/sub: no persistence, at-most-once delivery, offline subscribers lose messages. Streams: persisted, replayable, consumer groups, acknowledgments.

### Transactions and scripting
`MULTI`/`EXEC` queue commands and run them atomically (no isolation violations from other clients, but no rollback on command errors). `WATCH` gives optimistic locking (CAS). **Lua scripts** (`EVAL`) execute atomically and are the standard tool for read-modify-write logic (rate limiter, safe lock release). Redis 7 adds **Functions**.

### Common mistakes
- Using one huge key (big hash/list with millions of elements) — slow `DEL`, replication lag; use `UNLINK` and sharding of keys.
- Storing `Serializable` Java blobs (class version brittle, JDK serialization security risk).
- No expiry on cache keys → memory growth.
- Treating Redis as durable without configuring persistence.
- Using `HGETALL`/`SMEMBERS`/`LRANGE 0 -1` on large collections (O(N) block).

## 🔴 Senior Level

### Internal encodings
Redis picks compact encodings automatically and converts when thresholds are exceeded (check with `OBJECT ENCODING key`):
- String: `int` (integers up to 64-bit), `embstr` (≤44 bytes, one allocation), `raw`.
- Hash/ZSet/List: `listpack` (contiguous, small; Redis ≥7, replaced `ziplist`) up to `hash-max-listpack-entries 128` / value ≤64 bytes; beyond → `hashtable` / `skiplist`+`dict` / `quicklist` (linked list of listpacks).
- Set: `intset` for small integer-only sets, `listpack` (7.2), else `hashtable`.
- ZSet: skip list + hash table → `ZADD` O(log N), `ZSCORE` O(1).
Memory implication: 1 million small hashes (user objects, ≤128 fields) cost far less than 1 million JSON strings thanks to listpack, and a classic trick is **bucketing**: `HSET bucket:{id/100} id value` to store many tiny key-values compactly.

### Complexity awareness
`GET/SET/HGET/ZSCORE` O(1); `ZADD/ZRANK` O(log N); `LRANGE` O(S+N); `SMEMBERS/HGETALL/KEYS/SUNION` O(N); `SORT` can be O(N log N). A single O(N) command on 1M elements takes tens of ms and blocks every other client because of the single-threaded executor — check `SLOWLOG GET 10` and `LATENCY HISTORY`.

### Atomic patterns with Lua (Spring)

```java
import java.util.List;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;

public class AtomicCounterLimiter {
    private static final DefaultRedisScript<Long> SCRIPT = new DefaultRedisScript<>("""
            local current = redis.call('INCR', KEYS[1])
            if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
            return current
            """, Long.class);

    private final StringRedisTemplate redis;

    public AtomicCounterLimiter(StringRedisTemplate redis) { this.redis = redis; }

    public long hit(String key, int windowSeconds) {
        return redis.execute(SCRIPT, List.of(key), String.valueOf(windowSeconds));
    }
}
```
Without the script, `INCR` then `EXPIRE` as two commands can leave a key without TTL if the client dies between them.

### Hash tags and multi-key operations
In Cluster, multi-key commands (`MGET`, `SUNION`, Lua with several keys, `MULTI`) require all keys in the same hash slot. Force co-location with hash tags: `{user:42}:profile`, `{user:42}:cart` — only the part inside braces is hashed. Overusing one tag creates hot shards.

### Memory diagnostics
- `INFO memory`, `MEMORY USAGE key SAMPLES 0`, `MEMORY DOCTOR`, `redis-cli --bigkeys` / `--memkeys`.
- Key overhead ≈ 50–70 bytes plus allocator rounding (jemalloc size classes): 40-byte values may consume 48 or 64 bytes.
- Use `OBJECT FREQ` (LFU) or `OBJECT IDLETIME` to understand access.
- Use `UNLINK` (async free) instead of `DEL` for large keys; enable lazy-free configs.

### Choosing Redis vs alternatives
Memcached: simpler, multithreaded, strings only, no persistence/replication. Redis: structures, scripting, persistence, replication, cluster. Dragonfly/Valkey/KeyDB: Redis-protocol-compatible forks/alternatives; Redis 7.4+ licensing changed (RSALv2/SSPL, AGPL option from 8.0) and Valkey (Linux Foundation) is a BSD fork — worth knowing for enterprise choices; the client API is the same.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Redis is an in-memory data structure server: strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geo. It is fast because data is in RAM and commands are simple O(1)/O(log N) operations executed atomically by a single thread. Use it for caching, counters, leaderboards, queues, sessions, locks and rate limiting; mind big keys, O(N) commands and persistence settings.

**Must know:**
- Each data type with a real use case and complexity.
- TTL behavior, `SCAN` vs `KEYS`, `UNLINK` vs `DEL`.
- HyperLogLog accuracy (~0.81%) and fixed 12 KB.
- Streams with consumer groups vs Pub/Sub.
- Lua / `MULTI` / `WATCH` for atomicity; hash tags in Cluster.

**Follow-up questions:**
- How would you build a leaderboard / unique-visitor counter / daily-active-users metric?
- Hash vs JSON string for objects?
- Why is `KEYS *` dangerous?
- Are Redis transactions ACID?

**Red flags:** `KEYS` in production; no TTLs; JDK serialization; thinking Redis is multi-threaded for command execution; using `HGETALL` on huge hashes.
