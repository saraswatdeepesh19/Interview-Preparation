# Hot keys and big keys

---

## 🟢 Junior Level

* A **hot key** is a single key that receives a disproportionate share of traffic — e.g. the homepage config, a celebrity's profile, a flash-sale product's stock counter.
* A **big key** is a key whose value is very large — a 50 MB string, a hash with 2 million fields, a list with 10 million elements.

Both hurt because **Redis executes commands on a single main thread**, and in Redis Cluster **one key lives on one shard**:

* A hot key concentrates load on one shard (and one CPU core), no matter how many shards you have.
* A big key makes individual commands slow (reading 2 million hash fields blocks Redis for everyone), uses lots of network bandwidth, and makes deletion, migration and replication painful.

### Finding them

```bash
redis-cli --hotkeys          # requires maxmemory-policy *-lfu (LFU counters)
redis-cli --bigkeys          # samples keys, reports the largest per type
redis-cli --memkeys          # sizes in bytes (Redis 6+)
redis-cli MEMORY USAGE product:42
redis-cli --latency-history  # spikes often correlate with big-key operations
```

Rules of thumb: strings under ~10 KB, collections under ~5,000–10,000 elements are comfortable.

## 🟡 Middle Level

### Handling hot keys
1. **Local near-cache** in the application (Caffeine with a few seconds TTL). 1,000 pods each serving the key from memory remove almost all Redis traffic for it.
2. **Read replicas** — `ReadFrom.REPLICA_PREFERRED` spreads reads (eventual consistency).
3. **Key splitting / replication across shards** — store copies `homepage:{0}` … `homepage:{9}` (different hash slots) and read a random copy; writes update all copies.
4. **Counters**: instead of one `INCR stock:sku-1` hammered by everyone, shard the counter into N sub-counters (`stock:sku-1:3`) and sum on read, or batch increments in the app.

```java
// Read a random replica of a hot key; each copy lands on a different slot/shard
String key = "homepage:v42:" + ThreadLocalRandom.current().nextInt(10);
Homepage h = localCache.get(key, k -> redisJson.get(k, Homepage.class));
```

### Handling big keys
* **Split** large collections into buckets: `user:42:followers:{0..63}` by hash of member, or time-bucketed keys for timelines (`timeline:42:2026-10`).
* **Don't fetch everything**: replace `HGETALL`/`SMEMBERS`/`LRANGE 0 -1` with `HSCAN`/`SSCAN`/paged `LRANGE`.
* **Compress** large strings (and avoid storing huge JSON documents at all if you only need a few fields — use hashes).
* **Delete safely**: `DEL` on a 2 GB key blocks Redis; use **`UNLINK`** (frees memory in a background thread) and enable `lazyfree-lazy-eviction`, `lazyfree-lazy-expire`, `lazyfree-lazy-server-del`.

## 🔴 Senior Level

### Why big keys are operationally dangerous
* **Latency spikes** for all clients during O(N) commands — Redis is single-threaded for command execution.
* **Cluster resharding/migration** moves keys atomically per key; migrating a huge key blocks both source and target and can trigger failover timeouts.
* **Replication and persistence**: a big write inflates the replication backlog and AOF; RDB forks copy-on-write pages, so heavy writes to big keys during `BGSAVE` inflate memory.
* **Eviction**: evicting one huge key frees a lot at once, but finding candidates and freeing memory synchronously stalls the server (unless lazy free is on).
* **Network**: a 10 MB response to 100 clients per second saturates a 1 Gbit NIC.

### Detecting in production without hurting it
* `--bigkeys`/`--memkeys` use `SCAN` and are reasonably safe, but run them on a **replica**.
* Offline analysis of RDB snapshots (`redis-rdb-tools`, `rdb-cli`) gives exact sizes without touching production.
* Slow log (`SLOWLOG GET 128`) with `slowlog-log-slower-than 10000` (10 ms) shows which commands on which keys are slow.
* Managed services (ElastiCache, Memorystore) expose per-shard CPU and network metrics — one shard much hotter than others is the hot-key signature. Redis 7 also has `CLUSTER` per-slot stats in some distributions; client-side metrics per key prefix help identify the source.

### Hot keys in Redis Cluster and hash tags
Hash tags `{...}` force related keys into the same slot (needed for multi-key commands and Lua scripts). Overusing them — `{tenant42}:*` for a huge tenant — creates **hot slots**. Use hash tags only for keys that must be accessed atomically together.

### Architectural fixes
* Push hot read-only data to the **edge** (CDN) or into application memory with push-based invalidation.
* For hot write counters (likes, views), aggregate in a stream (Kafka) or in-app buffers and flush periodically; store the exact value elsewhere.
* For "top N" leaderboards with millions of members, keep the sorted set but read only ranges (`ZREVRANGE 0 99`), and partition by region/time if write volume is extreme.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Hot keys concentrate traffic on one shard and core; big keys make single commands slow, blocking single-threaded Redis, and complicate replication, migration and eviction. I find them with `--hotkeys`, `--bigkeys`, slow log and RDB analysis on replicas; fix hot keys with near-caches, replicas, or key copies across slots; and fix big keys by splitting into buckets, using SCAN-style iteration, compressing, and deleting with UNLINK and lazy-free settings.

**Must know:**
* One key = one slot = one shard; single-threaded execution.
* `--hotkeys` needs LFU policy; `--bigkeys`, `MEMORY USAGE`, `SLOWLOG`.
* Near-cache, read replicas, key replication, sharded counters.
* `UNLINK` and `lazyfree-*` settings.
* Hash tags can create hot slots.

**Common follow-ups:**
* A flash sale overloads one Redis shard — what do you do?
* How do you delete a 5 GB key in production?
* Why is `HGETALL` dangerous?

**Red flags:** `KEYS *` in production; storing entire user histories in one list; `DEL` on huge keys.
