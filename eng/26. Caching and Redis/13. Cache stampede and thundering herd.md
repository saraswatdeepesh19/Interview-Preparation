# Cache stampede and thundering herd

---

## 🟢 Junior Level

A **cache stampede** (also *dog-piling*) happens when a popular cached value **expires** and many requests **miss at the same moment**. All of them go to the database to recompute the same value, overloading it — sometimes enough to take it down, which keeps the cache empty and makes things worse.

A **thundering herd** is the broader version: many clients wake up or retry simultaneously (after a restart, a failover, or a cache flush) and hit a backend at once.

```text
t = 10:00:00.000  key "homepage" expires
t = 10:00:00.001  3,000 concurrent requests miss → 3,000 identical DB queries
t = 10:00:02      DB CPU 100%, queries time out, nothing gets cached → repeat
```

### Simplest mitigations
* **Jittered TTLs** so keys don't expire together.
* **Request coalescing**: only one request recomputes; the others wait for its result.
* **Never let hot keys expire under load**: refresh them in the background before expiry.

## 🟡 Middle Level

### Coalescing in one JVM
Spring's `@Cacheable(sync = true)` makes concurrent callers for the same key wait while one computes:

```java
@Cacheable(cacheNames = "homepage", key = "#locale", sync = true)
public Homepage homepage(Locale locale) { return builder.build(locale); }   // runs once per key per JVM
```

Caffeine does the same natively — `cache.get(key, loader)` computes once per key:

```java
LoadingCache<String, Homepage> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofMinutes(5))
        .refreshAfterWrite(Duration.ofMinutes(4))     // refresh-ahead: serve old value while reloading async
        .maximumSize(10_000)
        .build(builder::build);
```

With `refreshAfterWrite`, readers keep getting the old value while **one** background reload runs — no stampede at expiry.

### Across many pods: distributed locking

```java
Homepage homepage(String locale) {
    String key = "homepage:" + locale;
    Homepage cached = redis.get(key);
    if (cached != null) return cached;

    String lockKey = key + ":lock";
    Boolean acquired = redisTemplate.opsForValue().setIfAbsent(lockKey, instanceId, Duration.ofSeconds(10));
    if (Boolean.TRUE.equals(acquired)) {
        try {
            Homepage fresh = builder.build(locale);
            redis.set(key, fresh, jitter(Duration.ofMinutes(5)));
            return fresh;
        } finally {
            releaseIfOwner(lockKey, instanceId);          // Lua: delete only if value == instanceId
        }
    }
    // didn't get the lock: wait briefly for the winner, then fall back
    return pollForValue(key, Duration.ofMillis(500)).orElseGet(() -> staleOrDefault(locale));
}
```

## 🔴 Senior Level

### Probabilistic early expiration (XFetch)
Instead of a lock, each reader may decide to recompute **slightly before** expiry with a probability that increases as expiry approaches (Vattani et al., "Optimal Probabilistic Cache Stampede Prevention"):

```java
// stored with the value: delta = how long recomputation took; expiry = absolute expiry time
boolean shouldRecompute(long nowMillis, long expiryMillis, long deltaMillis, double beta) {
    double r = ThreadLocalRandom.current().nextDouble();          // (0,1)
    return nowMillis - deltaMillis * beta * Math.log(r) >= expiryMillis;   // log(r) < 0
}
```

With `beta = 1`, typically one request recomputes shortly before expiry, no coordination needed, and expensive values (large `delta`) refresh earlier. It works across pods without locks.

### Serve stale while revalidating
Store values with a *soft* TTL (refresh after) and a *hard* TTL (delete after). Readers past the soft TTL trigger a single async refresh and get the stale value immediately. This mirrors HTTP `Cache-Control: stale-while-revalidate` and CDN behavior, and also gives resilience: if the database is down, stale data keeps serving (`stale-if-error`).

### Thundering herds beyond caches
* **Cold start after flush/restart** — warm caches before taking traffic (readiness gated on warm-up of the top-N keys), or ramp traffic gradually.
* **Synchronized clients** — cron jobs at `00:00`, mobile apps syncing on the hour, retries without jitter. Add jitter to schedules and backoff.
* **Failover reconnect storms** — thousands of clients reconnecting to a new Redis primary or database at once; connection backoff with jitter on the client side, and connection limits on the server.
* **Lock release herds** — waiters polling a lock in tight loops; use pub/sub notification or exponential backoff.

### Protecting the source as the last line
Even with all of the above, put a **bulkhead/concurrency limit** in front of the expensive recomputation (e.g. at most 10 concurrent homepage builds per pod), and load-shed beyond it. Monitor cache miss rate per key class and DB query rate for the recomputation query — a spike in both at the same time is the stampede signature.

## 🎯 Interview Cheat Sheet

**30-second pitch:** A cache stampede happens when a hot key expires and many concurrent misses recompute it at once, overloading the database. I prevent it with jittered TTLs, request coalescing (`@Cacheable(sync = true)`, Caffeine loaders), refresh-ahead or stale-while-revalidate so hot keys never really expire under load, distributed locks or probabilistic early expiration across pods, and a concurrency limit on the expensive recomputation.

**Must know:**
* Stampede vs thundering herd.
* `sync = true`, Caffeine `refreshAfterWrite`.
* Lock with `SET NX PX` + owner-checked release.
* XFetch probabilistic early recomputation.
* Soft/hard TTL, stale-while-revalidate, warm-up after restarts.

**Common follow-ups:**
* Does `@Cacheable(sync = true)` work across pods?
* What if the lock holder crashes?
* How do you warm a cache after a deploy?

**Red flags:** same fixed TTL for millions of keys; flushing the whole cache in production at peak; retry loops without jitter.
