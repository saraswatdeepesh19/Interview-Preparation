# Lettuce vs Jedis

---

## 🟢 Junior Level

**Lettuce** and **Jedis** are the two main Java clients for Redis.

| | Lettuce | Jedis |
| --- | --- | --- |
| I/O model | Non-blocking, built on **Netty** | Blocking sockets |
| Thread safety | One connection can be **shared** by many threads | A connection is **not** thread-safe — use a pool (`JedisPool`) |
| APIs | Sync, async (`RedisFuture`), reactive (`Mono`/`Flux`) | Sync (plus pipelining/transactions) |
| Spring Boot default | **Yes** (`spring-boot-starter-data-redis`) | Optional (exclude Lettuce, add Jedis) |
| Cluster/Sentinel | Yes, with topology refresh | Yes |

```java
// Spring Data Redis abstracts the client; the same code works with both
@Autowired StringRedisTemplate redis;

redis.opsForValue().set("session:42", "ada", Duration.ofMinutes(30));
String user = redis.opsForValue().get("session:42");
```

### Short answer for interviews
Use **Lettuce** (the default) unless you have a specific reason: it shares connections efficiently, supports reactive code, and handles Redis Cluster topology changes. Jedis is simpler and fine for straightforward blocking workloads with a well-sized pool.

## 🟡 Middle Level

### Connection model differences
* **Lettuce** multiplexes commands from many threads over **one TCP connection** per Redis node. Commands are pipelined on the connection and responses are matched in order. Because Redis executes commands one at a time per connection anyway, this works very well for short commands.
* **Jedis** gives each thread its own connection from a pool. Pool size limits concurrency; exhausting the pool blocks threads (`JedisExhaustedPoolException` after `maxWait`).

### When a single Lettuce connection is not enough
Blocking or long-running commands block the **shared** connection for everyone:
* `BLPOP`, `BRPOP`, `XREAD BLOCK` (blocking reads),
* `MULTI`/`EXEC` transactions,
* `SUBSCRIBE` (Pub/Sub uses dedicated connections),
* large `KEYS`/`SMEMBERS`/`HGETALL` responses that take time to transfer.

For these, enable pooling (`commons-pool2` on the classpath + `spring.data.redis.lettuce.pool.enabled=true`) or use dedicated connections. Spring Data Redis already uses separate connections for transactions and Pub/Sub listeners.

### Configuration

```yaml
spring:
  data:
    redis:
      host: redis
      timeout: 500ms                    # command timeout
      connect-timeout: 1s
      lettuce:
        pool:
          enabled: true                 # only needed for blocking ops/transactions
          max-active: 16
        cluster:
          refresh:
            adaptive: true              # refresh topology on MOVED/ASK/reconnects
            period: 30s
```

## 🔴 Senior Level

### Throughput and latency characteristics
* With Lettuce, many threads issuing small commands get **automatic pipelining** over one connection; throughput is high and connection count stays low (important when hundreds of pods talk to one Redis — Redis `maxclients` defaults to 10,000 and each connection costs memory).
* With Jedis, explicit **pipelining** (`Pipeline p = jedis.pipelined(); ... p.sync()`) is needed for batch throughput; without it, every command is a round trip.
* For bulk operations in either client, use pipelining or multi-key commands (`MGET`, `MSET`, Lua scripts) — one round trip for N keys instead of N round trips (at 0.3 ms RTT, 10,000 sequential GETs cost 3 seconds).

### Failure behavior
* **Command timeouts**: Lettuce's default command timeout is 60 s; Spring Boot exposes `spring.data.redis.timeout` — set it (hundreds of ms) or a slow Redis stalls request threads for a minute.
* **Reconnects**: Lettuce auto-reconnects and, by default, buffers commands while disconnected (`ClientOptions.disconnectedBehavior`). For caches, prefer `REJECT_COMMANDS` so callers fail fast and fall back to the database instead of piling up queued commands.
* **Cluster topology**: without adaptive refresh, a failover leaves clients sending to the old master until `MOVED` redirections accumulate. Enable adaptive refresh triggers (`MOVED_REDIRECT`, `PERSISTENT_RECONNECTS`) plus periodic refresh.
* **Read from replicas**: Lettuce `ReadFrom.REPLICA_PREFERRED` offloads reads at the cost of stale reads (replication is async).

```java
@Bean
LettuceClientConfigurationBuilderCustomizer lettuceCustomizer() {
    return b -> b.readFrom(ReadFrom.REPLICA_PREFERRED)
                 .clientOptions(ClusterClientOptions.builder()
                         .disconnectedBehavior(ClientOptions.DisconnectedBehavior.REJECT_COMMANDS)
                         .topologyRefreshOptions(ClusterTopologyRefreshOptions.builder()
                                 .enableAllAdaptiveRefreshTriggers()
                                 .enablePeriodicRefresh(Duration.ofSeconds(30))
                                 .build())
                         .build());
}
```

### Alternatives and extras
* **Redisson** — higher-level client with distributed objects (locks, semaphores, rate limiters, maps with local caching), built on Netty. Useful when you need those primitives, heavier otherwise.
* **Client-side caching** (Redis 6 RESP3 `CLIENT TRACKING`): Lettuce and Redisson support server-assisted invalidation of a local near-cache — big latency wins for hot read-mostly keys.
* Observability: both clients integrate with Micrometer (Lettuce `MicrometerCommandLatencyRecorder`, Spring Boot auto-config) — watch command latency percentiles and connection counts.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Lettuce is a Netty-based, non-blocking, thread-safe Redis client that multiplexes many threads over one connection and offers sync, async and reactive APIs — it's Spring Boot's default. Jedis is a simpler blocking client that needs a connection pool because connections aren't thread-safe. I use Lettuce, add pooling only for blocking commands or transactions, and always configure command timeouts, disconnected behavior and cluster topology refresh.

**Must know:**
* Shared connection (Lettuce) vs pooled connections (Jedis).
* Blocking commands, transactions and Pub/Sub need dedicated connections.
* Pipelining / multi-key commands for bulk throughput.
* Set `spring.data.redis.timeout`; Lettuce default is 60 s.
* Adaptive topology refresh for Redis Cluster.

**Common follow-ups:**
* Why might Lettuce be slow for `BLPOP`?
* How many connections does each client open?
* What happens during a Redis failover?

**Red flags:** sharing a Jedis connection across threads; no command timeout; 10,000 sequential GETs in a loop.
