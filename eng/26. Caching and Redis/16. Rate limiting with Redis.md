# Rate limiting with Redis

---

## 🟢 Junior Level

When an application runs on many instances, each instance only sees part of the traffic. To enforce a **global** limit ("100 requests per minute per API key"), all instances need **shared, fast, atomic** counters — which is exactly what Redis provides.

### Fixed window counter (simplest)

```bash
INCR rate:apikey-123:202610161205      # key per client per minute
EXPIRE rate:apikey-123:202610161205 60
```

```java
boolean allow(String clientId, int limit) {
    String key = "rate:" + clientId + ":" + (System.currentTimeMillis() / 60_000);
    Long count = redis.opsForValue().increment(key);
    if (count != null && count == 1) redis.expire(key, Duration.ofSeconds(60));
    return count != null && count <= limit;
}
```

Problem 1: `INCR` and `EXPIRE` are two commands; if the process dies between them, the key never expires. Problem 2: fixed windows allow bursts at boundaries (100 requests at 12:05:59 and 100 more at 12:06:00).

## 🟡 Middle Level

### Atomic scripts
Run the whole algorithm inside Redis with a Lua script — scripts execute atomically:

```lua
-- Fixed window, atomic. KEYS[1]=key, ARGV[1]=limit, ARGV[2]=window seconds
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return {0, redis.call('TTL', KEYS[1])}      -- rejected, seconds until reset
end
return {1, tonumber(ARGV[1]) - current}        -- allowed, remaining
```

### Sliding window log with a sorted set
Exact limits over a rolling window:

```lua
-- KEYS[1]=key, ARGV[1]=now ms, ARGV[2]=window ms, ARGV[3]=limit, ARGV[4]=unique request id
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1
end
return 0
```

Accurate, but memory grows with requests per window (one entry per request) — fine for low limits (login attempts), costly for 10,000 req/min per key.

### Token bucket in Lua (bursts + steady rate)

```lua
-- KEYS[1]=bucket hash, ARGV: 1=capacity, 2=refill tokens per second, 3=now ms, 4=requested
local cap, rate, now, req = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = tokens >= req
if allowed then tokens = tokens - req end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return allowed and 1 or 0
```

O(1) memory per client; Spring Cloud Gateway's `RedisRateLimiter` and Bucket4j's Redis backend implement this idea.

## 🔴 Senior Level

### Time source
Using the application's clock (`ARGV now`) means skew between pods affects limits. Alternatives: use Redis server time inside the script (`redis.call('TIME')`) — allowed in Redis 5+ with effect replication (default in Redis 7), which makes all instances agree.

### Redis Cluster considerations
* A script may only touch keys in **one hash slot**; put per-client keys under a hash tag if you need several keys per decision (`{apikey-123}:tokens`, `{apikey-123}:ts`).
* Very hot clients (one huge tenant) become hot keys on one shard — shard their bucket (`{apikey-123:3}`) and divide the limit, or limit them locally first.

### Performance and failure modes
* Every request now has a Redis round trip (~0.2–1 ms in the same AZ). Use connection multiplexing (Lettuce), pipelining where possible, and keep scripts short (they block the Redis thread).
* Use `EVALSHA` (Spring's `DefaultRedisScript` does this automatically) to avoid sending script bodies each time.
* **Redis unavailable**: decide fail-open (allow, protect with a local in-memory limiter as fallback) or fail-closed (reject). Public APIs usually fail open with a conservative local limit; security-sensitive limits (login attempts, OTP verification) fail closed.
* **Two-tier limiting**: local token buckets per pod for burst absorption + Redis for global quotas, syncing periodically. Cuts Redis load dramatically at the cost of slight overshoot.

### Response semantics
Return `429 Too Many Requests` with `Retry-After` and the IETF `RateLimit`/`RateLimit-Policy` headers so well-behaved clients can back off precisely. Log and meter rejections per client and per limit to spot abuse and tune limits.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Distributed rate limiting needs a shared atomic counter, so I implement the algorithm as a Lua script in Redis: fixed window for simplicity, sliding-window log for exact low limits, or token bucket for O(1) memory with controlled bursts. I use Redis server time, keep keys in one slot, decide fail-open vs fail-closed explicitly, and return 429 with Retry-After and RateLimit headers.

**Must know:**
* INCR + EXPIRE race → Lua script.
* Fixed window boundary bursts; sliding log via sorted sets; token bucket via hash.
* `redis.call('TIME')` for consistent time.
* Cluster: single slot per script; hot client sharding.
* Fail-open vs fail-closed; local + global two-tier limiting.

**Common follow-ups:**
* How do you rate-limit 50 pods to 1,000 req/s total?
* Sliding window log vs token bucket memory?
* What happens if Redis goes down?

**Red flags:** read-modify-write in Java without atomicity; per-pod limits presented as global; no Retry-After.
