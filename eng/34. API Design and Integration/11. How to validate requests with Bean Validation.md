# How to validate requests with Bean Validation

---

## 🟢 Junior Level

**Jakarta Bean Validation** (formerly JSR 380; Hibernate Validator is the reference implementation) declares validation rules as annotations on fields and parameters. Spring validates `@Valid` request bodies automatically and returns **400 Bad Request** with details.

```java
public record CreateCustomerRequest(
        @NotBlank @Size(max = 100) String name,
        @NotBlank @Email String email,
        @NotNull @Past LocalDate birthDate,
        @Pattern(regexp = "^[A-Z]{2}$") String country,
        @Valid @NotNull AddressRequest address) {}            // @Valid cascades into nested objects

public record AddressRequest(@NotBlank String street, @NotBlank String city, @NotBlank String zip) {}

@RestController
@RequestMapping("/api/customers")
class CustomerController {
    @PostMapping
    ResponseEntity<CustomerResponse> create(@Valid @RequestBody CreateCustomerRequest req) { ... }
}
```

### Common constraints
`@NotNull`, `@NotBlank` (strings: not null and not only whitespace), `@NotEmpty` (collections/strings), `@Size`, `@Min`/`@Max`, `@Positive`/`@PositiveOrZero`, `@DecimalMin`, `@Digits`, `@Email`, `@Pattern`, `@Past`/`@Future`, `@AssertTrue`.

Requires `spring-boot-starter-validation` on the classpath.

## 🟡 Middle Level

### Validating path variables and request parameters
Annotate the controller (or rely on Spring 6.1+ built-in method validation for controllers):

```java
@RestController
@Validated                                            // enables method-level validation (needed before Spring 6.1)
class ProductController {
    @GetMapping("/api/products")
    Page<ProductDto> search(@RequestParam @Size(min = 2, max = 50) String q,
                            @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) { ... }
}
```

In Spring 6.1+, violations on parameters raise `HandlerMethodValidationException` (400) rather than `ConstraintViolationException` (500 unless handled) — map both to Problem Details.

### Collections and container elements

```java
public record CreateOrderRequest(
        @NotEmpty @Size(max = 100) List<@Valid @NotNull LineRequest> lines,
        Map<@NotBlank String, @Size(max = 200) String> attributes) {}
```

### Validation groups (same DTO, different rules)

```java
public interface OnCreate {}
public interface OnUpdate {}

public record ProductRequest(
        @Null(groups = OnCreate.class) @NotNull(groups = OnUpdate.class) Long id,
        @NotBlank(groups = {OnCreate.class, OnUpdate.class}) String name) {}

@PostMapping  ResponseEntity<?> create(@Validated(OnCreate.class) @RequestBody ProductRequest r) { ... }
@PutMapping("/{id}") ResponseEntity<?> update(@Validated(OnUpdate.class) @RequestBody ProductRequest r) { ... }
```

Groups get complicated quickly; separate DTOs per operation are often clearer.

## 🔴 Senior Level

### Custom constraints

```java
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = DateRangeValidator.class)
public @interface ValidDateRange {
    String message() default "start must be before end";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, BookingRequest> {
    @Override
    public boolean isValid(BookingRequest r, ConstraintValidatorContext ctx) {
        if (r.start() == null || r.end() == null) return true;          // let @NotNull handle nulls
        if (r.start().isBefore(r.end())) return true;
        ctx.disableDefaultConstraintViolation();
        ctx.buildConstraintViolationWithTemplate("{booking.range.invalid}")
           .addPropertyNode("end").addConstraintViolation();            // attach error to the "end" field
        return false;
    }
}

@ValidDateRange
public record BookingRequest(@NotNull Instant start, @NotNull Instant end) {}
```

Validators are Spring beans when created by Spring's `LocalValidatorFactoryBean`, so they can inject dependencies — but avoid database lookups in validators on hot paths (and remember they run before your transaction).

### Where validation belongs
* **Syntactic/format validation** (required, length, ranges, formats) at the API boundary with Bean Validation → fast 400s with field-level errors.
* **Business rules** ("SKU must exist", "credit limit not exceeded", "booking slot available") in the application/domain layer, inside the transaction, returning domain-specific problems (409/422). They depend on state and can't be expressed as static annotations reliably.
* **Database constraints** (NOT NULL, UNIQUE, CHECK, FKs) as the final safety net — they're the only guarantee under concurrency (two requests passing the "email unused" check simultaneously; the unique index decides).

### Security and robustness aspects
* Always bound sizes (`@Size(max)` on strings and collections) — unbounded inputs enable memory exhaustion; also set server limits (`server.tomcat.max-swallow-size`, `spring.servlet.multipart.max-file-size`, Jackson `StreamReadConstraints` for maximum string length/nesting depth).
* Regex `@Pattern` with catastrophic backtracking (`(a+)+$`) is a ReDoS risk — keep patterns simple and anchored.
* Normalize before validating (trim, Unicode normalization) if business logic compares strings.
* Don't echo invalid input verbatim in error messages without encoding (XSS in clients rendering errors).

### Messages and i18n
Message templates (`{booking.range.invalid}`) resolve via `ValidationMessages.properties` or Spring's `MessageSource` (configure `LocalValidatorFactoryBean.setValidationMessageSource`) — enabling localized messages while clients still rely on stable field names and error codes.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I validate request syntax at the API boundary with Jakarta Bean Validation — `@Valid` on bodies with cascading to nested objects and container elements, method validation for parameters — and return 400 Problem Details with field errors. Cross-field rules use custom class-level constraints, business rules live in the domain inside the transaction, and database constraints are the final guarantee under concurrency. I bound every input size and avoid ReDoS-prone patterns.

**Must know:**
* Core annotations; `@NotBlank` vs `@NotEmpty` vs `@NotNull`.
* `@Valid` cascading; `List<@Valid T>` container constraints.
* `@Validated` method validation; Spring 6.1 `HandlerMethodValidationException`.
* Groups vs separate DTOs; custom `ConstraintValidator` with property nodes.
* Layering: boundary vs domain vs database constraints.

**Common follow-ups:**
* How do you validate that `start < end`?
* Why can't you rely on a "unique email" validator?
* How do you return validation errors in a standard format?

**Red flags:** database queries in validators everywhere; no max sizes; validation only in the frontend.
