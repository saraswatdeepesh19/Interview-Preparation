# How to implement optimistic concurrency with ETag and If-Match

---

## 🟢 Junior Level

**The lost update problem over HTTP:** Alice and Bob both `GET /products/42` (price 10). Alice sets the price to 12 and saves; Bob, still looking at the old data, sets the description and saves the whole resource with price 10 — Alice's change is silently lost.

**Optimistic concurrency** prevents this without locks:
1. The server returns a version identifier — an **ETag** header — with the resource.
2. The client sends it back in **`If-Match`** when updating.
3. The server applies the update only if the current version still matches; otherwise it returns **412 Precondition Failed**.

```http
GET /api/products/42
→ 200 OK
  ETag: "7"
  {"id":42,"name":"Keyboard","price":10.00}

PUT /api/products/42
If-Match: "7"
{"id":42,"name":"Keyboard","price":12.00}
→ 200 OK   ETag: "8"

PUT /api/products/42            (Bob, still holding version 7)
If-Match: "7"
→ 412 Precondition Failed
```

Bob's client must reload, show the conflict, and let the user merge or retry.

## 🟡 Middle Level

### Implementation with JPA `@Version`

```java
@Entity
class Product {
    @Id Long id;
    String name;
    BigDecimal price;
    @Version long version;          // incremented by Hibernate on every update
}

@RestController
@RequestMapping("/api/products")
class ProductController {

    @GetMapping("/{id}")
    ResponseEntity<ProductDto> get(@PathVariable long id) {
        Product p = service.get(id);
        return ResponseEntity.ok().eTag(Long.toString(p.getVersion())).body(ProductDto.from(p));
    }

    @PutMapping("/{id}")
    ResponseEntity<ProductDto> update(@PathVariable long id,
                                      @RequestHeader(HttpHeaders.IF_MATCH) String ifMatch,
                                      @Valid @RequestBody ProductDto body) {
        long expected = parseVersion(ifMatch);                        // strips quotes; 400 if malformed
        Product updated = service.update(id, expected, body);         // throws VersionMismatch -> 412
        return ResponseEntity.ok().eTag(Long.toString(updated.getVersion())).body(ProductDto.from(updated));
    }
}

@Transactional
public Product update(long id, long expectedVersion, ProductDto dto) {
    Product p = repo.findById(id).orElseThrow(() -> new ProductNotFound(id));
    if (p.getVersion() != expectedVersion) throw new VersionMismatchException(id, expectedVersion, p.getVersion());
    p.apply(dto);
    return p;                                  // flush issues: update ... set version=version+1 where id=? and version=?
}
```

Two layers of protection: the explicit check returns a clean 412 for stale clients; Hibernate's `where version = ?` guards against a concurrent update between the read and the flush (raising `OptimisticLockException` → also map to 412).

### Requiring preconditions
To force clients to use concurrency control, reject updates without `If-Match` with **428 Precondition Required** (RFC 6585).

### Strong vs weak ETags
* Strong `"7"` — byte-for-byte identical representation; required for `If-Match`.
* Weak `W/"7"` — semantically equivalent; fine for caching with `If-None-Match`, not valid for `If-Match` comparisons.

## 🔴 Senior Level

### Designing ETag values
* **Version number** (from `@Version`) — cheap, exact, ideal for single-entity resources.
* **Hash of the representation** — works for computed or aggregated resources; Spring's `ShallowEtagHeaderFilter` hashes the response body for caching, but that saves only bandwidth (the server still does the work) and can't support `If-Match` safely for writes.
* **Composite versions** — for an aggregate (order + lines), use the aggregate root's version, and make every modification of a line bump the root's version (`@Version` on root + `OPTIMISTIC_FORCE_INCREMENT` lock when lines change).
* Don't leak sensitive information in ETags; treat them as opaque strings on the client.

### Caching with the same mechanism
`If-None-Match` + `304 Not Modified` lets clients and CDNs revalidate cheaply:

```java
@GetMapping("/{id}")
ResponseEntity<ProductDto> get(@PathVariable long id, WebRequest request) {
    long version = service.currentVersion(id);                       // cheap query: select version ...
    if (request.checkNotModified(Long.toString(version))) return null;  // Spring writes 304
    Product p = service.get(id);
    return ResponseEntity.ok().eTag(Long.toString(version)).body(ProductDto.from(p));
}
```

### PATCH and conflicts
JSON Merge Patch / JSON Patch updates still need `If-Match` when they read-modify-write fields that others might change. For high-contention fields (stock counters), prefer **commutative operations** (`POST /stock/42/reservations`) or server-side atomic updates rather than client-side read-modify-write with retries.

### Beyond HTTP
The same pattern appears everywhere: DynamoDB conditional writes on a version attribute, Elasticsearch `if_seq_no`/`if_primary_term`, Kubernetes `resourceVersion`, S3 conditional writes (`If-Match`/`If-None-Match` on PUT). Recognizing it lets you design consistent concurrency semantics across your stack.

## 🎯 Interview Cheat Sheet

**30-second pitch:** To prevent lost updates over HTTP I return an ETag — usually the entity's `@Version` — with every representation and require `If-Match` on updates; if the version changed, the server returns 412 Precondition Failed, and missing preconditions get 428. Hibernate's versioned update protects the read-to-write window, `If-None-Match` with 304 gives cheap caching, and high-contention fields are better handled with commutative server-side operations.

**Must know:**
* ETag / If-Match / 412; If-None-Match / 304; 428.
* Strong vs weak ETags.
* JPA `@Version` and `OptimisticLockException` mapping.
* Aggregate versioning (force increment).
* Same pattern in DynamoDB, Kubernetes, Elasticsearch, S3.

**Common follow-ups:**
* What does the client do after a 412?
* Can `ShallowEtagHeaderFilter` be used for concurrency control?
* How do you version an aggregate with child entities?

**Red flags:** last-write-wins PUTs on shared resources; ETags generated from timestamps with second precision; ignoring `OptimisticLockException` (500s).
