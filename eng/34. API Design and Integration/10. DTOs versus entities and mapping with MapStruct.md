# DTOs versus entities and mapping with MapStruct

---

## 🟢 Junior Level

* An **entity** represents persisted domain data (a JPA `@Entity` mapped to a table), with relationships, lazy loading and invariants.
* A **DTO (Data Transfer Object)** represents what crosses a boundary — an API request/response, a message payload — shaped for that consumer.

### Why not return entities directly from controllers?
* **Leaking internals** — every column (password hashes, internal flags) becomes part of the public API; renaming a column breaks clients.
* **Lazy loading during serialization** — Jackson touches a lazy collection outside the transaction → `LazyInitializationException`, or (with open-in-view) silent N+1 queries.
* **Infinite recursion** with bidirectional relationships (`Order.customer.orders.customer...`).
* **Mass assignment** — binding request JSON straight into an entity lets clients set fields they shouldn't (`role`, `price`).
* **Coupling** — API shape and database schema can't evolve independently.

```java
// Request and response DTOs as records
public record CreateOrderRequest(@NotNull Long customerId, @NotEmpty List<@Valid LineRequest> lines) {}
public record LineRequest(@NotBlank String sku, @Positive int qty) {}
public record OrderResponse(Long id, String status, BigDecimal total, List<LineResponse> lines) {}
public record LineResponse(String sku, int qty, BigDecimal price) {}
```

## 🟡 Middle Level

### MapStruct: compile-time mapping

```java
@Mapper(componentModel = MappingConstants.ComponentModel.SPRING,
        unmappedTargetPolicy = ReportingPolicy.ERROR)          // fail the build if a target field isn't mapped
public interface OrderMapper {

    @Mapping(target = "status", source = "status")              // enum -> String by name
    @Mapping(target = "total", expression = "java(order.total().amount())")
    OrderResponse toResponse(Order order);

    LineResponse toResponse(OrderLine line);                    // used automatically for List<OrderLine>

    @Mapping(target = "id", ignore = true)
    @Mapping(target = "status", constant = "DRAFT")
    @Mapping(target = "version", ignore = true)
    Order toEntity(CreateOrderRequest request);
}
```

MapStruct generates plain Java code at compile time (an `OrderMapperImpl` class) — no reflection, fast, debuggable, and type errors show up as compile errors. `unmappedTargetPolicy = ERROR` turns "forgot to map a new field" into a build failure.

### Alternatives
* **Hand-written mapping** (static factory `OrderResponse.from(order)`) — explicit, zero dependencies; great for few, simple DTOs.
* **ModelMapper / Dozer** — reflection-based, convention-driven: less code but slower, with surprises (wrong matches, silent nulls) found at run time.
* **JPA projections** — `select new OrderSummary(o.id, o.status, o.total) from Order o` or interface-based projections in Spring Data: skip entities entirely for read APIs (no dirty checking, fewer columns, no lazy loading).

## 🔴 Senior Level

### Read side vs write side
* **Reads**: map directly from queries to DTOs (projections, jOOQ records, `@Query` constructor expressions) — avoids loading entity graphs only to discard most fields; this is the cheapest performance win in many Spring apps.
* **Writes**: map request DTOs to **commands**, not entities: `CreateOrderCommand` → application service → domain methods enforce invariants. Never let a mapper set arbitrary entity fields from client input (it bypasses domain rules like "price comes from the catalog, not the client").

```java
@PostMapping("/orders")
ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest req) {
    Order order = orderService.place(new PlaceOrderCommand(req.customerId(),
            req.lines().stream().map(l -> new PlaceOrderCommand.Line(l.sku(), l.qty())).toList()));
    return ResponseEntity.created(URI.create("/orders/" + order.id())).body(mapper.toResponse(order));
}
```

### Updating entities from DTOs
`@MappingTarget` updates an existing entity in place (PATCH-like semantics), but be careful:

```java
@BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
void update(UpdateProductRequest req, @MappingTarget Product product);
```

* Null handling must be explicit: "field absent" vs "set to null" can't be distinguished with plain records — use `JsonNullable<T>` (openapi-jackson-databind-nullable) or JSON Merge Patch semantics when it matters.
* Collections: mapping replaces lists, which with JPA `orphanRemoval` can delete and re-insert children — map collection updates deliberately (merge by ID).
* Prefer domain methods (`product.reprice(newPrice, clock)`) over setter-based mapping for fields with rules.

### Avoiding mapping sprawl
* One DTO per use case where shapes differ (list vs detail), but avoid near-duplicate DTOs for every endpoint.
* Keep mappers in the API/adapter layer; the domain doesn't know DTOs.
* Test mappers with round-trip and "all fields mapped" tests (MapStruct's policies already cover most), and run ArchUnit rules so controllers don't return entities (`noClasses().that().areAnnotatedWith(RestController.class).should().dependOnClassesThat().areAnnotatedWith(Entity.class)` for return types).

## 🎯 Interview Cheat Sheet

**30-second pitch:** Entities model persistence and domain invariants; DTOs model what crosses a boundary. Returning entities leaks internals, triggers lazy-loading and recursion problems, and enables mass assignment. I use record DTOs, map with MapStruct — compile-time generated, no reflection, with an unmapped-target policy of ERROR — use projections for read endpoints, and map write requests to commands handled by domain methods rather than copying fields onto entities.

**Must know:**
* Problems with exposing entities.
* MapStruct basics: `@Mapper(componentModel = SPRING)`, `@Mapping`, `@MappingTarget`, null strategies.
* Reflection mappers vs MapStruct vs manual.
* JPA/Spring Data projections for reads.
* Commands for writes; PATCH null semantics.

**Common follow-ups:**
* How do you handle PATCH with partial fields?
* Why is ModelMapper risky?
* How do you prevent clients from setting the price?

**Red flags:** `@JsonIgnore` sprinkled on entities as the API strategy; `BeanUtils.copyProperties(request, entity)`; one giant DTO for every use case.
