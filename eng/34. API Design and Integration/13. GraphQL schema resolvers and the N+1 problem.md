# GraphQL schema resolvers and the N+1 problem

---

## 🟢 Junior Level

**GraphQL** is a query language for APIs: the server publishes a **typed schema**, and clients send queries asking for **exactly the fields they need** in one request, usually to a single endpoint (`POST /graphql`).

```graphql
type Query {
  order(id: ID!): Order
  orders(customerId: ID!, first: Int = 20, after: String): OrderConnection!
}

type Order {
  id: ID!
  status: OrderStatus!
  total: Money!
  customer: Customer!
  lines: [OrderLine!]!
}

type Customer { id: ID!  name: String!  email: String }
type OrderLine { sku: String!  qty: Int!  product: Product! }
enum OrderStatus { PENDING PAID SHIPPED CANCELLED }
```

```graphql
# Client query: one round trip, only the fields the screen needs
query {
  order(id: "42") {
    status
    total { amount currency }
    customer { name }
    lines { qty product { name } }
  }
}
```

### Resolvers
Each field is backed by a **resolver** — a function that fetches its value. Spring for GraphQL maps them with annotations:

```java
@Controller
class OrderGraphqlController {
    @QueryMapping
    Order order(@Argument String id) { return orders.get(id); }

    @SchemaMapping(typeName = "Order", field = "customer")
    Customer customer(Order order) { return customers.get(order.customerId()); }   // called once PER order!
}
```

## 🟡 Middle Level

### The N+1 problem
Query 50 orders with their customers: 1 resolver call for the list + **50** calls to `customer(order)` → 51 database queries or HTTP calls. Deeper nesting multiplies it (orders → lines → products).

### The fix: batching with DataLoader
Collect all keys requested in the same execution step and load them in **one** call:

```java
@Controller
class OrderGraphqlController {

    @BatchMapping(typeName = "Order", field = "customer")
    Map<Order, Customer> customer(List<Order> orders) {                 // called ONCE for all orders in the response
        Set<String> ids = orders.stream().map(Order::customerId).collect(Collectors.toSet());
        Map<String, Customer> byId = customers.findAllById(ids).stream()
                .collect(Collectors.toMap(Customer::id, c -> c));
        return orders.stream().collect(Collectors.toMap(o -> o, o -> byId.get(o.customerId())));
    }
}
```

`@BatchMapping` registers a `DataLoader` under the hood: field resolutions are queued, keys deduplicated, and dispatched as one batch per level — 51 queries become 2. DataLoaders also **cache per request**, so the same customer appearing in many orders is loaded once.

### Pagination
Use **cursor-based connections** (Relay spec): `orders(first: 20, after: "cursor")` returning `edges { cursor node }` and `pageInfo { hasNextPage endCursor }` — stable under inserts, efficient with keyset queries.

## 🔴 Senior Level

### Protecting the server
Clients choose the query shape, so they can also ask for something enormous:

```graphql
{ customers(first: 1000) { orders(first: 1000) { lines { product { reviews(first: 1000) { author { orders { ... } } } } } } } }
```

Defenses:
* **Max depth** and **max complexity/cost** analysis (assign costs per field, multiply by list sizes; reject above a budget) — graphql-java `MaxQueryDepthInstrumentation`, `MaxQueryComplexityInstrumentation`.
* **Pagination limits** on every list field (`first <= 100`).
* **Persisted queries / trusted documents**: in production, only allow pre-registered query hashes from your own clients (also improves caching and payload size).
* **Timeouts** and per-client **rate limits based on cost**, not request count.
* Disable **introspection** for public production endpoints if you don't want the schema browsable (it doesn't replace authorization).

### Authorization per field
A single endpoint means URL-based security rules don't apply. Authorize in resolvers / domain services (`@PreAuthorize` on service methods, field-level checks for sensitive fields like `email`), and ensure batch loaders apply the same filters (a DataLoader must not return objects the caller isn't allowed to see).

### Errors and partial results
GraphQL responses can contain both `data` and `errors` (HTTP 200 for partial success). Clients must handle partial data; servers should classify errors (`extensions.classification`: `NOT_FOUND`, `FORBIDDEN`, `BAD_REQUEST`) consistently — Spring for GraphQL's `DataFetcherExceptionResolverAdapter` maps exceptions.

### When to choose GraphQL
* **Good fit**: many client types with different data needs (web, mobile, partners), aggregating several backend services into one graph (BFF or **federation** — Apollo Federation, Netflix DGS), rapidly evolving UIs.
* **Weak fit**: simple CRUD with one client, heavy HTTP caching needs (GET + CDN caching is natural for REST; GraphQL needs persisted queries + GET for similar caching), file uploads/streaming, public APIs where predictable cost and simple tooling matter.
* Operationally: schema registry and breaking-change checks (deprecate fields with `@deprecated(reason:)`, never remove without usage data), field-level usage metrics, and tracing per resolver.

## 🎯 Interview Cheat Sheet

**30-second pitch:** GraphQL exposes a typed schema where clients request exactly the fields they need, resolved field by field. Naive per-object resolvers cause N+1 calls, which DataLoader batching — `@BatchMapping` in Spring for GraphQL — solves by collecting keys per level, loading them in one call and caching per request. In production I add depth and cost limits, pagination caps, persisted queries, field-level authorization and consistent partial-error handling, and use GraphQL where varied clients or service aggregation justify it.

**Must know:**
* Schema, queries, resolvers; `@QueryMapping`, `@SchemaMapping`, `@BatchMapping`.
* N+1 mechanics and DataLoader batching/caching.
* Cursor connections for pagination.
* Depth/complexity limits, persisted queries, introspection.
* Partial results; field-level authorization; federation.

**Common follow-ups:**
* How do you cache GraphQL responses?
* How do you prevent expensive queries?
* GraphQL vs REST for a mobile app?

**Red flags:** per-object resolvers hitting the DB in loops; unlimited list sizes; relying on gateway URL rules for authorization.
