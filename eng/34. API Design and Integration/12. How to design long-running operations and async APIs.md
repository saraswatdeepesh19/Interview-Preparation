# How to design long-running operations and async APIs

---

## 🟢 Junior Level

Some operations take too long for a normal HTTP request: generating a report, importing a 2 GB CSV, video transcoding, provisioning infrastructure, bulk refunds. Holding the connection open for minutes fails because of client/proxy timeouts (API gateways often cap at ~30 s), wastes server threads, and loses everything if the instance restarts.

### The asynchronous request-reply pattern

```http
POST /api/reports
{"type": "sales", "from": "2026-01-01", "to": "2026-09-30"}

HTTP/1.1 202 Accepted
Location: /api/operations/op_7f3a
Retry-After: 5
{"id": "op_7f3a", "status": "PENDING"}
```

```http
GET /api/operations/op_7f3a
→ 200 OK  {"id":"op_7f3a","status":"RUNNING","progress":0.42}

GET /api/operations/op_7f3a
→ 200 OK  {"id":"op_7f3a","status":"SUCCEEDED",
           "result":{"href":"/api/reports/rep_91"}}       (or 303 See Other -> /api/reports/rep_91)
```

1. **Accept** the request quickly, persist an operation record, enqueue the work → `202 Accepted` + status URL.
2. **Process** asynchronously in workers.
3. **Report** status via polling, webhooks/callbacks, or push (SSE/WebSocket).

## 🟡 Middle Level

### Implementation sketch (Spring)

```java
@PostMapping("/api/reports")
ResponseEntity<OperationDto> start(@Valid @RequestBody ReportRequest req,
                                   @RequestHeader("Idempotency-Key") String key) {
    Operation op = operations.createOrGet(key, "report", req);          // idempotent: same key -> same operation
    if (op.isNew()) outbox.add(new GenerateReport(op.id(), req));        // same transaction as the operation row
    return ResponseEntity.accepted()
            .location(URI.create("/api/operations/" + op.id()))
            .header(HttpHeaders.RETRY_AFTER, "5")
            .body(OperationDto.from(op));
}

@GetMapping("/api/operations/{id}")
ResponseEntity<OperationDto> status(@PathVariable String id) {
    Operation op = operations.get(id);
    return ResponseEntity.ok().cacheControl(CacheControl.noStore()).body(OperationDto.from(op));
}

// Worker (Kafka/SQS/RabbitMQ consumer)
@KafkaListener(topics = "report-jobs")
void run(GenerateReport job) {
    operations.markRunning(job.operationId());
    try {
        ReportId rep = reports.generate(job.request(), progress -> operations.progress(job.operationId(), progress));
        operations.succeed(job.operationId(), rep);
    } catch (Exception e) {
        operations.fail(job.operationId(), Problem.from(e));
    }
}
```

### Operation resource design
* **States**: `PENDING → RUNNING → SUCCEEDED | FAILED | CANCELLED` (optionally `CANCELLING`).
* **Fields**: `id`, `status`, `createdAt`, `updatedAt`, `progress`, `result` (link or inline), `error` (Problem Details), `expiresAt`.
* **Cancellation**: `POST /api/operations/{id}:cancel` or `DELETE /api/operations/{id}` — best effort; workers check a cancellation flag between chunks.
* **Retention**: keep operation records for a defined time (e.g. 7 days), then purge.

Google's AIP-151 "Long-running operations" and Azure's REST guidelines describe the same pattern; consistency across your APIs matters more than the exact naming.

## 🔴 Senior Level

### Notification options

| Mechanism | Pros | Cons |
| --- | --- | --- |
| Polling with `Retry-After` | Simple, firewall-friendly, stateless | Latency vs request volume trade-off |
| Webhooks (callback URL) | Immediate, no polling | Client must expose an endpoint; retries, signatures (HMAC), replay protection, SSRF risk when calling client-provided URLs |
| SSE / WebSocket | Real-time UI updates | Connection management, scaling sticky connections |
| Event (Kafka/SNS) | Internal service-to-service | Not for external clients |

For webhooks: sign payloads (`X-Signature: sha256=...` with a shared secret and timestamp), retry with exponential backoff for hours, deduplicate with an event ID, and let consumers verify and fetch the latest state rather than trusting the payload blindly.

### Robustness
* **Idempotent creation** — `Idempotency-Key` (or a client-chosen operation ID) so retries of the POST don't start duplicate jobs.
* **Durable handoff** — create the operation record and enqueue the job atomically (transactional outbox), otherwise a crash leaves `PENDING` forever.
* **Worker crashes** — jobs must be resumable or restartable; use checkpoints for long imports (process in chunks, persist progress), visibility timeouts/leases so another worker picks up abandoned jobs, and a sweeper that fails or retries operations stuck in `RUNNING` past a deadline.
* **Backpressure and quotas** — limit concurrent operations per tenant; return `429` with `Retry-After` when the queue is full.
* **Large inputs/outputs** — upload inputs to object storage with a presigned URL first, pass the object key; return results as presigned download links.

### Workflow engines
When operations have multiple steps, compensations, human approvals or long waits, use a workflow engine (Temporal, Camunda, AWS Step Functions) behind the operation API: the operation ID maps to a workflow execution; status comes from the workflow state. It provides durable timers, retries and history — far more robust than hand-rolled state machines in database rows.

## 🎯 Interview Cheat Sheet

**30-second pitch:** For long-running work I return `202 Accepted` with a `Location` to an operation resource and `Retry-After`, persist the operation and enqueue the job atomically, process it in workers, and expose status, progress, results and Problem Details errors on the operation resource. Clients poll, receive signed webhooks, or get SSE updates; creation is idempotent, jobs are resumable with checkpoints and stuck-job sweepers, and multi-step processes run on a workflow engine.

**Must know:**
* 202 + Location + Retry-After; 303 to the result.
* Operation states, cancellation, retention.
* Outbox for atomic enqueue; idempotency keys.
* Polling vs webhooks vs SSE; webhook signing and retries.
* Checkpointing, leases, sweepers; Temporal/Step Functions.

**Common follow-ups:**
* What if the worker crashes halfway through an import?
* How would clients get notified without polling?
* How do you cancel a running operation?

**Red flags:** 60-second synchronous requests; in-memory job maps; webhooks without signatures or retries.
