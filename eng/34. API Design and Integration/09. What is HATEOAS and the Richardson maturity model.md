# What is HATEOAS and the Richardson maturity model

---

## 🟢 Junior Level

The **Richardson Maturity Model** (Leonard Richardson, popularized by Martin Fowler) describes how "RESTful" an HTTP API is, in four levels:

| Level | Name | Characteristics | Example |
| --- | --- | --- | --- |
| 0 | The swamp of POX | One endpoint, one method, actions in the body (RPC over HTTP) | `POST /api` `{"action":"getOrder","id":42}` |
| 1 | Resources | Separate URIs per resource, but verbs ignored | `POST /orders/42/get` |
| 2 | HTTP verbs | Proper methods and status codes | `GET /orders/42` → 200, `POST /orders` → 201 + `Location` |
| 3 | Hypermedia controls (**HATEOAS**) | Responses contain links telling the client what it can do next | `_links: { cancel: ..., pay: ... }` |

**HATEOAS** — *Hypermedia As The Engine Of Application State* — means clients discover available actions and related resources from links in responses instead of hardcoding URLs and business rules.

```json
{
  "id": 42,
  "status": "PENDING_PAYMENT",
  "total": 49.90,
  "_links": {
    "self":     { "href": "https://api.shop.com/orders/42" },
    "pay":      { "href": "https://api.shop.com/orders/42/payment" },
    "cancel":   { "href": "https://api.shop.com/orders/42/cancellation" },
    "customer": { "href": "https://api.shop.com/customers/7" }
  }
}
```

When the order is shipped, the server simply omits `pay` and `cancel` — the client shows only the buttons for links that exist.

## 🟡 Middle Level

### Spring HATEOAS

```java
@GetMapping("/orders/{id}")
EntityModel<OrderDto> get(@PathVariable long id) {
    Order order = service.get(id);
    EntityModel<OrderDto> model = EntityModel.of(OrderDto.from(order),
            linkTo(methodOn(OrderController.class).get(id)).withSelfRel(),
            linkTo(methodOn(CustomerController.class).get(order.customerId())).withRel("customer"));

    if (order.canBePaid())      model.add(linkTo(methodOn(PaymentController.class).pay(id, null)).withRel("pay"));
    if (order.canBeCancelled()) model.add(linkTo(methodOn(OrderController.class).cancel(id)).withRel("cancel"));
    return model;
}
```

Responses are rendered as **HAL** (`application/hal+json`) by default; other media types include HAL-FORMS (adds templates describing required inputs), Siren, JSON:API and Collection+JSON.

### Benefits in practice
* **Business rules stay on the server** — "can this order be cancelled?" is decided once, not reimplemented in every client.
* **URL changes are less breaking** — clients follow links rather than constructing URLs (still need stable entry points).
* **Discoverability** — pagination (`next`, `prev`), related resources and actions are self-describing.

### Why most APIs stop at level 2
* Most clients (SPAs, mobile apps) are built against a specific API with generated SDKs from OpenAPI; they don't navigate dynamically.
* Link generation adds payload size and server effort; tooling for hypermedia-driven clients is limited.
* Teams get most value from level 2 (resources, verbs, status codes, caching) plus good documentation.

## 🔴 Senior Level

### Where HATEOAS genuinely pays off
* **Workflow/state-machine resources** (orders, claims, approvals): exposing allowed transitions as links (`approve`, `reject`, `request-changes`) keeps UI logic simple and consistent with server rules.
* **Long-lived public APIs** with many clients evolving at different speeds — links decouple clients from URL structure and let the server introduce new paths gradually.
* **Pagination and collection navigation** — RFC 8288 `Link` headers (`<...?cursor=abc>; rel="next"`) are a lightweight, widely understood form of hypermedia even in level-2 APIs.

### Pragmatic middle ground
* Include `self` and pagination links; include **action links** only for state-dependent operations.
* Use **link relations** with documented semantics (IANA registered ones like `self`, `next`, `edit`, or custom ones namespaced as URIs/CURIEs).
* Keep URLs **absolute** (or consistently relative to a base) and generate them behind proxies correctly (`ForwardedHeaderFilter` / `server.forward-headers-strategy=framework` so links use the external host and scheme).
* Combine with OpenAPI: describe the link relations and their target operations so generated clients still work.

### Common misconceptions
* "REST" ≠ "JSON over HTTP": Fielding's REST constraints include hypermedia; most "REST APIs" are level 2 HTTP APIs, and that's fine — but say so precisely in interviews.
* HATEOAS doesn't eliminate API versioning or documentation; clients still need to understand media types and relations.
* Links don't replace authorization — the server must still enforce rules when a client calls an action URL directly.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The Richardson model ranks HTTP APIs from level 0 (RPC over one endpoint) through resources (1) and proper verbs and status codes (2) to hypermedia controls (3). HATEOAS means responses include links to related resources and currently allowed actions, so state-dependent rules live on the server and clients follow links instead of hardcoding URLs. Spring HATEOAS produces HAL; in practice most APIs are level 2 with pagination links, and full HATEOAS pays off for workflow resources and long-lived public APIs.

**Must know:**
* Four levels with examples.
* HAL `_links`; HAL-FORMS; RFC 8288 `Link` header.
* Spring HATEOAS `EntityModel`, `linkTo(methodOn(...))`.
* Why level 2 is common; where level 3 helps.
* Forwarded headers for correct links behind proxies.

**Common follow-ups:**
* Is your API RESTful?
* How would a client know whether an order can be cancelled?
* Does HATEOAS remove the need for versioning?

**Red flags:** calling RPC-style `POST /doSomething` APIs RESTful; generating links with internal hostnames.
