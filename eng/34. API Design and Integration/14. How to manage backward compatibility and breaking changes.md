# How to manage backward compatibility and breaking changes

---

## 🟢 Junior Level

An API change is **backward compatible** if existing clients keep working without changes. A **breaking change** forces clients to change — and since you rarely control when (or whether) clients upgrade, breaking changes are expensive.

### Usually safe (additive)
* Adding a new endpoint or a new optional request parameter/field.
* Adding a field to a response (clients must ignore unknown fields — the *tolerant reader* principle).
* Adding a new enum value **only if** clients were told to handle unknown values.
* Relaxing validation (accepting more input).

### Breaking
* Removing or renaming an endpoint, field, or parameter.
* Changing a field's type or format (`"price": "12.50"` → `12.5`, date formats, ID type).
* Making an optional field required; tightening validation.
* Changing semantics (units, default values, sorting, error codes, pagination behavior).
* Changing authentication or required headers.

```java
// Server side: never fail on unknown input fields either (tolerant reader on both sides)
spring.jackson.deserialization.fail-on-unknown-properties=false   // Spring Boot default is already false
```

---

## 🟡 Middle Level

### Strategies for evolving without breaking
1. **Expand, then contract**: add the new field alongside the old one, migrate clients, then remove the old one after usage drops to zero.

```json
{ "price": "12.50", "priceAmount": { "value": 12.50, "currency": "EUR" } }
```

2. **Deprecate visibly**: mark in OpenAPI (`deprecated: true`), and in responses with the `Deprecation` and `Sunset` headers (RFC 8594 for Sunset; the `Deprecation` header is standardized in RFC 9745), plus a `Link` to migration docs:

```http
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT
Link: <https://developer.shop.com/migrations/price-v2>; rel="deprecation"
```

3. **Version when you must**: new major version for unavoidable breaking changes (URI `/v2/...`, media type `application/vnd.shop.v2+json`, or header-based), running both versions in parallel for a published period.
4. **Feature negotiation**: let clients opt into new behavior (`Prefer: return=minimal`, a query param or header) instead of forcing it.

### Detect breaking changes automatically
Compare the OpenAPI spec of the PR against `main` in CI:

```bash
# openapi-diff / oasdiff: fail the build on breaking changes
oasdiff breaking openapi-main.yaml openapi-pr.yaml --fail-on ERR
```

Combine with consumer-driven contract tests (Pact) for known consumers.

## 🔴 Senior Level

### Hidden breaking changes (the ones that slip through review)
* **Enum additions** to clients with exhaustive `switch` or strict deserialization (`READ_UNKNOWN_ENUM_VALUES_AS_DEFAULT` not enabled) — document "new values may appear" from day one and provide an `UNKNOWN` fallback in SDKs.
* **Ordering**: results that were implicitly sorted by ID and now aren't.
* **Nullability**: a field that was always present becomes null in some cases.
* **Error behavior**: switching from 404 to 403 for hidden resources, or changing problem `type` URIs.
* **Performance/limits**: lowering page size maxima or rate limits.
* **Number precision**: JavaScript clients lose precision on 64-bit integers > 2^53 — serialize large IDs as strings from the beginning.
* **Event schemas**: the same rules apply to messages, with stricter compatibility needs because old messages persist (schema registry compatibility checks).

### Running multiple versions
* Implement versions as **adapters** over one core: `v1` and `v2` controllers map to the same application services, with translation at the edge. Avoid forking business logic per version.
* Measure usage per version and per client (API keys, user agents, `X-Client-Version`), reach out to remaining users before sunset, and consider **brownouts** (temporarily failing deprecated endpoints for short windows) to surface forgotten integrations before the final shutdown.

### Governance
* An **API style guide** (naming, pagination, errors, versioning policy, deprecation periods — e.g. at least 6–12 months for public APIs).
* **API review** for changes to public contracts, ideally automated with linting (Spectral rules) and diff checks.
* **Changelog** per API, published to consumers; SDKs regenerated and released with versioning that mirrors API compatibility (semver).

## 🎯 Interview Cheat Sheet

**30-second pitch:** I evolve APIs additively — new optional fields and endpoints, tolerant readers on both sides — use expand/contract for renames and format changes, deprecate visibly with OpenAPI flags and Deprecation/Sunset headers, and only introduce a new major version for unavoidable breaks, running versions in parallel as thin adapters over one core. CI detects breaking changes with OpenAPI diffs and contract tests, and usage metrics drive sunsetting.

**Must know:**
* Additive vs breaking changes lists.
* Tolerant reader; unknown enum handling.
* Expand/contract for fields.
* Deprecation, Sunset, Link headers; brownouts.
* oasdiff/openapi-diff, Pact, Spectral; version adapters.

**Common follow-ups:**
* Is adding an enum value breaking?
* How long do you support an old version?
* How do you find out who still uses a deprecated endpoint?

**Red flags:** silent semantic changes; versioning every minor change; forking business logic per version.
