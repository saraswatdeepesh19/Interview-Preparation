# How to handle errors with Problem Details RFC 9457

---

## 🟢 Junior Level

**RFC 9457** ("Problem Details for HTTP APIs", which obsoletes RFC 7807) defines a standard JSON format for API errors, served with the media type `application/problem+json`:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.shop.com/problems/insufficient-stock",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Only 2 units of SKU A1 are available, 5 were requested.",
  "instance": "/api/orders/requests/8f2c",
  "sku": "A1",
  "available": 2
}
```

| Member | Meaning |
| --- | --- |
| `type` | URI identifying the problem type (stable, documentable; `about:blank` if none) |
| `title` | Short, human-readable summary of the type (same for every occurrence) |
| `status` | HTTP status code (repeated for convenience) |
| `detail` | Explanation specific to this occurrence |
| `instance` | URI identifying this occurrence |
| extensions | Any additional members (`sku`, `available`, `errors`) |

Clients branch on `type` (machine-readable) and show `detail` to humans — instead of parsing error strings.

### Spring Boot support
Spring Framework 6 has `ProblemDetail` and `ErrorResponse` built in; enable standard handling with:

```yaml
spring:
  mvc:
    problemdetails:
      enabled: true           # framework exceptions (validation, 404, 405, 415...) become problem+json
```

## 🟡 Middle Level

### Mapping domain exceptions centrally

```java
@RestControllerAdvice
class ApiExceptionHandler extends ResponseEntityExceptionHandler {   // handles Spring MVC exceptions as ProblemDetail

    @ExceptionHandler(InsufficientStockException.class)
    ProblemDetail insufficientStock(InsufficientStockException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "Only %d units of SKU %s are available, %d were requested."
                        .formatted(e.available(), e.sku(), e.requested()));
        pd.setType(URI.create("https://api.shop.com/problems/insufficient-stock"));
        pd.setTitle("Insufficient stock");
        pd.setProperty("sku", e.sku());
        pd.setProperty("available", e.available());
        return pd;
    }

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "Order " + e.id() + " does not exist.");
        pd.setType(URI.create("https://api.shop.com/problems/order-not-found"));
        return pd;
    }
}
```

Or make domain exceptions implement `ErrorResponse` / extend `ErrorResponseException` so they carry their own problem details.

### Validation errors

```java
@Override
protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex, HttpHeaders headers,
                                                              HttpStatusCode status, WebRequest request) {
    ProblemDetail pd = ex.getBody();                                    // already 400 with title/detail
    pd.setType(URI.create("https://api.shop.com/problems/validation-error"));
    pd.setProperty("errors", ex.getFieldErrors().stream()
            .map(fe -> Map.of("field", fe.getField(), "message", Objects.requireNonNullElse(fe.getDefaultMessage(), "invalid")))
            .toList());
    return ResponseEntity.status(status).headers(headers).body(pd);
}
```

```json
{ "type": "https://api.shop.com/problems/validation-error", "title": "Bad Request", "status": 400,
  "detail": "Invalid request content.",
  "errors": [ { "field": "lines[0].qty", "message": "must be greater than 0" } ] }
```

## 🔴 Senior Level

### Designing an error catalog
* Each `type` URI is a **contract**: document it (what it means, when it occurs, how to resolve, whether retrying helps). Make the URI resolvable to documentation.
* Choose **status codes** carefully — they drive client and proxy behavior:
  * 400 malformed/invalid input; 401 unauthenticated; 403 forbidden; 404 not found (or hidden); 409 conflict with current state; 412 precondition failed (ETag mismatch); 422 semantically invalid (if you distinguish it from 400); 429 rate-limited (with `Retry-After`); 503 temporarily unavailable (retryable).
* Separate **retryability** explicitly (an extension like `"retryable": true`) for clients that can't infer it.

### Security considerations
* Never leak internals: stack traces, SQL, class names, server paths, or whether a resource exists for unauthorized callers. Spring Boot defaults to `server.error.include-stacktrace=never`; keep it.
* Log the full exception server-side with a **correlation ID** and return it in the problem (`"traceId": "4bf92f..."`) so support can find the log entry.

```java
pd.setProperty("traceId", tracer.currentSpan() != null ? tracer.currentSpan().context().traceId() : null);
```

### Consistency across services and edges
* Errors from gateways, load balancers and filters (Spring Security's 401/403, rate limiters, request-size limits) must use the same format — configure `AuthenticationEntryPoint`/`AccessDeniedHandler` to write problem+json, and gateways to wrap upstream failures.
* Clients (and your own `RestClient`/`WebClient` code) should parse `application/problem+json` into a typed error and map `type` to domain exceptions rather than matching `detail` text.
* Localization: keep `title`/`detail` in English for developers, or localize via `Accept-Language` consistently; clients should never depend on the text.

### Evolution
Adding extension members is backward-compatible; changing a `type` URI or its meaning is breaking. Version the error catalog like the rest of the API, and include problem schemas in the OpenAPI spec (`components.schemas.Problem` with `oneOf` for specific types) so generated clients understand them.

## 🎯 Interview Cheat Sheet

**30-second pitch:** RFC 9457 Problem Details standardizes API errors as `application/problem+json` with `type`, `title`, `status`, `detail`, `instance` and extension members. In Spring 6 I enable problem details, map domain exceptions centrally in a `@RestControllerAdvice` extending `ResponseEntityExceptionHandler`, add field errors and a trace ID as extensions, keep type URIs as a documented catalog, choose status codes deliberately, and make security, gateway and filter errors use the same format without leaking internals.

**Must know:**
* Problem Details members and media type; RFC 9457 obsoletes 7807.
* `ProblemDetail`, `ErrorResponse`, `spring.mvc.problemdetails.enabled`.
* Validation errors as an `errors` extension.
* Status code semantics incl. 409/412/422/429/503.
* Trace ID, no internal leakage, consistent errors from security filters.

**Common follow-ups:**
* 400 or 422 for validation errors?
* How do clients know whether to retry?
* How do you make Spring Security's 401 use problem+json?

**Red flags:** `200 OK` with `{"error": ...}`; stack traces in responses; clients parsing human-readable messages.
