# How to catch performance regressions in CI

---

## 🟢 Junior Level

A **performance regression** is a change that makes the system slower or more resource-hungry: a new N+1 query, an accidental O(n²) loop, a heavier JSON mapping, a dependency upgrade with worse defaults. Found in production, they're expensive; found in CI, they're a one-line revert.

### Layers of performance checks in a pipeline

| Layer | What it catches | Cost |
| --- | --- | --- |
| Static checks / code review | Obvious anti-patterns (queries in loops, missing pagination) | Free |
| Query-count assertions in tests | N+1 queries, unexpected extra queries | Cheap |
| Microbenchmarks (JMH) | Regressions in hot algorithms/serialization | Medium |
| Service-level performance tests (Gatling/k6) | End-to-end latency/throughput changes | Higher |
| Production canary analysis | Real-traffic regressions | Requires good metrics |

### Cheapest and most effective: assert query counts

```java
@Test
void orderListUsesConstantNumberOfQueries() {
    QueryCountHolder.clear();                                  // datasource-proxy
    orderService.listOrders(customerId, PageRequest.of(0, 50));
    assertThat(QueryCountHolder.getGrandTotal().getSelect()).isLessThanOrEqualTo(2);   // not 51
}
```

## 🟡 Middle Level

### JMH benchmarks in the build
Benchmarks for hot code paths (pricing engine, serializers, parsers) can run in a dedicated CI job:

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
@State(Scope.Benchmark)
public class PricingBenchmark {
    private Cart cart;
    private PricingEngine engine;

    @Setup public void setUp() { cart = Carts.large(200); engine = PricingEngine.withDefaultRules(); }

    @Benchmark public Price price() { return engine.price(cart); }    // return value prevents dead-code elimination
}
```

Output JSON (`-rf json`), store the result as a build artifact, and compare with the baseline from `main`. Fail (or warn) if the score worsens beyond a threshold **and** outside the confidence interval.

### Service-level checks with thresholds

```javascript
// k6 script with pass/fail thresholds
export const options = {
  scenarios: {
    steady: { executor: 'constant-arrival-rate', rate: 200, timeUnit: '1s', duration: '5m',
              preAllocatedVUs: 100, maxVUs: 400 },
  },
  thresholds: {
    'http_req_duration{endpoint:checkout}': ['p(95)<400', 'p(99)<800'],
    'http_req_failed': ['rate<0.001'],
  },
};
```

k6 exits non-zero when thresholds fail, which fails the pipeline stage. Run against an ephemeral environment deployed from the same artifact.

## 🔴 Senior Level

### Dealing with noise
CI environments are noisy (shared runners, CPU frequency scaling, noisy neighbors). Without care, perf gates either flake or are so loose they catch nothing.
* **Dedicated, consistent runners** for benchmarks (same instance type, no other jobs, disable turbo boost if you can).
* **Repeat runs** and use statistics: compare distributions (Mann-Whitney U test, bootstrapped confidence intervals) rather than single numbers.
* **Relative comparisons**: run baseline and candidate **in the same job** on the same machine, alternating, instead of comparing to numbers from last week.
* **Track trends** over time (dashboards of benchmark results per commit) to see gradual creep that no single PR exceeds — tools like Bencher, Hunter (change-point detection), or custom time-series storage.
* **Measure resources, not only time**: allocation rate (`-prof gc` in JMH), number of queries, bytes transferred, objects per request — often more stable than wall-clock latency and directly tied to cost.

### What to gate on vs what to report
* **Gate (fail the build)**: deterministic metrics — query counts, allocations per operation, response payload size, startup time budget, number of HTTP calls to dependencies.
* **Report (comment on the PR)**: noisy metrics like latency percentiles from short load tests, with a link to the comparison.
* **Nightly**: longer load and soak tests, with alerts to the owning team on regression.

### Production as the last gate
* **Canary analysis** (Argo Rollouts/Flagger with Prometheus, Kayenta): route a small share of traffic to the new version and compare its p99, error rate and CPU per request with the baseline; abort automatically on significant regression.
* **Continuous profiling** (Pyroscope, Datadog, async-profiler in production) to diff flame graphs between versions and pinpoint which methods got slower.
* Annotate dashboards with deployments so regressions correlate with releases at a glance.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I catch performance regressions in layers: query-count and allocation assertions in normal tests, JMH benchmarks for hot code with statistical baseline comparison, k6 or Gatling service tests with p95/p99 and error-rate thresholds against ephemeral environments, and canary analysis plus continuous profiling in production. I gate on deterministic metrics and report noisy ones, using dedicated runners and same-job baseline comparisons to control noise.

**Must know:**
* Query-count assertions for N+1.
* JMH basics: warm-up, forks, `@State`, returning results; JSON results for comparison.
* k6/Gatling thresholds failing the build.
* Noise handling: dedicated runners, repeated runs, statistical comparison, trends.
* Canary analysis; continuous profiling diffs.

**Common follow-ups:**
* How do you avoid flaky performance gates?
* What would you gate on in every PR?
* How do you find gradual regressions?

**Red flags:** comparing single runs on shared CI agents; perf testing only before big releases; ignoring allocation and query counts.
