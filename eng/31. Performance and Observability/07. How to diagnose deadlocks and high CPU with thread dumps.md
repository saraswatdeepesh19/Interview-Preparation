# How to diagnose deadlocks and high CPU with thread dumps

---

## 🟢 Junior Level

### 1. What is a thread dump?

A **thread dump** is a text snapshot of every thread in the JVM: its name, state (`RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`) and its current stack trace. It answers "what is every thread doing *right now*?"

### 2. Real-world analogy

A photo of an office at 3 PM: who is typing (RUNNABLE), who is waiting for a colleague to finish with the printer (BLOCKED), and who is on hold on the phone (WAITING). If two people each hold one document the other needs and refuse to let go, that is a **deadlock**.

### 3. How to take one

```bash
jps -l                          # list Java processes
jstack <pid> > dump1.txt        # classic
jcmd <pid> Thread.print > dump1.txt   # preferred; works on all modern JDKs
kill -3 <pid>                   # Linux: prints dump to the app's stdout (does not kill)
```

On Windows, press `Ctrl+Break` in the console, or use `jstack`/`jcmd`.

### 4. A deadlock you can reproduce

```java
public class DeadlockDemo {

    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(100);
                synchronized (LOCK_B) {
                    System.out.println("t1 got both");
                }
            }
        }, "worker-1");

        Thread t2 = new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(100);
                synchronized (LOCK_A) {
                    System.out.println("t2 got both");
                }
            }
        }, "worker-2");

        t1.start();
        t2.start();
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

Run it, then `jstack <pid>`. At the bottom, the JVM prints:

```
Found one Java-level deadlock:
=============================
"worker-2":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "worker-1"
"worker-1":
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),
  which is held by "worker-2"
```

```mermaid
flowchart LR
    T1[worker-1 holds A] -->|wants B| T2[worker-2 holds B]
    T2 -->|wants A| T1
```

> [!IMPORTANT]
> The JVM detects classic monitor and `java.util.concurrent` ownable-synchronizer deadlocks automatically; `jstack` prints them. Always take **several dumps** (3 dumps, 5-10 s apart) to see what changes.

## 🟡 Middle Level

### 1. Thread states and what they mean

| State | Meaning | Healthy? |
| :--- | :--- | :--- |
| `RUNNABLE` | Running or ready to run (also blocked in native I/O such as socket read) | Depends, a socket read is "RUNNABLE" but idle |
| `BLOCKED` | Waiting to enter a `synchronized` block | Many → lock contention |
| `WAITING` | `Object.wait()`, `park()`, `join()` without timeout | Idle pool workers are normally here |
| `TIMED_WAITING` | `sleep`, `wait(ms)`, `parkNanos` | Often normal |

A dump excerpt:

```
"http-nio-8080-exec-17" #55 daemon prio=5 os_prio=0 cpu=1823.45ms elapsed=312.77s tid=0x00007f... nid=0x1a2b waiting for monitor entry [0x00007f...]
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.CacheService.get(CacheService.java:42)
        - waiting to lock <0x000000076ab62208> (a java.util.HashMap)
        at com.example.OrderController.show(OrderController.java:30)
```

`nid` is the native thread id in **hex**, which links Java threads to OS threads.

### 2. Finding the thread that burns CPU (Linux)

```bash
PID=$(pgrep -f myapp.jar)
top -H -b -n 1 -p $PID | head -15          # per-thread CPU: note the busiest TID, e.g. 6699
printf '%x\n' 6699                         # -> 1a2b
jcmd $PID Thread.print | grep -A 25 'nid=0x1a2b'
```

If the hot thread is "GC Thread" or "C2 CompilerThread", you have a GC or JIT problem, not application code. If it is `http-nio-exec-N`, read its stack: regex, JSON serialization, a `while` loop, `HashMap` corruption in unsynchronized code (old bug: infinite loop in `HashMap.get`), etc. Newer JDK dumps include `cpu=` and `elapsed=` per thread, enabling comparison between consecutive dumps (CPU delta per thread).

### 3. Patterns to recognize

| Pattern in the dump | Diagnosis |
| :--- | :--- |
| Many threads `BLOCKED` on the same lock address | Lock contention (hot `synchronized`) |
| Many threads `WAITING` in `HikariPool.getConnection` | DB pool exhaustion |
| Many threads `RUNNABLE` in `SocketInputStream.socketRead0` | Waiting on slow downstream without timeouts |
| All Tomcat `exec` threads busy in same business method | Slow dependency, thread starvation |
| Threads `WAITING` on `CompletableFuture.get`/`ForkJoinPool` | Blocking inside the common pool (starvation) |
| One thread `RUNNABLE` at 100% in same frame across dumps | CPU loop |
| Deadlock section at the end | Lock-order inversion |

### 4. Detecting deadlock from code

```java
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;

public class DeadlockWatchdog {

    public static void start() {
        ThreadMXBean mx = ManagementFactory.getThreadMXBean();
        Thread t = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                long[] ids = mx.findDeadlockedThreads();   // monitors + j.u.c locks
                if (ids != null) {
                    for (ThreadInfo info : mx.getThreadInfo(ids, true, true)) {
                        System.err.println(info);
                    }
                }
                try { Thread.sleep(10_000); } catch (InterruptedException e) { return; }
            }
        }, "deadlock-watchdog");
        t.setDaemon(true);
        t.start();
    }
}
```

Spring Boot Actuator exposes `GET /actuator/threaddump` (JSON, or `text/plain` with `Accept: text/plain`), and Micrometer has `jvm.threads.states` and `jvm.threads.live`, plus `jvm.threads.deadlocked` in newer releases.

### 5. Preventing deadlocks

- Acquire locks in a **global consistent order**.
- Use `ReentrantLock.tryLock(timeout)` and back off.
- Narrow critical sections; never call alien/unknown code (callbacks, listeners) while holding a lock.
- Prefer immutable data, `ConcurrentHashMap`, higher-level constructs.
- DB deadlocks are different (the DB detects and kills one transaction): keep a consistent row access order and short transactions.

### 6. Common mistakes

- Taking only one dump and drawing conclusions.
- Confusing `RUNNABLE` in socket read with "using CPU".
- Forgetting that a dump pauses the JVM at a safepoint (brief, but large thread counts make it longer).
- Not naming thread pools (use a `ThreadFactory` with names, so dumps are readable).

## 🔴 Senior Level

### 1. Reading dumps at scale

Production services can have thousands of threads. Aggregate: group threads by identical stack top, count them. Tools: fastThread (online), Spotify's `jstack-parser` style scripts, IntelliJ "Analyze Stack Trace/Thread Dump", JMC thread views. A quick one-liner to count by state:

```bash
grep 'java.lang.Thread.State' dump1.txt | sort | uniq -c | sort -rn
```

Group by the first frame under `State`:

```bash
awk '/java.lang.Thread.State/{getline; print $0}' dump1.txt | sort | uniq -c | sort -rn | head
```

### 2. Dump with lock info and JSON

```bash
jcmd <pid> Thread.print -l                         # include j.u.c ownable synchronizers
jcmd <pid> Thread.dump_to_file -format=json /var/data/threads.json   # JDK 21+, includes virtual threads
```

Plain `jstack` does **not** show virtual threads by default; the JSON format from `jcmd Thread.dump_to_file` (JDK 21+) does. Virtual-thread pinning (blocking inside `synchronized` before JDK 24, or native frames) can be diagnosed with `-Djdk.tracePinnedThreads=full` or JFR event `jdk.VirtualThreadPinned`.

### 3. Hidden deadlock-like situations the JVM does not report

- **Thread-pool deadlock (starvation):** tasks in a bounded pool wait for results of tasks queued in the *same* pool.

```java
import java.util.concurrent.*;

public class PoolStarvation {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<?> f1 = pool.submit(() -> wait(pool));
        Future<?> f2 = pool.submit(() -> wait(pool));
        f1.get(); // never returns: both workers wait for inner tasks that can't get a thread
    }
    static void wait(ExecutorService p) {
        try { p.submit(() -> "inner").get(); } catch (Exception e) { throw new RuntimeException(e); }
    }
}
```

The dump shows both workers `WAITING` in `FutureTask.get`, no "Found deadlock" message. Fixes: separate pools per dependency level, async composition (`CompletableFuture.thenCompose`), timeouts.

- **Livelock / spin:** threads `RUNNABLE` forever without progress; spotted by repeated dumps showing the same frame and high CPU.
- **Lost wake-up / missed signal:** threads `WAITING` forever; look at the condition they wait on.
- **DB lock wait:** app threads `RUNNABLE` in JDBC read; need `pg_stat_activity`/`SHOW ENGINE INNODB STATUS`.

### 4. Correlating with other evidence

For high CPU: top-thread TID → dump → JFR/async-profiler CPU profile to confirm statistically (a dump is a single sample; see [How to profile a Java application with JFR and async-profiler](04.%20How%20to%20profile%20a%20Java%20application%20with%20JFR%20and%20async-profiler.md)). Also compare `jstat -gcutil <pid> 1000`: if GC threads dominate CPU, move to GC logs.

For high latency with low CPU: count threads in `HikariPool.getConnection`, `Socket read`, `Object.wait` and `Unsafe.park`; that identifies the resource that threads are queued on.

### 5. Production-safe practices

- Use `jcmd` (not `kill -3` on prod apps whose stdout is lost).
- Take 3-5 dumps at fixed intervals with a script, keep timestamps.
- Be careful in containers: `jcmd` must run as the same user in the same PID namespace (`kubectl exec`).
- If the JVM is hung and unresponsive to attach, use `jhsdb jstack --pid <pid>` or `gdb`/`gcore` as last resorts (`jhsdb` freezes the process).
- Ensure thread names are meaningful: `new ThreadFactoryBuilder().setNameFormat("payments-%d")`, Spring `ThreadPoolTaskExecutor#setThreadNamePrefix`.

### 6. Script: three dumps and a CPU table

```bash
#!/usr/bin/env bash
PID=$1
for i in 1 2 3; do
  jcmd "$PID" Thread.print -l > "dump-$i-$(date +%H%M%S).txt"
  top -H -b -n 1 -p "$PID" | head -20 > "top-$i.txt"
  sleep 5
done
```

## 🎯 Interview Cheat Sheet

### 30-second elevator pitch
"A thread dump is a snapshot of all JVM threads with states and stacks. I take several with `jcmd Thread.print`, look for deadlock reports, many threads BLOCKED on one monitor, or many parked waiting for pool connections. For high CPU I map `top -H` thread IDs to hex `nid` values and read those stacks, then confirm with a profiler."

### Must-know bullets
- `jstack`, `jcmd Thread.print`, `kill -3`, Actuator `/threaddump`.
- States: RUNNABLE, BLOCKED, WAITING, TIMED_WAITING.
- `nid` is hex of the OS thread id; use with `top -H`.
- Take multiple dumps; one is a sample.
- Deadlock prevention: ordering, tryLock, short critical sections.
- Thread-pool starvation isn't reported as a deadlock.

### Common follow-up questions
1. How do you find which thread uses 100% CPU?
2. How is a deadlock different from starvation?
3. What does BLOCKED vs WAITING mean?
4. How do virtual threads appear in dumps?
5. How can an app detect deadlocks itself?

### 🚩 Red flags
- Restarting the service without a dump.
- Believing RUNNABLE always means consuming CPU.
- Using unnamed thread pools.
- Running `jhsdb` casually on production.
