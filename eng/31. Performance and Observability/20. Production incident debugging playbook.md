# Production incident debugging playbook

---

## 🟢 Junior Level

When production breaks, the goal is to **restore service first**, understand later. A calm, repeatable process beats heroics.

### The first 15 minutes
1. **Acknowledge** the alert and **declare** an incident if users are affected (open a channel, assign an incident commander).
2. **Assess impact** — which users, which features, since when? Check the SLO/RED dashboards.
3. **Look for recent changes** — deployments, config changes, feature flags, infrastructure changes, traffic spikes. Most incidents follow a change.
4. **Mitigate** — roll back the last deploy, disable a feature flag, scale up, fail over, shed load. Prefer reversible actions.
5. **Communicate** — status page / stakeholders updates at regular intervals.
6. **Then investigate** the root cause with logs, metrics, traces, dumps.

### Golden rule
If a deployment happened shortly before the problem started, **roll back first** and debug the old version offline. "Let me just check one thing" costs error budget and user trust.

## 🟡 Middle Level

### Symptom → where to look

| Symptom | First checks | Tools |
| --- | --- | --- |
| Error rate spike | Error types, which endpoints, which dependency | Logs grouped by exception, traces with errors, `http_client_requests` per dependency |
| Latency spike | Which percentile, which endpoint, DB vs downstream vs CPU | RED dashboard, traces of slow requests, Hikari pending, executor queues |
| High CPU | GC or application code? | GC logs / `jvm_gc_*`, `jcmd <pid> Thread.print` ×3, async-profiler CPU flame graph |
| Memory growth / OOM | Heap after GC trend, metaspace, direct memory | Heap dump (`jcmd <pid> GC.heap_dump`), MAT dominator tree, NMT |
| Requests hang | Threads blocked on locks, pools, I/O | Thread dumps, `jdk.ThreadPark` JFR, pool metrics |
| Pod restarts | OOMKilled vs liveness failure vs crash | `kubectl describe pod`, events, last logs (`kubectl logs --previous`) |

### JVM evidence collection (copy-paste ready)

```bash
# Thread dumps: take 3, 5 seconds apart, to see what is *persistently* running or blocked
for i in 1 2 3; do jcmd $PID Thread.print -l > threads-$i.txt; sleep 5; done

# Java Flight Recorder for 2 minutes with profiling settings (low overhead, safe in prod)
jcmd $PID JFR.start name=incident settings=profile duration=120s filename=/tmp/incident.jfr

# GC and heap overview
jcmd $PID GC.heap_info
jstat -gcutil $PID 1000 10

# Heap dump (pauses the JVM; large heaps take time and disk space)
jcmd $PID GC.heap_dump /tmp/heap.hprof

# Native memory (if started with -XX:NativeMemoryTracking=summary)
jcmd $PID VM.native_memory summary
```

In Kubernetes: `kubectl exec` into the pod (or use an ephemeral debug container with JDK tools: `kubectl debug -it pod/orders-7d9 --image=eclipse-temurin:21-jdk --target=orders`).

### Pre-configure the JVM for incidents

```text
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
-XX:+ExitOnOutOfMemoryError                 # let Kubernetes restart a broken JVM
-Xlog:gc*,safepoint:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m
-XX:StartFlightRecording=disk=true,maxage=6h,maxsize=500m,dumponexit=true,filename=/dumps/
```

A continuously running JFR ring buffer means you can dump the *last hours* after an incident (`jcmd $PID JFR.dump`).

## 🔴 Senior Level

### Diagnosis heuristics
* **Correlate in time**: overlay deploy markers, traffic, error and latency graphs; the first metric that changed usually points at the cause, the others are effects.
* **Differential diagnosis**: is it one pod, one AZ, one region, one tenant, one endpoint, one version? Narrowing the blast radius narrows the cause (`by (pod)`, `by (version)` in PromQL).
* **Distinguish cause from symptom**: rising latency + pool saturation + rising retries → which came first? Look at the slowest dependency spans in traces.
* **Beware of retries masking failures**: success-with-retry metrics rising is often the earliest signal.
* **Check the boring things**: certificate expiry, DNS, clock skew, disk full, quota limits, expired credentials, cloud provider status.

### Common JVM incident patterns
* **GC death spiral**: heap near full → back-to-back old-gen collections → CPU 100%, throughput collapses. Evidence: GC logs, `jvm_gc_pause_seconds`, heap after GC. Mitigate by restarting/scaling; root cause with heap dump.
* **Thread pool / connection pool exhaustion**: all request threads waiting on a slow dependency or `HikariPool.getConnection`. Evidence: thread dumps full of the same stack. Mitigate: shed load, timeouts, circuit breaker.
* **Deadlock**: `jcmd Thread.print` reports `Found one Java-level deadlock`. Restart; fix lock ordering.
* **Container CPU throttling**: latency spikes with moderate CPU use; check cgroup throttling metrics; raise/remove CPU limits.
* **Off-heap leaks**: RSS grows but heap is fine → direct buffers (Netty), thread stacks, glibc malloc fragmentation (`MALLOC_ARENA_MAX=2`), Metaspace from class loader leaks.

### After the incident
* **Blameless postmortem** within days: timeline, impact (SLO budget used), detection, mitigation, root cause(s) and *contributing factors*, what went well, action items with owners (detection gaps, missing timeouts, runbooks, tests).
* Track action items to completion and review recurring themes quarterly.
* Turn the investigation into **runbooks** and **automation** (auto-rollback on canary failure, alert annotations linking dashboards and queries).

## 🎯 Interview Cheat Sheet

**30-second pitch:** In an incident I first assess impact and mitigate — rollback, feature flag, scale, failover — then investigate with RED dashboards, traces, logs and JVM evidence: three thread dumps, JFR recordings, GC logs and heap dumps, collected with `jcmd`. I pre-configure heap dumps on OOM and a continuous JFR buffer, narrow the blast radius by pod, version or region, recognize common JVM patterns like GC spirals and pool exhaustion, and finish with a blameless postmortem and tracked action items.

**Must know:**
* Mitigate first; recent changes are the prime suspect.
* Symptom → tool table.
* `jcmd Thread.print`, `JFR.start/dump`, `GC.heap_dump`, `VM.native_memory`.
* JVM flags for incident readiness.
* Common patterns: GC spiral, pool exhaustion, deadlock, throttling, off-heap leaks.

**Common follow-ups:**
* Latency doubled after a deploy but rollback didn't help — what next?
* How do you take a heap dump of a 30 GB heap safely?
* What goes into a postmortem?

**Red flags:** debugging in production for an hour before rolling back; restarting without collecting evidence; blaming individuals.
