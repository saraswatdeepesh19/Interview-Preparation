# How to expose metrics with Micrometer and Spring Boot Actuator

---

## 🟢 Junior Level

**Micrometer** is the metrics facade for the JVM ("SLF4J for metrics"): you record metrics through one API, and registries export them to Prometheus, Datadog, CloudWatch, New Relic, OTLP and others. **Spring Boot Actuator** auto-configures Micrometer and instruments the JVM, HTTP server and clients, data sources, caches, executors and more.

```xml
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-actuator</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-registry-prometheus</artifactId></dependency>
```

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  metrics:
    tags:
      application: ${spring.application.name}      # common tag on every metric
```

Prometheus then scrapes `GET /actuator/prometheus`:

```text
http_server_requests_seconds_count{method="GET",outcome="SUCCESS",status="200",uri="/api/orders/{id}"} 1532
jvm_memory_used_bytes{area="heap",id="G1 Old Gen"} 2.1E8
hikaricp_connections_active{pool="HikariPool-1"} 4
```

### Meter types
* **Counter** — only increases (orders placed, errors).
* **Gauge** — current value sampled on scrape (queue size, cache size).
* **Timer** — count + total time + max, optionally percentiles/histograms (request latency).
* **DistributionSummary** — like a timer for non-time values (payload sizes, order amounts).
* **LongTaskTimer** — tracks in-flight long operations (batch job running for 12 minutes).

## 🟡 Middle Level

### Custom business metrics

```java
@Service
class CheckoutMetrics {
    private final Counter ordersPlaced;
    private final DistributionSummary orderValue;
    private final Timer paymentTimer;

    CheckoutMetrics(MeterRegistry registry, PendingQueue queue) {
        this.ordersPlaced = Counter.builder("shop.orders.placed")
                .description("Orders successfully placed")
                .tag("channel", "web")
                .register(registry);
        this.orderValue = DistributionSummary.builder("shop.orders.value")
                .baseUnit("eur")
                .publishPercentileHistogram()
                .register(registry);
        this.paymentTimer = Timer.builder("shop.payment.authorize")
                .publishPercentileHistogram()
                .serviceLevelObjectives(Duration.ofMillis(200), Duration.ofMillis(500))
                .register(registry);
        Gauge.builder("shop.pending.orders", queue, PendingQueue::size).register(registry);   // weak reference to queue
    }

    void placed(Order o) { ordersPlaced.increment(); orderValue.record(o.total().doubleValue()); }
    <T> T timePayment(Supplier<T> call) { return paymentTimer.record(call); }
}
```

Declarative alternatives: `@Timed` / `@Counted` (need `TimedAspect`/`CountedAspect` beans), or the **Observation API** (`@Observed`) which produces both metrics and traces.

### Naming and tags
* Names: lowercase dot-separated (`shop.orders.placed`); registries convert (`shop_orders_placed_total` in Prometheus).
* Tags (dimensions): **low cardinality only** — `status`, `method`, `uri` template, `region`, `tenant_tier`. Never user IDs, order IDs, raw URLs, or exception messages: each unique tag combination is a separate time series, and cardinality explosions take down Prometheus and inflate vendor bills.
* Spring uses URI **templates** (`/api/orders/{id}`) for `http.server.requests` — custom code that builds URIs by concatenation breaks this and creates one series per ID.

### Percentiles: histograms vs client-side percentiles
* `publishPercentileHistogram()` exports histogram buckets; Prometheus computes percentiles **across instances** with `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))` — correct aggregation.
* `publishPercentiles(0.95, 0.99)` computes percentiles **in the app**; they can't be aggregated across pods (averaging p99s is meaningless). Prefer histograms.

## 🔴 Senior Level

### Cost and cardinality control
Each timer with histograms produces dozens of series (buckets × tag combinations). With 200 URIs × 5 statuses × 3 methods × 70 buckets × 50 pods, that's millions of series. Controls:

```java
// Spring Boot applies every MeterFilter bean to the auto-configured registries
@Bean
MeterFilter denyUnusedMeters() {
    return MeterFilter.denyNameStartsWith("tomcat.sessions");            // drop meters nobody looks at
}

@Bean
MeterFilter capUriCardinality() {
    return MeterFilter.maximumAllowableTags("http.server.requests", "uri", 200,
            MeterFilter.deny());                                          // stop creating series beyond 200 URIs
}

@Bean
MeterFilter httpSloBuckets() {
    return new MeterFilter() {
        @Override
        public DistributionStatisticConfig configure(Meter.Id id, DistributionStatisticConfig cfg) {
            if (!id.getName().startsWith("http.server.requests")) return cfg;
            return DistributionStatisticConfig.builder()
                    .percentilesHistogram(false)                          // no ~70 default buckets...
                    .serviceLevelObjectives(                              // ...only these (timers use nanoseconds)
                            Duration.ofMillis(100).toNanos(),
                            Duration.ofMillis(300).toNanos(),
                            Duration.ofSeconds(1).toNanos())
                    .build()
                    .merge(cfg);
        }
    };
}
```

The same SLO buckets can be set without code via `management.metrics.distribution.slo.http.server.requests=100ms,300ms,1s`.

Prometheus native histograms and OTLP exponential histograms reduce bucket overhead further when your backend supports them.

### Exemplars: from a latency spike to the trace
With Micrometer Tracing on the classpath and Prometheus exemplar support, histogram buckets carry a sample `trace_id`. In Grafana you click a slow bucket point and jump straight to a trace of a slow request — the bridge between metrics and traces.

### Gotchas
* **Gauges hold weak references**: `Gauge.builder(..., obj, fn)` doesn't keep `obj` alive; if nothing else references it, the gauge reports `NaN`. Register gauges on long-lived objects.
* **Counters reset on restart**; always use `rate()`/`increase()` in queries, never raw values.
* **Push vs pull**: Prometheus scrapes (pull); short-lived jobs need Pushgateway or OTLP push. With Kubernetes, use ServiceMonitors/PodMonitors to discover pods.
* **Management port**: expose `/actuator/prometheus` on a separate port (`management.server.port`) not routed publicly; metrics can reveal internal endpoints and volumes.
* **Clock and step**: registries that push (Datadog, CloudWatch) aggregate per `step` (e.g. 1 min); a too-large step hides spikes, too small inflates cost.

### What to always have
RED metrics per endpoint (rate, errors, duration), USE metrics for resources (Hikari pool utilization and pending, executor queue sizes and rejections, GC pause and allocation rate, heap after GC), business KPIs (orders/min, payment success ratio), and SLO histograms — all tagged with `application`, `region`, `version` for deploy comparisons.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Micrometer is a vendor-neutral metrics facade; Spring Boot Actuator auto-instruments HTTP, JVM, pools and clients and exposes `/actuator/prometheus`. I add business metrics with counters, timers, summaries and gauges, keep tags low-cardinality, use histograms rather than client-side percentiles so they aggregate across pods, control cost with MeterFilters and explicit SLO buckets, and link metrics to traces with exemplars.

**Must know:**
* Meter types: Counter, Gauge, Timer, DistributionSummary, LongTaskTimer.
* `management.endpoints.web.exposure.include`, common tags.
* URI templates and cardinality.
* `publishPercentileHistogram` + `histogram_quantile` vs `publishPercentiles`.
* MeterFilter, exemplars, weak-reference gauges.

**Common follow-ups:**
* Why can't you average p99 across instances?
* Our Prometheus is running out of memory — what do you check?
* `@Timed` vs Observation API?

**Red flags:** user IDs as tags; `publishPercentiles` aggregated across pods; actuator exposed publicly.
