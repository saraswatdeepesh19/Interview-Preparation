# How to design SLO based alerts

---

## 🟢 Junior Level

Traditional alerts fire on **causes** ("CPU > 80%", "1 error in the log") — they're noisy, wake people for things users don't notice, and still miss real outages. **SLO-based alerts** fire on **symptoms that consume the error budget**: users are actually getting errors or slow responses at a rate that threatens the SLO.

### The idea in one example
SLO: 99.9% of checkout requests succeed over 30 days → error budget = 0.1% of requests.
* A brief spike of errors for 30 seconds consumes almost no budget → **no page**.
* 2% of requests failing for an hour burns the monthly budget 20× faster than allowed → **page now**.
* 0.2% failing all week burns budget 2× too fast → **ticket**, fix during working hours.

### Rules of good paging alerts
* **Actionable** — someone can and must do something now.
* **User-impacting** — tied to an SLI.
* **Low noise** — every page is real; otherwise people learn to ignore pages.
* **Has a runbook** link and dashboards.

---

## 🟡 Middle Level

### Burn rate
`burn rate = (error ratio observed over a window) / (1 − SLO)`.
* Burn rate 1 → budget lasts exactly the SLO period.
* Burn rate 14.4 → a 30-day budget is consumed in ~2 days (2% of budget per hour).

### Multi-window, multi-burn-rate alerts (Prometheus)

```yaml
groups:
  - name: checkout-slo
    rules:
      - record: sli:checkout_errors:ratio_rate5m
        expr: |
          sum(rate(http_server_requests_seconds_count{uri="/api/checkout", outcome="SERVER_ERROR"}[5m]))
          / sum(rate(http_server_requests_seconds_count{uri="/api/checkout"}[5m]))
      - record: sli:checkout_errors:ratio_rate1h
        expr: |
          sum(rate(http_server_requests_seconds_count{uri="/api/checkout", outcome="SERVER_ERROR"}[1h]))
          / sum(rate(http_server_requests_seconds_count{uri="/api/checkout"}[1h]))
      # ... same for 30m and 6h

      - alert: CheckoutErrorBudgetBurnFast
        expr: |
          sli:checkout_errors:ratio_rate1h > (14.4 * 0.001)
          and
          sli:checkout_errors:ratio_rate5m > (14.4 * 0.001)
        labels: { severity: page }
        annotations:
          summary: "Checkout burning error budget 14x faster than allowed"
          runbook_url: https://runbooks.shop.internal/checkout-errors

      - alert: CheckoutErrorBudgetBurnSlow
        expr: |
          sli:checkout_errors:ratio_rate6h > (6 * 0.001)
          and
          sli:checkout_errors:ratio_rate30m > (6 * 0.001)
        labels: { severity: page }
```

The **long window** ensures significance (enough budget consumed); the **short window** makes the alert stop quickly after recovery. A third, slower pair (burn rate 1 over 3 days / 6 hours) creates tickets.

### Latency SLO alerts
Use a threshold-based SLI: `good = requests faster than 500 ms`. With histogram buckets aligned to the threshold:

```promql
1 - (
  sum(rate(http_server_requests_seconds_bucket{uri="/api/checkout", le="0.5"}[1h]))
  / sum(rate(http_server_requests_seconds_count{uri="/api/checkout"}[1h]))
)
```

That "slow ratio" is compared against the latency SLO's budget exactly like errors.

## 🔴 Senior Level

### Edge cases and design choices
* **Low traffic**: at 10 requests/hour, one failure is a 10% error ratio → false pages. Options: require a minimum request count in the expression, use longer windows, aggregate related endpoints into one SLI, or add synthetic traffic (probes) to have a baseline.
* **Partial outages**: a 100% failure for one tenant or region can be <1% globally. Add per-region or per-tier SLIs for key segments, or alert on "any region burning fast".
* **Dependencies**: a downstream outage should page the owning team of the user-facing SLO (symptom), while cause-based alerts (dependency error rates) route to the dependency team as tickets or lower-severity notifications.
* **Maintenance and deployments**: planned downtime still consumes budget unless excluded deliberately; decide policy explicitly.
* **SLO windows**: rolling 28/30 days for alerting and reporting; calendar months for SLA reporting.

### Tooling
* **Sloth** and **Pyrra** generate recording rules and multi-burn-rate alerts from a compact SLO spec (and can enforce consistency across teams).
* **OpenSLO** is a vendor-neutral YAML spec for SLO definitions.
* Datadog, Grafana SLO, Dynatrace, New Relic and Google Cloud have native SLO objects with burn-rate alerts.

```yaml
# Sloth spec (simplified)
version: prometheus/v1
service: checkout
slos:
  - name: availability
    objective: 99.9
    sli:
      events:
        error_query: sum(rate(http_server_requests_seconds_count{uri="/api/checkout",outcome="SERVER_ERROR"}[{{.window}}]))
        total_query: sum(rate(http_server_requests_seconds_count{uri="/api/checkout"}[{{.window}}]))
    alerting:
      page_alert: { labels: { severity: page } }
      ticket_alert: { labels: { severity: ticket } }
```

### What to keep as non-SLO alerts
A few **cause-based** alerts remain valuable when they predict imminent impact faster than SLIs can: disk nearly full, certificate expiring in < 14 days, backup job failures, consumer lag growing toward retention limits, database replication broken. Route them as tickets or low-urgency pages.

### Measuring alert quality
Track pages per week, percentage actionable, time-to-acknowledge, and alerts with no runbook. Review after each incident: did the SLO alert fire? Too late? Was there a page with no user impact? Adjust windows, thresholds and SLIs accordingly.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I page on symptoms — the rate at which the error budget is burning — rather than on causes like CPU. Burn rate is the observed bad-event ratio divided by the allowed ratio; I use multi-window, multi-burn-rate rules such as 14.4× over 1 h and 5 min, and 6× over 6 h and 30 min, for pages and 1× over 3 days for tickets, with special handling for low traffic and segmented outages, generated by tools like Sloth or Pyrra.

**Must know:**
* Burn rate formula and meaning.
* Long + short window combination.
* Latency SLIs with histogram thresholds.
* Low-traffic and per-segment issues.
* Keep a few predictive cause-based alerts as tickets.

**Common follow-ups:**
* Why two windows?
* How would you alert for a service with 50 requests per day?
* Which cause-based alerts would you keep?

**Red flags:** paging on every error; CPU/heap alerts as primary paging; SLO alerts without runbooks.
