# Common Java performance anti-patterns

---

## 🟢 Junior Level

Most Java performance problems in business applications aren't about the JVM — they're about **how the code talks to databases, networks and memory**. The usual suspects:

1. **N+1 queries** — loading a list, then one query per element.
2. **Chatty remote calls** — calling a service in a loop instead of one batch call.
3. **Missing pagination** — `findAll()` on a table with millions of rows.
4. **String concatenation in loops** — `s += x` creates a new string each iteration.
5. **Wrong collection** — `List.contains` in a loop (O(n²)), `LinkedList.get(i)`.
6. **Exceptions for control flow** — creating stack traces is expensive.
7. **Excessive logging** — DEBUG logging in hot paths, string building for disabled log levels.
8. **No timeouts** — threads stuck forever on slow dependencies.

### Examples and fixes

```java
// N+1: one query for orders + one per order for its customer
List<Order> orders = orderRepo.findAll();
orders.forEach(o -> System.out.println(o.getCustomer().getName()));   // lazy load per order

// Fix: fetch join / entity graph
@Query("select o from Order o join fetch o.customer where o.status = :status")
List<Order> findWithCustomer(OrderStatus status);

// Chatty calls: 500 HTTP requests
ids.forEach(id -> prices.add(pricingClient.price(id)));
// Fix: batch endpoint
List<Price> prices = pricingClient.prices(ids);

// Logging: argument evaluated even when DEBUG is off
log.debug("Order details: " + order.toDetailedString());
// Fix: parameterized logging (and guard expensive arguments)
log.debug("Order details: {}", order);
if (log.isDebugEnabled()) log.debug("Details: {}", order.toDetailedString());
```

## 🟡 Middle Level

### Persistence anti-patterns
* **Open Session in View** (`spring.jpa.open-in-view=true`, Boot's default) — keeps a DB connection for the entire web request including view rendering and serialization; lazy loads happen silently in JSON mapping. Disable it and load what you need explicitly.
* **Fetching entities to read two fields** — use DTO projections (`select new ...` or interface projections).
* **Eager fetching everywhere** (`FetchType.EAGER` on collections) — loads half the database for one entity.
* **Inserting one row at a time** — enable JDBC batching (`hibernate.jdbc.batch_size=50`, `order_inserts=true`) and avoid `IDENTITY` ID generation which disables insert batching in Hibernate; use sequences with pooled optimizers.
* **Long transactions** that include remote calls — hold locks and connections; keep transactions short.
* **Missing indexes** for the main query predicates; `LIKE '%term%'` on large tables.

### CPU and memory anti-patterns
* **Creating expensive objects repeatedly** — `new ObjectMapper()`, `Pattern.compile()`, `DateTimeFormatter.ofPattern()`, HTTP clients per request. Create once, reuse (they're thread-safe; `SimpleDateFormat` is not — use `DateTimeFormatter`).
* **Boxing in hot loops** — `List<Integer>` sums, `Map<Long, Long>` counters; use primitives/arrays or primitive collections.
* **Unbounded caches** (`static Map` that only grows) — the classic memory leak; use Caffeine with size/TTL limits.
* **Regex in hot paths** — `String.split(",")` with single chars is optimized, but `replaceAll`/`matches` compile patterns each call.
* **Streams for tiny or hot loops** — fine for clarity, but `parallelStream()` on small collections or I/O tasks is slower and uses the shared common pool.

### Concurrency anti-patterns
* **`synchronized` on hot shared objects** — contention; use concurrent collections, `LongAdder` for counters, or partition state.
* **Blocking calls on the common ForkJoinPool** (`CompletableFuture.supplyAsync` without an executor, parallel streams doing I/O) — starves other users of the pool.
* **Huge thread pools** to "fix" slowness — more context switching and memory; the bottleneck (DB) stays.
* **Unbounded executor queues** (`Executors.newFixedThreadPool` uses an unbounded `LinkedBlockingQueue`) — memory grows under overload instead of rejecting.

## 🔴 Senior Level

### Subtle JVM-level issues
* **Exception stack traces**: `fillInStackTrace` is costly; for expected high-frequency failures (validation in parsers), use result types or exceptions with `writableStackTrace=false`. Note HotSpot's `-XX:+OmitStackTraceInFastThrow` drops stack traces for frequently thrown built-in exceptions — which also makes production NPE logs useless; disable it if you see empty traces.
* **Megamorphic call sites and excessive abstraction** on hot paths prevent inlining — measure with JMH and JIT logs before blaming.
* **False sharing**: counters updated by different threads in the same cache line; `@Contended` (JDK internal) or `LongAdder` padding mitigate it.
* **Allocation rate**: high churn of short-lived objects (e.g. 2 GB/s) increases GC frequency; a JFR allocation profile shows the top allocation sites — often logging, JSON mapping, or `String.format`.
* **Reflection-heavy frameworks on hot paths** (custom mappers using reflection per call) — cache metadata, or use code generation (MapStruct).
* **Large JSON payloads**: serializing 50 MB responses blocks threads and spikes heap; paginate or stream (`JsonGenerator`, `StreamingResponseBody`).

### Infrastructure-level anti-patterns
* **Container misconfiguration**: tiny CPU limits causing throttling; `-Xmx` equal to the container memory limit (no room for metaspace, threads, direct memory → OOMKilled); old JDKs not container-aware.
* **DNS caching**: JVM caches DNS forever when a SecurityManager is present or per `networkaddress.cache.ttl` — failovers to new IPs go unnoticed; set a sane TTL (e.g. 30–60 s).
* **Connection churn**: creating TLS connections per request (no keep-alive, new client per call) — TLS handshakes dominate CPU and latency.
* **Synchronous logging to slow appenders** under load — use async appenders with bounded queues and decide drop vs block behavior.

### How to find them systematically
Profile before optimizing: async-profiler (CPU, allocation, wall-clock, lock modes), JFR events (`jdk.ObjectAllocationSample`, `jdk.JavaMonitorEnter`, `jdk.SocketRead`), database query statistics (`pg_stat_statements`), and tracing to locate chatty patterns (dozens of sequential spans per request). Fix the biggest item, measure again.

## 🎯 Interview Cheat Sheet

**30-second pitch:** The common Java performance anti-patterns are mostly I/O-related: N+1 queries, chatty remote calls, missing pagination and batching, open-session-in-view, long transactions and missing timeouts. In code: recreating expensive objects, boxing, unbounded caches and queues, exceptions as control flow, blocking the common pool and over-synchronization. I find them with profilers, JFR, query stats and traces, and fix the biggest measured problem first.

**Must know:**
* N+1, fetch joins/entity graphs, DTO projections, JDBC batching.
* Disable open-in-view; keep transactions short.
* Reuse `ObjectMapper`, `Pattern`, HTTP clients; `DateTimeFormatter`.
* Bounded executors; no blocking on the common pool; `LongAdder`.
* Container memory/CPU settings; DNS TTL; allocation profiling.

**Common follow-ups:**
* Why does `IDENTITY` generation hurt batch inserts?
* How do you find the top allocation sites?
* What's wrong with `Executors.newFixedThreadPool` under overload?

**Red flags:** optimizing without profiling; increasing thread pools as the fix; `parallelStream` for HTTP calls.
