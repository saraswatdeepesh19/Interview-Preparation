# How to write reliable JMH microbenchmarks

---

## 🟢 Junior Level

### 1. What is a microbenchmark?

A microbenchmark measures a **tiny piece of code** (one method, one data structure operation) in isolation. **JMH (Java Microbenchmark Harness)** is the official OpenJDK tool for this. Writing your own loop with `System.nanoTime()` almost always gives wrong numbers because the JVM optimizes code while it runs.

### 2. Real-world analogy

Timing a runner's 100 m sprint: you must let them warm up, measure several runs, and not let them cheat by skipping part of the track. JMH does the warm-up, repeated runs, and prevents the JVM from "cheating" (skipping work).

### 3. Minimal working example

Maven dependencies (version current at time of writing; use the latest 1.37):

```xml
<dependency>
  <groupId>org.openjdk.jmh</groupId>
  <artifactId>jmh-core</artifactId>
  <version>1.37</version>
</dependency>
<dependency>
  <groupId>org.openjdk.jmh</groupId>
  <artifactId>jmh-generator-annprocess</artifactId>
  <version>1.37</version>
  <scope>provided</scope>
</dependency>
```

Benchmark class:

```java
import org.openjdk.jmh.annotations.*;
import java.util.concurrent.TimeUnit;

@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
public class StringConcatBenchmark {

    @Param({"10", "100"})
    int size;

    String[] parts;

    @Setup
    public void setup() {
        parts = new String[size];
        for (int i = 0; i < size; i++) parts[i] = "item" + i;
    }

    @Benchmark
    public String plusOperator() {
        String s = "";
        for (String p : parts) s += p;
        return s;
    }

    @Benchmark
    public String stringBuilder() {
        StringBuilder sb = new StringBuilder();
        for (String p : parts) sb.append(p);
        return sb.toString();
    }
}
```

Build and run (the JMH archetype creates `benchmarks.jar`):

```bash
mvn clean package
java -jar target/benchmarks.jar StringConcatBenchmark
```

Output reports `Score` and `Error` (± confidence interval) for every `@Param` combination.

> [!IMPORTANT]
> Always **return** the result from a benchmark method (or pass it to a `Blackhole`) so the JVM cannot throw the work away.

## 🟡 Middle Level

### 1. Why naive benchmarks lie

```java
// BROKEN: do not benchmark like this
long t = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    Math.sqrt(i);              // result unused -> eliminated by JIT
}
System.out.println(System.nanoTime() - t);
```

Problems: interpreter vs compiled code, JIT compilation happening mid-measurement, dead-code elimination, constant folding, GC noise, one-off measurement. See [How JIT and tiered compilation work in the JVM](06.%20How%20JIT%20and%20tiered%20compilation%20work%20in%20the%20JVM.md).

### 2. The classic pitfalls

| Pitfall | What happens | JMH remedy |
| :--- | :--- | :--- |
| **Dead-code elimination (DCE)** | Unused result → JIT deletes the computation → "0.3 ns" | Return the value or `Blackhole.consume()` |
| **Constant folding** | Inputs are `static final` constants → computed at compile time | Read inputs from non-final `@State` fields |
| **No warm-up** | Measuring interpreter and C1 code | `@Warmup` iterations |
| **Loop optimizations** | Manual `for` loops get unrolled/hoisted/vectorized | Let JMH call the method; avoid loops (use `@OperationsPerInvocation` if needed) |
| **Single fork** | Profile pollution from earlier benchmarks in the same JVM | `@Fork(n)` runs each benchmark in fresh JVMs |
| **Shared state in threads** | False sharing, contention | `@State(Scope.Thread)`, `@Threads` |
| **Branch/type profile pollution** | Megamorphic call site caused by other benchmarks | Fork; test with realistic type mix |
| **Unrealistic data** | Sorted data, tiny working set fits in cache | Randomized data in `@Setup`, realistic sizes |
| **GC noise / allocation** | Allocation cost distorts | Add `-prof gc` to see `gc.alloc.rate.norm` |

### 3. Dead-code elimination and `Blackhole`

```java
import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.infra.Blackhole;

@State(Scope.Thread)
public class DceBenchmark {

    double x = 42.0;   // non-final: prevents constant folding

    @Benchmark
    public void broken() {
        Math.log(x);                 // result discarded: may be eliminated
    }

    @Benchmark
    public double correctReturn() {
        return Math.log(x);          // implicit Blackhole
    }

    @Benchmark
    public void correctMultiple(Blackhole bh) {
        bh.consume(Math.log(x));
        bh.consume(Math.log(x + 1));
    }
}
```

### 4. Modes and state scopes

| Annotation | Choices |
| :--- | :--- |
| `@BenchmarkMode` | `Throughput` (ops/time), `AverageTime`, `SampleTime` (percentiles), `SingleShotTime` (cold start), `All` |
| `@State` | `Scope.Thread` (private per thread), `Scope.Benchmark` (shared), `Scope.Group` |
| `@Setup`/`@TearDown` | `Level.Trial`, `Level.Iteration`, `Level.Invocation` (avoid invocation level for fast methods, adds overhead) |

### 5. Useful command-line options

```bash
# 3 forks, 5 warm-up and 10 measurement iterations, JSON output
java -jar target/benchmarks.jar StringConcat -f 3 -wi 5 -i 10 -rf json -rff result.json

# GC profiler: allocation per operation
java -jar target/benchmarks.jar StringConcat -prof gc

# Stack profiler and async-profiler integration
java -jar target/benchmarks.jar StringConcat -prof async:libPath=/opt/async-profiler/lib/libasyncProfiler.so;output=flamegraph

# Pass JVM flags to forks
java -jar target/benchmarks.jar StringConcat -jvmArgs "-Xms2g -Xmx2g -XX:+UseG1GC"
```

### 6. Common mistakes

- Benchmarking from the IDE with other apps running; use a quiet machine, pin CPU, disable turbo/power saving for serious measurement.
- Comparing scores with overlapping error bars as if one is "faster".
- Benchmarking `ArrayList` vs `LinkedList` with 10 elements and generalizing.
- Optimizing for a microbenchmark that is not in the hot path of the application (verify with a profiler first).

## 🔴 Senior Level

### 1. Understanding what JMH does under the hood

JMH generates code around your `@Benchmark` method: a loop calling the method in `@Fork` JVMs, with infrastructure to prevent inlining of the harness into the benchmark, handle `Blackhole`, and control state. `@CompilerControl(CompilerControl.Mode.DONT_INLINE)` helps isolate a method's cost; the opposite (`INLINE`) shows costs when inlined. Inspect generated code in `target/generated-sources`.

### 2. Measuring what matters: percentiles and contention

Use `Mode.SampleTime` for a latency distribution:

```java
@BenchmarkMode(Mode.SampleTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Threads(8)
@State(Scope.Benchmark)
public class MapContentionBenchmark {

    java.util.Map<Integer, Integer> chm = new java.util.concurrent.ConcurrentHashMap<>();
    java.util.Map<Integer, Integer> sync =
            java.util.Collections.synchronizedMap(new java.util.HashMap<>());

    @Benchmark public Integer concurrentHashMap() {
        int k = java.util.concurrent.ThreadLocalRandom.current().nextInt(1024);
        return chm.merge(k, 1, Integer::sum);
    }

    @Benchmark public Integer synchronizedMap() {
        int k = java.util.concurrent.ThreadLocalRandom.current().nextInt(1024);
        return sync.merge(k, 1, Integer::sum);
    }
}
```

The output lists p0.00, p50, p90, p99, p99.9, p100, showing tail behavior, not just the mean.

### 3. Pitfalls that survive JMH

- **Profile pollution & megamorphism:** if a benchmark only ever sees one implementation type at an interface call, C2 inlines it monomorphically, which is unrealistically fast. Feed realistic type mixes.
- **Escape analysis / scalar replacement:** allocations may vanish in the benchmark but not in production where objects escape. Check with `-prof gc` (zero `gc.alloc.rate.norm` is a hint).
- **Hardware effects:** CPU frequency scaling, NUMA, cache sizes, SMT noisy neighbors, cloud steal time. Use dedicated hardware, `taskset`/`numactl`, repeat on a second machine.
- **Coordinated measurement bias:** a loop around fast methods measures throughput of a hot loop, not cold-path latency. Use `SingleShotTime` for startup/cold paths.
- **Lack of end-to-end validity:** a 20% microbenchmark win might be 0.1% of request time. Always map back to the profile.

### 4. Comparing results properly

Treat results as distributions. Use enough forks (≥ 3) so inter-JVM variance is included in the confidence interval; JMH's error is within-fork only per fork aggregated. For decisions, use significance tools (JMH visualizer, `jmh-compare`, or bootstrap in a notebook). Report units, JVM version/flags, CPU model.

### 5. JMH in CI

Use `-rf json`, store results as build artifacts, and compare to the main branch baseline with a tolerance (e.g. fail at > 10% regression on a stable dedicated runner). Shared CI runners are noisy: use relative comparisons within the same job (baseline and candidate run back-to-back) rather than absolute thresholds. See [How to catch performance regressions in CI](22.%20How%20to%20catch%20performance%20regressions%20in%20CI.md).

### 6. When NOT to use JMH

Whole-request behavior (I/O, DB, GC across heap sizes, contention at scale) belongs to load testing and profiling, not microbenchmarks. Use JMH for algorithms, data structures, serialization libraries, parsing, and tight utility code.

## 🎯 Interview Cheat Sheet

### 30-second elevator pitch
"Hand-rolled timing loops are unreliable because of JIT warm-up, dead-code elimination and constant folding. JMH handles forks, warm-up and measurement iterations, and gives `Blackhole` to consume results. I return values, use non-final `@State` inputs, run several forks, check with `-prof gc`, and confirm the benchmark reflects something hot in a real profile."

### Must-know bullets
- JMH annotations: `@Benchmark`, `@State`, `@Setup`, `@Warmup`, `@Measurement`, `@Fork`, `@Param`, `@BenchmarkMode`.
- DCE: consume results; constant folding: avoid `static final` inputs.
- Multiple forks defeat profile pollution.
- Error bars matter; overlapping results are not "faster".
- `-prof gc`, `-prof async` for insight.
- Microbenchmarks ≠ production performance.

### Common follow-up questions
1. What is dead-code elimination in the JIT?
2. Why do we need `@Fork`?
3. How does `Blackhole` work?
4. Why is `@Setup(Level.Invocation)` dangerous?
5. How would you benchmark startup time?

### 🚩 Red flags
- `System.nanoTime()` around a `for` loop as "benchmark".
- Ignoring warm-up.
- Publishing a ratio of two scores with no error margin.
- Choosing a library solely from a vendor microbenchmark.
