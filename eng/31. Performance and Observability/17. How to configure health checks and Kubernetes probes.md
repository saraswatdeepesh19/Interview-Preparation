# How to configure health checks and Kubernetes probes

---

## 🟢 Junior Level

Kubernetes uses three probes to manage containers:

| Probe | Question | On failure |
| --- | --- | --- |
| **startupProbe** | Has the app finished starting? | Keep waiting until `failureThreshold`, then restart; liveness/readiness are disabled until it succeeds |
| **livenessProbe** | Is the process healthy, or stuck beyond recovery? | **Restart** the container |
| **readinessProbe** | Can it serve traffic right now? | **Remove** the pod from Service endpoints (no restart) |

Spring Boot Actuator provides dedicated endpoints (enabled automatically when running on Kubernetes, or with `management.endpoint.health.probes.enabled=true`):
* `/actuator/health/liveness` — reflects `LivenessState` (`CORRECT` / `BROKEN`).
* `/actuator/health/readiness` — reflects `ReadinessState` (`ACCEPTING_TRAFFIC` / `REFUSING_TRAFFIC`).

```yaml
containers:
  - name: orders
    ports:
      - { name: http, containerPort: 8080 }
      - { name: management, containerPort: 8081 }
    startupProbe:
      httpGet: { path: /actuator/health/liveness, port: management }
      periodSeconds: 5
      failureThreshold: 36            # up to 3 minutes for slow starts
    livenessProbe:
      httpGet: { path: /actuator/health/liveness, port: management }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3             # 30 s of failures before restart
    readinessProbe:
      httpGet: { path: /actuator/health/readiness, port: management }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2
```

## 🟡 Middle Level

### What to include in each
* **Liveness**: only internal state that requires a restart to fix — e.g. a deadlocked event loop, an unrecoverable error. **Never** include databases, caches, or other services: if the DB blips, restarting every pod makes things worse (crash loops, reconnect storms, lost in-flight work).
* **Readiness**: things that make *this instance* unable to serve: still warming caches, draining during shutdown, an essential local dependency unavailable. Including a shared database here removes **all** pods at once when the DB is down — usually better to stay ready and return fast errors (circuit breakers) than to have zero endpoints and opaque 503s from the ingress. Include dependencies only if the instance is truly useless without them and partial availability isn't possible.

```yaml
management:
  server:
    port: 8081
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState, cacheWarmup    # custom indicator, not the shared DB
```

### Controlling availability states from code

```java
@Component
class CacheWarmup implements ApplicationListener<ApplicationReadyEvent> {
    private final ApplicationEventPublisher events;
    private final ApplicationContext context;
    // ...
    @Override
    public void onApplicationEvent(ApplicationReadyEvent e) {
        AvailabilityChangeEvent.publish(context, ReadinessState.REFUSING_TRAFFIC);
        warmTopProducts();                                         // load hot data before taking traffic
        AvailabilityChangeEvent.publish(context, ReadinessState.ACCEPTING_TRAFFIC);
    }
}

// Mark liveness broken on an unrecoverable condition
AvailabilityChangeEvent.publish(context, LivenessState.BROKEN);
```

## 🔴 Senior Level

### Probe timing math
* Restart time after a real hang ≈ `periodSeconds × failureThreshold` (+ timeout): 10 s × 3 = ~30 s.
* JVM services can have long **GC pauses** or CPU throttling under load; a liveness `timeoutSeconds: 1` with `failureThreshold: 1` restarts healthy-but-busy pods during traffic peaks — a self-inflicted outage. Be generous with liveness, strict with readiness.
* Probes run on the kubelet; if the management endpoint shares the request thread pool with saturated application traffic, probes time out exactly when the app is overloaded. A **separate management port** (its own connector/thread pool) avoids that.

### Graceful shutdown sequence
1. Pod gets `SIGTERM` (or `preStop` runs first).
2. Spring marks readiness `REFUSING_TRAFFIC`; with `server.shutdown=graceful` it stops accepting new connections and waits for in-flight requests (`spring.lifecycle.timeout-per-shutdown-phase`).
3. **Endpoint removal is asynchronous**: kube-proxy, ingress controllers and cloud load balancers need seconds to stop sending traffic. Add `preStop: sleep 5–10` so traffic drains before the server closes.
4. `terminationGracePeriodSeconds` must exceed preStop + graceful shutdown time, or the kubelet sends `SIGKILL`.

```yaml
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 10"] }
terminationGracePeriodSeconds: 45
```

### Startup optimization and probes
* Prefer **startupProbe** over a huge `initialDelaySeconds` on liveness: fast starts become ready quickly, slow starts aren't killed.
* Reduce startup time (CDS/AppCDS, lazy initialization of non-critical beans, fewer auto-configurations, Spring AOT, CRaC or native images where appropriate) — faster starts mean faster scaling and recovery.
* With HPA scaling, pods that receive traffic while JIT-cold show high latency; readiness can gate on a warm-up phase (synthetic requests) for latency-sensitive services.

### Beyond Kubernetes probes
* Load balancers (ALB/NLB target groups) have their own health checks — point them at readiness and align thresholds.
* Deep "dependency health" belongs in monitoring (synthetic checks, SLO alerts), not in probes that trigger automated restarts or traffic removal.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Startup probes protect slow starts, liveness restarts truly stuck processes, and readiness removes instances from traffic without restarting. With Spring Boot I use `/actuator/health/liveness` and `/readiness` on a separate management port, keep external dependencies out of liveness (and usually out of readiness), control readiness during warm-up and shutdown, and combine graceful shutdown with a preStop delay and an adequate termination grace period.

**Must know:**
* Probe semantics and failure actions.
* Actuator health groups and availability states.
* Why DB checks in liveness cause cascading restarts.
* Timing: period × threshold; GC pauses; separate management port.
* Graceful shutdown + preStop + `terminationGracePeriodSeconds`.

**Common follow-ups:**
* All pods restarted when the database failed over — why?
* How do you warm caches before receiving traffic?
* Why do we still get 502s during deploys?

**Red flags:** one `/health` endpoint with every dependency for all probes; aggressive liveness timeouts; no preStop delay.
