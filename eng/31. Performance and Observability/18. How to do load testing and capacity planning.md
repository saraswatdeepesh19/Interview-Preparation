# How to do load testing and capacity planning

---

## 🟢 Junior Level

* **Load testing** — simulate realistic traffic to measure how a system behaves (latency, throughput, errors, resource usage) at expected and higher loads.
* **Capacity planning** — use those measurements plus traffic forecasts to decide how many instances, database resources and headroom you need — before users find the limits for you.

### Types of performance tests

| Test | Load profile | Question |
| --- | --- | --- |
| **Smoke** | Tiny load | Does the test script and environment work? |
| **Load** | Expected peak | Do we meet SLOs at normal peak? |
| **Stress** | Increase until failure | Where and how does it break? |
| **Spike** | Sudden jump (10× in seconds) | Does autoscaling/backpressure cope? |
| **Soak / endurance** | Normal load for hours | Leaks, GC degradation, connection exhaustion over time? |
| **Breakpoint** | Ramp continuously | What's the maximum sustainable throughput? |

### Popular tools
Gatling (Java/Kotlin/Scala DSL, great for JVM teams), k6 (JavaScript scripting, CLI-friendly), JMeter (GUI, mature), Locust (Python), plus cloud runners for distributed load.

```java
// Gatling (Java DSL)
public class CheckoutSimulation extends Simulation {
    HttpProtocolBuilder http = http.baseUrl("https://staging.shop.internal")
            .acceptHeader("application/json");

    ScenarioBuilder browseAndBuy = scenario("browse and buy")
            .exec(http("list products").get("/api/products?page=0").check(status().is(200)))
            .pause(Duration.ofSeconds(1), Duration.ofSeconds(3))                   // think time
            .exec(http("checkout").post("/api/checkout")
                    .body(StringBody("{\"sku\":\"A1\",\"qty\":1}")).asJson()
                    .check(status().is(201)));

    {
        setUp(browseAndBuy.injectOpen(
                    rampUsersPerSec(10).to(200).during(Duration.ofMinutes(5)),     // ramp to 200 new users/s
                    constantUsersPerSec(200).during(Duration.ofMinutes(15))))
            .protocols(http)
            .assertions(global().responseTime().percentile(99.0).lt(800),
                        global().failedRequests().percent().lt(0.1));
    }
}
```

## 🟡 Middle Level

### Make the test realistic
* **Traffic mix** from production analytics (e.g. 70% browse, 20% search, 8% cart, 2% checkout), not one endpoint hammered in isolation.
* **Open vs closed workload models**: real users arrive independently of your response time (open model: arrivals per second). A closed model (fixed number of virtual users looping) slows its arrival rate when the system slows — hiding overload (**coordinated omission**). Prefer open models (`injectOpen`, k6 `constant-arrival-rate`).
* **Data**: production-like data volume and distribution (cache hit ratios and query plans change with data size), unique users/IDs to avoid unrealistic cache hits.
* **Environment**: same instance types, JVM flags, limits, and dependencies as production (or a proportionally scaled copy); otherwise results are guesswork.
* **Warm-up**: JIT compilation and caches need minutes; exclude warm-up from measurements.

### What to record
* Client side: throughput, latency percentiles (p50/p95/p99/max), error rates by type.
* Server side: CPU, heap/GC, connection pools, thread pools, DB metrics (active queries, locks, IOPS), downstream latencies — the USE metrics that explain the bottleneck.
* The **knee point**: where latency rises sharply while throughput stops growing.

## 🔴 Senior Level

### From test results to capacity
1. Find max sustainable throughput per instance at SLO (e.g. 450 req/s per pod with p99 < 800 ms at 70% CPU).
2. Forecast peak load (seasonality, campaigns, growth): e.g. 6,000 req/s Black Friday peak.
3. Required instances = peak / per-instance capacity / target utilization headroom → 6,000 / 450 ≈ 14 pods; add N+1 for zone loss and deployment surges → plan 18–20.
4. Check shared resources scale with it: 20 pods × Hikari pool 10 = 200 DB connections — does the database have CPU and `max_connections` for that? Often the database, not the app tier, is the real limit.
5. Validate with a test at the planned peak, and set autoscaling bounds and alerts accordingly.

### Little's law for sanity checks
`concurrency = throughput × latency`. At 6,000 req/s and 120 ms average latency, ~720 requests are in flight; with platform threads you need that many request threads across the fleet (or virtual threads), plus enough DB connections for the portion of time spent in the database.

### Testing practices that find real problems
* **Soak tests** reveal leaks (heap creeping after each GC, growing thread counts, file descriptors, connection leaks with `leakDetectionThreshold` warnings), log volume issues and slow degradation.
* **Spike tests** reveal autoscaling lag (HPA reacts in ~1 min, node provisioning in minutes), cold JIT, connection storms, and whether rate limiting/load shedding works.
* **Failure under load**: kill a pod, fail over the DB, add latency to a dependency during a load test — resilience patterns behave differently when the system is busy.
* **Continuous performance testing**: run a smaller benchmark on every main-branch build and compare to a baseline to catch regressions early.

### Common mistakes
* Load generator becomes the bottleneck (CPU-bound, too few connections) — monitor the generator and distribute it.
* Testing through a CDN or cache that won't be hit in reality, or skipping auth flows.
* Reporting averages; ignoring errors ("throughput was great" while 10% returned 500).
* Running once — results vary; repeat and compare distributions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I load-test with realistic traffic mixes, production-like data and open workload models to avoid coordinated omission, measuring client percentiles and server USE metrics to find the knee point and bottleneck. I run load, stress, spike and soak tests, then turn per-instance capacity at SLO plus forecasts into instance counts with headroom for zone loss, check shared resources like database connections, and validate with Little's law.

**Must know:**
* Load vs stress vs spike vs soak vs breakpoint tests.
* Open vs closed workload model; coordinated omission.
* Warm-up, realistic data and environment.
* Capacity formula with headroom and N+1; DB as the shared bottleneck.
* Little's law.

**Common follow-ups:**
* How do you know the load generator isn't the bottleneck?
* What would a soak test reveal that a load test doesn't?
* How many pods for Black Friday?

**Red flags:** testing one endpoint in isolation; reporting average latency; tiny staging data sets.
