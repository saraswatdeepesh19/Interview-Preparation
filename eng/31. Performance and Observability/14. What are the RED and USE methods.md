# What are the RED and USE methods

---

## 🟢 Junior Level

Two simple checklists tell you **what to measure** so you can find problems quickly instead of staring at hundreds of graphs.

### RED — for request-driven services (Tom Wilkie)
For every service (and ideally every endpoint):
* **R**ate — requests per second.
* **E**rrors — failed requests per second (or error ratio).
* **D**uration — latency distribution (p50, p95, p99), not averages.

RED answers: *"Are my users having a bad time?"*

### USE — for resources (Brendan Gregg)
For every resource (CPU, memory, disk, network, but also thread pools, connection pools, queues):
* **U**tilization — % of time/capacity the resource is busy.
* **S**aturation — how much work is waiting (queue length, run-queue, pending acquisitions).
* **E**rrors — error events (failed allocations, I/O errors, rejected tasks).

USE answers: *"Which resource is the bottleneck?"*

| Use RED for | Use USE for |
| --- | --- |
| HTTP/gRPC endpoints, message consumers, DB queries as seen by the caller | CPU, memory, disks, NICs, JVM heap, Hikari pool, executors, Kafka partitions |

## 🟡 Middle Level

### RED with Spring Boot metrics (PromQL)

```promql
# Rate
sum by (uri) (rate(http_server_requests_seconds_count{application="orders"}[5m]))

# Errors (ratio)
sum by (uri) (rate(http_server_requests_seconds_count{application="orders", outcome="SERVER_ERROR"}[5m]))
/
sum by (uri) (rate(http_server_requests_seconds_count{application="orders"}[5m]))

# Duration p99 (requires histogram buckets)
histogram_quantile(0.99, sum by (le, uri) (rate(http_server_requests_seconds_bucket{application="orders"}[5m])))
```

Apply the same three to Kafka consumers (records consumed/s, failed records, processing time) and outgoing calls (`http_client_requests_seconds`).

### USE for JVM-level resources

| Resource | Utilization | Saturation | Errors |
| --- | --- | --- | --- |
| CPU | `process_cpu_usage` | Load average / run queue, CFS throttling (`container_cpu_cfs_throttled_seconds_total`) | — |
| Heap | `jvm_memory_used_bytes` after GC / max | GC pause time, allocation rate, GC frequency | `OutOfMemoryError` |
| JDBC pool (Hikari) | `hikaricp_connections_active / max` | `hikaricp_connections_pending`, acquire time | `hikaricp_connections_timeout_total` |
| Thread pool | active / max threads | `executor_queued_tasks` | `executor_rejected_tasks` (Spring/Micrometer executor metrics) |
| Disk | % busy, used % | I/O wait, queue depth | I/O errors |
| Network | bandwidth used | retransmits, socket backlog | connection errors |

### Using them together during an incident
1. RED dashboard shows checkout p99 jumped from 300 ms to 4 s, errors rising.
2. USE dashboard for the checkout service: CPU fine, but Hikari `pending` = 40 and acquire time = 3 s → the pool is saturated.
3. Drill down: why are connections held longer? Slow query traces or a downstream call inside a transaction.

## 🔴 Senior Level

### Why saturation matters most
Utilization alone misleads: a pool at 80% utilization looks healthy, but if requests arrive in bursts, queueing theory says latency grows sharply as utilization approaches 100% (for an M/M/1 queue, waiting time ∝ ρ / (1 − ρ): at 50% → 1×, 80% → 4×, 90% → 9×, 95% → 19× service time). **Saturation** metrics (pending acquisitions, queue length, CPU throttling) show the queueing directly and are usually the best alerting signal for resources.

### Hidden resources to apply USE to
* **Container CPU limits** — cgroup throttling causes latency spikes even when average CPU is low; watch `nr_throttled` / throttled seconds. Many JVM services perform better with CPU requests and no hard limit, or limits sized for GC and JIT bursts.
* **File descriptors / ephemeral ports** — `process_files_open_files / process_files_max_files`; port exhaustion from not reusing HTTP connections.
* **Locks** — lock contention is saturation: JFR `jdk.JavaMonitorEnter` events, `jdk.ThreadPark`.
* **Kafka consumer partitions** — utilization = processing time / poll interval; saturation = lag.
* **Downstream rate limits and quotas** — 429 rates are errors of a shared resource.

### Building dashboards that scale
* One **RED overview** per service (top: rate/errors/duration with SLO lines), then **USE panels** for its key resources, then **dependencies** (RED of each outgoing client).
* Standardize via templates (Grafana dashboards-as-code, jsonnet/Grafonnet) so every service looks the same; on-call engineers navigate unfamiliar services quickly.
* Pair with the **Four Golden Signals** (Google SRE: latency, traffic, errors, saturation) — essentially RED plus saturation.

### Alerting
Alert on **symptoms** (RED vs SLO, via burn-rate alerts) for paging; use USE metrics for **diagnosis** and for capacity tickets (e.g. pool saturation > 0 for 15 minutes), not for waking people at night unless they predict imminent user impact (disk 95% full).

## 🎯 Interview Cheat Sheet

**30-second pitch:** RED — rate, errors, duration — measures request-driven services from the user's point of view; USE — utilization, saturation, errors — finds which resource is the bottleneck, including JVM pools, executors and container CPU. I page on RED symptoms against SLOs and use USE for diagnosis, paying most attention to saturation because queueing makes latency explode near full utilization.

**Must know:**
* RED vs USE and when to use each.
* PromQL for rate, error ratio, p99 from histograms.
* USE table for CPU, heap, Hikari, executors, disks.
* Queueing: latency vs utilization curve.
* Container CPU throttling as saturation.

**Common follow-ups:**
* Your p99 doubled but CPU is at 30% — where do you look?
* What's the difference with the Four Golden Signals?
* Which of these would you alert on?

**Red flags:** averages for duration; alerting on CPU usage alone; no saturation metrics for pools.
