# Trade-offs of stored procedures triggers views and materialized views

---

## 🟢 Junior Level

Databases can hold logic and derived data, not just tables:

| Object | What it is | Typical use |
| --- | --- | --- |
| **View** | A saved query; evaluated on each access | Simplify complex joins, expose a stable read interface, restrict columns |
| **Materialized view** | A query whose **result is stored** and refreshed explicitly | Expensive aggregates for dashboards/reports |
| **Stored procedure / function** | Code (PL/pgSQL, SQL) running inside the database | Set-based data processing close to the data, bulk operations |
| **Trigger** | Function run automatically on INSERT/UPDATE/DELETE | Audit trails, `updated_at` maintenance, enforcing invariants, sync of derived data |

```sql
-- View: reusable read model
create view customer_order_stats as
select c.id, c.name, count(o.id) as orders, coalesce(sum(o.total), 0) as revenue
from customer c left join orders o on o.customer_id = c.id and o.status = 'PAID'
group by c.id, c.name;

-- Materialized view: precomputed daily revenue
create materialized view daily_revenue as
select date_trunc('day', created_at at time zone 'Europe/Berlin') as day, sum(total) as revenue
from orders where status = 'PAID'
group by 1;
create unique index on daily_revenue (day);              -- required for CONCURRENTLY refresh
refresh materialized view concurrently daily_revenue;     -- readers aren't blocked during refresh
```

## 🟡 Middle Level

### Triggers: useful, but invisible
A classic safe use: maintaining `updated_at` and audit history regardless of which application writes:

```sql
create or replace function set_updated_at() returns trigger as $$
begin
  new.updated_at := now();
  return new;
end $$ language plpgsql;

create trigger orders_updated_at
before update on orders
for each row execute function set_updated_at();
```

Risks: logic hidden from application developers ("why did this column change?"), surprising performance costs on bulk operations (row-level triggers fire per row), cascading triggers that are hard to reason about, and ORMs not knowing the database changed values (refresh entities or use `@Generated`).

### Stored procedures: pros and cons
**Pros**: fewer round trips for set-based operations, data never leaves the database, consistent logic for all clients, powerful for ETL/batch jobs.
**Cons**: harder to test, debug, version and deploy than application code; vendor lock-in (PL/pgSQL vs T-SQL vs PL/SQL); scaling business logic on the database tier (the hardest tier to scale); fewer engineers comfortable maintaining it.

A pragmatic middle ground: keep business rules in the application, use SQL functions for **data-centric** operations (bulk transformations, complex reporting queries, partition maintenance), and manage them as migrations with tests.

### Views as an API
Views decouple consumers (reporting tools, other services' read access, legacy integrations) from table structure changes — rename columns in the table and keep the view's shape stable. Security barrier views and column-level privileges can restrict what's visible.

## 🔴 Senior Level

### Materialized view operations
* `REFRESH MATERIALIZED VIEW` recomputes **everything** — costly for large aggregates; `CONCURRENTLY` avoids blocking readers but needs a unique index and is slower (computes a diff).
* PostgreSQL has no built-in incremental refresh; alternatives: summary tables maintained incrementally (by triggers, CDC, or periodic delta jobs), TimescaleDB continuous aggregates, the `pg_ivm` extension, or dedicated OLAP stores.
* Schedule refreshes (pg_cron, application scheduler) and expose staleness (`last_refreshed_at`) to users.

### Performance details
* Plain views are inlined into queries — no performance cost by themselves, but stacked views can hide expensive joins and prevent good plans; read `EXPLAIN` of the final query.
* Functions marked `IMMUTABLE`/`STABLE`/`VOLATILE` affect optimization (inlining, index usage in expressions); mislabeling causes wrong results or slow plans.
* Statement-level triggers with **transition tables** (`REFERENCING NEW TABLE AS new_rows`) process bulk changes set-based instead of per row — much faster for audit or summary maintenance.
* Triggers run in the same transaction: a slow trigger slows every write and holds locks longer.

### Architectural guidance
* In **microservices**, database logic shared across services (one schema read and written by many) is an anti-pattern; each service owns its schema, and views/procedures are internal implementation details of that service.
* **Event publishing via triggers** (writing to an outbox table in a trigger) is acceptable for capturing changes from legacy writers, but prefer explicit outbox writes in the application or CDC (Debezium reading the WAL) — CDC has zero write-path overhead and captures everything.
* **Versioning**: manage views, functions and triggers in migrations (Flyway repeatable migrations `R__views.sql` are a good fit — re-applied when their checksum changes).
* **Testing**: integration tests with Testcontainers against the real database engine; pgTAP for unit-testing SQL functions.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Views are saved queries that simplify and stabilize reads at no storage cost; materialized views store results for expensive aggregates but need explicit, often full refreshes, with `CONCURRENTLY` requiring a unique index. Stored procedures reduce round trips for data-heavy operations but are harder to test, version and scale; triggers enforce cross-cutting rules like audit or `updated_at` for every writer but hide logic and cost per-row overhead. I keep business rules in the application, use database logic for data-centric tasks, manage it via migrations, and prefer CDC over triggers for event capture.

**Must know:**
* View vs materialized view; refresh semantics; unique index for concurrent refresh.
* Trigger uses and risks; statement-level triggers with transition tables.
* Stored procedure pros/cons; volatility categories.
* Repeatable migrations for views/functions; pgTAP/Testcontainers.
* Microservice schema ownership; CDC vs trigger-based capture.

**Common follow-ups:**
* How would you keep a dashboard aggregate fresh?
* Should business rules live in stored procedures?
* Why did a bulk update become 50× slower after adding a trigger?

**Red flags:** core business logic spread across triggers; materialized views refreshed every minute on huge tables; shared database procedures across services.
