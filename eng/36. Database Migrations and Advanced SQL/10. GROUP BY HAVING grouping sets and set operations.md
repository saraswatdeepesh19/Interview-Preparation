# GROUP BY HAVING grouping sets and set operations

---

## 🟢 Junior Level

* **`GROUP BY`** collapses rows with the same key into one row per group and lets you compute **aggregates** (`count`, `sum`, `avg`, `min`, `max`).
* **`WHERE`** filters rows **before** grouping; **`HAVING`** filters **groups after** aggregation.

```sql
-- Revenue per customer in 2026, only customers above 1,000 EUR
select customer_id,
       count(*)        as orders,
       sum(total)      as revenue
from orders
where created_at >= '2026-01-01' and created_at < '2027-01-01'   -- row filter (can use indexes)
  and status = 'PAID'
group by customer_id
having sum(total) > 1000                                          -- group filter
order by revenue desc;
```

Logical evaluation order: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`. That's why you can't use a `SELECT` alias in `WHERE` (PostgreSQL allows aliases in `GROUP BY`/`ORDER BY`, not in `WHERE`/`HAVING`).

## 🟡 Middle Level

### Conditional aggregation (pivoting)

```sql
select date_trunc('month', created_at) as month,
       count(*) filter (where status = 'PAID')      as paid,
       count(*) filter (where status = 'CANCELLED') as cancelled,
       sum(total) filter (where status = 'PAID')    as revenue
from orders
group by 1
order by 1;
```

`FILTER (WHERE ...)` is standard SQL (PostgreSQL, SQLite); elsewhere use `sum(case when status = 'PAID' then total end)`.

### Grouping sets, ROLLUP and CUBE
Compute several groupings in **one** pass — e.g. totals by region and category, subtotals per region, and a grand total:

```sql
select region, category, sum(total) as revenue,
       grouping(region, category) as level        -- bitmask: which columns are aggregated away
from sales
group by rollup (region, category);
-- rows: (region, category), (region, NULL) subtotals, (NULL, NULL) grand total

group by cube (region, category)                   -- all combinations, including (NULL, category)
group by grouping sets ((region, category), (category), ())   -- exactly the sets you list
```

Use `grouping()` (not `IS NULL`) to distinguish "subtotal row" from "real NULL value in the data".

### Set operations

| Operation | Result | Duplicates |
| --- | --- | --- |
| `UNION` | Rows in either query | Removed (requires sort/hash) |
| `UNION ALL` | Rows in either query | Kept (cheaper — use it unless you need dedup) |
| `INTERSECT [ALL]` | Rows in both | |
| `EXCEPT [ALL]` (`MINUS` in Oracle) | Rows in the first but not the second | |

```sql
-- Reconciliation: payments recorded by us but missing at the provider
select payment_id, amount from our_payments where day = '2026-10-15'
except
select payment_id, amount from provider_settlements where day = '2026-10-15';
```

Columns must match in number and compatible types; names come from the first query.

## 🔴 Senior Level

### Performance of aggregation
* **HashAggregate vs GroupAggregate** (PostgreSQL): hashing groups in memory (needs `work_mem`; spills to disk in PG 13+ when exceeded) vs sorting first (cheap if an index provides order). `EXPLAIN (ANALYZE, BUFFERS)` shows which, and whether it spilled (`Disk Usage`).
* **Index-only scans** can feed aggregates like `count(*)` over an index range when the visibility map is up to date (autovacuum matters).
* **Partial aggregation in parallel** — large aggregates use parallel workers (`Partial HashAggregate` + `Finalize`).
* `count(distinct x)` is expensive (sort/hash per group); approximate with HyperLogLog (`postgresql-hll` extension, or analytics stores) when exactness isn't required.

### Pre-aggregation for dashboards
Aggregating billions of rows on each dashboard load is wasteful:
* **Materialized views** refreshed periodically (`REFRESH MATERIALIZED VIEW CONCURRENTLY` with a unique index).
* **Rollup tables** maintained incrementally (daily totals updated by a job or by triggers/CDC).
* **Columnar/OLAP stores** (ClickHouse, BigQuery, TimescaleDB continuous aggregates) for analytics workloads.

### Subtle correctness issues
* **Non-aggregated columns**: standard SQL requires every selected non-aggregate column to be in `GROUP BY` (or functionally dependent on the primary key — PostgreSQL allows `select c.id, c.name ... group by c.id`). MySQL with `ONLY_FULL_GROUP_BY` disabled returns arbitrary values — a classic source of wrong reports.
* **`avg` of integers** in some databases returns integers; cast to `numeric` for money and ratios. Never store money as float.
* **NULLs**: aggregates ignore NULLs (`count(col)` vs `count(*)`); `sum` over zero rows is NULL, not 0 — use `coalesce(sum(x), 0)`.
* **Time zones in date grouping**: `date_trunc('day', created_at)` on `timestamptz` uses the session time zone — set it explicitly (`date_trunc('day', created_at at time zone 'Europe/Berlin')`) so daily reports match business days.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `GROUP BY` produces one row per group with aggregates; `WHERE` filters rows before grouping and `HAVING` filters groups after. I use `FILTER` or `CASE` for conditional aggregation, `ROLLUP`, `CUBE` and `GROUPING SETS` with `grouping()` for subtotals in one pass, and set operations — preferring `UNION ALL` unless dedup is needed, `EXCEPT` for reconciliation. For performance I check hash vs group aggregate and spills, and pre-aggregate with materialized views or rollup tables for dashboards.

**Must know:**
* Logical query order; WHERE vs HAVING.
* `count(*)` vs `count(col)`; NULL behavior; `coalesce(sum(...), 0)`.
* `FILTER (WHERE ...)`; ROLLUP/CUBE/GROUPING SETS; `grouping()`.
* UNION vs UNION ALL; INTERSECT; EXCEPT.
* HashAggregate spills; materialized views; time zones in grouping.

**Common follow-ups:**
* Difference between WHERE and HAVING performance-wise?
* How do you produce subtotals and grand totals?
* Why does my daily revenue report differ from the business day?

**Red flags:** `UNION` where `UNION ALL` suffices; `HAVING` for row-level conditions; floats for money.
