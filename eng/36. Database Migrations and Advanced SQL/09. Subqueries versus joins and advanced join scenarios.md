# Subqueries versus joins and advanced join scenarios

---

## 🟢 Junior Level

A **join** combines rows from tables side by side; a **subquery** is a query nested inside another (in `WHERE`, `FROM`, `SELECT`). Many questions can be written either way:

```sql
-- Customers who placed at least one order: join (needs DISTINCT, joins multiply rows)
select distinct c.id, c.name
from customer c
join orders o on o.customer_id = c.id;

-- Same with a subquery: EXISTS stops at the first match per customer (a "semi-join")
select c.id, c.name
from customer c
where exists (select 1 from orders o where o.customer_id = c.id);

-- Customers who NEVER ordered: anti-join
select c.id, c.name
from customer c
where not exists (select 1 from orders o where o.customer_id = c.id);
```

### Rule of thumb
* Need columns from both tables → **join**.
* Only need to **filter** by existence in another table → `EXISTS` / `NOT EXISTS` (clear intent, no duplicates).
* Modern optimizers (PostgreSQL, MySQL 8, SQL Server, Oracle) usually transform both forms into the same plan — readability and correctness matter more than folklore.

## 🟡 Middle Level

### The `NOT IN` + NULL trap

```sql
-- If ANY orders.customer_id is NULL, this returns NO rows at all:
select * from customer where id not in (select customer_id from orders);
-- because "x NOT IN (1, 2, NULL)" evaluates to NULL (unknown), never TRUE.
```

Use `NOT EXISTS` (or `LEFT JOIN ... WHERE o.id IS NULL`) for anti-joins; they handle NULLs correctly.

### Correlated subqueries and `LATERAL`
A correlated subquery references the outer row and conceptually runs per row. `LATERAL` makes that explicit in `FROM` and can return multiple columns/rows — perfect for "top-N per group":

```sql
-- Latest 3 orders per customer
select c.id, c.name, o.id as order_id, o.created_at
from customer c
cross join lateral (
    select id, created_at
    from orders
    where customer_id = c.id
    order by created_at desc
    limit 3
) o;
-- With an index on orders(customer_id, created_at desc) this is 3 index reads per customer.
```

The alternative with window functions:

```sql
select * from (
  select o.*, row_number() over (partition by customer_id order by created_at desc) as rn
  from orders o
) t
where rn <= 3;
```

`LATERAL` wins when few groups are needed and an index exists; the window version wins when processing most rows anyway.

### Join types beyond inner/left

| Join | Returns |
| --- | --- |
| `INNER JOIN` | Matching pairs |
| `LEFT JOIN` | All left rows; NULLs where no match |
| `FULL OUTER JOIN` | All rows from both sides — useful for reconciliation ("in A but not B, in B but not A") |
| `CROSS JOIN` | Cartesian product — combining dimensions (dates × products) |
| Self-join | A table joined to itself (employees → managers, consecutive events) |
| Semi/anti-join | `EXISTS` / `NOT EXISTS` |

## 🔴 Senior Level

### Common correctness pitfalls
* **Filtering the outer side in `WHERE` turns a LEFT JOIN into an INNER JOIN**:

```sql
-- Wrong: customers without paid orders disappear
select c.id, count(o.id)
from customer c left join orders o on o.customer_id = c.id
where o.status = 'PAID'
group by c.id;

-- Right: put the condition in the ON clause
select c.id, count(o.id)
from customer c left join orders o on o.customer_id = c.id and o.status = 'PAID'
group by c.id;
```

* **Fan-out when joining two one-to-many relations**: joining `orders → lines` and `orders → payments` multiplies rows (lines × payments), inflating `sum()`s. Aggregate each relation in its own subquery/CTE first, then join the aggregates.
* **Aggregates over joins**: `count(*)` counts joined rows, `count(distinct o.id)` counts orders.

### How databases execute joins
* **Nested loop** — for each outer row, look up the inner (great with an index and few outer rows; terrible without an index).
* **Hash join** — build a hash table on the smaller input, probe with the larger (good for large unsorted inputs; needs memory: `work_mem` in PostgreSQL).
* **Merge join** — both inputs sorted on the join key (great when indexes provide order).

Reading `EXPLAIN ANALYZE` shows which one was chosen and whether row estimates were wrong — misestimates (often from correlated columns or stale statistics) cause nested loops over millions of rows.

### Range and inequality joins
Joins like "events within a session's time range" (`e.ts between s.start and s.end`) can't use hash joins; use B-tree/GiST indexes on ranges (`tstzrange` with `&&`/`@>` operators) or sort-based approaches. In PostgreSQL:

```sql
select s.id, count(*)
from sessions s
join events e on s.during @> e.ts          -- during is tstzrange; GiST index on s.during
group by s.id;
```

### Java/ORM perspective
JPA `JOIN FETCH` on multiple collections causes the fan-out problem (and Hibernate's `MultipleBagFetchException` for `List` bags); fetch one collection per query or use batch fetching. For complex reporting queries, native SQL or jOOQ with explicit joins and CTEs is clearer than forcing JPQL.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Joins combine columns from tables; subqueries filter or compute. For existence checks I use `EXISTS` and `NOT EXISTS` — avoiding the `NOT IN` NULL trap — `LATERAL` for top-N per group, and window functions as the alternative. I watch for WHERE conditions that turn left joins into inner joins, fan-out when joining multiple one-to-many relations, and I read `EXPLAIN ANALYZE` to see nested loop, hash or merge joins and row misestimates.

**Must know:**
* Semi-join/anti-join with EXISTS; `NOT IN` + NULL.
* `LATERAL` vs `row_number()` for top-N per group.
* Join types including FULL OUTER and self-joins.
* LEFT JOIN + WHERE pitfall; fan-out and aggregate-first.
* Nested loop vs hash vs merge join.

**Common follow-ups:**
* Is a subquery slower than a join?
* Find customers without orders.
* Why did my sum double after adding a join?

**Red flags:** `NOT IN` with nullable columns; `DISTINCT` to hide join duplicates; filters on the nullable side in WHERE.
