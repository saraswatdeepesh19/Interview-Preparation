# How to paginate at scale with keyset pagination

---

## 🟢 Junior Level

**Offset pagination** (`LIMIT 20 OFFSET 100000`) is easy but gets slower with every page: the database still reads and discards the first 100,000 rows. It also shows **duplicates or skips** when rows are inserted or deleted between page requests.

**Keyset pagination** (also called *seek* or *cursor* pagination) remembers the **last row's sort key** and asks for rows *after* it:

```sql
-- Page 1
select id, created_at, total
from orders
where customer_id = 42
order by created_at desc, id desc
limit 20;

-- Next page: continue after the last row of the previous page (created_at = '2026-10-01 10:15', id = 9876)
select id, created_at, total
from orders
where customer_id = 42
  and (created_at, id) < ('2026-10-01 10:15:00+00', 9876)   -- row-value comparison
order by created_at desc, id desc
limit 20;
```

With an index on `(customer_id, created_at desc, id desc)`, every page is a short index range scan — constant time whether it's page 1 or page 10,000.

## 🟡 Middle Level

### Rules for correct keysets
* The ordering must be **unique and deterministic** — add a tie-breaker (usually the primary key) to non-unique sort columns, or rows with equal `created_at` get skipped or repeated.
* The `WHERE` comparison must match the `ORDER BY` direction exactly.
* The index must match the order (`(customer_id, created_at desc, id desc)`), so the database can seek directly.
* Row-value comparisons `(a, b) < (x, y)` are supported in PostgreSQL and MySQL 8; elsewhere expand it: `a < x OR (a = x AND b < y)`.

### Opaque cursors in the API

```java
public record Cursor(Instant createdAt, long id) {
    // Keep FULL precision: PostgreSQL timestamptz has microseconds; truncating to millis
    // would make the next page skip or repeat rows created within the same millisecond.
    String encode() {
        return Base64.getUrlEncoder().withoutPadding()
                .encodeToString((createdAt + "|" + id).getBytes(StandardCharsets.UTF_8));   // ISO-8601 with micros
    }
    static Cursor decode(String token) {
        String[] parts = new String(Base64.getUrlDecoder().decode(token), StandardCharsets.UTF_8).split("\\|");
        return new Cursor(Instant.parse(parts[0]), Long.parseLong(parts[1]));
    }
}

@GetMapping("/api/customers/{id}/orders")
PageResponse<OrderDto> orders(@PathVariable long id,
                              @RequestParam(required = false) String after,
                              @RequestParam(defaultValue = "20") @Max(100) int limit) {
    Cursor c = after == null ? null : Cursor.decode(after);
    List<Order> rows = repo.page(id, c, limit + 1);                 // fetch one extra to know if there's a next page
    boolean hasNext = rows.size() > limit;
    List<Order> page = hasNext ? rows.subList(0, limit) : rows;
    String next = hasNext ? new Cursor(page.getLast().createdAt(), page.getLast().id()).encode() : null;
    return new PageResponse<>(page.stream().map(OrderDto::from).toList(), next);
}
```

Clients treat the cursor as opaque — you can change its internal format later (sign it with an HMAC if tampering matters).

### Spring Data support
Spring Data 3.1+ offers **`ScrollPosition`** and `Window<T>` for keyset scrolling:

```java
Window<Order> findFirst20ByCustomerIdOrderByCreatedAtDescIdDesc(long customerId, ScrollPosition position);

Window<Order> first = repo.findFirst20ByCustomerIdOrderByCreatedAtDescIdDesc(42, ScrollPosition.keyset());
Window<Order> next  = repo.findFirst20ByCustomerIdOrderByCreatedAtDescIdDesc(42, first.positionAt(first.size() - 1));
```

## 🔴 Senior Level

### Trade-offs

| | Offset | Keyset |
| --- | --- | --- |
| Deep pages | O(offset + limit) | O(limit) |
| Consistency under inserts/deletes | Duplicates/skips | Stable |
| Jump to page N / total pages | Easy | Not directly |
| Arbitrary sort columns | Easy | Needs an index per sort order |
| Implementation | Trivial | Cursor encoding, tie-breakers |

Use keyset for feeds, infinite scrolling, APIs over large collections, and **batch processing** (iterating a whole table in chunks: `where id > :last order by id limit 1000` — never `OFFSET`). Keep offset for small admin tables where "page 7 of 12" UX matters.

### Totals and "page N"
* Exact `count(*)` over large filtered sets is expensive (full scan of matching rows). Options: don't show totals; show "1,000+"; use estimates (`EXPLAIN` row estimates or `pg_class.reltuples` for whole tables); maintain counters.
* For "jump to a date", seek by the sort key (`where created_at < :date`), which keyset handles naturally.

### Sorting by user-chosen columns
Each allowed sort needs a deterministic key and ideally an index. Limit sorting options to a small allow-list; for search-like UIs with many sort/filter combinations, use a search engine (Elasticsearch/OpenSearch `search_after` is keyset pagination).

### NULLs and descending order
NULLs sort last by default for ASC (first for DESC) in PostgreSQL; cursor comparisons with NULL yield NULL (row excluded). Either make sort columns NOT NULL, coalesce them consistently (with a matching expression index), or handle NULL segments explicitly.

### Distributed and sharded data
In sharded stores, keyset pagination requires merging per-shard sorted streams (k-way merge) and a composite cursor containing positions per shard — or using global sort keys (time-ordered IDs like UUIDv7/Snowflake) so one key orders everything.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Offset pagination reads and discards all skipped rows and shifts under concurrent writes, so for large or changing collections I use keyset pagination: order by a unique, deterministic key — sort column plus primary-key tie-breaker — seek with a row-value comparison after the last row, back it with a matching composite index, and expose an opaque cursor while fetching `limit + 1` to detect a next page. Spring Data's `ScrollPosition` and `Window` support it; totals and page jumps need alternatives.

**Must know:**
* Why OFFSET is O(offset) and inconsistent.
* Row-value comparison and matching index.
* Tie-breaker for uniqueness; NULL handling.
* Opaque cursors; `limit + 1`.
* Batch processing by key; Elasticsearch `search_after`.

**Common follow-ups:**
* How do you show the total number of results?
* How do you support multiple sort orders?
* How do you paginate backwards?

**Red flags:** `OFFSET 500000` in batch jobs; cursors without tie-breakers; exposing raw SQL values as cursors without validation.
