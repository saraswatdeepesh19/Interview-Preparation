# How window functions work in SQL

---

## 🟢 Junior Level

### 1. What is a window function?

A **window function** calculates a value for each row using a "window" of related rows — **without collapsing rows** the way `GROUP BY` does. Each input row stays in the output, and gets an extra computed column such as a rank, a running total or the previous row's value.

**Analogy:** `GROUP BY` is a class photo — one picture per class. A window function is a report card — every student still has a line, plus a column showing "rank in class".

### 2. Syntax

```sql
function_name(args) OVER (
    PARTITION BY column_list     -- optional: restart for each group
    ORDER BY column_list         -- optional: order inside the group
    frame_clause                 -- optional: which rows around the current one
)
```

### 3. Example data

```sql
CREATE TABLE sale (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    seller    TEXT           NOT NULL,
    sold_on   DATE           NOT NULL,
    amount    NUMERIC(10, 2) NOT NULL
);
```

### 4. ROW_NUMBER, RANK, DENSE_RANK

```sql
SELECT seller, amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC) AS row_num,
       RANK()       OVER (ORDER BY amount DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY amount DESC) AS dense_rnk
FROM sale;
```

| amount | row_num | rnk | dense_rnk |
| :--- | :--- | :--- | :--- |
| 500 | 1 | 1 | 1 |
| 400 | 2 | 2 | 2 |
| 400 | 3 | 2 | 2 |
| 300 | 4 | 4 | 3 |

- `ROW_NUMBER` — always unique, ties broken arbitrarily.
- `RANK` — ties share a rank, then **gaps** appear (1, 2, 2, 4).
- `DENSE_RANK` — ties share a rank, **no gaps** (1, 2, 2, 3).

```mermaid
flowchart LR
    T[All rows] --> P[PARTITION BY seller]
    P --> O[ORDER BY sold_on]
    O --> F[Compute function per row]
    F --> R[Same number of rows out]
```

## 🟡 Middle Level

### 1. PARTITION BY: top-N per group

"Latest sale per seller":

```sql
SELECT *
FROM (
    SELECT s.*,
           ROW_NUMBER() OVER (PARTITION BY seller ORDER BY sold_on DESC, id DESC) AS rn
    FROM sale s
) x
WHERE rn = 1;
```

Window functions cannot appear in `WHERE`, so they are wrapped in a subquery or CTE. (PostgreSQL also offers `DISTINCT ON (seller) ... ORDER BY seller, sold_on DESC` as a shortcut.)

### 2. LAG and LEAD

Look at the previous / next row:

```sql
SELECT seller, sold_on, amount,
       LAG(amount)  OVER w AS prev_amount,
       LEAD(amount) OVER w AS next_amount,
       amount - LAG(amount, 1, 0) OVER w AS delta_vs_prev
FROM sale
WINDOW w AS (PARTITION BY seller ORDER BY sold_on);
```

`LAG(expr, offset, default)`. The named `WINDOW w` clause avoids repetition.

Gaps-and-islands / session detection:

```sql
SELECT user_id, event_at,
       event_at - LAG(event_at) OVER (PARTITION BY user_id ORDER BY event_at) AS gap
FROM events;
```

### 3. Running totals and moving averages

Aggregates become window functions with `OVER`:

```sql
SELECT sold_on, amount,
       SUM(amount) OVER (ORDER BY sold_on, id)                         AS running_total,
       AVG(amount) OVER (ORDER BY sold_on, id
                         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)     AS moving_avg_7
FROM sale;
```

### 4. The frame clause — the #1 source of bugs

When `ORDER BY` is present and no frame is given, the default is
`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. With `RANGE`, rows with **equal** ORDER BY values (peers) are included together, so a running total over a non-unique date jumps by the whole day's sum at once. Use `ROWS` and a unique tiebreaker for a true row-by-row running total:

```sql
SUM(amount) OVER (ORDER BY sold_on, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
```

Frame modes: `ROWS` (physical rows), `RANGE` (value distance, peers), `GROUPS` (peer groups; PG 11+). Offsets with `RANGE` need an ordering on a numeric/date column: `RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW`.

### 5. FIRST_VALUE, LAST_VALUE, NTILE, percent

```sql
SELECT seller, amount,
       FIRST_VALUE(amount) OVER (PARTITION BY seller ORDER BY sold_on) AS first_sale,
       LAST_VALUE(amount)  OVER (PARTITION BY seller ORDER BY sold_on
            ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)   AS last_sale,
       NTILE(4)     OVER (ORDER BY amount) AS quartile,
       PERCENT_RANK() OVER (ORDER BY amount) AS pct_rank
FROM sale;
```

`LAST_VALUE` with the default frame returns the *current* row's value — you must widen the frame as above.

### 6. Window functions with Spring Data JDBC / JPA native

```java
public interface SaleRepository extends JpaRepository<Sale, Long> {

    @Query(value = """
        SELECT seller, sold_on, amount,
               SUM(amount) OVER (PARTITION BY seller ORDER BY sold_on, id) AS running_total
        FROM sale
        WHERE sold_on >= :from
        ORDER BY seller, sold_on, id
        """, nativeQuery = true)
    List<SaleRunningTotal> runningTotals(@Param("from") LocalDate from);

    interface SaleRunningTotal {
        String getSeller();
        LocalDate getSoldOn();
        BigDecimal getAmount();
        BigDecimal getRunningTotal();
    }
}
```

HQL supports window functions since Hibernate 6 (`over(...)`), but native SQL is clearer for complex reporting.

## 🔴 Senior Level

### 1. Execution order

Logical order: `FROM → WHERE → GROUP BY → HAVING → WINDOW functions → SELECT list → DISTINCT → ORDER BY → LIMIT`. Consequences:

- Window functions see rows **after** `WHERE`/`GROUP BY`. Filtering by `WHERE` changes the window contents.
- You can use window functions on aggregated results: `SUM(SUM(amount)) OVER (ORDER BY month)`.
- You cannot filter on them in the same query level; use a CTE/subquery (or `QUALIFY` on engines that support it — not PostgreSQL).

```sql
SELECT date_trunc('month', sold_on) AS month,
       SUM(amount)                                             AS month_total,
       SUM(SUM(amount)) OVER (ORDER BY date_trunc('month', sold_on)) AS ytd_total,
       round(100.0 * SUM(amount) / SUM(SUM(amount)) OVER (), 1)      AS pct_of_all
FROM sale
GROUP BY 1
ORDER BY 1;
```

### 2. Performance

- A window with `PARTITION BY a ORDER BY b` needs rows sorted by `(a, b)`. An index on `(a, b)` lets PostgreSQL avoid the sort (`WindowAgg` over an `Index Scan`).
- Multiple window functions with the **same** `OVER` spec share one pass; different specs cause extra sorts. Group functions by identical window definitions (or use the named `WINDOW` clause) and minimise distinct specs.
- Large partitions are computed in memory or spilled to disk (`work_mem`); check `Sort Method: external merge` in `EXPLAIN (ANALYZE)`.
- Top-N per group over a huge table: `ROW_NUMBER` sorts everything. For a few groups with a supporting index, `LATERAL` + `LIMIT` is often much faster:

```sql
SELECT c.id, o.*
FROM customer c
CROSS JOIN LATERAL (
    SELECT * FROM orders o WHERE o.customer_id = c.id ORDER BY o.created_at DESC LIMIT 3
) o;
```

### 3. Idioms every senior should know

**De-duplicate keeping the newest row:**

```sql
DELETE FROM contact
WHERE id IN (
    SELECT id FROM (
        SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC, id DESC) rn
        FROM contact
    ) d WHERE rn > 1
);
```

**Gaps and islands (consecutive days):**

```sql
SELECT user_id, min(day) AS from_day, max(day) AS to_day, count(*) AS streak
FROM (
    SELECT user_id, day,
           day - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
    FROM (SELECT DISTINCT user_id, day FROM activity) a
) t
GROUP BY user_id, grp;
```

**Time-weighted / sessionization:** flag a new session where `gap > 30 min` using `LAG`, then `SUM(flag) OVER (PARTITION BY user ORDER BY ts)` to assign session ids.

**Percentiles:** `percentile_cont(0.95) WITHIN GROUP (ORDER BY latency)` is an *ordered-set aggregate*, not a window function, but combines with `FILTER`.

### 4. Pitfalls and edge cases

- `ORDER BY` inside `OVER` with ties and no tiebreaker → **non-deterministic** `ROW_NUMBER`; add a unique column.
- `NULL` ordering: `ORDER BY x DESC` puts NULLs first in PostgreSQL; use `NULLS LAST`.
- `COUNT(*) OVER ()` for total rows alongside a page of results forces computing all rows — costs the same as a count query; do not use it on huge result sets for pagination.
- Window functions disable some optimizations: a `LIMIT` cannot be pushed below a `WindowAgg`; predicates on the window result cannot be pushed into the scan. Filter before the window where semantics allow it (e.g. by `seller` or date partition key).
- `DISTINCT` + window + `ORDER BY` interplay: `DISTINCT` is applied after windows.
- Floating results: use `NUMERIC` to avoid drift in running totals.

### 5. Testing and correctness

Unit-test SQL with Testcontainers and golden data that includes ties, NULLs and single-row partitions, since those are where `RANK`/`LAG` bugs hide (first row `LAG` → NULL; supply a default).

## 🎯 Interview Cheat Sheet

**30-second pitch:** Window functions compute values across related rows while keeping every row: `ROW_NUMBER/RANK/DENSE_RANK` for ordering, `LAG/LEAD` for neighbouring rows, and `SUM/AVG OVER` with frames for running totals and moving averages. `PARTITION BY` restarts the calculation per group; `ORDER BY` and the frame define the window. Index `(partition, order)` columns to avoid sorts.

**Must-know bullets:**
- RANK has gaps, DENSE_RANK doesn't, ROW_NUMBER is unique.
- Default frame with ORDER BY is `RANGE ... CURRENT ROW` (includes peers) — use `ROWS` for running totals.
- `LAST_VALUE` needs an explicit full frame.
- Window functions can't be used in `WHERE`; wrap in CTE/subquery.
- Top-N per group: `ROW_NUMBER` or `LATERAL ... LIMIT`.
- Add tiebreakers for deterministic results.

**Common follow-up questions:**
- Difference between `GROUP BY` and window aggregate?
- How to get the 2nd highest salary per department?
- How would you compute a 7-day moving average?
- Why is my running total jumping?

**Red flags:**
- Using self-joins to emulate LAG on big tables.
- Not knowing frame defaults.
- Using `COUNT(*) OVER()` for pagination on millions of rows.
