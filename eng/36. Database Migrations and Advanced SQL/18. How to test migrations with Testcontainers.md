# How to test migrations with Testcontainers

---

## 🟢 Junior Level

Database migrations are code that runs **once per environment** against **real data** — a bad one can take production down or corrupt data. Testing them means:
1. Every migration **applies cleanly** to an empty database (new environments, CI).
2. Migrations apply on top of the **current production schema** (upgrade path).
3. The application's **entities match** the migrated schema.
4. Data migrations transform **existing data correctly**.

**Testcontainers** starts the same database engine and version as production in Docker, so tests catch dialect-specific problems that H2 would hide.

```java
@SpringBootTest
@Testcontainers
class MigrationsTest {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16.4-alpine");

    @Autowired Flyway flyway;

    @Test
    void allMigrationsApplyAndValidate() {
        // Spring Boot already ran flyway.migrate() at startup; validate checksums and pending state
        assertThat(flyway.info().pending()).isEmpty();
        flyway.validate();
    }
}
```

With `spring.jpa.hibernate.ddl-auto=validate`, the Spring context **fails to start** if entities don't match the migrated schema — a free compatibility test.

## 🟡 Middle Level

### Testing a data migration
Apply migrations up to the version **before** the change, insert representative data, apply the new migration, and assert the result:

```java
@Testcontainers
class V42SplitFullNameTest {
    @Container static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16.4-alpine");

    @Test
    void splitsFullNameIntoFirstAndLast() throws Exception {
        Flyway before = Flyway.configure().dataSource(db.getJdbcUrl(), db.getUsername(), db.getPassword())
                .target(MigrationVersion.fromVersion("41")).load();
        before.migrate();

        try (Connection c = DriverManager.getConnection(db.getJdbcUrl(), db.getUsername(), db.getPassword());
             Statement s = c.createStatement()) {
            s.execute("insert into customer(id, full_name) values (1, 'Ada Lovelace'), (2, 'Plato'), (3, null)");
        }

        Flyway.configure().dataSource(db.getJdbcUrl(), db.getUsername(), db.getPassword())
                .target(MigrationVersion.fromVersion("42")).load().migrate();

        JdbcTemplate jdbc = new JdbcTemplate(new SingleConnectionDataSource(db.getJdbcUrl(), db.getUsername(), db.getPassword(), true));
        assertThat(jdbc.queryForList("select first_name, last_name from customer order by id"))
            .extracting(r -> r.get("first_name"), r -> r.get("last_name"))
            .containsExactly(
                tuple("Ada", "Lovelace"),
                tuple("Plato", ""),                                    // edge cases are the point of the test
                tuple(null, null));                                    // null stays null
    }
}
```

Edge cases matter most: NULLs, empty strings, Unicode, very long values, duplicates that violate new constraints.

### Upgrade-path testing
Fresh installs and upgrades can diverge (e.g. someone edited a historical migration, or production has manual hotfixes). Test from a **snapshot of the production schema**:
* Dump the production schema (`pg_dump --schema-only`) plus Flyway history in CI as an artifact, restore it into a container, run pending migrations.
* Or keep a long-lived "pre-prod" database restored nightly from an anonymized production backup and run migrations there in the pipeline.

## 🔴 Senior Level

### Testing safety, not just correctness
A migration can be correct and still cause an outage:
* **Lock behavior**: run the migration against a container with **concurrent load** (a background thread doing inserts/updates) and assert the load doesn't block beyond a threshold — catches `ACCESS EXCLUSIVE` locks and non-concurrent index builds.
* **Duration on realistic volume**: seed millions of rows (`generate_series`) and measure migration time; backfills should be batched.
* **Lint rules**: run Squawk (PostgreSQL migration linter) in CI to flag risky statements (`ADD COLUMN ... DEFAULT` on old versions, `SET NOT NULL` without a check constraint, non-concurrent indexes, type changes).

```java
@Test
void addIndexDoesNotBlockWrites() throws Exception {
    seedOrders(2_000_000);
    ExecutorService writer = Executors.newSingleThreadExecutor();
    Future<Duration> maxWriteLatency = writer.submit(() -> measureInsertsFor(Duration.ofSeconds(20)));
    flywayTo("57").migrate();                                         // CREATE INDEX CONCURRENTLY ...
    assertThat(maxWriteLatency.get()).isLessThan(Duration.ofMillis(500));
}
```

### Backward compatibility tests
During rolling deployments, the **old application version** runs against the **new schema**. Test it:
* Check out the previous release's integration test suite (or its container image) and run it against the database migrated to the new version.
* Simpler heuristic gate: forbid destructive operations (`DROP`, `RENAME`, type changes) in the same release as code changes; require the expand/contract sequence.

### Speed and hygiene
* One container per test JVM (singleton) and **template databases** for parallel tests: migrate once into `template_db`, then `create database test_n template template_db` per test class in milliseconds.
* Reuse containers locally (`testcontainers.reuse.enable=true`), never in CI.
* Pin the exact database version and extensions (`postgis/postgis:16-3.4`), matching production.
* Test rollbacks you actually rely on (Liquibase rollback blocks, or "roll-forward" fix scripts) the same way.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I test migrations against the production database engine with Testcontainers: all migrations apply and validate, Hibernate `ddl-auto=validate` checks entities against the migrated schema, data migrations are tested by migrating to N−1, seeding edge-case data, applying N and asserting results, and upgrades are tested from a production schema snapshot. For safety I lint with Squawk, measure duration on realistic volumes, check locking under concurrent load, and verify the previous app version still works against the new schema.

**Must know:**
* Flyway `migrate`/`validate`/`info`, `target` versions in tests.
* `ddl-auto=validate` as a schema compatibility check.
* Data migration test pattern (N−1 → seed → N → assert).
* Upgrade-path testing from production schema snapshots.
* Lock/duration tests, Squawk, template databases.

**Common follow-ups:**
* How do you test a migration that backfills 100M rows?
* Why not use H2 for migration tests?
* How do you make sure old code works with the new schema?

**Red flags:** migrations tested only on empty databases; H2 compatibility mode; editing applied migrations to "fix" tests.
