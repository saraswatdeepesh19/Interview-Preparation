# Which index types does PostgreSQL offer

---

## 🟢 Junior Level

PostgreSQL has several index **access methods**, each suited to different data and operators:

| Type | Supports | Typical use |
| --- | --- | --- |
| **B-tree** (default) | `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN`, `IS NULL`, sorting, prefix `LIKE 'abc%'` (with `C` collation or `text_pattern_ops`) | Almost everything: IDs, foreign keys, timestamps, strings |
| **Hash** | `=` only | Rarely better than B-tree; WAL-logged since PG 10 |
| **GIN** (Generalized Inverted Index) | Containment/overlap: `@>`, `?`, `&&`, full-text `@@` | JSONB, arrays, full-text search, trigram `LIKE '%x%'` |
| **GiST** (Generalized Search Tree) | Geometric, range overlap `&&`, nearest-neighbor `<->`, exclusion constraints | PostGIS, `tstzrange`, booking overlaps |
| **SP-GiST** | Space-partitioned structures (quad-trees, radix trees) | IP addresses, points, prefix searches |
| **BRIN** (Block Range Index) | Ranges of values per block range | Huge append-only tables ordered by time/ID |

```sql
create index on orders (customer_id);                                    -- B-tree
create index on products using gin (attributes jsonb_path_ops);          -- JSONB containment
create index on bookings using gist (during);                            -- range overlap
create index on events using brin (created_at) with (pages_per_range = 64);  -- tiny index on a huge table
```

## 🟡 Middle Level

### B-tree variations that matter
* **Composite indexes**: column order matters — `(customer_id, created_at)` serves `where customer_id = ? order by created_at`, and `where customer_id = ?`, but not `where created_at > ?` alone (left-prefix rule; PG 18 adds skip scans for some cases).
* **Partial indexes**: index only rows you query — small and fast:

```sql
create index orders_open_idx on orders (created_at) where status in ('PENDING', 'PAID');
create unique index users_email_active_uq on users (lower(email)) where deleted_at is null;   -- unique among active users
```

* **Expression indexes**: `create index on users (lower(email));` — the query must use the same expression (`where lower(email) = lower(?)`).
* **Covering indexes** with `INCLUDE` for index-only scans: `create index on orders (customer_id) include (status, total);`
* **Descending / NULLS ordering**: `(created_at desc nulls last)` matching `ORDER BY` avoids sorts.

### GIN for JSONB and search

```sql
-- JSONB containment
select * from products where attributes @> '{"color": "red", "size": "M"}';
create index products_attr_gin on products using gin (attributes jsonb_path_ops);   -- smaller, faster for @>

-- Substring search with trigrams
create extension if not exists pg_trgm;
create index customers_name_trgm on customers using gin (name gin_trgm_ops);
select * from customers where name ilike '%schmidt%';                               -- can use the trigram index

-- Full-text search
create index articles_fts on articles using gin (to_tsvector('english', title || ' ' || body));
select * from articles where to_tsvector('english', title || ' ' || body) @@ websearch_to_tsquery('english', 'kafka retries');
```

GIN indexes are larger and slower to update (pending list, `fastupdate`); great for read-heavy search, costly for write-heavy tables.

## 🔴 Senior Level

### Choosing well
* **Selectivity**: an index helps when it narrows rows substantially or provides order; for predicates matching a large fraction (> ~5–20% depending on correlation), a sequential or bitmap scan is often better — the planner decides using statistics.
* **Write amplification**: every index slows `INSERT`/`UPDATE` and adds WAL; non-HOT updates must update all indexes. Indexing columns that are frequently updated prevents **HOT updates** (heap-only tuples), increasing bloat — drop unused indexes (`pg_stat_user_indexes.idx_scan = 0` over a representative period).
* **BRIN** shines when physical order correlates with the column (`pg_stats.correlation` near ±1), e.g. append-only `created_at`: a BRIN index might be 1,000× smaller than a B-tree with similar range-scan pruning. Useless when data is scattered.
* **GiST exclusion constraints** enforce non-overlap at the database level:

```sql
create extension if not exists btree_gist;
alter table bookings add constraint no_double_booking
  exclude using gist (room_id with =, during with &&);
```

### Operational practices
* Build indexes on live tables with `CREATE INDEX CONCURRENTLY` (no write lock; can't run in a transaction; if it fails it leaves an `INVALID` index to drop and retry).
* Rebuild bloated indexes with `REINDEX INDEX CONCURRENTLY` (PG 12+).
* Monitor index usage and size: `pg_stat_user_indexes`, `pg_relation_size`, and bloat estimation queries; tools like `pgstattuple`.
* Foreign keys: PostgreSQL does **not** automatically index the referencing column — add indexes on FK columns used in joins or cascading deletes, or deletes on the parent will scan the child table.
* Collations: B-tree indexes on text depend on collation; OS/glibc collation changes (upgrades) can corrupt index order — reindex after OS upgrades, consider ICU or `C` collation for identifiers.

### Specialized and newer options
* **Bloom index** extension for queries filtering on arbitrary combinations of many columns (equality only).
* **pgvector** HNSW/IVFFlat indexes for embedding similarity search.
* **Multicolumn GIN** via `btree_gin` to combine scalar and JSONB/array conditions in one index.

## 🎯 Interview Cheat Sheet

**30-second pitch:** B-tree is the default and covers equality, ranges, sorting and prefix matches, with composite, partial, expression and covering variants. GIN handles JSONB containment, arrays, full-text and trigram substring search; GiST handles ranges, geometry, nearest-neighbor and exclusion constraints; BRIN gives tiny indexes for huge, physically ordered tables; hash is rarely needed. I choose by operator and selectivity, mind write amplification and HOT updates, index foreign keys, and build or rebuild concurrently.

**Must know:**
* Index types ↔ operators table.
* Composite column order; partial, expression, INCLUDE indexes.
* GIN `jsonb_path_ops`, `pg_trgm`, full-text.
* BRIN correlation requirement; GiST exclusion constraints.
* `CREATE INDEX CONCURRENTLY`, unused index cleanup, FK indexes.

**Common follow-ups:**
* How do you speed up `LIKE '%term%'`?
* Why isn't my composite index used?
* When is BRIN better than B-tree?

**Red flags:** indexing every column; no index on FK columns; non-concurrent index builds on production tables.
