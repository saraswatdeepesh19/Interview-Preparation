# How table partitioning works in PostgreSQL

---

## 🟢 Junior Level

**Partitioning** splits one large logical table into smaller physical tables (**partitions**) by a **partition key**. Queries still target the parent table; PostgreSQL routes rows and skips irrelevant partitions.

PostgreSQL (10+) supports **declarative partitioning** with three strategies:

| Strategy | Key example | Typical use |
| --- | --- | --- |
| **Range** | `created_at` by month | Time-series data, logs, events, orders history |
| **List** | `region in ('EU')`, `tenant_tier` | Discrete categories |
| **Hash** | `hash(customer_id) % 8` | Even distribution when no natural range |

```sql
create table events (
    id          bigint generated always as identity,
    tenant_id   bigint      not null,
    created_at  timestamptz not null,
    type        text        not null,
    payload     jsonb       not null,
    primary key (id, created_at)                  -- PK/unique must include the partition key
) partition by range (created_at);

create table events_2026_10 partition of events
    for values from ('2026-10-01') to ('2026-11-01');
create table events_2026_11 partition of events
    for values from ('2026-11-01') to ('2026-12-01');
create table events_default partition of events default;   -- catches rows outside defined ranges
```

### Why partition?
* **Partition pruning** — `where created_at >= '2026-10-01'` scans only matching partitions.
* **Cheap data retention** — dropping or detaching an old partition is instant, versus a huge `DELETE` that bloats the table and generates WAL.
* **Maintenance per partition** — vacuum, reindex and statistics work on smaller pieces.

## 🟡 Middle Level

### Pruning in practice

```sql
explain (analyze, buffers)
select count(*) from events
where created_at >= '2026-10-15' and created_at < '2026-10-16' and tenant_id = 42;
--  Aggregate
--    ->  Index Only Scan using events_2026_10_tenant_created_idx on events_2026_10 ...
--  (only one partition appears in the plan)
```

Pruning happens at **planning time** for constants and at **execution time** for parameters (prepared statements, joins) — shown as `Subplans Removed: N` in the plan. Queries that don't filter on the partition key scan **all** partitions — design partition keys around your main access patterns.

### Indexes
Creating an index on the parent creates it on all partitions (and future ones). Unique constraints must include the partition key, so global uniqueness of a column like `id` alone can't be enforced across partitions — use an identity/sequence or UUIDv7 for uniqueness by construction, or a separate lookup table.

### Retention with detach/drop

```sql
alter table events detach partition events_2025_10 concurrently;   -- PG 14+: no long lock on the parent
-- archive it (pg_dump / copy to S3) then:
drop table events_2025_10;
```

### Automating partition creation
Create partitions ahead of time (e.g. next 3 months) with a scheduled job or the **pg_partman** extension (premake, retention policies, background worker). Missing future partitions send rows to the default partition (or fail without one) — monitor it.

## 🔴 Senior Level

### Design guidelines
* **Number and size**: aim for partitions of manageable size (tens of GB, not MB). Thousands of partitions increase planning time and lock overhead (each query touching the parent may lock all partitions during planning, though PG 12+ improved this greatly with execution-time pruning). Monthly or weekly partitions are typical; daily for very high volume.
* **Choose the key from queries and retention**: time for time-series; tenant (list/hash) when every query is tenant-scoped and tenants need isolated maintenance — or **sub-partitioning** (range by month, then hash by tenant) for both.
* **Default partitions** are convenient but attaching a new partition requires scanning the default partition for conflicting rows — keep it empty and alert if rows arrive.
* **Foreign keys** referencing partitioned tables are supported since PG 12; references *from* partitioned tables work since PG 11.

### Partitioning vs alternatives
* An **index** solves most "big table is slow" problems; partition when you need cheap retention, pruning for time-bounded scans over huge tables, or maintenance isolation.
* **BRIN indexes** on naturally ordered, append-only time columns give pruning-like benefits with tiny indexes — sometimes enough without partitioning.
* **Sharding** (Citus, application-level) distributes partitions across machines when one server isn't enough; partitioning alone stays on one server.

### Migrating an existing table to partitions
1. Create the new partitioned table with the same schema (plus partition key in PK).
2. Create partitions for historical data and backfill in batches (`insert into new select ... where created_at between ...`), or attach existing tables as partitions after adding matching `CHECK` constraints (attaching validates via the constraint and avoids a full scan).
3. Keep the old and new tables in sync during migration (triggers or dual writes from the app), then switch with a rename inside a short transaction.
4. Verify counts/checksums per range; drop the old table later.

### ORMs and partitioned tables
Hibernate/JPA work transparently with the parent table. Ensure queries include the partition key (`where created_at between ...`) — repository methods like `findById(id)` without the key scan all partitions; with a composite PK (`id`, `created_at`) map an `@IdClass`/`@EmbeddedId` or query by both.

## 🎯 Interview Cheat Sheet

**30-second pitch:** PostgreSQL declarative partitioning splits a table by range, list or hash; queries target the parent and pruning — at plan or execution time — skips irrelevant partitions. Its main wins are cheap retention through detaching and dropping partitions, faster time-bounded scans and per-partition maintenance. Primary keys must include the partition key, partitions should be created ahead with pg_partman or jobs, and queries must filter on the key or they scan everything.

**Must know:**
* Range/list/hash; default partition; sub-partitioning.
* Pruning; `Subplans Removed` in plans.
* PK/unique must include the partition key.
* `DETACH PARTITION CONCURRENTLY` (PG 14+), pg_partman.
* When indexes/BRIN suffice; migration approach.

**Common follow-ups:**
* How would you keep only 90 days of events?
* Why is my partitioned-table query slower than before?
* Partitioning vs sharding?

**Red flags:** partitioning a 2 GB table; thousands of tiny partitions; queries without the partition key.
