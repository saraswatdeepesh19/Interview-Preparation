# How to read EXPLAIN ANALYZE output

---

## 🟢 Junior Level

* `EXPLAIN` shows the **plan** the PostgreSQL optimizer chose, with **estimated** costs and row counts.
* `EXPLAIN ANALYZE` **executes** the query and adds **actual** times and row counts (careful: `ANALYZE` on `INSERT/UPDATE/DELETE` really modifies data — wrap it in `BEGIN ... ROLLBACK`).
* `EXPLAIN (ANALYZE, BUFFERS)` also shows how many 8 KB pages came from the cache (`shared hit`) vs disk (`read`) — usually the most revealing addition.

```sql
explain (analyze, buffers)
select o.id, o.total
from orders o
where o.customer_id = 42 and o.status = 'PAID'
order by o.created_at desc
limit 20;
```

```text
Limit  (cost=0.43..18.91 rows=20 width=16) (actual time=0.041..0.112 rows=20 loops=1)
  Buffers: shared hit=24
  ->  Index Scan using orders_customer_created_idx on orders o
        (cost=0.43..905.11 rows=979 width=16) (actual time=0.040..0.108 rows=20 loops=1)
        Index Cond: (customer_id = 42)
        Filter: (status = 'PAID')
        Rows Removed by Filter: 3
        Buffers: shared hit=24
Planning Time: 0.210 ms
Execution Time: 0.139 ms
```

### How to read it
* The plan is a **tree**; read from the **innermost/indented** nodes up. Each node feeds rows to its parent.
* `cost=startup..total` — optimizer's abstract cost units (not milliseconds).
* `rows` — estimated vs actual; `loops` — how many times the node ran (multiply actual rows and time per loop by loops).
* `actual time=first_row..last_row` in milliseconds, **per loop**.

## 🟡 Middle Level

### Node types you'll see most

| Node | Meaning | Watch for |
| --- | --- | --- |
| Seq Scan | Reads the whole table | Fine for small tables or large fractions; bad for selective filters on big tables |
| Index Scan | Walks index, fetches table rows | Many random heap fetches if many rows match |
| Index Only Scan | Answers from the index alone | `Heap Fetches` high → visibility map stale (vacuum) |
| Bitmap Index/Heap Scan | Collects matching pages, reads them in order | `Recheck Cond`, `lossy` pages when `work_mem` is small |
| Nested Loop | For each outer row, probe inner | Great with few outer rows + index; disastrous with misestimates |
| Hash Join | Build hash on one side, probe with other | `Batches > 1` = spilled to disk (raise `work_mem` or reduce rows) |
| Merge Join | Merge two sorted inputs | Needs sorted inputs (index or Sort node) |
| Sort | Sorting | `Sort Method: external merge Disk: …kB` = spill |
| HashAggregate / GroupAggregate | Grouping | Spills; huge group counts |

### The most important signal: estimate vs actual
```text
->  Nested Loop  (cost=... rows=12 ...) (actual ... rows=480312 loops=1)
```
The planner expected 12 rows and got 480,312 — it picked a nested loop that's now doing 480k index probes. Causes:
* **Stale statistics** → run `ANALYZE table` (autovacuum may be behind after bulk loads).
* **Correlated columns** (`city` and `zip`): the planner assumes independence → create **extended statistics**: `create statistics orders_city_zip (dependencies, mcv) on city, zip from orders; analyze orders;`
* **Skewed data / generic plans** for prepared statements (see below).
* Functions/expressions on columns hiding statistics (`where lower(email) = ...` without an expression index).

## 🔴 Senior Level

### A systematic approach
1. **Find the node with the largest self time** (actual total time minus children) × loops — that's where time goes. Tools like `explain.depesz.com`, `explain.dalibo.com` (PEV2) visualize this.
2. **Compare estimated vs actual rows** at each level; the first big divergence (×10 or more) usually explains a bad plan choice above it.
3. **Check buffers**: high `read` → I/O bound (cold cache, too much data touched); high `shared hit` on a small result → touching too many pages (bad index, filters after the fact).
4. **Look for filters after scans**: `Rows Removed by Filter` large → index doesn't match the predicate; consider composite or partial indexes.
5. **Spills**: Sort/Hash `Disk:` → `work_mem` too low for this query (set per session/role, not globally huge).

### Index design driven by the plan

```sql
-- Filter after index scan: "Rows Removed by Filter: 120000" for status = 'PAID'
create index concurrently orders_paid_customer_created_idx
    on orders (customer_id, created_at desc)
    where status = 'PAID';                                    -- partial index matches the query exactly

-- Covering index enabling Index Only Scan for the selected columns
create index concurrently orders_customer_created_incl_idx
    on orders (customer_id, created_at desc) include (total);
```

### Prepared statements and generic plans
JDBC drivers use server-side prepared statements after a threshold (pgJDBC `prepareThreshold=5`). PostgreSQL may switch to a **generic plan** (independent of parameter values) after five executions if it looks no worse than custom plans. With skewed data (`tenant_id = 1` has 90% of rows), a generic plan can be terrible for some values. Diagnose with `EXPLAIN (ANALYZE) EXECUTE stmt(...)`; options: `plan_cache_mode = force_custom_plan` for the session/role, rewrite queries, or partial indexes.

### Production tooling
* **`pg_stat_statements`** — top queries by total time, mean time, calls, rows, shared blocks read; the starting point for "what to optimize".
* **`auto_explain`** — logs plans of slow queries automatically (`auto_explain.log_min_duration = '500ms'`, `log_analyze = on` with sampling) — captures real-world plans with real parameters.
* Compare plans before/after changes in staging with production-like data volumes; plans on a 1,000-row dev database are meaningless.
* JIT (`jit = on`) can add hundreds of ms planning/compile overhead to OLTP queries with high estimated costs — check `JIT:` sections in plans and tune `jit_above_cost` or disable for OLTP roles.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `EXPLAIN ANALYZE` executes the query and shows the plan tree with estimated and actual rows, time per loop and loops; with `BUFFERS` it shows cache hits vs disk reads. I find the node with the most self time, look for large estimate-vs-actual mismatches that cause bad join choices, check filters applied after scans, spills of sorts and hashes, and heap fetches on index-only scans — then fix with statistics, extended stats, composite, partial or covering indexes, query rewrites or `work_mem`. In production I use `pg_stat_statements` and `auto_explain`.

**Must know:**
* cost vs actual time; rows × loops; reading the tree.
* Node types and their warning signs.
* Estimate vs actual mismatches; `ANALYZE`, extended statistics.
* Partial/covering indexes from plan evidence.
* Generic plans with prepared statements; `pg_stat_statements`, `auto_explain`.

**Common follow-ups:**
* Why does the planner choose a Seq Scan despite an index?
* What does `Rows Removed by Filter` tell you?
* The query is fast in psql but slow from the app — why?

**Red flags:** reading costs as milliseconds; tuning on tiny datasets; running `EXPLAIN ANALYZE DELETE` without rollback.
