# Soft delete and data archiving strategies

---

## 🟢 Junior Level

* **Hard delete** — `DELETE` removes the row permanently.
* **Soft delete** — mark the row as deleted (`deleted_at timestamp`, or a status) and hide it from normal queries; it can be restored and still appears in history and audits.
* **Archiving** — move old or inactive data out of the hot tables into cheaper storage (archive tables, partitions, object storage, a data warehouse) while keeping it retrievable.

### Basic soft delete with Hibernate

```java
@Entity
@SQLDelete(sql = "update customer set deleted_at = now() where id = ?")   // repository.delete() becomes an UPDATE
@SQLRestriction("deleted_at is null")                                     // Hibernate 6.3+: added to every query
public class Customer {
    @Id Long id;
    String email;
    Instant deletedAt;
}
```

(Older Hibernate versions use `@Where(clause = "deleted_at is null")`; Hibernate 6.4+ also offers `@SoftDelete`.)

### When soft delete makes sense
* Users expect **undo/restore** (trash bins).
* **Audit/legal** requirements to keep records (invoices, orders).
* **References** from other data must stay valid (an order references a deactivated product).

---

## 🟡 Middle Level

### Problems soft delete introduces
* **Every query must filter** deleted rows — easy to forget in native queries, reports and other services reading the database.
* **Unique constraints** break: a soft-deleted user keeps the email, so a new signup with the same email fails. Fix with a partial unique index:

```sql
create unique index customer_email_active_uq on customer (lower(email)) where deleted_at is null;
```

* **Foreign keys** no longer protect you: rows pointing to "deleted" parents remain valid at the database level.
* **Table and index bloat**: dead-but-kept rows grow tables and slow queries; indexes should be partial (`where deleted_at is null`) for hot queries.
* **GDPR/right to erasure**: soft delete is *not* erasure — personal data must eventually be truly deleted or anonymized.

### Alternatives to a deleted flag
* **Status-based lifecycle** (`ACTIVE`, `DEACTIVATED`, `CLOSED`) when "deleted" is really a business state — more explicit than a generic flag.
* **History/audit tables** (or Hibernate Envers): hard delete from the main table, keep the full history in `*_history` with who/when — the main table stays clean and constraints keep working.
* **Event sourcing / append-only logs** where history is the model.

## 🔴 Senior Level

### Archiving strategies for large tables

| Strategy | How | Fit |
| --- | --- | --- |
| **Partition by time + detach/drop** | Range partitions; detach old ones, archive with `COPY`/`pg_dump` to S3, drop | Time-series, orders, events — the cleanest at scale |
| **Archive tables** | Move rows older than N months into `orders_archive` in batches | When queries occasionally need old data in SQL |
| **Export to data lake/warehouse** | CDC or batch export to Parquet in S3 / BigQuery; delete from OLTP | Analytics and compliance retention |
| **Tiered storage** | Cold tablespaces on cheaper disks, or managed tiering (Aurora/I/O-optimized options) | Rarely accessed, still online |

Batch-moving rows safely:

```sql
-- Move in small batches to avoid long locks, bloat and replication lag
with moved as (
  delete from orders
  where id in (
    select id from orders
    where status in ('COMPLETED', 'CANCELLED') and created_at < now() - interval '2 years'
    order by id
    limit 5000
    for update skip locked
  )
  returning *
)
insert into orders_archive select * from moved;
-- repeat until no rows; throttle between batches; run VACUUM afterwards (or rely on autovacuum)
```

### Designing for retention from the start
* Define **retention per data class** (e.g. invoices 10 years for tax law, logs 30 days, PII deleted 30 days after account closure) with legal/compliance input.
* **Separate PII** from business records so you can erase or anonymize personal data while keeping financial records (replace the customer reference with a pseudonymous ID; crypto-shredding: encrypt PII with per-user keys and delete the key).
* Make deletion **propagate**: caches, search indexes, replicas, backups (document backup retention), analytics copies, and downstream services (emit `CustomerErased` events).
* **Restore paths** for archives: documented and tested (can support retrieve a 3-year-old order within a day?).

### Choosing
* Product needs undo → soft delete with partial unique indexes and a purge job after N days.
* Compliance needs history → hard delete + history/audit table, or event log.
* Performance/cost of huge tables → time partitioning and archiving, not soft delete.
* GDPR → real deletion/anonymization pipelines; soft delete only as a short grace period.

## 🎯 Interview Cheat Sheet

**30-second pitch:** Soft delete marks rows as deleted to allow restore, auditing and stable references, implemented in Hibernate with `@SQLDelete` plus `@SQLRestriction` or `@SoftDelete`. It costs query filtering everywhere, broken unique constraints — fixed with partial unique indexes — weakened foreign keys, bloat and GDPR issues. For history I prefer hard delete plus audit tables, and for large data I archive by time partitions or batched moves, with retention defined per data class and PII erasure that propagates to caches, indexes and downstream systems.

**Must know:**
* Hard vs soft delete vs archiving.
* Hibernate `@SQLDelete`, `@SQLRestriction`/`@Where`, `@SoftDelete`.
* Partial unique indexes; partial indexes for hot queries.
* Partition detach/drop; batched archive moves with SKIP LOCKED.
* Retention policies, PII separation, crypto-shredding, GDPR.

**Common follow-ups:**
* A user deletes their account — what exactly happens to their data?
* Why does signup fail with "email exists" for a deleted user?
* How do you remove 500 million old rows safely?

**Red flags:** soft delete as GDPR compliance; one giant `DELETE` on a busy table; native queries forgetting `deleted_at`.
