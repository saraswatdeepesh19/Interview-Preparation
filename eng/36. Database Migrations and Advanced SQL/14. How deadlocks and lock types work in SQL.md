# How deadlocks and lock types work in SQL

---

## 🟢 Junior Level

Databases use **locks** so concurrent transactions don't corrupt each other's work. In PostgreSQL, MVCC means **readers don't block writers and writers don't block readers** for normal `SELECT`s; locks mostly matter between **writers**, and for explicit locking and DDL.

A **deadlock** happens when two transactions each hold a lock the other needs:

```text
T1: update accounts set balance = balance - 10 where id = 1;   -- locks row 1
T2: update accounts set balance = balance - 20 where id = 2;   -- locks row 2
T1: update accounts set balance = balance + 10 where id = 2;   -- waits for T2
T2: update accounts set balance = balance + 20 where id = 1;   -- waits for T1  -> deadlock
```

PostgreSQL detects the cycle (after `deadlock_timeout`, default 1 s) and aborts one transaction:

```text
ERROR:  deadlock detected
DETAIL:  Process 4711 waits for ShareLock on transaction 9001; blocked by process 4712.
         Process 4712 waits for ShareLock on transaction 9000; blocked by process 4711.
```

### Simplest prevention
**Lock in a consistent order** — e.g. always update the lower account ID first:

```java
long first = Math.min(from, to), second = Math.max(from, to);
accounts.lockById(first);      // select ... for update
accounts.lockById(second);
// then debit/credit
```

And **retry** the aborted transaction (deadlocks are expected, transient errors — SQLState `40P01`).

## 🟡 Middle Level

### Row-level locks (PostgreSQL)

| Lock | Taken by | Conflicts with |
| --- | --- | --- |
| `FOR KEY SHARE` | FK checks on referencing inserts | `FOR UPDATE` |
| `FOR SHARE` | `SELECT ... FOR SHARE` | `FOR UPDATE`, `FOR NO KEY UPDATE` |
| `FOR NO KEY UPDATE` | `UPDATE` not changing key columns | `FOR SHARE`, `FOR NO KEY UPDATE`, `FOR UPDATE` |
| `FOR UPDATE` | `SELECT ... FOR UPDATE`, `DELETE`, key-changing `UPDATE` | All row locks |

Useful modifiers:
* `NOWAIT` — fail immediately instead of waiting.
* `SKIP LOCKED` — skip rows locked by others — the basis of safe concurrent job queues:

```sql
-- Each worker claims different jobs without blocking
with next as (
  select id from jobs
  where status = 'READY'
  order by priority desc, created_at
  limit 10
  for update skip locked
)
update jobs set status = 'RUNNING', started_at = now()
where id in (select id from next)
returning id, payload;
```

### Table-level locks and DDL
Every statement takes a table lock: `SELECT` → `ACCESS SHARE`; DML → `ROW EXCLUSIVE`; `CREATE INDEX` (non-concurrent) → `SHARE` (blocks writes); most `ALTER TABLE` → `ACCESS EXCLUSIVE` (blocks everything, including reads). The dangerous part is **lock queues**: an `ALTER TABLE` waiting behind a long-running transaction blocks every subsequent query on that table. Always:

```sql
set lock_timeout = '3s';      -- give up quickly instead of building a queue
alter table orders add column note text;
```

### JPA locking

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)                        // SELECT ... FOR UPDATE
@Query("select a from Account a where a.id = :id")
Optional<Account> lockById(long id);

@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-2"))   // Hibernate: SKIP LOCKED
```

Optimistic locking (`@Version`) avoids holding locks and is preferable when conflicts are rare.

## 🔴 Senior Level

### Hidden deadlock sources
* **Foreign keys**: inserting child rows takes `FOR KEY SHARE` on the parent row; concurrent updates of the parent's key or `SELECT ... FOR UPDATE` on it interact. Batch jobs updating parents while API calls insert children can deadlock.
* **Unordered multi-row updates**: `update ... where id in (...)` locks rows in physical scan order, which differs between transactions — sort and lock explicitly (`select ... where id = any(?) order by id for update`).
* **Unique index conflicts**: concurrent inserts of the same key wait on each other; with multiple keys in different orders they can deadlock — consistent ordering or `insert ... on conflict`.
* **Triggers and cascades** touching other tables in varying orders.
* **Hibernate flush order**: entity updates are flushed in an order that may differ between code paths; `hibernate.order_updates=true` sorts updates by entity type and ID.

### Diagnosing
* Enable logging: `log_lock_waits = on` (logs waits longer than `deadlock_timeout`), and deadlock details appear in the server log with both queries.
* Live blocking chains:

```sql
select pid, pg_blocking_pids(pid) as blocked_by, state, wait_event_type, wait_event,
       now() - xact_start as xact_age, left(query, 120) as query
from pg_stat_activity
where cardinality(pg_blocking_pids(pid)) > 0;
```

* `pg_locks` joined with `pg_stat_activity` for details; kill the root blocker if needed (`pg_terminate_backend(pid)`).

### Design guidelines
* Keep transactions **short**; never wait for user input or remote calls while holding locks.
* Set **`idle_in_transaction_session_timeout`** to kill sessions that hold locks while idle (leaked transactions from apps).
* Prefer **optimistic concurrency** or **atomic single-statement updates** (`update stock set qty = qty - 1 where sku = ? and qty >= 1`) over read-lock-modify-write.
* Treat deadlocks and serialization failures (`40001`) as retryable: Spring's `@Retryable` around the transactional method (not inside it), with jitter and a small attempt limit.
* For `SERIALIZABLE` isolation, PostgreSQL uses predicate locks (SSI) and aborts with `40001` instead of blocking — design for retries.

## 🎯 Interview Cheat Sheet

**30-second pitch:** In PostgreSQL, MVCC keeps reads and writes from blocking each other, so locks matter between writers, explicit `FOR UPDATE`/`FOR SHARE` and DDL. Deadlocks are cycles of lock waits; the database aborts one transaction with `40P01`. I prevent them with consistent lock ordering, short transactions, atomic updates or optimistic locking, use `SKIP LOCKED` for job queues and `lock_timeout` for DDL, diagnose with `log_lock_waits` and `pg_blocking_pids`, and retry deadlocks and serialization failures.

**Must know:**
* Row lock modes; NOWAIT; SKIP LOCKED.
* Table lock levels; ALTER TABLE lock queue danger; `lock_timeout`.
* Deadlock detection, `deadlock_timeout`, retry on 40P01/40001.
* Hidden sources: FKs, unordered multi-row updates, flush order.
* Diagnostics: `pg_stat_activity`, `pg_blocking_pids`, `pg_locks`.

**Common follow-ups:**
* How would you implement a job queue in PostgreSQL?
* Why did a simple `ALTER TABLE` take the site down?
* Pessimistic or optimistic locking for inventory?

**Red flags:** long transactions holding row locks during HTTP calls; DDL without lock timeouts; no retry for deadlocks.
