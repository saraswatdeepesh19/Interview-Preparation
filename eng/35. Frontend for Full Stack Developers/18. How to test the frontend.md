# How to test the frontend

---

## 🟢 Junior Level

Frontend testing follows the same pyramid idea as backend testing, adapted to UIs (often drawn as a "testing trophy" with more integration tests):

| Level | What it tests | Tools |
| --- | --- | --- |
| **Static** | Types, lint rules | TypeScript, ESLint |
| **Unit** | Pure functions, hooks, small utilities | Vitest / Jest |
| **Component / integration** | Components rendered with their children, user interactions, mocked network | Testing Library + Vitest/Jest, MSW |
| **End-to-end** | Real browser against a running app (and backend) | Playwright, Cypress |
| **Visual regression** | Pixel/screenshot diffs | Playwright screenshots, Chromatic, Percy |
| **Accessibility** | ARIA roles, contrast, keyboard navigation | axe-core, Playwright + axe |

### Component test with Testing Library
Test **behavior as a user sees it** — find elements by role and label, click and type, assert visible output — not implementation details (component state, CSS classes):

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('shows an error when quantity is zero', async () => {
  const user = userEvent.setup();
  render(<AddToCart sku="A1" />);

  await user.clear(screen.getByLabelText(/quantity/i));
  await user.type(screen.getByLabelText(/quantity/i), '0');
  await user.click(screen.getByRole('button', { name: /add to cart/i }));

  expect(screen.getByRole('alert')).toHaveTextContent('Quantity must be at least 1');
});
```

## 🟡 Middle Level

### Mocking the network with MSW
**Mock Service Worker** intercepts `fetch`/XHR at the network level, so components use their real data-fetching code:

```typescript
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/orders/:id', ({ params }) =>
    HttpResponse.json({ id: params.id, status: 'PAID', total: 49.9 })),
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test('renders order status', async () => {
  render(<OrderBadge orderId="42" />, { wrapper: QueryProvider });
  expect(await screen.findByText('PAID')).toBeInTheDocument();       // findBy* waits for async UI
});

test('renders problem details on 404', async () => {
  server.use(http.get('/api/orders/:id', () =>
    HttpResponse.json({ title: 'Order not found', status: 404 }, { status: 404,
      headers: { 'Content-Type': 'application/problem+json' } })));
  render(<OrderBadge orderId="404" />, { wrapper: QueryProvider });
  expect(await screen.findByText(/order not found/i)).toBeInTheDocument();
});
```

The same handlers can power local development without a backend and Storybook stories.

### E2E with Playwright

```typescript
import { test, expect } from '@playwright/test';

test('customer can place an order', async ({ page }) => {
  await page.goto('/products/A1');
  await page.getByRole('button', { name: 'Add to cart' }).click();
  await page.getByRole('link', { name: 'Cart' }).click();
  await page.getByRole('button', { name: 'Checkout' }).click();
  await expect(page.getByRole('heading', { name: /thank you/i })).toBeVisible();   // auto-waiting assertion
});
```

Playwright auto-waits for elements, runs Chromium/Firefox/WebKit, records traces (screenshots, DOM snapshots, network) for debugging failures, and parallelizes across workers.

## 🔴 Senior Level

### Keeping E2E suites reliable
* **Few, critical journeys** (login, search, checkout) — E2E tests are slow and the most brittle layer.
* **Stable selectors**: roles and accessible names (`getByRole`), or `data-testid` for elements without semantics; never CSS classes or DOM structure.
* **Own the test data**: create data via API calls in setup (or seed the database per test run), unique per test; don't depend on shared staging data.
* **No fixed sleeps**: rely on auto-waiting and web-first assertions (`await expect(locator).toBeVisible()`).
* **Isolate external services**: route third-party calls (`page.route('**/analytics/**', r => r.abort())`), stub payments in test mode.
* **Trace on failure** in CI (`trace: 'on-first-retry'`) and quarantine flaky tests with owners.

### Contract alignment with the backend
* Generate TypeScript types/clients from the backend OpenAPI spec; type errors catch drift at build time.
* Keep MSW handlers consistent with the real API — generate them from OpenAPI examples, or run a small set of tests against the real backend, or use consumer-driven contract tests (Pact JS) so the backend verifies what the frontend expects.

### Accessibility and visual testing
* Run **axe-core** in component and E2E tests (`@axe-core/playwright`) to catch missing labels, contrast issues, and invalid ARIA — accessibility bugs are real defects (and legal requirements in many markets).
* Visual regression for design-system components (Storybook + Chromatic/Playwright screenshots) catches unintended CSS changes; keep snapshots deterministic (fixed fonts, disabled animations, mocked dates).

### What not to test
* Implementation details (internal state, which hook was called) — tests break on refactors without catching bugs.
* Third-party library internals.
* Exhaustive combinations in E2E — push combinatorics down to unit/component tests.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I rely on TypeScript and linting as the static base, unit tests for logic, most coverage in component tests with Testing Library and MSW-mocked network — testing behavior through roles and labels — and a few Playwright E2E tests for critical journeys, plus axe accessibility checks and visual regression for shared components. I keep E2E stable with role-based selectors, owned test data, auto-waiting and traces, and align mocks with the backend via generated types or contract tests.

**Must know:**
* Testing trophy layers and tools.
* Testing Library principles; `findBy*` for async.
* MSW handlers and `onUnhandledRequest: 'error'`.
* Playwright auto-waiting, traces, `page.route`.
* Accessibility (axe) and visual regression; contract alignment.

**Common follow-ups:**
* Why not test component state directly?
* How do you avoid flaky E2E tests?
* How do frontend mocks stay in sync with the API?

**Red flags:** snapshot tests of entire component trees as the main strategy; `sleep(2000)` in E2E; selectors on CSS classes.
