# How do fetch and CORS work in the browser

---

## 🟢 Junior Level

**`fetch`** is the browser's built-in API for HTTP requests. It returns a `Promise<Response>`:

```javascript
const response = await fetch('/api/orders/42', {
  headers: { Accept: 'application/json' },
});
if (!response.ok) {                         // fetch does NOT reject on 4xx/5xx!
  throw new Error(`HTTP ${response.status}`);
}
const order = await response.json();
```

Two things surprise backend developers:
1. **`fetch` only rejects on network errors** (DNS failure, connection refused, CORS blocked) — a 404 or 500 resolves normally; check `response.ok` / `response.status`.
2. **Cookies are not sent to other origins** by default, and responses from other origins are hidden unless the server allows them via **CORS**.

### Same-origin policy and CORS
An **origin** is scheme + host + port. A page at `https://app.shop.com` calling `https://api.shop.com` is **cross-origin**. The browser sends the request with an `Origin` header and only lets JavaScript read the response if the server replies with matching **CORS headers**:

```http
Access-Control-Allow-Origin: https://app.shop.com
```

## 🟡 Middle Level

### Simple vs preflighted requests
A **preflight** (`OPTIONS`) is sent first when the request is not "simple" — e.g. methods like `PUT`/`DELETE`/`PATCH`, `Content-Type: application/json`, or custom headers such as `Authorization`:

```http
OPTIONS /api/orders/42
Origin: https://app.shop.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

204 No Content
Access-Control-Allow-Origin: https://app.shop.com
Access-Control-Allow-Methods: GET, PUT, POST, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600
```

Only after a successful preflight does the browser send the real `PUT`. `Access-Control-Max-Age` caches the preflight result.

### Credentials (cookies)

```javascript
await fetch('https://api.shop.com/api/cart', {
  credentials: 'include',                    // send cookies cross-origin
});
```

The server must then respond with `Access-Control-Allow-Credentials: true` **and** an explicit origin (not `*`). The cookie itself must allow cross-site sending: `SameSite=None; Secure` (modern browsers default to `SameSite=Lax`, which blocks most cross-site cookie sending). Third-party cookie restrictions in browsers make cross-site cookie auth increasingly fragile — prefer same-site deployments.

### Exposing headers and reading errors
* JavaScript can read only "safe" response headers by default; others (`Location`, `ETag`, custom headers) need `Access-Control-Expose-Headers`.
* If a cross-origin **error** response (401/500) lacks CORS headers, the browser reports a CORS error and the code can't see the real status — make sure error responses include CORS headers too.

## 🔴 Senior Level

### Robust client wrapper

```typescript
export class ApiError extends Error {
  constructor(public status: number, public problem?: { type?: string; title?: string; detail?: string }) {
    super(problem?.title ?? `HTTP ${status}`);
  }
}

export async function api<T>(path: string, init: RequestInit = {}, timeoutMs = 10_000): Promise<T> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);          // fetch has no default timeout
  try {
    const res = await fetch(path, {
      ...init,
      signal: controller.signal,
      headers: { Accept: 'application/json', ...(init.body ? { 'Content-Type': 'application/json' } : {}), ...init.headers },
    });
    if (res.status === 204) return undefined as T;
    const isProblem = res.headers.get('Content-Type')?.includes('application/problem+json');
    if (!res.ok) throw new ApiError(res.status, isProblem ? await res.json() : undefined);
    return (await res.json()) as T;
  } finally {
    clearTimeout(timer);
  }
}
```

Points: explicit timeouts via `AbortController` (also used to cancel requests when a component unmounts or a newer search replaces an older one), Problem Details parsing, and typed results.

### Architecture choices that avoid CORS entirely
* Serve the SPA and API from the **same origin** (reverse proxy/CDN routes `/api/*` to the backend) — no preflights, simpler cookies (`SameSite=Strict/Lax`), fewer misconfigurations.
* A **BFF** (backend for frontend) on the same origin holds OAuth tokens server-side and exposes session-cookie-authenticated endpoints to the SPA (the recommended pattern for browser-based OAuth clients).

### Security notes
* CORS is **not** access control for your API: non-browser clients ignore it. Authentication and authorization still happen server-side.
* Never reflect arbitrary `Origin` values together with `Allow-Credentials: true`.
* Same-origin requests with cookies need **CSRF** protection (SameSite cookies help; tokens for state-changing requests); cross-origin token-based (Authorization header) APIs are not vulnerable to classic CSRF because browsers don't attach the token automatically.
* Private Network Access rules in Chromium add preflights for public sites calling private/local addresses — relevant for intranet tools and IoT dashboards.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `fetch` returns a promise that only rejects on network failures, so clients must check `response.ok`, add timeouts with AbortController and parse error bodies. Cross-origin calls are governed by the same-origin policy: the server opts in with CORS headers, non-simple requests trigger an OPTIONS preflight, and credentials need an explicit origin plus `SameSite=None; Secure` cookies. Same-origin deployment or a BFF avoids most of this, and CORS never replaces server-side authorization.

**Must know:**
* `fetch` semantics: no rejection on HTTP errors; no default timeout.
* Origin definition; simple vs preflighted requests.
* `credentials: 'include'` + `Allow-Credentials` + explicit origin + SameSite.
* `Access-Control-Expose-Headers`; CORS headers on error responses.
* Same-origin proxy / BFF; CORS vs CSRF.

**Common follow-ups:**
* Why does the request work in Postman but not the browser?
* Why can't my JS read the `Location` header?
* How do you cancel an in-flight request?

**Red flags:** `Access-Control-Allow-Origin: *` with credentials; treating CORS as API security; ignoring `response.ok`.
