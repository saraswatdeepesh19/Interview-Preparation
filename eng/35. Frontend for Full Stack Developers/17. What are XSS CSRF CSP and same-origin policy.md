# What are XSS CSRF CSP and same-origin policy

---

## 🟢 Junior Level

Four concepts that define browser security for web apps:

* **Same-origin policy (SOP)** — scripts from one origin (scheme + host + port) can't read data from another origin. It isolates sites from each other in the browser.
* **XSS (Cross-Site Scripting)** — an attacker gets *their* JavaScript to run in *your* origin (via injected HTML), so the SOP no longer protects you: the script can read the page, call your APIs as the user, and steal non-HttpOnly tokens.
* **CSRF (Cross-Site Request Forgery)** — a malicious site makes the user's browser **send** a request to your site with the user's cookies attached (e.g. a hidden form posting to `/transfer`). The attacker can't read the response, but the action happens.
* **CSP (Content Security Policy)** — a response header telling the browser which scripts, styles, frames and connections are allowed, making XSS much harder to exploit.

| | XSS | CSRF |
| --- | --- | --- |
| Attacker's code runs in your origin? | Yes | No |
| Can read responses? | Yes | No |
| Relies on | Injection flaws | Browser auto-sending cookies |
| Main defenses | Output encoding, sanitization, CSP, Trusted Types | SameSite cookies, CSRF tokens, Origin checks, non-cookie auth |

## 🟡 Middle Level

### Preventing XSS in frontend code
Frameworks escape interpolated values by default (`{order.note}` in React renders text, not HTML). Danger lies in escape hatches:

```tsx
// DANGEROUS: renders attacker-controlled HTML
<div dangerouslySetInnerHTML={{ __html: comment.body }} />

// If rich text is required, sanitize with an allow-list first
import DOMPurify from 'dompurify';
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(comment.body) }} />
```

Other sinks: `element.innerHTML = ...`, `document.write`, `eval`/`new Function`, `setTimeout("string")`, `href={userUrl}` with `javascript:` URLs (validate schemes: allow only `https:`/`mailto:`), and server-rendered templates using unescaped output (`th:utext`).

### Preventing CSRF
* **SameSite cookies**: `SameSite=Lax` (browser default) blocks cookies on cross-site POSTs and subresource requests; `Strict` blocks even top-level navigations from other sites.
* **CSRF tokens** (synchronizer token or double-submit cookie) for cookie-authenticated state-changing requests — Spring Security enables this by default for session-based apps.
* **Check `Origin`/`Sec-Fetch-Site` headers** on state-changing requests.
* **Token-based auth in headers** (`Authorization: Bearer ...`) isn't sent automatically by browsers, so classic CSRF doesn't apply — but then XSS becomes the main threat to tokens stored in JS-accessible storage.

```java
// Spring Security for an SPA using cookie sessions: token in a cookie readable by JS, echoed in a header
http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())    // XSRF-TOKEN cookie
        .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()));            // custom handler per Spring docs
// The SPA sends header X-XSRF-TOKEN with the cookie value on POST/PUT/DELETE
```

## 🔴 Senior Level

### CSP that actually helps

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  connect-src 'self' https://api.shop.com;
  img-src 'self' data: https://cdn.shop.com;
  report-to csp-endpoint
```

* **Nonce-based** `script-src` with `'strict-dynamic'` blocks injected inline scripts even if HTML injection occurs; avoid `'unsafe-inline'` and `'unsafe-eval'`.
* `frame-ancestors 'none'` stops clickjacking; `base-uri 'none'` stops `<base>` tag injection; `connect-src` limits where scripts can send data (exfiltration).
* Roll out with `Content-Security-Policy-Report-Only` first and collect violation reports.
* For SPAs served as static files, nonces need server/edge involvement (inject per response) or use hash-based CSP for fixed inline scripts.

### Token storage trade-off (a classic interview debate)
* **localStorage/sessionStorage**: easy, immune to CSRF, but any XSS can read and exfiltrate the token.
* **HttpOnly cookies**: not readable by JS (XSS can still *use* the session while active but can't steal it), but need CSRF protection and are subject to third-party cookie restrictions cross-site.
* **BFF / token handler pattern** (recommended by OAuth 2.0 for Browser-Based Apps guidance): tokens stay on a same-origin backend; the browser holds only an HttpOnly, Secure, SameSite session cookie.

### Defense in depth summary
1. Output encoding by default + sanitization for rich text.
2. Strict CSP with nonces; **Trusted Types** (`require-trusted-types-for 'script'`) to lock down DOM XSS sinks.
3. HttpOnly + Secure + SameSite cookies; short-lived tokens.
4. CSRF tokens or Origin checks for cookie-authenticated mutations.
5. `X-Content-Type-Options: nosniff`, correct `Content-Type` for JSON.
6. Dependency hygiene — compromised npm packages are XSS by supply chain.
7. CORS configured narrowly (it's about reading cross-origin responses, not about CSRF).

## 🎯 Interview Cheat Sheet

**30-second pitch:** The same-origin policy isolates origins; XSS breaks it by running attacker code inside your origin, while CSRF abuses the browser's automatic cookie sending to trigger actions without reading responses. I prevent XSS with default output encoding, sanitizing rich text, avoiding dangerous sinks, a nonce-based strict CSP and Trusted Types; I prevent CSRF with SameSite cookies, CSRF tokens or Origin checks; and for SPAs I prefer a BFF with HttpOnly session cookies over storing tokens in localStorage.

**Must know:**
* SOP definition; XSS vs CSRF comparison.
* Dangerous sinks (`dangerouslySetInnerHTML`, `innerHTML`, `javascript:` URLs).
* SameSite Lax/Strict/None; CSRF tokens; Spring's cookie CSRF repository for SPAs.
* Strict CSP with nonces, `strict-dynamic`, `frame-ancestors`, report-only rollout.
* Token storage trade-offs; BFF pattern.

**Common follow-ups:**
* Does CORS protect against CSRF?
* Is a JWT in localStorage safe?
* What does `'strict-dynamic'` do?

**Red flags:** disabling CSRF in a cookie-session app; CSP with `unsafe-inline`; "React prevents all XSS".
