# How to optimize web performance

---

## 🟢 Junior Level

Web performance is about **how fast users see and can use the page**. Google's **Core Web Vitals** are the standard user-centric metrics:

| Metric | Measures | "Good" threshold (75th percentile of users) |
| --- | --- | --- |
| **LCP** — Largest Contentful Paint | Loading: when the main content appears | ≤ 2.5 s |
| **INP** — Interaction to Next Paint | Responsiveness: delay from user input to visual update | ≤ 200 ms |
| **CLS** — Cumulative Layout Shift | Visual stability: unexpected layout jumps | ≤ 0.1 |

Also useful: **TTFB** (Time to First Byte — server/network speed) and **FCP** (First Contentful Paint).

### Quick wins
* **Compress** text responses (Brotli/gzip) and **minify** JS/CSS.
* **Cache** static assets with content-hashed filenames and long `Cache-Control` (`max-age=31536000, immutable`).
* Serve assets from a **CDN** close to users; use HTTP/2 or HTTP/3.
* **Optimize images**: modern formats (AVIF/WebP), correct dimensions, `srcset`/`sizes`, `loading="lazy"` below the fold.
* **Ship less JavaScript**: code-split by route, remove unused dependencies.

```html
<img src="/img/hero-1200.avif"
     srcset="/img/hero-600.avif 600w, /img/hero-1200.avif 1200w"
     sizes="(max-width: 600px) 100vw, 1200px"
     width="1200" height="600" alt="Autumn collection"
     fetchpriority="high">                     <!-- LCP image: load early, never lazy -->
```

Width/height attributes reserve space and prevent layout shift (CLS).

## 🟡 Middle Level

### Improving each vital
**LCP**
* Fast TTFB: server-side caching, efficient backend queries, CDN caching of HTML where possible (SSR/static generation).
* Discoverable LCP resource: preload the hero image/font (`<link rel="preload">`), avoid client-side rendering for above-the-fold content.
* Remove render-blocking resources: inline critical CSS, `defer`/`async` scripts.

**INP**
* Keep the **main thread** free: break long tasks (> 50 ms) into chunks (`scheduler.yield()`/`setTimeout`), move heavy work to Web Workers.
* Reduce re-render cost in frameworks (memoization, state colocation, virtualization of long lists).
* Avoid heavy third-party scripts (tag managers, chat widgets) or load them after interaction.

**CLS**
* Always reserve space for images, ads, embeds (`width`/`height` or `aspect-ratio`).
* Use `font-display: optional`/`swap` with size-adjusted fallback fonts.
* Don't insert content above existing content unless in response to a user action.

### Network-level optimization
* **Fewer round trips**: `preconnect` to critical third-party origins, avoid request waterfalls (fetch data in parallel; let the server render or stream initial data).
* **API design matters**: one well-shaped endpoint (or BFF/GraphQL) instead of ten sequential calls on page load; paginate; return only needed fields; enable HTTP caching (`ETag`, `Cache-Control`) for GETs.

## 🔴 Senior Level

### Measure the right way
* **Lab data** (Lighthouse, WebPageTest, Chrome DevTools Performance panel) for debugging and CI regression checks — controlled but not representative.
* **Field data / RUM** (Chrome UX Report, `web-vitals` library sending metrics to your analytics, commercial RUM): real devices and networks; evaluate at the **75th percentile**, segmented by device class and country.

```typescript
import { onLCP, onINP, onCLS } from 'web-vitals';

function send(metric: { name: string; value: number; id: string }) {
  navigator.sendBeacon('/rum', JSON.stringify(metric));        // survives page unload
}
onLCP(send); onINP(send); onCLS(send);
```

* **Performance budgets** in CI: max bundle size per route, Lighthouse score thresholds, LCP in synthetic tests.

### Rendering strategies

| Strategy | Pros | Cons |
| --- | --- | --- |
| CSR (client-side rendering SPA) | Simple hosting, rich interactivity | Slow first load (blank until JS runs), SEO challenges |
| SSR (server-side rendering) | Fast first paint, SEO | Server cost; hydration cost on the client |
| SSG / ISR (static generation, incremental regeneration) | CDN-fast, cheap | Stale content; build/regeneration complexity |
| Streaming SSR + Server Components | Progressive rendering, less client JS | Framework complexity (Next.js App Router, Remix) |
| Islands / partial hydration (Astro) | Minimal JS for content sites | Less suited for app-like UIs |

Choose per page type: marketing/content pages static or SSR; authenticated dashboards CSR or SSR with streaming.

### Backend contributions (often the biggest wins)
* TTFB budgets for HTML/API responses (e.g. p75 < 200 ms server time); profile slow endpoints and N+1 queries.
* **Compression** at the server or edge (Spring Boot: `server.compression.enabled=true` for JSON/text, or offload to CDN).
* **HTTP caching** for API responses that are cacheable per user (`private, max-age=60`) or public (CDN).
* **Early hints** (HTTP 103) to start fetching critical assets while the server computes the page.
* Avoid huge JSON payloads — paginate and project fields; large responses hurt both network and main-thread parse time.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I optimize for Core Web Vitals — LCP for loading, INP for responsiveness, CLS for visual stability — measured with real-user data at the 75th percentile and with lab tools for debugging. The levers are fast TTFB and CDN caching, less and split JavaScript, optimized and correctly sized images, eliminating render-blocking resources and request waterfalls, breaking long main-thread tasks, reserving layout space, choosing the right rendering strategy per page, and backend work like compression, HTTP caching and lean APIs.

**Must know:**
* LCP/INP/CLS thresholds and what affects each.
* Caching with hashed assets; CDN; compression.
* Image optimization and `fetchpriority`; preload/preconnect.
* Long tasks, Web Workers, framework re-render costs.
* Lab vs field data; CSR/SSR/SSG/streaming trade-offs.

**Common follow-ups:**
* Lighthouse score is 95 but users complain — why?
* How does the backend affect LCP?
* What causes layout shift?

**Red flags:** optimizing without measurement; lazy-loading the LCP image; shipping megabytes of JS for a static page.
