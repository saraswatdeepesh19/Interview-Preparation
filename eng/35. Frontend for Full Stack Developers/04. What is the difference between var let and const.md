# What is the difference between var let and const

---

## 🟢 Junior Level

JavaScript has three ways to declare variables:

- **`var`** — the old way (pre-ES2015). Function-scoped, hoisted and initialized as `undefined`, can be redeclared.
- **`let`** — block-scoped, can be reassigned, cannot be redeclared in the same scope.
- **`const`** — block-scoped, **cannot be reassigned**. (The object it points to can still be mutated.)

### Simple Real-World Analogy
`var` is a sticky note posted on the whole office (function): anyone in any room sees it. `let` is a note posted inside one room (block). `const` is a note laminated to a door — you cannot swap the note, but if it says "see the box" you can still change what is inside the box.

### Minimal example

```js
function demo() {
  if (true) {
    var a = 1;   // function-scoped
    let b = 2;   // block-scoped
    const c = 3; // block-scoped, no reassign
  }
  console.log(a); // 1
  console.log(b); // ReferenceError: b is not defined
}

const user = { name: 'Ann' };
user.name = 'Bob';      // OK: mutation
user = {};              // TypeError: Assignment to constant variable
```

### Rule of thumb
1. Default to `const`.
2. Use `let` when you must reassign (counters, accumulators).
3. Never use `var` in new code.

### Classic loop surprise

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0); // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j), 0); // 0 1 2
```
`let` creates a fresh binding per iteration; `var` shares one variable.

## 🟡 Middle Level

### Hoisting explained
Declarations are processed *before* code runs (in the creation phase of the execution context). What differs is initialization:

| Keyword | Hoisted? | Initial value | Access before declaration |
|---|---|---|---|
| `var` | yes | `undefined` | returns `undefined` |
| `let` | yes (binding exists) | uninitialized | `ReferenceError` (TDZ) |
| `const` | yes (binding exists) | uninitialized | `ReferenceError` (TDZ) |
| function declaration | yes | the function itself | works |
| function expression / arrow | depends on var/let/const | — | `TypeError` or TDZ |
| `class` | yes (TDZ) | uninitialized | `ReferenceError` |

The **Temporal Dead Zone (TDZ)** is the span from the start of the block until the declaration is executed.

```js
console.log(x); // undefined (var)
var x = 5;

console.log(y); // ReferenceError: Cannot access 'y' before initialization
let y = 5;

sayHi();                      // works: function declarations are fully hoisted
function sayHi() { console.log('hi'); }

sayBye();                     // TypeError: sayBye is not a function
var sayBye = function () {};
```

### Global object behavior
Top-level `var` and function declarations (in classic scripts) become properties of `window`; `let`/`const` do not. In ES modules, top-level declarations are module-scoped and never touch `window`.

```js
var g1 = 1; let g2 = 2;
console.log(window.g1, window.g2); // 1 undefined (in a classic script)
```

### `const` is about binding, not immutability
Use `Object.freeze` for shallow immutability, `structuredClone` for deep copies, and TypeScript `readonly`/`as const` for compile-time guarantees.

```js
const config = Object.freeze({ retries: 3, nested: { a: 1 } });
config.retries = 5;      // silently ignored (throws in strict mode)
config.nested.a = 2;     // works: freeze is shallow
```

### Redeclaration and shadowing

```js
var v = 1; var v = 2;    // allowed
let l = 1; let l = 2;    // SyntaxError

let s = 'outer';
{ let s = 'inner'; }     // shadowing is legal, often confusing; ESLint no-shadow
```

### Common mistakes
- Declaring `var` inside blocks and expecting block scope.
- Using `const` for values that change, then switching to `let` - fine, but not `var`.
- Relying on TDZ-free `typeof` — `typeof undeclared` is `"undefined"` but `typeof tdzVar` throws.
- Assuming `const arr = []` makes the array immutable.

## 🔴 Senior Level

### Engine view: scope chain and environments
Each execution context has a **LexicalEnvironment** (for `let`/`const`/class, per block) and a **VariableEnvironment** (for `var` and functions, per function). Identifier resolution walks the scope chain outward. V8 allocates variables on the stack when they are not captured by closures, and in a heap "context" object when captured — so excessive captured variables in hot paths can matter, but premature micro-optimization rarely does.

```js
function counter() {
  let n = 0;                 // captured -> heap context
  return () => ++n;
}
```

### Why TDZ exists
It catches use-before-define bugs and makes `const` semantically meaningful (a `const` could not safely be "undefined" first). It is also required for `class` declarations whose `extends` expressions may reference other bindings.

```js
function f(a = b, b = 1) {} // ReferenceError: parameters have TDZ too
f();
```

### Enforcing it with tooling
- ESLint: `no-var`, `prefer-const`, `no-use-before-define`, `no-shadow`, `no-redeclare`.
- TypeScript: `const` assertions narrow literal types; `readonly` arrays/properties communicate intent.

```ts
const roles = ['admin', 'user'] as const;   // readonly ['admin', 'user']
type Role = typeof roles[number];            // 'admin' | 'user'

function process(items: readonly string[]) {
  // items.push('x'); // compile error
}
```

### Production scenarios
1. **Legacy migration** (jQuery-era code): replacing `var` with `let/const` mechanically can change behavior where code relied on hoisting or function-scope leakage (e.g., a variable declared inside an `if` and used after it). Use codemods + test coverage; ESLint `block-scoped-var` finds the risky spots.
2. **Closures in loops** inside async callbacks — `let` fixes it, but also consider `Array.prototype.forEach/map` which gives per-call scope.
3. **Module singletons**: top-level `const` in an ES module is evaluated once per module instance; module-level mutable `let` state is shared across all importers and is a hidden global. In SSR, module-level mutable state leaks between requests — a real multi-user data-leak risk in Next.js/Node servers.

```js
// BAD in SSR: shared across all requests
let currentUser = null;
export function setUser(u) { currentUser = u; }

// GOOD: per-request context object
export function createContext(req) { return { user: req.user }; }
```

### Edge cases
- `switch` cases share one block; declare `let` inside `case` with braces.
- `const` in `for...of`: `for (const x of arr)` is fine (new binding per iteration); `for (const i = 0; i < n; i++)` throws on `i++`.
- Function declarations in blocks have legacy semantics in sloppy mode; use strict mode/modules.
- Global lexical environment: top-level `let x` conflicts with another script's `var x` -> SyntaxError.

## 🎯 Interview Cheat Sheet

**30-second pitch:** `var` is function-scoped, hoisted as `undefined`; `let` and `const` are block-scoped and live in a Temporal Dead Zone until declared. `const` prevents reassignment, not mutation. Default to `const`, use `let` when necessary, never `var`.

**Must-know bullets**
- Scope: function (`var`) vs block (`let`/`const`).
- TDZ throws `ReferenceError`; `var` yields `undefined`.
- Loop closures: `let` makes a binding per iteration.
- `Object.freeze` is shallow.
- Module-level mutable state is shared; dangerous in SSR.

**Common follow-up questions**
1. What is the output of the `var` loop with `setTimeout`, and how do you fix it?
2. Are `let` and `const` hoisted?
3. How to make an object deeply immutable?
4. Difference between function declaration and expression hoisting?

**Red flags**
- "`let` and `const` are not hoisted."
- Thinking `const` makes data immutable.
- Using `var` by habit in new code.
