# How to manage state in React

---

## 🟢 Junior Level

"State" in a React app comes in different kinds, and most state-management trouble comes from treating them all the same way:

| Kind | Examples | Where it should live |
| --- | --- | --- |
| **Local UI state** | Is the dropdown open? Current input text | `useState` in the component |
| **Shared UI state** | Theme, current user, sidebar collapsed | Context or a small store |
| **Server state** (cache of backend data) | Orders list, product details | A server-state library (TanStack Query, SWR, RTK Query) |
| **URL state** | Filters, page number, selected tab | The URL (query params / route params) |
| **Form state** | Field values, validation errors, dirty flags | Form library (React Hook Form) or local state |

### Lifting state up
When two siblings need the same state, move it to their closest common parent and pass it down as props:

```tsx
function OrdersPage() {
  const [statusFilter, setStatusFilter] = useState<Status | 'ALL'>('ALL');
  return (
    <>
      <StatusFilter value={statusFilter} onChange={setStatusFilter} />
      <OrderTable status={statusFilter} />
    </>
  );
}
```

## 🟡 Middle Level

### Server state: don't put it in a global store
Data from the backend has its own lifecycle: loading, errors, caching, staleness, refetching, deduplication, pagination, optimistic updates. TanStack Query models this:

```tsx
function useOrders(status: string) {
  return useQuery({
    queryKey: ['orders', { status }],                         // cache key
    queryFn: () => api<Order[]>(`/api/orders?status=${status}`),
    staleTime: 30_000,                                        // serve from cache for 30 s without refetching
  });
}

function OrderTable({ status }: { status: string }) {
  const { data, isPending, error } = useOrders(status);
  if (isPending) return <Spinner />;
  if (error) return <ErrorBanner error={error} />;
  return <Table rows={data} />;
}

// Mutation with cache invalidation
function useCancelOrder() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => api(`/api/orders/${id}/cancellation`, { method: 'POST' }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['orders'] }),
  });
}
```

Most apps that "needed Redux" mainly needed a server-state cache.

### Context for low-frequency shared state

```tsx
const AuthContext = createContext<User | null>(null);
export const useUser = () => useContext(AuthContext);
```

Every consumer re-renders when the context value changes — fine for rarely changing data (user, theme, locale), not for high-frequency state.

### URL as state
Filters and pagination in the URL (`/orders?status=PAID&page=2`) make views shareable, bookmarkable, and back-button friendly; read/write them with the router's search-param hooks.

## 🔴 Senior Level

### Global client state libraries
When real client-side global state exists (complex editors, multi-step wizards with cross-cutting state, offline-first apps):
* **Redux Toolkit** — predictable reducer-based updates, devtools time travel, middleware; RTK Query for server state. Good for large teams needing strict conventions.
* **Zustand** — minimal store with selector-based subscriptions (components re-render only when the selected slice changes).
* **Jotai/Recoil** — atomic state; fine-grained dependencies.
* **XState** — explicit state machines/statecharts for complex flows (checkout, onboarding) — impossible states become unrepresentable.

```typescript
// Zustand: components subscribe to slices
const useCart = create<CartState>()((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  clear: () => set({ items: [] }),
}));

const count = useCart((s) => s.items.length);   // re-renders only when the count changes
```

### Principles that scale
* **Single source of truth per piece of data**: don't copy server data into local state (it gets stale); derive views from the cache.
* **Normalize** relational data in client stores (entities by ID) to avoid inconsistent duplicates.
* **Immutable updates** — React detects changes by reference; mutating objects in place causes missed renders.
* **Colocate** state with the components that use it; lift only as far as necessary.
* **Optimistic updates** with rollback on error for snappy UX (TanStack Query `onMutate` / `onError`), and server reconciliation via invalidation.

### Full-stack considerations
* With server-side rendering/React Server Components, much "fetching state" moves to the server; the client holds only interactive state.
* Consistency with the backend: use ETags/versions in mutations (`If-Match`) to detect conflicts, and design APIs so the UI can refetch a resource after a change rather than reconstructing it.
* Real-time updates (SSE/WebSocket) should update or invalidate the server-state cache, not a parallel store.

## 🎯 Interview Cheat Sheet

**30-second pitch:** I classify state first: local UI state in `useState`, shared low-frequency state in context, server data in a server-state cache like TanStack Query, filters and pagination in the URL, and forms in a form library. Only genuinely global client state goes into a store such as Zustand or Redux Toolkit, or XState for complex flows. I keep one source of truth, update immutably, colocate state, and use optimistic updates with invalidation.

**Must know:**
* State categories and where each belongs.
* Lifting state up; context re-render behavior.
* TanStack Query: query keys, staleTime, mutations, invalidation.
* Redux Toolkit vs Zustand vs Jotai vs XState.
* Immutability, normalization, optimistic updates.

**Common follow-ups:**
* Do we need Redux?
* Why does the whole app re-render when the theme changes?
* How do you keep the UI in sync after a mutation?

**Red flags:** copying API responses into Redux and manually syncing them; one giant context for everything; mutating state.
