# What are npm Vite and Webpack

---

## 🟢 Junior Level

The frontend toolchain has two layers:

* **Package managers** — **npm** (bundled with Node.js), **pnpm**, **Yarn**: install dependencies from the npm registry into `node_modules`, run scripts, manage versions. The JavaScript equivalent of Maven's dependency management.
* **Build tools / bundlers** — **Vite**, **webpack**, Rollup, esbuild, Rspack, Turbopack: transform source (TypeScript, JSX, CSS), resolve imports, bundle and optimize files for the browser, and run a dev server with hot reload. Roughly the equivalent of the Maven build lifecycle + compiler plugins for the frontend.

```json
// package.json
{
  "name": "storefront",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "test": "vitest run",
    "lint": "eslint ."
  },
  "dependencies": { "react": "^18.3.1", "react-dom": "^18.3.1" },
  "devDependencies": { "vite": "^5.4.0", "typescript": "^5.6.0", "@vitejs/plugin-react": "^4.3.0" }
}
```

`npm install` resolves versions (`^18.3.1` = any 18.x ≥ 18.3.1) and writes **`package-lock.json`**, which pins exact versions for reproducible installs; `npm ci` installs exactly from the lockfile (use it in CI).

## 🟡 Middle Level

### Vite vs webpack

| | Vite | webpack |
| --- | --- | --- |
| Dev server | Serves native ES modules; transforms files on demand with esbuild → near-instant startup and HMR | Bundles the app before serving; slower startup on large apps |
| Production build | Rollup-based (Rolldown in newer versions), tree-shaking, code splitting | Own bundler, extremely configurable |
| Configuration | Minimal, sensible defaults | Powerful but verbose (loaders, plugins) |
| Ecosystem | Default for new React/Vue/Svelte projects | Huge legacy ecosystem; Next.js historically, Angular CLI previously |

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: { '/api': 'http://localhost:8080' },   // same-origin dev setup: no CORS with the Spring Boot backend
  },
  build: { outDir: 'dist', sourcemap: true },
});
```

### What a production build does
* **Transpile** TypeScript/JSX to browser-compatible JavaScript.
* **Bundle** modules into a few files; **code-split** by route (`import()`), so users download only what they need.
* **Tree-shake** unused exports, **minify**, and add **content hashes** to filenames (`index-3f9a1c.js`) for long-term caching (`Cache-Control: max-age=31536000, immutable` on hashed assets; no-cache on `index.html`).
* Process CSS (PostCSS, CSS modules), optimize assets.

### Serving the build from Spring Boot (one deployable)
Build the frontend in the Maven/Gradle build (e.g. `frontend-maven-plugin` runs `npm ci` and `npm run build`) and copy `dist/` to `src/main/resources/static` — Spring Boot serves it, and `/api` lives on the same origin. Add a fallback so client-side routes (`/orders/42`) return `index.html`.

## 🔴 Senior Level

### Dependency management at scale
* **Lockfiles are mandatory**; `npm ci` in CI; pin the Node version (`.nvmrc`, `engines`, Volta) for reproducible builds.
* **pnpm** uses a content-addressed store and symlinks — faster installs, less disk, and strict dependency resolution (no accidental access to undeclared transitive deps). Workspaces (pnpm/npm/Yarn) and tools like Nx/Turborepo manage frontend monorepos with affected-only builds and caching.
* **Supply chain risk**: npm packages can run install scripts; typosquatting and compromised maintainers happen (event-stream, ua-parser-js incidents). Mitigate with `npm audit`/Snyk/Dependabot, lockfile review, `--ignore-scripts` where possible, a private registry proxy (Artifactory/Nexus/Verdaccio) and provenance checks (`npm audit signatures`).

### Bundle performance
* Analyze bundles (`rollup-plugin-visualizer`, `webpack-bundle-analyzer`) — common culprits: whole icon libraries, moment.js locales, lodash imported as a whole, duplicated dependency versions.
* Route-level code splitting and lazy loading of heavy components (charts, editors).
* Set **performance budgets** in CI (max JS per route, e.g. 170 KB compressed for critical path).
* Modern output targets (ES2020+) to avoid shipping polyfills to modern browsers.

### Build tool landscape trends
* Native-speed tooling written in Go/Rust: **esbuild**, **SWC**, **Rspack** (webpack-compatible), **Rolldown** (Rust Rollup replacement in Vite), **Turbopack** (Next.js). The motivation is the same as Gradle's build cache/incremental compilation: fast feedback on large codebases.
* Type checking is separated from transpilation (esbuild/SWC strip types without checking), so `tsc --noEmit` must run in CI.

## 🎯 Interview Cheat Sheet

**30-second pitch:** npm (or pnpm/Yarn) manages JavaScript dependencies with semver ranges pinned by a lockfile, installed reproducibly with `npm ci`; build tools like Vite and webpack transpile TypeScript and JSX, bundle, code-split, tree-shake, minify and hash assets, and run dev servers with hot reload. Vite serves native ES modules in development and uses Rollup for production; webpack is the configurable veteran. For full-stack Java apps I proxy `/api` in dev and serve the built assets from the same origin.

**Must know:**
* `package.json`, semver ranges, lockfile, `npm ci`.
* Vite vs webpack dev and build models.
* Code splitting, tree-shaking, content hashing and caching headers.
* Dev proxy to Spring Boot; SPA fallback routing.
* Supply-chain risks and mitigations; bundle analysis; budgets.

**Common follow-ups:**
* Why is our bundle 3 MB?
* `npm install` vs `npm ci`?
* How do you deploy a SPA with a Spring Boot backend?

**Red flags:** no lockfile; `npm install` in CI; caching `index.html` forever.
